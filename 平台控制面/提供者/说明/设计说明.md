# 提供者 设计说明（平台控制面.提供者）

## 为什么这样切

`平台控制面/提供者/` 是平台控制面里**真实系统能力**的落点：HTTP 回环服务、进程与
进程组、资源硬限制、资源采样、控制面对账、版本兼容、治理面专属依赖审计。
这 21 个模块原先只有目录、没有包声明，调用方（开发工具门禁）只能 import 实现——
治理层 0 个包声明时，依赖防火墙口径下这就是越层。

本包把其中**能跨能力边界表达**的三件事收成公开能力，其余模块保留为包内实现：

| 对外能力 | 承载本体 | 为什么对外 |
| --- | --- | --- |
| `采样资源` | `采样器.py` | 资源监督报告需要真实的进程内存/句柄/临时空间数值，调用方不该自己读 `getrusage` |
| `审计平台控制面` | `防火墙审计.py` | 治理面专属依赖防火墙（动态导入/反射导入/深入实现目录/直连外部服务）是发布前的静态门禁，可跨边界表达 |
| `只读激活指针` | `控制面对账.py` | 控制面停机期间，已激活调用面需要不依赖控制面服务、只读取激活指针继续工作 |

## 管什么

- 资源采样：内存峰值（`getrusage`）/文件句柄（`/proc/self/fd` 或 `/dev/fd`）/临时空间字节，并合并资源监督执行单元峰值。
- 治理面审计：对目标目录（留空即平台控制面目录）逐文件 AST 判定四类规则，返回违规条数、文件数与清单。
- 只读激活指针：只读打开权威状态库取激活指针（`指针id/目标/版本/栅栏令牌/状态`），未命中如实返回 `是否命中=false`。

## 不管什么

- **不重复登记子包能力**：`动态库提供者`（`调用动态库`/`可用库列表`/`宿主可用性`）与
  `注册表`（`登记提供者`/`调用提供者`/`查询提供者`/`卸载提供者`）已各自持有包声明与
  注册函数，本包不代管、不重复登记——同一机制两套能力即缺陷。
- **不凑能力数**：`会话恢复` 需要调用方注入授权服务句柄、`版本兼容`（推进/回退）需要
  状态+快照+发布管理三个句柄、`超时治理` 需要资源监督器句柄、`进程提供者`/`进程组管理`
  持有真实子进程与端口生命周期——这些跨能力边界不可表达或不具备幂等只读语义，
  一律保留为包内实现，不用占位参数硬包一层。
- **不做默认值兜底、不做静默降级**：参数形态不符、目录不可用、权威状态库不可用一律
  返回带错误码的明确失败；采样失败如实标注（内存/句柄/临时空间任一失败即不报成功）。

## 与子包的关系

本包是 `平台控制面/提供者/` 的顶层声明；`注册表/` 与 `动态库提供者/` 是**独立成包的
子域**（各自有 `包声明.json` 与 `能力定义.json`），能力 id 分别是
`平台控制面.提供者.注册表.*` 与 `平台控制面.提供者.动态库提供者.*`，
本包的 `包声明.json` 只声明 `平台控制面.提供者.*` 三条能力，不越权登记子包能力。

## 已知边界（如实记录，未在本包解决）

`防火墙审计.py` 的第三类规则「任何导入不得深入实现目录」与正式包的标准入口写法
（入口 `__init__.py` 依赖同包 `实现/` 下的能力实现层）在当前口径下相互冲突：
兄弟面（`平台状态`/`发布管理`/`授权`/`备份恢复`）的入口同样如此。该冲突属治理面
审计规则与正式包入口规范之间的口径问题，不在本包范围内单方面改动。
