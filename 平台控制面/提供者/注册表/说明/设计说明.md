# 提供者注册表 设计说明（平台控制面.提供者.注册表）

## 为什么这样切
平台需要一条「注册 → 授权 → 资源监督 → 真实执行 → 证据」的提供者链：
外部提供者经 `注册()` 建立**有界执行单元**（信号量/超时/释放），经 `调用()`
统一执行并追加调用证据。这条链只有一处实现（本包），不新增第二条执行腿。

## 管什么
- `登记提供者`：校验预算声明（10 项）→ 建执行单元 → 登记调用函数 → 追加注册证据。
- `调用提供者`：真实执行 + 有界（信号量/超时）+ 调用证据；未登记即失败。
- `查询提供者` / `卸载提供者`：登记态只读查询、卸载并优雅停止执行单元。

## 关键设计：提供者在能力面上表达为「对目标能力的委托」
调用函数是**进程内可调用对象**，跨能力边界不可表达（不能进 JSON、不能进网关）。
若把「注册任意 Python 可调用对象」做成能力，等于给外部开一条绕过能力治理的
执行口子（与第 26 条能力唯一权威冲突）。因此本包的能力面只接受**目标能力id**：
委托函数经唯一能力调用入口按能力 id 调用目标能力，真实执行仍经资源监督器的
有界执行单元，失败（含目标能力失败）一律透传，不伪绿。

## 不管什么
- 不做能力发现/装配（那是运行核心与加载器的事）。
- 不缓存能力实现、不绕过唯一能力调用入口直接 import 目标实现。
- 不静默降级：调用入口不可用、预算不合法、未登记，全部明确失败。

## 失败如何表达
`参数不合法` / `存储目录不可用` / `注册被拒绝` / `提供者未登记` / `调用失败`
（目标能力自身错误码在委托结果里原样返回，不吞不换）。

## 相对安全口径
本包允许调用方登记并调用**任意已装配能力**（做不到能力白名单），这是
**相对安全**而非绝对边界：护栏是预算校验 + 有界执行 + 全量证据；用户对
登记哪些能力有绝对自主权，平台只守「不造成系统性破坏」这条底线。
