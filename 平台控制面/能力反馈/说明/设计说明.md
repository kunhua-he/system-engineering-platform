# 能力反馈（平台控制面.能力反馈）设计说明（设计权威）

> 本文是本包的**设计哲学与边界权威**：它为什么存在、管什么、不管什么、失败如何表达。
> 调用口径——能力、参数、返回结构、错误码与调用示例——以同目录 `使用说明.md` 为准（由能力契约生成）。
> 两份说明都计入包指纹，任何改动都要升包版本。

## 为什么有这个包

决策记录 `0012_装配根声明式化与平台治理能力面` 的待办「波2：给平台控制面/运行核心的功能面补正规包」
未完成时，`平台控制面` 与 `运行核心` 下 0 个 `包声明.json`：治理层功能面进不了装配表，
能力注册表里调不到，于是治理工具只能**直接 import 实现**（依赖防火墙按层判定即为越层）。
本包是这一治理动作的批次 A 试点：把反馈治理面补成**正式包**，让反馈动作可从能力注册表调到。

正式根清单的唯一事实源是 `公共契约/正式根.py`：`平台控制面` 已在其中，根内**含 `包声明.json` 才参与发现**，
所以补包本身就是「进装配」的动作，不需要改发现器、不需要把 `平台控制面` 加进任何允许依赖表。

## 本包是什么

反馈治理面的**对外动作收口**，事实唯一落 `平台控制面/平台状态.py`（权威状态库）：

| 能力 | 做什么 | 事实落点 |
|---|---|---|
| `登记能力反馈` | 运行时诊断反馈的登记：必填字段/契约版本格式/能力存在/大小上限校验，按去重键幂等 | `能力反馈` 专表 |
| `查询能力反馈` | 只读查询（反馈id/状态/能力id 过滤，公开字段） | `能力反馈` 专表 |
| `迁移能力反馈状态` | 8 态状态机迁移：合法性校验、已修复必须带验证证据与发布制品、状态版本条件更新 | `能力反馈` 专表 + `证据` 账本 |

三条能力对应的是**治理面对外需要的反馈动作**，不是按目录或函数拆的：反馈服务的公开方法只有登记/查询/状态迁移三个，
能力划分与「调用方真正需要什么」一一对应，不为凑数拆能力，也不把 8 态状态机里的每个状态做成一条能力。

## 本包不是什么

- **不重写反馈语义**：字段校验、脱敏、摘要上限、去重键、状态机仍在同目录 `反馈服务.py`；
  本包只加一层「能力边界」——参数校验、存储目录缺省、能力存在判定装配、统一结果归一。
- **不拥有开发反馈的能力面**：`开发反馈服务.py` 的开工id 五字段反馈与升级候选通道是另一条腿
  （对象不同，按第 1 条 3 项不构成重复），本批只把运行时诊断反馈补成能力，开发反馈的能力面留待后续批次。
- **不做静默降级**：能力核不可用时 `登记能力反馈` 明确返回 `能力校验不可用` 并带原因，
  **绝不**退回「不校验即放行」（放行等于任意能力 id 都能写反馈，正是旧 `mcp_feedback` 的自证绕过缺口）。

## 存储目录与能力存在判定的归属

- **存储目录由调用方按部署配置传入**：能力参数 `存储目录` 显式暴露，缺省才取平台默认目录
  （`工程缓存/平台控制面`）。这样网关能把 `反馈状态目录` 配置继续传进来，不把调用方的缓存根硬编进能力层。
- **能力存在判定不硬编码**：默认判定经**唯一能力调用入口**取注册表（`获取唯一调用服务().注册表.能力id列表`），
  与收敛前网关自查的是同一份注册表；解析失败即 fail-closed 并给出原因。
  包内亦提供 `设置能力存在判定`（唯一注入点），供验证场景注入固定判定，避免能力实现自己造第二套注册真相。

## 版本与漂移

`包声明.json` / `能力定义.json` / `完整性摘要.json` 三者的版本必须一致；
新增能力、改参数或改返回结构都要升包版本、重跑契约编译器并重算完整性摘要。
`__init__.py` 是**手写入口**（编译器识别到含 `注册能力` 即不覆盖），改动同样要计入摘要。
