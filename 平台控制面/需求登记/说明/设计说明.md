# 需求登记（平台控制面.需求登记）设计说明（设计权威）

> 本文是本包的**设计哲学与边界权威**：它为什么存在、管什么、不管什么、失败如何表达、
> 旧路径怎么兼容。调用口径——能力、参数、返回结构、错误码与调用示例——以同目录
> `使用说明.md` 为准。
> 两份说明都计入包指纹，任何改动都要升包版本。

## 为什么有这个包

`平台控制面/需求登记.py` 原来是一份**平铺服务文件**：目录里没有 `包声明.json`、
没有任何能力 id，于是这个"一切需求闸门的唯一前置"在**能力注册表里完全看不见**——
全仓搜能力 id 含「需求」= **0**（审计 `审计_能力化缺口_20260916` A1）。

后果是三条真实断点：

1. **发布门禁 3 项检查无法能力化**（`平台-空需求id阻断`／`平台-未确认需求阻断开发`／
   `平台-需求确认后开发放行`）：它们必须先拿到 `需求id`，而"登记需求"没有能力 id，
   网关 `capability_call` 根本无法登记/确认需求；
2. **`平台控制面/统一入口.py` 的 3 个稳定操作**（确认需求／装配计划／创建组件）闸门
   全部压在它身上，而能力面只暴露了 `执行稳定操作`/`查询稳定操作表` 两条壳；
3. **`平台控制面/能力反馈/开发反馈服务.py` 跨包直连**它的类（升级候选通道）。

`平台控制面` 已在 `公共契约/正式根.py` 的正式根清单里，**根内含 `包声明.json` 才参与发现**，
所以补包本身就是「进装配」的动作：不需要改发现器、不需要把 `平台控制面` 加进任何允许依赖表。

## 本包是什么

需求治理面的**对外动作收口**，事实唯一落既有 `需求登记` 服务（`平台状态` 权威状态库）：

| 能力 | 覆盖的既有动作 | 事实落点 |
|---|---|---|
| `登记需求` | `需求登记.登记需求` | `需求` 表 + `证据` 账本 |
| `确认需求` | `需求登记.确认需求` | `需求` 表确认状态 + `证据` 账本 |
| `查询需求` | `需求登记.查询需求`（新，只读）／`需求登记.需求已确认`／`需求登记.查询工作包` | 只读 `需求`/`工作包` 表 |
| `登记装配计划` | `需求登记.生成装配计划`／`需求登记.保存工作包` | `需求` 表装配计划字段 + `工作包` 表 |

**为什么是四条、不是六条**：能力划分对应"调用方真正需要什么"，不是按目录或函数拆——

- `需求已确认`（布尔判定）不单列：它是 `查询需求` 返回里的 `是否已确认` 字段，
  单列等于把一次读取拆成两条能力；
- `查询工作包` 不单列：工作包是需求聚合的一部分（按 `需求id` 归属），
  由 `查询需求` 的 `包含工作包=true` 返回；
- `保存工作包` 不单列：它与 `生成装配计划` 共用同一份 `工作包表` 入参，
  合并为 `登记装配计划` 的 `落工作包` 开关（见下"两处加法"）；
- 也不把 `需求` 表的每一列做成一条能力（那是表结构，不是动作）。

## 本包不是什么

- **不重写需求语义**：快照不可变、版本递增、确认幂等、波次冲突判定、工作包写盘仍在
  同目录 `需求服务.py`（本次包化由平铺文件 `平台控制面/需求登记.py` **逐字迁入**，
  类名仍为 `需求登记`，全部既有方法与其行为一字未改）；
  本包只加一层「能力边界」——参数校验、存储目录缺省、统一结果归一。
- **不产生第二套实现、也不留转发壳**：旧路径 `from 平台控制面.需求登记 import 需求登记`
  由本包 `__init__.py` **重新公开同一个类**，所以旧路径逐字可用，
  既没有第二份需求服务，也没有"1 行转发"的空壳模块（第 3 条"不留壳"）。
- **不做静默降级**：状态库不可用、快照写入失败、波次冲突、工作包形状不全都返回
  明确失败结果与稳定错误码，绝不在失败时"假装成功"或退回不写。

## 两处加法偏离（键只增不减，已在能力定义与说明书写明）

1. **`查询需求`：新增只读方法**（`需求服务.查询需求`）。原服务只有
   `需求已确认`(bool) 与 `查询工作包`，没有"读需求记录"的公开入口；包化把
   `读取记录`/`查询记录` 这两个既有调用收在服务里，语义零新增（未命中返回空列表，
   不伪造记录），不构成第二套实现。
2. **`登记装配计划`：`落工作包` 开关（逻辑型，默认 `false`）**。默认 `false` 与收敛前
   `生成装配计划` 逐字一致（只落装配计划，`统一入口._装配计划` 的口径不变）；
   `true` 时额外把 `工作包表` 每项逐条交给**同一个** `需求服务.保存工作包` 落盘
   （等价收敛前 `保存工作包`，`示例项目/稳定平台完整示例` 的用法）。
   `true` 时**先校验全部工作包形状**（必须给齐 波次/说明/输入快照/允许修改路径/
   能力占用/资源预算/验收命令）再动任何写，避免"计划已落、工作包半落"。

## 需求闸门与稳定错误码

门禁口径**逐字保持**，只是把两份口径的对应关系收在 `需求错误码.py` 一张表里：

| 中文域错误码（本包返回） | 平台稳定码 | 触发条件 |
|---|---|---|
| `需求id不能为空` | `REQUIREMENT_REQUIRED` | 空需求id（`统一入口.py` 4 处同码） |
| `需求不存在` | `REQUIREMENT_UNCONFIRMED` | 需求不存在或未确认（旧文案把两者并成"需求未确认或不存在"） |

- 失败结果同时带 `详细信息.稳定错误码`，调用方不必再猜；
- `参数不合法` / `需求登记失败` / `需求查询失败` / `装配计划生成失败` / `工作包登记失败`
  一并登记在同一张表（`INVALID_PARAMETER` / `REQUIREMENT_REGISTER_FAILED` / …），
  不散落到各调用方各写一份；
- **不越权替调用方做闸门**：本包只回答"这条需求在不在、确认没有"，
  "禁止开发/发布放行"的判断仍在门禁与策略中心（口径不变）。

## 存储目录与项目id 的归属

- **存储目录由调用方按部署配置传入**：能力参数 `存储目录` 显式暴露，缺省才取平台默认目录
  （`工程缓存/平台控制面`）——与 `平台控制面.平台状态` / `平台控制面.能力反馈` 同口径，
  不把调用方的缓存根硬编进能力层；
- **项目id 固定 `平台控制面`**：与 `统一入口.统一能力服务` 构造 `平台状态` 时的取值一致
  （`平台状态(存储目录, 项目id="平台控制面")`），保证能力面与调用方读写**同一个状态库身份**。

## 版本与漂移

`包声明.json` / `能力定义.json` / `完整性摘要.json` 三者的版本必须一致；
新增能力、改参数或改返回结构都要升包版本、重跑契约编译器并重算完整性摘要。
`__init__.py` 是**手写入口**（编译器识别到含 `注册能力` 即不覆盖），改动同样要计入摘要。
