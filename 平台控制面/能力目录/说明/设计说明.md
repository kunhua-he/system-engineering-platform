## 本包是什么

平台控制面的**能力目录面**，把两件事切成可经唯一网关调用的公开能力：

1. **消费者契约注册表**——能力被谁消费、消费方要求什么（请求/响应约束、错误码、超时、释放要求），以及当前契约相对登记契约是否漂移；
2. **文件租约**——多会话/多子代理并行改同一仓库时，按项目根相对路径原子认领文件，防止两个写者改同一个文件。

事实唯一落盘在包内的存储文件（消费者契约表、租约表），本包只做边界校验、原子写读与结果归一。

## 本包不是什么

- **不实现契约校验算法与发布门禁的判定逻辑**：本包只回答「有没有漂移」「是否阻断」，真正的门禁接线在 `开发工具/发布门禁/`。
- **不做文件锁**：租约是**协作式约定**（登记 + 心跳 + 过期回收），不是操作系统级排他锁；绕过租约直接改文件，本包无法阻止。
- **不管项目业务语义**：只处理「路径 / 能力 id / 消费者 id」这类通用标识，不认识任何业务项目。
- **不管能力的注册与路由**：能力注册表在 `运行核心`，本包只登记「消费者对能力的契约」。

## 管什么 / 不管什么

| 管 | 不管 |
|---|---|
| 消费者契约的登记、查询、删除（覆盖写、幂等） | 契约内容的合法性判定标准从哪来（那是消费者自己的事） |
| 契约漂移判定与门禁判定（只给结论 + 漂移列表） | 漂移后怎么修、要不要阻断发布（发布门禁决定） |
| 文件租约的申请、续租、释放、过期回收、查询 | 进程存活探测（由 `系统核心支持库.进程管理` 提供） |
| 路径越界拒绝（项目根为界） | 项目根由谁指定（调用方传参） |

## 为什么这样切

**理由一：契约漂移必须是「可查询的事实」，不能只存在于发布时的一次性检查。**
把「登记契约」与「判定漂移」拆成两个能力，是为了让漂移可以**随时查**（查询是只读、幂等、零副作用），而不必等到发布门禁跑起来才知道违约。发布门禁只用 `判定契约门禁` 这一个出口取结论。

**理由二：文件租约与消费者契约同包，因为二者共用同一套「单文件互斥存储」。**
两者都需要「同一时刻只有一个写者、写读可并发」，共用 `单文件互斥存储.py`，避免各写一套原子写。**注意这不是把两件事混为一谈**：契约表按「消费者id + 能力id」索引，租约表按「路径」索引，互不干扰。

**理由三：空 id 一律失败，不许返回空结果。**
`查询消费者契约` 空 id 会命中空表，`判定契约门禁` 空 id 会得到「不阻断」——两者都是**假证据**（看起来正常，实际什么都没查）。因此本包对必填标识一律硬失败，宁可报错也不给空结论。这是「失败即失败，不静默成功」在本包的具体落法。

## 「公开能力必须有登记」的反向断言（2026-09-18 新增）

**病根（哲学 14.1 归因② 架构错位）**：漂移门禁原先只问「**已登记**的契约有没有漂移」，
而**没有登记**的能力根本不参与对比——于是登记表为 0 份时，门禁对全部真实包恒放行。
现场实测：`find . -name "消费者契约*.json" -not -path './工程缓存/*' | wc -l` = **0 份**，
而全仓跨包消费者关系真实存在 119 条（依赖声明口径）。

**补的是「反向」那半件**：`判定消费者登记完整性` 现场枚举跨包消费者关系
（证据 = 消费者包 `包声明.json` 的 `依赖` + 提供包 `能力定义.json` 的能力面），
逐条核对有没有登记；缺一条即 `是否阻断=True`。判定事实一律**现场枚举**，
不接受外部传入的判据——传进来的判据就是自造样例自证。

**契约字段全部逐字取自声明面，不造值**：请求参数列表/示例、响应约束返回键/结构、
错误码集来自 `能力定义.json` 与 `能力契约/参数契约.json`；超时取提供包
`资源预算.json` 的 `单次调用超时`（能力声明面**没有**能力级超时字段，凭空造一个
就是假证据）；释放要求取 `行为.资源释放` 原文。**取不到的字段一律按「没有登记」
处理**（fail-closed）——判不出就必须报红，不许当通过。

**口径边界**：包内自消费不算消费者契约要管的关系（契约管的是跨边界承诺）；
验证场景里的调用步只是交叉核对证据，不单独构成登记义务（把「测试怎么调」
升格成「对外承诺」会把登记表撑成噪声）。存量与新增按 `消费者关系基线.json` 分治
（与 `公开调用完整性门禁存量基线.json` 同一套路：基线内只报、基线外判红、
基线读不成全量判红）。

## 失败如何表达

统一结果（成功 / 值 / 错误码 / 错误说明）。本包的错误码只列实现里真实存在的：

| 错误码 | 触发条件 |
|---|---|
| `参数不合法` | 必填参数缺失、类型不符、契约结构不齐备 |
| `契约非法` | 契约结构不齐备（缺请求/响应约束等必需项），错误说明回带问题原文 |
| `未登记` | 删除一个未登记的消费者契约绑定（失败即失败，不静默成功） |
| `路径越界` | 租约申请中包含项目根之外的路径，**整批硬失败**，不做部分认领 |
| `文件已被占用` | 租约申请中任一文件被活跃租约占用，**整批失败**，回带占用者与占用开始时间 |
| `租约不存在` | 续租已过期或已释放的租约（已结束的租约不能复活） |

**幂等口径**：释放与回收是幂等的——重复释放回「已结束且已释放」，重复回收第二次回带空清单且不报错。**续租不是幂等的**：对已结束租约续租必须失败，否则会出现「复活一条假活跃租约」的脏状态。

## 与发布门禁的接线（本批只做判据，接线落在 `开发工具/`）

按任务边界，本批**只**改 `平台控制面/能力目录/`，所以「公开调用完整性门禁」的接法
在这里写明，由持有 `开发工具/` 的批次落地（两处，都是加检查项，不改既有判据）：

1. **`开发工具/公开调用完整性门禁.py`**：在主程序里加一个检查项，直接复用本包
   `消费者登记判定.判定登记完整性带基线`（`参考目录` 传本包目录，读
   `消费者关系基线.json`），`通过=False` 即计入违规清单并让退出码为 1。
   基线读不成时该函数自己返回 `通过=False`（fail-closed），门禁不需要再兜。
2. **`开发工具/发布门禁/运行发布门禁.py`** 的 `第十四阶段门禁._项1_消费者契约漂移`：
   该项现在只跑「登记 → 正向放行 → 篡改阻断」，**没有断言「登记表不许为空」**，
   所以它在空注册表下照样绿。接法是把该项的反向证据补一条：用空存储目录跑一次
   `判定消费者登记完整性`，断言 `是否阻断=True` 且 `缺登记关系数 == 总关系数`
   （即「0 份登记必须报红」本身就是一条反向证据）。

**为什么不把基线判据直接放进本包的能力里当默认**：能力是给调用方用的判据面，
基线属于**门禁的存量分治配置**（与 `公开调用完整性门禁存量基线.json` 同一性质）。
能力默认返回**全量事实**（缺一条就 `是否阻断=True`），是否按基线分治由门禁决定——
这样「判据」与「存量策略」不混在一处，门禁换分治口径也不用改能力。

## 生命周期覆盖

- **存储初始化**：首次调用时惰性创建存储文件，不要求预先初始化。
- **登记/删除**：覆盖写与幂等删除，不留半成品记录。
- **租约过期**：`回收过期文件租约` 按心跳超时判定并置为已过期；**不自动后台回收**（无守护线程），需调用方按周期显式调用——这是刻意的：本包不持有任何长驻资源。
- **进程退出**：无句柄、无子进程、无线程，退出不留下需要释放的运行态。

## 改能力参数的两条铁律（来自 2026-09-21 一次真实「整包消失」）

1. **`__init__.py` 的参数名序必须与契约（`能力定义.json` → 派生 `能力契约/参数契约.json`）逐字逐序一致。**
   实测：给 `查询文件租约` 加两个参数时，`能力定义.json` 把新参数插在 `含现场指纹` **之前**、
   `__init__.py` 的 `_参数契约表` 加在**之后** → 装配器 fail-closed 拒**整包**
   （`平台控制面.能力目录` 14 个能力一起消失），而 MCP 侧只看到「能力未注册」，
   真原因只写在 `/tmp/网关40007.err` 的 `[装配告警]` 里。
   **参数事实源只有契约一处，入口不得另立一份**（哲学 12.1）；顺序不一致就是违约，不是风格问题。
   自检姿势：`rg -n '"平台控制面.能力目录.<能力名>"' __init__.py` 拿到入口名序，
   与 `能力契约/参数契约.json` 里同能力的 `参数` 数组逐字对齐。
2. **`能力定义.json` 是 JSON 文件，布尔写 `true`/`false`，不是中文 `真`/`假`。**
   中文 `真/假` 只在 `.py` 里用（`from 公共契约.基础类型.逻辑类型 import 真, 假`）。
   写错时编译器报 `能力定义 JSON 解析失败: Expecting value: line N column M` ——
   列号就落在那个中文布尔上。
