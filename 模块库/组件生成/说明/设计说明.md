# 组件生成（模块库.组件生成）设计说明（设计权威）

> 本文是该模块的**设计哲学与边界权威**：为什么这样切、管什么、不管什么、失败如何表达。
> 调用口径——参数、返回结构、错误码与调用示例——以同目录 `使用说明.md` 为准。
> 两份说明都计入包指纹，任何改动都要升包版本。

- 包id：模块库.组件生成
- 版本：1.0.0
- 公开能力：`组件生成.生成模块脚手架`（1 个原子能力）

## 一、为什么有这个模块（第 32–36 条）

起因：真实生成器 `开发工具/组件规范/模块模板生成器.py` 原来**只能由 MCP 工具
`generate_module_template` 调用**（`MCP工具箱/项目服务.py:833` 是全仓唯一生产调用点），
且**没有 CLI**（模块里唯一的 `__main__` 命中是它生成的测试骨架字符串）。按第 32 条归因：
不是「做不到」，而是**底座缺一个正规原子能力**——调用方（其他 Agent、其他项目、HTML 黑盒、
后台任务）无法经唯一入口 `调用能力(能力id, 参数)` 生成脚手架。按第 33/34 条，它属于
**模块库**（组合能力完成一类流程），故新建 `模块库/组件生成/`，对外只暴露一个原子能力。

## 二、分层选择与理由（关键决策，写清依据）

| 事项 | 选择 | 依据 |
| --- | --- | --- |
| 脚手架内容（模板文本） | **复用** 唯一模板实现 `开发工具/组件规范/模块模板生成器.生成模块模板`，不重写 | 第 26 条「能力唯一权威，杜绝旁路」：全仓只能有一套模板；再写一套就是第二套实现。模板生成器是**纯文件工具**（`开发文档/规范/新建支持库与模块指南.md` 第七节：纯文件工具不调能力），本身不构成第二条调用腿 |
| 路径边界校验 | 经 **支持库公开能力** `系统核心支持库.路径安全.校验路径` | 第 12 条：最小原子能力（防穿越/符号链接逃逸）归支持库，已存在就不新写；模块只做「传哪个相对路径」的决策 |
| 存在性探测 / 生成后文件清单 | 经 **支持库公开能力** `文件系统支持库.文件操作.判断存在`、`文件系统支持库.文件操作.搜索文件` | 第 12 条：文件系统原子操作归文件系统支持库；模块不自己 `os.walk`，也不复制一套遍历 |
| 是否把生成器「下沉」为支持库能力 | **不下沉** | 生成器只写文件、不调能力、无第三方边界，不具备支持库「第三方/系统边界 + 参数与错误转换」的职责；下沉会新增一层无收益的转发，且改动 `支持库/**` 超出本次允许修改目录。现状做法＝模块薄门面复用唯一生成器，层数更少、失败面更小 |
| 写入范围 | **只允许** `项目根/模块库/<模块名>/` 与 `项目根/测试中心/模块库/测试_<模块名>.py` | 第 33 条：能力最小且边界明确；调用方声明项目根，能力不替调用方猜目标 |

调用链（唯一调用腿，第 4 条）：

```text
调用能力(组件生成.生成模块脚手架, 参数)
  → 模块实现：参数校验 → 路径边界校验（支持库能力）→ 复用唯一生成器 → 文件清单（支持库能力）
  → 统一结果（成功/值/错误码/错误说明）
```

## 三、第 37 条：现状做法 ↔ 候选架构 对比（做新功能前先问架构）

| 方案 | 层数 / 步骤 | 失败面 | 边界 | 结论 |
| --- | --- | --- | --- | --- |
| **现状做法（本模块）**：模块薄门面 + 复用唯一生成器 + 支持库原子能力做边界与清单 | 1 次调用；模块内 4 步（校验→边界→生成→清单） | 生成器内部异常在模块内被捕获转 `生成失败`；复用同一份模板口径，模板改动自动跟随 | 写入固定在项目根内两处；越界提前拒绝，不产生半成品 | **采用** |
| 候选 A：模块内重写一套脚手架生成（复制模板文本） | 步骤数相同 | **多一套模板**：模板一改就要改两处，口径必然漂移；且违反第 26 条 | 边界仍在模块内 | **不做**（要维护两套模板，重复实现） |
| 候选 B：把生成器整体下沉为「脚手架支持库」，模块只转发 | 多 1 层（模块→支持库→生成器） | 与现状相同 | 与现状相同 | **不做**：层数与文件都更多，耗时/稳定性无任何改善；纯文件工具没有第三方边界需要支持库承担 |
| 候选 C：新写 CLI 脚本给调用方用 | 多 1 条腿（脚本直连文件系统） | 无统一结果、无权限/场景治理、不进 MCP/网关 | 无边界校验 | **不做**：第 4 条禁止第二入口；CLI 无契约、无错误码、无验证场景 |

结论：**现状做法最少层、最少重复实现、失败面最小**；候选 A/B/C 都没有换来更快或更稳，故不做（「不做」同样是结论）。

## 四、管什么 / 不管什么

管：

- 按声明生成模块脚手架（包声明 + 聚合契约 + 实现骨架 + 入口 + 说明 + 验证场景引用 + 完整性摘要 + 测试骨架）；
- 强制写入边界：只写调用方声明的项目根内固定两处，越界返回 `路径逃逸`；
- 生成后读取真实文件清单并随结果返回。

不管：

- 不替调用方写实现业务逻辑（生成的是骨架，`实现/` 里的占位需调用方按 `使用说明.md` 的下一步补齐）；
- 不做契约编译、不重算摘要、不跑验证（那是 `开发工具.契约编译`、`开发工具.组件规范` 与验证器的职责，模块不复制别人的逻辑）；
- 不删除、不覆盖已存在目标；失败后不清理已写文件（撤销是调用方决策，底座不静默删文件）。

## 五、失败如何表达

统一 `结果`（成功/值/错误码/错误说明），错误码只写实现里真实存在的分支：

| 错误码 | 触发条件 |
| --- | --- |
| 参数不合法 | 项目根/模块名/类型 非文本、能力清单非非空列表、依赖能力清单非列表 |
| 目录不存在 | 项目根或支持库扫描根不存在（只读探测，不创建） |
| 路径逃逸 | 目标路径越出项目根（含 `..` 跳转、绝对路径注入、符号链接逃逸） |
| 已存在 | 模块目录或测试骨架已存在，拒绝覆盖 |
| 类型不合法 / 能力重复 / 参数类型不合法 | 由唯一生成器校验返回，原样透传 |
| 无提供者 | 依赖能力清单里的能力在支持库扫描根下无提供者 |
| 清单读取失败 | 脚手架已生成，但生成后文件清单读取失败（说明里带出模块目录，不伪装成功） |
| 提供者不可用 | 唯一能力调用器未装配或支持库能力调用失败 |
| 生成失败 | 唯一生成器抛出未预期异常（不向调用方抛异常） |

> 验证场景口径：验证器**禁止**场景入参出现静态绝对路径或 `..` 路径逃逸字符串
> （`开发工具/HTML验证/路径安全.py::_校验动态声明`），因此场景文件里的越界用例用
> 「模块名含路径分隔符」（→ `路径逃逸`）触发；`..` 跳转型越界由定向 unittest
> （`测试中心/模块库/测试_组件生成.py`）与真实网关调用取证，两者返回同一 `路径逃逸` 错误码。

## 六、副作用与并发

- 副作用只有「写文件」，范围见上；**不幂等**（第二次调用返回 `已存在`），支持方需要自己保证目标目录干净再调用；
- 线程安全/进程安全为「否」：同一目标目录并发调用会竞争，由调用方按资源键串行（与验证器「同一共享目录必须串行」同源）。
