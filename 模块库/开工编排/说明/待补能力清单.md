# 开工编排 模块 · 待补能力清单

本模块只经 `获取能力调用器().调用能力(...)` 组合已有支持库能力，**不自起子进程、不自建租约表、
不自己解析 JSON**。原 MCP 工具 `project_context` + `development_start`
（`MCP工具箱/项目服务.py`，两者已合并为本模块的 `开工编排.开工准备`）里的实现按
「能收口的立即收口、收不了的如实登记」两分处理，下表是**收不了**的部分
（底座 538 个公开能力全表核对后的结论）。

## 一、已收口（不再是缺口，不再需要新能力）

| 原实现的自写动作 | 现在的落点（能力id） | 说明 |
| --- | --- | --- |
| `git rev-parse HEAD` / `rev-parse --abbrev-ref` | `版本控制支持库.Git操作.获取当前提交哈希` | 返回 `{提交哈希, 分支}` |
| `git status --short` / `git branch --show-current` / `git log` | `版本控制支持库.Git操作.当前状态` | 返回 `{分支, 未提交修改, 最近提交}` |
| 文件租约的路径归一化（`_归一化路径`） | 模块内 `_归一化相对路径`（纯字符串运算，非 I/O）**＋** `系统核心支持库.路径安全.校验路径` | 归一化之后必须过边界校验，见第二节第 7 条 4 项 |
| `os.path.exists` / `Path.exists` 判目录与账本存在 | `文件系统支持库.文件操作.判断存在` | 直接返回布尔 |
| `Path.read_text` 读 `验证历史.jsonl` | `文件系统支持库.文件操作.读取文件` | — |
| `str.splitlines()` 切行 | `数据操作支持库.文本处理.按行分割` | — |
| `json.loads` 逐行解析 JSONL | `数据操作支持库.数据交换.反序列化JSON` | 模块内不再出现 `json.loads`（模块合规「格式解析原子操作」） |

> 结论：本模块 `实现/开工编排.py` 内 0 起进程、0 次直接文件 I/O、0 次 `json.loads`
> （第 7 条 4 项 统一调用接口铁律）。

## 三、与原实现的差异（有意为之，必须让调用方知道）

| 项 | 原实现 | 本模块 | 原因 |
| --- | --- | --- | --- |
| 入口数量 | `project_context` 与 `development_start` 两个工具（后者是前者超集） | 收敛为一个能力 `开工编排.开工准备` | 结果唯一即收口（第 1 条 3 项）：同一目的不留第二个入口 |
| 修改路径越界（`../x.py`） | 文件租约内**只归一化**，越界路径照样进租约，调用方无感知 | **硬失败** `路径越界`（400），说明里带原始输入/归一化结果/解析后绝对路径/项目根/越界条数，`详情.越界清单` 逐条列出 | 修掉真缺陷：`MCP工具箱/文件租约.py` 的 `申请文件租约` 无项目根边界校验 |
| 绝对路径入参（`/etc/passwd`） | 归一化把前导 `/` 抹掉 → 伪装成仓内相对路径 | 绝对性在**归一化之前**判，直接 `路径越界` | 同一个坑的第二条路：只归一化不看原文，越界会「洗白」 |
| 代码指纹匹配数 | 用真实工作区指纹算出匹配数（可能是 25/50） | 指纹原子能力缺失 → 恒 0，并在 `依据` 字段明写「指纹原子能力缺口，匹配数恒0」 | 缺能力就报缺，不虚报可信度 |
| 文件租约 | 开工时真申请租约，冲突即拒开工 | 只做边界校验 + 输出 `申请清单`，`状态=未申请` | 缺原子能力时不假装已申请（不为了功能齐造第二条腿） |
