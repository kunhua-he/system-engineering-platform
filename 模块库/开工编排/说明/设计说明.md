## 一、为什么有这个模块

原 MCP 工具箱里 `project_context`（项目开工上下文）与 `development_start`（开发统一开工入口）
是两个独立工具，`development_start` 是 `project_context` 的超集：前者只返回上下文，
后者在上下文之外还要申请文件租约、给验证计划。同一件事两套入口，属「结果唯一即收口」要收敛的对象。

本模块 = 两者合并后的**唯一开工能力**：一次调用返回开工上下文（Git 指纹、证据可信度、
工作区快照、代码地图）＋修改路径边界校验结论＋文件租约状态＋缺失原子能力清单。

## 二、修掉的旧缺陷（本模块的核心价值）

旧 `development_start` 在拿到「修改路径」后直接调 `MCP工具箱/文件租约.py.申请文件租约`，
而该实现的 `归一化路径` **只做**反斜杠转正斜杠、去前导 `./`、去首尾斜杠——
**没有任何项目根边界校验**。于是 `../外面的文件`、`../../别人的模块/x.py` 这类越界相对路径
也能进入文件租约，把「同仓并行互斥」的保护扩到了项目外，且调用方看不到任何提示。

本模块在**入参侧**把边界校验前移为硬失败，两道判据：

1. 模块内 `Path(项目根).resolve()` ＋ `目标.resolve().is_relative_to(项目根解析)`
   —— 挡住 `..`、绝对路径、以及解析后落在外面的相对路径；
2. `系统核心支持库.路径安全.校验路径`（根目录=项目根，相对路径=归一化路径）
   —— 挡住符号链接逃逸。

任一条不通过 → `结果.失败("路径越界", 明确说明)`，说明里带**原始输入、归一化结果、解析后绝对路径、
项目根、越界条数**，并在 `详情.越界清单` 里逐条列出，便于一次改完不用来回试。
`路径越界` 是已登记的公开错误码（HTTP 400），不是新造码。

## 三、管什么 / 不管什么

**管**：入参校验、修改路径边界校验、Git 提交与工作区状态取数、证据账本成功记录读取、
代码地图可用性弱判据、开工上下文的组装与缺失能力如实登记。

**不管**（一律经 `获取能力调用器().调用能力(...)` 委托支持库，模块内不 import 支持库/提供者/
第三方/核心，不做原子级 I/O 与格式解析）：

| 动作 | 委托的能力 |
| --- | --- |
| Git 提交哈希/分支 | 版本控制支持库.Git操作.获取当前提交哈希 |
| Git 工作区状态 | 版本控制支持库.Git操作.当前状态 |
| 路径边界（符号链接逃逸） | 系统核心支持库.路径安全.校验路径 |
| 路径是否存在 | 文件系统支持库.文件操作.判断存在 |
| 读证据账本文本 | 文件系统支持库.文件操作.读取文件 |
| 文本按行分割 | 数据操作支持库.文本处理.按行分割 |
| 单行 JSON 解析 | 数据操作支持库.数据交换.反序列化JSON |

## 四、诚实边界：三个原子能力缺口

以下三件事旧实现里都有、本模块**做不到**，因为公开能力目录里没有对应的原子能力，
而模块不许自己实现（要执行 git/子进程或持租约表就是原子能力）。它们不降级为「静默跳过」，
而是**如实出现在返回值的 `缺失原子能力` 里**，并在语义上留痕：

1. **工作区指纹**（旧 `发布治理.当前工作区指纹`）：内容级指纹（porcelain 清单＋变更文件真实字节）。
   缺它 → `工作区快照.工作区指纹` 为空、`证据可信度.匹配成功记录数` 恒为 0、
   `依据` 字段明写「指纹原子能力缺口，匹配数恒0」。**分数因此不会虚高。**
2. **验证证据读取**（旧 `项目服务._读取成功记录`）：当前由本模块拼四个能力自筛
   （判断存在→读取文件→按行分割→反序列化JSON），筛选口径与写入侧同源：
   退出码=0 且 `判定.成功 非 False`（老记录无 `判定` 字段时不降级）。
   但这是平台规则不是业务规则，应收敛为原子能力。
3. **代码地图状态**（旧 `项目服务._代码地图状态`）：当前只给 `.codegraph` 目录存在性弱判据，
   `codegraph status` 的可用性详情与「需同步」状态取不到，返回值里明写是弱判据。
4. **文件租约申请/续租/释放**（旧 `MCP工具箱/文件租约.py`）：**已于 2026-09-19 接入**——
   底层六个能力全部在场（`申请文件租约` / `续租文件租约` / `释放文件租约` / `回收过期文件租约` /
   `查询文件租约` / `文件租约留言`，均属 `平台控制面.能力目录`），本模块提供两条腿：
   - `开工编排.开工即占` = **真自动门**：原子认领全部 `修改路径` 的租约，任一条被占即整体不开工
     并回带占用者（租约 id + 占用开始/过期时间），绝不部分认领；与 `收工释放` 成对。
   - `开工编排.开工准备` = **只读查**：现场查这批路径有没有活跃租约、如实给撞车清单，
     **只校验不互斥**（要互斥用 `开工即占`）。
   `修改路径` 同时兼容 `{"路径": …, "指纹": …}` 认知条目（配合 `校验指纹=真` 做乐观锁）；
   裸 64 位 hex 指纹由 `_归一指纹` 自动补 `sha256:` 前缀，避免把「格式没对齐」错报成「文件被改过」。
   五场景经唯一网关实测 9/9 通过（占成功/被挡/释放可重占/错指纹拦截/正确指纹放行）。

## 五、失败语义

| 错误码 | 触发条件 | 是否可重试 |
| --- | --- | --- |
| 参数不合法 | 任务/项目根 空或非文本；修改路径不是列表；验证级别不在枚举内；项目根不存在 | 否 |
| 路径越界 | 任一修改路径越出项目根（`..`、绝对路径、解析后在外、符号链接逃逸） | 否 |
| 提供者不可用 | 取 Git 提交哈希失败（目录不是 git 仓库 / 提供者不可用 / 调用器未装配） | 是 |

失败即失败：越界不「归一化后照收」，取不到提交不「空字符串照跑」，缺口不「假装有」。

## 六、本次任务强规范注入（2026-09-18 新增）

**缺口**：开发规范此前靠**主代理记性**写进子代理任务信（`开发工具/任务记忆/任务记忆.py`
把「通用开工纪律」附在记忆包上，读记忆包才拿到）。实测夜间连派 6 路**全部没建记忆包**
→ 纪律一次都没到达子代理 → 该批 `terminal` 读文件 418 次（上批 252）、全仓 grep 117 次（75）。

**做法（底座内部解决，Hermes 只是接入方）**：
1. 新增数据文件 `开发文档/规范/任务类型规范.json`：一类一条（任务类型/识别词/强规范/判据/原文位置）。
2. 新增纯函数 `实现/任务类型规范.py`：双字滑窗子串匹配（同 `查开工上下文` 口径，**不调大模型**），
   只回命中的几类（默认 ≤3），未命中如实返回空与提示。
3. 新增公开能力 `开工编排.取任务类型规范`（主代理**派活前**取一次贴进任务信）。
4. `开工编排.开工准备` 返回值**只增两键** `任务类型` / `强规范`（老键逐字兼容），
   使接入方调一次开工准备即得规范，**无需额外调用**。

**省 token 的硬约束**：只返回命中的那几类（实测单类强规范 75–146 字符），
细节一律走 `原文位置` 按需跳转，**不载入 126KB 项目说明与 1065 行哲学**。

**边界**：两个能力都**只读**（不改库、不写文件、不推进状态机）；字典缺失时明确失败，
不返回空列表冒充「无规范」。
