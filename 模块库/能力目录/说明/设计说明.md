## 为什么有这个模块

底座此前**没有任何一个能力承载「能力检索」**：全表核对 539 个能力无一命中，真实检索由
多份并行实现各自完成（`MCP工具箱/公开能力.py` 10 字段、`开发工具/能力搜索/能力搜索器.py`
14 字段、`开发工具/开发入口.py` 的 `搜索能力` 5 字段、`开发工具/统一能力入口/Agent查询`
的 `查询入口.搜索能力`）。同一目的多套实现即缺陷（1.3「结果唯一即收口」），故本模块把
「平台有哪些能力」收敛成**唯一的两个只读能力**，供薄壳「查询能力」转发；薄壳侧不再自己
解析声明文件。

**收口现状（2026-09-17 实测）**：检索的**实现腿全仓只剩本模块一条**——
`开发工具/能力搜索/能力搜索器.py`、`开发工具/开发入口.py 的 搜索能力`、
`开发工具/统一能力入口/Agent查询/查询入口.py 的 搜索能力` 三处**改为转调**：都经唯一调用链
（`后端核心.启动()` → `调用(能力目录.搜索能力, 参数)`）转发到本模块，自身不再扫描任何声明
文件；`MCP工具箱/` 层已整目录删除。三处覆盖字段（5／10 字段）都是本模块 14 字段口径的
**子集**，故转调后无信息损失、无静默降级；能力腿返回失败时转调方如实上报错误码与说明，
不用空列表冒充「平台没有能力」。

## 管什么

- **搜索能力**：关键词（大小写不敏感、整条记录子串匹配）→ 能力记录列表；支持**游标分页**
  与**三档细节级别**（`名称`／`名称+说明`／`完整契约`），默认档只回精简字段。
- **读取能力**：能力id → 单条完整契约（参数/必填/默认值/返回结构/错误码/调用示例/权限/
  资源预算/依赖/版本/最近成功验证/验证状态）。

## 分层披露与分页（P-9 能力可发现性）

### 默认档为什么选「名称」（不是「名称+说明」，也不是「完整契约」）

依据 `开发文档/方案/外部借鉴落实方案_哲学与架构候选_20260917.md` 第 280-295 行（P-9 六条取舍），
三条外部范式都指向同一个结论，本项目据此定档：

1. **Anthropic tool search 的实测后果**：工具定义全预载会让上下文膨胀（多服务器组合约 55k token），
   且可用工具超 30–50 个后选择准确率开始退化；被延迟的定义不进 system prompt 前缀，
   **prompt 缓存不受影响**。本项目 664 条能力的完整契约远超这个量级。
2. **P-9 第 2 条**：搜索应「返回**指针**而不是全文」，展开留到真要用的那一刻。
3. **P-9 第 6 条成本递减顺序**：先做「游标分页 + 总数 + **精简字段默认返回**」，
   再加 detail level。

**为什么不是「名称+说明」当默认**：该档每条多带 7 个字段（`说明` 全文 + 包名称/提供方/类型/
版本/包版本）。`说明` 是整句话，一个 100 条页面的「说明」合计就是几千 token——正是第 1 条
要避免的「每轮都进上下文」。**面向 Agent 的发现动作要的是「我是谁、在哪、干什么用」**
（`能力id`/`名称`/`包id`/`一句话说明`），这四项足以完成「选出候选 → 再 `读取能力` 展开」两步走；
`版本`/`类型`/`提供方` 属于「决定用不用它」的信息，那一刻才需要，放在中间档正合适。

**为什么不是「完整契约」当默认**：重字段（`参数`/`行为`/`返回`/`资源预算`/`错误码`/验证状态）
是**每调用一次就白付一次的固定成本**，而绝大多数命中的能力最终不会被调用。

**默认档必须是「名称」的第三个理由（向后兼容的诚实交代）**：旧默认行为是返回 21 字段全记录，
新默认档返回 5 字段，这是一个**已存在消费方的行为变化**（不是纯追加）。取舍是：P-9 的处方
明确要求「精简字段**默认**返回」，而「要重字段必须显式传最高档」是需求原文的一部分——
若默认保留全字段，这条改造就等于没做。为此：① 旧键名/旧参数名一个不删，`细节级别=完整契约`
与改造前**逐字段一致**（有定向测试守住）；② 变化在能力定义 `说明`、设计说明（本节）与
使用说明三处都写明，不靠调用方自己撞；③ 消费方兼容走法只有一句：传 `细节级别=完整契约`。

### 游标为什么锚在排序键上（不是偏移量）

- 命中集每次调用都**重新构建**（索引的 stat 指纹缓存会在任何包声明变更后失效重建）。
  若游标存偏移量，翻页期间任何一个包的增删都会让后续页整体位移——**偏移量分页在动态集合上
  必然漏项或重项**（第 9 页取到第 10 页的内容，或直接跳过一条）。
- 现口径：命中先按 `能力id` 升序排序，游标里带的是「上一页最后一条的 `能力id`」，
  续取用 `bisect_right` 找第一个**严格大于**锚点的位置。排序键不动，续取位置就不动。
- **不透明**：载荷是 base64url(JSON) + sha256 校验位（绑定 `游标版本` + `关键词` + 锚点 id）。
  校验位的作用是「自己拼的会被拒」——不透明的价值在于把分页正确性的责任留在服务端。
- **换关键词必须拒绝**：游标绑定签发时的关键词，同一轮翻页传了不同 `关键词` 一律报
  `参数不合法`。否则等于「换了过滤条件还接着老位置取」——那是必然的漏项/重项来源。
- 非法游标一律 **fail-closed 报错**，绝不静默退回「从头开始」或「按偏移近似」：
  那会把调用方的错变成静默漏项，比报错难查得多。

### 重字段判据是「互斥表」而非「键数」

`重字段表`（`实现/能力目录.py`）逐键列出所有重型字段，默认档与中间档**与它互斥**。
定向测试断言的是「精简档里不含这些键」，不是「键数等于 5」——只数键数的断言挡不住
重字段换个名字偷偷回流。反向验证则把游标实现改成偏移量并故意漏一项，断言「翻页合计 < 总数」
真的会红，证明这条断言有分辨力（不是恒绿）。

## 不管什么（边界）

- **不加载任何能力实现**：只读 `包声明.json` / `能力契约/参数契约.json` / `能力定义.json` /
  `权限契约/权限契约.json` / `资源预算.json` / `能力数据/能力搜索数据.json` / `验证场景引用.json` /
  `开发文档/项目证据/验证历史.jsonl`。
- **不 import 支持库、提供者、第三方、开发工具**：只用标准库 + `公共契约.基础类型.结果类型`，
  故不存在「模块绕过唯一调用链直连支持库」的问题（本模块上游本来就没有原子能力可复用）。
- **不写盘**：资源预算里 `临时空间上限 = 0`，无句柄、无常驻资源，调用幂等。
- **不暴露内部边界**：`支持库.适配层.*`（内部实现边界）与 `包声明 内部层=true` 的支持库一律不出现在结果里
  （`包声明` 里 `内部层` 的定义就是「第三方能力内部支持库：装配可用、网关 0 暴露」）。
  收口前各实现口径不一：`开发工具/开发入口.py` 的 `搜索能力` 同样跳过内部层，而
  `开发工具/能力搜索/能力搜索器.py`（旧 `搜索公开能力`）与 `查询入口.搜索能力` 只过滤适配层、
  会把内部层包漏给调用方；收口后一律以本模块口径（公开能力面）为准。
- **不做能力调用**：只回答「有什么能力、契约是什么」，不代替调用方执行能力。

## 失败如何表达

统一返回 `成功/值/错误码/错误说明`，不向调用方抛异常：

| 情形 | 错误码 | HTTP（网关口径） |
| --- | --- | --- |
| 关键词非文本、限制非整数、能力id 为空或非文本 | `参数不合法` | 400 |
| 游标 非文本／非法／版本不认识／校验位不符 | `参数不合法` | 400 |
| 游标 与本次 关键词 不匹配（换了过滤条件还接老位置） | `参数不合法` | 400 |
| `细节级别` 不在三档之内 | `参数不合法` | 400 |
| 按能力id 找不到公开能力 | `能力不存在` | 404 |
| 项目根下缺少 `支持库`/`模块库`/`技能库` 数据根 | `文件不存在` | 404 |
| 包声明可读但未解析到任何公开能力 | `内部错误` | 500 |

- **限制入参越界按边界收敛**（1~100，与旧实现一致），不静默失败；**类型不符一律拒绝**。
- **空关键词表示不过滤**（返回候选，按限制截断），不返回「未找到」这种含糊结论。
- 索引为空时**不返回空列表冒充「平台没有能力」**，而是明确报失败。
- 单个包的声明文件不可读时，该包被跳过并把原因计入扫描问题（在 `读取能力` 侧对目标能力仍报失败），
  不伪造字段、不用「未声明/无」这类占位话术掩盖。

## 去重口径（实测依据）

同一 能力id 会同时出现在**聚合父包**（如 `支持库.后端.系统核心支持库`，无 `能力定义.json`）
与**子域正式包**（如 `支持库.后端.系统核心支持库.删除守卫`，有 `能力定义.json`）的包声明里。
全仓实测 166 处重复，**全部**符合「父包聚合视图 vs 子包正式定义」这一形态，
故保留带 `能力定义.json` 的那一份——父包的聚合视图会遮蔽子包的完整契约。

## 验证历史两类字段的口径差

- **`最近成功验证`是断言型字段**（它断言「本能力被成功验证过」），只认 `包id` / `能力id`
  精确令牌，宁缺勿假。实测教训：按包末段子串匹配时，包末段「能力目录」会命中
  2026-08-24「渐进能力目录与统一网关工作包验证」这条与本事无关的记录——
  一个裸时间戳会被读成「本能力已验证通过」，属伪造证据。
- **`验证状态`是披露型字段**，允许用包id/包末段/能力id 三个令牌并查以提升命中率，
  但**必须在同一字符串里写明命中的令牌与记录名称**（如「按「网页分析」匹配：网页分析 提取网页正文回归」），
  匹配依据可见、可核对，不冒充强绑定。

## 检索规模（实测）

115 个正式包、705 条能力声明、539 个唯一公开能力id；全量只读解析约 30 毫秒级，
故不做进程内缓存（缓存会引入「声明已改但读旧值」的漂移风险，收益不成比例）。
