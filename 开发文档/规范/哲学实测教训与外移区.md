## §9.4.1 写关键值的硬约束（对应哲学 9.4.1）

**规则本体（正文保留）**：钉关键值前必须先看该能力真实返回了哪些键；
算「缺口」必须调验证器真函数，不许自写扫描脚本。

**四条实测教训（原文搬移）**：

① **「没有」要在场景内看，不只看库外** —— 钉 `{"数量": 0}` 只有当「**该步骤是该场景内第一次触碰该存储**」时才成立。
若场景**前序步骤写过数据**（写类能力也是目标步骤），后续读类的数量就不为 0
（实例：`记忆支持库.项目维度与仅关键词` 先 `写入记忆` 3 条 → 后续 `最近记忆(项目=A项目)` 真值 **1 非 0**；
`发布管理` 先留未完成事务 → `查询未完成发布事务` 真值 **1 非 0**）。

② **写关键值前先看该能力「真实返回了哪些键」** —— **写类/追加类能力的返回体不含 `数量` 键**
（如 `写入记忆` 返回 `名称`/`状态`，`追加记忆` 返回 `标识`/`已追加`/`标题`）。
对它钉一个不存在的键，验证器报 `<object object> != <期望值>`（读不到该键），**不是值不对而是键不存在**。

③ 配套：**改场景后必须重编译制品再验** —— 制品保留旧场景，不重编译会报与本次改动无关的失败（实测报过无关 `503`）。

④ **算「缺口」必须直接调验证器真函数，不许自写扫描脚本**（2026-09-18 实证，代价最大的一条）：
   `开发工具/HTML验证/单步场景.正向断言有实断言(...)` 是**唯一判据**，它认 **6 条等价通道**
   （`关键值` / `值类型`∈16 正式类型名 / `必需字段` / `字段类型` / 完整 `值` / 非恒真 `包含`）。
   自写脚本若只认 `关键值` 一条，会把 **568 条已有实断言的步骤误判为缺口**——本轮据此连跑多轮、
   派出多路子代理做无用功。**正确姿势**：`from 开发工具.HTML验证.单步场景 import 正向断言有实断言`，
   对每个正向步骤按其 6 个形参逐条传入。
   **真值（2026-09-18，用验证器自己的加载链重算）**：包目录 135｜正向步骤 **963**｜有实断言 **963**｜零断言 **0**。
   （旧口径 590 / 312 都是扫子集的错值 —— 只扫 `验证场景/*.json` 会漏掉内联在 `验证场景引用.json` 里的场景。）

**9.4 的起因（原文搬移）**：2026-09-17 定：原「同样的输入 → 同样的输出」是无条件规则，
而随机数 / 当前时间 / 网络 / 浏览器 / 大模型五类正式能力天然不满足它；
本条同时给出「正向步骤里只有一部分需要关键值」的分派依据。

## §8.3 唯一性判定四级框架的落地细则（对应哲学 8.3）

**规则本体（正文保留）**：能参数化成一个能力的绝不分家；四级框架判「合并 / 加模式 / 增强 / 新建」。

**第②类落地细则（原文搬移）**：同一能力 id，参数加「模式」，
实现内 `if 模式==1: 实现A elif 模式==2: 实现B`；输入/输出/存储格式完全一致，
用户只传模式号——不新增能力 id、不暴露内部差异、不产生重复底子。
示例：工具并发调度（`调度模式=1串行/2并行/3滚动池`）、循环软护栏（`护栏模式=1提示/2硬杀/3静默`）、
快照（`快照模式=1复制/2git裸仓`）。

**上层业务（V3 等）的边界（原文搬移）**：
- 上层一律 `调用能力(能力id, 参数)`，不 import 实现、不复制逻辑、不维护第二套。
- 上层项目各自的哲学写各自权威文档，本哲学只约束底座能力治理；双方分开落盘、分开验收。

## §12.3 子代理规模的实测数据（对应哲学 12.3）

**规则本体（正文保留）**：单任务目标 10 分钟、按「一个可独立验收的交付物」切。

**实测数据（原文搬移）**：全历史 262 个子代理任务统计——撞 `timeout` 的 **22 个任务 100% 都撞在 1800s 上限**
（不是任务本身失败，是规模超出单次会话预算）；而**完成任务的中位耗时是 647s ≈ 10.8 分钟**。
本轮正反例：同一批里最接近 10 分钟的任务（`640s`，只写一份处置方案 md）**一次过**；
而把「C-7 建包 + C-12 补能力 + C-13 能力面 + C-8 出方案」**四件事塞进一个任务**的那路，
跑满 1800s 超时，只完成其中两件，并把组件规范支持库停在半成品。
华哥原话：「正常一个任务最好是控制在 10 分钟以内，就是子代理。你任务估计过大了。」

## §12.1 非核心不中途跑验证的代价（对应哲学 12.1）

**规则本体（正文保留）**：非核心改动一律不在中途跑验证；唯一例外是接口/契约的真实字段名与返回结构。

**实测代价（原文搬移）**：为确认一个字典键名，反复「改一行 → 跑门禁 → 发现键名不对 → 再改 → 再跑」，
单条判据耗掉数轮工具调用。**正确做法**：先用一条命令把**事实**查清（如打印返回字典的真实键集），
一次改对，然后继续往下做，把验证攒到最后一批统一跑。
**判据**：同一处改动如果跑了第二次验证，说明第一次缺了「先查事实」这一步，属方法错误、不是谨慎。

## §6.2 命名与英文门面的边界（对应哲学 6.2）

**规则本体（正文保留）**：命名一眼能懂（禁用无实义序次类汉字）；英文只留最底层一处门面。

**适用边界（原文搬移）**：全中文命名管的是**本仓自有的标识与对外契约面**
（变量 / 函数 / 类 / 文件 / 目录 / 注释 / 文档 / 契约字段 / 错误码），
**不覆盖第三方与标准库 API 的签名位置**（如 `os.walk(topdown=True)`、`subprocess.run(check=False)`、
`open(..., closefd=)`）——那是第三方协议的一部分，改它会脱节于第三方文档且**无收益**
（实测把这类位置纳入迁移会让工作量翻一倍以上；决策记录 `0024` 第一项）。

**中文门面样板与分界（原文搬移）**：样板见 `公共契约/基础类型/数据类.py`（把 `dataclasses` 收成
`数据类`/`字段`/`不可变数据类`）、`公共契约/运行时/进程终止.py`（收口 `os.killpg`）、
`公共契约/运行时/平台适配.py`（收口 `sys.platform`）。门面**只做可读性收口、不重写实现**。
两段分界：签名位置豁免继续有效；本仓自有面上新写代码不得再直连英文，第三方协议签名位不受此限。
（判据：`新代码` 出现 `from dataclasses import` 之类**本仓自有面**的英文直连即违规。）

## §12.4 哲学空间收敛的实测起因（对应哲学 12.4）

**规则本体（正文保留）**：哲学只放跨项目通用、长期稳定的原则；新增子项前先查合并；
重裁前必须先读既有裁决；写新增段落要显式写明与相邻段的分界。

**实测起因（原文搬移）**：2026-09-17 一次重裁**没先读** `未完成事项.md` 的 `H2/H-1` 段，
裁出了与它**方向相反**的结论，当场制造两个矛盾事实源。
华哥提醒：「不打架」不止查规则冲突，也要查内容冲突——同一主条内相邻段落、
或本条与相邻子项之间，不得出现互相矛盾的判据。
（同源实测：2026-09-18 发现 `开发文档/方案/` 有 **4 份文档同时写全仓批次编排且各自自称权威**、
三套批次编号并存——这是立 `方案文档生命周期规范.md` 的直接起因。）

## §3.3 三种缺口与补法（对应哲学 3.3）

**规则本体（正文保留）**：报错必须回填说明文档；一次命中是核心目标；先补文档再修代码。

**三种常见缺口与补法（原文搬移）**：

① **独立工具/脚本怎么合法调能力没写** → 补「装配与调用方式」段落
（进程内必须经 `后端核心` 装配，直接 `获取能力调用器()` 会 `E未装配`）；
② **真实返回结构与文档描述不符** → 补「返回结构」原文（照现场实测形状写，不许照印象写）；
③ **只有结论没有步骤** → 补「命令 + 入参 + 期望返回」三段式。

**纪律（原文搬移）**：补文档与改代码**分开落盘、各自可验证**；
文档补完必须回读，确认别人照着能一次做对。
