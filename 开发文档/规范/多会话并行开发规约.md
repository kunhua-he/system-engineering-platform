# 系统工程平台 · 多会话并行开发规约

> 目的：多个会话（人 + 多个智能体）在**同一个仓库、同一套集成环境**里同时开发时，不抢同一个文件、不互相卡死、不覆盖彼此成果。
> 方式沿用本平台惯例：上方文本流程图，下方详细条目。
> 事实以实际代码和正式能力索引为准；本文只写"怎么协调"，不写"平台有什么"。

### 0.2 薄壳的 3 个工具（唯一元数据来源：`开发工具/薄壳/工具清单.py`）

| 工具（协议名） | 中文名 | 入参 | 转发目标 |
|----------------|--------|------|----------|
| `capability_search` | 查询能力 | `关键词`（必填）、`限制`（默认 20） | 网关操作「调用能力」→ 能力 id `能力目录.搜索能力` |
| `capability_call` | 调用能力 | `能力id`（必填）、`参数`（对象） | 网关操作「调用能力」→ 入参指定能力 id |
| `tool_catalog` | 工具目录 | 无 | 不转发（薄壳本地元数据） |

薄壳**零业务语义**：只做 MCP 协议翻译 + 转发唯一网关，不解析业务参数、不做业务判断、不落业务数据。

- **没有 HTTP 端口**。薄壳由 MCP 客户端按绝对路径拉起，配置见 `.mcp.json`（服务名 `system_engineering_toolkit`，命令 `python3.14 开发工具/薄壳/薄壳服务.py`）。
- **凭证**只从环境变量 `系统库网关凭证` 读，只在 `Authorization: Bearer <凭证>` 请求头里用，不打印、不落盘、不进错误文本。缺凭证时明确失败 `网关凭证缺失`。
- 薄壳支持传**中文工具名**：`调用工具` 会用 `中文名到协议名` 归一化，所以"查询能力/调用能力/工具目录"三个中文名可直接用。

### 0.3 执行网关 40007

- 唯一执行入口：`POST http://127.0.0.1:40007/网关/调用`；探活：`GET http://127.0.0.1:40007/健康`。
- **网关默认要求凭证**：任何请求（含 `/健康`）不带凭证一律 `401` + `权限不足 / 访问凭证缺失或无效`（本节实测：无凭证 `401`，带凭证 `200`）。
- bash **不支持中文变量名**，取凭证必须用 ASCII 中转名：

  ```bash
  TOKEN="$(plutil -extract EnvironmentVariables.系统库网关凭证 raw -o - ~/Library/LaunchAgents/com.huashi.gateway-40007.plist)"
  ```

- 请求体形状是**扁平**的（旧版把它写成嵌套 `参数:{能力id,参数}` 会 `参数不合法`）：

  ```json
  {"操作": "调用能力", "能力id": "开工编排.开工准备", "参数": {}}
  ```

## 一、总览流程图（认领式开工）

```text

  ├─ 第 0 步　判断工作性质 ─────────────────────────────
  │    ├─ 只读类（探索 / 审计 / 找落点 / 只跑查询）
  │    │     → 不认领任何文件 → 天然无冲突
  │    │     → 干完把发现写进「旁路问题」清单，交给写者批次
  │    │
  │    └─ 写入类（改源码 / 契约 / 产物 / 测试）
  │          → 进入认领
  │
  ├─ 第 1 步　开工准备（可执行的那一半：边界校验）──────────
  │    capability_call  能力id=开工编排.开工准备
  │      参数：任务 / 项目根 / 修改路径=[...] / 验证级别
  │      → 逐条做「项目根边界校验」（越界即 路径越界 失败）
  │      → 返回 路径校验.通过清单 / 越界清单 / 工作区快照 / 旧缺陷修复说明
  │      ⚠ 同一次返回里的 文件租约.状态 实测恒为「未申请」：
  │         申请/续租/释放尚无公开原子能力（见第三节机制一）

  │         它挡不住第二个写者，只保证你不越出项目根
  │
  ├─ 第 2 步　认领（人工等价物，当前唯一有效护栏）──────────

  │      父会话在派活前把**文件域**切开，每路任务书写死
  │      「允许修改的文件清单」，清单之间不许有交集
  │      → 同一文件、同一时刻，只派给一路
  │    （详见第九节：非 MCP 写者的降级规程）
  │

  │      → 属于「零件在、通道通、仍然靠自觉」，不能声称"已强制"

  │    没有租约 = 没有心跳机制，也没有 300 秒过期回收
  │    → 让路只能靠人工：抢到文件的人尽快收口，抢不到的人立刻换活
```

## 二、为什么"复制一份"走不通，以及第三条路

华哥点出的两条路，各有死穴：

| 做法 | 死穴 |
|------|------|
| 复制一份（工作树 / 克隆）到别处开发 | **没有集成环境**。平台是"网关 40007 + 能力注册表 + 数据库 + 编译产物"一体的，副本里的源码 import 是全的，但跑起来的服务仍然只认主目录 —— 验证根本没法在副本里做。改完还是要合回主仓，合并那一下照样冲突。 |
| 不复制，多会话直接改主仓 | **抢同一个文件**。A 读了旧内容，B 改了，A 再写回去 → A 把 B 的改动覆盖掉，且常常无声无息。 |

> **注：本仓有 `自修复工具.创建修复工作区`（Git worktree + 精确补丁 + 定向验证 + 可回滚提交）**，但它解决的是**单人改动的隔离与最后合并**，**不解决**上面两个死穴：它仍是同一个 `.git`，且跑起来的服务与数据库仍指向主目录，副本里做不了真实集成验证；合并那一步冲突依旧。

**第三条路：同仓 + 分区认领 + 写前校验。**

理由很直接：文件在 Git 层面本来就能分开提交，两个会话改**不同文件**永远不冲突。真正会出事的只有一种情况 —— **同一文件、同一时刻、两个写者**。所以不需要隔离出一整套环境，只需要保证：

> 同一个文件，同一时刻，只允许一个会话持有写入权；抢不到就立刻让路，而不是写到一半才发现。

这就是本规约的全部核心。下面三套机制分别防三种不同的事故。

## 三、三套机制（详细）

### 机制一：文件级独占（防"同时写"）

**理想形态**（旧版设计、现已被删）：开工时对每个路径做「原子插入」文件租约，全成功才开工，任一失败即拒绝并回带占用者。

**当前真实状态（实测）**：`开工编排.开工准备` 会返回一个 `文件租约` 字段，但实测值为

```json
{"状态": "未申请", "数量": 0,
 "说明": "文件租约（申请/续租/释放）尚无公开原子能力；边界校验已由本模块完成，租约申请待原子能力补齐后接入"}
```

也就是说：**开工门口只剩"校验"，没有"互斥"。** 它能保证你不越出项目根、能给你工作区快照和路径通过清单，**但它挡不住第二个写者**。

因此在租约原子能力补齐之前，本机制**只能靠人工等价物**（第九节的"文件域切分"）落地，**不许**在文档或实践里声称"文件租约已强制"。

**为什么粒度必须到文件、不到包**：包太大（一个支持库几十个文件），按包认领会把并行度压死。按文件认领，两个会话改同一包的不同文件仍然并行无阻。这条设计结论**与工具面无关，继续有效**。

### 机制二：写前摘要校验（防"先后写"）

光有认领还不够。还有一种事故：

> A 会话读了文件、改完、提交、收工；B 会话基于**它自己更早读到的旧内容**来改，此时没人占着这个文件，B 照样能写 —— 就把 A 的改动盖掉了。

**这个零件在本仓是真实、可达、可执行的**（旧版说"通道缺、只能人工约定"，**该结论已作废**）：

```bash
# 经薄壳 capability_call，或直接 POST 40007 /网关/调用
TOKEN="$(plutil -extract EnvironmentVariables.系统库网关凭证 raw -o - ~/Library/LaunchAgents/com.huashi.gateway-40007.plist)"
curl -s -X POST http://127.0.0.1:40007/网关/调用 \
  -H 'Content-Type: application/json' -H "Authorization: Bearer $TOKEN" \
  -d '{"操作":"调用能力","能力id":"文件系统支持库.文本补丁.应用精确替换","参数":{
        "文件路径":"<绝对路径>","旧文本":"<原文片段>","新文本":"<新片段>",
        "根目录":"/Users/hekunhua/Documents/Agent/PHP/系统工程平台",
        "预期文件摘要":"<整文件 SHA256>","写入":false}}'
```

- `预期文件摘要` = **整文件 SHA256 乐观锁**；摘要对不上 → `500` + 错误码 **`文件摘要不符`**，拒绝落盘（本节实测通过）。
- `写入=false` → **只回统一差异预览**（`差异` / `差异行数` / `新增行数` / `删除行数`），不落盘。**先看 diff 再决定落不落**，这是本仓现在能做到的最好写前纪律。
- 另有 `预期旧文本摘要`（旧文本 SHA256）与 `根目录` 越界校验（越界返回 `路径越界`）。

**但仍有一条必须说清的边界**：**没有任何工具强制你必须带 `预期文件摘要`。** 能力支持 ≠ 流程强制。所以本机制的正确描述是「**零件在、通道通、靠自觉**」——它是**可用**的护栏，**不是已强制的闸门**，不许对外声称"写盘已强制乐观锁"。

### 机制三：心跳与过期回收（防"锁死"）

**当前不存在**。没有租约就没有心跳、没有过期时间、没有自动回收。

推论（很重要）：

- **不存在"锁死了要人工清库"**——因为没有锁；
- 也**不存在**"崩了就 300 秒自动放行"——**所以长任务必须自带硬超时**，绝不能指望机制帮你收口；
- 让路只能靠人工：抢到文件的人尽快收口，抢不到的人**立刻换活**，不要等。

## 七、冲突处置规程（撞上了怎么办）

按冲突的层级分三档处理，**不许硬闯，不许强改别人的文件**：

条目 1：**文件级冲突**（目标文件正被另一个会话改）
   → 不做。记入旁路清单，换下一个不重叠的工作包。这是绝大多数情况。
   → 注意：现在**没有工具能替你发现**这个冲突（`文件租约.状态 = 未申请`），
     只能靠**派活时的文件域切分**（第九节）+ 写前 `git status` / 回读现场。

条目 2：**资源级冲突**（两个会话都要占同一个独占资源：编译、迁移、网关重启）
   → 走能力 `并发控制支持库.占用容量`（容量闸门，强锁检查 + 占用，超限直接拒绝不排队）
     或 `系统核心支持库.资源管理.资源短锁`（原子获取并释放资源级跨进程短锁）。
   → 抢不到就排队或换活，**不许绕过闸门直接干**。

条目 3：**语义级冲突**（两方改的是**不同文件**，但动的是同一处逻辑）
   → 这类工具挡不住（任何工具都挡不住），靠两道人工兜底：
     - 收口时按改动路径做**定向验证**（改了哪就必须跑对应测试，否则不予收口）；
     - 旁路清单 + 收口汇总，由收口者**通读一遍**确认没有互相拆台。

## 九、多会话 / 多子代理并发写者的降级规程（本文核心，与工具面无关）

**这一节是本文存在的理由。** 它覆盖一个规约原先没覆盖的情况：写者**可能连开工门口都不经过**——例如由父会话编排的 Hermes 子代理，直接用 `git` / `python` 写盘，全程不碰任何网关。此时第三节的三套机制**一道都不会触发**。

**而现在的处境更严重**：即使写者**老老实实**走 `开工编排.开工准备`，实测 `文件租约.状态 = 未申请` —— **自动门本来就不存在**。所以第九节**不是"降级"，它是当前唯一有效的护栏**。

**原则不变**：同一个文件、同一时刻、只允许一个写者；抢不到就立刻让路。变的只是"谁来当那个守门人"——**由父会话（编排者）用人工等价物替代机制**：

| 机制 | 旧版 MCP 通道做法（已删） | **当前及降级的等价做法** | 责任方 |
|------|---------------------------|--------------------------|--------|
| **文件级独占**（防同时写） | `development_start` 收 `modified_paths` → 批量原子申请 `文件::<路径>` 租约，全成功才开工 | **父会话在派活前切分文件域**：每个子代理的任务书写死「允许修改的文件清单」，清单之间**不许有交集**；同一文件同一时刻只派给一路。**开工前用 `git status --porcelain` 现场回读一遍**，看目标文件是否已被别人动过 | 父会话 |
| **写前摘要校验**（防先后写覆盖） | `apply_file_patch` 带「预期文件摘要」乐观锁 | ① 优先用现成能力：`capability_call` → `文件系统支持库.文本补丁.应用精确替换`，`写入=false` 看 diff 再带 `预期文件摘要` 真写；② **没有通道时**（子代理只用 git/python）：改前先 `read` 确认当前内容、改后 `git diff` 自查；③ **提交时逐文件核对 `git add` 清单** | 子代理 + 父会话 |
| **心跳与过期回收**（防锁死） | 300 秒无心跳 → 租约自动过期可重认领 | **不存在任何自动回收** → **硬超时必须写进任务书**，到点立刻停手并分列已完成/未完成；父会话现场验收产物后主动收口。**绝不能靠"锁会自动过期"兜底** | 双方 |
| **共享资源避让**（见第六节） | 避让表逐项遵守 | **禁止任何全仓级动作**：不得跑"全量重算摘要 / 全量编译 / 全量重建依赖锁"这类会写多个包文件的命令；**只允许包级操作**（包级编译、包级生成摘要）。派生产物"只重算自己那一包"这条**必须写进任务书** | 父会话 |
| **语义级冲突**（不同文件改同一处逻辑） | 收口时定向验证 + 收口者通读 | 同左——**父会话必须做收口者通读**，这是唯一兜底，不可省略 | 父会话 |

### 9.1 Git 提交纪律（最容易出人命的一条）

- **只 `git add` 自己改的路径**，逐文件显式列出，**绝不用 `git add -A` / `git add .`** —— 本仓工作区**常年**有别的会话在途的半成品（自检办法：`git status --porcelain` 若列出**多于你自己改的**文件，那些就是别人的在途改动），一条 `-A` 就会把别人的半成品带进你的提交。
- ★ **`commit` 也必须带 pathspec**（2026-09-18 实测事故）：只 `git add` 自己的文件、却跑不带 pathspec 的 `git commit -m "…"`，会**把别的会话已经 staged 的文件一起提交**。索引是**全局共享**的，不是你私有的 —— 现场实证：C 簇自称"精确路径提交"，实际提交了 5 个文件（其中 4 个是 F 簇的），提交信息还写着 B5，把别人的成果卷进了一个语义不符的提交。
  **正确姿势**：`git commit -m "…" -- <精确路径1> <精确路径2>`，提交后 **`git show --stat HEAD` 核对文件数**与预期一致。
- 提交前**逐文件核对** `git diff --cached --name-only`，确认清单里没有不是自己改的文件。
- 被他人改动覆盖时，**以现场回读为准**（重读磁盘真内容），不采信自己记忆里的旧内容。
- **父会话验收提交时**，除哈希外还要看 **`git show --stat <哈希>` 的文件数**：数量对不上就是夹带，按「接手在途工作」口径处置（验收内容 → 判断是否需要补提交或改写提交信息），不默认它干净。

### 9.2 受保护文件要请示授权

- `AGENTS.md` 等**全局协作规则/受保护文件**：**必须先向华哥请示授权**，授权前**不许改、不许格式化、不许顺手提交**。
- 不确定某文件是否受保护时，**默认当它受保护**（fail-closed），先问再做。

### 9.2.1 任务记忆包是**只读输入**，不是回传落点（2026-09-18 实测踩坑）

**事故**：E 簇子代理把回传报告直接写进 `工程缓存/任务记忆/二次审计E_*.md`（任务记忆包本体），
被 Hermes 的写保护拦下（`Refusing to overwrite`），绕三次才改用 `patch` 追加；
并把 11KB 验证脚本留在 `工程缓存/任务记忆/` 下（违反哲学 1.6「临时脚本不留库」）。

**根因**：任务书写了「回传格式」，**没写「回传到哪个路径」** → 子代理就近写进了记忆包。

**规则（写任务书时必须照抄）**：
1. **任务记忆包是只读输入**：子代理**只在开工时读它，绝不改写、绝不追加、绝不在其所在目录新增文件**。
2. **回传落点写死**：任务书必须指定回传文件绝对路径（本项目统一 `开发文档/分析/<任务名>_回传_<日期>.md`）；
   没指定时默认**只在最终回答里回传**，不落盘。
3. **临时脚本必须在受管临时目录**（`/private/tmp/系统平台临时脚本_<日期>/`），**禁止留在仓库内**。
4. **父会话收口时检查**：`git status` 里 `工程缓存/任务记忆/` 不该出现新文件；有则迁出并还原记忆包。

### 9.2.2 子代理自述「已提交」不等于已提交（2026-09-18 实测）

**事故**：E 簇自述「已提交」，实际只执行到 `git add`（工作树显示 `M ` 在第一列 = 已暂存未提交）。
父会话若不核对，产物会**停留在暂存区**，既没进历史，也可能被后续 `git commit` 误带。

**规则**：
1. 任务书必须写「**`git add` 后必须真 `git commit`，并在回传里给出提交哈希（`git rev-parse --short HEAD`）**」。
2. **父会话验收硬判据**：拿到哈希后自己跑 `git log --oneline -1 <哈希>` 核对该提交**确实存在且文件清单正确**；
   **不接受子代理自述的「已提交」**。
3. 只 `git add` 没 `commit` 的产物，由父会话核对后补提交（或退回重做），**不算完成**。

### 9.3 子代理硬超时与产物验收（纪律，必须写进任务书）

- **硬超时**：任务书必须写明"到点立刻停手"，并写明超时后的收口动作（现场验产物、不等待）。本机**没有 `timeout` / `gtimeout` 命令**，别在任务书里写依赖它们的命令。
- **产物验收**：父会话**逐个产物实测验收**，**不采信子代理自述的"成功"**——子代理的最终报告是自述，不是事实。
- **验收要有可核验的把手**：要求子代理交出**绝对路径 / 能力 id / 实测命令与真实输出**，父会话自己再跑一遍。

### 9.5 收口时（父会话）

- [ ] 逐个产物**实测验收**（不采信子代理自述的成功声明）；
- [ ] `git add` 只加自己负责的路径，**逐文件核对**，别人的在途改动一律不进本批提交；
- [ ] 通读一遍所有改动，确认没有互相拆台（语义级冲突兜底）；
- [ ] 跑一次 `python3.14 -m 开发工具.全量重算摘要 --只报`，确认摘要漂移已被自己这一批闭合。

> **为什么不让父会话也去申请租约**：当前**根本没有可申请的租约能力**（`开工编排.开工准备` 实测 `文件租约.状态 = 未申请`）；且编排式子代理的写盘走 `git`/`python`，不经过任何网关，租约**申请了也拦不住**。所以在租约原子能力真正落地之前，**人工等价物是唯一有效护栏**——它的可靠性来自"父会话是唯一裁决者"这一点，而不是来自机制强制。

## 十、开工 / 收工自检清单

**开工时：**
- [ ] `python3.14 -m 开发工具.环境自检` 过了吗？（一跑就知道本机能不能跑）
- [ ] 这次是只读还是写入？只读就直接干，不认领。
- [ ] 写入的：要动哪几个文件？**清单写全了吗？**
- [ ] 别人是不是正在改这些文件？→ `git status --porcelain` **现场回读**一次（没有租约工具，只能自己看）。
- [ ] 需要声明边界就走 `capability_call` → `开工编排.开工准备`（填 `修改路径`）。**知道它只校验、不互斥。**
- [ ] 被占了 → 选出路：换活 / 记旁路（**不许硬闯，也不建议干等**）。

**写入时：**
- [ ] 走能力写盘时，**先 `写入=false` 看 diff**，再带 `预期文件摘要` 真写。
- [ ] 没有通道（只用 git/python）时：改前重读、改后 `git diff` 自查。
- [ ] 改的是共享文件（`AGENTS.md` 等）吗？→ **先请示授权**。
- [ ] 有没有做**全仓级动作**（全量重算 / 全量编译）？→ 只做包级。

**提交时：**
- [ ] `git add` 只加自己改的路径，**逐文件核对**，**绝不用 `-A`**。
- [ ] `git diff --cached --name-only` 里有没有不是自己改的文件？→ 有就撤出。

**收工时：**
- [ ] 长任务有没有**硬超时**？（本机无 `timeout`/`gtimeout`，别指望自动锁过期）
- [ ] 改了包内文件 → 跑了 `python3.14 -m 开发工具.全量重算摘要` 吗？
- [ ] 动了依赖 → 跑了 `python3.14 -m 开发工具.重建依赖锁 --干跑` 吗？要写就 `--写入`。
- [ ] 抢不到 / 顺延的，有没有落进旁路清单？
