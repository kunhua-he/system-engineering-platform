## 一、什么叫「机器化」（华哥 2026-09-20 口径，原文）

> 「**机器化**指的是，例如说，是统一的生成器，编译器等这种，全自动的叫机器化。」
>
> 「如果 **md 文档本身就有个问题，那应该是弄好 md 文档**。然后后面就
> **统一的生成器，去生成这个规范**。应该是这个意思。」
>
> 「底子有问题，你修统一的，也估计修不好呀。你要**两边都归一**才行。」

三条口径拆成可执行判据：

| 口径 | 判据 |
|---|---|
| 统一生成器 | 同一类产物只有**一个**生成器入口；出现第二套即缺陷（哲学 1.2） |
| 全自动 | 生成/核验**不靠人记得跑**：接进编译口或发布门禁，改了东西没刷即报红 |
| 两边都归一 | **源头与产物同时归一**：先把 md/正文本身修对，再由生成器从它生成；只加事后体检、底下的手写源头还在，等于没修 |

**反例（本仓实测两次返工，都是「只修了一边」）**：

- 只给债务清单加「账目体检」，但顶部账目**仍是手写** ⇒ 下一个人照样会写错；
  正解是账目**由正文实数生成**，体检只作兜底门禁。

## 二、★ 全项目 md 只走一个统一生成器（华哥 2026-09-20 定）

> 「能不能 **1 个统一的生成器**，专门维护去整个项目的 md 文档。
>   你可以**传参**到时候选择是什么类型的文档生成和修改等。」
> 「你把**包级说明，决策记录，方案，权威文档，规范**；这多种类型，**每一种规范一个格式**；
>   然后后面**传参就好了。后面就不能直接写文档了**。」

⇒ **md 的编辑收口到 `开发工具/`（SDK 式单一腿）**：全仓 md 只经下面这一个入口，
**一类文档一个格式**，格式定义是**数据**（判据文件），不是散在各处的习惯。

```bash
python3.14 -m 开发工具.MD文档生成 --列出                        # 有哪些类型（序号 + 处置）
python3.14 -m 开发工具.MD文档生成 --类型 <类型名> --校验          # 门禁形态（漂移即退出 1）
python3.14 -m 开发工具.MD文档生成 --类型 <类型名> --写盘          # 生成器形态（只换生成区）
python3.14 -m 开发工具.MD文档生成 --序号 <n> --全部 --校验        # 按序号跑一整类
python3.14 -m 开发工具.MD文档生成 --类型 决策记录 --新建 --标题 <标题>   # 出骨架
```

**已登记类型（序号 ↔ 名称 ↔ 生成区 ↔ 唯一生成器）**：见
`开发文档/规范/文档类型判据.json`（数据侧唯一真源，取自 `--列出` 实测）。
**新增一类文档 = 改该判据文件一处**，不改代码、不加文件。

**几何纪律**：生成区只有生成器能写；人改了会在 `--写盘` 被刷掉、并被 `--校验` 当场判红。
**边界切不出即 fail-closed 报错**，绝不猜、绝不整文件重写（防「一次杀完」）。

### 2.1 ★ 落盘前查重：防「同一件事写好几条腿」（华哥 2026-09-20 定）

> 「有没有办法这个生成器，可以排查相似性？就是尽量写的时候，可以判断一下，
>   有没有重复的落盘了。**不然就变成了这里写一下，那里写一下，变成了文案都几条腿来。**」

⇒ 查重**长在生成器里**（不是另一个事后审计工具），因为要的是**写的时候就判**：

```bash
python3.14 -m 开发工具.MD文档生成 --查重                    # 全仓两两比，报相似文档对
python3.14 -m 开发工具.MD文档生成 --查重 --类型 决策记录      # 只看该类内部
python3.14 -m 开发工具.MD文档生成 --查重 --文件 <路径>        # 只查这一份（落盘前用）
python3.14 -m 开发工具.MD文档生成 --查重 --阈值 0.6 --取前 10  # 调阈值与条数
```

**判据（两级，先粗筛再精算）**：① 归一化（去围栏、去标点空白）后取字符 3-gram 集合，
Jaccard 粗筛取前若干名；② 对短名单用标准库 `difflib.SequenceMatcher` 精算文本相似比
（与本仓 `说明书生成/合并重生成` 同一实现血统，不引第三方）。
默认报 `≥0.40`，`≥0.70` 标「★高度疑似重复」。

**定位：降噪器，不是裁决器**（哲学 9.5②：不许包装成绝对边界）——
它比的是**字面相似**：同义改写查不出来；反之上文那种「同模板出的不同内容的件」
（如各包 `说明/目录树与命令.md`、`说明/设计说明.md`）**会报高相似**。
⇒ 机器只负责把候选摆到面前，**该不该合并由人看一眼决定**。

## 三、现役其它统一生成器（唯一入口，禁第二套）

| 产物 | 唯一生成器 | 核验（门禁形态） |
|---|---|---|
| 全项目 md（权威文档/规范/决策记录/方案/包级说明/债务清单） | **`开发工具.MD文档生成 --类型 <类型> --写盘`** | **同入口 `--校验`（编译口「债务清单」阻断项）** |
| 包使用说明 | `开发工具.MD文档生成.说明书.合并重生成`（按血统 G1/G2 自动选，行级合并，人工行零丢失） | `开发工具.契约编译.生成物一致性检查 --全部` |
| 完整性摘要（含父包级联） | `开发工具.全量重算摘要` | 编译口「摘要闭合」阻断项 |
| 依赖分两段声明 | `开发工具.依赖派生.生成依赖分两段` | `--校验`（退出码 1 = 过期或与派生结果不一致） |
| 契约编译（参数契约/包声明/能力清单） | `开发工具.契约编译.契约编译器` / `能力定义编译器` | 编译口「契约漂移」阻断项 |
| 错误码文案 | `开发工具.错误码文案派生` | 公开调用完整性门禁（错误码登记环） |
| 能力目录说明书 | `开发工具.MD文档生成.说明书.说明书生成器` | 规范漂移体检 + 生成物一致性检查 |

**铁律**：上表任何一行出现第二套实现（哪怕是「一次性脚本」「临时工具」），
按哲学 1.2 属缺陷——**一次性脚本进仓前必须先归并到唯一生成器**（本仓已有先例：
`/private/tmp` 里的一次性合并脚本升为 `开发工具/MD文档生成/说明书/合并重生成.py`；
原先独立的债务清单生成器已于同日整体归并进 `开发工具/MD文档生成`）。

## 四、元信息头的日期为什么从 git 派生（不按「生成当天」）

`最后更新` 若打成「跑生成器那一天」，有两个**必然**错误：内容没变日期天天变（假新鲜）；
`--校验` 拿「今天」当应然 ⇒ **隔夜必假红**，门禁天天无故转红。

⇒ 唯一诚实且可机判的口径：**`最后更新` = 该文件最后一次提交的日期**；
文件有未提交改动时（`git status` 脏）取当天 —— 那一刻内容确实是新的。
如此「内容没变 ⇒ 日期不动 ⇒ 校验恒过」，日期是**事实**而非**人为动作**。

**一个刻意的行为（不是 bug，别修）**：文档有未提交改动时，应然日期 = 当天；
若你改完不提交、隔天再跑 `--校验`，它会**判红**——这条红的意思就是
「这份文档有新内容还没落盘」。正常流程（改 → `--写盘` → 提交）里这个窗口只有几分钟，
且**提交后日期自动等于提交日、立即转绿**。

**只刷已有的、不强加**：`--写盘` 对缺元信息头的文件**默认不动它**（现场 16 份规范里只有
4 份有头，其余 12 份按自身体例写，体例规范 §3.0 第 4 条：不要求、但也不得发明第二种）。
生成器擅自补头 = 替人发明格式，属噪声；确需补头须显式 `--补头`（`口径`/`维护者` 留占位待人填）。

## 五、债务账目为什么必须机器生成

`开发文档/未完成事项.md` 的顶部账目**曾是手写汇总**，而正文才是逐条实数。现场两次对不上：

| 次序 | 现象 | 根因 |
|---|---|---|
| 第一次 | 账目写「真正待处置 71 条」，正文实数只有 **52** | 账目写于前一天深夜，之后正文删过已修条目、清过待裁决段，账目没跟着改 |
| 第二次 | 账目写「合计 52 = 一+二+四+7.1–7.6+7.9.1+7.9.2」，而那几项相加只有 **49** | 52 把「不计入待办」的 3 条也算进「计入待办」合计，**同一张表两个口径打架** |

两次都靠**人工重数**才发现 ⇒ 手写汇总本身就是缺陷源。

**现在**：账目块的数字与条目列**全部由正文派生**，标题行明写「**机器生成，禁止手改**」。

```bash
python3.14 -m 开发工具.MD文档生成 --类型 债务清单 --写盘   # 生成器形态：按正文实数重写账目块
python3.14 -m 开发工具.MD文档生成 --类型 债务清单 --校验   # 门禁形态：漂移即退出 1
```

**使用纪律**：改 `未完成事项.md` 的正文（增删条目、改分区）后，**必须跑 `--写盘`**
把账目刷一遍，再提交；漏刷会被编译口「债务清单」阻断项当场判红。

## 六、新增一条规则的流程（防「人工维护再偏移」）

1. 规则要能回答「**怎么机器验证 / 怎么现场取证**」——答不出即口号，不写（哲学 13.1）。
2. 该规则产生的**任何产物形态**（清单、账目、地图、索引）先判定：
   是否有**唯一生成器**？没有就新建一个，**不许手写维护**。
3. 生成器落地后同批接门禁：**生成** + **核验**两个形态都要有，核验进编译口或发布门禁。
4. 反向验证三拍（弄坏必红 / 还原必绿 / sha 一致）——没有反向验证的判据不算修好。
5. 登记到本文件第二节的表里，保持「一类产物一个入口」。
