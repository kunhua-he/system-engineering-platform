## 一、这份口径管什么

**管**：「场景覆盖率」这一个指标的**分子、分母、算与不算、存量怎么分治**——让任意一次现场计算都能得出**唯一**结果，且任何人重跑同一条命令得到同一个数。

**不管**：① 覆盖率要不要进发布门禁（那是 `开发文档/未完成事项.md` 第 26 项的裁决，本文件只把「进得去」所需的口径备齐）；② 缺口怎么补（那是各包的事）；③ 验证资产的**强度**（正向关键值够不够硬，那是第 13／32 项，与本文的「有没有场景」是两回事）。

**为什么必须有这份文件**：本项目曾报出「158 条零场景能力／23.8% 未覆盖」，实测**零场景 = 0 条**——旧值系算法只统计「场景内嵌在 `验证场景引用.json` 里」的情形，**整类漏读「外部场景文件」**（`验证场景/*.json` 与 `验证场景.json`；当时据记为 83 份，**当前实测该类共 89 份被引用**）。同一份代码，口径不同，结论从「四分之一的底座无人验」翻成「几乎没有缺口」。**本文件存在的唯一理由就是让口径不能再漂。**

> **作废声明**：任何场合再见 `158`、`23.8%`，**一律按作废处理**，不得引用、不得据此派活。同理，`664`、`830`、`925` 都是旧时点的装配面数字或被父包重复登记抬高的 rglob 累加值，**都不是能力面口径**（见第七节）。

## 二、唯一计算公式

```text
                     |{能力 ∈ 分母 : 该能力存在至少一个「正向目标步骤」}|
场景覆盖率 = ─────────────────────────────────────────────────────────────
                                                 |分母|

分母 = 正式公开能力全集 − 显式豁免能力全集
```

三个集合逐项定义如下，**每一句都对应可计算的判据**。

### 2.1 分母：正式公开能力全集

**定义**：目标目录内，经**三方严格对账**后的能力 id 集合。三方是——

| 对账方 | 文件 | 判据 |
|---|---|---|
| 统一正式包索引 | 由 `开发工具/项目编译/正式包索引.构建索引()` 生成 | 能力所有者 id 集合 |
| 包级声明 | 每个包目录的 `包声明.json` 的 `能力[]` | 与该包的 owner 能力集合**必须相等** |
| 能力契约 | 每个包目录的 `能力契约/参数契约.json` 的 `能力契约[]` | 与包声明**必须相等** |

**任一方不等即直接报错**（`开发工具/HTML验证/制品事实.py::_扫描公开能力`），不给「取交集凑合一算」的余地——对账不过就说明连「底座有哪些正式公开能力」这件事都没定清，此时算出的覆盖率毫无意义。

- **只认正式公开能力**：进不了这份对账的能力（无契约、契约与声明差集、owner 冲突）**不是分母成员**，它们的问题由「能力契约完整性」类判据承担，不在这里冒充覆盖率缺口。
- **口径只取装配后（或制品内）的对账结果**：**禁止**用 `包声明.json` 的 `rglob` 累加值当分母。父包与子包会在累加里重复登记，实测虚高（见第七节）。

### 2.2 分子：有「正向目标步骤」的能力

**定义**：分母中，**至少存在一个**满足下列全部条件的步骤的能力：

1. 该步骤出现在某个场景的 **`目标步骤`** 数组里（**不是** `前置步骤`、**不是** `清理步骤`）；
2. 该步骤声明的能力 id 等于该能力 id；
3. 该步骤的 `预期.成功 == true`（**正向**）。

**一个能力只算一条**：同一能力在 N 个场景、M 个步骤里重复出现，分子里仍只贡献 1。因此**分子 ≤ 分母**恒成立。

### 2.3 豁免：显式扣除项（不是「算覆盖」）

**定义**：包内 `能力定义.json` 的能力条目里，写了

```json
"外部依赖": { "豁免正向场景": true, "地址": "<上游地址>" }
```

且该能力确实是正式公开能力。**它从分母里扣除，不是被算作覆盖**。

**为什么两者必须分开**：把豁免算成「覆盖」等于让豁免冒充证据（哲学第 1 条 4 项：空转即杀）；而从分母扣除是**如实承认它不参与这个比率**，且豁免条款本身可审计（写在能力定义里，谁都能看见，上游恢复后必须删声明并补正向场景）。

**实测当前豁免 = 0 条**。**豁免只对「底座之外的上游服务当前不可用」这一种场景开放**，不是给「懒得补场景」开的门。

### 2.4 缺口存量（门禁真正要判的量）

```text
缺口存量 = |分母 − 分子| = |正式公开能力全集 − 显式豁免 − 正向目标能力|
```

**门禁判的是缺口存量，不是覆盖率百分比**。原因：分母随建包在动，百分比的小数点会一直跳；而缺口存量是**整数集合上的差集**，可以逐条点名（`开工编排.开工即占` 就是 `开工编排.开工即占`），能挂基线、能只减不增、能一眼看出是谁漏了。

## 四、哪些算覆盖、哪些不算（逐条判据）

### 4.1 算覆盖（计入分子）

| 情形 | 算不算 | 依据 |
|---|---|---|
| 能力出现在任一场景的 **`目标步骤`** 且 `预期.成功=true` | **算** | 2.2 定义本文 |
| 同一能力在多个场景重复出现 | **算一条**（不重复计数） | 分子是集合 |
| 能力出现在 `目标步骤` 且该步骤是**多步链的一环**（前后有前置/清理） | **算** | 目标步骤的判定与链长无关 |
| 能力 id 带 `内部.` 前缀但**在正式能力契约里** | **算**（照常计入分母与分子） | 它是正式公开能力；实测 5 条，全部已覆盖 |
| 场景是外部文件 `验证场景/*.json`／`验证场景.json` 引用的 | **算** | 与内联场景同权（**历史作废值的病根就在这里**） |
| 场景用 `{"$动态": "环境变量", ...}` 声明环境取值 | **算**（照常计入分子） | 见 4.2 最后一行 |

### 4.2 不算覆盖（不计入分子）

| 情形 | 算不算 | 为什么 |
|---|---|---|
| 能力**只**出现在 `前置步骤` 或 `清理步骤`，`目标步骤` 里没有 | **不算** | 前置/清理是**给别的能力铺路**和收尾，不是「本能力被验证」的证据。否则任何一个被前置带到的工具能力都会被自动认作"已验" |
| 能力**只**出现在 `目标步骤` 但 `预期.成功 == false`（负向步骤） | **不算** | 负向验的是「该失败的时候失败了」，与「正向能不能成」是两条证据。实测：源码根「仅负向目标」= **0** 条、制品 = **0** 条（即当前这条口径不改变数字，但必须写明——否则将来一条 `预期.成功=false` 的负向目标步骤会被误算成覆盖） |
| 能力只登记在 `包声明.json`／`能力定义.json`／`能力契约`／说明书里 | **不算** | 那是**能力面**，覆盖率算的是**场景面**。登记齐全 ≠ 有人验过 |
| 能力只被 40007 网关 `/健康` 或能力目录查出 | **不算** | 同上，那是「存在」，不是「验过」 |
| 有 `外部依赖.豁免正向场景=true` 的显式声明 | **不计入分母**（≠ 算覆盖） | 见 2.3；实测当前 0 条 |
| 只写了场景文件但 `验证场景引用.json` 没引用它 | **不算**（该场景整体不参与计算） | 实测：磁盘场景体 93 份、被引用 89 份、**未被引用 4 份**（`系统核心支持库` 下 `工具执行`／`检查点恢复`／`资源管理`／`进程管理` 的 `验证场景/正向HTTP场景.json`，均已另有 `验证场景.json` 被引用）。这 4 份是**孤儿场景**，属独立债务，不影响覆盖率数字，值得单独收口 |

### 4.3 环境依赖类能力的口径（重点澄清）

**结论：环境依赖类能力**不另设口径**，与普通能力同权——必须有正向目标步骤，否则就是缺口。**

理由与操作：

1. **环境依赖不是「不算」的理由**。本项目哲学第 1 条 1 项：模型文件、外部应用这类环境依赖**由运行环境提供，不进场景静态路径**；场景只声明「读哪个环境变量」（`{"$动态": "环境变量", "名称": X}`），取值由运行环境负责。
2. 所以场景**照常写正向目标步骤**；环境未就绪时，该步骤是**执行失败**（`环境依赖未就绪：环境变量 X 未设置或为空`），**不是覆盖率缺口**。两者在报告里分得开：前者算进「分子已覆盖 / 执行红」，后者根本进不了分子，会以「缺目标」阻断在**加载期**。
3. **实测**：声明环境变量动态值的场景 **1** 个、涉及能力 **1** 个，该能力**已在正向目标步骤里**；按 `转写`／`直播逐字稿`／`网页浏览`／`健康监督` 关键字圈出的环境依赖类候选能力 **17** 条，**17 条全部有正向目标步骤，未覆盖 = 0**。
4. **因此本机「环境依赖未就绪」造成的红，永远不应被记成覆盖率缺口**——它记在 `未完成事项.md` §8.5 第 2／4 项（环境/运行态依赖类，非代码缺陷）。本节就是防止有人为了"让响应变绿"把环境依赖类能力从分母里摘出去。

## 五、存量分治（照 13.2 门禁五态）

### 5.1 两个口径的存量，各自独立挂基线

| 口径 | 当前存量 | 门禁结论态 | 判定 |
|---|---|---|---|
| **制品口径**（发布门禁实际消费） | **0 条** | **干净通过** | 基线 0 ⇒ 出现任意 1 条即**新增**，直接**失败** |
| **源码口径**（构建前预检） | **0 条**（2026-09-18 补场景后归零；原 2 条见下） | **干净通过** | 基线 **0**，任何新增立即失败 |

### 5.2 三条铁律

1. **基线只减不增**。源码口径的 2 条是 C-14 新增能力的待补项，**补一条基线减一条**（补 `开工即占` → 基线变 1；两条都补 → 基线变 0，从此该口径也是「新增即红」）。**不允许**因为"反正才 2 条"把基线写成 3、4、5。
2. **增量即红**。任何**不在基线里的**缺口能力 = 新增，**无论总数是 1 还是 50，一律失败**。这一条是覆盖率能进发布门禁的前提：`未完成事项.md` 第 26 项担心的「未覆盖一上来就把门禁打死」，**只在总缺口直接判红时成立**；按「基线内=债务冻结、基线外=失败」分级后不成立。
3. **豁免与基线不是一回事，禁止混用**。基线是**临时债**（到期必须归零）；豁免是**结构性声明**（上游服务不在底座内，写在能力定义里可审计）。**不许**把「基线里的能力」也塞进 `豁免正向场景=true` —— 那是把债伪装成结构。

### 5.3 进发布门禁时的接线要求（本文件只定口径，接线单独立项）

判据本体已存在于产品代码（`开发工具/HTML验证/场景加载.py::_校验场景全集`，加载期 fail-closed），**但它是「全等」判据，不认基线**。要进发布门禁，接线时必须：

- 把「全等」**降级为分级判定**：`缺口 ∩ 基线 = 债务冻结`、`缺口 − 基线 = 失败`；
- **基线文件缺失／非法即 fail-closed**（全部算新增），**不得静默判绿**（照 `防回潮存量基线.json` 的同形做法）；
- 结论**必须落在 13.2 五态之一**，不得与其它项共用「通过」一词。

## 八、一页速查

```text
分子 = 有「预期.成功=true 的目标步骤」的能力（每个能力只算一条）
分母 = 正式公开能力全集 − 显式豁免（豁免写在 能力定义.json 的外部依赖.豁免正向场景）
缺口存量 = 分母 − 分子          ← 门禁判这个，不判百分比
覆盖率 = 分子 / 分母

算覆盖   ：目标步骤 + 预期成功=true（含外部场景文件、含 内部.*、含环境依赖类）
不算覆盖 ：只在 前置/清理步骤、只在负向目标步骤、只在声明/契约/说明里、孤儿场景

存量分治：制品口径基线 0（新增即红，干净通过）
          源码口径基线 2（开工编排.开工即占／收工释放，只减不增，债务冻结）
          基线外新增一律失败；基线缺失则全部算新增（fail-closed）

取证：第六节 6.1（数字）／6.2（退出码）
```
