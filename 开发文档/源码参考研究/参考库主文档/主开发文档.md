# GitHub 源码参考库 · 开发文档

> 本仓库是华哥本机的开源源码参考库，**不是生产项目**。源码默认只读，用于架构研究、源码对照和后续技术裁决。
> 新会话读本文档即可了解全貌，不需要翻 166 个仓库源码。

## 项目简介

这是一个独立的开源工程参考与通用软件底座研究库，不是华哥个人自我蒸馏项目，也不是华世王镞 V3 业务项目。仓库按支持库、模块库、Agent 平台、工作流、知识库、文档解析、检索、多模态与媒体、易语言原子支持库等工程方向归档成熟开源实现，研究其真实边界、契约、调用链、数据模型、资源治理和发布方式，为系统工程平台通用底座提供可复用的架构依据。

华哥个人自我蒸馏只是 05 区的一个专项研究方向；华世王镞 V3 则是建立在系统工程平台项目底座之上的上层业务项目，均不改变本源码参考库的总体定位。

- 给谁用：系统工程平台维护者、Hermes Agent，以及需要进行架构对照和技术裁决的上层项目维护者
- 产出物：每个开源项目根目录唯一的 `ARCHITECTURE.md`、跨项目底座升级框架和 `00_catalog/` 导航索引（不动开源项目源码本身）
- 规模：166 个 Git 仓库 / 约 16G / 7 大分类（以本机 `.git` 实际扫描为准）

## 与系统工程平台、华世王镞 V3 的继承边界

本源码参考库研究的是**可复用的支持库、模块库和系统工程平台项目底座**，不是华世王镞 V3 本身。三者关系固定为：

```text
本源码参考库
  ↓ 只提取源码已证的边界、契约、算法和治理模式
支持库
  ↓ 原子能力、第三方/系统适配、资源释放和提供者边界
模块库
  ↓ 组合能力、标准流程和公开模块接口
系统工程平台项目底座
  ↓ 公共契约、运行核心、统一网关、治理、制品、发布和证据
华世王镞 V3
  ↓ 项目适配层、业务模块、品牌规则、业务数据和业务 UI
```

- **底座研究对象**：支持库、模块库、运行核心、统一能力网关、契约治理、资源治理、证据链、制品发布和可回滚机制。
- **华世王镞 V3 定位**：建立在系统工程平台之上的上层业务项目；只通过公开契约、项目适配层和允许的模块接口接入，不反向定义底座通用事实。
- **严格隔离**：源码参考库的研究不能读取、复制或改写华世王镞 V3 的业务源码、数据库、配置和运行数据；华世王镞的业务需求只有在形成通用能力需求后，才进入底座候选裁决。
- **当前交付边界**：本库的 `ARCHITECTURE.md` 和主文档只形成研究证据与底座候选框架，不直接修改系统工程平台，更不直接修改华世王镞 V3。

### 架构 Markdown 语言规范

- 架构文档的项目定位、分层职责、数据流说明、表格解释、备注、风险、结论和研究裁决，默认使用中文。
- 源码路径、类名、函数名、变量名、字段名、API 路由、命令、协议名、第三方产品名和源码原文，按实际形式保留，不为翻译而改写标识符。
- 流程图和目录地图中的说明文字也尽量使用中文；只有源码目录/文件/符号本身必须保留英文或原项目语言。
- 子代理返回的英文分析只能作为取证材料，落盘前必须由主协调者蒸馏为中文说明，不能直接形成正式事实源。

### 源码版本新鲜度检查

- 每个项目首轮建档前先读取远程地址、当前分支、当前提交、提交时间和远程默认分支最新提交，不能只相信本地已有快照。
- 如果本地落后，优先通过本机代理 `127.0.0.1:4780` 拉取远程引用；已有工作树存在未跟踪架构文档或细探材料时，禁止直接 `pull` 覆盖。
- 最新源码使用独立工作区/快照分析，记录远程提交、时间、本地落后提交数和关键变更；确认后再把增量结论合并回该项目唯一 `ARCHITECTURE.md`。
- 版本快照只作为取证工作区，不成为第二份架构事实源；项目正式事实仍只回写项目根 `ARCHITECTURE.md`。
- **临时文档**：只服务当前施工；稳定结论合并本文档后清理，不作为新会话入口。

## 使用规则（铁律）

1. 同一 GitHub/Gitee 远程仓库只保留一份本地副本，无重复。
2. 源码参考默认只读；单仓分析结论唯一写入目标项目根的 `ARCHITECTURE.md`，跨仓横向结论才写到 `00_catalog/`，不改源码、不装依赖、不生成权重/数据库/构建产物。
3. 需要做架构分析时，先读目标项目 README → 架构文档 → 核心入口 → 数据模型 → 测试；已有 `细探-*.md` 只能作为待吸收材料，不能与 `ARCHITECTURE.md` 并列为事实源。
4. **不要直接照搬**：不把任何项目部署成第二个长期记忆中枢；不让 LLM 直接覆盖事实/状态/人格；不把一次情绪/玩笑升级为稳定人格；不把 README 性能宣传当源码已证结论；不把 30 仓库拼成大泥球——只提取边界、契约和可验证模式。

## 递进式全量研究循环

全库研究不是“一轮写完就结束”。对 166 个仓库按以下顺序循环 4～5 轮；每轮完成后，逐项目人工读取并把新证据蒸馏回同一份 `ARCHITECTURE.md`，不新建平行报告：

1. **首轮：全量架构建档**——入口、分层、核心数据流、数据模型、API/CLI/SDK、依赖、测试和未确认项。
2. **第二轮：核心实现深挖**——沿真实调用链追入口到核心函数，补状态机、写入/读取路径、索引、缓存、事务和关键算法。
3. **第三轮：工业治理深挖**——补并发、队列、重试、超时、幂等、资源上限、错误降级、权限、安全和可观测性。
4. **第四轮：产品边界深挖**——补插件/扩展、Provider、协议、部署、迁移、配置、测试契约和版本兼容；对 README 与源码冲突做裁决。
5. **第五轮（按价值选择）：横向归纳**——只将跨项目共性写入 `00_catalog/` 的专题文档；单项目事实仍回到各自 `ARCHITECTURE.md`。

每个项目每轮都必须人工读取已有架构文档和本轮发现的源码/测试；需要核对的字段、路径、接口和数量必须回到原始文件核实。子代理只负责独立项目的现场取证，主协调者负责逐项目收口、去重和验收。

- `细探-*.md`、`探索-*.md`、`临时分析-*.md` 是施工材料；完成人工吸收并核对后删除。

## 支持库/模块库/系统工程平台项目底座升级框架（研究收敛版）

> 本节是从当前已完成首轮建档的项目中提炼的**支持库、模块库和系统工程平台项目底座升级候选框架**。华世王镞 V3 是该底座之上的接入项目，不是本节的直接修改对象。这里的结论是研究结果，不等于已经实施；任何落地仍需需求确认、能力搜索、契约、工作包和验收门禁。

### 总体目标

不复制某一个开源项目，而是形成一条可被多个上层项目复用的、可审计、可回滚、可扩展的通用软件底座主链；智能代理只是其中一个应用板块：

```text
多源输入
  → 原始证据/事件账本（不可覆盖）
  → 事实/观察/关系/时间有效期
  → 个人模型与项目状态投影
  → 有界混合召回与上下文装配
  → Agent 执行与工具调用
  → 反馈/验证/纠错
  → 异步巩固、能力提炼、版本制品与可回滚激活
```

### 当前明确吸收的工业模式

1. **原始证据永不被摘要覆盖**：摘要、画像、技能和世界模型都是派生投影；纠错写新版本并保留来源链。
2. **记忆按生命周期分层**：工作记忆、逐字事件、语义事实、程序技能、视觉/媒体和项目状态不能混成一张表。
3. **写入与读取分开治理**：写入强调来源、幂等、版本和审计；读取强调权限、时间有效性、混合排序和预算。
4. **检索采用多路召回再融合**：语义、BM25、结构字段、时间、图和实体各自可降级，不能只押一个向量库。
5. **上下文注入必须有界且带来源声明**：稳定块缓存、动态块限额；历史记忆标记为数据，不得当作指令；旧事实需要复核提示。
6. **同步热路径与异步冷路径分离**：对话不能等待完整巩固；巩固失败不能伪装成功，也不能阻塞主回答。
7. **能力/Provider/协议通过适配边界接入**：第三方 SDK、模型、向量库、MCP、渠道都不能渗透正式业务层。
8. **反馈先验证再改变状态**：LLM 提出的 UPDATE/DELETE/Skill/画像变化必须经过规则、证据或二次审查。
9. **所有长期变化都可追溯和回滚**：保留 before/after、来源、理由、验证结果、制品摘要和激活指针。
10. **资源必须有界**：队列、并发、上下文、检索候选、重试、超时、日志、缓存和子进程都要有硬上限。
11. **远程源码缓存按版本隔离并可自愈刷新**：远程地址和分支共同决定缓存身份；刷新过程加锁、fetch、切换目标分支、hard reset，并返回 cloned/cached/refreshed 和结构化错误，不能让不同分支共用一个可变目录。
12. **输入接收与执行调度分离**：先把请求写入有序 durable inbox，再由运行器在安全边界按 steer/queue 规则提升；重试必须以幂等键和冲突校验为前提，不能只靠内存队列。
13. **事件投影作为读模型边界**：原始事件按 aggregate sequence 持久化，projector 负责 Schema 编解码、状态投影、用量累加和历史重放；读模型损坏时可由事件重建，不把界面状态当事实源。
14. **Provider 兼容逻辑集中在适配层**：模型模态、空消息、reasoning 状态、输出上限、Provider 参数键和异常格式在支持库适配层收口，正式模块只接收统一结果。

### 当前明确废弃的模式

- 让 LLM 直接覆盖用户事实、画像、权限或长期状态；
- 把向量库当作唯一事实源，丢失原文、来源和时间有效性；
- 为不同入口复制多套记忆/检索/写入内核；
- 把 README、论文指标或旧分支代码当作当前实现证据；
- 把“异步入队很快”宣传成“业务已经处理完成”；
- 让无权限/空 scope 默认放行；
- 通过无界队列、无限重试、全库扫描或大上下文解决质量问题；
- 把实验分支、兼容包、历史快照和当前生产主链混为一谈；
- 用一份跨项目大泥球替代模块边界和公开契约；
- 在没有真实返回值、错误路径和资源释放证据时宣称“已验证”。
- 把本地旧源码快照当成当前上游实现，未核对远程分支、提交时间和落后提交数就开始深度裁决。

### 后续每轮补充格式

后续第二至第五轮只允许向本节追加或修订三类内容：

```text
吸收：成熟、源码已证、能映射到底座边界的模式
废弃：源码证据不足、与底座铁律冲突或风险大于收益的模式
待核：有价值但需要继续读源码/测试/运行证据的候选
```

单个项目的具体证据仍留在它自己的 `ARCHITECTURE.md`；本节只保留跨项目的底座裁决，避免再次形成多源头。

## 166 个项目标准架构文档与跨项目共性裁决（2026-08-21）

> 本节是对 166 个项目根 `ARCHITECTURE.md` 的首轮横向归纳，不替代任何单项目事实文档。现场已确认 166/166 个 Git 仓库均有根架构文档；166 份文档均包含 ` ```text ` 流程图。统计只用于确认标准覆盖，具体实现结论仍以各项目源码证据为准。

### 一、标准 Markdown 已形成固定骨架

166 份文档虽然项目类型不同，但有效文档基本收敛到以下顺序：

```text
项目身份/定位与证据边界
  → 总体文本流程图
  → Git 分支/提交/远程/新鲜度
  → 真实目录地图与分层职责
  → 核心数据模型/持久化/资源所有权
  → 真实写入、读取、执行、事件或查询调用链
  → API/CLI/SDK/插件/协议/ABI 边界
  → 技术栈、第三方依赖与构建配置
  → 测试结构、已执行验证与未执行事项
  → 已实现/仅声明/未实现/未验证矩阵
  → 风险、阻断缺口、后续复核顺序
  → 源码证据路径与版本基线
```

标准的核心不是章节名称完全一致，而是必须回答五个问题：

1. **它到底是什么**：库、模块、应用、前端、服务、协议 SDK，还是只完成 ABI/元数据的工程骨架？
2. **真实怎么跑**：输入从哪里来，经过哪些模块，在哪里写入/查询/执行，结果如何返回？
3. **边界在哪里**：第三方库、外部服务、宿主运行时、数据库、浏览器、系统 API 和其他仓库分别负责什么？
4. **什么已经证明**：源码静态证据、测试源码、历史构建日志和实际运行验证必须分级，不能混成“已完成”。
5. **什么还不能证明**：未安装、未构建、未连接、未运行、远程版本漂移、缺少外部依赖和资源释放缺口都要明确写出。

### 二、跨项目反复出现的真实共性

#### 1. 契约先于实现，注册表连接契约与实现

`llama_index` 的 core/integration、`Verba` 的五类组件、`OpenHands` 的 typed client/manifest、Graphiti 的 driver/operations，以及易语言项目的 `LIB_INFO`/`CMD_INFO`/函数指针表，都反复证明同一模式：

```text
公开契约/元数据
  → 注册表或名称/索引解析
  → 具体实现/provider
  → 统一结果/事件/状态
```

平台应吸收：

- 能力 id、契约版本、参数/返回/错误码、资源释放行为必须有唯一来源；
- 注册表既是运行时分派表，也是持久化恢复/版本兼容的路由表；
- 注册、发现、装配、调用和发布门禁必须检查同一份契约，不能各自维护“差不多”的列表；
- 接口存在、元数据存在、函数符号存在，不等于目标能力实现。

#### 2. 稳定编排骨架与可替换 provider 分离

成熟项目普遍把稳定流程留在核心，把变化点放到 provider 或适配层：

- `llama_index`：core 定义 `VectorStore`/storage/index/retriever 契约，integration 独立发布；
- `Verba`：Reader → Chunker → Embedding → Retriever → Generator 五类组件由 Manager 编排；
- Graphiti：Graphiti 编排 ingestion/search，driver 和 operations 适配 Neo4j/FalkorDB/Neptune/Kuzu；
- `OpenHands`：前端只经 typed client、Cloud proxy 和 WebSocket 接入后端；
- `jywke`、`iconv`：易语言 ABI 适配层与 miniblink/libiconv 真实内核分层。

平台应吸收：核心模块只组合公开能力；第三方 SDK、模型、数据库、浏览器、动态库和外部协议只能在受管适配边界内出现；正式业务只接统一结果，不直接接 provider 异常和对象。

#### 3. 数据流通常是“摄取/转换 → 存储/索引 → 召回 → 合成/输出”

RAG、记忆和媒体项目高度重复这一主链：

```text
原始输入/事件
  → 解析、分块、标准化、抽取
  → 文档/节点/事实/向量/图/索引持久化
  → 词法/语义/结构/时间/图多路召回
  → 过滤、融合、重排、上下文预算
  → LLM/规则/组件合成
  → 带来源、状态、错误和流式进度的输出
```

`Graphiti`、`Cognee`、`llama_index`、`Verba` 和 `AriadneMem` 的差异主要在数据模型和召回策略，不在这条主链本身。平台底座应把“原始证据、派生事实、索引投影、查询结果、最终回答”分开保存，禁止用最终摘要反向覆盖原始输入。

#### 4. 事件、历史和实时投影是独立边界

`OpenHands` 的 REST 历史 + WebSocket 增量事件 + `eventIds` 去重，`Verba` 的导入进度 WebSocket，Graphiti/各记忆系统的 session/episode/事件时间，以及 Cognee 的 pipeline run/recovery，都说明：

- 历史读取与实时事件接收不能混成一次无序请求；
- 原始事件要有稳定 id、顺序/时间锚点、去重和重放语义；
- UI、进度、统计和状态是事件投影，不是原始事实源；
- 断线恢复要有 since/all、补偿、幂等和资源释放策略。

这直接支撑现有底座的“事件账本 → 状态投影 → 可重放读模型”设计，应继续保留并落实到统一事件契约。

#### 5. 记忆与状态必须区分来源、时间和生命周期

Graphiti 的 `valid_at/invalid_at/expired_at`、Cognee 的 dataset/provenance/session 双通道、LangMem 的 namespace/Store/checkpoint 区分、AriadneMem 的原子记忆与增强索引，以及已有 05 区研究共同说明：

- 原始对话/证据、会话缓存、语义事实、画像/偏好、程序技能、项目状态、索引摘要不是同一种数据；
- 事实的发生时间、系统记录时间、失效时间和当前投影时间不能只存一个 `updated_at`；
- 记忆更新必须产生新版本/新证据/新事件，不能让 LLM 直接覆盖权威状态；
- namespace、dataset、tenant、项目和权限范围必须进入写入与查询边界。

平台应把 `valid_at/known_at` 语义、来源链、版本、撤销/失效和权限过滤纳入统一契约，而不是留给每个模块自行解释。

#### 6. 预算、有界执行和资源释放是架构能力，不是优化项

`llama_index` 的 token budget、Graphiti/Cognee 的并发闸、OpenHands 的历史/重连/事件边界、Verba 的批量上传、易语言项目的大量句柄/窗口/外部 DLL 风险，都反复暴露同一问题：

- 输入大小、批次、候选数、上下文 token、并发、队列、重试、超时、日志和缓存必须有上限；
- 每个线程、进程、子进程、连接、句柄、临时文件、外部 WebView 和动态库都有明确释放路径；
- “有取消接口”不等于真正取消；“有析构函数”不等于所有权闭环；
- 异步任务完成、失败、取消、超时和进程崩溃必须分别定义结果和证据。

这与平台已有资源监督、租约、强杀回收、独立进程和慢速层门禁完全一致，应作为硬门禁继续执行。

#### 7. 安全边界必须穿过宿主、输入和 provider

样本中的共同风险包括：外部 manifest/工具被当作可信指令、路径/SQL/JavaScript 直接拼接、密钥进入前端或日志、默认关闭 TLS 校验、宽松 CORS、单用户缓存误当租户隔离、旧 provider 直接 import 进主进程、C 扩展退出崩溃等。

平台应固定：

- 外部输入先校验、准入和能力协商，再生成动作；
- manifest、工具、LLM 输出只能是候选/请求，不得越过授权和确定性服务直接改变权威状态；
- 凭据只以引用/受控环境变量进入 provider，日志和事件必须脱敏；
- 路径、SQL、JS、命令、ZIP、模型输出和反序列化分别有专门边界；
- 不可控第三方或 C 扩展进入独立进程，主进程只接统一 JSON/结果契约。

#### 8. 测试结构必须验证真实边界，不能只验证模型存在

最有参考价值的项目不是“测试文件最多”，而是能把边界写成测试：

- OpenHands：禁止直接 HTTP 调用的静态规则、manifest 全量准入、历史/实时事件和 mock-LLM E2E；
- `llama_index`：core 与 integration 分包测试、构建/类型检查/发布矩阵；
- Graphiti：provider、检索安全和 driver 路由测试；
- `jywke`：独立测试程序和例程验证真实 WebView 生命周期；
- Verba：反例是只有少量数据对象测试，不能证明 API/WebSocket/Weaviate/LLM 端到端。

平台应继续要求：契约测试、真实返回值测试、资源释放测试、故障/超时/取消测试、跨进程测试、发布门禁和未执行项分开记录；“测试文件存在”“历史构建日志存在”“子代理声称通过”都不能替代真实退出码证据。

### 后续批量深挖的统一标准：从“架构概览”升级为“底座取证包”

后续再派发项目研究任务时，任务信不能只写“请分析架构并生成 Markdown”，而要明确要求子代理交付可直接用于底座设计的取证包。每个项目至少需要以下内容：

#### 1. 契约与对接方式

```text
调用方
  → 包级公开入口/SDK/路由
  → 能力 id、注册表或命令索引
  → 模块编排器
  → provider/第三方/宿主 API
  → 结果转换与错误归一化
  → 事件、状态、投影或最终输出
```

必须逐节点写清：入口符号、参数类型、传值/传址/借用/所有权、返回形状、错误码、可重试、超时、取消、幂等、版本兼容和谁负责释放。只写“调用某模块”“接入某 SDK”不算完成。

#### 2. 每个小节点的细节

关键节点必须形成“职责—输入—输出—状态—读写—上下游—失败—恢复—证据”九字段记录，至少覆盖：

- 入口装载和配置解析；
- 注册表发现、能力选择和版本匹配；
- 参数校验、默认值、数据转换和错误转换；
- 核心执行、队列/线程/进程调度和并发边界；
- 数据写入、索引、召回、重排、上下文装配和输出；
- 事件生成、历史补偿、去重、重放和状态投影；
- provider 不可用、第三方异常、部分成功、回滚和重启恢复。

每个节点都要回到真实 `path:line` 或真实测试/运行输出，不能用项目 README 的功能列表替代。

#### 3. 资源控制与释放

每份架构文档必须单独列出资源生命周期，而不是把“资源管理”写成一句泛话：

| 资源 | 创建/获得 | 持有/转移 | 正常释放 | 失败/超时/取消释放 | 崩溃后清理与验证 |
|---|---|---|---|---|---|
| 内存/指针/对象 |  |  |  |  |  |
| 文件/临时目录 |  |  |  |  |  |
| 数据库连接/事务/游标 |  |  |  |  |  |
| HTTP/SDK 会话 |  |  |  |  |  |
| 线程/线程池/队列 |  |  |  |  |  |
| 进程/进程组/动态库 |  |  |  |  |  |
| 模型上下文/GPU/浏览器/WebView |  |  |  |  |  |

必须同时检查上限：输入大小、批次、队列、并发、候选数、上下文 token、重试、超时、日志、缓存、进程存活时间和临时文件数量。重点验证“用完释放”，而不是只确认“有一个 close/free/析构函数”。

#### 4. 防假绿验证

以后统一使用以下证据等级：

```text
L0：README/注释/命令表/函数声明存在
L1：源码中存在可执行路径
L2：测试源码覆盖该路径
L3：本轮真实执行，记录命令、退出码、测试数和输出
L4：外部依赖/真实宿主/真实服务/真实资源释放已验证
```

只有 L3/L4 才能写“本轮验证通过”；L0/L1 只能写“已声明/源码存在”，L2 只能写“有测试覆盖但未运行”。以下情况一律不能算通过：

- 测试文件存在但没有断言、只打印或依赖外部状态未说明；
- `skip`、空实现、固定返回值、历史构建日志、已有二进制或子代理回执；
- 只测成功路径，不测缺依赖、非法输入、重复、超时、取消、崩溃、回滚和二次释放；
- 只验证内存 mock，不验证真实 provider、数据库、HTTP、浏览器、进程和文件残留；
- 只看到命令/组件元数据就声称业务能力实现。

#### 5. 任务回传必须能被主代理验收

后续每个子代理回传必须包含：

1. 契约表所在章节和源码证据；
2. 真实对接调用链和每个关键节点；
3. 资源生命周期表及四种终态；
4. L0-L4 真假验证等级、命令、退出码、测试/跳过数；
5. 修改文件和未修改边界；
6. 未验证事项、阻断风险和下一步复核顺序。

主代理仍必须回读文档和源码，不能按回执直接验收。该标准的目的不是把 Markdown 写长，而是把每个开源项目变成可比较、可复用、可审计的底座取证单元。

### 研究轮次与单链路底座原则

后续研究不能第一轮看完项目就直接把它接进平台，必须分三轮推进：

#### 第一轮：项目事实建档

只回答“项目本身是什么”：入口、目录、模块、数据模型、调用链、接口、依赖、测试、Git 新鲜度和实现/声明/未验证边界。第一轮产物是项目根唯一 `ARCHITECTURE.md`，不做平台改造判断。

#### 第二轮：项目内部深挖

只围绕项目自身继续取证：契约、对接、关键小节点、资源生命周期、并发、失败/超时/取消/崩溃恢复、权限、安全、成本、测试真假和版本兼容。必须形成契约表、节点表、资源表、失败矩阵和验证等级，不能把平台概念硬套进去。

#### 第三轮及以后：基于底座映射和裁决

从第三轮开始才把项目能力映射到平台已有的公共契约、支持库、模块库、运行核心和统一网关，逐项判断：

```text
复用现有能力
  / 升级现有支持库
  / 升级现有模块
  / 建立新的原子能力
  / 废弃或隔离项目模式
  / 继续待核
```

第三轮交付必须有：现有能力命中表、缺口表、单链路落点、复用/升级/新建/废弃裁决、依赖与资源契约、验收契约和装配计划。缺少需求确认、能力搜索、复用决策、占用租约、验收契约、装配计划和工作包时，不修改生产底座。

#### 单链路原则：一个功能只能有一个权威归属

底座不是把 166 个项目各接成一条新链，而是把同类能力收敛到一个 owner 和一条可审计调用链：

```text
正式代码/上层项目
  → 项目适配层（版本、配置、权限、路径、别名）
  → 模块库公开入口（领域流程编排）
  → 唯一能力调用器/能力注册表
  → 支持库公开能力（一个能力 id 一个契约 owner）
  → 受管 provider/独立进程
  → 数据库、系统 API、第三方 SDK 或外部协议
  → 统一结果、事件、资源释放和证据
```

固定裁决：

1. **一个原子功能**只有一个规范能力 id、一个契约 owner、一个公开入口和一条注册/调用路径；历史英文键或别名只能在唯一入口归一化，不能由每个消费者各维护映射。
2. **一个模块**只负责一个领域流程，只通过支持库公开入口组合能力；不同 provider 是同一模块契约下的策略，不复制一套业务流程。
3. **一个能力系列**共享领域契约和数据结构。比如文档解析系列统一输出通用文档结构，各格式差异留在 provider，模块层只做一次统一转换。
4. **一个权威写 owner**：事件、事实、状态、索引、制品、激活指针和证据分别明确写入服务；其他层只能读或提交公开命令，禁止旁路写库。
5. **禁止侧链**：正式代码直连第三方、模块各自实现同一能力、消费者各自翻译错误码、隐藏 fallback、绕过统一网关、provider 对象穿透契约、兼容旧入口复制第二套内核。
6. **资源责任跟随调用链传递**：创建者声明持有者，转移必须显式，释放必须覆盖正常完成、业务失败、超时、取消和崩溃，并有现场证据。

这就是“支持库 + 模块库”不产生多条链路的核心：支持库拥有原子能力，模块拥有领域编排，运行核心拥有装载/调度/资源/调用治理，统一网关拥有对外入口；上层项目只做适配，不再自己造一套。

### 三、必须区分的三类共性

| 类别 | 可以吸收 | 不能直接泛化 |
|---|---|---|
| Agent/记忆/RAG 共性 | 证据→事实→索引→召回→上下文→合成；时间/来源/namespace；预算与事件投影 | 某个项目的 prompt、模型、向量库默认值、性能数字 |
| 应用/前端/服务共性 | typed client、组件契约、manifest 准入、REST+WebSocket、状态投影、部署/测试分层 | OpenHands/Verba 的具体 API、认证方式、单用户或 Cloud 拓扑 |
| 易语言支持库共性 | `GetNewInf`、`LIB_INFO`、命令索引、ABI 参数、动态/静态工程、宿主通知、x64 配置检查 | “命令已登记”推导“功能已实现”；某个 `.fne` 历史产物推导当前可构建 |

### 四、跨项目裁决清单

#### 吸收

1. 契约、注册表、provider、统一结果和资源释放五件事必须成套设计。
2. 原始证据、派生事实、索引投影、实时事件、最终输出必须分层保存。
3. 热路径、异步巩固、失败恢复、历史重放和发布回滚必须有不同状态与证据。
4. 多路检索、上下文预算、能力准入、事件去重和版本兼容应成为平台公共能力。
5. 真实外部依赖必须有可用性探测、独立环境、超时、取消、重试上限和崩溃回收。
6. 每个架构结论必须回到 `path:line`、测试退出码或可复现运行证据。

#### 废弃

1. 把元数据、接口声明、README、论文、历史构建产物或旧细探当作当前实现证明。
2. 复制多套 provider 注册、能力调用、记忆写入、检索内核或错误结果结构。
3. 让全局 singleton、隐式 fallback、默认空权限、无界队列和无限重试承担治理职责。
4. 把已归档项目的组件边界、旧依赖和安全配置直接搬进平台生产链。
5. 把易语言项目的 ABI 骨架与真实后端实现混为一类，或根据命令名补写不存在的功能。

#### 待核

1. 各项目真实运行时的资源上限、并发行为、故障恢复和跨进程语义仍需按价值分批实测。
2. Graphiti/Cognee/LangMem/AriadneMem 的长期记忆模型还需统一比较 `valid_at`、`known_at`、namespace、冲突和删除语义。
3. OpenHands/llama_index 等多仓库项目的跨仓契约、版本兼容和发布回滚还需建立版本矩阵。
4. 易语言区的 x64、静态库、宿主 ABI、句柄宽度、组件序列化和真实返回值需要 Windows 隔离环境验证。
5. 剩余旧 `细探-*.md` 只有在逐份吸收、人工核对并回读正式文档后，才允许清理。

本轮继续核对的 Elephant-Agent、MIRIX、OpenHuman、Letta、MemOS、coze-studio 等项目又补充了五条底座事实：事件通知不等于可重放事件账本；内存队列、传输队列和持久任务必须分层；Redis/缓存/向量/全文/图索引不能成为第二事实源；REST、WebSocket、CLI、MCP、SDK 必须汇聚到一个领域执行内核；旧仓库名称和历史实现不能代替当前 checkout 的源码证据。它们已合并到系统工程平台 `项目说明.md` 的第三轮样本结论中。

### 五、对系统工程平台的直接影响

当前八层底座框架不需要推翻，横向阅读反而验证了它的方向。应补强的不是再增加一层，而是给现有八层增加以下横向硬契约：

```text
证据层：原始输入、来源、版本、哈希、不可覆盖、可追溯
记忆/状态层：生命周期、namespace、valid_at/known_at、版本投影
检索/上下文层：多路召回、权限过滤、预算、来源标记、降级
执行层：契约注册、provider 隔离、任务 admission、统一结果、事件投影
治理层：准入、授权、反馈验证、故障注入、资源监督、审计
制品层：不可变摘要、环境指纹、版本兼容、激活指针、回滚证据
横向门禁：真实返回值、失败/取消/超时、资源释放、依赖防火墙、远程新鲜度
```

本节结论：166 个项目不是 166 套可直接复制的系统，而是反复验证了少数稳定架构规律。后续底座升级应优先封装这些规律，优先拒绝“声明即实现、摘要即事实、异步即完成、provider 直连、无界资源和无证据通过”六类错误。

3. **系统工程平台 `支持库总览.md` / `模块库总览.md`**：各自清单、职责、公开能力和组合边界；
4. **各源码项目根 `ARCHITECTURE.md`**：该项目自身源码事实、版本、调用链、风险和验证等级；
5. **各包 `包声明.json`、参数契约和验证引用**：字段级和能力级机器可读事实；
6. **旧细探、探索文档、异步回执和临时报告**：施工材料，不得作为独立事实源。

研究批次采用小批次滚动：

- 每批最多 10 个真实工作包，回收一个、现场验收一个、确认落盘一个，再补一个；
- 已有有效第三轮文档的项目不重复派发；
- MCP 错绑、目标无代码图或验证器拒绝目标路径时，记为待核/弱验证，不冒充正式证据；
- 子代理回执只作线索，完成数按目标文件、章节、范围和父代理现场验证计算；
- 同一个原子能力的候选项目先进入对比清单，不直接接入平台生产链；
- 没有能力需求、复用决策、契约、资源预算、装配计划和验收工作包，不启动底座实现。

### 人工收口纪律（华哥明确）

源码研究进入收口阶段后，主协调者按单项目顺序处理：

```text
读取一个项目的 ARCHITECTURE.md
  → 读取对应旧细探
  → 回到源码逐条核对
  → 只把源码确认事实吸收到唯一架构文档
  → 标出未确认、阻断和验证等级
  → 父代理肉眼回读确认无漂移
  → 删除已经完整吸收的旧细探
  → 再处理下一个项目
```

子代理可以继续在后台取证，但回执、临时报告和子代理推理都不是事实源；未经主协调者逐份回读的项目不得计入“已收口”。架构记忆只能进入本主文档、系统工程平台 `项目说明.md`、下层总览或对应项目根 `ARCHITECTURE.md`。华哥的原始表达单独记录在 `用户架构表达记录.md`，只作旁路施工记录，不得混入架构事实。

固定禁止：

- 不把助手自己的推测、扩展思路或“看起来合理”的设计写成源码事实；
- 不因为文档太长而删掉已确认的架构事实，必要时只把原始用户表达放入旁路记录；
- 不在未吸收、未核对前删除旧细探；
- 不因子代理 `completed`、文件存在或结构检查通过，就跳过主代理人工回读。

当前阶段收口验收标准：

```text
文档已收口 = 权威层级明确 + 冲突表述清理 + 关键决策回读
研究已完成 = 项目 ARCHITECTURE.md 写入 + 第三轮裁决人工核对
实现已验证 = 真实注册表调用 + 真实返回 + 资源释放证据
待核 = 文件存在但缺少真实运行、目标绑定、失败路径或资源证据
```

### 后续发展（裁决方向）

基于现有 166 仓库，后续对华哥平台的落地裁决优先级（待华哥拍板后启动）：

1. **个人记忆边界定型**：以 Second-Me / MemOS 的「身份-状态-投影」三层结构为参照，确定华哥人脉数据系统的记忆边界与回滚机制，避免一次聊天污染长期人格。
2. **事实有效期与图谱**：以 Graphiti 时间知识图谱 + Hindsight retain/recall/reflect 分层，建立「带有效期的证据」模型，对接人脉数据 PostgreSQL 权威库。
3. **Hermes 接入范式**：以 Icarus（Hermes 插件模式）为准，个人记忆/训练数据抽取走插件而非平行 Agent 中枢。
4. **媒体蒸馏链路**：以 30 类媒体工具（FunASR/PyAV/PaddleOCR/FlagEmbedding 已在系统工程平台封装为受管提供者）为底座，打通录音→视频→OCR→向量→人像是人脉蒸馏输入。
5. **代码地图复用**：`00_catalog/代码地图/` 已生成 struct/call/tree 索引，可作为快速定位工具，避免重复 grep 全仓。

> 注意：以上为「候选方向」，未启动任何实现；任何落地必须先有华哥确认的需求与任务信。
