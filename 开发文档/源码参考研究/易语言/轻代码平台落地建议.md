# 从易语言工程架构落地轻代码平台

## 文档定位

本文是对《易语言（e.7z）架构参考》的工程化转译，不是对易语言的复述，也不是要求照搬其二进制格式。目标是回答一个落地问题：如何保留“用户可视化开发 + Agent 生成开发 + 可扩展能力库 + 可发布制品”的优点，同时避免 PE32、裸函数指针、隐式全局状态和不可审计模块格式。

```text
易语言的有效经验
  结构化工程树 + 支持库元数据 + 编译目标矩阵 + 运行核心 + IDE 扩展
          │
          ├─ 保留：同一工程模型服务人和 Agent
          ├─ 保留：声明、实现、制品、运行时分层
          └─ 改造：公开契约、受管 Provider、可迁移 IR、证据链
```

## 先给结论

新平台的唯一事实源应是版本化项目 IR，而不是编辑器文本、数据库私有表或某个 Agent 的提示词。用户和 Agent 都只能读写 IR；编译器把 IR 编译成带能力锁定和权限边界的执行计划；运行核心通过唯一能力注册表调用受管 Provider；发布只激活不可变制品。

```text
用户 IDE ─────┐
              ├─→ 项目 IR ─→ 契约校验 ─→ 编译计划 ─→ 运行核心 ─→ Provider
Agent 工具 ───┘       │            │             │            │
                      ▼            ▼             ▼            ▼
                 版本/差异      权限审计      制品摘要      调用证据
```

## 推荐总架构

```text
┌─────────────────────────────────────────────────────────────┐
│                         平台控制面                           │
│  项目目录  能力目录  包仓库  策略  制品  发布指针  证据账本    │
└──────────────┬──────────────────────────────────────────────┘
               │声明、版本、权限、发布事务
┌──────────────▼──────────────────────────────────────────────┐
│                         项目 IR 层                           │
│ 项目/模块/页面/流程/节点/变量/资源/事件/能力调用/目标矩阵      │
└───────┬─────────────────┬───────────────────┬────────────────┘
        │                 │                   │
        ▼                 ▼                   ▼
   用户 IDE 视图       Agent 编排器        校验/迁移器
        │                 │                   │
        └─────────────────┴──────────┬────────┘
                                     ▼
┌─────────────────────────────────────────────────────────────┐
│                         编译与运行核心                       │
│ IR 解析 → 类型/权限校验 → 计划生成 → 调度 → 资源/取消/超时   │
│                         唯一能力调用器                       │
└──────────────────────────┬──────────────────────────────────┘
                           │能力 id + 契约版本 + 受管上下文

              │       Provider 层       │

              └─────────────────────────┘
```

## 与易语言的逐项映射

| 易语言观察 | 新平台落点 | 不照搬的部分 |
| --- | --- | --- |
| `LIB_INFO` + `GetNewInf` | `包声明.json` + 能力契约 + 包级公开入口 | 不把 C 结构体直接当跨进程协议 |
| 命令数组/方法索引 | 稳定 `能力 id`、契约版本、迁移别名 | 不允许删除或重排后复用旧 id |
| `.fne/.fnl/.fnr/.lib` | 编辑声明、运行 Provider、构建制品三种包层 | 不让编辑包隐式携带可执行任意代码 |
| `.e8` | 项目声明、目标矩阵、用户常量、源清单 | 不让配置覆盖权限或偷偷改写源码 |
| `.ec` | 可审计模块 IR + 依赖锁 + 版本迁移器 | 不把模块做成不可 diff 的黑盒加密文件 |
| `MacroProcessor` | 编辑期扩展 API | 权限、生命周期和资源预算显式声明 |
| `CompileProcessor` | 编译期变换器 | 只能修改受限 IR 和元数据，不能任意写发布目录 |
| 运行 `.fnr`/外部 DLL | 受管 Provider | 原生扩展独立进程，超时/取消/释放可证据化 |
| `epackage/setup` | 制品打包、签名、激活、卸载事务 | 不从源码分支回滚，不用安装副作用代替发布账本 |

## 项目 IR 的最小形状

```text
项目
  ├─ 身份：项目 id、版本、作者、兼容目标
  ├─ 模块[]
  │    ├─ 模块 id、版本、公开入口、依赖锁
  │    ├─ 页面/流程/组件/资源
  │    └─ 事件 → 节点图 → 能力调用
  ├─ 类型[]：基础类型、对象类型、数组、错误类型
  ├─ 能力调用[]：能力 id、契约版本、参数、错误策略、权限
  ├─ 目标[]：桌面、服务、Agent、批处理等运行目标
  ├─ 提供者锁：能力 → Provider → 制品摘要
  └─ 证据[]：编辑、校验、编译、运行、发布
```

每个节点必须有稳定 id、输入输出类型、来源位置和可重放参数。显示文本、布局坐标和 Agent 生成理由是视图/审计信息，不应成为执行语义的唯一来源。

## 用户开发与 Agent 开发共用一条链

```text
用户拖入组件/节点 ──┐
                     ├→ IR 变更集 → 语义校验 → 预览执行计划
Agent 生成节点 ──────┘                         │
                                              ▼
                                    用户确认或策略自动批准
                                              │
                                              ▼
                                   编译、运行、发布证据
```

Agent 不应直接生成 Python、Shell 或任意插件代码作为第一产物。推荐顺序是：先生成 IR 变更集，再由平台能力搜索器补齐能力契约，最后由编译器生成执行计划。需要自定义代码时，将其封装成独立受管 Provider，经过同一依赖防火墙和发布门禁。

## 三类扩展协议

```text
编辑期扩展
  输入：当前 IR 片段、光标/选择、只读能力目录
  输出：编辑命令或 IR 补丁
  限制：不得执行任意系统命令，不得绕过撤销栈

编译期变换器
  输入：已校验 IR、目标矩阵、只读依赖锁
  输出：新的 IR/执行计划/制品元数据
  限制：变更可 diff、可回滚、不可写入激活目录

运行期 Provider
  输入：能力契约参数、请求上下文、租约/权限
  输出：统一结果（成功、值、错误码、错误说明）
  限制：超时、取消、资源上限、释放和调用证据必须闭环
```

扩展注册时必须声明扩展类型、版本、所需能力、读写路径、网络范围、资源上限和卸载动作。易语言把三类扩展都压进 DLL/通知模型，新平台应在协议层拆开。

## 组件与 UI 设计器落点

易语言的 Delphi EDK 证明一个组件至少需要“创建、属性读写、属性持久化、属性可用性、事件通知”五组契约。新平台可以把它们设计成纯声明 + 宿主适配器：

```text
组件包声明
  ├─ 组件类型、图标、容器能力
  ├─ 固定属性与自定义属性 schema
  ├─ 属性默认值、可见/可用条件、迁移规则
  ├─ 事件名称、参数契约、取消/返回值语义
  ├─ 设计态预览 Provider
  └─ 运行态 Provider/资源释放策略
```

设计器交互建议保持单向可审计：

```text
用户修改属性
  → 生成 SetProperty IR 命令
  → 校验属性类型/权限/依赖
  → 写入撤销栈和变更集
  → 设计态预览
  → 保存 schema 版本化属性块
```

不要让设计器直接把窗口句柄、跨 DLL 指针或宿主对象地址写进项目文件。易语言的 `EVENT_NOTIFY2` 只应转译为“组件 id + 事件 id + 参数值”，而不是复用内存布局。

## 编译器落点

### 目标矩阵

```text
同一项目 IR
  ├─ Agent 任务：执行计划/工具调用
  ├─ 服务：HTTP/队列/定时任务
  ├─ 桌面：组件宿主 + 本地 Provider
  ├─ 批处理：无 UI 的可重放流程
  └─ 发布包：不可变制品 + 运行时锁
```

目标选择只能改变受支持的后端和资源策略，不能改变项目语义。编译器应输出：IR 摘要、能力依赖、Provider 锁、权限集合、资源上限、可执行计划、源映射和制品哈希。

### 推荐编译阶段

```text
1. 读取项目 IR 与模块锁
2. 解析能力 id 和契约版本
3. 类型检查、事件检查、目标兼容检查
4. 权限/路径/网络/资源预算检查
5. 生成规范化中间表示
6. 绑定唯一 Provider 与不可变制品
7. 生成执行计划和源位置映射
8. 运行静态检查与最小沙箱试运行
9. 签名/摘要/写入制品仓库
```

编译后动作必须是平台控制面登记的工作包，而不是任意 `post_link_action`。需要外部工具时，应在独立执行单元中运行并记录命令、输入摘要、输出摘要和退出码。

## 运行核心落点

```text
启动请求
  → 校验制品摘要/激活指针
  → 创建请求上下文和授权租约
  → 加载执行计划
  → 调度节点
      ├─ 解析能力注册表
      ├─ 选择锁定 Provider
      ├─ 注入超时、取消、日志和资源预算
      └─ 统一转换结果/异常
  → 关闭 Provider、队列、临时文件和租约
  → 写入完整调用证据
```

核心不能因为 Provider 缺失就静默换另一个实现。幂等重放只在能力 id、契约版本、Provider 摘要和输入摘要一致时成立；所有其他情况都应返回可诊断错误。

## 包与依赖治理

```text
包声明
  → 能力/契约扫描
  → 依赖图与版本范围解析
  → 单一 Provider 冲突检查
  → 完整性摘要
  → 隔离构建
  → 签名制品
```

建议包至少包含：`包声明.json`、`能力契约/`、`说明/`、`验证场景引用.json`、`完整性摘要.json` 和包级入口。原生扩展、动态库和不可控全局状态必须独立进程；正式代码不得导入第三方实现目录。

## 从旧工程迁移

```text
旧工程扫描
  ├─ 读取可读 .e8/INI/帮助/依赖清单
  ├─ 对 .e/.ec/.epk 标记“可迁移/需人工确认/不可解析”
  ├─ 建立命令/类型/事件映射表
  ├─ 将外部 DLL/OCX/运行库转成 Provider 候选
  ├─ 生成 IR 草稿和差异报告
  └─ 人工确认后编译为新制品
```

`.e/.ec/.epk` 的专有二进制字段不能假定可完全解码；迁移器应优先使用帮助目录、公开 SDK、样例和 `.e8` 配置重建语义。对无法确定的命令索引、资源块或授权状态，输出阻断项，不尝试猜测。

## 交付路线

```text
阶段 1：契约底座
  项目 IR、能力契约、统一结果、包声明、摘要和错误模型

阶段 2：运行闭环
  唯一注册表、Provider 隔离、租约、超时取消、调用证据

阶段 3：用户 IDE
  工程树、代码/流程视图、组件设计器、属性/事件和撤销栈

阶段 4：Agent 入口
  能力搜索、IR 变更集、预览执行计划、审批和回放

阶段 5：编译发布
  多目标编译、依赖防火墙、签名、不可变制品、激活/回滚
```

每个阶段都必须有可执行验收，不以“能打开界面”或“能导入一个示例”作为平台完成标准。

## 必须吸收的旁路经验

1. 运行依赖清单必须独立于源码：易语言的 `.fnr/.dll/.ocx/.npk` 说明真实运行环境常常在工程目录之外。
2. 用户态 IDE 状态必须可导出：配置、收藏、最近目标、插件和配色会影响行为，但不应污染项目语义。
3. 构建后动作必须治理：`tools/link.ini` 证明链接之后的命令同样是供应链边界。
4. 文档是能力契约的一部分：帮助目录中的命令、类型、属性和事件不能只作为展示文本，应能生成结构化说明。
5. 兼容性要靠追加和迁移：旧命令 id 不重排，新能力追加，重大变化通过契约版本和迁移器处理。

## 明确不采用的设计

```text
不采用：PE32/VC98 作为平台基线
不采用：裸函数指针作为跨进程公开协议
不采用：动态导入、全局单例或 sys.path 拼接第二套源码树
不采用：不可 diff 的加密工程文件作为唯一事实源
不采用：插件任意写发布目录或执行未登记命令
不采用：Provider 缺失时静默降级到未知实现
```

## 最小落点清单

```text
项目 IR schema              ← 用户和 Agent 共用
能力目录 + 契约版本         ← IDE 提示、Agent 搜索、编译绑定共用
唯一能力注册表              ← 运行时唯一解析点
受管 Provider               ← 第三方、系统和原生扩展边界
编译计划                    ← 类型、权限、资源和目标的可审计结果
制品仓库 + 激活指针          ← 发布和回滚事实源
证据账本                    ← 编辑、编译、运行、发布全链路
```

最终判断标准不是“像不像易语言”，而是用户拖拽、Agent 生成、Provider 执行和发布回滚是否都经过同一份可迁移 IR、同一套契约校验和同一条证据链。

## 证据来源与边界

- 架构事实主要来自 `/tmp/e语言研究.1xgEB2/sdk/cpp/docs.txt`、`sdk/cpp/elib/lib2.h`、`sdk/cpp/elib/PublicIDEFunctions.h`、`sdk/delphi/e.pas`、`sdk/delphi/docs/main.html`。
- 工程配置来自 `samples/e8/*.e8`、`tools/link.ini` 和 `lib/eTools/Set/*.json`、`lib/eTools/Data/*.ini`。
- 版本演进来自归档顶层 `readme.txt`；制品和启动链来自 `epackage/source/*.asm`、`epackage/readme.txt`、`linux/readme.txt`。
- 对 `.e/.ec/.epk` 的完整二进制字段、`e.exe` 内部 AST、授权/补丁行为没有作超出证据的断言。
