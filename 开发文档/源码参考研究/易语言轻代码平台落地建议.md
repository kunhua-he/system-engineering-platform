# 从易语言架构到新轻代码平台：落地建议

## 文档定位

本文是第二份、面向落地的建议文档。第一份[易语言架构参考](./易语言/ARCHITECTURE.md)只记录易语言自身的证据和推断；本文将这些机制转换为一个同时服务 Agent 和普通用户的新轻代码平台方案。

目标不是复刻易语言的二进制格式、32 位 ABI 或 Windows 控件，而是保留它最有价值的产品关系：

```text
用户/Agent 组织结构化项目
          ↓
编辑器看到可理解的能力、类型、事件和资源
          ↓
编译器把项目转成可验证执行计划
          ↓
运行核心按契约装配能力和 Provider
          ↓
网关执行并返回统一结果、状态和证据
```

## 一、推荐总架构

```text
┌────────────────────────────────────────────────────────────┐
│                         开发者体验层                         │
│  桌面/浏览器 IDE · Agent 项目生成器 · 能力搜索 · 文档/诊断      │
└──────────────────────────────┬─────────────────────────────┘
                               │ 读写项目 IR / 调用编译服务
                               ▼
┌────────────────────────────────────────────────────────────┐
│                         项目编译层                           │
│  IR 解析 → 结构校验 → 能力解析 → 依赖锁定 → 执行计划 → 制品      │
└──────────────────────────────┬─────────────────────────────┘
                               │ 只输出声明完整的执行计划
                               ▼
┌────────────────────────────────────────────────────────────┐
│                         唯一 HTTP 网关                       │
│  搜索 · 契约 · 执行 · 请求状态 · 租约 · 证据 · 取消 · 释放        │
└──────────────────────────────┬─────────────────────────────┘
                               │ 唯一跨边界调用路径
                               ▼
┌────────────────────────────────────────────────────────────┐
│                         运行核心                             │
│  能力注册表 · Provider 路由 · 进程/线程 · 资源预算 · 健康/恢复     │
└─────────────┬──────────────────────────────┬─────────────────┘
              │                              │
              ▼                              ▼
       支持库原子能力                    模块库领域流程
  文件/文本/PDF/数据库/LLM          文档解析/Agent/知识库/工作流
              │                              │
              └──────────────┬───────────────┘
                             ▼
                  受管 Provider / 外部系统
             Python · 原生库 · GPU · 浏览器 · 数据库 · 模型
```

### 与易语言的对应关系

| 易语言机制 | 新平台保留的思想 | 新平台替换实现 |
| --- | --- | --- |
| 工程树、窗口程序集、子程序 | 结构化项目 IR 和节点树 | JSON/数据库 IR，带版本和迁移器 |
| `.fne` 编辑/运行描述 | 包声明和能力契约 | 结构化声明 + 包级公开入口 |
| 命令表/参数表 | 能力 id、参数、返回、错误 | 唯一注册表 + 契约编译器 |
| `.ec` 易模块 | 可复用模块包 | 模块库包，只保存能力 id 和契约版本 |
| `.e8` 配置 | 项目配置与多目标构建 | 项目配置文件，不能覆盖核心事实源 |
| 编译前插件 | 编译器扩展点 | 受权限约束的编译变换器 |
| `.lib` 静态支持库 | 可选制品后端 | Provider 制品和可复现构建，不暴露裸符号 |
| `setup.exe` | 发布安装事务 | 制品仓库、激活指针、回滚事务 |

## 二、统一项目 IR

### IR 的职责

项目 IR 是用户 IDE 和 Agent 的共同语言，也是编译器的唯一输入。它必须能表达用户界面、流程、代码、资源、能力调用和调试信息，但不直接保存第三方对象、线程、数据库连接或 Provider 私有句柄。

```text
项目 IR
  ├─ project：项目 id、名称、版本、目标、作者
  ├─ modules：模块、页面、流程、公共子程序
  ├─ nodes：顺序、条件、循环、并行、事件、返回
  ├─ values：变量、常量、类型、默认值、作用域
  ├─ capabilities：能力 id、契约版本、参数映射
  ├─ resources：受管文件、图片、模型、密钥引用
  ├─ permissions：文件/网络/进程/设备/数据权限
  ├─ build：目标、Provider 锁、编译插件、输出制品
  ├─ debug：源位置、节点 id、断点、日志策略
  └─ evidence：编译摘要、调用记录、释放结果
```

### 最小 IR 示例

```json
{
  "project_id": "demo_document_agent",
  "ir_version": "1.0",
  "target": {"kind": "agent_service", "platform": "local"},
  "modules": [
    {
      "module_id": "文档问答",
      "nodes": [
        {"id": "读取", "kind": "能力调用", "capability_id": "文件系统.读取文件"},
        {"id": "解析", "kind": "能力调用", "capability_id": "文档解析.解析文档"},
        {"id": "回答", "kind": "能力调用", "capability_id": "对话.生成回答"}
      ]
    }
  ]
}
```

IR 的硬规则：

- `capability_id` 必须能在唯一注册表中解析到一个 owner。
- 所有跨模块、跨支持库、跨 Provider 的边界只保存可序列化值或受管句柄。
- 每个节点有稳定 id，源文件、界面组件、Agent 生成修改和运行证据都引用这个 id。
- 删除节点必须留下迁移/变更记录，不能静默改变旧节点的语义。
- IR 可以有多个视图，但不能存在第二份可执行事实源。

## 三、IDE UI 与内部架构

### 推荐的桌面/浏览器 IDE 布局

```text
┌─────────────────────────────────────────────────────────────┐
│ 项目  编辑  运行  调试  构建  发布    [搜索能力] [运行] [停止]    │
├───────────────┬───────────────────────────────┬───────────────┤
│ 项目/模块树     │ 中央编辑区                     │ 属性/契约检查器  │
│                 │                               │               │
│ 页面            │ ① 流程画布                    │ 当前节点        │
│ 流程            │ ② 结构化代码                  │ 参数            │
│ 子程序          │ ③ 表单/组件设计                │ 类型            │
│ 资源            │ ④ 差异/变更                    │ 权限            │
│ 依赖            │ ⑤ 调试状态                     │ 资源预算        │
├───────────────┴───────────────────────────────┴───────────────┤
│ 输出/诊断/调用证据/资源释放/Agent 操作记录                      │
└─────────────────────────────────────────────────────────────┘
```

### UI 模块职责

```text
项目树
  → 只负责导航和节点选择

中央编辑区
  → 只编辑 IR 投影
  → 不直接导入支持库实现

能力面板
  → 查询注册表的能力目录
  → 显示输入、输出、错误、权限、预算和示例
  → 插入节点时生成契约化参数映射

属性/契约检查器
  → 显示当前节点的类型、作用域、权限和资源占用
  → 参数不满足契约时即时标红

输出/诊断面板
  → 编译错误、运行错误、Provider 日志、请求 id、释放结论
  → 所有结果都可跳回 IR 节点和源位置
```

### Agent 与用户共用编辑内核

```text
用户拖拽/输入 ─────┐
                   ▼
              IR 变更命令
                   ▲
Agent 生成/修改 ────┘
                   │
                   ▼
             变更校验器
       ┌───────────┼───────────┐
       ▼           ▼           ▼
    类型校验     权限校验     依赖校验
                   │
                   ▼
              IR 版本提交
```

Agent 不应该直接写项目文件或调用 Provider。Agent 只能提交“添加节点、替换能力、修改参数、解释错误、生成测试”等结构化变更命令；宿主校验后再写入 IR。用户与 Agent 因而共享同一撤销、审计、冲突合并和预览机制。

## 四、编译器与快速反馈链

### F5/构建完整流程

```text
按下运行/构建
  │
  ├─ 读取当前 IR 和项目配置
  ├─ 检查 IR 版本和迁移状态
  ├─ 解析能力 id → owner/契约/provider
  ├─ 校验参数、类型、权限、资源预算
  ├─ 建立依赖图并检测循环
  ├─ 固化 Provider/制品/配置摘要
  ├─ 编译节点为执行计划
  ├─ 运行编译插件（只能改声明允许的字段）
  ├─ 输出可审计制品
  └─ 交给网关执行或发布事务
```

### 错误必须分层

```text
语法/IR 错误       → 编辑器节点错误，不启动 Provider
契约/类型错误      → 编译阻断，不生成可执行计划
权限/依赖错误      → 装配阻断，不允许越界访问
Provider 启动错误  → 运行错误，可重试/不可重试明确
业务能力失败       → 统一结果失败，保留请求证据
释放/回收错误      → 运行核心告警，不能伪装成成功
```

快速编译落点建议使用现有 `开发工具/快速编译/运行快速编译.py`；它应成为 IDE F5、Agent 预检和 CI 的同一入口，而不是再造一套 IDE 专用编译逻辑。

## 五、运行时与能力调用

```text
IR 执行计划
    │
    ▼
唯一 HTTP 网关
    ├─ 请求 id / deadline / 权限 / 大小限制
    ├─ 能力目录查询
    ├─ 参数契约校验
    ├─ 建立 execution/lease（必要时）
    └─ 统一结果和证据
    │
    ▼
运行核心
    ├─ 选择 Provider
    ├─ 启动/复用/健康检查
    ├─ 传递取消和超时
    ├─ 监督进程、线程、临时目录、句柄
    └─ 排空、释放、记录残留
    │
    ▼
Provider
    ├─ 纯标准库原子能力：可进程内
    ├─ 第三方库：受管适配器
    ├─ GPU/浏览器/原生扩展：独立进程
    └─ 外部系统：协议适配 + 失败转换
```

外部调用者永远只看到：

```text
请求 = 能力 id + 契约版本 + 参数 + 可选受管句柄
响应 = 成功 + 值 + 错误码 + 错误说明 + 可重试 + 证据
```

不允许把 Python 对象、C 指针、数据库连接、线程、队列、浏览器页面对象或 GPU 句柄写入 IR 或跨边界传递。

## 六、支持库、模块库和插件落点

### 支持库

适合放在 `支持库/`：一个稳定外部边界或一个原子动作，例如文件读写、文本处理、PDF 解析、数据库 SQL、模型调用、窗口描述。每个包需要：

```text
包声明.json
能力契约/参数契约.json
权限契约/资源预算/依赖锁
包级公开入口 __init__.py
实现/（私有）
说明/与验证场景
完整性摘要.json
```

### 模块库

适合放在 `模块库/`：跨两个以上原子能力的流程，例如文档读取、知识入库、Agent 任务、工作流。模块只保存能力 id 和契约版本，不能静态导入支持库实现，也不能自己启动 Provider。

```text
模块库/文档问答
  → 文件系统.读取文件
  → 文档解析.解析文档
  → 文本处理.分块
  → 检索.召回
  → 对话.生成回答
```

### 编译器插件

编译器插件应是受控变换器：

```text
读取 IR 摘要
  → 声明可修改字段
  → 校验项目权限
  → 产生 IR patch
  → 重新校验/重新摘要
  → 进入制品构建
```

不能允许插件直接改源码目录、发布指针、权限文件、依赖锁或任意外部路径。

## 七、项目内的具体落点

| 建议能力 | 当前平台落点 | 需要保持的边界 |
| --- | --- | --- |
| 基础类型/结果/句柄 | `公共契约/基础类型/`、`公共契约/错误结构/`、`公共契约/句柄体系.py` | 不让每个包自定义一套类型和错误 |
| 项目 IR | `公共契约/基础类型/文档结构.py` + `开发工具/项目编译/` | IR 是公开事实，编译器只读写 IR |
| 能力目录/注册 | `公共契约/能力契约/契约.py`、`平台控制面/能力目录/` | 一个能力一个 owner |
| 编译/预检 | `开发工具/快速编译/`、`开发工具/契约编译/` | IDE、Agent、CI 共用入口 |
| 用户/Agent IDE | `开发工具/轻代码前端编辑器/`、`开发工具/统一能力入口/`、`前端核心/` | UI 只编辑 IR，不碰实现 |
| 支持库 | `支持库/` | 原子能力、错误转换、资源释放 |
| 模块库 | `模块库/` | 只编排能力 id，不直连 Provider |
| 运行时 | `运行核心/`、`启动监督器/` | 调度、租约、超时、取消、恢复、释放 |
| 制品/安装/回滚 | `平台控制面/包仓库/`、`平台控制面/发布管理/`、`客户端/` | 不可变制品 + 激活指针 |

## 八、迁移和实施顺序

```text
阶段 0：冻结概念
  → project/module/node/capability/provider/lease/evidence 类型

阶段 1：先做可读 IR
  → JSON Schema/版本迁移/节点 id/变更日志
  → 用一个表单项目和一个 Agent 项目验证

阶段 2：能力目录和 F5
  → 搜索能力 → 查看契约 → 编译预检 → 统一错误

阶段 3：可视化 IDE
  → 项目树 → 流程画布 → 属性检查器 → 诊断/证据
  → 用户操作和 Agent patch 共用同一编辑命令

阶段 4：运行核心
  → 唯一网关 → Provider 路由 → 租约/取消/回收

阶段 5：模块和复用市场
  → 模块包 → 依赖锁 → 签名/摘要 → 安装/升级/回滚

阶段 6：多目标制品
  → 本地服务/Web/桌面/Agent 执行计划
  → 统一证据和发布门禁
```

## 九、必须保留的验收不变式

```text
一个能力 id
  → 一个契约来源
  → 一个 owner
  → 一个注册路径
  → 一个调用器
  → 一条证据链
```

```text
一次运行
  → 有 request_id
  → 有 deadline/预算
  → 有成功或失败结果
  → 有 Provider 版本和制品摘要
  → 有取消/超时状态
  → 有资源释放结论
```

```text
一次发布
  → IR/契约/依赖锁完整
  → 依赖防火墙通过
  → 制品摘要和签名固定
  → 激活指针事务提交
  → 旧制品可回滚
  → 不恢复源码旧分支、不旁路网关
```

## 十、明确不要复制的旧问题

- 用全局命令索引作为唯一兼容标识；新平台使用稳定 `capability_id + contract_version`，索引只作为内部实现细节。
- 把编辑元数据、运行实现、静态制品塞进同一个 DLL；新平台拆成声明、Provider 和制品。
- 用二进制工程文件作为唯一事实源；必须有可读 IR 和迁移器。
- 让模块直接拿到第三方对象或自己管理线程池、重试队列和资源回收。
- 让编译后动作、插件或安装器获得不受限的宿主写权限。
- 用 UI 宏/Agent 文本替换直接修改工程；所有修改都必须成为可审计 IR patch。

## 最终落点

```text
用户视角：我在 IDE 里搭页面、流程和能力，不需要懂底层库
Agent 视角：我生成同一份 IR，不需要伪造点击或直接写 Provider
开发者视角：我实现支持库/模块契约，不需要复制网关和生命周期
运行视角：我只执行经过编译、装配、授权和资源预算校验的计划
平台视角：我能搜索、验证、发布、回滚，并知道每次调用是否真正释放
```

这就是值得从易语言继承的“轻代码平台”核心：可视化只是入口，真正的产品壁垒是稳定的工程 IR、能力元数据、编译期校验、运行时治理和可追溯制品链。
