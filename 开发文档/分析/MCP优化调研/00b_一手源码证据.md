## 四、补充取证：`执行命令` 不走 shell（新登记）

- **现状**：`系统核心支持库.进程管理.执行命令` 的能力说明写明「与 `执行命令` 同口径：**直启不经 shell**」，
  但**没有警告 `|`、`*`、`>`、`2>`、`||`、`&&` 一律不可用**，且失败信息极具误导性。
- **本轮实测**（三条全部踩中）：
  | 我写的 | 真实返回 |
  |---|---|
  | `grep -n "x" f.py \| head -20` | `grep: \|: No such file or directory`（把 `\|` 当成文件名） |
  | `ls -la dir/ 2>/dev/null \|\| echo 无此目录` | `ls: 2>/dev/null: No such file or directory` |
  | `wc -c 路径/*.md` | `wc: 路径/*.md: open: No such file or directory`（**通配符不展开**） |
- **为什么算缺陷**：报错把"我不支持这个语法"伪装成"这个文件不存在"，调用方会去查文件而不是查语法
  —— 这正是"看不见的红项"在**入参层**的同族表现。而且它逼着 Agent 反复试错（又一轮往返）。
- **优化方向**：`执行命令` 检测到 argv 里出现 shell 元字符（`|` `>` `<` `&&` `||` `*` `$(` 反引号）
  时，**直接回一条明确的 400**：「本能力直启不经 shell，管道/重定向/通配符不可用；
  要串联用 `执行命令集`（命令表 + 模式），要通配用 `rg --glob`」。成本极低，收益是一整类往返。

## 五、补充取证：E2 的「默认精简」**不是随意，是有明文原则的**（结论要修正）

我上一轮在 `00_本项目内部审计.md` 里写「这套取向与华哥的判据相反」——**这个说法不准确，必须修正**。

`模块库/能力目录/能力定义.json:10` 与 `:45` 原文（`搜索能力` 的能力说明）明确写了依据：

> *"默认档＝「名称」：每条只回 能力id/名称/中文名称/包id/一句话说明 五个精简字段，
> 把 参数/行为/返回/资源预算 这类重字段挡在默认返回之外，**保住 Agent 的 prompt 前缀缓存**
> （依据 **P-9 第 6 条「精简字段默认返回」与第 2 条「返回指针而不是全文」**）"*

> *"`含常用参数=真` 时每条命中追加 `常用参数` … 默认 假 —— 每条挂 5 组会把返回体量放大数倍，
> 正是「调用几次打爆上下文」的成因；要细则就该显式要（与 细节级别 同一取舍）。"*

**所以真实情况是：平台上有一条明文设计原则 P-9（精简字段默认返回 / 返回指针而非全文），
它与华哥这次的元判据在"精确命中"这个场景上发生了冲突。**

冲突的**正确解法不是推翻 P-9**，而是**给 P-9 加一个场景例外**：

| 场景 | P-9 现状 | 建议 |
|---|---|---|
| 关键词模糊搜、多命中 | 精简（**正确，保持**） | 不改 |
| **精确命中单条**（1 命中） | 也精简 → 调用方必须再跑 `读取能力` 拿参数名 | **改为直接回完整契约**：1 条的体量本来就小，省掉的是整整一跳 |
| 调用失败（400 缺参数） | 只回"缺哪个参数" | **回带该能力的完整签名 + 一组真实样例** |

⇒ 即：**P-9 管"宽搜"，元判据管"精确命中"**，两者不矛盾，只是此前没有为精确命中开口子。
这条要作为**待华哥裁决项**列出（涉及既有原则的边界，不宜由我单方面改）。

## 七、补充取证：MCP 官方 Registry 的「元数据该带哪些字段」（E2/A2 的权威答案）

来源（真源码，本轮 clone）：
`/Users/hekunhua/.hermes/cache/scratch/开源调研/08/modelcontextprotocol_registry/docs/reference/server-json/draft/server.schema.json`
（该文件自带 `$comment`：*"auto-generated from docs/reference/api/openapi.yaml. Do not edit manually.
Run 'make generate-schema' to update."* —— **它本身就是生成物，这条对 D1 也是旁证**）

### 7.1 必填字段只有三个（极简主义）

`ServerDetail.required = ["name", "description", "version"]`，其中：
- `name`：**反域名格式**（`io.github.user/weather`），`pattern: ^[a-zA-Z0-9.-]+/[a-zA-Z0-9._-]+$`
- `description`：**≤100 字**，官方原文 → *"Clear human-readable explanation of server functionality.
  **Should focus on capabilities, not implementation details**."*
- `version`：语义化版本，**明确拒绝版本区间**（`not: {const: "latest"}`，`^1.2.3`/`~1.2.3`/`1.x` 全拒）

### 7.2 `Input` 类型的字段集 —— **这就是 A2 缺的东西**

| 字段 | 作用 | 本项目对应 |
|---|---|---|
| `isRequired` | 必填声明 | ✅ 有（`必填`） |
| `format` | **语义类型**：`string`／`number`／`boolean`／**`filepath`** | ❌ **缺**（我们只有"文本型"，没说"这是文件路径"） |
| **`choices`** | **枚举可选值列表** | ❌ **缺**（这是"猜取值"问题，比"猜参数名"更隐蔽） |
| **`placeholder`** | **示例值/引导** | ⚠️ 有近似物（`含常用参数`／`常用参数组合`），但**默认关** |
| `default` | 默认值 | ✅ 有 |
| `isSecret` | 敏感值标记（password/token） | ❌ 缺（本项目走"密钥引用"另一条路，可对照） |
| `description` | 参数说明 | ✅ 有 |
| `value` | 固定值（不可被用户改）+ `{curly_braces}` 变量替换 | ➖ 本项目用能力契约表达，形态不同 |

**⇒ 最值得照搬的是 `choices` 与 `format`**：
- `choices`：本项目 745 个能力里大量参数是**枚举式**（如 `细节级别` 三档、
  `冲突策略` 留空/整体拒绝/跳过占用、`模式` 串联/并行）。这些取值**写在说明文字里**
  而不是**机器可读的枚举字段**里 → 调用方只能读散文猜取值。加 `可选值` 字段是**纯收益**。
- `format: filepath`：让"文本型"带上语义。本项目 `文件路径`、`根目录`、`输出目录` 这类参数
  全靠参数名暗示，`format` 能把它变成机器可判。

### 7.3 安全声明的原文（印证本项目"不走 shell"是**正确**的）

`Argument` 类型的 `description` 原文：

> *"Warning: Arguments construct command-line parameters that may contain user-provided input.
> This creates potential command injection risks if clients execute commands in a shell environment.
> For example, a malicious argument value like ';rm -rf ~/Development' could execute dangerous commands.
> **Clients should prefer non-shell execution methods (e.g., posix_spawn) when possible to eliminate
> injection risks entirely.**"*

⇒ 本项目 `执行命令` **不走 shell 是符合业界安全共识的正确设计**。
本节第四部分登记的问题**不是"该改走 shell"**，而是**"该把不支持的语法明确告知"** ——
保持 posix_spawn 直启，只在检测到 shell 元字符时给一条可读的 400。
（这条要写清，防止后续有人误读成"给执行命令加 shell"。）

### 7.4 命名与版本的两条可比口径

- `name` 用**反域名**（`io.github.user/weather`）做全局唯一；本项目用**全中文能力 id**
  （`模块库.自修复工具` + `自修复工具.效率巡检`）——形态不同但**唯一性目标一致**，
  且本项目已明文「能力 id 全局唯一、中文显示名可跨包重复」，**不需要照搬反域名**。
- `version` **拒绝版本区间**：与本项目「契约版本不兼容 → 409」同源思路，口径一致。

### 8.2 工具类型三分法（可直接用作本项目归类口径）

官方原文：
- **Extension**：*"A tool executed on the **agent-side** to directly call external APIs, bridging the gap
  between the agent and real-world systems."*
- **Function**：*"A tool executed on the **client-side**, where the agent generates parameters for a
  predefined function, and the client executes the logic."*
- **Datastore**：*"A tool used by the agent to access and query structured or unstructured external data
  for retrieval-augmented tasks or knowledge updates."*

⇒ 本项目对照：`capability_call` 走 HTTP 到网关 → 属 **Extension**；
`execute_code` 类 → **Function**；`搜索能力`/`读取能力`/`仓库地图` → **Datastore**。
**这个三分法正好能当 F2"账本该按什么维度分类"的现成口径**，不用自己发明。

### 8.3 ★ 两条独立权威得出同一结论：必须声明枚举取值

OTel 的 `gen_ai.tool.definitions` **不是自由格式** —— 官方硬性要求：
> *"[14] `gen_ai.tool.definitions`: Instrumentations **MUST** follow
> [Tool Definitions JSON Schema](.../gen-ai-tool-definitions.json)."*

该 schema 的官方示例里，参数是这样描述的：

```json
"unit": {
  "type": "string",
  "enum": ["celsius", "fahrenheit"]
}
```

**把这条与第七节的 MCP Registry 合起来看：**

| 权威 | 枚举字段名 | 要求 |
|---|---|---|
| MCP 官方 Registry | **`choices`** | `Input` 类型的一等字段："If provided, the user **must** select one of these values" |
| OpenTelemetry GenAI | **`enum`**（JSON Schema） | 工具定义 **MUST** 遵循，官方示例带 `enum` |

⇒ **两个互不相干的标准化组织，都把"枚举取值"做成了机器可读的一等字段。**
本项目 745 个能力里大量枚举式参数（`细节级别` 三档、`模式` 串联/并行、`冲突策略` 三种、
`值类型` 多种）**目前只写在中文散文说明里** —— 这是 A2「猜参数」问题的**第二形态**：
- 第一形态（已知）：猜**参数名** → 本轮实测错 3 次（`命令列表`→`命令表` 等）
- 第二形态（新登记）：**猜取值** → 参数名对了，值写错，一样白跑一趟

**这条是本轮审计里"照搬外部成熟架构"最直接、代价最低、收益最确定的一条。**

### 8.4 一条治理教训：GenAI 语义约定已迁出主仓

上面 8.1 全部 7 个属性，在 `semantic-conventions` 主仓里都标着

（新地址：`github.com/open-telemetry/semantic-conventions-genai`）。
