## 一、元判据（后面每条都要用它称重）

华哥原话：
> *"尽量能节省时间，你访问 3 次，和你一次访问。本质上一次访问注入上下文再多，也没 3 次访问那么贵。这个是实打实的问题。"*

形式化：

```
真成本 = 往返次数 × 每轮全上下文注入

推论一：一次调用返回更多内容，几乎总是便宜于分多次各返回一点。
推论二：一次「什么都没拿到」的调用，是纯损失（成本照付，收益为零）。
推论三：判断任何优化值不值，只问一句 —— 它能不能减少往返次数？
```

**这条判据推翻了两个直觉**：

| 直觉 | 按元判据的实际结论 |
|---|---|
| 「返回体小一点更省」 | ❌ 错。返回体小到「拿不到答案」→ 必然重调 → **更贵**。 |
| 「错误信息简短更干净」 | ❌ 错。错误信息少一个字段（落点/修法/候选签名）→ 多一轮 → **更贵**。 |

## 五、待华哥裁决项

### 裁决项一：E2「默认精简」与「精确命中给全」的口径冲突

**事实**：平台**不是随意精简**，有明文原则 —— `模块库/能力目录/能力定义.json:10,45` 写着
**P-9 第 6 条「精简字段默认返回」+ 第 2 条「返回指针而不是全文」**，
且给出理由：*「保住 Agent 的 prompt 前缀缓存」*。

**冲突**：这条原则与元判据在**一个特定场景**下相反 ——
当搜索**精确命中单条**能力时，精简反而逼出第二次 `读取能力`（实测 `describe` 21 次）。

**我的建议**（不单方面改，请你定）：
- **保留 P-9 不动**（它在前缀缓存上的收益是真的）；
- **只开两个口子**：① 搜索**精确命中唯一一条**时直接给全签名（体量小，无缓存损失）；
  ② **调用失败**时给全签名（此时不存在缓存收益，只有下一轮成本）。
- 这两个口子不改默认行为，属「只增不改」。

### 裁决项二：A1 的改法在薄壳还是等 Hermes

**事实**：A1 的限制**落点在 Hermes 侧**（`tool_search_validation.py:196`），且**有意为之** ——
docstring 原话 *"small models re-send an identical batch when told only the constraint"*。

**两条路**：
- **路 A（推荐）**：薄壳加 `工具清单` 入参，**对 Hermes 零改动**。平台侧自己就能一次收多个。
- **路 B**：改 Hermes 源码放开限制。跨仓、影响所有 profile，**不建议**。

### 裁决项三：C2 要不要消除真空期

**事实**：`docker/compose` 证明「指望简单重建就零中断」**不成立**（`:55-56` 明写滚动更新只在 Swarm）；
本项目当前「数秒～数十秒真空期」与之**同档，是诚实口径**。

**选项**：① 接受真空期（照 `决策记录/0046` E1 执行，**代价 0**）；
② 消除真空期（需两进程共享 40007 socket / `SO_REUSEPORT`，改动中、风险中）。
