但 `常用参数` 是**历史入参样例**（来自 `公共契约.诊断.调用账本`，`能力目录.py:343-359`），**不是签名** —— 它不告诉你参数类型、必填、返回结构。

**第三个相关入口（不是 search 的口子，是独立能力）**：`能力目录.常用参数组合` —— `能力目录.py:486-526`，按能力 id 单独查历史入参。

**结论表**：

| 想要的东西 | 有口子吗 | 怎么拿 | 代价 |
|---|---|---|---|
| 参数名 / 类型 / 必填 / 默认值 / 返回结构 / 调用示例 | ✅ 有 | `细节级别="完整契约"` | 一条命中 = 38 键 |
| 真实能跑通的入参样例 | ✅ 有 | `含常用参数=true` 或 `能力目录.常用参数组合` | 每条挂 5 组 |
| **默认档命中即自动带签名** | ❌ **没有** | —— | —— |
| **「唯一命中」自动带签名** | ❌ **没有** | —— | —— |

**【改造点】**

- 若要「命中即给全签名」，落点就是 **2.3 的自动升档分支**（`能力目录.py:459-462`），或 **2.2 的「档一加参数骨架」**（`能力目录.py:54`）。
- 另一条更省事的路线（**不改能力，只改薄壳描述**）：把 `细节级别="完整契约"` 的**用法指引**写进 `capability_search` 的工具描述，让模型第一次搜就直接要全契约。落点 `开发工具/薄壳/工具清单.py:55-59`（现文案已在引导，但把默认档说成「只回指针，8 字段」——**字段数写错，见第五节第 2 条**）。

**【代价】**

- 改能力（自动升档 / 加字段）：`能力目录.py` + `能力定义.json` + 测试，**≥3 个文件**（同 2.2 / 2.3）。
- 只改薄壳描述：`开发工具/薄壳/工具清单.py` **1 个文件、几行**。⚠ 但薄壳是**常驻进程**，改完必须重启 MCP 客户端才生效（`工具清单.py:193-194`：`"薄壳为会话启动时的旧进程，盘上代码已更新；请重启 MCP 客户端后再调"`），`tool_catalog` 的 `是否一致` 会报假。

**【风险】**

1. **`含常用参数=true` 的口子有个隐藏成本** —— `_常用参数表` 对**每条命中各查一次账本**（`能力目录.py:350-351` docstring 明说「为什么一次只查一个能力」）。一页 10 条 = 10 次 SQLite 查询，在并发路径上会被 GIL 串行化（`能力目录.py:174-180` 记录了同类踩坑：`json.dumps` 单次 13.5ms、并发吞吐恒为 ~73 req/s）。
2. **「命中即给全签名」与「返回体量可控」是同一个裁决的两面** —— `工具清单.py:55` 的原文是华哥 2026-09-21 裁决「返回的内容需要可控，不然调用几次打爆上下文」。要推翻它必须显式裁决，不能顺手改。
3. **`含常用参数` 与 `细节级别` 的交互没在契约里写死** —— 实测「档一 + 含常用参数」得到 8 键，但 `能力定义.json` 的 `值结构` 是按「档」描述的还是按「键」描述的，需核对；否则调用方无法从契约推出「哪些档能带 `常用参数`」。

### 3.3 改造点

**（a）描述瘦身（最小改动）**

- 落点：`开发工具/薄壳/工具清单.py:82-145`（`capability_call` 的描述，2871 字符，占常驻体量 48%）。该段现含大量**实测踩坑叙事**（「实测踩过…连错 3 次」「此前必须手抄，实测连传 4 次错才开通工」等）。
- 改法：把**叙事性内容**移到平台内文档（如 `开发文档/`），描述只留**可执行规则**（参数两层怎么放、热接入怎么调、返回上限怎么设）。
- **注意**：描述里同时承载了**硬规则**（`工具清单.py:41-49` 的「3 次探索规则」「慢调用自报」）—— 这些是华哥裁决的送达点，**不能删**，只能压缩措辞。

**（b）把描述拆成「常驻短描述 + 按需长指引」**

- 落点：`工具清单.py:32-175` 整体 + `薄壳服务.py:345-348`。
- 改法：`tools/list` 只回短描述；长指引经 `tool_catalog`（已在，`工具清单.py:244-281` 返回 `工具[].描述`）按需拉。⚠ **`tool_catalog` 现在就把完整 `描述` 回带**（`工具清单.py:258`：`"描述": 工具.description`）—— 即**长文本已经在两条路径上各存一份口径**，拆分时不要把 `tool_catalog` 变成第二套描述来源。

**（c）MCP 原生延迟加载**

- ⚠ **MCP 协议本身没有 `defer_loading` 等价物** —— 08 报告第 24 行核实的 `defer_loading` 是 **Anthropic API 侧**字段（`defer_loading` controls what enters the context window, not what you send in the request），**不是 MCP 协议字段**。薄壳是 stdio MCP server，`tools/list` 返回什么，客户端就注入什么 ⇒ **在 MCP 层做不到「定义照旧发、但不进上下文」**。
- 唯一可行的等价物：**减少 `tools/list` 返回的定义体量**（即 (a)/(b)），或**客户端侧**做工具过滤（如 ToolHive 的 `filter` 白名单 / MetaMCP 的 tool overrides）。⇒ **（c）在当前形态下不可落地**，如实标注。

**【代价】**

- （a）：`工具清单.py` **1 个文件**（描述文本重写，行数不变或减少）。⚠ 改完需重启 MCP 客户端（薄壳常驻，`工具清单.py:193-194`）。
- （b）：`工具清单.py` + `薄壳服务.py` **2 个文件**，另需 `开发文档/` 承接移出的长文本。
- （c）：**不可落地**（协议不支持）。

**【风险】**

1. **改描述会破前缀缓存** —— 描述常驻在 system prompt 前缀里；一改，**所有会话的缓存前缀全失效**（这是一次性成本，但要挑时机）。
2. **`tool_catalog` 的 `是否一致` 会报假** —— `工具清单.py:221-241` 用 `工具清单.py` / `薄壳服务.py` 的 sha256 判「手里这个壳是不是盘上那一版」。改了这两个文件、旧壳还在跑，`是否一致=假`，调用方应**不要照旧描述调**。这是**有意设计**，不是 bug。
3. **删描述 = 删硬规则送达点** —— 「3 次探索规则」「慢调用自报」「禁止 py 腿」「开工第一步调 开工准备」都只在描述里（`工具清单.py:41-49`、`:130-137`）。**描述是这些规则的唯一送达点**（`:137` 原文：「规则正文以该返回为唯一送达点，本文不复述」指的是开工准备那条，但其余几条确实只在描述里）。压缩措辞可以，**整段删会造成规则静默失效**。
4. **描述长度不是主要成本** —— 1986 token 常驻 vs 08 报告实测的「search 90 次 + describe 21 次」每次全上下文注入，**后者才是大头**。描述瘦身是「顺手做」，不该占用 E2 主线资源。

## 五、与任务描述/既有审计报告不符的现场事实

1. **「745 个能力」与「发现面条数」不是同一个数。** 现场三个口径：
   - **745** = 全仓 `能力定义.json` 的 `能力列表` 条数合计（实测；其中 `支持库/适配层/` 占 **72** 条）；
   - **673** = 发现面实际条数（进程内 `搜索能力(关键词='')` 返回 `总数= 673`）—— `支持库/适配层.*` 被 `排除包前缀` 排除（`模块库/能力目录/实现/能力索引.py:155-173`，理由原文：「那是**同一实现的第二条腿**…放进来会让同一能力出两条重复记录」）；
   - **713** = 网关注册数（`能力索引.py:161` 注释原文：「经 能力目录.搜索能力 全部 0 命中（`/健康` 报 713，搜索空关键词只回 470）」—— 该注释记录的是 2026-09-20 改判前的旧值）。
   ⇒ 说「745 个能力」时须注明是**契约条数**，不是**可搜到条数**。

2. **「默认档只回指针，8 字段」写错，现场是 7 字段。** 两处都写「8」：
   - `开发工具/薄壳/工具清单.py:56`：`` "默认 `名称`（只回指针，8 字段）／`名称+说明`（加一段话看懂）／" ``
   - `开发文档/分析/MCP优化调研/08_工具发现与动态工具集.md:201`（表格行）
   而 `模块库/能力目录/实现/能力目录.py:54` 的 `精简字段表` 是 **7** 项，进程内实测**返回 7 键**。⇒ **薄壳描述里的字段数不准**，而薄壳描述是模型唯一的常驻依据，会直接误导。

3. **「既不读 `.gitignore`，也不支持 glob」不准确。** 07 报告第 323 行如此表述，但 `目录树` **有 glob 参数**（`名称模式`，`目录树.py:9` / `:99`，契约 `能力定义.json:1363-1367`）—— 只是它是**文件包含白名单**（「只作用于文件条目，目录骨架始终保留」），**不是忽略模式**。准确表述应为「**不支持忽略型 glob / 不读 `.gitignore`**」。这个差别有实操意义：调用方若照 07 报告理解「没有 glob」，就不会知道可以用 `名称模式='*.py'` 做包含过滤。

4. **「同层按名称升序（目录与文件混排）」是写进 docstring 的显式口径，不是疏漏。** `目录树.py:11` 与 `:30-31` 两处 docstring 都明确写了「目录与文件混排」，且契约 `能力定义.json:1409` 声明 `"排序稳定": true`。⇒ 改「目录优先」不是「补一个漏掉的功能」，而是**改一条已声明的对外口径**，需要按契约变更流程走（至少同步 docstring + 契约说明 + 快照场景）。

5. **默认落点目录里已有一个 `.db`，容易被误读成「已建图」。** `工程缓存/仓库地图/` 下现有 `仓库地图夹具_审计.db`（53248 字节，Sep 21 15:14）与 `文件系统支持库.db`（204800 字节，Sep 21 14:25），但**默认落点 `<仓名>.db` = `系统工程平台.db` 不存在**（实测 `is_file()=False`）。⇒ 判定建图与否**只能看 `<仓名>.db`**，不能看目录里有没有 db。

6. **同仓内存在两套 token 估算公式，且都不是真 tokenizer。**
   - `仓库地图`：`字符数/3` 向上取整（`地图渲染.py:12,18-20`，注释自述「中文场景保守口径，不用 4 字符/token」）；
   - `上下文压缩.估算token数`：`中文字数×0.8 + 英文字符数/4 + 1`（`上下文压缩.py:70-71`）。
   ⇒ 07 报告第 326 行只说「口径是字符数/3，不是真 tokenizer」，**没提平台内还有第三把尺子**（`上下文压缩`）。给 `目录树` 加 token 字段时若不先统一口径，会从两把尺子变三把。

7. **`取仓库地图` 的两条失败路径文案不一致，且调用方看不到有用的那条。**
   - 库文件不存在 → `图库.py:85`：`"仓库地图文件不存在: {路径}"`（**不含「请先调 建符号图」**）；

   ⇒ 当前未建图状态下，调用方拿到的是前者 —— **有指引的那条文案在未建图时不可达**。

8. **`限制` 有两个默认值，且能力契约里那个在薄壳路径下不可达。**
   - 能力层：`默认限制 = 5`（`能力目录.py:38`；契约 `模块库/能力目录/能力定义.json:23` 同为 `5`）；
