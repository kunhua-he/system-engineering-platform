#### 4.5 双层转义的机制（为什么现在必须转义）

`执行命令` 的实现按「可执行文件 + 参数」**直启不经 shell**（`进程管理/能力定义.json:263` 的 `说明` 原文），
而调用方经 MCP 走 JSON：`{"参数": {"命令": "<shell 命令行文本>"}}`。

⇒ 一个多行 / 带引号的 shell 串，要经 **JSON 一层**（`\"`、`\n`）+ **shell 一层**（`'`、`"`、`\`）双重转义。
现场痛点即 `git commit -m "标题\n\n正文"`（方案 `:45`）。

**旁证（同类痛点已被记录）**：`开发文档/分析/MCP优化调研/00b_一手源码证据.md:145` 记着「要串联用 `执行命令集`（命令表 + 模式），要通配用 `rg --glob`」——即调用方已经在用「把 shell 语法塞进文本参数」的方式绕。

### 【风险】

- **低：契约层**。只增可选参数，不动 `必填`、不改既有类型 ⇒ 现有调用（含 `任务类型规范.json:45` 里写的 `capability_call(能力id='系统核心支持库.进程管理.执行命令', 参数={'命令': '<完整命令行>'})`）逐字不变即可继续跑。

- **中：argv 拆分口径**。`执行命令集` 的 `说明` 明写「逐条复用 执行命令，故危险命令拦截/**argv 拆分**/输出有界/进程组整组回收同一实现」（`能力定义.json:328`）——新增 argv 参数必须**复用同一处拆分/直启实现**，不许在 `执行命令集` 里再写一份（哲学 1.1）。
