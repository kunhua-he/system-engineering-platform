3. **指纹与回执口径**：`开发工具/薄壳/工具清单.py:185-241` 的指纹只算两个源文件的字节 sha256，不含运行时 schema，故 L9-1 **不改指纹**；但 `构建工具目录` 的 `入参` 键（`工具清单.py:257` `"入参": 工具.inputSchema`）会回带补全后的 schema，与 `三个工具定义` 里的原始 schema 出现差异 —— 需确认 `测试中心/开发工具/测试_薄壳返回可控.py:35`/`:42` 的断言口径按哪一份。
4. **常驻进程不重载**：改 `支持库/适配层/MCP协议提供者` 后，运行中的薄壳进程不会自动重载（`工具清单.py:186-190`），须重启 MCP 客户端；`tool_catalog` 的指纹段**不覆盖**该提供者文件（`薄壳源文件 = ("工具清单.py", "薄壳服务.py")`，`工具清单.py:191`）→ 此时指纹会报「一致」，但实际工具面已变。**这是指纹口径的一个盲区，值得单独登记。**

## 与任务描述不符 / 需修正的现场事实

1. **A2 的性质比「签名不够详细」严重一层**：`capability_call` 的 `参数` **连 `properties` 都没有**（`开发工具/薄壳/工具清单.py:152` 只有 `"type": "object"`）。所以「猜参数名错 3 次」不是概率问题而是**结构必然** —— MCP 签名上根本不存在能力参数的位置，唯一可用信息是 138 字散文 + 必须另调一次 `capability_search`/`能力目录.读取能力`。
2. **A1 的「限制在 Hermes 侧」在本仓无法落点**：本仓**没有**任何 MCP 并发/批量上限代码（`运行核心/统一网关/协议/操作协议表.py:9-14` 无批量操作；薄壳无并发参数；`开发工具/薄壳/网关转发.py:34` 单请求）。平台上唯一支持批量的是能力层 `系统核心支持库.进程管理.执行命令集`（`命令表` 列表型 / `模式` 串联|并行 / `失败即停`；说明「最多 64 条、并行最多 8 路」）。→ 改薄壳**不会**解除调用方并发上限，只是把 N 次往返压成 1 次往返。按工作空间权限边界，Hermes 侧配置未读取、不作结论。
3. **A2b 的「薄壳反而有 enum」还有一层**：enum 在 schema 里（`工具清单.py:71`、`:149`），实现层另有**硬编码合法值表**（`薄壳服务.py:83`、`:94`），两处靠测试钉住同源（`测试中心/开发工具/测试_薄壳返回可控.py:295`）。能力层**没有**同类门禁。
4. **「薄壳 0 命中 additionalProperties」已扩大证实**：全仓源码/契约（开发工具/公共契约/运行核心/支持库/模块库/后端核心/前端核心/客户端/平台控制面/测试中心/技能库）**全部 0 命中**；SDK 1.28.1 也不补。→ 「是客户端补了还是豁免」这一待裁定项，本仓只能证实「我们没生成」，客户端行为不可在本仓验证。
