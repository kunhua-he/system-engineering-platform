## 一、结论速览（先给答案，再给证据）

1. **业界对「工具多到爆上下文」的主线答案不是「把返回变小」，而是「把工具定义从每一轮上下文里拿出去」**——两种机制：
   - **检索式延迟加载**（Anthropic Tool Search Tool / OpenAI `tool_search` / RAG-MCP / MuleSoft·Teradata 的 meta-tool）：默认只注入「搜索工具」这一个定义，模型先检索、命中后才把**完整定义**展开进上下文。
   - **代码化（code execution / code mode）**（Anthropic Code execution with MCP、Cloudflare Code Mode、ToolHive `execute_tool_script`）：工具变成文件系统里的代码 API，模型「列目录 → 读文件 → 写代码调」，一次代码执行里跑完整条链。
2. **「一次调用就对」靠的是签名自描述 + 检索命中后立刻给全签名，不靠调用失败回带签名**。所有主流实现（Anthropic `tool_reference`、OpenAI `defer_loading`、Teradata/MuleSoft 的 `search_tool`→`invoke_tool`）都是「检索命中即展开完整 JSON Schema」，**没有任何一家把「调用失败再回带正确签名」当主路径**；失败回带只被当作**兜底提示**（Anthropic 明确要求错误响应写「具体可执行的改进」而不是错误码）。
3. **对本项目 E2 的硬结论**：本项目已经具备「三档细节级别 + 游标翻页 + 常用参数组合」这套**检索侧**能力（`capability_search` 的 `细节级别`＝名称/名称+说明/完整契约、`含常用参数`、`游标`；能力目录另有 `常用参数组合`），**缺的不是检索档位，而是「检索命中即同轮拿到可用签名」与「薄壳工具描述本身的体量」**：薄壳 3 个工具的 description 是**常驻注入**，而 745 个能力的签名是**按需拉取**，两者成本模型相反。E2 的真实成本大头是「search → describe → call」三跳里 **search 与 describe 各自一次全上下文注入**（实测 search 90 次、describe 21 次），业界对应解法是**把 describe 折进 search 的同一跳**（一次命中就回带该能力的完整参数/返回结构）或**把发现折进一次代码执行**（一次 `capability_call` 里批量搜索 + 取详情）。

### 2.1 Anthropic Tool Search Tool（官方平台能力）

- 仓库/来源：Anthropic 官方文档 + 工程博客（非 GitHub 仓库，地址 https://platform.claude.com/docs/en/agents-and-tools/tool-use/tool-search-tool 与 https://www.anthropic.com/engineering/advanced-tool-use ）
- 近似 star 数：不适用（厂商文档）
- 具体怎么做的（实测抓取原文，落盘 `.../开源调研/08/文档/tool_search_tool.md`，35785 字节）：
  - 两个变体：`tool_search_tool_regex_20251119`（Claude 写 Python `re.search` 正则，最长 200 字符）与 `tool_search_tool_bm25_20251119`（自然语言，最长 500 字符）。
  - 关键字段 `defer_loading: true`：**工具定义照旧每轮全量发给 API**，只是**不进上下文**；「`defer_loading` controls what enters the context window, not what you send in the request」。即：省的是**上下文 token**，不是请求体。
  - 检索命中返回 `tool_reference` 块（默认最多 5 条，Claude 可用 `limit` 指定 1~10000），**API 自动把引用展开成完整定义**再给模型；开发者**不要自己展开**。
  - 上限：单请求最多 **10000 个** `defer_loading` 工具。
  - 命中后可**跨轮复用**：`tool_reference` 留在历史里，后续轮次无需重搜；搜不到返回空 `tool_references` 数组而**不是错误**。
  - **prompt caching 友好**：延迟工具从 system-prompt 前缀里被排除，命中时以 `tool_reference` 内联追加，前缀不变，缓存不破。
  - 与 strict mode 正交：严格模式语法按**全量工具集**编译，`defer_loading` 不触发语法重编译。
  - MCP 接入：不逐个工具设 `defer_loading`，而是在 `mcp_toolset` 的 `default_config` 上一次设整台服务器，或按工具在 `configs` 里覆盖（示例：整个 google-drive 延迟、`search_files` 保持常驻）。
  - **自定义检索**（最重要的一条）：可以自己实现检索（如向量检索），**只要返回标准 `tool_result` 且 content 里带 `tool_reference` 块**即可，API 同样自动展开。
  - 何时用（官方判据）：工具 ≥10 个、工具定义 >10K token、选择准确率随工具数下降、聚合 200+ 工具的多 MCP 场景。实测收益：Opus 4 从 49%→74%，Opus 4.5 从 79.5%→88.1%（MCP 评测）；上下文从 ~77K token 降到 ~8.7K。
  - 官方优化建议：常驻保留 **3~5 个最常用工具**；工具名做**一致前缀命名空间**（`github_`、`slack_`）让一次检索命中整组；描述里放**用户会用的关键词**；system prompt 里写清「有哪些类别的工具可检索」。

### 2.2 Anthropic《Writing effective tools for agents》（工具设计规则）

- 来源：https://www.anthropic.com/engineering/writing-tools-for-agents
- 近似 star 数：不适用（工程博客）
- 具体怎么做的（原文要点，落盘 `.../08/文档/` 同批缓存）：
  - **少而精优于多**：反对把 API 端点逐个包成工具；举 `list_contacts` → `search_contacts`、`list_users/list_events/create_event` → `schedule_event`、`get_customer_by_id/list_transactions/list_notes` → `get_customer_context`——**把多步合成一个工具**，把中间结果留在工具内部。
  - **命名空间**：按服务（`asana_search`、`jira_search`）或资源（`asana_projects_search`）加前缀；前缀式 vs 后缀式对评测有非平凡影响，要按自己的评测选。
  - **返回体只回高信号**：优先上下文相关性而非灵活性；**避免 uuid/256px_image_url/mime_type 这类底层标识**；把 UUID 解析成语义化名字能显著降低幻觉。
  - **返回详略由参数控制**：暴露 `response_format` 枚举（`concise` / `detailed`），详版 206 token vs 简版 72 token；类比 GraphQL 按需取字段。
  - **token 效率**：对可能吃掉大量上下文的返回实现分页/区间/过滤/截断，并给合理默认值（Claude Code 默认把工具返回限制在 25000 token）；**截断要带指引**（引导模型改用多个小而准的检索，而不是一次大而全的检索）。
  - **错误响应要可执行**：不要给不透明错误码或 traceback，要在错误里写清「具体怎么改」。
  - **参数命名无歧义**：`user` → `user_id`；用严格数据模型约束输入输出。
  - 评测法：用 Claude Code 造几十条真实任务（强任务要求多次工具调用），跑评测循环，读 transcript 与 reasoning，看**冗余调用**（说明分页/上限参数没调好）与**参数非法错误**（说明描述不清）。

### 2.3 Anthropic《Code execution with MCP》与 Programmatic Tool Calling（把工具当代码 API）

- 来源：https://www.anthropic.com/engineering/code-execution-with-mcp ；https://www.anthropic.com/engineering/advanced-tool-use
- 近似 star 数：不适用（工程博客）
- 具体怎么做的：
  - **把每台 MCP 服务器的每个工具生成为一个文件**：目录树 `servers/<server>/<tool>.ts`，每个文件是 `export async function getDocument(input: GetDocumentInput): Promise<GetDocumentResponse> { return callMCPTool<...>('google_drive__get_document', input); }`。
  - 模型**靠探索文件系统发现工具**：先列 `./servers/` 看有哪些服务器，再读具体工具文件看接口——**只加载当前任务需要的定义**；官方给的对比：150000 token → 2000 token（-98.7%）。
  - **中间结果留在执行环境**：先 `filter`/聚合再 `console.log`，模型只看到 5 行而不是 10000 行；循环/条件/错误处理用代码表达，不再「工具调用 + sleep 轮询」。
  - **隐私**：中间结果默认不进模型上下文，敏感字段可在 MCP 客户端侧 token 化（`[EMAIL_1]`）。
  - **状态与技能沉淀**：中间结果写文件、把跑通的代码存成 `./skills/*.ts` + `SKILL.md`，形成可复用工具箱。
  - **另一种渐进披露**：给服务器加一个 `search_tools` 工具，并**带 detail level 参数**（只要名字 / 名字+描述 / 完整定义），让模型自己控制取多少。
  - 代价（原文明确）：需要安全沙箱、资源限制与监控，运维开销高于直接工具调用。
  - Programmatic Tool Calling（同一批发布）：模型写 Python 在沙箱里编排多次工具调用，**工具结果交给脚本处理而不是进模型上下文**，模型只看到最终输出；适合可并行、可重试（幂等）的工具。

### 2.7 OpenAI：function calling / namespaces / tool_choice / strict / tool_search

- 来源：官方文档 markdown（落盘 `.../08/文档/openai_function_calling.md`，75013 字节；抓取命令见第五节）
- 近似 star 数：不适用（厂商文档）
- 具体怎么做的：
  - **`tool_search`**：官方明确「you can defer loading some or all of those tools with `tool_search`. The `tool_search` tool lets the model search for relevant tools, add them to the model context, and then use them」，**仅 `gpt-5.4` 及以后模型支持**——与 Anthropic 的 Tool Search Tool 是同一思路的两家实现。
  - **命名空间（namespace）**：`{"type":"namespace","name":"crm","description":"CRM tools for customer lookup and order management.","tools":[...]}`，**命名空间里单个 function 也能带 `defer_loading: true`**；官方建议「**For deferred tools, put detailed guidance in the function description and keep the namespace description concise**」——命名空间描述帮模型**决定加载什么**，函数描述帮它**加载后正确使用**。
  - **定义工具的最佳实践**：初始可用函数**少于 20 个**（软建议）；「**Pass the intern test**」（实习生只凭你给的东西能不能正确调用）；用 enum/对象结构**杜绝非法状态**（反面例子 `toggle_light(on, off)`）；**别让模型填你已经知道的参数**（如 `order_id` 应由代码传，工具定义成无参 `submit_refund()`）；**把总是一起调用的函数合并**（`query_location` 后必跟 `mark_location` → 合成一个）。
  - **token 事实**：函数定义注入 system message，**计入上下文并按输入 token 计费**；官方建议「限制前置函数数量 / 缩短描述 / 用 tool search 延迟加载」。
  - **`tool_choice`**：`auto` / `required` / 指定单个 function / **`allowed_tools` 白名单**（`{"type":"allowed_tools","mode":"auto","tools":[{"type":"function","name":"get_weather"}]}`）——后者专为「**不改 tools 列表以保住 prompt caching，但只放开一个子集**」设计；用 tool search 时 `tool_choice` 作用于**当前轮已可调用的工具**。
  - **`strict` 模式**：`strict: true` 保证调用**严格符合 schema**（走 structured outputs），硬要求两条：每个 object 的 `additionalProperties: false`、`properties` 里**所有字段都必须列进 `required`**（可选用 `type: ["string","null"]` 表达）；**schema 不合规会直接 400 拒绝**并指出缺哪个约束；Responses 默认会尝试自动归一化到 strict，失败则退回 best-effort（响应里 `strict: false`），Chat Completions 默认非 strict。
  - **并行调用**：`parallel_tool_calls: false` 可强制每轮 0 或 1 个工具；GPT-5 起支持并行。

### 2.8 RAG-MCP（工具语义检索的学术/工程实证）

- 论文：arXiv 2505.03275《RAG-MCP: Mitigating Prompt Bloat in LLM Tool Selection via Retrieval-Augmented Generation》；工程实现 `fintools-ai/rag-mcp`（https://github.com/fintools-ai/rag-mcp）与 `memoverflow/rag-mcp`、`adeweaver/RAG-MCP-example`
- 近似 star 数：小项目量级（GitHub API 当日 403 限流，未取到；取数命令见第五节）
- 具体怎么做的：
  - **三步**：① Retrieval——用轻量检索器（论文用 Qwen）对**外部向量索引**里的 MCP 元数据做语义检索，取 top-k；② Validation——对每个候选生成 few-shot 查询试跑，做**兼容性 sanity check**；③ Invocation——**只把选中的那一个 MCP 的完整描述（含参数）注入 prompt**。
  - **索引可增量**：新工具入索引即可，**不需要重训模型**。
  - **硬数据（论文实测）**：工具选择准确率 **43.13%**（RAG-MCP）vs 18.20%（Actual Match）vs **13.62%（全量注入基线）**；平均 prompt token **1084** vs 1646 vs 2133.84。即：**工具一多，全量注入的准确率会崩到 13.62%**，检索把准确率「三倍化」。
  - 反面证据（同论文）：工具数量超过约 100 个后基线性能急剧下降；GPT-4 曾**幻觉出不存在的 API**，Claude 曾选错库。
  - `adeweaver/RAG-MCP-example` 给出最小可抄实现：`initialize_tool_registry()`（嵌入建索引）→ `retrieve_tools(query, top_k)` → `build_prompt_with_tools(tools, query)` → `handle_query(query)`，用 sentence-transformers + 余弦相似度。

### 2.9 ToolHive 的「code mode」（开源侧最接近 Code execution with MCP 的实现）

- 仓库全名：`stacklok/toolhive`；地址 https://github.com/stacklok/toolhive
- 近似 star 数：**2,199**（2026-09-21 实测）
- 具体怎么做的：`docs/operator/crd-api.md` 中 `enabled` 字段文档原文——「Enabled turns code mode on. When false (the default), **`execute_tool_script` is not advertised in `tools/list`** and scripts cannot be executed.」即：开启后**工具目录里只多出一个 `execute_tool_script`**，模型写脚本调工具，与 Anthropic 的 Programmatic Tool Calling / Cloudflare Code Mode 同一形态。
- 同仓还有一条值得抄的**安全联动**：组合工具的注解在**广播时（serve `tools/list` 时）**派生，派生底线是 fail-closed，若显式注解会让工具「显得比它的步骤更安全」，该组合工具**在运行时从 `tools/list` 直接剔除并打警告**。

## 三、三个硬问题的回答

### 问题 1：「一次调用就对」靠签名自描述、检索，还是失败回带正确签名？有实例吗？

**靠「签名自描述 + 检索命中即展开完整签名」，失败回带只是兜底。三家都有实例：**

| 做法 | 实例（可核） | 机制落点 |
|---|---|---|
| 签名自描述（常驻） | OpenAI 最佳实践「Pass the intern test」、Anthropic「描述要像对新同事讲」 | 描述里写清参数格式、返回含义、何时该用/不该用 |
| 检索命中即给全签名 | Anthropic `tool_reference` **自动展开**成完整定义；OpenAI `tool_search` 把工具「add them to the model context」；Teradata `search_tool` **可选带参数详情**；MuleSoft `search_tools` 命中即返回工具 | 检索结果 = **完整 JSON Schema**，不是「名字指针」 |
| 失败回带签名（兜底） | Anthropic 明确要求错误响应写**具体可执行的改进**；OpenAI strict 模式 schema 不合规时 **400 并指出缺哪条约束** | 只在出错路径出现，**没有一家把它当主路径** |

**对我们的直接含义**：把「describe 一次」当常态，就是选了最贵的那条路。业界主路径是**让 search 的返回里直接带完整签名**（细节级别＝完整契约），一次往返拿到「能不能用 + 怎么传」。MuleSoft 甚至把它做成 `hotTools`：**高频工具连 schema 一起常驻广播**，低频工具才走检索。

### 问题 2：工具元数据应带哪些字段才能一跳到位（我们缺哪些）？

**业界字段清单（按「一跳到位」的贡献排序）**：

1. **唯一标识 + 稳定命名空间**（`github.createPullRequest`、`org/server`、`crm` namespace）——让一次检索命中整组。
2. **面向用户语言的描述**（描述里要出现用户会说的词；Anthropic 明确「Use keywords in descriptions that match how users describe tasks」）。
3. **完整入参 schema**：参数名（无歧义：`user_id` 而非 `user`）、**类型**、**必填**、**默认值**、enum 取值、`additionalProperties:false`（strict 硬要求）。
4. **返回结构**（Anthropic 在 Programmatic Tool Calling 指南里**要求把返回格式写进描述**，好让模型写对解析代码；MCP 规范里是 `outputSchema`）。
5. **调用示例**（Anthropic `input_examples`／Tool Use Examples：1~5 条、真实数据、覆盖最小/部分/完整三种写法；OpenAI 提示 reasoning 模型加例子可能反而掉分）。
6. **行为注解**（MCP `annotations`：是否只读/破坏性/开放世界；ToolHive 用它做安全底线并**在 `tools/list` 时剔除矛盾者**）。
7. **分页/游标 + 结果上限**（Anthropic「分页/区间/过滤/截断 + 合理默认值」；MCP `tools/list` 原生支持 `cursor`/`nextCursor`）。
8. **版本与元信息**（registry `ServerDetail.version`、`repository`、`packages.transport`；日期化 schema）。
9. **常用调用样例**（本项目已有：`能力目录.常用参数组合` 返回某能力历史上最常用的 5 组入参——**业界公开资料里少见，是本项目的差异化优势**）。

**本项目现状（实测，只读）**：

- 已有的（不必重造）：
  - 能力索引是**14 字段**记录（`模块库/能力目录/实现/能力索引.py:40` 的 `搜索字段表`：`能力id`/`中文名`/`说明`/`参数类型`/`必填`/`默认值`/`返回结构`…；记录体另有 `名称`/`说明`/`包名称`/`参数名`/`必填`/`默认值`/`前置能力`/`后继能力`/`使用指引`）。
  - 薄壳 `capability_search` 已有 **`细节级别`＝名称 / 名称+说明 / 完整契约** 三档、**`含常用参数`**、**`游标`** 翻页、零命中自动兜底扩词；`能力目录.常用参数组合` 给真实样例。
  - 薄壳工具名 ASCII 合规（`工具清单.py:3` 注明 SEP-986：`Tool.name` 仅允许 `[A-Za-z0-9_.-]+`，中文名写进 description）。
- 缺的（对标上面的 1~8）：
  - **① 一跳签名**：`细节级别` 默认「名称」只回指针，要参数得**再调一次**（`读取能力` / 完整契约）——这正是 E2「search 90 次 + describe 21 次」的结构性来源。业界对应做法是**让检索命中项直接带完整入参 schema**（MuleSoft `search_tools`、Teradata `search_tool` 的「可选参数详情」、Anthropic `tool_reference` 自动展开）。
  - **② 参数级样例常驻**：`含常用参数` 默认关（理由是会放大返回体量）——但按元判据「一次访问注入再多也比三次便宜」，**默认关的应当是「多次往返」而不是「返回体量」**。
  - **③ 反向索引/语义检索**：现在是关键词子串匹配（registry 也是子串匹配，属同一档；RAG-MCP 那一档是向量语义检索，准确率差 3 倍）。零命中靠「兜底扩词」属规则补丁，没有语义召回。
  - **④ 组合能力（composite tool）**：ToolHive 的「隐藏但不删除、留给组合工具编排」提示一条更根本的路——**把常见的「search→describe→call」三跳固化成平台侧一个组合能力**，模型只调一次。
  - **⑤ 行为注解**：`annotations` 这一档在本项目能力定义里未见等价字段（本报告只读抽样，未做全量比对，此项列为**待核**）。

### 问题 3：745 个能力，怎么在不牺牲准确率的前提下把发现成本压到 1 跳？

三条路线，按「改动面 / 收益 / 风险」排序（均为只读结论，未改任何代码）：

**路线 A（最小改动、收益最直接）：把 describe 折进 search——命中即带完整签名。**

- 做法：`capability_search` 增加档位语义，或在**同一跳返回体里**对每条命中直接带 `参数名/类型/必填/默认值/返回结构`（现在这些字段**索引里已经有**，`能力索引.py` 的 14 字段记录已包含，只是默认档没吐出来）。
- 依据：Anthropic `tool_reference` 自动展开、MuleSoft `search_tools` 命中即回工具、Teradata `search_tool` 带参数详情；RAG-MCP 实测「只注入选中的完整签名」准确率反而从 13.62% 升到 43.13%——**给全签名不伤准确率，反而提准确率**。
- 代价：`capability_search` 返回体变大（这正是元判据允许的：一次给全 ≫ 三次给全）；需同步薄壳工具描述与 `说明/使用说明.md`（改文档判据）。

**路线 B（收益最大、代价中等）：常驻 3~5 个高频工具 + 其余延迟。**

- 做法：按 Anthropic「Keep your 3–5 most frequently used tools non-deferred」，把高频能力（如 `执行命令集`、`读取文件`、`能力搜索`）做成**签名常驻**，其余 745 个只暴露检索口。
- 依据：Anthropic 官方「10+ 工具 / >10K token 定义」即适用；OpenAI「初始可用函数 <20 个」。
- 代价：需要一张**高频清单**并定期重算（本项目 F1 已有「执行命令耗时记录」这类账本，可派生）；清单漂移要有判据，否则会退化成「全都常驻」。

**路线 C（结构性、最贵）：一次代码执行里跑完发现+调用。**

- 做法：薄壳暴露一个「脚本编排」口（类比 ToolHive `execute_tool_script`、Anthropic Programmatic Tool Calling），模型写代码在一次执行里 `搜索→取详情→调用→只打印结论`。
- 依据：Anthropic 实测 150K→2K token（-98.7%）；中间结果不进上下文；`执行命令集` 已支持并行 8 路，说明平台侧有并发底座。
- 代价：**需要沙箱、资源限制与监控**（Anthropic 原文点名的运维开销）；与现有权限契约、资源租约的交互要重新设计；风险最高，建议放在 A/B 之后。

**一条硬提醒**：三条路线都**不能靠「把返回变小」**。元判据是「往返次数 × 每轮全上下文注入」，而本项目薄壳 **3 个工具的 description 是常驻注入**——只读抽样显示这三个描述本身就有**数千字**（`开发工具/薄壳/工具清单.py`，含大量实测踩坑说明）。也就是说：**在给能力加检索档位的同时，薄壳工具描述自身也在吃上下文**。若把描述再膨胀一倍，省下的往返会被常驻描述吃掉。业界对这一层的解法正是 Anthropic 的 `defer_loading`（**常驻只留必要的、其余按需**）。
