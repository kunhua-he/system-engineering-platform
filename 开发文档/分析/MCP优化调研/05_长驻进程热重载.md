## 二、Python 侧：热更新的六种工业做法

### 2.1 encode/uvicorn 的 `--reload`：**根本不是 reload，是杀子进程换新的**

- **仓库**：`encode/uvicorn`，https://github.com/encode/uvicorn，≈10,974 star。
- **机制（实测源码）**：`uvicorn/supervisors/basereload.py`
  - `BaseReload.__init__(config, target, sockets)` —— **监听 socket 由父（reloader）进程持有**，作为参数传给子进程（第 25–38 行）；
  - `restart()`（第 86–100 行）：
    ```python
    else:                                   # 非 win32
        self.process.terminate()            # 给子进程发 SIGTERM
    self.process.join()                     # 等它真的死透
    self.process = get_subprocess(config=..., target=..., sockets=self.sockets)
    self.process.start()                    # 起一个全新子进程
    ```
  - 也就是说：**`--reload` 是「进程级替换」，进程内一行模块都没重载**。代码改动通过「新解释器重新 import 全部模块」生效。
- **子进程侧优雅退出**：`uvicorn/server.py`
  - `HANDLED_SIGNALS = (SIGINT, SIGTERM)`（第 46–47 行）；
  - `should_exit` / `force_exit` 两个标志（第 73–74 行）；
  - `handle_exit()`（第 351–356 行）：第一次信号置 `should_exit`，**第二次 SIGINT 才置 `force_exit`**（降级语义）；
  - `shutdown()`（第 281–325 行）：`timeout=self.config.timeout_graceful_shutdown` 有界等待
    `server_state.connections` 与 `server_state.tasks` 归零，超时或 `force_exit` 才放弃。
- **变更检测**：`uvicorn/supervisors/watchfilesreload.py` 第 55–86 行，`WatchFilesReload` 构造时
  `self.watcher = watch(*self.reload_dirs, watch_filter=None, stop_event=self.should_exit, yield_on_timeout=True, ignore_permission_denied=True)`，
  `should_restart()` 先 `pause()`（`should_exit.wait(config.reload_delay)`）再 `next(self.watcher)`，最后用
  `FileFilter(config)`（`reload-include` / `reload-exclude` 正则）过滤路径。**有 debounce，不是每写一字节就重启**。
- **与本项目节点 C1 的对应**：这就是「热接入不重载已导入模块」的工业解法 —— **不试图重载，换进程**。
  本项目 C1 的难点恰恰是「不能换进程」（40007 是全机唯一执行网关，重启牵连 V3 后端与 Agent 工具面），
  所以本项目走了 uvicorn **没走**的那条路（见 §五）。
- **落地代价**：照搬到本项目 = 需要引入 master/worker 分层（父进程持 listen socket，worker 可被替换）。
  本项目现在是 launchd 直接拉单进程（`ProgramArguments = [python3.14, 运行核心/启动运行核心网关.py]`），
  没有 master 层。改动量：中（新增一个 supervisor 入口 + 端口继承），风险：中（listen socket 继承是零丢连接的关键，做错就是连接被拒）。

### 2.2 samuelcolvin/watchfiles：Rust 侧 inotify/FSEvents + debounce

- **仓库**：`samuelcolvin/watchfiles`，https://github.com/samuelcolvin/watchfiles，≈2,537 star。
- **机制**：Python 面 `watchfiles/main.py:53 def watch(*paths, watch_filter=DefaultFilter(), debounce: int = 1_600, step: int = 50, stop_event=None, ...)`；
  实现下沉到 Rust：`watchfiles/src/lib.rs:42 struct RustNotify`，`extern crate notify`（第 1 行），
  用 `notify` crate 拿到 OS 原生事件（macOS = FSEvents / kqueue），Python 侧只消费聚合后的事件批次。
  过滤在 `watchfiles/filters.py`：`DefaultFilter`（第 71 行）排除 `__pycache__`/`*.pyc`/VCS 目录，`PythonFilter`（第 125 行）只放 `*.py`。
  `debounce=1600ms` 表示「静默 1.6 秒才吐一批」——**把「连续保存 10 个文件」压成 1 次事件**。
- **与本项目节点 C1 的对应**：本项目的变更检测不是文件监听，而是**源码指纹比对**：
  `后端核心/后端核心.py` 第 411 行 `if self.计算包指纹(声明) != self._包指纹表.get(声明.包id)`。
  指纹比对比文件监听**更弱**（不会自动触发，要人显式调 `热接入`），但**更适合本项目**：
  40007 是被动执行网关，自动重载会在「改一半」的瞬间把半成品推上线（这正是决策记录 0046 说的「污染」）。
- **落地代价**：不建议引入。引入 watchfiles 只会把「人主动调热接入」变成「文件一存就重载」，
  在并发维修场景下**降低**安全性。若将来要做「开发槽自动重载」，应只在开发槽（非 40007）启用。

### 2.3 benoitc/gunicorn 的 graceful reload（HUP）：先起新 worker，再请旧 worker 优雅退出

- **仓库**：`benoitc/gunicorn`，https://github.com/benoitc/gunicorn，≈10,677 star。
- **机制（实测源码）**：`gunicorn/arbiter.py`
  - 信号表第 47 行：`for x in "HUP QUIT INT TERM TTIN TTOU USR1 USR2 WINCH".split()`；
  - `handle_hup()`（第 305–316 行）→ `self.reload()`；
  - `reload()`（第 530–601 行）**顺序即语义**：
    1. 第 550 行 `self.app.reload()` —— 重读配置/应用（**WSGI app 对象是重新加载的**）；
    2. 第 554 行 `self.log.reopen_files()` —— 重开日志文件（配合 logrotate）；
    3. 第 557–562 行：**若监听地址变了才重建 `self.LISTENERS`**（否则沿用同一批 listener）；
    4. 第 585–586 行：`for _ in range(self.cfg.workers): self.spawn_worker()` —— **先把新 worker 全起起来**；
    5. 第 589 行：`self.manage_workers()` —— 再让**超出数量的旧 worker** 退出；
    6. 第 592–601 行：`deadline = time.monotonic() + self.cfg.graceful_timeout`，
       等所有 worker 的 `age` 都新于 `last_worker_age`（即旧 worker 全部退场）才返回。
  - **零丢连接的关键**：`LISTENERS`（listen socket）由 **arbiter 持有**，worker 是 `fork()` 出来的、直接继承 fd。
    新 worker 一出生就能 accept，旧 worker 退场前也还能 accept → 新旧重叠期**不丢连接**。
- **worker 侧优雅退出**：`gunicorn/workers/base.py`
  - `init_signals()`（第 164–182 行）：`SIGTERM → handle_exit`、`SIGQUIT/SIGINT → handle_quit`、
    `SIGWINCH → handle_winch`（**graceful stop of workers**，见 `arbiter.py:370–377`）；
  - **第 176–179 行**：`signal.siginterrupt(signal.SIGTERM, False)` + `siginterrupt(SIGUSR1, False)`
    —— 注释原文 *"Don't let SIGTERM and SIGUSR1 disturb active requests by interrupting system calls"*。
    **这就是「不打断在途请求」的具体做法**：让信号不打断正在进行的系统调用；
  - `handle_exit()`（第 187–188 行）只置 `self.alive = False`，worker 主循环读到才退 —— **不立刻 sys.exit**。
- **与本项目节点 C2 的对应**：本项目的 `运行核心/统一网关/停机编排.py` 已经是同一套语义
  （停收 → 有界排空 → 整组回收 → 持久化，见 §五），**但缺 gunicorn 的「先起新、再退旧」这一步**。
  本项目现在是「先退旧、再起新」（launchd `kickstart -k` 直接杀再拉），中间有真空期。
- **落地代价**：小～中。本项目已有 `运行核心/加载器/版本系统/热切换.py::真实热切换`（第 277–371 行），
  流程就是「启动旧 → 启动新 → 健康检查 → 最小调用 → 影子 → 灰度 → 切换路由 → 排空 → 停止旧」——
  **这就是 gunicorn HUP 的进程级 blue-green，本平台自己已经写好了**，只是没接到「网关自身」上。
  要照搬，缺的是「两个网关进程共享同一个 40007 listen socket」的机制（`SO_REUSEPORT` 或 fd 继承），
  改动量：中，风险：中（两个进程同时绑 40007 需要 `SO_REUSEPORT`；macOS 支持，但凭证/世代账本要能分清两个世代）。

### 2.5 breuleux/jurigged：唯一真正的「原地热补丁」，但明确只给开发期

- **仓库**：`breuleux/jurigged`，https://github.com/breuleux/jurigged，≈1,647 star。
- **机制（实测源码）**：
  - 它**不重跑模块**，而是**改函数的 `__code__`**：`jurigged/src/jurigged/codetools.py:745 new_code = new_obj.__code__`、

    于是**所有已经持有这个函数对象的地方（注册表、装饰器、闭包、实例属性）自动用上新代码**，不需要重新注册。
  - `jurigged/src/jurigged/live.py` 负责 watch + 调度（第 172 行 `def watch(...)`、第 180 行 `registry.auto_register(...)`）。
  - **作者自己写的边界（README 原文，非我推断）**：
    - 第 110 行 Troubleshooting：*"If you are editing the body of a for loop inside a function that's currently running,
      the changes will only be in effect the next time that function is called."* —— **正在运行的函数体改不了**；
    - 第 130 行：*"There may be issues updating some functions when they are decorated or stashed in some data structure
      that Jurigged does not understand. Jurigged does have to find them to update them, unfortunately."*
      —— **找不到就改不了**（装饰器包装 / 藏在数据结构里）；
    - 第 175 行 Caveats 段 + 第 18 行：定位是 `--loop` 一个函数反复跑，**开发期交互调试**，
      原文 *"The rest of the program is **not** re-run, so preprocessing is preserved and heavy modules do not have to be reloaded!"*。
  - 第 249 行还直接对比了 IPython `%autoreload`：*"`%autoreload` will properly re-execute changed decorators,
    but these decorators will return new objects, so if a module imports an already decorated function, it won't update to the new version."*
- **与本项目节点 C1 的对应（★ 最关键的一条）**：本项目决策记录
  `开发文档/决策记录/0008_能力更新走热接入不重启网关.md` 第 55–79 行的「实测补充：模块级全局实例的刷新坑」
  —— 现象是「热接入成功后，网关调用立即返回 `内部错误`（HTTP 500，0.27 毫秒），
  但同一份代码在进程内直接调用完全正常；再执行一次热接入后立即恢复正常」，根因写的是
  「该包的实现模块里有**模块级全局实例**：`_提供者 = 浏览器自动化提供者()` / `句柄系统 = 句柄体系()` / `会话表: dict[int, str] = {}`」。
  **这正是 jurigged 要解决的问题域，而 jurigged 的答案是「改 `__code__` 而不是重跑模块」**。
  本项目的热接入是「弹 `sys.modules` + 重跑模块体」，于是**旧实例仍被闭包/注册表/其他模块的模块级属性持有**，
  新模块体的全局实例与旧持有者并存 → 首次调用打到旧对象 → 500。二次热接入之所以能修好，
  是因为第一次已经把「依赖方」也连带重载了（`后端核心.py` 第 435–443 行的反向依赖闭包），第二次才彻底。
- **落地代价（两条路，建议选第二条）**：
  - **路 A（引入 jurigged 式原地补丁）**：改动量大、风险高。要把「重跑模块体」改成「diff 出函数级变更并改 `__code__`」，
    还要处理装饰器/注册表/类实例。**不推荐**：本项目的能力是「注册进 `能力注册表` 的函数对象」，
    jurigged 那条路等于把注册表的存在意义绕过去，与哲学「同一目的不保留第二套实现」冲突。
  - **路 B（收口现有机制的已知缺口，成本最低）**：把 0008 第 72–79 行的**临时处置**固化成机器判据 ——
    即 `后端核心._自证重载已生效`（第 212–246 行）现在只验「模块对象换新 + 旧对象退场 + 源文件可 stat」，
    **不验「模块级全局实例是否被重新构造」**。建议补第 4 条判据：重载前后对包内模块级对象做一次
    「同名对象标识必须换新」的对账（与现有三判据同口径、同一次现场取证），不通过就计入 `未生效包`
    并**自动再跑一轮重载**（把 0008 第 74–75 行「人工再执行一次热接入」变成机器动作）。
    改动量：小（一个判据函数 + 一处重试），风险：低。

### 2.6 ipython/ipython 的 autoreload 与 Python 官方 `importlib.reload` 的边界

- **仓库**：`ipython/ipython`，https://github.com/ipython/ipython，≈16,783 star。
- **机制（实测源码，`IPython/extensions/autoreload.py`）**：
  - 入口 `ModuleReloader.check()`（第 273–342 行）：`if do_reload: ... superreload(m, reload, self.old_objects)`（第 326 行）；
  - **`superreload(module, reload=reload, old_objects=None, shell=None, import_from_tracker=None)`（第 543 行）**
    —— 先遍历模块 `__dict__` 把旧对象记进 `old_objects`（第 555–564 行），再 `reload(module)`（即 `importlib.reload`），
    然后**逐个把旧对象升级成新对象**（第 588–626 行），最后清空退场的旧引用；
  - 升级规则表 `UPDATE_RULES`（第 437–449 行）：
    ```python
    UPDATE_RULES = [
        (lambda a, b: isinstance2(a, b, type),            update_class),
        (lambda a, b: isinstance2(a, b, types.FunctionType), update_function),
        (lambda a, b: isinstance2(a, b, property),         update_property),
    ]
    ```
  - **`update_function(old, new)`（第 363–369 行）**：按 `func_attrs` 列表（含 `__globals__` / `__dict__` /
    `__kwdefaults__` / `__annotations__` / `__type_params__`，第 355–360 行）**逐属性 `setattr` 到旧函数对象上**
    —— 目的：让「别处已经持有的那个函数对象」也变新（**和 jurigged 改 `__code__` 是同一个目的，两种手段**）；
  - **`update_instances(old, new)`（第 372–381 行）—— 这就是「类身份漂移」的标准解法**：
    ```python
    refs = gc.get_referrers(old)
    for ref in refs:
        if type(ref) is old:
            object.__setattr__(ref, "__class__", new)
    ```
    用 GC 反查所有引用旧类的对象，把它们的 `__class__` 直接指到新类 —— 否则 `isinstance(旧实例, 新类) == False`；
  - `update_class(old, new)`（第 384–423 行）：逐 `__dict__` 键比对，**旧类里新类没有的键要 `delattr` 删掉**
    （第 395–401 行，注释 *"obsolete attribute: remove it"*），新类新增的键补上（第 415–420 行），
    最后调 `update_instances`（第 423 行）。
- **`importlib.reload` 本身的边界（为什么业界普遍放弃它）**：
  1. **只重跑模块体，不修「别处的引用」**。`reload` 会新建模块命名空间里的函数/类对象，
     但任何**已经被别的对象持住**的旧引用（装饰器返回值、注册表条目、其他模块的模块级属性、实例属性、默认参数、闭包单元）
     仍指向旧对象 —— 必须像 IPython 那样手工 `update_function` / `update_class` 去追。
  2. **类身份漂移**：`reload` 后类是新对象，已存在实例的 `__class__` 还指旧类，`isinstance` / `except` 匹配全部失效。
     IPython 的 `gc.get_referrers` + `object.__setattr__(ref, "__class__", new)` 是**唯一能在 CPython 上表达的补救**，
     而它本身是「绕过类型系统」的操作（`object.__setattr__` 直写 `__class__`）。
  3. **依赖顺序**：只 reload 一个模块，依赖它的模块在**模块级**绑定的旧函数对象不会更新
     —— 本项目的 `#195` 根因与此完全同形（`后端核心.py` 第 250–255 行注释：
     *"它自己的 `包声明.json` 的 `依赖` 是**空的** —— 只按声明的依赖排，根本排不出「提供者在前」"*）。
  4. **字节码缓存**：源文件 mtime 秒级相同 / size 相同时 Python 复用旧 `.pyc`
     —— 本项目 `后端核心.py` 第 507–511 行主动 `包根.rglob("__pycache__")` 后 `平台适配.清只读后删除树`。
  5. **模块级副作用不幂等**：重跑模块体会重跑所有模块级语句（建连接池、起线程、注册回调）。
     `reload` 对「重跑一次会出问题」的代码无保护。
- **结论（回答硬问题 1 的前半）**：`importlib.reload` **不是设计给生产长驻服务用的**；
  IPython 的 autoreload 是**交互式 REPL 场景**的尽力而为，它自己还要用 GC 反查 + 强改 `__class__` 来补漏。
- **与本项目节点 C1 的对应**：本项目 `后端核心.热接入` 已经踩过上面第 1、3、4 条，并各自有对策
  （反向依赖闭包 / 显式删 `__pycache__` / `_自证重载已生效`）；**第 2 条（类身份漂移）与第 5 条（模块级全局实例）尚未有机器判据**。
- **落地代价**：小。照搬 `update_instances` 那 8 行到 `后端核心._自证重载已生效`，
  作为「类身份漂移」的**检测**（不一定要修）：重载后对包内模块级类，用 `gc.get_referrers` 查还有没有实例挂在旧类上，
  有就计入 `未生效包`。风险：低（只读 GC 反查，不改对象）。

## 四、硬问题回答

### 4.1 为什么 Python「reload 已导入模块」在实践中不彻底？业界主流是放弃 reload 改走 graceful restart 吗？

**不彻底的原因（五条，逐条有源码证据，见 §2.6）**：

| # | 原因 | 证据 | 本项目现状 |
|---|---|---|---|
| 1 | `reload` 只重跑模块体，**不修别处已持住的旧引用** | ipython `autoreload.py:363 update_function` 要逐属性 `setattr` 追旧函数对象 | 用**反向依赖闭包连带重载**（`后端核心.py:435–443`）绕过 |
| 2 | **类身份漂移**：实例 `__class__` 仍指旧类，`isinstance` 失效 | ipython `autoreload.py:372–381 update_instances` 用 `gc.get_referrers` + `object.__setattr__(ref,"__class__",new)` | **无机器判据**（缺口） |
| 3 | **依赖顺序**：依赖方模块级绑定的旧对象不更新 | 本项目 `后端核心.py:250–255` 的 `#195` 根因注释 | 已修（AST 导入图 + 拓扑序） |
| 4 | **`.pyc` 缓存**：mtime 秒级/size 相同即复用旧字节码 | 本项目 `后端核心.py:507–511` 主动删 `__pycache__` | 已修 |
| 5 | **模块级全局实例**：新模块体的全局对象与旧持有者并存 | 本项目决策 0008 第 55–79 行实测（500，二次热接入才恢复）；jurigged 用改 `__code__` 规避 | **只有临时处置，无机器判据**（缺口） |

**业界是否放弃 reload？—— 是的，且分两类，界限清楚**：

- **生产长驻服务（uvicorn / gunicorn / hupper / nginx / Envoy / K8s / celery / rq）**：
  **一律放弃进程内 reload，走「新进程 + 切流量」**。
  - uvicorn `--reload`：`basereload.py:86–100` 杀子进程换新的（**连 `importlib.reload` 都不调**）；
  - gunicorn HUP：`arbiter.py:530–601` 起新 worker → 旧 worker 优雅退；
  - hupper SIGHUP：`reloader.py:349–372` `worker.kill(soft=True)`；
  - nginx HUP：起新 worker，旧 worker 关 listen socket 服务完老客户端；
  - celery / rq：排空在途 job 后重启。
- **开发期交互调试（jurigged / IPython `%autoreload`）**：**是原地补丁**，
  但 jurigged 自己写明「正在运行的 for 循环体改不了」「装饰器/藏在数据结构里的函数找不到」（README 第 110、130 行），
  IPython 要靠 GC 反查 + 强改 `__class__` 才补得住。**没有一个是给生产长驻服务用的**。

⇒ **本项目走「进程内 reload + 反向依赖闭包 + 自证生效」，是工业界的少数派路径，但方向是对的**：
它规避了「重启打断在途调用」（C2）这个更贵的代价。代价是必须自己把上面 5 条边界全部收口 —— 其中第 2、5 条尚未收口。

### 4.3 本项目现在是「重启网关会掉本次调用所在进程组」，最小改动方案是什么？

   ⇒ 常驻提供者**不在网关的进程组里**，网关死了它们不会跟着死。

     记录归属网关进程已消失（kill -9 / 异常退出）→ **孤儿，整组回收**"*；
   - `_回收账本行()`（第 212–237 行）第 227 行 `进程终止.强制结束子进程(组长进程id)`，
     第 228–230 行「组长已回收但同组子孙仍在」再按组号补一次强杀。
3. 任务侧同理：`运行核心/任务调度/任务进程_对象.py` 第 19 行注释
   *"`os.setsid` 出现在 `_执行任务进程入口`"* —— 独立任务进程也是自己的进程组。

**⇒ 机制确证**：40007 重启（`launchctl kickstart -k`）→ 旧网关进程消失 → 新世代启动 →
`清扫上一代常驻进程()` 判定上一代账本行为孤儿 → `强制结束子进程(组长进程id)` **整组强杀**。
若此刻某个并行会话的调用**正跑在那个上一代常驻提供者/任务进程里**，它的进程组被整组端掉
—— 这就是「重启会掉本次调用所在进程组，打断并行会话」的物理路径。
（注意：Hermes 薄壳本身是纯 HTTP 转发、不起子进程 —— `开发工具/薄壳/薄壳服务.py` 第 3 行
*"零业务语义：只做 MCP 协议翻译 + 转发唯一网关 40007"*，全文无 `subprocess`/`Popen`。
所以被掉的是**网关派生的进程组**，不是薄壳。）

**最小改动方案（三档，按代价从小到大，建议做第 1 档 + 第 2 档）**：

**第 1 档｜给整组回收加宽限期（最小、零新架构）**

- **改哪**：`运行核心/加载器/提供者隔离/独立进程_账本.py` 的 `_回收账本行` 与 `清扫上一代常驻进程`。
- **改什么**：现在 `清扫等待秒 = 2.0`（第 70 行）是「**强杀之后**等整组消失的上限」，
  **回收动作本身没有宽限期** —— 一判定孤儿就立刻 `强制结束子进程`。
  加一个**回收前宽限期**：判定为孤儿后先给归属进程组发一次「停止收新请求」的优雅信号
  （收口层已有 `进程终止.终止进程组(pid, 信号="终止")`，`独立进程_进程组收口面.py:134` 已在用），
  等 `宽限秒`（建议默认与 `停机编排.默认排空上限秒 = 20.0` 同量级，即 20 秒），
  仍未收敛再走 `强制结束子进程`。
- **改动量**：小（`_回收账本行` 加一段「先发终止信号 → 有界等 → 再强杀」，参数与现有 `等待秒` 并列）。
- **风险**：低。宽限期只影响「孤儿回收变慢」，不影响正确性；且 `清扫上一代常驻进程` 的判据
  「归属网关进程仍活着 → 跳过」（第 271 行）保证**不误伤另一个仍在运行的网关**。
- **为什么这是「最小」**：它把「重启瞬间整组被强杀」变成「重启后给在途调用 20 秒收尾窗口」，
  与 nginx 的「旧 worker 关 listen socket 但服务完老客户端」是同一语义，**不引入任何新组件**。

**第 2 档｜把「整组回收」从新世代启动时挪到排空之后（对齐 gunicorn）**

- **改哪**：`运行核心/启动运行核心网关.py` 第 318–326 行（A 簇公开仓底）的调用时机。
- **改什么**：现在的顺序是「新网关起来 → 立刻清扫上一代」。改成「新网关起来 → 先服务 →
  确认自身就绪（`/健康` 通过）→ 再在后台清扫上一代」。这样上一代在途调用拿到的是
  **「新网关已在接流量」的重叠期**，而不是「新网关一起来就把我端掉」。
- **改动量**：小～中（挪调用点 + 一个后台线程/定时触发 + 把清扫结果接进 `停机编排` 的报告）。
- **风险**：中。孤儿回收被推迟 → 若上一代残留了大量常驻提供者，会在重叠期短暂占用资源
  （端口/内存）。需要给清扫加一个「最多推迟 N 秒」的硬上限。

**第 3 档｜采纳 0046 的 E1/E5 双槽切换（唯一能同时解决 C1 + C2 的做法）**

- **改哪**：按 `开发文档/决策记录/0046_开发槽与稳定槽分离.md` 第五节 E1（40007 从跑源码切到跑激活制品）、
  E5（激活切换接优雅停机 + 整组回收 + 三个探针），按
  `开发文档/方案/稳定槽切换执行方案_20260918.md` 第八节 8.7 已裁定的**方案 1**
  （plist 显式钉住 `系统底座_工程缓存根 = <源码树>/工程缓存`，**数据零迁移**，第 8.6 节已实测跑通：
  `系统底座_网关端口=48001` 3 秒起、**686 个能力**装配成功、回收后 48001 无残留、40007 未受影响）。
- **为什么它能同时解决 C1**：C1 的真正剩余缺口是「**网关自身进程内代码变更仍需重启**」
  （决策 0008 第 27 行原文：*"只有热接入确实无法覆盖的变更（例如网关自身 `运行核心/统一网关/` 的进程内代码变更）才重启"*）。
  双槽切换让「重启」变成「切指针 + 起新制品」，而**在途调用由排空段保护**。
- **改动量**：中（改 plist 两处 + 按方案执行 + 四条反向验证）。
- **风险**：**不可逆动作**（改本机长期运行配置 + 影响在线服务），
  0046 第 66–68 行已裁定：*"E1 属**不可逆动作**，且**必须在源码树干净、门禁通过之后**做"* ——
  本路只读审计，**不执行**，仅列为方案。

**明确不建议的第 4 档｜让热接入去重载网关自身模块**

- 即把 `后端核心._包依赖序`（`后端核心.py:299–361`）的反向依赖闭包扩到 `运行核心/统一网关/*`，
  让 `热接入` 也能弹掉网关自己的模块。
- **为什么不做**：网关自身模块里有大量**不可幂等重跑的模块级状态** ——
  `本地网关.py:51` 的 `ThreadingHTTPServer`、第 660 行 `serve_forever` 的线程、
  `后端核心.py:49` 的 `_装配模板` / 第 386 行 `_装配锁`、
  `停机编排.py:509` 的进程级信号归属 `_信号归属`（注释原文 *"信号处理是**进程级**资源"*）、
  `独立进程_账本.py:74` 的 `_网关世代id`（重跑会让「本世代」身份漂移，世代账本判据当场失效）。
  弹掉它们 = 监听 socket 断、信号处理器丢、账本判据崩。
- **工业界无先例**：§2.1–§2.5 六个项目，**没有一个**试图 reload 自己的 HTTP 服务器/信号层。
