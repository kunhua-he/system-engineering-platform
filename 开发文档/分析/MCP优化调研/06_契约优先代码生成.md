# 契约优先代码生成与防漂移的成熟生态 —— D1/D2 审计调研

- **最后更新**：2026-09-21
- **口径**：只读审计调研。所有结论以 GitHub 真实开源仓库的源码 / README / CI 配置 / 代码注释为准，14 个仓库均**浅克隆到本机**（`--depth 1`）后逐条取证，命令与真实输出原文附于第二节。star 数为 2026-09-21 抓取的**近似值**（会变，取值命令见第二节，不在正文写死）。
- **维护者**：华哥 Agent（D1 路）

## 一、本路要回答的问题

本项目的 MCP 调用链是：Hermes 薄壳（`mcp__system_engineering_toolkit__*`）→ 40007 唯一网关 → 能力目录 → 具体能力实现。本路负责两个节点：

- **D1（派生物层·改 1 个能力要同步 N 个文件）**：编译器只自动产 6 份派生物，说明书×2、验证场景、权限契约、能力定义手工段仍手改（实测改 4 个键动 9 个文件）。
- **D2（派生物层·互锁死结）**：生成器拒写 ↔ 门禁要求机器印记，会卡成死结。

调研目标：**「改一处定义，所有派生物自动生成，且 CI 能校验零漂移」这件事，成熟生态怎么做。**

元判据（华哥原话）：

> 「你访问 3 次，和你一次访问。**本质上一次访问注入上下文再多，也没 3 次访问那么贵**。这个是实打实的问题。」

即 **往返次数 × 每轮全上下文注入 = 真成本**。任何只把返回变小、没减少往返的方案都不算解决问题。

> **本方向与元判据的关系（先说清，免得后面被误读）**：D1/D2 不直接减少**运行时**往返，它减少的是**改一个能力所需的往返与返工**（实测改 4 个键动 9 个文件 = 9 次读+写+验）。防漂移判据若不闭环，Agent 会在「改 → 门禁红 → 读门禁原文 → 猜 → 再改」上反复付全上下文注入。所以本方向的成本单位是**「一次契约变更的往返数」**，与元判据同构。

每条四件套：**仓库全名 + 地址 + 近似 star 数 + 它具体怎么做的**；末尾补**与本项目节点的对应**与**照搬落地代价**。

### 3.1 protocolbuffers/protobuf（≈72056★，本批最高）

- 地址：https://github.com/protocolbuffers/protobuf
- **怎么做的**：
  1. **契约自举**。`src/google/protobuf/descriptor.proto` 用 `.proto` 描述 `.proto` 本身（`:16 syntax = "proto2"; :18 package google.protobuf;`），且把**所有语言的命名空间写在同一份契约里**：`:20 option go_package`、`:21 option java_package`、`:22 option java_outer_classname`、`:23 option csharp_namespace`、`:24 option objc_class_prefix`。→ **一份定义，多形态派生物的命名由契约决定，不由生成器各写各的。**
  2. **生成器是独立进程，靠一份元契约通信**。`src/google/protobuf/compiler/plugin.proto`：
     - `:43 message CodeGeneratorRequest` / `:47 repeated string file_to_generate = 1;` / `:83 message CodeGeneratorResponse`
     - `:92 optional string error = 1;`（**生成器可以只报错不写文件**，且错误走结构化字段）
     - `:96 optional uint64 supported_features = 2;` + `:101 FEATURE_PROTO3_OPTIONAL = 1; :102 FEATURE_SUPPORTS_EDITIONS = 2;` + `:109 optional int32 minimum_edition = 3; :115 optional int32 maximum_edition = 4;`（**能力协商**：生成器声明自己支持哪些特性、哪个版本区间）
     → 关键：**新增一类派生物 = 新增一个 plugin 可执行文件，契约解析器（protoc）与生成器完全解耦，不需要改契约、不需要改 protoc。**
  3. **生成物自带来源标注**。`src/google/protobuf/compiler/cpp/file.cc:170` 原文：
     ```
     "// Generated by the protocol buffer compiler.  DO NOT EDIT!\n"
     "// NO CHECKED-IN PROTOBUF "
     "GENCODE\n"
     "// source: $filename$\n"
     ```
     → 头三行：**生成器名 + 禁止手改 + 来源契约文件名**，机器可判、可 grep、可审计。
  4. 重算入口 `generate_descriptor_proto.sh`（`:56 echo "Updating descriptor protos..."`），把 `descriptor.proto` 本身也再生成一遍——**自举闭环**。

- **与本项目节点的对应**：我们的 `能力定义编译器.py` 同时扮演 protoc（解析契约）+ 6 个 plugin（生成 6 类派生物），**耦合在一个进程里**。D1 的"只产 6 份"正是这个耦合的直接后果——加第 7 类派生物必须改编译器本身。protobuf 的 plugin 协议给出 D1 的正解：**派生物注册表 + 每个派生物一个独立生成器**。
- **照搬落地代价**：**中**。改 `开发工具/契约编译/能力定义编译器.py`（新增"派生物注册表"层，把 `生成能力契约/生成包声明/生成注册入口/生成搜索数据/生成Agent数据/生成摘要` 注册为 6 个条目 + 允许新增条目）；风险在于 6 个生成器当前共享 `从包推导编译参数` 等上下文，注册表需要把上下文对象化。生成物头三行（生成器名/来源契约/契约版本）**代价低、收益直接**，可先做。

### 3.2 grpc/grpc（≈45328★）

- 地址：https://github.com/grpc/grpc
- **怎么做的**：`.proto` 契约集中在 `src/proto/grpc/`（`health/v1`、`channelz`、`status`、`testing`、`gcp` 各自一份），**语言派生物不在这个仓里**——C++ 核心留在本仓，Java/Go/Python 派生物在各自语言仓生成。即 **「契约在中央仓，派生物在各自域仓」**。
- **与本项目节点的对应**：我们的 9 个手改件全在**同一个包目录内**，所以"改一处动 9 个文件"的物理路径必然发生。grpc 的形态说明：**派生物的归属要按"谁消费"分域**——例如"验证场景"的消费者是测试中心，"权限契约"的消费者是网关，二者的生成物不该挤在能力作者的工作面上。
- **照搬落地代价**：**中-高**。这是目录结构级改动，会与在途的包结构改动撞车；建议**只照搬口径**（派生物清单里标注 owner 域），不照搬物理拆分。

### 3.3 OpenAPITools/openapi-generator（≈26751★）—— ★「生成区 vs 人工区」的权威划法

- 地址：https://github.com/OpenAPITools/openapi-generator
- **怎么做的**：
  1. **生成物清单文件**。`modules/openapi-generator/src/main/java/org/openapitools/codegen/DefaultGenerator.java:1994-2051` `generateFilesMetadata(List<File> files)`，注释原文：
     > *"Generates a file at `.openapi-generator/FILES` to track the files created by the user's latest run. **This is ideal for CI and regeneration of code without stale/unused files from older generations.**"*
     - 常量：`:73 private static final String METADATA_DIR = ".openapi-generator";`，`DefaultCodegen.java:217 protected String filesMetadataFilename = "FILES";`
     - 写出：`:2041 String targetFile = config.outputFolder() + File.separator + METADATA_DIR + File.separator + config.getFilesMetadataFilename();`，路径统一转 linux 风格（`:2017-2032`，为了 Windows/macOS 输出可比对）。
  2. **人工区用「被生成目录里的忽略清单」声明**。`.../codegen/ignore/CodegenIgnoreProcessor.java:36` 注释原文 *"Presents a processing utility for parsing and evaluating files containing common ignore patterns. (.openapi-generator-ignore)"*；`:52-53 public CodegenIgnoreProcessor(final String baseDirectory) { this(baseDirectory, ".openapi-generator-ignore"); }`；判据入口 `:145 public boolean allowsFile(final File targetFile)`。
     → **生成器本身不持有"哪些文件是人工的"这份知识**；知识放在**输出目录里的 `.openapi-generator-ignore`**，随代码一起 review、随代码一起改。
  3. `dryRun` 模式：`DefaultGenerator.java:75/110/129`——**只算不写**，供 CI 预检。
- **诚实标注的局限**：我只取证到 `FILES` 的**写入**（`:2000-2051`），在 `modules/openapi-generator/src/main/java/org/openapitools/codegen` 内 `rg 'getFilesMetadataFilename|METADATA_DIR|filesMetadata'` 只找到**定义与写出**，**没有找到"读回 FILES 自动删陈旧文件"的实现**。即：陈旧文件清理在 openapi-generator 里是**留给用户/CI 的**（注释只说"ideal for CI"）。这正是我们要避免的坑——**光有清单不读回，等于没有防漂移闭环**。
- **与本项目节点的对应**：我们的 `说明书白名单`（`生成物一致性检查.py:271-275` "（人工类·血统细分）… 生成器不得覆盖"）与 openapi-generator 的 `.openapi-generator-ignore` **目的相同、位置相反**：我们把"人工区"写进**生成器/门禁内部**，它把"人工区"写在**被生成目录里的用户文件**。位置相反正是 D2 死结的成因。
- **照搬落地代价**：**低**。把说明书白名单从 `生成物一致性检查.py` 里搬成**包目录内的 `.契约生成-忽略` 文件**（含 `类别`/`血统细分`/`原因` 三列），门禁读该文件判豁免。改动面 = 1 个判据模块 + N 个包目录新增 1 个小文件；风险 = 需要一次性迁移存量白名单条目（可脚本生成）。

### 3.6 kubernetes-sigs/controller-tools（≈868★）—— ★★ 本报告最高性价比的一条

- 地址：https://github.com/kubernetes-sigs/controller-tools
- **怎么做的**：
  1. `Makefile:121-123`：
     ```make
     .PHONY: verify-generated
     verify-generated:
     	./hack/verify-generated.sh
     ```
     `Makefile:90-95` 把它串进总门禁：
     ```make
     test-all:
     	$(MAKE) verify-modules
     	$(MAKE) verify-boilerplate
     	$(MAKE) verify-k8s-deps
     	$(MAKE) verify-generated
     	$(MAKE) test
     ```
  2. `hack/verify-generated.sh` **全文 26 行，核心 3 行**（真实原文）：
     ```bash
     set -euo pipefail
     cd "$(dirname "$0")/.."
     hack/update-generated.sh
     if [[ -n "$(git status --porcelain)" ]]; then
       echo "ERROR: generated files are out of date. Run 'hack/update-generated.sh' to update." >&2
       git status --short >&2
       exit 1
     fi
     ```
  3. 同一手法用于 go.mod，`Makefile:110-115`：
     ```make
     verify-modules: modules
     	@if !(git diff --quiet HEAD); then \
     		git diff; \
     		echo "go module files are out of date, please run 'make modules'"; exit 1; \
     	fi
     ```
- **这条为什么能解 D2**：它的判据**不是**"生成物必须存在/必须等于某个字符串"，而是**"跑一次重算后工作区没有差异"**。生成器拒写时重算不产生差异 → 判绿。**判据与生成器共用同一个写入口，因此不可能互锁。**
- **与本项目节点的对应**：
  - 我们的 `生成物一致性检查.py:300-334` 是**直接 import 生成器函数**（`from 开发工具.契约编译.能力定义编译器 import 生成Agent数据, 生成包声明, 生成能力契约, 生成注册入口, 生成搜索数据, ...`）再逐字比对——**绕开了写入口**，于是与 `:276-282` 的"该生成器拒绝覆盖已有文件"直接冲突 → **D2 死结的机制就在这里**。
  - 正确形态：判据改成「调用**重算入口**（写入口）→ `git status --porcelain` 非空即红」，并把差异**文件名原样打印**（K8s `git status --short >&2`）——这同时命中 B2（门禁报红要给落点）。
- **照搬落地代价**：**低**（本批最低）。新增 1 个 `开发工具/契约编译/重算全部派生物.py`（幂等、只写生成物、不碰人工区），门禁新增 1 条判据「重算后 git 无差异」。**前置硬条件：重算必须幂等**（跑两次结果字节相同），否则判据自己抖——K8s 靠 `git status` 天然把这件事验证了。

## 四、三个硬问题的回答

### 问题 1：成熟生态怎么做到「文档/契约/骨架」不手改？「生成区 vs 人工区」怎么划？

实测出**四种划法**，按推荐度排序：

| 划法 | 代表实现（取证位置） | 机制 | 评价 |
|---|---|---|---|
| **A. 目录内清单文件** | openapi-generator `.openapi-generator/FILES`（`DefaultGenerator.java:1994-2051`）+ `.openapi-generator-ignore`（`CodegenIgnoreProcessor.java:36-63`） | 生成物清单与忽略清单都是**被生成目录里的普通文件**，随代码 review | ★★★ 推荐。人工区知识**不在生成器里**，从根上避免 D2 |
| **B. 文件头标记约定** | protobuf `// Generated by ... DO NOT EDIT! // source: $filename$`（`compiler/cpp/file.cc:170`）、Go `// Code generated ... DO NOT EDIT.`（golangci-lint `skip-any-generated`） | 生成物自带可 grep 的头，工具链按头整体识别 | ★★★ 推荐。**新增派生物不用改门禁** |
| **C. 目录级/仓级隔离** | docusaurus `website/versioned_docs/version-*`；grpc 契约仓 vs 各语言派生物仓；terraform 官网文档独立仓 | 生成物与人工物物理分域 | ★★ 有效但改动面大，易与在途结构改动撞车 |
| **D. 生成器/门禁内白名单** | **我们现在的** `说明书白名单`（`生成物一致性检查.py:271-275`） | "哪些是人工的"写死在判据侧 | ★ **不推荐**——正是 D2 死结成因 |

**结论（可直接写进规范的一句话）**：**生成器不得持有"人工区"的知识。** 人工区的知识必须放在 (A) 被生成目录里可 review 的清单文件，或 (B) 命名/文件头约定。放在生成器或门禁内部（D）必然导致"生成器拒写 ↔ 门禁要求存在"的互锁。

### 问题 2：「生成器拒写 ↔ 门禁要求生成物必须存在」的互锁，别的项目怎么避免？

**答案：它们根本没有"要求生成物存在"这条独立判据。**

K8s（`hack/verify-generated.sh`）与 ent（`ci.yml:81-87`）用的是**同一条判据**：

```
跑生成器（写入口） → git status --porcelain 非空？→ 非空即红，原样打印差异文件名
```

三个必要性质：

1. **判据走与生成器相同的写入口**（先真跑 update，再判差）。生成器拒写 → 无差异 → 判绿。**互锁在结构上不可能发生。**
2. **生成器必须幂等**（跑两次字节相同）。K8s 靠 `git status` 天然把这条也验了。
3. **报红必须给落点**（`git status --short >&2` / `git --no-pager diff`；ent 直接写"you need to run X and commit the changes"）。

**我们的偏差（现场取证）**：`生成物一致性检查.py:300-308` 直接 `from 开发工具.契约编译.能力定义编译器 import 生成Agent数据, 生成包声明, ...` 做**逐字比对**，绕开了写入口；而同文件 `:276-282` 又记录"该生成器**拒绝覆盖已有文件**"。两条口径相撞 = D2。

**修法**：判据从"import 生成器函数做逐字比对"改为"调用重算入口 → git 判差"。
