## 1. 要解决的问题（B1 现场事实）

本项目 MCP 调用链：Hermes 薄壳（`mcp__system_engineering_toolkit__*`）→ 40007 唯一网关 → 能力目录 → 具体能力实现。

实测暴露：**结构化字段超限被整段丢弃，文本字段才是截断，规则不统一**；一次返回 81874 字符被裁到 3292，同一个能力重调 6 次才看全。

现场已存在一层「返回体积控制」（`开发工具/薄壳/薄壳服务.py:75-83`）：`默认返回上限字符 = 6000`，`_裁剪值()` 按「字典丢尾键 / 列表截尾 / 长文本截断」做结构化裁剪并回带 `值裁剪` 说明。**这说明本项目的方向与业界一致，缺的是「丢了之后怎么拿全」的那条腿。**

## 2. 业界做法清单（7 个，四件套齐全）

### 2.1 MCP 官方规范：分页游标（`cursor` / `nextCursor`）

- **仓库全名**：`modelcontextprotocol/modelcontextprotocol`
- **地址**：https://github.com/modelcontextprotocol/modelcontextprotocol
- **近似 star**：**9,264**（2026-09-21 实测）
- **它具体怎么做的**：

  规范文件 `docs/specification/2026-07-28/server/utilities/pagination.mdx`（全文 111 行）原文要点：

  | 项 | 原文（行号） |
  |---|---|
  | 游标语义 | 「Pagination in MCP uses an **opaque cursor-based** approach, instead of numbered pages」（L26） |
  | 游标性质 | 「The **cursor** is an opaque string token, representing a position in the result set」（L28） |
  | 页大小 | 「**Page size is determined by the server**, and clients **MUST NOT** assume a fixed page size」（L29-30） |
  | 结束判据 | 「Clients **SHOULD**: Treat a **missing `nextCursor`** as the end of results」（L99） |
  | 不透明性 | 「Clients **MUST** treat cursors as opaque tokens: Don't attempt to parse or **modify** cursors …（e.g. an empty string is a valid cursor and thus **MUST NOT** be treated as the end of results）」（L102-107） |
  | 服务端义务 | 「Servers **SHOULD**: Provide **stable** cursors；Handle invalid cursors gracefully」（L94-96） |
  | 错误码 | 「Invalid cursors **SHOULD** result in an error with code **-32602 (Invalid params)**」（L111） |

  **支持分页的操作仅 4 个**（L85-90）：`resources/list`、`resources/templates/list`、`prompts/list`、`tools/list`。
  **关键事实：`tools/call` 不在分页列表里** —— MCP 规范**没有**为「一次工具调用的返回体」定义分页机制。分页只覆盖「列表类枚举」，不覆盖「结果体」。

  2026-07-28 版另新增两条与本节点直接相关的机制（`docs/specification/2026-07-28/changelog.mdx`）：

  - **L36**：`tools/list` 等 5 个操作的结果**必须**带 `ttlMs`（新鲜度毫秒）与 `cacheScope`（`"public"` / `"private"`），通过新接口 `CacheableResult`。原文解释：「`ttlMs` is a freshness hint … allowing clients to **cache responses and reduce polling**」。
  - **L34**：服务端 **SHOULD** 按确定性顺序返回 `tools/list`，理由写明是「enable client-side caching and **improve LLM prompt cache hit rates**」——即上游已经把「返回体的稳定性」当成省钱手段。
  - **L49-52**：放宽 `inputSchema` / `outputSchema` 允许任意 JSON Schema 2020-12 关键字，`structuredContent` 允许任意 JSON 值。

- **与本项目节点的对应**：B1 想要「一次不大、但能拿全」，MCP 给的答案不是「把大返回分页」，而是**「列表分页 + 结果体给引用 + 只读列表可缓存」**三件。本项目的「能力搜索 / 能力目录」是列表类操作 → 可直接照 `nextCursor` 形状；「调用能力」是结果体类 → 要照的是 2.2 / 2.4，不是分页。

- **照搬过来的落地代价**：
  - 改哪：`运行核心/统一网关/协议/操作协议表.py`（操作参数）+ 薄壳 `开发工具/薄壳/工具清单.py`（工具入参）。
  - 改多大：只增不改（加 `cursor` 入参 + `nextCursor` 出参），契约兼容，无需版本递增。
  - 风险：`nextCursor` 是**不透明**的，服务端若用「可解析的位置编码」会诱使调用方自己拼游标 —— 规范明确要求不能解析。落地时必须同时定「游标有效期」（对应本项目已有的资源租约/句柄时限）。

### 2.2 MCP 官方规范：结构化输出（`structuredContent` + `outputSchema`）

- **仓库全名**：同上（规范正文 `docs/specification/2026-07-28/server/tools.mdx`）
- **近似 star**：9,264
- **它具体怎么做的**（原文 L404-632）：

  | 机制 | 原文（行号） |
  |---|---|
  | 两类内容并存 | 「Tool results may contain **structured** or **unstructured** content.」（L406） |
  | 非结构化 | 「**Unstructured** content is returned in the `content` field … can contain **multiple content items of different types**」（L408）→ text / image / audio / resource_link / embedded resource |
  | 结构化 | 「**Structured** content is returned as a JSON value in the `structuredContent` field … can be **any JSON value** that conforms to the tool's `outputSchema` if one is defined.」（L498） |
  | ★向后兼容 | 「For backwards compatibility, a tool that returns structured content **SHOULD also return the serialized JSON in a TextContent block**.」（L500）|
  | 校验义务 | 「Servers **MUST** provide structured results that conform to this schema. Clients **SHOULD** validate structured results against this schema.」（L514-515） |
  | 这一版新增 | `content` 与 `structuredContent` 在 2026-07-28 里**并存且互为兜底**：同一份数据同时给「机器可读的结构」与「模型可读的文本」。|

  ★ **L500 那条「同一份数据同时出两遍」是本节点最重要的一条**：规范把「结构化 + 文本」定义成**冗余**而不是**二选一**。本项目现在的现象（结构化字段被整段丢、文本字段被截断）恰好是把两者当成了**互斥的两种处置**。

- **与本项目节点的对应**：本项目网关返回的信封是 `{成功, 值, 错误说明, ...}`，`值` 就是 `structuredContent` 的角色，而能力各自返回的文本是 `content` 的角色。**业界口径：两者都保留、都能降级到对方**，而不是「结构化超限就丢、文本超限就截」。
- **落地代价**：改哪 —— 薄壳 `_裁剪值()` 的裁剪顺序（`薄壳服务.py:106-175`）。改多大 —— 一个函数内的分支重排：裁剪 `值` 时**同时**生成一份「同内容的文本摘要/序列化投影」放进 `值裁剪.文本兜底`，保证结构化被丢时仍有一份可读的东西。风险 —— 无契约变更；但要注意别把 6000 字符预算算重（`content` 与 `structuredContent` 共用一个预算，不是各 6000）。

### 2.3 MCP 官方规范：资源引用（Resource links / Embedded resources）

- **仓库全名**：同上
- **近似 star**：9,264
- **它具体怎么做的**（`tools.mdx`）：

  **Resource links**（L451-470）：
  ```json
  { "type": "resource_link", "uri": "file:///project/src/main.rs",
    "name": "main.rs", "description": "Primary application entry point", "mimeType": "text/x-rust" }
  ```
  原文：「A tool **MAY** return links to Resources … the tool will return a URI that **can be subscribed to or fetched by the client**」（L453-454）；
  **重要限定**：「Resource links returned by tools are **not guaranteed to appear in the results** of a `resources/list` request.」（L468-470）—— 即**链接是「按需拉」而不是「进对话」的**。

  **Embedded resources**（L473-494）：`"type": "resource"` 直接内嵌 `{uri, mimeType, text, annotations}`，带 `annotations`：`audience`（`["user","assistant"]`）、`priority`（0-1 浮点）、`lastModified`。

  ★ **注意二者是相反的两条路**：`resource` = 塞进上下文（大就危险）；`resource_link` = 只给句柄，内容**不进上下文**。

  **Stateful tools / 句柄**（L683-729）：MCP 无协议级会话，「Servers that need to maintain state across calls … should do so by returning an **explicit handle** from a creation tool and accepting that handle as an argument on subsequent calls」（L695-697）。设计建议（L721-729）：
  - **Authorization**：「a handle is a **name, not a capability**. The server should **validate the caller's authorization against the handle on every call**. For unauthenticated servers … generate with **sufficient entropy**（e.g., a UUIDv4）and give it a **bounded lifetime**.」
  - **Opacity**：「Handles that encode internal structure invite parsing or guessing; **opaque identifiers do not**.」

- **与本项目节点的对应**：**这是 B1 缺失的那条腿**。本项目已有「资源租约 / 资源状态 / 资源续租 / 资源关闭」四个操作（见任务信操作协议表），形状与 MCP 的 handle 完全同构，但**能力返回值没有挂「引用」这一层** —— 所以 81874 字符只能靠重调 6 次拿全，而不是「先拿引用、再按需拉」。
- **落地代价**：改哪 —— 网关信封加一个 `值引用`（`{引用id, 字节数, 摘要, 过期秒}`），薄壳在裁剪发生时把它回带给调用方，并加一个「取引用」操作。改多大 —— 中等：需要一条「大值落盘 + 按 id 读回」的通道（可复用平台已有的租约/资源表）。风险 —— 引用会过期（要定 `过期秒` 与续租语义）；落地后**必须**保证「引用失效时明确报错」，不能静默给空。

### 2.4 官方 servers：大返回怎么处置（fetch 的 start_index / max_length）

- **仓库全名**：`modelcontextprotocol/servers`（官方参考实现集）
- **地址**：https://github.com/modelcontextprotocol/servers
- **近似 star**：**90,514**（2026-09-21 实测；README L8-9 自述「intended as **reference implementations** … educational」）
- **它具体怎么做的**（`src/fetch/src/mcp_server_fetch/server.py`）：

  入参（L151-178）：
  ```python
  max_length: Annotated[int, Field(default=5000, gt=0, lt=1000000,
      description="Maximum number of characters to return.")]
  start_index: Annotated[int, Field(default=0, ge=0,
      description="On return output starting at this character index, "
                  "useful if a previous fetch was truncated and more context is required.")]
  raw: Annotated[bool, Field(default=False, description="Get the actual HTML content …")]
  ```
  返回体处理（L240-255）—— **这是「截断 + 续取」的教科书实现**：
  ```python
  original_length = len(content)
  if args.start_index >= original_length:
      content = "<error>No more content available.</error>"
  else:
      truncated_content = content[args.start_index : args.start_index + args.max_length]
      ...
      remaining_content = original_length - (args.start_index + actual_content_length)
      if actual_content_length == args.max_length and remaining_content > 0:
          next_start = args.start_index + actual_content_length
          content += f"\n\n<error>Content truncated. Call the fetch tool with a "
                     f"start_index of {next_start} to get more content.</error>"
  ```
  ★ 四个可照搬的细节：
  1. **默认值小而硬**（5000，且 `lt=1000000` 上限）；调用方要更多就显式给。
  2. 截断时**返回体自带下一跳指令**（`start_index of 17428`）—— 模型不需要自己算偏移。
  3. **续取耗尽时明确报「No more content available」**，而不是回空串（否则调用方分不清「到底了」和「坏了」）。
  4. 只有「正好取满且还有剩余」才追加提示（`actual_content_length == args.max_length and remaining_content > 0`），避免尾部噪声。

  另一参考实现 `src/filesystem/index.ts`：
  - `read_text_file` 用 **head / tail 行数**代替偏移（L195-203：`head` 与 `tail` 同时给直接抛错「Cannot specify both head and tail parameters simultaneously」）；
  - ★ **结构化与非结构化同出**（L208-212）：
    ```ts
    return { content: [{ type: "text" as const, text: content }],
             structuredContent: { content } };
    ```
    即 2.2 的 L500 那条规范在官方实现里就是字面照做的。

  **`everything` 参考 server 里 resource_link 的用法**（`src/everything/docs/how-it-works.md` L31-37 + `tools/gzip-file-as-resource.ts`）：
  - `registerSessionResource(server, resource, type, payload)`：「Registers a resource with the given `uri`, `name`, and `mimeType`, **returning a `resource_link`**. The content is served **from memory for the life of the session only**.」
  - 工具入参里**把「给引用」还是「给全文」做成显式开关**（`gzip-file-as-resource.ts` L35-40）：
    ```ts
    outputType: z.enum(["resourceLink", "resource"]).default("resourceLink")
      .describe("'resourceLink' returns a link to a resource that can be read later, "
                "'resource' returns a full resource object.")
    ```
    ★ **默认值是 `resourceLink`（省上下文的那一个）**，要全文得显式要。
  - 另有一条大输入上限：`GZIP_MAX_FETCH_SIZE = 10 * 1024 * 1024`、`GZIP_MAX_FETCH_TIME_MILLIS = 30 * 1000`（L11-18）。

- **与本项目节点的对应**：`fetch` 的 `start_index` 与本项目薄壳的 `值字段` 是同类（都是「让调用方自己收窄」），但 `fetch` **多了「下一跳指令」与「到底了」两个回带**。官方 servers 的 `outputType` 枚举 = 「默认给引用、要全文显式要」的现成形状。
- **落地代价**：改哪 —— 薄壳 `_裁剪值()` 的说明字典增加三项：`下一跳参数`（以**本项目自己的入参名**给出，如 `{"值字段": [...], "返回上限字符": 0}` 或 `{"引用id": "..."}`）、`是否到底`、`原值字节数`。改多大 —— 小（一个 return 的字段扩充）。风险 —— 说明字典本身占预算，要给说明留独立小额度（不要挤进 6000 里）。

### 2.5 Anthropic 工程博客（3 篇，官方原文）

- **来源**：Anthropic Engineering Blog（非仓库，官方一手）
- **地址**：
  - https://www.anthropic.com/engineering/writing-tools-for-agents
  - https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents
  - https://www.anthropic.com/engineering/code-execution-with-mcp
- **它具体怎么做的**（逐篇关键原文）：

  **① Writing effective tools for agents**
  - 「Optimizing tool responses for **token efficiency**」节：「We suggest implementing some combination of **pagination, range selection, filtering, and/or truncation** with **sensible default parameter values** for any tool responses that could use up lots of context.」并给出 Claude Code 的硬数字：「For Claude Code, we restrict tool responses to **25,000 tokens by default**.」
  - 「If you choose to truncate responses, be sure to **steer agents with helpful instructions**」——**截断必须带指令**，与本项目 `值裁剪.提示` 同向。
  - 错误体也要 prompt-engineer：「prompt-engineer your error responses to clearly communicate **specific and actionable improvements**, rather than **opaque error codes or tracebacks**」——这条正对 B2（门禁报红只给一行原文）。
  - 「Returning meaningful context」节：只回**高信号**字段，**避免**低级技术标识符（原文举 `uuid`、`256px_image_url`、`mime_type` 为例）；且「merely resolving arbitrary alphanumeric **UUIDs to more semantically meaningful … language**（or even a **0-indexed ID scheme**）significantly improves Claude's precision」。
  - **响应详略交给调用方控制**：暴露 `response_format` 枚举（`DETAILED` / `CONCISE`），示例 detailed 响应 206 tokens、concise **72 tokens**。原文：「You can add more formats … similar to **GraphQL where you can choose exactly which pieces of information you want to receive**」。
  - **工具应合并而非增加**：「instead of `list_users`/`list_events`/`create_event`, consider `schedule_event`」；「instead of `get_customer_by_id`/`list_transactions`/`list_notes`, implement `get_customer_context` which **compiles all of a customer's recent & relevant information all at once**」；「instead of `read_logs`, `search_logs` which only returns relevant log lines」。★ 这一条**直接命中华哥的元判据**（一次给全 > 三次各给一点）。
  - 诊断口径：「Lots of **redundant tool calls** might suggest some **rightsizing of pagination or token limit parameters** is warranted」——即「同一个能力重调 6 次」在 Anthropic 的评测口径里就是一个明确的可修项，指向**分页/上限参数没调对**。

  **② Effective context engineering for AI agents**
  - 核心原则：「good context engineering means finding the **smallest possible set of high-signal tokens**」；且「Context … must be treated as a **finite resource with diminishing marginal returns**」（引 context rot 研究）。
  - ★★ **just-in-time 检索**（与本节点最相关）：「Rather than pre-processing all relevant data up front, agents … maintain **lightweight identifiers (file paths, stored queries, web links, etc.)** and use these references to **dynamically load data into context at runtime** using tools.」
  - 并给出「引用元数据本身有信息量」的论证：「the **metadata of these references** provides a mechanism to efficiently refine behavior … file sizes suggest complexity; naming conventions hint at purpose; **timestamps** can be a proxy for relevance」。
  - 代价也明说了：「runtime exploration is **slower** than retrieving pre-computed data」，且「Without proper guidance, an agent can **waste context by misusing tools, chasing dead-ends**」。→ 这就是「引用 + 按需拉」不是免费的原因。
  - **tool result clearing**：Anthropic 称之为「one of the **safest lightest touch forms of compaction**」——「once a tool has been called deep in the message history, why would the agent need to see the raw result again?」并已产品化（Claude Developer Platform 的 context management）。
  - **sub-agent 架构**：子代理「might explore extensively, using tens of thousands of tokens or more, but **returns only a condensed, distilled summary** of its work（often **1,000-2,000 tokens**）」。
  - **compaction 的取舍口径**：「Start by **maximizing recall** … then iterate to improve precision by eliminating superfluous content.」

  **③ Code execution with MCP: building more efficient agents**
  - 量化现场：「For a 2-hour sales meeting, that could mean processing an additional **50,000 tokens**. Even larger documents may **exceed context window limits, breaking the workflow**.」
  - ★ **中间结果不要过模型**：Google Drive 全文 → Salesforce 的例子，「the full call transcript flows through **twice**」；改成代码执行后「the agent sees **five rows instead of 10,000**」（`pendingOrders.slice(0, 5)`）。
  - **工具定义按需加载**：把 MCP server 暴露成文件树（`./servers/<server>/<tool>.ts`），agent 先 `ls` 再读需要的定义，「reduces the token usage from **150,000 tokens to 2,000 tokens** — a **98.7%** saving」。
  - **`search_tools` 带 detail level**：「Including a **detail level parameter** … allows the agent to select the level of detail required（such as **name only, name and description, or the full definition with schemas**）」——★ 这与本项目薄壳的 `细节级别`（`名称` / `名称+说明` / `完整契约`，`工具清单.py:71`）**是同一种设计**，可互相印证。
  - **执行环境留状态**：「Agents can write intermediate results to files」，并可把成功代码**存成可复用函数**（`./skills/save-sheet-as-csv.ts`），配 `SKILL.md` 成为 skill。
  - 诚实交代代价：「code execution introduces its own complexity. Running agent-generated code requires a secure execution environment with appropriate **sandboxing, resource limits, and monitoring**.」

- **与本项目节点的对应**：
  - 「一次给全」在 Anthropic 那边的实现形式是 **①合并工具** + **②response_format 详略档** + **③代码执行里过滤**，三者都**减少往返**而不是减小单次返回。
  - 「引用 + 按需拉」在 Anthropic 那边是 just-in-time 检索，**代价是慢**——所以他们的建议是**混合**（`CLAUDE.md` 前置 + glob/grep 按需）。
  - 本项目的 `细节级别` 已经命中了 `search_tools` 的 detail level；`值字段` 命中了 response_format / range selection。
- **落地代价**：无代码依赖，纯口径。最大的收益点是「合并工具」这条：本项目 `能力搜索 → 能力详情 → 调用能力` 三跳（对应 E2，实测 search 90 次 / describe 21 次），按 Anthropic 口径应合并成「一次返回选中能力的完整契约」而不是三跳。

### 2.6 OpenAI function calling 官方最佳实践

- **来源**：OpenAI Platform Docs（官方一手）
- **地址**：https://platform.openai.com/docs/guides/function-calling
- **它具体怎么做的**（原文）：
  - **返回值形状**：「The result you pass in the `function_call_output` message should typically be a **string**, where **the format is up to you**（JSON, error codes, plain text, etc.）. The model will interpret that string as needed.」
  - **无返回值时也要给信号**：「If your function has no return value … simply return a string that indicates **success or failure**（e.g. `"success"`）」。
  - **图像/文件走数组**：可传 image/file 对象数组代替字符串（即**大二进制不进文本**）。
  - **省 token 的三条**（Token Usage 节）：「**limiting the number of functions loaded up front**, **shortening descriptions** where possible, or using **tool search** so deferred tools are loaded only when needed」。
  - **函数数量**：「Aim for **fewer than 20 functions available at the start of a turn**」（软建议）。
  - **把负担从模型挪到代码**：「Don't make the model fill arguments you already know」；「**Combine functions that are always called in sequence**」。
  - **命名空间**：用 `namespace` 分组（`crm` / `billing`），支持 `defer_loading: true` 让「命名空间描述求简、函数描述求详」（「put detailed guidance in the **function description** and keep the **namespace description concise**」）。
  - **`strict` 模式**：`"strict": true` + `additionalProperties: false` 强制参数符合 schema。
- **与本项目节点的对应**：OpenAI 侧**没有**「返回体超限怎么办」的官方条款 —— 它把返回体当**应用自己的字符串**，治理责任在调用方。★ 这条本身是结论：**「工具返回体多大」不是协议层的义务，而是调用方（本项目＝薄壳/网关）的工程义务**，不能指望模型自己扛。
- **落地代价**：`strict` 对应的迁移是「字段类型不符由网关直接拒绝」（本项目已有该规范，见契约冻结条目）；`namespace + defer_loading` 对应本项目「能力目录分域 + 按需拉契约」。

- **近似 star**：**34,878**（2026-09-21 实测；monorepo 74MB）

**（b）`Arize-ai/phoenix`**

- **地址**：https://github.com/Arize-ai/phoenix
- **近似 star**：**11,559**（2026-09-21 实测；仓库 92MB）
- **它具体怎么做的**（`src/phoenix/server/mcp/sql/execute.py`，全文 1441 行）——★ **这是本清单里与 B1 最贴近的一份实现**：
  - **成组的上限常量**（L75-90，带理由注释）：
    ```python
    DEFAULT_ROW_LIMIT = 500
    # The tool parameter is caller-controlled, so the default protects nothing on its
    # own. Rows accumulate in memory before encoding, and the per-cell byte check
    # cannot see a response made large by many small rows rather than one big one.
    MAX_ROW_LIMIT = 5_000
    # Ceiling on the whole encoded response, as distinct from any single cell.
    MAX_RESPONSE_BYTES = 4 * 1024 * 1024
    MAX_SQL_BYTES = 2 * 1024          # 唯一能限制单次调用 CPU 的界（注释 L84-86）
    BYTE_LIMIT = 262_144              # 单单元格
    PG_STATEMENT_TIMEOUT_MS = 30_000
    SQLITE_TIMEOUT_SECONDS = 30
    ```
    ★ **四层界**：单单元格（256KB）→ 整个响应（4MB）→ 单次调用输入（2KB）→ 时间（30s）。并有**夹紧逻辑**（L659-670）：`row_limit = max(1, min(requested, MAX_ROW_LIMIT))`，夹紧时**如实回带** `notes.append(f"row_limit clamped to {row_limit}")`。
  - **超限时的行为是「截断 + 显式部分标记」，不是丢弃**（L1361-1373）：
    ```python
    if total_bytes + len(encoded) > MAX_RESPONSE_BYTES:
        partial = True
        notes.append("response byte limit reached")
        break
    total_bytes += len(encoded)
    rows.append(values)
    if len(rows) > row_limit:
        # The extra row the rewrite asked for. Its arrival is the proof of
        # truncation; it is dropped rather than returned.
        rows.pop()
        partial = True
        notes.append("row_limit reached")
        break
    ```
    ★ **「多取一行，靠它到达来证明被截了」** —— 这是「静默截断」的正面反面教材：截断是**有证据的**（`partial` + `notes`），调用方永远分得清「就这么多」和「被截了」。
  - **`partial` 直接进返回信封**（L1395-1399）：`row_count_is_partial=partial`。
  - **★信封只放「会变的字段」**（L1389-1394 注释，含真实量化）：
    > 「Only what varies. Every field here can differ between two calls, so a reader who skips one loses information; anything constant — the caps, the read-only guarantee, the runtime backstop, the areas — is a property of the surface and is stated **once by `describeSqlSchema` instead of repeated on every answer**. Before that split, a one-row result was **696 bytes** of which **53 were the row** and **401 could not have taken another value**.」
    → **696B → 53B 是「把常量从每轮返回里搬走」的实测收益（约 13 倍）**。这正是华哥元判据的微观版：同一个常量在每轮全上下文注入里被重复付费。
  - **技能/参考的按需加载**（`src/phoenix/server/mcp/skills/__init__.py`）：`_SUMMARY_MAX_CHARS = 140`（L35），摘要自动从 description 截断生成（L117 `_truncate(description, _SUMMARY_MAX_CHARS)`）；`_truncate` 在**词边界**截断并收尾省略号（L141-148）；并提供 `load_skill` / `load_skill_reference` 两个工具（L27-29），参考文件是「A file **read on demand**, named by its path from the skill root」（L43-44）。
  - 另一处上限对照：`server/api/routers/oauth2_authorization_server.py:70-71` 的 `_DCR_CLIENT_NAME_MAX_LENGTH = 200`、`_DCR_LOGO_URI_MAX_LENGTH = 2048`。

- **与本项目节点的对应**：
  - Phoenix 的「**信封只放会变的字段、常量由一次 describe 声明**」→ 直接对应本项目 E2（发现要三跳）的正面解法，也对应 B1（每轮重复被判据面常量灌上下文）。**本项目 `值裁剪` 说明里若每次都回 `上限字符: 6000` 这种常量，就是 Phoenix 注释里那 401 字节的翻版。**
  - Phoenix 的「单格 → 整响应 → 输入 → 时间」四层界 → 本项目只有一个 `返回上限字符`（单值），**缺整响应层与时间层**。
  - Langfuse 的「截断标记写进载荷 + 裁剪是可选渲染属性」→ 本项目 `值裁剪` 是**另开字段**而不是标记在载荷里，形状不同（都能用，但要统一）。

## 3. 四个硬问题的回答

### 硬问题 1：大返回体的三种主流处置，各自代价？

| 处置 | 真实实现（出处） | 机制 | 代价 |
|---|---|---|---|
| **① 截断 + 续取** | 官方 servers `fetch`（`server.py:240-255`，90,514★）；Phoenix `execute.py:1361-1373`（11,559★） | 定一个「小而硬的默认上限」，截断时**返回体自带下一跳指令**（`Call the fetch tool with a start_index of 17428`），并有显式 `partial` / `notes` 标记 | **往返次数 = 内容量 / 每次上限**，这是它的天花板。Anthropic 明说「lots of redundant tool calls might suggest some rightsizing of pagination or token limit parameters」——即**上限调太小就是 bug**。本项目现状（81874 → 3292，重调 6 次）正是这个代价的极端形式 |
| **② 引用 + 按需拉** | MCP `resource_link`（`tools.mdx:451-470`）+ Stateful handles（`tools.mdx:683-729`）；官方 servers `everything` 的 `outputType: "resourceLink"`（默认值，`gzip-file-as-resource.ts:35-40`） | 返回体只给**不透明句柄**（URI / id），内容**不进上下文**，要时再拉 | **① 多一跳**（先拿引用、再拉内容）；**② 引用会过期**（规范要求 bounded lifetime）→ 必须定过期与续租；**③ 授权义务转移**（规范：「a handle is a name, not a capability … validate the caller's authorization **against the handle on every call**」）；**④ 元数据信息量丢失**（Anthropic：引用本身的「大小/命名/时间」是有用的启发信息，得额外回带）。**Anthropic 明说这类做法「runtime exploration is slower」** |
| **③ 摘要 + 原文留档** | Anthropic sub-agent（「returns only a condensed, distilled summary … often 1,000-2,000 tokens」）；Phoenix `load_skill` 摘要 `_SUMMARY_MAX_CHARS = 140`（`skills/__init__.py:35,117`）；Anthropic **tool result clearing**（「safest lightest touch forms of compaction」） | 上下文里只放**摘要/挂载点**，原文落在**上下文之外**（文件、memory、子代理语境），需要时按标识符回捞 | **① 摘要必然丢信息**（Anthropic 的取舍口径：先最大化 recall，再迭代提 precision）；**② 摘要生成本身要花一次调用**（谁摘、何时摘）；**③ 「原文在哪」需要一条稳定寻址**（本项目已有租约/资源表可复用）。优点：**单轮上下文最小**，且原文可全量留档供审计 |

★ **三者的共同底层**（三家都说了同一句）：
- Anthropic：「maintain **lightweight identifiers**（file paths, stored queries, web links）and use these references to **dynamically load data into context at runtime**」；
- MCP 规范：handle「returning an **explicit handle** … accepting that handle as an argument on subsequent calls」，且 handle 必须 **opaque**；
- Phoenix：常量由 `describeSqlSchema` **一次性**声明，不进每轮返回。

→ **结论：业界不是「三选一」，而是「三件套同时上」——默认给小的（①的默认值 + ③的摘要），同时永远给一条能拿全的把手（②的引用），且截断永远显式（Phoenix `partial` / fetch 的 `<error>`）。**

### 硬问题 2：MCP 的 `nextCursor` 语义是什么？我们能不能直接照它的形状做？

**语义（规范原文，`pagination.mdx`）**：
1. **不透明令牌**（L26-28）：「opaque cursor-based approach, instead of numbered pages」；「an **opaque string token**, representing a position in the result set」。
2. **页大小由服务端定**（L29-30）：客户端「**MUST NOT** assume a fixed page size」。
3. **结束判据是「字段缺失」而非空串**（L99、L102-107）：missing `nextCursor` = 到底；**空串是合法游标，MUST NOT 当结束**。
4. **不得解析、不得修改**（L102-107）。
5. **服务端 SHOULD 给稳定游标 + 优雅处理非法游标**；非法游标 **SHOULD** 回 **-32602**（L94-96、L111）。
6. **作用面只有 4 个 list 操作**（L85-90），**不含 `tools/call`**。
7. 2026-07-28 起列表结果**必须**带 `ttlMs` / `cacheScope`（`changelog.mdx:36`）。

**能不能照？分两处答**：

- **「能力搜索 / 能力目录」这类列表操作：能，且应该照**。形状极简，只增不改：入参加 `cursor`（字符串，可选），出参加 `nextCursor`（字符串，可选；**没这个键＝到底**）。本项目契约规范允许「只增不改」，故**不需要版本递增**。
- **「调用能力」这类结果体：不能照**。理由有二：① 规范本身没为 `tools/call` 定义分页；② 结果体分页会把「一次原子返回」拆成 N 轮，**正撞华哥元判据**（一次访问 > 三次访问）。
  → 结果体这一侧要照的是**同一份规范的另一条**：**Stateful handles**（`tools.mdx:683-729`）——「returning an explicit handle … accepting that handle as an argument on subsequent calls」，即 `值引用` + `取引用`，而**默认值给引用、要全文显式要**（官方 servers `outputType` 的默认值就是 `resourceLink`）。

★ **两个必须照的细节（容易被忽略，规范写得很硬）**：
- **空串不是结束**（L102-107）。本项目若把「空游标」当「没数据」，会与规范冲突。
- **句柄必须不透明**（L728-729）：「Handles that encode internal structure **invite parsing or guessing**; opaque identifiers do not.」→ 本项目若把文件路径/字段名编进引用 id，会诱使调用方自己拼。

### 硬问题 3：「结构化字段整段丢弃、文本字段截断」的不一致，业界有对应规范吗？

**有，而且是正面规范出来的**：MCP 2025-06-18 起引入 structured tool output，**2026-07-28 明确要求二者并存、互为兜底**：

- `docs/specification/2026-07-28/server/tools.mdx:500`：
  > 「For backwards compatibility, a tool that returns structured content **SHOULD also return the serialized JSON in a TextContent block**.」
- `docs/specification/2025-06-18/server/tools.mdx:301` 同一条（该版本 changelog 第 2 条即「Add support for structured tool output」）。
- 官方实现字面照做：`servers/src/filesystem/index.ts:208-212`
  ```ts
  return { content: [{ type: "text" as const, text: content }],
           structuredContent: { content } };
  ```
- 校验义务对称：`tools.mdx:514-515`「Servers **MUST** provide structured results that conform to this schema. Clients **SHOULD** validate structured results against this schema.」——**是校验，不是丢弃**。

**还配了「调用方可控详略」这一层**：
- Anthropic：`response_format` 枚举（`DETAILED` 206 tokens vs `CONCISE` **72 tokens**），并类比 GraphQL「choose exactly which pieces of information you want to receive」；
- Anthropic `search_tools`：**detail level** 参数「name only / name and description / the full definition with schemas」；
- OpenAI：`strict: true` + `additionalProperties: false` 让「非法状态不可表示」。

★ **对照本项目现状**：
- 本项目**没有**「结构化与文本并存」这一层 —— 现状是**二选一**（结构化超限整段丢 / 文本超限截断），这正是规范里被否定的那种处置。
- 本项目**已有**「调用方可控详略」这一层（`细节级别` 三档 = Anthropic 的 detail level；`值字段` = GraphQL 式字段选择；`返回上限字符` = range selection）——**这部分是领先的**，问题只在**超限后的兜底**。
- ★ **业界对「超限时怎么降级」的答案是统一的**：**降级到另一种表示，而不是丢**。Phoenix 是降到 `partial=true + notes`；fetch 是降到「截断体 + 下一跳」；MCP 是降到「同内容的 TextContent」；langfuse 是降到「`io.slice(...) + "...[truncated]"`」。

### 硬问题 4：华哥元判据（一次给全 > 三次各给一点）在这层怎么落地？

**元判据**：「你访问 3 次，和你一次访问。本质上一次访问注入上下文再多，也没 3 次访问那么贵。」

业界对这条的正面支持（**不是我推的，是他们写的**）：
1. **Anthropic 合并工具**：「implement a `get_customer_context` tool which **compiles all of a customer's recent & relevant information all at once**」；「combine functions that are **always called in sequence**」（OpenAI 同条）。
2. **Anthropic 中间结果不过模型**：`pendingOrders.slice(0, 5)` ——「the agent sees **five rows instead of 10,000**」；「reduces the token usage from **150,000 tokens to 2,000 tokens** — a **98.7%** saving」。★ 注意方向：**省的是「过模型的量」，不是「工具取的量」** —— 与元判据完全同向。
3. **Phoenix 常量搬出每轮返回**：696B → 53B（约 13×），理由是「401 **could not have taken another value**」。
4. **MCP 列表可缓存**：`ttlMs` / `cacheScope`（`changelog.mdx:36`）——理由写明是「reduce polling」，且列表要确定性排序以「improve **LLM prompt cache hit rates**」（L34）。

★ **落地在本层的三条可执行口径**：

| 口径 | 具体做法 | 依据 |
|---|---|---|
| **A. 默认给「一次能拿全的最小」** | 默认上限不要为了「不超预算」压到远小于典型返回；压到需要重调的默认值是 bug（Anthropic 明确把「redundant tool calls」判为 pagination/token limit **参数没调对**）。判据：**同一能力被同一会话重调 > 2 次 = 默认值错了** | Anthropic ①；官方 servers `fetch` 默认 5000 且给了 `lt=1000000` 的抬升空间 |
| **B. 超限时「降级不丢 + 给把手」** | 三件同时给：①显式标记（Phoenix `partial`）；②**下一跳指令**（fetch：`start_index of 17428`）；③**引用把手**（MCP handle）拉全量 | Phoenix `execute.py:1361-1373`；官方 servers `server.py:252-254`；`tools.mdx:683-729` |
| **C. 常量不进每轮返回** | 上限值、只读保证、覆盖面等**不会变的字段**由一次「说明/契约」调用声明，每轮返回只带**会变的字段** | Phoenix `execute.py:1389-1394`（696B→53B）；MCP `ttlMs`/`cacheScope` |

### 4.3 本层元判据的可验证判据（建议纳入验收）

1. **同能力重调次数**：同一会话内，同一能力 + 同一参数被调用次数 **> 2 次 = 红**（依据：Anthropic「redundant tool calls → pagination/token limit 参数没调对」）。
2. **截断必带出路**：任何 `值裁剪.已裁剪 = 真` 的返回，必须同时含 `下一跳入参` 或 `值引用`；二者皆无 = 红（依据：Phoenix `partial`+`notes`、fetch 的下一跳 `<error>`）。
3. **到底可区分**：调用方必须能区分「已取全」与「被截断」（依据：fetch 的 `No more content available.` vs `Content truncated. Call ... start_index of N`；Phoenix `row_count_is_partial`）。
