## 一、本路要回答的问题

本项目的 MCP 调用链是：Hermes 薄壳（`mcp__system_engineering_toolkit__*`）→ 40007 唯一网关 → 能力目录 → 具体能力实现。本路负责一个节点：

- **B2（返回体层·门禁报红只给一行原文）**：门禁判红时返回的是「一行原文」，**不给落点（file:line:col）、不给修法（可复制的命令 / 可应用的替换）**，人只能拿着这行字再去全仓找、再猜怎么改，于是又变成多轮往返。

元判据（华哥原话）：

> 「你访问 3 次，和你一次访问。**本质上一次访问注入上下文再多，也没 3 次访问那么贵**。这个是实打实的问题。」

即 **往返次数 × 每轮全上下文注入 = 真成本**。对本路的含义：**一条红项如果一次没给全「哪一行 + 怎么改」，就注定要被再问一轮**——所以「报错可修复性」就是「往返次数」问题，不是排版问题。

## 三、逐仓库审计

### 3.1 `astral-sh/ruff` —— 一条诊断的「可修」是**字段**，不是一个形容词

- 地址：https://github.com/astral-sh/ruff ｜ star ≈ 49.7k
- 关键文件：`crates/ruff_diagnostics/src/fix.rs`、`crates/ruff_db/src/diagnostic/render/json.rs`、`crates/ruff/src/args.rs`
- 机制（源码原文取证）：

  1) **修复分三档可信度**，`fix.rs` 的 `pub enum Applicability`：`DisplayOnly`（只给人看，可能改坏语法）/ `Unsafe`（**可能不是你要的**，会改运行行为、可能吃掉注释，需用户显式 opt-in）/ `Safe`（**可以无条件应用**，保留注释）。另有 `IsolationLevel`（`Group(u32)`）描述「同一组里不能同时应用」的互斥关系。
  2) **机器可读出口把每个字段都摊平**：`render/json.rs` 的 `JsonDiagnostic` = `code / message / severity / url / fix{applicability, edits[]}`；每个 edit 带 `location{row,column}` 与 `end_location{row,column}`（源码里逐字段算行列表，并对「跨单元格拼接源码」这种边界单独处理）。
  3) **URL 是诊断自带的字段**（`url: diagnostic.documentation_url()`，单测断言 `"url": "https://docs.astral.sh/ruff/rules/test-diagnostic"`）——即**规则文档地址随红项一起返回**，不需要人再去猜规则名搜文档。
  4) CLI 把「看」与「改」分成两个口：`--diff`（只输出差异、不写盘、无差异退 0）/ `--fix` / `--no-fix` / `--fix-only` / `--unsafe-fixes`（`args.rs`，`--diff` 与 `--output-format` 等显式 `conflicts_with`）。

- **与本项目节点的对应**：本项目的红项应当像 `JsonDiagnostic` 一样**先有字段、再谈排版**。最低配是四件：`code`（判据名，本项目已有）、`location{file,line,col}`、`url`（规则/说明文档落点）、`fix{applicability, edits}`（能不能自动改、怎么改）。
- **落地代价**：小。本项目门禁都是自己写的 Python，打印点集中（`[判据名] …` 前缀已统一），把打印点从「拼一行字符串」改成「先构造红项字典、再按 `--格式=文本|json` 渲染」即可；风险是各门禁各有各的打印点（数量现场取，见 §2.3），要一次性收敛到统一渲染器，否则又是第二套判据。

### 3.2 `golangci/golangci-lint` —— 「能自动修」的完整工程链：建议 → 冲突检测 → 回传未修项

- 地址：https://github.com/golangci/golangci-lint ｜ star ≈ 19.4k
- 关键文件：`pkg/result/issue.go`、`pkg/result/processors/fixer.go`、`pkg/printers/{text,json,sarif,checkstyle}.go`
- 机制（源码原文取证）：

  1) **`Issue` 结构体字段即「可修」的全部要件**：`FromLinter`（判据名）、`Text`（原文）、`Severity`、`SourceLines`（出问题的源码行）、`Pos token.Position`（**文件+行列**）、`LineRange`、`HunkPos`（跑在 diff 上时的落点）、`SuggestedFixes []analysis.SuggestedFix`（**建议修复，可能多条**）。
  2) **指纹字段**：`Issue.Fingerprint()` = `md5(文件名 + 文本 + 首行)`——用来在多次运行/多工具间**认领同一条红项**（本项目缺的就是这个：同一个红项跨轮次认不出来，所以每次都要重新解释一遍）。
  3) **自动修复是真跑通的**：`fixer.go` 把 `SuggestedFixes[].TextEdits[]` 转成 `diff.Edit{Start,End,New}`，**先做冲突检测**（`validateEdits` 检查相邻编辑是否重叠；不同 linter 之间再两两查 `diff3Conflict`），冲突的 linter 整组跳过并告警，然后 `diff.ApplyBytes` 写盘、再走 formatter；**修不掉的 issue 作为 `notFixableIssues` 继续往下流**——即「改不了的照样报给你」，不会静默消失。
  4) **输出形态可切换**：`pkg/printers/` 同时提供 `text`（`文件:行: 消息`，`text.go` 里 `pos := p.SprintfColored(color.Bold, "%s:%d", issue.FilePath(), issue.Line())`，并画出 `^` 指位）、`json`、`sarif`、`checkstyle`、`codeclimate`、`junitxml`、`teamcity`。**同一份红项，人看的和机器读的是两个渲染器**。
- **与本项目节点的对应**：① 本项目的红项**缺 `file:line` 与 `SuggestedFixes` 两类字段**，而 `Fingerprint` 正是「跨轮次认出同一条红项」的现成解法；② 「修不掉的照样报」＝ 本项目 `_尾部()` 里「判红时违规条目一条不砍」的同源思路，可继续沿用；③ 多渲染器（文本给模型、json 给程序）是本项目要补的那一层。
- **落地代价**：中。要动的不是某一个门禁，而是**统一的红项构造器 + 渲染器**（把各门禁打印点一次性收敛）；风险：门禁之间已有「只报告 / 阻断」角色差异，渲染层不得改写判定逻辑（本项目 `编译口.py` 明令「不新建第二套判据」）。

### 3.3 `eslint/eslint` —— 「可修」与「可建议」是两件事，且修复要声明类型

- 地址：https://github.com/eslint/eslint ｜ star ≈ 27.5k
- 关键文件：`docs/src/use/command-line-interface.md`、`lib/cli-engine/formatters/{stylish,json,json-with-metadata}.js`
- 机制（源码/文档原文取证）：

  1) CLI 三档：`--fix`（自动修并写盘）、`--fix-dry-run`（**只算不写**，官方原文：「you'll have to use another formatter (e.g. `--format json`) to get the fixes」）、`--fix-type Array`（只应用指定类别：`directive, problem, suggestion, layout`）。
  2) 修复分**两类**：规则的 `meta.fixable`（可自动改）与 `suggestions`（**只给建议，不自动改**，Linter 会校验「Fixable rules must set the meta.fixable property」）。
  3) 输出：`stylish.js` 人读形态是 `文件路径` + 缩进的 `行:列  错误级别  消息  规则名`（源码里 `String(message.line||0)`、`String(message.column||0)`、`message.ruleId ? styleText("dim", message.ruleId)`）；`json.js` 就是 `JSON.stringify(results)`——**同一份结果对象原样序列化**，字段名不另起（`line/column/ruleId/message/severity/fix/suggestions/endLine/endColumn/nodeType`）。
- **与本项目节点的对应**：本项目红项现在**既没有「可自动修」也没有「只给建议」的区分**——一律是一行原文。eslint 的分档（自动修 / 建议 / 修哪一类）正好是本项目「步骤4 自动修复」缺失的分类学（`编译口.py` 明文写着「步骤4（自动修复）属审计件 §8.7 第二批，本版未实现」）。
- **落地代价**：小-中。先给红项加一个 `修复类别`（可自动 / 需人工）字段即可，无需真做自动修；风险：类别判断错了会误导（把「需人工」标成「可自动」＝ 假绿通道）。

### 3.4 Rust 编译器 + `cargo fix` —— `Applicability` 是「机器可应用」的行业定义

- 仓库：`rust-lang/rustc-dev-guide`（https://github.com/rust-lang/rustc-dev-guide，star ≈ 1.9k）、`rust-lang/cargo`（https://github.com/rust-lang/cargo，star ≈ 15.5k）、`rust-lang/rust-clippy`（https://github.com/rust-lang/rust-clippy，star ≈ 13.5k）
- 关键文件：`rustc-dev-guide/src/diagnostics.md`、`cargo/src/ops/cargo_fix/mod.rs`、`cargo/src/bin/cargo/commands/fix.rs`、`rust-clippy/clippy_utils/src/sugg.rs`
- 机制（源码原文取证）：

  1) **四档 `Applicability`（rustc-dev-guide 原文列全）**：`MachineApplicable`（**可机械应用**）/ `HasPlaceholders`（有占位符，不能机械应用）/ `MaybeIncorrect`（**可能不对**，不能机械应用）/ `Unspecified`。文档原句：从高到低排序，`MachineApplicable` 最高。
  2) **suggestion 的降级是自动的**：clippy 的 `sugg.rs` 会在源码来自宏展开时把 `MachineApplicable` 降为 `MaybeIncorrect`、在出现占位符时降为 `HasPlaceholders`——**「可自动修」这个标记不许吹牛，由工具自己降级**。
  3) **`cargo fix` 的执行链（`cargo_fix/mod.rs` 头部注释逐字）**：代理模式下每个 rustc 进程 → 从主 cargo 取锁 → **读 rustc 的 JSON 输出里的 suggested fixes** → 用 `rustfix` crate 应用 → 有重叠等失败时**最多重试 4 轮**（只要还有成功的） → 应用后**再跑一次 rustc 验证没改坏**，改坏了**回滚**（除非 `--broken-code`）。
  4) `cargo fix` 的旗标即「安全阀」：`--broken-code`（允许改坏）、`--allow-dirty` / `--allow-no-vcs`（脏工作区/无版本控制才敢动文件）、`--edition` / `--edition-idioms`（按迁移目标修）。
- **与本项目节点的对应**：本项目**已经是 git 仓库**（安全阀天然具备），门禁里「改哪个文件、改成什么」多数是确定性的（如「说明书缺某字段」「目录树有摘要无」），属于 `MachineApplicable` 那一档；先把红项标出「可机械应用 / 需人工」，再谈自动修。
- **落地代价**：中-大（若真做自动修）。`cargo fix` 的可信度来自「改完再跑一遍验证 + 坏了回滚」，本项目要做等价物就必须把「改 → 重跑门禁 → 失败回滚」串起来；**风险最高的一步是「回滚」**——本仓明文禁止 `git stash` 系列，回滚必须走 `git checkout HEAD -- <精确路径>`。

### 3.5 SARIF（`oasis-tcs/sarif-spec` + `microsoft/sarif-sdk`）—— 静态分析结果的交换格式，字段就是标准答案

- 仓库：`oasis-tcs/sarif-spec`（https://github.com/oasis-tcs/sarif-spec，star ≈ 212）、`microsoft/sarif-sdk`（https://github.com/microsoft/sarif-sdk，star ≈ 226）
- 关键文件：`sarif-2.1/schema/sarif-schema-2.1.0.json`（规范 schema，逐字段 description 已实测导出）、`src/Sarif/Autogenerated/Result.cs`、`src/Sarif/Core/Result.cs`
- 机制（**schema 逐字段实测**，非记忆）：

  | 对象 | 关键字段（schema 原文） |
  |---|---|
  | `result` | `ruleId`（规则的稳定唯一 id）/ `ruleIndex` / `rule` / `level`（**枚举 `none/note/warning/error`，默认 `warning`**）/ `message`（**唯一必填项**，首句用于空间受限时显示）/ `locations` / `relatedLocations` / `fixes`（**一组建议修复**）/ `partialFingerprints`（**贡献稳定唯一身份的一组字符串**）/ `properties` |
  | `fix` | `description`（**给人看的修复说明**）+ `artifactChanges`（必填） |
  | `artifactChange` | `artifactLocation` + `replacements` |
  | `replacement` | `deletedRegion`（必填）+ `insertedContent{text/binary/rendered}` |
  | `region` | `startLine` / `startColumn` / `endLine` / `endColumn` / `charOffset` / `charLength` / `snippet` / `message` |
  | `physicalLocation` | `artifactLocation{uri,uriBaseId,index,description}` + `region` + `contextRegion`（**给查看器补上下文**） |
  | `reportingDescriptor`（规则定义） | `id`（必填）/ `name` / `shortDescription` / `fullDescription`（原文：「should…provide details **sufficient to enable resolution** of any problem」）/ `help` / **`helpUri`**（规则文档地址）/ `defaultConfiguration` |

  关键结构事实：**`helpUri` 挂在「规则描述符」上，不挂在结果上**——结果靠 `ruleId`/`ruleIndex`/`rule` 回指规则。`microsoft/sarif-sdk` 的 `Result.cs` 与 schema 一一对应（`RuleId` / `Level`(FailureLevel) / `Message` / `Locations` / `RelatedLocations` / `Fixes` / `PartialFingerprints`）。
- **与本项目节点的对应**：这是**字段清单的直接来源**。本项目红项要补的字段，逐个都能在这里找到对应物（判据名↔`ruleId`、红绿↔`level`、落点↔`locations[].physicalLocation.region`、修法↔`fixes[].artifactChanges[].replacements[]`、跨轮次认领↔`partialFingerprints`、文档↔`helpUri`）。
- **落地代价**：小（只借字段，不必真产 SARIF 文件）。若真要产 SARIF（能被 GitHub Code Scanning 直接吃），代价在 `ruleIndex`/`artifacts` 的索引一致性校验——本项目当前无此需求。

### 3.6 `reviewdog/reviewdog` —— 「任意 linter 的原始输出 → 结构化红项 → 落到 diff 行」的三段式

- 地址：https://github.com/reviewdog/reviewdog ｜ star ≈ 9.6k
- 关键文件：`proto/rdf/reviewdog.proto`（Reviewdog Diagnostic Format）、`parser/{errorformat,checkstyle,rdjson,rdjsonl,sarif}.go`、`cmd/reviewdog/main.go`
- 机制（源码原文取证）：

  1) **RDF 是「给编译器和 linter 与开发工具之间通信用」的通用消息结构**（proto 文件开头原文），两种线格式：`rdjsonl`（每行一条 `Diagnostic`）与 `rdjson`（一条 `DiagnosticResult`）。
  2) **`Diagnostic` 字段**（proto 逐字段）：`message` / `location{path, range{start{line,column}, end{line,column}}}` / `severity`（`ERROR/WARNING/INFO/UNKNOWN_SEVERITY`）/ `source{name,url}` / **`code{value, url}`**（规则码 + **打开更多信息的 URL**）/ **`suggestions[]{range, text}`**（可插入/可替换的具体文本，删除＝空串）/ `original_output`（**原始输出原文**，便于「结构化失败就退回原文」）/ `related_locations[]{message, location}`。
  3) **它能吃任意 linter**：`parser/errorformat.go` 用 `github.com/reviewdog/errorformat` 把 `%f:%l:%c: %m` 这类格式串解析成 RDF；另有 `checkstyle` / `sarif` / `rdjson(l)` 解析器——**这就是「先统一格式，再谈可修」的工程证明**。
  4) **过滤与投递分离**：`-filter-mode` = `added`(默认，只报**新增/修改的 diff 行**) / `diff_context` / `file` / `nofilter`；`-reporter` = `local`(默认) / `rdjson` / `rdjsonl` / `github-pr-check` / `github-pr-review` / `gitlab-mr-discussion` 等。
- **与本项目节点的对应**：① `original_output` 字段正是本项目现在**唯一**有的东西——reviewdog 的做法是「**原文保留，但结构化字段另给**」，不是二选一；② `-filter-mode=added` 对应本项目「只对本次改动集判红」（`编译口.py` 的 `--变更` 已经是这个口径，只是没有红项级过滤）；③ `code.url` + `suggestions[]` 是「一条红项自带修法与文档」的现成形状。
- **落地代价**：小。RDF 字段可以**直接当本项目的红项字段表**抄（不必引入 reviewdog 本身）；风险：`suggestions` 的 range 语义是「**end 为开区间**」（proto 里用大段注释专门讲零宽插入与行尾），自己实现时必须照抄这个语义，否则插入位置会偏。

### 3.7 `open-policy-agent/opa` —— 策略判定的「决策 + 理由追踪」是另一种可修：给路径，不给文本

- 地址：https://github.com/open-policy-agent/opa ｜ star ≈ 12.3k
- 关键文件：`cmd/eval.go`、`v1/topdown/trace.go`、`v1/topdown/lineage/lineage.go`、`v1/ast/policy.go`
- 机制（源码原文取证）：

  1) **`--explain` 四档**：`eval.go` 里 `explainModeOff/full/notes/fails/debug`；四种解释分别由 `lineage.Full / Notes / Fails / Debug` 生成，结果挂在返回体的 **`result.Explanation`** 字段上（`eval.go`：`result.Explanation = lineage.Full(*(ectx.tracer))`）——**解释是返回体的一等字段，不是日志**。
  2) **追踪事件带源码位置**：`topdown/trace.go` 的 `Event` 有 `Op`（`Enter/Exit/Eval/Redo/Fail/...`）、`Node ast.Node`、**`Location *ast.Location`**、`Locals`（变量绑定）、`Message`。`ast` 侧几乎所有节点都带 `Location *Location json:"location,omitempty"`（`policy.go` 里逐类型可见）。
  3) 即：OPA 判红时给的不是「一句话」，而是**「哪条规则的哪一行 → 哪一步求值失败 → 当时变量是什么」的因果链**，而且这条链是可序列化的字段。
- **与本项目节点的对应**：本项目门禁里最像策略引擎的是「契约漂移 / 参数可用性 / 说明书白名单」这类**规则扫描**。它们现在的输出是结论（`[违规] {问题}`），**没有「为什么判这一条」的中间步骤**——OPA 的 `lineage.Fails` 对应「只解释失败路径」这一档，恰好是给模型看的最省 token 的档位。
- **落地代价**：中。要在本项目复刻，需要门禁在扫描时**记录命中位置（文件+行）与命中原因**，而不是最后 `print` 一行；风险：门禁逐条记录会变慢（本项目已有 15 秒/条命令的硬上限），需实测耗时后再决定档位（`full` 与 `fails` 的代价差别很大，OPA 用 `--explain` 档位把这个选择权交给调用方，本项目也应照此做成可选档）。

### 3.8 小结：七个仓库给出的共同形状

把上面七家的「一条红项」字段做交集，**任何一家都至少给了这五件**：

1. **判据名/规则码**（`FromLinter` / `ruleId` / `code.value` / `diagnostic.code`）
2. **落点**：文件 + 行 + 列（`Pos token.Position` / `locations[].region` / `location.range`）
3. **严重级别**（`Severity` / `level` 枚举 / `severity`）
4. **修法**：可机械应用的建议（`SuggestedFixes` / `fixes[].replacements` / `suggestions[]` / `Applicability::MachineApplicable`）
5. **规则文档地址**（ruff 的 `url` / SARIF `reportingDescriptor.helpUri` / RDF `code.url`）

外加两家额外给了「**跨轮次认领**」字段：golangci-lint 的 `Fingerprint()`、SARIF 的 `partialFingerprints`。

**本项目现在只有第 1 项（且是文本形式），第 2/4/5 项完全缺失，指纹也没有。**

## 四、硬问题回答

### 4.1 一条红项应该带哪几个字段才算可修？

按「**一次给全 = 少一轮往返**」这条元判据，字段必须让模型**不回读源码也能动手**。最小可修字段集（六件，全部有上面七家的对应物）：

| # | 字段 | 为什么必须有（缺了会多一轮什么） | 来源参照 |
|---|---|---|---|
| 1 | `判据名` | 现在有；用来定位规则文档与判定口径 | `FromLinter` / `ruleId` |
| 2 | `落点 {文件, 行, 列}` | **缺它就必须再全仓搜一次**（本项目现在正是这样） | `Pos` / `region` / `location.range` |
| 3 | `原文片段`（该行或该区块的 snippet） | 缺它就要再读一次文件；SARIF 有专门的 `contextRegion`/`snippet` | `SourceLines` / `snippet` |
| 4 | `修法`（**二选一**：可复制的命令 **或** 可应用的替换 `{region, 新文本}`） | 缺它就要再猜一轮怎么改 | `SuggestedFixes` / `fixes` / `suggestions` |
| 5 | `可自动修级别`（可机械应用 / 需人工） | 缺它模型会尝试自动改不该自动改的东西 | `Applicability` / `meta.fixable` vs `suggestions` |
| 6 | `规则文档落点`（本仓内路径，或 `helpUri`） | 缺它就要再搜「这个判据是什么意思」 | ruff `url` / `helpUri` |

建议额外加两件（成本极低、收益明确）：

7. `红项指纹`（`md5(判据名 + 文件 + 文本)` 级别即可）——用于**跨轮次认领同一条红项**，避免「修了 3 条、还剩几条」每轮重新解释一遍（golangci-lint `Fingerprint()` 同形制）。
8. `本轮未修项标记`——像 golangci-lint 的 `notFixableIssues` 一样，「改不了的照样报出来」，防止「报了但没修」被读成「没有这条」。

**一句话口径**：一条红项 = **「哪条规则 + 哪一行 + 长什么样 + 怎么改 + 能不能自动改 + 去哪看规则」**。六件齐了，模型一轮就能改；缺一件，就要多一轮。

### 4.2 SARIF 的 `fixes` 字段能不能直接映射成「可复制的修复命令」？

**不能直接映射，但能映射成「可应用的替换」，命令要自己再包一层。** 依据（schema 实测）：

- `fix.artifactChanges[].replacements[]` 的语义是**内容替换**：`deletedRegion`（必填，一个 `region`）+ `insertedContent{text|binary|rendered}`——它是「把这段删掉、插上这段」，**不是命令行**。
- 而且 `fixes` 是**数组**（schema：`An array of 'fix' objects`），一个红项可能有多套修法；SARIF 里**没有**「该用哪一套」的默认语义，也没有「应用者」角色定义。
- `reportingDescriptor.helpUri` 提供的是**规则文档地址**，不是修法命令。

⇒ **正确的映射链是两层**：

1. **第一层（标准化，抄 SARIF/RDF）**：红项带 `fixes[]{deletedRegion, insertedContent}`，这是**任何修法都能表达的最小公分母**（`reviewdog` 的 `suggestions[]{range,text}` 与 `ruff` 的 `fix.edits[]` 同构，三家的语义完全一致）。
2. **第二层（本项目自己的渲染器）**：在红项上加一个**本项目特有的 `修复命令` 字段**——因为本项目多数门禁的修法是**生成器命令**（例如「改完正文必须跑 `--写盘`」「改完契约必须重跑契约编译器」），这类修法 SARIF 表达不了（它不是文本替换），但**本项目自己知道**。

**关键结论**：`fixes` 不能替代命令，但**命令必须与 `fixes` 同一条红项一起返回**——这正是本项目「一次给全」的落点：红项里同时给「人可读的修法说明 + 机器可应用的替换 + 本项目可复制的生成器命令」，三样一次给完，不给第二次往返的理由。

### 4.3 本项目编译口的门禁报红输出，改成什么形状最省后续往返？

**结论：把「一行文本」改成「红项对象数组 + 两种渲染」，且必须保持退出码与五态判定一字不动。**

具体形状（字段名可直接抄 §4.1 六件套；这里是落点建议，不是已实现的承诺）：

```
═══ 结论 ═══
五态结论：失败 —— 阻断类红项 2 条（另有只报告类 1 条）

红项①  判据=公开调用完整性  级别=阻断  指纹=8f3a…
  落点  能力id=…  包=…  路径=…/服务.py:88:5
  片段  def 调用(…):
  修法  [可机械应用] 补「说明书字段」行：…/说明/使用说明.md 的能力清单表
  命令  python3.14 -m 开发工具.契约编译.能力定义编译器 <包目录> && python3.14 -m 开发工具.MD文档生成 --类型 包级说明-使用说明 --写盘
  规则  开发文档/规范/…（或 说明/…）
```

为什么这个形状最省往返（逐条对着元判据）：

1. **红项自带落点与修法** ⇒ 省掉「再打开文件找行」「再猜怎么改」两轮（对应 §3.1/§3.2 的字段缺失）。
2. **`命令` 字段是可直接复制执行的** ⇒ 省掉「修完再问一遍该跑什么」这一轮（对应 §4.2 的第二层，SARIF 给不了）。
3. **指纹 + 未修项标记** ⇒ 省掉「还剩几条、是不是同一条」的反复对账（对应 §3.2 的 `Fingerprint` 与 `notFixableIssues`）。
4. **文本渲染给人/模型、json 渲染给程序** ⇒ 同一次调用，模型看文本、脚本读 json，**不需要第二次调用**（对应 §3.1 ruff 的 `--output-format json`、§3.3 eslint 的 `--format json`）。
5. **`--explain` 式档位**（对应 §3.7 OPA）⇒ 默认只给「失败路径的解释」，需要时才 `--解释=全`，避免默认把返回体撑爆（这与本项目 B1 的「结构化字段被整段丢弃」是同一个约束的两面）。

**必须同时守住的三条**（否则是假绿）：

- **退出码与五态结论一字不动**：渲染只换形状，不改判定（`编译口.py` 明令「不新建第二套判据」）。
- **判红时违规条目一条不砍**：现在靠 `违规条目前缀 = "["` 做全量透出，改成对象数组后**必须保持全量**（否则退回「反复单跑才看全」）。
- **没有落点/修法的红项不许假装有**：拿不到行列就写「无落点」，**不许编**（对应 §3.4 clippy 的自动降级：`MachineApplicable` 该降就降）。

## 五、照搬进本项目的落地代价

| 改动 | 改哪 | 改多大 | 风险 |
|---|---|---|---|
| 统一「红项对象 + 渲染器」 | `开发工具/开发编译口/编译口.py` 的 `_尾部()` 与各门禁打印点 | 中：一个渲染器 + 逐门禁把 `print(f"[判据] …")` 改成构造红项 | 门禁打印点分散（清单见 `编译口.py` 的 `门禁清单`，项数现场取），漏改会造成两种形状并存；**判定逻辑一律不许动** |
| 补 `file:line:col` 落点 | 各门禁的扫描点（如 `公开调用完整性门禁.py` 的 `路径=` 处、`参数可用性体检.py` 的 `[违规]` 处） | 中：扫描时本就要读文件，加行号是顺带 | 有的判据**本来就没有单一行落点**（如「存量基线计数」类），必须允许「无落点」而不是硬凑 |
| 补 `修复命令` 字段 | 红项构造处 | 小：多数门禁的修法就是固定的一条生成器命令 | 命令写错比不写更坏（模型会照抄执行）⇒ 命令必须由门禁自己给，不许渲染层拼 |
| 补 `指纹` | 红项构造处 | 小：`md5(判据名+路径+文本)` | 指纹必须稳定（含路径与判据名），否则跨轮次认不出来，等于白加 |
| 补 `--解释` 档位 | 需要解释链的规则扫描类门禁（漂移/参数可用性/说明书白名单） | 中-大：要记录「为什么判这一条」的中间步骤 | 本项目有**单命令 15 秒硬上限**，记录中间步骤会变慢 ⇒ 必须先实测耗时（OPA 用档位把代价选择权交给调用方，本项目照此做） |
| 真做自动修复（`cargo fix` 等价物） | `编译口.py` 步骤4（现为「本版未实现」） | 大：改 → 重跑门禁 → 失败回滚 三件套 | **回滚必须走 `git checkout HEAD -- <精确路径>`**（本仓严禁 `git stash` 系列）；且并行维修期禁跑发布门禁（会假红）⇒ 自动修复只能在自己的精确路径上做 |
