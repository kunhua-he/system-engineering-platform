## 零、元判据（后面每条都要用它称重）

```
真成本 = 往返次数 × 每轮全上下文注入
```

推论（本文所有建议都按它排序）：

1. **减少往返 > 缩小返回**。把一次返回从 8 万字符压到 6 千字符、却要重调 6 次，是**亏的**。
2. **工具描述（description）也是每轮注入**。薄壳 3 个工具的 description 已经长到需要靠它
   教模型「怎么用」，这本身是设计缺陷的补偿成本。
3. **一次给全，哪怕单次返回体更大**。只有「上下文真的装不下」才该分次。

## 二、逐节点审计

### A1 薄壳一次只许调 1 个 local 工具 —— **落点在 Hermes 侧，不是平台**

- **落点**：`~/.hermes/hermes-agent/tools/tool_search_validation.py:196 local_batch_error()`
- **现状**：批量请求里只要出现 local 工具名，整批拒绝，回带：
  `tool_call takes exactly one entry for local tools; you sent N.`
  并**回显调用方自己第一条 payload**作为可复制模板。
- **关键事实（推翻我上一轮的口径）**：这不是遗漏，是**有意为之**，且 Hermes 作者知道代价 ——
  函数 docstring 原文：
  > *"small models re-send an identical batch when told only the constraint, and the echoed payload is what gets them unstuck."*
  即：作者预期小模型会**重发同一批**，所以特意回显 payload。这说明「批量被拒 → 重试」是
  **已知且被容忍**的路径。
- **对比矛盾**：平台自己的 `系统核心支持库.进程管理.执行命令集` **支持并行最多 8 路**
  （同一份能力定义里写死「命令表最多 64 条；并行最多 8 路」）。**下能并行、上不能批量**。
- **实测代价**：本轮我调 `能力目录.搜索能力` 想与 `读取能力` 并行，被当场拦下；整个任务里
  绝大多数能力调用都是串行的，每一跳都是完整上下文重注。
- **优化方向（三选一，代价递增）**：
  1. **薄壳侧聚合成一个工具**：`capability_call` 支持 `调用列表=[{能力id,参数},…]`，
     平台内部串行/并行跑完**一次返回**。→ 对 Hermes 零改动，只改薄壳 + 网关。
     **这是最小改动、最符合华哥判据的一条。**
  2. Hermes 侧放开 local 批量（需保留逐个审批链，代价大、影响所有工具）。
  3. 不做，继续容忍重试。

### A2 工具签名不自描述 → 第一跳必错

- **落点**：`开发工具/薄壳/工具清单.py:148-152`
- **现状（决定性）**：`capability_call` 的入参 schema 是：

  ```
  properties:
    能力id: {type: string}
    参数:   {type: object}   ← 自由对象，无 properties、无 required、无类型
  ```

  **能力自身的参数形状完全不暴露**。模型只能盲填 → 必错 → 400 → 再读契约 → 重调。
- **Hermes 侧已在补偿，且注释直说了这件事**（`tool_search_validation.py`）：
  > *"Models invoke deferred tools 'blind' (schema unseen) and omit required args;
  > without this, the opaque downstream failure makes cheap models loop."*
  补偿手段：required-field 探测 → `coerce_tool_args` 类型强转 → jsonschema 校验 → 回带
  `path` / `constraint` / `parameters` 的**结构化纠错**。
  **但这套补偿只作用于 Hermes 自己注册的工具**；`capability_call` 里的 `参数` 是 `object`，
  Hermes 看不见内部形状 → **兜不住，只能靠平台侧**。
- **实测代价（本轮 3 次）**：
  | 我写的 | 真实参数名 | 结果 |
  |---|---|---|
  | `命令列表` | `命令表` | 400 缺少必填参数 |
  | `替换表` | `编辑列表` | 400 缺少必填参数 |
  | `编辑列表` 里每项只给 `旧文本/新文本` | 每项还必须带 `文件路径` | 400 第 1 条的 文件路径 必须是非空文本 |
  | `路径` | `文件路径` | 400 缺少必填参数 |
- **平台侧已有现成答案，但默认关着**：
  - `能力目录.搜索能力` 有 `含常用参数`（历史上最常用的 5 组**真实入参样例**），
    **默认 `false`**（理由是"会放大返回体量"）；
  - 独立的 `能力目录.常用参数组合`（取单个能力的组合）。
  → 按元判据：**为了省一次返回的体量，换来的是"猜参数名"的额外往返**，这是**算反了**。
- **优化方向**：
  1. `capability_call` 的 400 回执**必须带该能力的正确签名**（参数名/类型/必填/一组真实样例）。
     一句话：**调用失败时把答案一起给**，而不是让调用方再跑一趟。
  2. `能力目录.搜索能力` **单命中时自动带参数名**（多命中才需要控体量）——精确命中场景
     体量本来就不大。
  3. `含常用参数` 默认改 `true`，或者改成"单命中自动带"。

### B1 返回体超限被丢 → 同一个能力重调 6 次

- **落点**：`开发工具/薄壳/薄壳服务.py:79-173`（裁剪实现）
- **现状（读实现后修正我上一轮的口径）**：规则其实是**自洽的**，不是"规则不统一"：
  - `默认返回上限字符 = 6000`
  - `值` 是 **dict** → 逐键试算，**单键超限就整键丢弃**（注释明写"不搞至少留一个的例外"）
  - `值` 是 **list** → 截尾
  - `值` 是 **str** → 截断到上限
  - 超限必回带 `值裁剪` 说明（`丢弃字段` / `列表截断` / `文本截断` / `全部丢弃` / `提示`）
- **真痛点（比"规则不统一"更准确）**：`执行命令` 的返回形状是
  `值 = {退出码, 标准输出, 错误输出}` —— 走 **dict 分支**，而**唯一有用的那个字段
  （`标准输出`）恰恰是最长的**，于是被**整键丢弃**，只剩 `退出码`。
  实测：`执行命令集` 返回 6453 字符 → `结果表` 整段没了；`运行开发编译口` 返回 81874 字符
  → 裁剪到 3292，**同一个能力我重调了 6 次**才把 15 项门禁看全。
  **这不是"看不见的红项"，这是"看不见的结果"。**
- **另一处同族缺陷**：`执行命令` 有硬输出上限
  （`公共契约/运行时/有界IO.py:18 默认子进程输出上限字节 = 256 * 1024`），
  超了由 `支持库/后端/系统核心支持库/进程管理/实现/进程管理.py:356` 回
  `结果.失败("超出限制", "命令输出超过上限")` → HTTP 413。
  **报错不带"上限是多少、实际多少"**，调用方无法判断该切多小。本轮实测撞过一次 413。
- **Hermes 侧已有成熟答案，平台没接**（本轮最有价值的发现）：
  | 文件 | 机制 |
  |---|---|
  | `tools/tool_result_storage.py` | `generate_preview()` → `_write_to_spillover()` 落盘 → `_build_persisted_message()` 回「预览 + 落盘路径 + 取回方法」；`extract_persisted_path()` 后续能认；`enforce_turn_budget()` 按 turn 预算压缩 |
  | `tools/hook_output_spill.py` | `spill_if_oversized()`，`max_chars` 默认 10000，落 `<HERMES_HOME>/hook_outputs/<session>/`，回执带 `saved to <path>` |
  | `tools/spill_safety.py` | `ensure_spill_dir(private=True)` + `write_text_exclusive()` 防逃逸 |
  其回给模型的原文是：
  > *"Use the read_file tool with offset and limit to access specific sections of this output."*
- **优化方向（照搬 Hermes 的做法，这是成熟方案）**：
  1. 薄壳 `值裁剪` 增加 **`落盘` 模式**：超限时把**完整返回**写到
     `工程缓存/运行数据/薄壳回执/<时间戳>_<能力id>.json`，回执里给
     **预览 + 绝对路径 + 取回命令**（`读取文件` + `起始行/行数`）。
  2. dict 分支里对**字符串值**改为**截断**（而不是整键丢弃）—— 丢字段等于丢答案。
  3. `413` 错误说明必须带 **上限值 + 实际值 + 一条"怎么切小"的建议**。
  4. `返回上限字符` 默认值从 6000 提到"能装下一次典型门禁结论"的量级（编译口结论 ~3.3K，
     留 5 倍余量 = 30000），**一次看全**比省体量重要。

### B2 门禁报红只给一行原文，不给落点 / 修法

- **落点**：`开发工具/开发编译口/编译口.py`（`_尾部()` 与结论块）
- **现状**：门禁输出经 `_尾部()` 处理，判红时保留 `[判据名]` 开头的违规行（2026-09-21 已修
  「截断导致看不见红项」），但每条红项**仍只有一行原文**，没有：
  - `文件:行号`
  - 规则名/规则 id
  - **可复制的修复命令**
- **实测代价**：本轮修 4 条红项，每条都要"读原文 → 自己搜落点 → 自己判断怎么改"，
  平均每条 2–3 跳。若红项自带 `文件:行号`，可直接跳到落点；若自带修复命令，可能 0 跳。
- **优化方向**：红项输出对齐 **SARIF 的最小可修集** ——
  `判据名 + 级别 + 文件:行号 + 消息 + 一条 fix 命令（或 fix 提示）`。
  平台已有 `开发工具.MD文档生成` 这类"唯一入口"，修复命令天然可生成（如"跑
  `--类型 X --写盘`"），成本很低。

### C1 热接入不重载已导入模块 → 只能重启网关

- **落点**：`运维脚本/热接入.py` → `运行核心/统一网关/本地网关.py:533 _处理热接入请求()`
  → `后端核心.热接入()`；网关侧 `运行核心/统一网关/核心处理/网关执行面.py:115`
- **现状**：热接入的设计目标是**扫描新增/变更包 + 增量装配**（注册新能力），
  脚本自己的注释写着"不重启进程"、"只动变更包"、"直接重启会中断在途调用、打断句柄与租约"
  （依据 `开发文档/决策记录/0008_能力更新走热接入不重启网关.md`）。
- **已知缺陷（未完成事项 #195，本会话前序已实测）**：它报「成功包」后**旧代码仍在跑**，
  二次调用报「无待接入变更」。根因是 Python 语义：**装配 ≠ 重新导入**，
  `sys.modules` 里已存在的模块对象不会因为装配而被替换。
- **加重项**：`运行核心/依赖防火墙.py:416-424` 把 `__import__` / `importlib.import_module`
  的**非字面量调用一律拒绝**（防越层）。这意味着"运行期动态重新导入"这条路
  在本项目里是**被硬约束堵住的**。
- **优化方向（两选一）**：
  1. **热接入如实降级**：检测到变更包里含**已导入模块**时，直接返回
     「本次需重启网关（附重启命令）」，不要报"成功"。→ 消灭假绿，成本极低。
  2. **引入 graceful restart**（先摘流量 → 等在途结束 → 换新进程 → 再挂流量），
     这是业界标准做法（详见子代理 05 报告），但改动面大。

### C2 重启网关会打断在途调用

- **现状**：重启走 `开发工具/能力网关/重启网关.py`，结论写
  `工程缓存/网关重启结果.json`（因为重启会掉本次调用所在进程组）。
- **实测代价**：本轮我重启一次网关来让新能力生效，**打断了正在跑的其他会话/子代理**。
  在并行维修期这是实打实的浪费。
- **优化方向**：重启前把在途调用**排队落盘**，重启后自动续跑；或做 graceful restart（同 C1）。

  ④ `能力搜索数据.json`（行 469）
  ⑤ `Agent查询数据.json`（行 487）

  **明确不生成**：`验证场景引用.json` —— 行 506-512 写着恒返回 `None`，

### D2 派生物互锁：生成器拒写 ↔ 门禁要求机器印记

- **落点**：`开发工具/MD文档生成/说明书/合并重生成.py:644`（人工类一律不产提案、不写盘）
  × `开发工具/MD文档生成/__main__.py:214 _拒绝手写校验()`（改动集里无印记的 md 一律判红）
- **现状**：两条规则各自都对，叠在一起**成死结**：某个 md 被登记为「人工类 ⇒ 生成器不得覆盖」
  时，它一旦出现在改动集里就**必判红**，而唯一"合法加印记"的通道（生成器）又拒写。
- **本轮实测命中两处**（已修，但**机制还在**）：
  1. `模块库/项目文档/说明/使用说明.md` —— 白名单把它登记成「人工类」，
     而该条**自己的证据栏**写着"与生成器逐字相同（差 0 行人工改写）"= 本就是生成物类。改类后刷新通过。
  2. `支持库/适配层/说明/README.md` —— **不属于任何文档类型**，`--加印记` 报"找不到归属"，
     等于**没有合法纳管路径**。新增文档类型「说明目录导航」（序号 11）后解决。
- **优化方向**：**加一条自动检测** —— 扫描"白名单登记类别"与"该文件证据栏自述"是否矛盾、
  以及"改动集里的 md 是否都能匹配到某个文档类型"。这类死结应该由门禁**主动报出来**，
  而不是等人踩。

### E1 只有单层列目录，没有"树"

- **落点**：`支持库/后端/文件系统支持库/文件操作`、`模块库/文件管理` 的 `列出目录`
- **现状**：只有单层列出。要看一棵树必须 N 次往返，或退回 `find`/`ls -R`。
- **实测代价**：`find` 扫一棵树 **12.4 秒 / 9.3 秒**（同一台机器 `rg` 只要 0.07 秒，差 170+ 倍）。
  **Agent 为省事就会去敲终端 → 漂移源**（未完成事项 #208 G1 已登记）。
- **优化方向**：补一个 `目录树` 原子能力：入参 `根目录 / 最大深度 / 忽略规则 / 输出上限`，
  输出**排序后的紧凑树**（含文件数、字节数）。参考 aider 的 repo map 做法（见子代理 07）。

### E2 发现三跳：search → describe → call

- **落点**：`开发工具/薄壳/工具清单.py`（3 个工具）+ `模块库/能力目录`
- **现状**：
  - `capability_search` 的 `细节级别` 三档：`名称`（默认，只回指针 8 字段）／`名称+说明`／
    `完整契约`；`限制` 默认 10；结果多用 `游标` 翻页。
  - 设计取向是**刻意控体量**（"不要靠加大 限制 一次拿全"）。
  - 想拿到参数名与类型，得再调 `能力目录.读取能力`（`含常用参数=true`）。
- **实测代价（本轮）**：`capability_search` 90 次、`tool_describe` 21 次 —— **纯发现成本**。
- **元判据下的结论**：这套取向**与华哥的判据相反**。正确取向应是
  **"一次给全（含参数名/类型/样例）"**，用"少往返"换"单次体量"。
- **优化方向**：
  1. `capability_search` **精确命中单条时**直接回完整契约（体量小、收益大）；
  2. 或把 `细节级别` 默认从 `名称` 改成 `名称+说明+参数名`；
  3. `tool_catalog`（薄壳自身清单）与 `capability_search` 合并，少一个工具 = 少一次注入。

### F1 有账本，没有"耗时榜"

- **落点**：`工程缓存/运行数据/`（本轮实测目录）
  已存在：`调用参数账.sqlite3`、`底座运行.db`、`权威状态.db`、`网关幂等.sqlite3`、
  `开发效率巡检/`、`缺陷巡诊/`、`子代理超时归因.json`
- **现状**：执行命令经 MCP 跑，**有耗时记录**（华哥原话"有日志记录，才知道怎么加速"），
  但**没有按调用聚合的耗时榜**，也没有分位/趋势。本轮 189 条单命令超 15 秒，
  是我事后读 `开发效率巡检` 才发现。
- **优化方向**：在 `调用参数账` 上加一个只读能力 `调用耗时榜`（Top N + 分位 + 趋势），
  并把 `开发效率巡检` 的 `慢命令明细` 接到它上面 —— 现在 `开发效率巡检` 已经能出 HTML，
  缺的是**常驻可查**。

### F2 没有"一次全查"的原子口

- **落点**：`开发工具/开发编译口/编译口.py`（15 项静态门禁）
- **现状**：15 项门禁**串行**跑（本轮前实测单轮 30.4 秒）。
  平台有 `执行命令集`（并行 8 路），但编译口自己是串行的。
- **本轮已修**：14 项改为并发起跑（`门禁并行路数 = 8`），单轮 **30.4 → 12.2 秒**；
  但**这是我在 `执行命令` 里跑脚本**，不是"平台提供的原子能力"。
- **优化方向**：编译口应作为**原子能力**暴露（现在靠 `自修复工具.运行开发编译口` 兜），
  且返回要能"一次看全"（受 B1 制约，需先修 B1）。

## 三、意外发现：Hermes 侧已有的成熟机制（平台没接）

这几条是本次审计最有价值的部分 —— **问题不全在平台，答案也不全在外面**。

| Hermes 侧已有 | 平台对应缺陷 | 照搬方式 |
|---|---|---|
| `tool_result_storage.py`：超限 → 落盘 → 预览 + 路径 + `read_file(offset/limit)` 取回 | 薄壳 `值裁剪` 直接**丢字段** | 薄壳加"落盘模式"，回执给绝对路径 + 取回命令 |
| `hook_output_spill.py`：`max_chars` 默认 10000，私有目录落盘 | 同上 | 同上；落盘根用 `工程缓存/运行数据/薄壳回执/` |
| `spill_safety.py`：`private=True` + `write_text_exclusive` 防逃逸 | 薄壳落盘需同款安全 | 直接复用同一思路 |
| `validate_deferred_call_args`：required 探测 + 类型强转 + jsonschema + 结构化纠错回执 | `capability_call.参数` 是自由 `object`，兜不住 | 平台侧在 400 回执里带**正确签名 + 真实样例** |
| `local_batch_error`：回显调用方自己的 payload 帮它脱困 | 平台无批量入口 | 薄壳加 `调用列表` 批量入参（一次返回多条结果） |

## 五、按元判据的优先级（内部视角，最终排序等外部调研回来再定）

