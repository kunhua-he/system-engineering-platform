## 一、结论摘要（先给答案）

1. **字段口径有现成国际标准，且已经覆盖到「MCP 工具调用」这一粒度**：OpenTelemetry 的 GenAI/MCP 语义约定给出了 span 属性表 + 四支 histogram 指标（`mcp.client.operation.duration` 等）和一支**正对工具调用耗时的** `gen_ai.execute_tool.duration`。本项目现在只记 `耗时秒`/`耗时毫秒` 一个数，缺的是**维度**（能力id 之外的调用方/项目/错误码/返回体量/是否超时/执行形态）与**分位**。
2. **「耗时榜」的成熟形态 = 分位（p50/p95/p99）+ 按对象聚合 + 趋势**，而不是「最慢 N 条明细」。langfuse 首页直接放三张延迟分位表（traces/generations/observations），phoenix 把延迟做成**查询侧计算列** `latency_ms`，helicone 用 `response_created_at - request_created_at` 派生并单列 `time_to_first_token`。
3. **本项目不是「没有耗时榜」，而是「榜的粒度与闭环缺失」**：`运行核心/运行诊断/安全审计/安全审计.py::慢调用报告()` 已经产出「按能力聚合（条数/最慢/平均，按最慢降序）+ 最慢明细 Top N + 3 秒/10 秒分级」，从权威审计账本派生、不另存第二份。缺的是：**分位（p95/p99）、趋势对比、每次调用的返回体量与 token 成本、失败率联表、以及「改完再看榜」的闭环入口**。
4. **最小补法不新建日志**：在既有 `慢调用报告` 上加「分位 + 窗口对比 + 返回体量列」，并把 `开发工具/开发效率巡检.py` 已有的「慢命令明细 Top 20 + 快照趋势」模式平移过来做 HTML 看板。新增第二份耗时日志会直接违反项目哲学 1.2（同一件事两套实现即缺陷），且两份落不同根必然静默分叉。

## 三、硬问题 1：一次工具调用应该记哪些字段才算可分析？

按 2.1 的属性表 + 2.5/2.6 的存储实践，**最小可分析字段集**如下（标注本项目现状）：

| 字段（对齐 OTel 语义） | 用途 | 本项目现状 |
|---|---|---|
| `能力id`（≈`gen_ai.tool.name`） | 榜的主键 | ✅ 已有 |
| 起止时间 / `耗时毫秒` | 分位计算 | ✅ 已有（单点值，够算分位） |
| `成功` + `错误码`（≈`error.type`，低基数） | 失败率、失败-耗时联表 | ✅ 已有 |
| `调用方` / `项目id` / `会话id` / `请求id`（≈`mcp.session.id`、`jsonrpc.request.id`） | 分「谁在慢」、串起一次会话 | ✅ **已落盘**（`安全审计.记录()` 第 85-108 行的字段清单含 `用户id/项目id/会话id/请求id/任务id/操作id/来源地址/提供者/契约版本`，逐条写进 JSONL） |
| 执行形态（`即时纯计算`/`阻塞IO`/`长耗时`/`常驻有状态`） | 慢是形态问题还是实现问题 | ⚠️ 只挂在**失败**结果的 `详细信息.执行形态判定`（`唯一能力调用.py` 第 245-250 行注释：成功结果没有该载体） |
| 返回体字符数 / 是否被截断 | 直接对应 B1（返回体被整段丢弃） | ❌ 缺 |
| 重试次数 / 是否超时（`超时残留`） | 区分「慢」与「超时」 | ⚠️ 有超时残留记录，未进耗时榜 |
| 排队耗时 vs 执行耗时（分段） | 区分网关排队慢与能力实现慢 | ❌ 缺（只有一段 `耗时秒`） |
| token / 成本 | LLM 类能力才有意义 | ❌ 缺（本项目多数能力非 LLM，优先级低） |

**判断**：对本项目而言，**优先级最高的三个新增字段是「返回体字符数/是否截断」「分段耗时（排队/执行）」「执行形态（成功也记）」**——前两个直接服务 B1/E 系列节点，第三个让「慢」可归因。

## 四、硬问题 2：「耗时榜」在别的项目里长什么样？有没有现成看板可直接用？

**成熟形态（三家一致）**：
1. **分位而非均值**：p50 / p95 / p99（langfuse 首页三张延迟分位表；phoenix 的 `latency_ms` 可直接进 SQL 聚合与分位）。
2. **按对象分层**：langfuse 分 traces / generations / observations 三层；本项目对应「按能力id / 按调用方 / 按项目」。
3. **Top N 明细可下钻**：本项目已有（`慢调用报告` 的 `最慢明细`，`上限` 默认 20）。
4. **趋势**：`开发工具/开发效率巡检.py` 已实现「快照 + 下次跑自动对比出趋势」（第 22 行注释：`工程缓存/运行数据/开发效率巡检/<时间戳>.json`，第 472 行 `比趋势`）。
5. **阈值分级而非单一阈值**：本项目已有两级（3 秒考虑 / 10 秒必须）。

**现成看板**：**没有可直接用的**。
- langfuse / phoenix / helicone 的看板都绑死各自的数据存储与前端栈（ClickHouse / Postgres+Arrow / ClickHouse），移植成本高于自建；
- 本项目**已经有一个自研 HTML 看板先例**：`开发工具/开发效率巡检.py::写HTML()`（第 543 行起，含「慢命令明细（Top 20：久在哪一条）」第 610 行、卡片式 KPI 第 598 行）。**照它的样式再做一个「能力耗时榜」是最低成本路径**。

**结论**：可直接复用的是**结构与样式**（分位表 + Top N + 趋势 + HTML 卡片），不可直接复用的是**实现**。

## 五、硬问题 3：本项目最小补法（改哪、改多大、风险）

**现场事实（重要，与任务信口径有差异，如实报告）**：任务信说「执行命令有耗时记录但没有『调用耗时榜』」。实际现场是——**能力调用的耗时榜已经存在**：

- `运行核心/运行诊断/安全审计/安全审计.py::慢调用报告()`（第 177-258 行）：从**权威审计账本**派生，返回 `审计文件 / 读取记录数 / 阈值秒{考虑优化秒,必须优化秒} / 分级计数 / 慢调用条数 / 按能力聚合[能力id,条数,最慢毫秒,平均毫秒,必须优化条数,等级] / 最慢明细[时间,能力id,耗时毫秒,等级,成功,错误码] / 说明`；聚合按 `最慢毫秒` 降序（第 240 行），明细同序（第 247 行）。
- 阈值与裁决：分级阈值在 `安全审计.py` 第 44-45 行（华哥 2026-09-21 裁决：超 10 秒必须优化、超 3 秒考虑优化）；「超标」裁决的唯一实现在支持库能力 `数据操作支持库.度量.判定耗时超标`（默认 5 秒）——**运行核心不依赖支持库，故只分级不裁决**。
- 落盘口径：`公共契约/诊断/调用账本.py` 是**形状/表结构的唯一定义处**（写入方在 `运行核心/统一网关`，读方在 `模块库/能力目录`），并明确「另开一份『调用耗时日志』等于把同一事实记两遍、且两份落不同根 ⇒ 静默分叉」，故 `网关处理面.py` 第 96-116 行只保留**一个权威账本**。

**因此最小补法不是「新建榜」，而是补三件东西**：

| 补法 | 改哪 | 改多大 | 风险 |
|---|---|---|---|
| ① **分位**：在 `慢调用报告` 的 `按能力聚合` 项里加 `p50/p95/p99 毫秒` | `运行核心/运行诊断/安全审计/安全审计.py` 的 `慢调用报告()` | 约 +15 行（对 `条目["耗时毫秒"]` 列表排序取分位） | **低**（纯派生，只增字段；契约只增不改） |
| ② **返回体量维度**：账本增 `返回字符数` / `是否截断` 两字段 | `公共契约/诊断/调用账本.py` 表结构（唯一定义处）+ 写入方 `网关处理面.py` | 表结构加列（SQLite 需迁移或按 `幂等存储.py` 的既有模式兼容旧行） | **中**（动权威账本，需保证旧行可读、fail-soft 不变） |
| ③ **HTML 榜**：按 `开发效率巡检.py::写HTML()` 的样式输出「能力耗时榜」 | 新增一个只读入口（不改现有代码路径） | 约 80-120 行（可复用其卡片/表格渲染） | **低**（只读） |

**明确不建议做的事**（各有实证理由）：
- ❌ 新建「调用耗时日志」：`公共契约/诊断/调用账本.py` 第 3-14 行已把「另开一份」判为静默分叉源；MCP 官方也把自造日志通道判为过渡态（2.3）。
- ❌ 引入 OpenTelemetry SDK / Collector：本项目单机单进程、无多后端汇聚需求（2.8）；引 SDK 会把「出个榜」变成「接一条数据管道」。
- ❌ 把账本从「存耗时」改成 phoenix 式「存起止时间、查询侧算」：会动权威账本表结构，收益（换口径可重算）远低于风险（2.5）。
- ❌ 给单次调用定 SLO 阈值：SLO 必须落在**分布**上（2.9）；先有 histogram/分位再谈 SLO。
