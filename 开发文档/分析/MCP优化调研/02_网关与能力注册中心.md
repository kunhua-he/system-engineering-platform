## 0 结论摘要（四条硬答案）

1. **注册中心的必有字段**：MCP 官方注册表只强制 `name / description / version` 三项（`ServerDetail.required`），但**可检索、可安装、可治理**靠的是另外 6 类字段：传输方式（stdio / streamable-http / sse 三型）、包引用（registryType+identifier）、**来源仓库（source+url）**、**多版本 + latest 标记 + status**、环境变量/密钥声明（isSecret / isRequired）、图标与站点。我们当前能力目录缺的是**「来源 + 传输 + 版本轴 + 状态位」**这四类中的后三类（详见 §4）。
2. **「一次请求多能力」是网关层聚合，且聚合的产物是「一个清单端点」**：docker/mcp-gateway 把 N 个 MCP server 的 tools/prompts/resources 合成一张 `Capabilities` 表挂到单一 MCP 端点；envoy 系（现 agent-router）用 `MCPRoute.backendRefs` 聚合多后端；IBM ContextForge 用「虚拟服务器」把任意工具打包成一个 server。**没有一家是让客户端逐个 describe 的**——这与本项目元判据（往返次数×全上下文注入才是真成本）方向一致：正确解法是**一次 list 拿全 + 单端点调用**，不是把返回体改小。
3. **热更新没有一家靠「重启网关」**，主流三条路线：① 配置中心 watch（apisix 走 etcd watch，从 revision 续读）；② 文件 watch（mcpo 用 watchdog 监听配置，回调丢回事件循环重建端点）；③ **缓存失效广播 + 按上游增量替换能力表**（ContextForge 走 Redis pubsub 频道 `mcpgw:cache:invalidate`；docker/mcp-gateway 的 `reloadServerCapabilities` / `updateServerCapabilities(serverName, oldCaps, newCaps)` 是**按 server 粒度增量换**，不是整体重载）。
4. **最接近本项目的组合**（PHP/Python 本地私有部署、唯一网关、契约冻结）：
   - 字段/版本语义 → `modelcontextprotocol/registry`；
   - 能力聚合与命名冲突治理 → `docker/mcp-gateway`；
   - 「一个工具 = 一个可发现端点」→ `open-webui/mcpo`；
   - 虚拟服务器/联邦 → `IBM/mcp-context-forge`；
   - 热更新姿势 → `apache/apisix`（etcd watch）。
   **不能照抄的**：`Kong/kong` 与 `envoyproxy/gateway` 开源主仓里 `rg -i mcp` **零命中**——通用网关不内置 MCP，Kong 的 MCP 能力不在开源主仓，故二者只作「路由/限流/观测抽象」参照，不作照抄对象。

### 2.4 envoyproxy/gateway
- 全名/地址：`envoyproxy/gateway` https://github.com/envoyproxy/gateway ｜ 3040★ ｜ Go ｜ 7042 个 blob。
- 实测：对全树 `rg -i mcp` **零命中**——**通用应用网关不内置 MCP**。MCP 能力全在 2.3 那条线上。

## 3 四个硬问题的答案

### Q1 「能力注册中心」必有的字段，我们缺哪些
把 `modelcontextprotocol/registry::ServerDetail`、ContextForge `Tool` 表、consul 服务定义、apisix route 四处字段取并集，成熟生态的字段可归为 **8 类**：

| # | 字段类 | 生态实例（字段名） | 本项目现状 | 缺否 |
|---|---|---|---|---|
| 1 | 标识与命名 | `name` + `title` + 命名空间前缀（`<backend>__<tool>`） | 能力 id（`包.能力`）已有；**无对外别名/前缀治理** | 缺前缀/别名 |
| 2 | 人类说明 | `description`（required） | 说明书.md 有，但**不在目录返回体里** | 缺（发现层看不到） |
| 3 | 版本轴 | `version`（required）+ 语义版本比较 + `latest` 标记 | `能力定义.json::版本` 有，**无 latest/多版本并存** | 部分缺 |
| 4 | 生命周期状态 | `status`（registry migration 013）、ContextForge `enabled/deprecated` | 只有「存在/不存在」 | **缺** |
| 5 | 传输/调用方式 | `transport`(stdio/streamable-http/sse)、ContextForge `integration_type/request_type` | 固定 HTTP POST 40007 | 不适用（可留位） |
| 6 | 参数形状 | `input_schema`(JSON)、`Input{format,isRequired,isSecret,choices,default}` | 参数契约.json 有，**但 A2 实测「第一跳必错」** | 有源未暴露 |
| 7 | 来源与归属 | `repository{url,source}`、`gateway_id`、`team_id`、`tags` | 有包/目录归属；**无来源 URL、无标签检索** | 部分缺 |
| 8 | 度量与健康 | consul 健康位、litellm 成本/耗时、ContextForge 独立 metrics 子系统 | F1 说「有耗时记录但无调用耗时榜」 | **缺（未闭环）** |

**必缺四项**：③ latest/多版本、④ 状态位、⑦ 标签与来源、⑧ 调用耗时/健康（对外可见）。

### Q2 怎么把「一次请求多能力」做掉
**两层都有人做，但主流是网关层聚合，且产物是「清单端点」而非「批量调用口」**：
- 网关层聚合：`docker/mcp-gateway` 的 `Capabilities`（N server → 一张工具表 → 单 MCP 端点）；`theagentrouter/agent-router` 的 `MCPRoute.backendRefs`（N 后端 → 一路由）；`IBM/mcp-context-forge` 的虚拟服务器（N 工具 → 一个 server）。
- 客户端层聚合：`TBXark/mcp-proxy`（一个配置文件挂 N server）。
- **没有一家提供「一次 RPC 调 N 个能力」**；它们提供的是**一次 `tools/list` 拿全清单 + 单端点 `tools/call`**。对我们的元判据而言，这恰恰是正解：把 E2 的三跳（search→describe→call）压成**一跳清单 + 一跳调用**，而不是把返回体截断。
- 附带发现：ContextForge 的 **TOON compression** 与 litellm 的 fallback/cooldown 说明——**「省 token」与「减往返」是两个正交手段，成熟项目两个都做，但从不以牺牲往返换体积**。

### Q3 怎么解决「改了实现要重启」
四条可抄的路线（按照搬代价从低到高）：
1. **文件 watch**（mcpo）：`watchdog` 监听配置，事件回调丢回 asyncio 主循环重建端点；有 `test_hot_reload.py` 做回归。→ 最轻，适配本地单机。
2. **缓存失效广播**（ContextForge）：`redis.publish("mcpgw:cache:invalidate", ...)` + 订阅端 `CacheInvalidationSubscriber`，且支持**按上游粒度失效**（`invalidate_gateway(gateway_id)`）。
3. **能力表增量替换**（docker/mcp-gateway）：`reloadServerCapabilities` / `updateServerCapabilities(serverName, oldCaps, newCaps, toolFilter)`——**按来源粒度换表，不动进程**。
4. **配置中心 watch**（apisix / consul）：etcd watch 从 `rev` 续读、consul blocking query（WaitIndex）。→ 最重，但语义最完整。

对本项目 C1/C2 的直译：**「热接入不重载已导入模块」的病根是进程内 `sys.modules` 缓存**——生态里没有任何一家把「重启网关」当热更新手段；最小改法是给能力实现加一层**按能力 id 的模块缓存失效**（等价 mcpo 的文件 watch + 显式 reload 钩子），而不是重启 40007（重启还会掉调用所在进程组，正是 C2）。

### Q4 哪一套最接近本项目
| 我们的特征 | 最贴近的项目 | 理由（源码级） |
|---|---|---|
| PHP/Python 本地私有部署、单机 | `open-webui/mcpo`（327KB，纯 Python，文件 watch 热更新） | 无外部依赖即可跑通「MCP→可发现端点」 |
| 唯一网关 + 能力目录 | `docker/mcp-gateway` | `Capabilities` + 命名冲突治理 + 增量重载，形态与我们最像 |
| 契约冻结、生成物单一事实源 | `modelcontextprotocol/registry` | schema 由 openapi.yaml `make generate-schema` 生成；版本规则显式 |
| 虚拟服务器/一次拿全 | `IBM/mcp-context-forge` | `associated_tools` 打包 + Redis 失效广播 + TOON |
| 统一错误码 | `BerriAI/litellm` | 异常类即状态码，继承表达细分 |
| 不适用 | `Kong/kong`、`envoyproxy/gateway` | 开源主仓 `rg -i mcp` 零命中，MCP 不在其中 |

**结论：没有一个项目能整体照抄；最优组合是「registry 的字段与版本语义 + docker/mcp-gateway 的聚合与命名治理 + mcpo 的热更新与清单端点 + litellm 的错误码表」。**

## 5 照搬落地代价（改哪 / 改多大 / 风险）

**低代价（建议优先，纯设计/字段，不动运行核）**
1. **目录返回体内联参数契约**（对应 A2/E2）：改能力目录/能力详情返回体，把 `参数契约.json` 的参数名、类型、必填、字段形状内联。风险：返回体变大 → 与 B1 的截断规则冲突，须先统一截断口径（**这是唯一需要同时动两处的地方**）。
2. **门禁消息模板**（B2）：只改文案生成，参考 docker 的 `...; enable tool-name-prefix or set a unique catalog prefix`。
3. **错误码表**（B2/F2）：照 litellm 的做法「类即码 + 继承表达细分」；我们已有 `公开错误码状态映射`，只需补细分。
4. **标签/来源/状态位字段**（Q1 的 ④⑦）：在能力定义加 `状态`（启用/弃用/草稿）、`标签`、`来源` 三键，走契约编译派生。

**中代价（需动缓存/注册层）**
5. **按能力 id 的模块缓存失效**（C1/C2）：参照 mcpo 的 `_trigger_reload` + ContextForge 的 `invalidate(name)`；风险是**并发会话**下换模块要保证旧调用不被掐断（对应 C2 的进程组问题）——建议「新调用走新模块、在途调用持旧引用」。
6. **一次全量清单/树视图**（E1）：参照 mcpo `/openapi.json` 与 docker `Capabilities`；风险是清单随能力数线性增长，需要分页（registry 用 `cursor+limit`）。

**高代价（不建议本轮做）**
7. **配置中心 watch 化**（apisix/consul 路线）：要引入 etcd/consul 或自建长轮询，与「本地私有部署、唯一网关」的轻量定位冲突。**只在「文件 watch」不满足时再考虑。**
