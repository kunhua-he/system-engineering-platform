### 2.1 【P0】契约默认值与实现默认值不一致（静默，已实测）

**现象**：`开工编排.开工准备` 的 `细节级别` 参数，**声明默认「完整」，实际默认「摘要」**。

**四处声明 / 一处实现，逐字对照**：

| 位置 | 写的是什么 |
|---|---|
| `模块库/开工编排/能力契约/参数契约.json:55` | `"默认值": "完整"` |
| `模块库/开工编排/能力定义.json:58` | `"默认值": "完整"` |
| `模块库/开工编排/__init__.py:31` | `"默认值": "完整"` |
| `模块库/开工编排/实现/开工编排.py:350`（docstring） | 「**默认档是 `完整`**，与改前返回逐字段一致」 |
| `模块库/开工编排/实现/返回体量分档.py:39`（实现） | `默认细节级别 = "摘要"` |

**现场实证**（经网关真实调用，2026-09-23）：

```
不传 细节级别        → 6,143 字符（= 摘要档，逐字段等于摘要）
传 细节级别=摘要      → 6,143 字符
传 细节级别=索引      → 6,084 字符
传 细节级别=完整      → 21,011 字符
```

取证命令：

```bash

```

**影响**：
- 调用方照契约（默认「完整」）规划上下文预算，实际拿到的是摘要档 —— **静默的档位降级**。按哲学 5.3，**改默认值属「破坏档」契约面变化，必须递增版本**；本条既没同步契约、也没见版本递增。
**★ 2026-09-23 更正（我原写「门禁看不见它」，现场核实后改口）**：门禁**看得见**实现侧默认值 ——
`开发工具/契约编译/口径比对.py:225 检测实现默认值差异` 早就存在，注释逐字写着「**只报不计分不判红**」，
由 `漂移检测.py:307` 输出为「实现默认值差异 **265 条**（契约null 102／其中实现空串 98）」。
所以本条不一致**本来就在那 265 条只报项里**，不是「没人看得见」。

**准确表述**：不是**覆盖面缺口**，而是**「只报不判红」的设计选择**。
本次发布门禁自报的「默认值硬不一致 **0**」指的是另一条更窄的判据（**契约 ↔ 注册表**，
两处同源于 `能力定义.json`，自然一致）；实现侧那条走的是 `实现默认值差异` 这个**只报**桶。
**要把它升为判红属裁决**：265 条里 102 条是「契约 null」、其中 98 条是「实现空串」，
直接判红会造一批红风暴（本仓已多次栽在「判据太宽＝假红、太窄＝形同没接」上）。

**这条更正的教训**：结论要落到**判据实现**上读一遍再说，不能只看「门禁输出里没这一项」
就推断「没有这条判据」—— 我原判正是这么来的。

**证据等级**：**已证实**（源码直读 + 网关实测 + 门禁输出三重）。

**建议方向**（不在本轮做）：默认档应当**由契约派生**（单一事实源），实现不得自带一份默认值；并给门禁补一条「契约声明的默认值 ↔ 实现实际默认值」一致性判据，否则同类分歧会再犯。

### 2.3 【P1】三档区分度失效：索引档并不比摘要档省

**现象**：文档与契约都写「索引 < 摘要 < 完整」，实测**索引档与摘要档几乎等量**。

| 档位 | 实测字符数（2026-09-23） | 最大块 |
|---|---|---|
| 索引 | **6,084** | 通用纪律 1,604 / 工作区快照 1,186 / 缺失原子能力 786 |
| 摘要（= 默认） | **6,143** | 最近成功验证 1,489 / 通用纪律 1,456 / 缺失原子能力 786 |
| 完整 | **21,011** | **通用纪律 12,042** / 工作区快照 2,589 / 开发流程 1,957 |

**两点结论**：

1. **索引与摘要只差 59 字符（1%）** —— 档位名义上有三档，实际只有「约 6.1k」与「21k」两档。索引档没有兑现「比摘要更省」的语义。
2. **两个非完整档都原样返回了几块未收窄的内容**：`缺失原子能力` 786 字符（两档同值）、`开发流程提示`、`通用纪律提示`、`下一步`。这几块**不随档位变化**，属无条件返回，正是「不需要的也一起给」的典型。
3. **完整档 `通用纪律` 单块 12,042 字符**，是「单块 ≤2000 字符」预算的 **6 倍**。完整档被定义为「改前行为」而保留，但它在契约里是**默认值**（§2.1）—— 一个调用方什么都不传，理论上该拿到 21k。

**证据等级**：**已证实**（网关实测）。**注**：此处中途出过一次口径错误（用字节数比较），已按字符复测纠正，见 §零。

### 2.4 【P1】「先构造全量、再后置投影」：省的是发送量，不是成本

**现象**：分档投影是**最后一步**，前面所有读取与组装照旧全量做。

**证据**：

- `模块库/开工编排/实现/开工编排.py:522` —— 无条件 `_取通用纪律(项目根)`，把整份纪律字典读出来（该函数每次都 `_读字典` 重新解析整份 JSON）。
- `模块库/开工编排/实现/开工编排.py:749` —— `return 结果.成功结果(投影开工上下文(_完整上下文, 档位))`，**先有 `_完整上下文`，才有投影**。
- `模块库/开工编排/实现/返回体量分档.py:15-25` 的模块 docstring 也自述：默认档的收窄是「给体积 + 展开指针」的**投影**行为。

**影响**：
- 对 Agent 的上下文成本而言，投影确实省了 token（这是真的收益，不该抹掉）。
- 但对**底座自身**，读盘、解析、组装、跨能力调用（代码地图、租约、证据账本）**一样不少跑**，只为了最后丢掉大部分。这解释了为什么「注入面收窄」做了三轮，`开工准备` 的**默认档仍要 ~6.1k 字符**：收的是末端，不是源头。
- 更根本的一层：`通用纪律` 是**无条件返回**设计（2026-09-18 为防派活方手写漏注入而定，`能力定义.json:82` 逐字写着「**无条件返回**」）。它和「越精准越好、不需要的不要」是**结构性冲突** —— 不能简单砍（砍了会退回「派活方漏注入」那个已修复的缺陷），只能改**交送方式**。

**建议方向**（不在本轮做）：把「无条件返回」改成「**按任务类型命中 + 按需展开**」—— 通用纪律只回与本次任务类型相关的段落指针，正文走已有的 `项目文档支持库.查哲学条款` / 明细查询按需取。这样既保住「不漏注入」，又不再无条件灌全量。

**证据等级**：**已证实**（源码直读 + 体量实测）。
