## 八、统一编译口：易语言模式落地方案（2026-09-19 华哥定调「一个编译、规则全查、秒级反馈」）

### 8.1 需求原话与翻译

华哥原话要点：修改一个文件后要改很多文件；想要统一编译器，改完直接走它验证；测试很多很好但开发时想要**基于规则的快速判定**（易语言式），而不是跑大量测试；现在开发经常「这里弄好那边爆」；开发一个小模块/新支持库时间金钱双重消耗。目标：**高速开发、高速维护、高效可控、兼容易用、规则强制率拉满**。

翻译成架构语言：要的是一个**开发循环的统一编译口**——一条命令完成「生成物联动 + 静态规则全查 + 影响面预告 + 定向测试点名」，秒级出五态结论；测试与 HTML 黑盒退到收口/发布两道门。

### 8.2 计时取证：慢的不是检查，是「没有那一个按钮」

2026-09-19 实测（`/usr/bin/time`，同机串行）：

| 静态门禁 | 耗时 | 结果 |
|---|---|---|
| `能力id冻结基线门禁` | 0.15 秒 | 通过 |
| `验证场景体检` | 0.42 秒 | 全部通过 |
| `契约编译.漂移检测 --报告` | 0.53 秒 | 存量债冻结态（漏声明 126 / 默认值差异 157，登记在案） |
| `全量重算摘要 --只报` | 0.72 秒 | 全部闭合 |
| `公开调用完整性门禁` | 1.69 秒 | 通过 |
| `环境自检` | 约 2.4 秒 | 全过 |

对照：unittest 单模块实测 0.05 秒起（本身也不慢）；真正烧时间烧钱的是 **agent 在 40+ 个工具入口里探索「该跑什么」+ 自由发挥跑测试/黑盒** 的会话时间。结论：易语言模式在速度上零障碍，纯编排工程。

### 8.3 为什么 agent 一直理解不了（根因，不是态度问题）

- agent 的训练先验是「验证 = 跑测试」，unittest 是所有代码 agent 的默认反射；「编译即验证」不在它的第一反应里。
- AGENTS.md 给 agent 的开发期示例恰好就是 unittest 模块入口，没有规定「第一动作」；开发工具/ 下 40+ 入口，agent 每次都要重新探索。
- 解法靠机制不靠解释：① 唯一入口一条命令；② 写进 AGENTS.md「改完必做」第一行；③ `开发工具/任务记忆/派活任务信.py` 生成任务信时自动携带该命令（实测巡检已证明手抄纪律必漏）；④ 用 `开发效率巡检.py` 量化验证 agent 是否真的在用。

### 8.4 方案：开发编译口（一条命令，五阶段）

现状盘点（★ 证真后修正）：`快速编译`（契约+原则静态检查）自带独立 CLI（`--包目录/--文件/--执行样例/--执行外部`），初稿「已降为项目编译器内部阶段且不可独立调用」的字面不成立——那是传了不存在的 `--帮助` 参数换来的防误用提示，被误读；另有 `快速编译/单文件自查.py`（`--改过` 读 git 已改文件）已覆盖「按变更集入径」的雏形；`统一验证器` 是结构/契约/资产/装配/加载器/示例项目/项目适配六范围的静态+样板验证器，与编译口步骤3 存在范围重叠。**经证真收窄后的「空位」结论：五阶段编排口（影响面 + 生成物自动联动 + 全查 + 自动修 + 定向测试点名）确实不存在**——方案是新建 `开发工具/开发编译口/`，复用全部现成检查器，只做编排，不造第二套事实源：

```bash
python3.14 -m 开发工具.开发编译口.编译口 --变更    # 落地形态：读 git 变更集（并行期用 --文件 显式点名；--全仓 全仓口径；--联动 允许重算生成物；默认只读）
python3.14 -m 开发工具.开发编译口.编译口 --自证    # 三拍自证（绿/红/恢复）
```

（★ 证真注记：① `--包` / `--新建包` 为方案参数、第一版未实现，见 8.6/8.7；② 第一版门禁清单 = 8.2 表 5 项 + 变更 .py 语法编译，环境自检/包体检/门面核验/测试体系门禁/生成物一致性检查尚未纳入；③ 8.2 表计时时点各门禁相互独立，报告数字为实测当时值，波动 ±50% 内不影响「秒级」结论。）

五阶段（目标全程 30 秒内）：

- 步骤1 变更集与影响面（秒级）：git 变更 → 包/文件映射（复用 `项目编译/正式包索引.py` 与 `工作区指纹.py`），依赖反向闭包输出**影响面清单**（会牵连的包/能力/场景/文档）——「这里弄好那边爆」变成动手前列出来。闭包算法直接复用 `项目编译器.计算影响闭包` 的现成实现。
- 步骤2 生成物自动联动（不靠人记得）：直接执行 `全量重算摘要`（0.72 秒，含聚合父包级联）、说明书生成行刷新、能力id基线增量导出（人工只审 diff）。把 OK 判据③「手工联动 10+ 份 json」收编为编译口内部动作。
- 步骤3 静态规则全查（合计约 6 秒）：8.2 表全部检查器 + `包体检` / `门面核验` / `测试体系门禁`（静态部分）/ `生成物一致性检查`，统一红项格式：**文件 + 行号 + 规则id + 修法**（能自动修的标「可自动修」）。
- 步骤4 自动修复（带反向验证）：摘要不闭合、说明书载位、基线增量这类机械红项当场修，修完自动复跑确认转绿——易语言的编译器不帮你改代码，但生成物联动这类「爆点」本就该机器做。
- 步骤5 定向测试点名（默认不跑，`--测试` 才跑）：按变更闭包列出受影响 unittest 模块清单，交给执行者；HTML 黑盒仍只在发布时跑一次（维持现有验证分级）。

结论输出：**门禁五态**（干净通过 / 债务冻结 / 只报告 / 未核验 / 失败，哲学第 13 条），退出码唯一判定；红项里区分「本次变更引入」与「存量冻结」（对照存量基线，如漂移检测的 126 条），杜绝「带着存量也报成功」的含糊。

### 8.5 规则强制率拉满的机制（回应「设计哲学拉到最高」）

- **规则三分法**：静态可判 → 进编译口；运行时可判 → 进验证场景（HTML 黑盒）；真人工 → 显式登记「强制者 + 时机 + 证据」（OK 判据①原文允许人工强制，但必须写明）。

### 9.2 假绿/假红规避（检查器自身的可信度工程）

静态检查最大的风险是「检查器自己错了没人知道」。按假绿/假红的真实来源逐一设防：

假绿四源与对策：

- **规则1 判据遗漏**（没覆盖某类缺陷）→ **变异样本常态化**：每条判据登记时必须附「最小坏样本」（故意弄坏的最小文件/JSON/代码片段）；`编译口 --自证` 后续扩展为跑全部变异样本，任何一个坏样本没被变红 = 该判据假绿，编译口立即红。三拍从「一次性验收动作」升级为「常备弹药库」。先例：`开发工具/验证_能力id冻结基线反向验证.py`。
- **规则2 解析失败静默跳过**（#72 实证：AST 求值不出 → 整块静默放行）→ **fail-closed 原则**：解析不出来的一律记「未核验」，未核验数 > 0 就不许「干净通过」。（★ 证真修正 + 2026-09-19 夜间已修完：初稿称「编译口第一版已按此实现」——产物验收路证伪，只报告类门禁的超时/崩溃/新增判红在第一版被整类吞掉仍打「干净通过」，属 P1 假绿通道；**该 P1 与 11.4 全表已于 2026-09-19 夜间全部修完并做双向反向验证**，本句现成立，实现与表述一致。）
- **规则3 宽 except 吞错**（内部故障伪装成检出成功）→ 检查器自身也要过编译口（py_compile + 裸 except 扫描）；检查器崩溃 = 未核验，禁止 except 后返回「通过」。
- **规则4 存量基线越养越宽** → 红项强制分两桶：「本次变更引入」（永远阻断）与「存量冻结」（以登记基线为准，基线单向收缩只减不增）。`公开调用完整性门禁` 已是此口径（「无新增违规」）。
