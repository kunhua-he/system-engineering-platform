## 二、三层做法拆解（视频主线）

```text
第 1 层 自动发现      服务端广播「我是 AI 节点 / 地址 / 支持什么 / 怎么调」
                     技术底座：mDNS + DNS-SD；声明格式：LocalAI
                     客户端：DSH（DeepSeek Harness）上的发现插件，每几秒扫一次并提示切换
                     ⇒ 用户不再手填 Base URL / API Key / 模型名 / 接口格式

第 2 层 隐私路由      只回答一个问题：这个请求能不能离开本地
                     ① 正则规则查已知格式（API Key、私钥片段、手机号）→ 命中即留本地
                     ② 本地分类模型结合语义与上下文判断（含多轮指代：「有啥能优化的」也知道在说私有仓库）
                     ③ ★ 不只查最新一句：Harness 请求里还有系统提示词、工具定义、工具结果、整段历史
                        ⇒ 命中即「重新构建一份新请求」，只带明确批准的 Public 信息，打标签的对话/工具调用全部剔除

第 3 层 任务分配      按任务特点选模型：能本地的本地，本地干不动的公开任务上云
                     算力池：NVIDIA PAIR（Personal AI Router）把局域网内多台设备组织成池，统一入口分发
                     云端请教模式：PurpleX 本地编排 + Privacy Gate 局部打码（只把筛选后的上下文给云端，云端只回文字建议）
```

### 4.2 逐条对照

### 4.3 实测证据（本节全部现场跑过）

**证据 1｜底座已能接管本机在跑的端点**（A/B 两种部署形态都通）：

```bash
curl -s -X POST http://127.0.0.1:40007/网关/调用 \
  -H 'Content-Type: application/json' -H "Authorization: Bearer <网关凭证>" \
  -d '{"操作":"调用能力","能力id":"大语言模型支持库.模型连接器.连接LLM",
       "参数":{"模型":"qwen2.5-14b:latest","部署形态":"本地",
               "url":"http://127.0.0.1:11434/v1","协议":"chat_completions"}}'
```

实测返回：`成功=True`，`句柄=532602`，`模型=qwen2.5-14b:latest`；随后真实推理返回
`回复='明白了，如果你有任何问题或需要帮助的地方，请随时告诉我！…'`，
`用量={"prompt_tokens":24,"completion_tokens":21,"total_tokens":45}`；
`释放句柄=True`，且 ollama 自身仍在跑（**底座没有留下孤儿进程**）。

**证据 2｜反向验证（防假绿）**：故意传不存在的句柄 `999999`，返回
`成功=False`、`错误码=句柄失效`、`句柄不存在: 999999` —— 校验真的在起作用，不是空转。

**证据 3｜本机当前真实在跑的推理端点（底座得靠调用方手填 url）**：

```bash
for p in 8000 8016 30001 11434 8050; do
  printf "%s -> %s\n" "$p" "$(curl -s -m 3 -o /dev/null -w '%{http_code}' http://127.0.0.1:$p/v1/models)"
done
```

实测：`8000`→200（Qwen3-Embedding-8B）、`8016`→200（Qwen3VL-8B）、`30001`→200（bge-reranker-v2-m3）、
`11434`→200（ollama 多模型）；`8050`→000（未启动）。
⇒ **四个端点同时在跑，而底座能力目录里搜「端点池 / 已运行」= 0 条**，只能人工填 url。

**证据 4｜自动发现可以零第三方依赖（纯标准库实测）**——这是 P0 可行性的关键：

```bash
/opt/homebrew/bin/python3.14 测mdns标准库.py   # socket + 组播 224.0.0.251:5353 手搓 DNS 报文
```
（该脚本为一次性实测探针，已按哲学 1.6「临时脚本不留库」移出仓库——历史见 Git 提交；
下列实测数字是现场跑出的原始结论，仍然有效）

实测结果：

| 探测的服务类型 | 结果 |
|---|---|
| `_services._dns-sd._udp.local` | ✅ 有应答（918 字节） |
| `_http._tcp.local` | ✅ 有应答 |
| `_ipp._tcp.local` | ✅ 有应答，**真解析出局域网内的 HP LaserJet Pro MFP M126nw**（含 mac 地址、型号标签） |
| `_ollama._tcp.local` | ❌ 无应答（该服务类型无人广播，属正常） |
| `_localai._tcp.local` | ❌ 无应答（同上） |

⇒ 结论：**「发现」这件事符合底座「只允许标准库」铁律**，不需要为它引入第三方，
也不需要走适配层提供者。局域网里真的能发现设备（正好复刻了视频里「打印机」那个比喻）。
反过来，也说明视频里那套「AI 节点自动发现」**目前没有通用约定**——`_ollama` / `_localai`
都没人广播，所以任何自建发现机制都得先自己定声明格式。

## 五、建议落地（按「是不是真缺、符不符合定位、成本多少」排序）

### P0 · 本机推理端点自动发现与接管（建议做）

- **是什么**：一条原子能力——扫本机在监听的推理端口 + 探测 `/v1/models`，返回「可用端点清单」（服务类型、端口、模型名、是否可用）。
- **解决什么**：现在本机同时跑着 4 个推理端点，底座却要调用方手填 url；有了它，`连接LLM` 可以直接吃「发现结果」，用户不再背端口。
- **为什么符合定位**：**单机内**（本机能力总线正是「整台机器只部署一套」），不涉及跨机、不涉及隐私判断。
- **零依赖**：证据 4 已证标准库 `socket` 足够。
- **落点**：`支持库/后端/大语言模型支持库/模型连接器/`（与 `连接LLM` 同域，原子能力）。
- **注意**：只做「发现 + 探活」，**不做自动切换**（切换是策略，见 P1 与哲学第 9 条边界）。

### P1 · 模型端点选型（可做，需先确认需求）

- **是什么**：输入「候选端点清单 + 约束（如上下文长度、是否需视觉、并发上限）」，返回选中的端点。
- **边界（关键）**：只做**中立的技术匹配**，**不内嵌任何隐私/合规判断**——「这个请求能不能出本机」按哲学 9.3 归业务端。
- **为什么是真缺口**：搜索「选择模型 / 切换 / 难度」均为 0 条，而视频第 3 层讲的正是这件事。
- **前置**：按铁律，新能力须先有确认需求、能力搜索、复用决策、验收契约、装配计划——**待华哥确认后再开工**。

### P2 · 只记录不落地（说明理由，防后人重复评估）

| 项 | 不做的理由 |
|---|---|
| 跨机算力池 / 多机分发（PAIR 式） | `开发文档/项目说明.md` 明文「多实例、分布式不在范围内」。真要做＝先改定位（那是华哥裁决级的事），不是顺手加能力 |
| 隐私路由 / 敏感分类 / 上下文打码 | 违背哲学第 9 条「0 业务假设」与 9.3「隐私是业务端的事」。**若将来要用，落在 V3**（业务端在调用前脱敏、结果后加安全层），底座最多提供中立原子件（如「按标签过滤消息列表」），判断权不下沉 |
| 直接用 NVIDIA PAIR | 本机 `Apple M3 Ultra`，PAIR 门槛为 **M4 及更新**（实测芯片见下） |

## 六、本机与视频场景的差异（避免照搬）

```bash
system_profiler SPHardwareDataType | grep -E "Chip|Memory|Model Name"
```

实测：`Apple M3 Ultra` / `96 GB` / `Mac Studio`。

| 维度 | 视频（林亦LYi） | 本机（华哥） |
|---|---|---|
| 硬件 | 2× DGX Spark（GB10，各 1 PFLOP / 128GB 统一内存） | Mac Studio M3 Ultra / 96GB |
| PAIR 支持 | DGX Spark ✅ | **M3 Ultra 不在 M4+ 门槛内 ❌** |
| 场景诉求 | 跨机分摊多 agent 排队 | 单机，本机已能跑 27B–35B 级模型 |
| 收益来源 | 3 台机器并行 5 subagent（18 分 → 8 分 48 秒） | 单机，**跨机收益不成立** |

⇒ 视频的「算力池」收益建立在**多台机器并行**上；单机照搬没有收益。
**真正对本机有价值的是前两层里的「发现」与「接管的顺滑度」**，这也是底座当前唯一实在的缺口。
