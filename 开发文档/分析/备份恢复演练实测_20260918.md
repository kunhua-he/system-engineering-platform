## 二、演练设计（全程只碰副本，绝不动生产）

流程 = 受管临时目录内建**源副本** → 经唯一能力调用入口**备份** → **校验** → **恢复到另一副本**
→ **四类数据逐类核对** → 报实测 RPO/RTO。

- **源副本**：生产数据根经只读 `VACUUM INTO` 一致性快照（不复用 `copy2`，避免撕裂快照）+ 四类数据真实复制。
  生产缺失的类按需补**真实文件夹具**（不是造假数据），并在 `逐类来源` 里逐类标注「生产副本／演练夹具／演练自建」——
  不标注等于把夹具伪装成生产数据。
- **只走公开能力**：`开发工具` 层不允许 import `平台控制面`（`运行核心/依赖防火墙.py:允许依赖表`），
  故一律按能力 id 经后端核心调用（实测：`审计依赖` 对本工具 **违规 0**）。
- **核对判据（强度下限）**：权威状态**逐表行数 + 全行取值指纹**；证据账本**逐条关键字段**；
  包仓库**逐文件 sha256**；项目锁**关键字段**。**空集不判绿**（无可核对 = 判不出 ≠ 通过，
  否则「什么都没恢复」会被算成「核对一致」）。
  反向验证了判据强度：**行数全部相同、只改一个字段**（`元信息.值`）→ 核对仍报红
  （`表 元信息 全行指纹不符（行数同为 1）`），证明报红来自指纹而非行数。
- **RPO 口径**：= 恢复时刻 − 备份恢复点（即「能恢复到最近多久前的状态」）。恢复点由清单写入，是**秒级字符串**，
  故解析度只有 1 秒——已在输出里显式标注 `恢复点解析度秒=1`，不把秒级数字包装成毫秒精度。
  **数据损失量**另由「源/恢复副本逐表全行指纹一致 + 演练写入那条证据逐字段存在」实测：两条一起看才是完整的「丢了多少」。

## 五、发现的缺口（本次实测新发现，均已处置或登记）

### 缺口 1（真缺陷，已修）：恢复到「已存在的目标目录」必假红

**现象**：同一目标目录恢复**第 1 次通过、第 2 次起必然失败**，`权威状态` 报
`sqlite 打开或检查失败: database is locked`。
**根因**：`恢复执行.恢复` 用 `BEGIN EXCLUSIVE` 独占目标库，**在持锁期间**就对目标目录跑
`校验权威状态`（以 `mode=ro` 再开同一个文件）——被自己的写锁挡住。目标库不存在时不加锁，
所以首次恢复能过，于是这条路径长期藏着一个「重试/覆盖恢复必失败」的假红。
**影响**：任何「恢复失败后重试」或「覆盖式恢复」的运维动作都会拿到错误的失败结论
（调用方看得到「恢复失败」，但库其实已经恢复好了）。
**修法**：`平台控制面/备份恢复/恢复执行.py` 把权威状态校验**延后到独占锁释放之后**执行
（只延迟校验，校验不写盘、不受锁保护；恢复顺序与 `结果` 列表顺序都不变）。
**验证**：同一目标目录连续恢复 3 次，实测 3/3 全部 `成功=True` / `完整性检查通过`（修前 1/3）。
回归：`测试中心.平台控制面.测试_工作包09_备份契约` 7/7 通过、`测试_工作包10_恢复编排器` 8/8 通过。

### 缺口 2（治理缺口，登记）：生产数据根四类数据缺两类，备份**恒校验不通过**

生产数据根（`工程缓存/运行数据`）实测缺 `制品/` 与 `项目锁.json`，且 `证据账本` 为空（空账本一律判失败）。
⇒ **直接备份生产数据根，`校验备份` 永远通过=False**。而「空集/缺失判失败」这条判据本身是对的
（不能把「什么都没备份到」认成「备份有效」），所以这不是判据的 bug，是**归属/口径问题**：
`包仓库` 与 `项目锁` 的真实宿主不在 `运行数据` 下（制品实际在 `工程缓存/制品仓库`），
而备份契约把 `存储根目录` 当成四类数据的同一个根。
本演练已用「真实文件夹具 + 逐类来源标注」把演练跑通，但**生产级备份要成立，须先裁定
`包仓库`/`项目锁` 的权威落点**（是改契约的根口径，还是让生产把这两类落到 `运行数据` 下）——属对外契约面变更，本批不动。

### 缺口 3（覆盖缺口，登记）：演练没有定期跑

本入口是**手动一键**。B7 原话是「一键演练**并定期跑**」，定期化（cron/发布门禁接线）本批未做——
接线点属 `开发工具/发布门禁/`（明令不许改）。建议后续：① 加入发布前必跑清单；② 或挂定期任务。
