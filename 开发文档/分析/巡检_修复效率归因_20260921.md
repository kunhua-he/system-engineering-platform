## 二、根因（5 条，按代价排序）

1. **改一个能力要同步 N 个派生物（结构性成本，最大头）**
   平台编译器只自动生成 6 份（能力契约 / `__init__` / 能力搜索数据 / Agent 查询数据 / 完整性摘要 / 参数契约），
   而**说明书两份、验证场景、权限契约、能力定义的手工段**仍需逐份手改；漏一份即被 `包体检`/`验证场景体检`/`公开调用完整性` 判红。
   实测：#156 改 4 个键 → 动 9 个文件；#196 ④ 新增 4 个能力 → 补 4 条权限声明 + 2 个正向场景步骤 + 修正非法断言字段。

2. **189 条单命令超 15 秒（按华哥口径「这不是慢，是 bug」）**
   大头是「跑 py 工具」：编译口单轮 **39.3 秒**（其中 `md查重` 14.09 秒、`测试伪装门禁` 1.78 秒）、
   全量重算摘要 ~1 秒、验证场景体检 ~0.5 秒、包体检 ~0.15 秒。
   这些调用**串在子代理的主链路上**，每跑一轮就吃掉十几到几十秒。

3. **sleep 等后台 15 次（纯 bug）**
   实测最贵形态 `sleep 420` / `sleep 400`，**单条烧光整路子代理预算**；本轮另有 4 路撞 2400 秒硬超时。

4. **派活纪律 100% 未送达（34/34）**
   本轮 12 批全部由主会话**手写 context**，没经 `开发工具/任务记忆/派活任务信.py` →
   子代理缺「工具姿势 / 提交纪律 / pathspec / 命令环境」四条固定条款 →
   重复踩已登记过的坑（猜参数名、拿 terminal 敲 git、提交不带 pathspec），额外往返。

5. **能力发现开销（`capability_search` 90 + `tool_describe` 21 + 读契约）**
   「先搜能力 → 读契约 → 猜参数名 → 报参数不合法 → 再读」这条链在本轮反复出现（#196 ⑥⑨ 两例均因此误判为缺陷）。

## 三、必须指出的指标失真（否则无法度量改进）

`开发效率巡检` 的四类分类判据（`开发工具/开发效率巡检.py:100-110`）是**关键词匹配 CLI 文本**：

```python
if <修改词>: 修改 += 1
elif <验证词>: 验证 += 1      # 验证词 = py_compile / pytest / unittest / 反向 / 验证 / assert / curl
elif <探索词> or 名 == "read_file": 探索 += 1   # 探索词 = grep / read_file / search_files / git show / cat / head / tail / sed
else: 其他 += 1
```

**本轮 82% 的调用是 `capability_call`**，其请求文本形如 `{'能力id': '文件系统支持库.文件操作.读取文件', '参数': {...}}` ——
**不含上述任何 CLI 关键词** ⇒ 读文件、搜代码、跑验证、改文件**统统落进「其他」**。

⇒ **「其他 71.7%」不是「无效时间」，而是「经 MCP 能力做的一切事」**；
但四类占比指标在「全 MCP 化」之后**已经失去分辨力**（探索/修改/验证被系统性低估）。
**改进前提**：分类器改为**按 `能力id` 判定类别**（读/搜/列 → 探索；写入/精确替换 → 修改；执行命令带验证词、测试类 → 验证），
否则「探索占比 ≥50% 判红」这类阈值全部失去意义。

## 五、一句话结论

**效率不正常，但瓶颈不在「改代码」，而在「改完之后要同步的一圈派生物 + 慢工具串在主链路上 + 派活纪律没送达」。**
改代码本身只占 1.3%；把 2/3/5/6 四项做完，「知道问题 → 修完验收」的典型耗时可从 ~18 分钟压到 ~5 分钟量级。
