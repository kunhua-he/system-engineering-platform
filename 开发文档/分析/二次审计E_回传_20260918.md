### P1-5 已修：池锁内不再做 join / fsync
- 两段式拆分：`_轮询任务` = `_判定轮询`（锁内，零阻塞 I/O：读快照 + 单读者收取 + 定终态意图）+ `_收敛任务`（**锁内**占「回收者」权并登记待发布终态 → **锁外** 取消事件/TERM→KILL/join → **锁内**条件回写终态或记「资源未收敛」）。
- 资产完整保留：`poll`/`recv_bytes` 与 `结果已收取` 的**单读者仲裁**仍在同一把池锁内、每连接最多读一次；**判崩溃前必复查 `进程.exitcode`** 一字未改。新增的 `回收者` 标签只是补齐「锁外期间谁在动手」的显式互斥（句柄体系「回收中」标记同形），其他线程看到非空即不介入。
- 落盘收口成**一份实现** `_落盘(任务表)`（旧 `_持久化` 已删除）：单任务关键路径（提交后/取消请求）逐文件 fsync；多任务波次（一轮轮询里同时进终态）全部写出 + 原子替换后**目录 fsync 一次**（N 次 fsync → 1 次）。`_落盘波次`（锁外批量）由监视循环轮尾、取消、等待、排空、停止调用；`_兜住落盘` 让排空/停止不被单条落盘失败截断（异常仍在出口如实上抛）。
- 慢 I/O 出锁的调用点：`提交`（能力不存在分支 + 提交后落盘）、`取消`（终止/join 与终态落盘）、`停止`（终止循环整体出锁，标记段只锁内记账）、`_拒绝等待队列`（排队任务无工作进程，走同一回收路径）。旧 `_完成`/`_完成失败`/`_发布响应` 直接删除，无兼容壳、无别名。
- 唯一保留在锁内的落盘：`取消` 的单任务 `_落盘([任务对象])` —— 「先落盘成功、再发出不可撤销的取消请求」的顺序承诺要求回滚不被并发观察者看见，已在注释中写明理由。

### 剩余风险
1. **多任务波次的快照只做目录 fsync 一次**（换取 N 次 fsync → 1 次）：极端掉电可能丢最近一轮非关键任务的磁盘快照。任务权威账本是运行库（`任务系统._保存已加锁`），磁盘快照只用于重启后可见性；单任务关键路径仍逐文件 fsync。若评审要求「波次也逐文件 fsync」，改 `_落盘` 里一行 `逐文件 = len(唯一表) == 1` 即可，池锁占用不再随 N 增长这一点不变。
2. 严格编码口径（`allow_nan=False` + 字节集冻结包装）目前有 4 处实现（本地网关、网关核心、HTTP连接器、任务工作器）——根治应把编码侧提到 `公共契约/运行时/JSON解码.py`（该文件不在本次允许修改范围，未动）。
3. `bytearray`/`memoryview` 出站会被包装、入站还原成 `bytes`（类型收敛为 bytes，符合网关口径）。
4. `任务接入.py::_构造执行器` 的失败二元组未被改写（该文件不在允许修改范围）：现行 `_是失败信封` 完整兼容它（第二项 `假` 单例 + 错误结构），未出现语义回退；若将来要彻底去掉二元组形态，需在 `任务接入.py` 改用显式信封。
5. 破坏点均已还原（`grep 破坏点` 两个文件均为 0 处命中），备份留在 /tmp/反E备份/（临时目录，不入库）。
