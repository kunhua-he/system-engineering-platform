## 各处修法与理由

- **P2-7 选了改法①**（获锁判据加「租约截止 > 0 且 < now 即可 CAS 抢占」）：任务名就是「租约不抢占」，改法②只写注释等于把机制留成半成品。抢占判据用**观察到的 `租约截止` 原值**做 CAS（并发抢占只有一个 rowcount=1），同一事务内递增栅栏令牌 + 写一条 `回收证据(类型='锁租约过期抢占')`；被抢占者的提交/续期/释放全部被令牌判据拒绝（已断言）。`租约秒 = 0`（缺省，也是当前全部调用点的实际取值）→ `租约截止 = 0` → **行为与硬化前逐字一致**，不会影响在跑的锁。
- **P2-8**：选「捕获该特定 OperationalError 转并发冲突（可重试）」而不是全局 `BEGIN IMMEDIATE`——后者会改动现有写事务语义与嵌套调用（`_事务`）行为，收益不抵风险。判据是 `是并发冲突`（`isinstance(OperationalError)` + sqlite **主码** ∈ {BUSY, LOCKED}，现场实测 BUSY_SNAPSHOT 扩展码 517 → 主码 5），返回 `(假, "并发冲突: …可原样重试")`，不再冒泡成「内部错误」。为保持单一事务边界，原方法体拆成 `_提交资源单事务`。
- **P2-10①**：`表名/列名/主键/唯一列` 用记忆包指定的正则 `^[\u4e00-\u9fa5A-Za-z0-9_]+$`；`条件SQL/条件` 用**裸条件词法**逐段吃掉（字符串字面量/占位符/标识符/数字/比较与逻辑运算符/括号/逗号/空白）+ 结构关键字拒绝（SELECT/UNION/DROP/PRAGMA…）。现场用 AST 扫全仓取到全部 33 条真实条件与 27 个标识符，逐条放行（见白名单自检）；17 条注入样例（分号、`--`、`/*`、引号拼接、`UNION SELECT`、子查询）全部拦下。拒答类型 `标识符不合法` 继承 `sqlite3.OperationalError`：`平台状态/实现/能力入口.py` 只捕 `sqlite3.Error`，这样公开能力仍回既有的 `读取记录失败/查询记录失败/写入记录失败`（网关 400），不会退化成 500，也**不需要新增错误码**。
- **P2-10②**：`_列名表(连接, 表)` 一次取列名，`读取记录`/`查询记录` 都提到结果行循环外（实测 20 行从 20 次 PRAGMA 降到 1 次）。
- **P2-10③**：`_拼UPSERT` 取代「先 SELECT 整行 → 合并 → INSERT OR REPLACE」。**记录带主键列** → `ON CONFLICT(主键) DO UPDATE SET 仅传入列=excluded.列`（无更新列时 `DO NOTHING` 幂等空操作）；**记录不带主键列** → 保持修复前语义（`写入记录` 走 `INSERT OR REPLACE`，`写入记录或唯一冲突` 走纯 INSERT，绝不 REPLACE 掉占着唯一列的那行）。这一分支是**轻检测抓出来的真实回归**：`需求登记.登记需求` 等 12 个调用点不传 `主键`（走缺省 `"id"`），记录里只有业务主键，无条件 `ON CONFLICT(id)` 会直接报 `no such column: id`。
- **P1-6**：`_迁移结构` 失败时 `raise … from 错误` 保留原始异常；`_初始化` 判 `错误.__cause__` 的 sqlite 主码 ∈ {SQLITE_ERROR, SQLITE_BUSY, SQLITE_LOCKED}（对应原文案的 no such table / database is locked / database table is locked），不再解析英文消息。

## 剩余风险

1. **P1-6 判据略宽于原文案**（已写进代码注释）：`SQLITE_ERROR` 是 sqlite 通用码，`no such column` 之类也会重试——代价有界（最多 4 次尝试、合计 ≤0.3 秒），最终抛出的仍是同一条「结构迁移失败」异常。要按码判就没法区分 no such table / no such column（两者同码 1）。
2. **`_初始化` 重试只覆盖被 `_迁移结构` 包成 RuntimeError 的错误**：迁移脚本外层 `CREATE TABLE 元信息`/`SELECT 版本`/`INSERT 版本` 若直接抛 `sqlite3.OperationalError`（如瞬时 lock），会落到外层 `except sqlite3.DatabaseError` 走「损坏恢复」而不是重试。这是硬化前就有的边界，本次按记忆包「P1-6 一处」的范围没动，建议后续单独收口。
3. **裸条件是过滤条件改写不是注入**：`条件 = "1=1 OR 1=1"` 这类词法合法、语义是过滤改写，白名单不拦。该能力本来就允许按表名读任意声明表，且既有条件 `计数>0` 本身就是常量比较，语义层收紧会误伤既有调用——按「纵深防御」定位保留，未做语义校验。
4. **`写入记录` 的无主键分支保留 REPLACE 语义**（与修复前逐字一致）：这些调用点传的是整行（发布/信任/激活指针/角色授予/制品/需求），REPLACE 与 UPSERT 等价；但若将来有人用无主键记录做**部分写**，仍会清空未传列。建议调用方补上自己的主键（如 `需求服务.登记需求` 传 `主键="需求id"`）——那属于其他路的文件，本次未动。
5. **`全量重算摘要` 全写模式未跑**：`--只报` 显示 5 个待重算包全部是别的路正在改的在飞文件（含 `模型连接器/__init__.py`、`转写/实现/提供者.py` 等），全写会把别人的摘要按半成品状态重写、越出本次允许修改范围。我自己的包已用同一 `生成完整性摘要` 入口单独收口（已闭合）。建议：等各路收工后由编排者跑一次全写模式，把全仓收敛到 0/N。
6. **公开能力 `平台控制面.平台状态.读取记录/查询记录/写入记录` 仍允许调用方指定任意表名**（白名单只保证是合法标识符）。表级授权不在本次范围，若需要「谁能读哪张表」的门禁，应另立任务。
