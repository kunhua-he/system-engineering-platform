## 二之五：目标形态 —— **全项目只留 2 个公开能力**（华哥 2026-09-23 裁决）

> 「然后总结成 2 个能力就行，整个项目的。1. 静态编译（就是我给你讲的那一套）2. 动态编译
> （就是跑实际的测试，但是测试需要超小型的，而且和静态编译一样，多线程+多线程嵌套+还能再往下嵌套都行）」
>
> 「当你发现我说的路径中，出现了旁路或者散装节点的，那就应该把它的 html 能力给移除掉了，
> 转换成内部能力。能力分为公开能力跟内部能力。公开能力都是成熟稳定的能力。内部能力是公开能力的某一个节点。」

### 目标形态

| 公开能力 | 一次调用做完什么 | 并行口径 |
|---|---|---|
| **静态编译** | 影响面 → 派生件（含**制品生成**）→ 静态门禁 → 全仓按库分片（三态：跳过已有／补齐缺的／重生成有差异的） | 一线程一包；线程内可再嵌套（分片→分文件）；并发上限按核数与包数派生（不再写死 8） |
| **动态编译** | 跑实际测试（**测试必须超小型**） | 与静态编译**同构**：多线程 + 嵌套 + 再嵌套 |

### 「公开能力 / 内部能力」的现成机制（不用新建概念）

- **网关暴露面**：`公共契约/包声明/声明.py:57` 的 `内部层: bool = 假` —— 原文注释
  「第三方能力内部支持库：装配可用、网关 **0 暴露**」。`内部层=真` ⇒ 该包能力装配可用但不对外。
- **前端(HTML) 暴露面**：由页面引用的 `能力id` 决定 —— `开发工具/轻代码前端编辑器/页面模型.py:54-58,111-114`
  校验每个 `能力id` 必须在能力目录内；页面引用即「这个能力有 HTML 面」。
- 故「撤掉 HTML 能力、转内部能力」= **两个面一起撤**：页面引用移除 + `内部层=真`（只撤一面会留下另一面）。

| `模块库/自修复工具/说明/使用说明.md` 有没有机器印记 | **有**（`<!-- 机器管理｜类型：仓库内其他文档｜生成器：开发工具.MD文档生成 -->`，第 2 行） |
| 我本轮是**直接写文件**（python 写入）改的它 | 是 |
| `python3.14 -m 开发工具.MD文档生成 --拒绝手写校验` | **通过**（“本轮改动的 md 全部在生成器管理下”） |

⇒ **判据是「有没有印记」，不是「这份文件的这次改动是不是经工具做的」**。
印记是**文件级、加一次就永久有效**，所以：**只要某份 md 曾经被生成器写过，此后人（或 Agent）直接编辑它就永远不会被拦** ——
这就是华哥要堵的口子，且它比“无印记手写”更隐蔽（那种好歹会被拦）。

### 三层落点（缺一层都堵不住）

| # | 要做的事 | 落点 | 为什么在这里 |
|---|---|---|---|
| B1 | **人工类说明书补能力段不得直接写**：缺失的能力段得走一个“受管写”入口（唯一写入点），不是直接 `write_text` | `开发工具/MD文档生成/说明书/载位同步.py`（已有载位行就地替换）；新增“**能力段插入**”档 | 这条腿已存在且方向正确（只改已存在载位行、不增删行）；缺的是“**能力段整段缺失时怎么办**”——现在只能人写 |
| B2 | **判据从“有无印记”换成“能不能证明本次写入经工具”**：印记只能证明“曾经被生成器管过”，证明不了“本次” | `开发工具/MD文档生成/机器印记.py` + `__main__.py::_拒绝手写校验` | 这是根因。可用的既有机机制：**写入留痕**（工具写入时记下文件指纹→内容指纹），校验时对「本轮改动的 md」逐个比“现场内容指纹是否等于某次工具写入留下的指纹” |
| B3 | **人工类说明书的内容完整性判据要可机检**（现在“缺能力段”已经是门禁项，但“人写的那段对不对”判不出） | `开发工具/公开调用完整性门禁_说明书解析.py`（已有 `说明书-缺能力段` / `说明书-缺参数`） | 已有 → 只需把“段内容与契约对账”也纳入（现在只对账字段行） |

### 最小可行的一步（先做 B2，因为它是根因且可机检）

现有机制“机器印记”记的是**文件级曾经纳管**；把它升为 **“本次写入凭据”**：

  · 工具每次 `--写盘` 时，除印记外再记一条 **`开发文档/项目证据/MD写入流水.jsonl`**：`{相对路径, 内容sha256, 时刻, 工具, 类型名}`（一行一 JSON，只增不改）；
  · `_拒绝手写校验` 对**本轮改动集**里的每份 md，不只查印记，还查：**现场内容指纹是否命中写入流水**；命中 → 该文件是工具写的（通过）；不命中 → **判红并明说“这份文件被改动过但没有任何工具写入记录”**（这就是“直接手写”的机器定义）；
  · 反向验证：用例里**直接写**一份已有印记的 md ⇒ 必须判红；再用生成器 `--写盘` 同一份 ⇒ 必须转绿。

这样“人工参与只能改生成器输入源、不能改 md 本身”就有了**机器判据**（哲学 13.1 三要素齐），而不是只靠纪律。

**未做（下轮）**：B1 的“能力段插入”受管入口；B3 的段内容对账。本轮只落地 B2 判据 —— 因为它是根因，且**不落地它就无法防止我这个错再次发生**。

## 二之八：只读锁 —— 真正能做“拒绝落盘”的形态（含一条关键实测）

> 华哥 2026-09-23：「mcp 写入的时候，db 记录一个很短的东西。类似于凭据一样的那种，比如说开工 ID + md5 摘要；…
> **当 agent 用自带的工具落盘时，直接拒绝。只能用 mcp 工具。**
> 本质上其实可以把**整个项目的文件全部变成只读**。只有通过 mcp 的时候，才会立刻放开某个文件的读写权限，
> 然后可以开始落盘。落盘结束然后登记凭据后，就立刻又变成只读。这样子就解决了这个问题了吧」

### 关键实测（本轮跑来，直接决定形态）

| 操作 | `chmod 444` 之后 |
|---|---|
| `path.write_text(...)` | ❌ **PermissionError 被拒** —— 这就是“agent 自带工具直接拒绝”的机器根据 |
| `os.replace(临时文件, 目标)` | ✅ **照样成功**（原子换名只靠**目录**写权限，不看文件自身权限） |

实测现场（`/tmp/只读验证`）：`文件权限 444` → 直接写「被拒 ✅」→ `os.replace` 后内容已是新的。

### 由此得出一条比原先设想更省的结论

**不需要“先放开权限 → 写 → 再锁回”**：平台两条写入腿里，
`文本补丁` 本来就是 `os.replace` 原子写（`_原子写保留权限`），**它天然能写只读文件**；
只有 `文件操作.写入文件` 走的是 `path.write_text` ⇒ 只读锁定后**它自己会被拦**。
故只需把这一条腿改成原子写，**全项目只读就不影响 MCP 写入面**。

### 形态（三层，与你说的一致）

| 层 | 做什么 | 落点 |
|---|---|---|
| **锁面** | 正式源码面的文件置 `0444`（只读）；`工程缓存/` **不动**（运行数据要能写） | 新增能力：`平台控制面.能力目录.落盘只读锁`（上锁 / 解锁 / 查看状态） |
| **写入面** | 写入腿一律 `os.replace` 原子写（天然过锁）；落盘后登记凭据（开工ID + 内容 md5/sha256），这正是你说的“db 记一个很短的东西” | `文件操作.写入文件`（改原子写）+ `文本补丁`（已是）+ 凭据已接（`公共契约/诊断/写入流水.py`） |
| **拒绝面** | agent 自带工具（Edit/Write/`echo >`/`write_text`）碰到只读文件 ⇒ **OS 直接拒**，不需任何判据 | 就是 `chmod 0444` 本身 |

### 必须如实报的两条代价（不报就是坑）

| 代价 | 具体影响 | 缓解 |
|---|---|---|
| **git 也会被拦** | `git checkout` / `git stash` / `git merge` 要**改写工作树文件**，只读时它们会失败（`unable to unlink`/`Permission denied`） | 上锁时把 `git` 列入“需先解锁”的操作；提供 `落盘只读锁.解锁` 一键放行（解锁后 git 自己能跑完，再上锁） |
| **编译口/生成器也写盘** | 生成物（完整性摘要 / 说明书 / 债务清单…）走的是 `write_text` 与各生成器自己的写盘；全项目只读后**编译口会红** | 分两阶段：① 先把全部生成器写盘改成原子写（或走 `落盘只读锁` 的开窗）；② 再上锁。**顺序反了会当场把开发循环打死** |

### 结论：可行，但要按顺序做（本轮已完成的先决件）

已就位的先决件（本会话实测）：
  · 三条写入腿已接内容指纹凭据（`写入流水.py`），且**已实测拦住了我自己**（3 份终端改的 md 被判“无凭据”）；
  · 判据 `--拒绝手写校验` 已升为两问（印记 + 本次写入凭据），并加了**受管分档**（存量只报不拦，防一次打红 700 份）；
  · `pre-commit` 钩子已建（提交腿强制点，调同一判据，不另写第二套）。

**下一步（需你确认顺序）**：① 先做「写入腿全改原子写 + 生成器开窗」；② 再跑 `落盘只读锁.上锁`；
③ 反向验证：终端 `write_text` 必须被 OS 拒、MCP 写入必须成功、git 需解锁才能动。

### 判据：怎么区分“经 MCP”与“终端直跑”

可用的现成信号（三档，由强到弱）：

| 档 | 信号 | 可靠性 |

**落地方向**：给 `脚本入口准入` 加一个可选门槛（默认关，避免此刻就把开发循环打死）：
`脚本入口准入(用途, 要求经MCP=真)` ⇒ 当 A 档信号不在且不在白名单时，拒启。

与 `开发工具/环境自检.py`（诊断入口，哲学既有口径：“把排查手段拦掉等于失去诊断入口”）。

### 必须先说清的三条边界（不报就是坑）

| 边界 | 影响 |
|---|---|
| **编译口步骤5 跑定向测试是子进程** | 那些子进程由编译口起，环境可能不带 MCP 信号 ⇒ 会被自己的准入拦死。必须先让编译口把信号**显式传递**给子进程（它已有环境传递机制，见嵌套防自递归标记的做法） |
| **git 钩子调 python** | `pre-commit` / `commit-msg` 用 `git` 触发，不是 MCP ⇒ 会被拦（但钩子本来就不是“运行项目代码”，需在白名单或改成不调 python） |
| **开发工具的只读件** | `开发工具/环境自检.py` 这类“换平台时正需要跑”的入口，按既有哲学口径不得接准入 |

**结论**：要做，但**先做信号传导**（编译口→子进程、钩子→python）再上门槛；
否则顺序反过来会当场把编译口与提交腿一起打死（就是本仓反复栽的“判据太宽＝假红”）。

```

请使用：capability_call(能力id="静态编译", 参数={"类型":1,"模块ID":"<你改的库/模块>"})
或        capability_call(能力id="动态编译", 参数={"类型":1,"模块ID":"<你改的库/模块>"})
（终端直跑不带识别符号；若你确实在修 MCP 自身，见哲学 7.1 的终端腿例外）
```

**落点**：`公共契约/运行时/平台适配.py` 已有 `脚本入口准入(用途)` —— 给它加可选门槛
`要求经MCP=真`（默认关，避免此刻就把开发循环打死），内里就做上面 A+B 两层对账。
调用方：新增/修改的**脚本入口**要逐步接上；已接准入的六个入口（构建脚本 / 受控文件读写 /
热接入 / 薄壳 / 能力网关 / …）优先。

**边界（必报）**：
  · 终端腿仍可用 `--no-verify` 类途径绕过**提交**，但**运行时**这层不需要钩子：
    对账不过就直接退出码非 0（进程根本跑不起来）；
  · 对账自身出错（凭证文件缺失/不可读）按 **拒绝**处理（fail-closed），
    但报错文案要区分“没符号”与“对不上账”（一个是没走 MCP，一个是环境被改过），
    否则排查的人会朝错方向查（哲学 3.1 一次命中）。

---

## 三、结论：不是「修完这个下一个再炸」

上面 19 条**全部落在树上的具体节点**，每条只动它自己那一个节点。真正会造成「连锁炸」的只有一处：

**① 是唯一的连锁根** —— 它同时在 E1（派生链的声明侧）和 D1.1.11（实现侧），
改任一侧而不改另一侧，门禁都看不见（③ 是它为什么看不见）。所以 ① 必须先修，
且修完必须跑编译口让派生件同步。

其余 18 条互不依赖，任意顺序单独修，互不影响。
