## 二、逐类根因（**关键：不是所有缺口都在被测对象侧**）

### 1. 参数顺序漂移 56 条 —— **判据口径问题（占多数）**

样例：
```
组件控件.创建窗口: 契约 ['窗口id','标题','宽度','高度'] ≠ 入口 ['窗口id','标题','宽度','高度','项目id','所有者']
组件控件.创建页面: 契约 ['窗口句柄','页面id','路由'] ≠ 入口 ['窗口句柄','页面id','路由','标题']
```

**根因**：契约只登记**必填参数**，而实现签名里带**默认值的可选参数**（`项目id: str = ""`）也在签名里。
入口参数是契约参数的**超集**（契约是子序列）时，判据判「漂移」——**这是判据没区分「可选参数」与「顺序真错」**。

- **真顺序错了**的形态应是：契约 `[A, B]`、入口 `[B, A]`（相对顺序颠倒）或契约必填项在入口里缺失。
- **应该判对的形态**：入口 = 契约 + 尾部可选参数（相对顺序保持）。
- **处置**：改判据——先按**契约必填参数的相对顺序**在入口里做**子序列匹配**；
  子序列不成立才判漂移，且报「哪些必填项缺失/顺序颠倒」；入口多出的带默认值参数**只报不判**。

### 2. 参数类型漂移 49 条 —— **契约真错（被测对象侧）**

样例：
```
组件控件.创建组件: 页面句柄 契约类型 整数型 ≠ 入口注解 str
组件控件.设置组件属性: 组件句柄 契约类型 整数型 ≠ 入口注解 str
```

**根因**：句柄体系的句柄 id **本来就是字符串**（`_句柄体系.创建句柄(...)` 返回字符串），
契约却写「整数型」。**实现是对的、契约是错的**（违反「实现是最终事实」——哲学：三方不一致以实现为准）。

- **处置**：改**契约**（`能力定义.json` → 编译器重算派生物），不是改实现。
- **派活前必须逐条核**：这 49 条是不是同一病根（句柄类参数）——若是，一次批量改；
  若有非句柄参数混入，单独列出。

### 3. 声明无实现 16 条 —— **判据认不出「转调文件」（合法手法）**

样例：
```
文档转换支持库.PDF文本表格.解析PDF（实现/ 下未找到函数 解析PDF）
技能库.技能索引.生成索引（技能库/后端/技能库/实现 下未找到函数 生成索引）
```

**根因已现场查到（不是包错、也不是简单口径问题）**：
`支持库/后端/文档转换支持库/PDF文本表格/实现/PDF文本表格.py` 只有 **39 行**，
它的作用是**把本模块对象替换成唯一实现**——
```python
sys.modules[__name__] = sys.modules["支持库.适配层.pdfplumber提供者.实现.PDF文本表格"]
```
这是 **D-2 结构债收口**的成果（同一份逻辑只能有一个实现，两份逐字节相同的文件收敛成"一份实现 + 一份转调"），
文件头注释写明「跨包导入 `实现/` 被依赖防火墙强制拒绝，故先导公开入口再让两个模块名指向同一对象」。

**该文件里当然没有 `def 解析PDF`**（函数在适配层那份里），所以判据按 AST 找函数名必然报「声明无实现」；
并且会**连带**报「入口文件缺失 + 实现文件未定位」——**一条缺陷被报三次**。

- **处置**：改判据，**识别「模块对象替换」形态**：入口文件（或 `实现/` 下的文件）里出现
  `sys.modules[__name__] = ...`（或等价的 `sys.modules[<本模块名>] = ...`）时，
  判据应**跟随到被替换模块**去定位函数与签名，而不是就地判「无实现」。
  若确实跟不到，也应报「转调目标未解析」，与「真无实现」**分开表述**（13.1：判不出 ≠ 判绿，但也不该混为一谈）。
- **不要去改包**：转调是平台认可的既有做法（先例 `平台控制面/授权/__init__.py`），包在装配期能正常调用即为正确。

### 4. 错误码漂移 3 条 —— **判据口径问题（可能）**

样例：
```
FFmpeg媒体.检查提供者: 实现引用 参数不合法 但契约未声明（探测.py）
```

**根因待核**：报的是 `探测.py`（探针能力），而 `参数不合法` 是**通用错误码**——
要么契约该补声明，要么判据该放行「通用码」。**逐条核**，不要批量改。

### 5. 说明书版本不一致 2 条 —— **真问题（小）**

```
测试资源.申请资源 / 回收资源: 说明书与契约不一致: 缺少版本 1.0.0
```

- **处置**：按甲方/乙方口径（见 `规范/说明书权威分工与维护规约.md`）判定该说明书是生成物还是人工权威，
  再决定"重生成"还是"手补版本行"。

## 三、处置顺序（**不是一次性全修**）

1. **第一步（判据侧，收益最大）**：修「参数顺序漂移」判据（子序列匹配）与「声明无实现」判据（入口定位）。
   这两项占 56+16 = **72 条**，且都是判据把正确的东西判成缺陷。
   **判据修完必须做双向验证**：①被误判的转绿；②**故意真错**（颠倒必填顺序 / 摘掉一个必填项）仍红。
2. **第二步（契约侧，49 条）**：核句柄类参数类型，改 `能力定义.json` + 编译重算派生物。
3. **第三步（小项）**：错误码 3 条逐条核、说明书 2 条按甲乙支口径修。
4. **第四步（接线 + 基线）**：上述修完后**再**生成基线（`--生成基线 --写盘`），
   并把 `全面漂移检测门禁` 接进发布门禁（**此前它零调用方**，正是未完成事项第 24 项）。
   **顺序不能反**：先建基线会把 126 条（含判据误判）冻成"合法存量"，反而掩盖真缺陷。

## 四、这条链暴露的架构问题（比 126 条本身更重要）

1. **判据零调用方 → 无人知道它判错**：`全面漂移检测门禁` 早就写好了（含基线机制、fail-closed、收缩基线），
   但**从来没接进任何必经路径**，所以它把「可选参数」判成「顺序漂移」这类口径错误**长期无人发现**。
   这正是华哥口径「判据在、门禁不调 ＝ 纸面规则」的又一实例。
2. **同一缺陷被报三次**（声明无实现 + 入口文件缺失 + 实现文件未定位）——判据之间没有去重/归并，
   放大缺口数、也让读者误判严重程度。
3. **另一路的自造探针重复实现了官方能力**：子代理为跑这条判据自己写了 3503 字节探针，
   而官方 `全面漂移扫描` 已经存在——**派活时写清"用哪个官方入口"能省一整轮**。
