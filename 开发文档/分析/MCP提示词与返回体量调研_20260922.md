## 三、已有的可复用设施（重要：不是从零建）

### 3.1 `公共契约/诊断/调用账本.py` 已经存在

表结构（实测）：

```sql
CREATE TABLE 调用参数账 (
  能力id TEXT NOT NULL,
  入参形状 TEXT NOT NULL,      -- 「键:类型|键:类型」按键名升序
  调用次数 INTEGER,            -- 同一形状自增 1
  最近时间 REAL,
```

落点：`<运行数据根>/调用参数账.sqlite3`（与 `权威状态.db` / `网关幂等.sqlite3` 同级）。
写方在 `运行核心/统一网关`（每条请求自增），读方在 `模块库/能力目录`

**现有账本只记入参，不记返回**。华哥要的「把返回值记录在 db」是在这个基础上**扩一维**
（返回体 + 读过哪些字段），不是另起一个库。

## 四、四条候选方向（供裁，不是结论）

调研到的事实支持以下方向，但**哪条该做、做到什么程度属产品决策**，不在本次调研内定论。

### 方向 A：工具提示词由「能力契约」生成，而非固定散文

华哥描述的形状是「POST(路径) + 参数 json{A/B/C 带类型}」。落到实处即：
- 固定散文（「入参分两层」那套）只保留**极简版**（一层话讲清两个入参位置）；
- 具体参数名与类型**来自能力契约**，调用哪个能力就展示哪个能力的参数表。
- 现有设施：`能力详情` 操作已能读权威落盘契约（含参数名/类型/必填）；
  `查询节点` 类结构化检索也已存在。

### 方向 B：返回先落库、回执只给摘要 + 偏移取用入口

- 每次调用把完整返回落到一个可回查的库（或沿用 `调用参数账.sqlite3` 扩列）；
- 回执里给 `大小 / 键清单 / 本次裁了多少 / 取全的入口（偏移或字段名）`；
- 调用方要细看的，用已有的 `起始行`/`起始偏移` 能力取那一段。

### 方向 C：按调用意图给默认投影（「要什么给什么」）

华哥的核心句：「如果只是想知道真还是假，例如运行的目的就是要他 200 的成功的，那你其他的参数没用」。
- 判真假类调用 → 只回 `成功`/`错误码`/`状态码`；
- 要数据类 → 回业务字段；
- 默认投影由**规则**推（如按能力的返回声明分类），不由调用方每次手填。

### 方向 D：记「哪些字段被高频读」，反推该砍什么（华哥的「证明还有优化空间」）

现有账本记到「入参形状」粒度。华哥要的是再进一步：**记录返回里哪些键被读了**。
难点（实测发现）：`值字段` 的投影发生在薄壳，且**没记下来读过什么**；
要统计「高频读的字段」必须先在投影处埋一笔账。

### 方向之间的关系

B 是 D 的前提（不落库就无从统计读了什么）；A 与 B/C 互不冲突（一个管入口、一个管出口）。

   而同一时刻**制品里根本还没有 `绑定文件认知`**（已现场核实：制品内 `开工编排.py` 里
   该词出现 0 次）——即**制品未重建，网关跑的是旧装配**。

2. **工具描述与真实契约存在双源**：`capability_call` 描述里教的调用格式（散文）
   与能力契约（结构化）是两份，可能漂移。哲学 1.2 的同类形态。
3. **通用纪律占开工返回 58%**：这是「越精准越好」当下最大的单点浪费，
   且它本身是**无条件返回**的设计（2026-09-18 定：不依赖派活方记性）——
   砍它等于回退那个修复，故不能简单砍，只能改交送方式（待裁决）。

## 七、结论

华哥的两个判断都被实测证实：

1. **工具提示词确实是固定的**：三个工具 1320 字符描述对所有调用**逐字相同**，
   与「这个调用要干什么」无关。这正是已定口径「固定提示词本质上是缺陷」的另一处落点。
2. **返回确实是全量的**：开工准备一次 15964 字符，其中 **58% 是通用纪律**；
   而调用方可能只需要 23 字符的开工 ID。现有的 `值字段`/`返回上限字符` 能用，
   但要调用方**每次主动填**——与「越精准越好、不需要的不要」相背。

**已有的可复用设施比预期多**：调用账本（参数形状+次数）、返回深裁、偏移读取能力
都已存在，三个方向都可在这三者基础上扩展，**不需要新建第二套**。
