**一句话**：收口层（`公共契约/运行时/平台适配.py` + `进程终止.py`）**已经建成**，且 **41/46 个 `Popen` 调用点已接上它**；但**换到 Windows 后项目仍然起不来**——原因不是收口层没做完，而是**三处独立于收口层的硬阻断**加在启动路径上（依赖锁平台指纹 fail-closed、平台准入 fail-closed、`resource` 相关探测 fail-closed），且**没有任何 Windows 实测记录**（收口层自述、`未完成事项.md`、`交付报告.md` 三处一致声明「Windows 分支未经真机实测」）。

### 三条最重要的判断（供华哥先看）

1. **「后续批次到底做完了没有」——做完了。** 平台适配.py 第 9 行那句「后续批次把 6 处硬编码 `bin/python3` 与全部 `start_new_session=True` 调用点切到本模块」**已经是事实**：生产代码里 **0 处** `start_new_session=True` 字面量、**0 处** `bin/python3` 拼接、**0 处** `os.killpg`/`os.getpgid`/`os.setsid` 直接调用（除收口层自身与注释）。解释器路径 6 处（`环境管理器.py:319/406/615/681`、`强制校验.py:286`）**全部**已改走 `平台适配.虚拟环境解释器路径()`。

2. **真正拦路的是「准入」，不是「代码」。** `运行核心/启动运行核心网关.py:17`、`开发工具/薄壳/薄壳服务.py:28`、`运维脚本/热接入.py:27`、`客户端/构建平台客户端.py:27`、`开发工具/能力网关/能力网关.py:32` 五个入口都调了 `平台适配.脚本入口准入()`，其唯一判据 `校验支持范围()` 在 `平台适配.py:220` 明确 **只放行 `macOS` + `arm64/aarch64`**，Windows/Linux/x86 **一律 `sys.exit(1)`**。这是 2026-09-18 的**有意裁决**（不是缺陷，见 §五），但它同时意味着：**「Windows 兼容性」在当前代码基线上被显式设计成不可达**——要真机验证，必须先裁定「是否放开准入」。

3. **依赖锁是第二道墙，且比准入更难绕。** 仓库内 **33 份 `依赖锁.json`，33 份全部写死 `{"Python":"3.14.4","操作系统":"macOS","CPU":"arm64"}`**（实测 33/33，无一份例外）。`强制校验.py` 规则 5（第 240–274 行）逐份比对「Python 主次版本 / 操作系统大类 / CPU 架构」，不符即**拒绝运行**（fail-closed）。重建入口 `开发工具/重建依赖锁.py` **确实存在且可用**（这是 README 那句「若当前版本尚未提供，按结构对齐」的答案：**已不成立，入口已提供**），但重建本身也依赖底座能导入 → 而底座导入与装配又被准入/锁拦住。**换平台的正确顺序因此是「先裁定准入 → 再重建锁 → 再跑自检」**，见 §三。

## 五、不是缺陷（设计取舍）清单

以下 10 条**看起来像兼容性缺陷，实际是有意裁决**。列在这里是为了防止后续批次被误改。

| # | 现象 | 为什么是取舍 | 证据 |

| 1 | 平台准入拒绝 Windows/Linux/x86 | 2026-09-18 有意裁决：正式支持范围只声明 macOS+arm64，避免「未实测平台被当成可用平台」 | `平台适配.py:195-196`、`:208-231`；`未完成事项.md` 与 `交付报告.md` 一致声明「Windows 分支未经真机实测」 |
| 2 | 句柄枚举目录在 Windows 返回**空元组**而不是抛错 | 空元组是**显式无能力信号**，调用方必须报「不支持」而不是报 0。这是刻意的「不假装有数据」 | `平台适配.py:155-168`；消费方 `容量基线.py:52`、`采样器.py:48` 都判空 |
| 3 | 内存峰值在 Windows **抛不支持**而不是返回 0 | `resource` 是 POSIX 独占；返回 0 会被下游当成真实读数污染监控 | 收口层 `平台适配.py:130-152`；`采样器.py:34` |
| 4 | 进程存活判定**刻意不用** `os.kill(pid, 0)` | Windows 上 `os.kill(pid,0)` 会**真发信号**并可能误杀；改用 `OpenProcess(SYNCHRONIZE)+WaitForSingleObject` | `进程终止.py:236-298`（含注释说明） |
| 5 | 进程组号在 Windows 返回 `None` | Windows 无 POSIX 进程组语义；返回 `None` 让调用方走「单进程/进程树」替代路径，而不是拿到一个假的组号 | `进程终止.py:817-836` |
| 6 | `spawn` 下要求执行器可序列化 | 这是 `multiprocessing` 的**语言级约束**，不是本项目选择；Python 在 Windows 上只有 `spawn` | `任务进程.py:228-244` |

## 七、审计局限

1. **平台事实来自 macOS 本机 + 静态代码**。收口层的 Windows 分支（`creationflags=0x200`、`taskkill /F /T`、`OpenProcess`、`LOCALAPPDATA` 回退链）**没有任何一处在本轮被真机执行过**。桶 A 的 12 条全部是「代码已收口」的证据结论，**不等于「Windows 上真能跑」**。收口层自述、`未完成事项.md`、`交付报告.md` 三处一致声明「仅 monkeypatch 模拟过」——本报告承袭这一限定。

2. **41/46 这个覆盖数是窗口扫描口径**。判据是「`Popen(` 后 ±14 行窗口内出现 `子进程组启动标志`」。存在两种误判可能：(a) 子进程组标志写在更远的位置而被漏算；(b) 窗口内出现但实际未生效（例如写在另一分支里）。真机验证时应以「子进程是否真的在新进程组」为最终判据，而非以本数字为准。

3. **33 份依赖锁是按当前仓库文件数统计**。若后续新增包，份数与 B2 的量化值都会变。

4. **外部命令的 Windows 等价性未做真机探测**。B4 表中「Windows 无原生」的判定基于 Windows 平台常识与各提供者的调用形态，未在 Windows 上执行 `where ps` / `where pgrep` / `where textutil`。真机第 1 步的环境自检第 9 项会给出真实缺项清单，应以那份清单为准覆盖 B4 表。

5. **`GBK` 编码风险是静态扫描**（扫描「cp936 编码表编不出的字符」，命中 265 处符号）。是否真的触发 `UnicodeEncodeError` 取决于 Windows 控制台的代码页（`chcp`）与是否设置 `PYTHONUTF8=1`；本轮未在 `cp936` 控制台真跑过。

6. **`spawn` 下执行器可序列化（B7）的具体失败名单未穷举**。「691 个能力全注册闭包执行器」是注册面统计；真正会被 `pickle` 拒绝的是「闭包捕获了不可序列化对象」的那部分，本轮未逐个能力实测。真机第 7 步的异步任务提交会给出第一批真实失败名单。

7. **本轮未跑测试、未起服务、未改代码**（按纪律）。因此不存在「修复后回归」的证据；本报告是**问题清单**，不是修复验证。

8. **`未完成事项.md`、`项目说明.md`、`交付报告.md` 的跨平台结论已交叉引用**，但它们本身也可能滞后于代码；凡本报告与文档冲突处，均以现场代码取证为准（已在各条注明）。
