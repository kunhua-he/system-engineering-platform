# 归因：子代理探索占 76% —— 代码符号定位链断裂（2026-09-18）

> 最后更新：2026-09-18
> 口径：**实测**（每条带命令与输出）
> 维护者：小马仔
> 状态：生效（归因记录 + 补底层清单）

---

## 一、现象（华哥提出「子代理 20-30 分钟太慢，能不能加速」）

13 路子代理实测：**墙钟合计 16,318 秒，其中工具执行仅 4,215 秒（25.8%）**，
**非工具（模型思考+交互）12,103 秒（74.2%）**。

进一步量化**调用意图**：

| 类别 | 次数 | 占比 |
|---|---|---|
| 探索（grep / sed / find / ls / read_file / search_files） | **683** | **76%** |
| 修改（patch / write_file） | 215 | 24% |

**极端样本**：C 簇（网关修复）**探索 82 次、修改 0 次** —— 86 次调用几乎全在「找某东西在哪」。

## 二、根因（三层，逐层实测）

### 2.1 不是工具慢，也不是模型慢

| 实测项 | 结果 |
|---|---|
| 模型单次往返（8328，短/中/长提示） | 1.8s / 1.9s / 2.7s |
| 生成速度 | 51 → **131 tok/s** |
| 并发 16 路压测 | 单次中位 1.9s、整批 4.3s，**无排队退化** |
| 最长工具命令 | 40–104s（正常长测试），但**中位仅 3-5s** |

⇒ 模型与工具都不是瓶颈，**时间花在「每轮都在决定去哪里找」**。

### 2.2 真因：C 簇找的符号，在代码地图里**根本不存在**

C 簇 86 次调用反复找的东西（实测 grep 真实位置）：

| 它找的 | 真实位置 | **代码地图里有几个节点** |
|---|---|---|
| `资源账本维护循环` | `运行核心/资源协调/句柄服务.py:331` | **0**（该文件在地图里 0 节点） |
| `协议表` | `运行核心/统一网关/协议表.py` | **0** |
| `装配状态` | （分散多处） | 0 |

**而地图本身是有的、数据也很大**：`nodes` 10,896 行、`edges` 22,788 行、`files` 564 行。

### 2.3 更深一层：地图**陈旧 28 天，且平台没有「重建/更新」能力**

实测 `.codegraph/codegraph.db`：
- 文件时间 **2026-08-21 16:57**（陈旧 28 天）
- `project_metadata.index_state = complete`、`indexed_with_version = 1.5.0`
- **但 `运行核心/资源协调/句柄服务.py`、`运行核心/统一网关/协议表.py` 都是 0 节点**
  → 这些文件是**索引之后新增的**，地图从未同步

查「谁负责更新地图」：`代码解析支持库.代码地图` 包**只有查询能力**
（`查询节点` / `查询关系`），**没有任何「建图 / 索引 / 重建 / 同步」能力**。
`.codegraph` 由**外部 `codegraph` CLI** 建立并维护（`~/.npm-global/bin/codegraph`），
**平台侧无任何机制保证它被更新** → 无人维护 → 陈旧漂移。

## 三、这是不是一个「bug」？（华哥判断：是）

**是**，且是**底层缺口**（哲学 14.3「反复犯错的开发要补底层」）：

1. **能力面断裂**：平台把「查地图」做成了原子能力，却**没把「地图保鲜」做进平台** ——
   查的是一个**没人负责更新的副本**，属于「有查询无维护」的半条腿。
2. **注入面断裂**：子代理开工时**拿不到「去哪找符号」的方法**。
   `开工编排.开工准备` 返回里虽有「代码地图可用性」（`index_state=complete` 会显示"可用"），
   **却无法表达「地图不覆盖我要改的文件」** —— 于是子代理拿到"可用"就信了，
   一查命中 0，只能退回 grep 满地找。
3. **契约注入断裂**（华哥原话：「你看你都要猜，证明着底层有东西没注入给你」）：
   我调 `查询节点` 时**必须猜参数名**（先猜 `名称`→报未知参数；真实是 `关键词`，
   且 **`代码地图路径` 是必填**）。⇒ 说明**契约没有在开工时注入**，
   连主会话都要靠试错才能调通，子代理更不可能知道。

## 四、补底层清单（四处，按优先级）

| # | 补什么 | 落点 | 状态 |
|---|---|---|---|
| 1 | **地图保鲜**：给 `代码解析支持库.代码地图` 补「重建/同步索引」原子能力（内部调 codegraph CLI 或原生重建），并纳入开工自检 | `支持库/后端/代码解析支持库/代码地图/` | ⏳ 待做 |
| 2 | **开工注入**：`开工编排.开工准备` 返回里，地图可用性必须**按「本次要改的文件」判定覆盖率**，不覆盖就明确报「地图陈旧/不覆盖 X 文件，勿依赖符号查询」 | `模块库/开工编排` | ⏳ 待做 |
| 3 | **契约注入**：开工上下文里带上本次任务可能用到能力的**参数名清单**（至少能力id + 必填参数），避免「靠猜参数名」 | 开工上下文 / `项目文档支持库.查开工上下文` | ⏳ 待做 |
| 4 | **当下止血**：立即 `codegraph sync` 把地图刷到最新 | `.codegraph/` | ✅ 已执行（见第五节） |

## 六、被否决的做法

- **「再派一路去 grep 快点」** —— 治不了根；下一批任务还会重复 76% 的探索。
- **「让子代理开工先跑 codegraph sync」** —— CLI 不在平台契约里、耗时不可控，且属**第二执行腿**（哲学 1.2）。
  正确做法是把保鲜做成**平台能力**（清单 1），由平台统一维护。
- **「把地图文件提交进仓库」** —— `.codegraph/.gitignore` 明确「local to each machine, not for committing」，
  且地图是**派生物**，提交等于把生成物当事实源。

## 七、结论

子代理慢**不是模型慢、不是工具慢、不是并发排队**，而是
**「找东西」占了 76%，而本来该帮它们找的代码地图已经陈旧 28 天、且平台没有任何机制保证它更新**。
按华哥裁定这是 **bug**，按哲学 14.3 **补底层**（第四节四处），不靠「让子代理多找几次」解决。
