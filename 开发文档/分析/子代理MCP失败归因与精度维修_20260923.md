## 二、三条精度缺陷（逐条：现场复现 → 根因 → 修法）

### D1 多词查询反而零命中（**最致命**：越想精确表达越一无所获）

- **现场复现**（MCP 实调，修前）：
  `capability_search(关键词="执行命令 进程 沙箱 运行")` → `总数 0`，
  `兜底说明` 原文：「兜底命中占比过高（**224/678 = 33% > 上限 30%**），判无效兜底，已如实报零命中」。
  而 `关键词="执行命令"` 有 **17 条**命中（含目标 `系统核心支持库.进程管理.执行命令`）。
- **根因**：`_兜底检索` 的第二条护栏（`兜底占比上限 = 0.30`）本意是挡「全表充数」，却把
  「**有候选、只是候选偏多**」也一并判死 ⇒ 返回空。多词查询天然更容易凑够相关度下限，
  故**词越多越容易被判无效**。
- **修法**：占比超上限**不再判零命中**，降级为「只回相关度最高的前 `兜底低置信条数上限 = 20` 条
  + 如实标注 `低置信`」。有界（绝不给全表）、可对账（`兜底判据` 里 `低置信`/`是否无效`/`已回条数`）。
- **修后实测**：同查询 → `总数 20`、`低置信=真`，且**第 2 条就是正确答案 `系统核心支持库.进程管理.沙箱执行命令`**；
  回归样本不变：`把视频转成音频` → 8 条含 `媒体转写.转写视频文件`；`执行命令` → 21 条精确命中、`低置信=假`。
- **判据**：`测试中心/模块库/测试_能力目录.py::test_兜底占比超上限仍返回有界候选且标注低置信`
  ＋ 反向 `test_兜底低置信不得影响精确命中路径`（精确命中路径一行都不许变）。

### D2 74 条「可调不可搜」，其中 12 条**零孪生**＝完全不可发现

- **现场复现**（MCP 实调，修前）：
  `capability_call(能力id="适配层.YAML提供者.检查可用性")` → `成功: true`（`{可用: 真, 版本: 6.0.3}`）；
  同一能力 `capability_search(关键词="YAML提供者")` → 只回 2 条 `数据操作支持库.数据交换.*`，
  **一条适配层都搜不到**。`浏览器自动化.检查可用` 同样调用成功、搜索 0 命中。
- **口径**：`/健康` 的 `能力数` **752**（注册表去重后 id 数，含适配层） vs 搜索面 **678** ⇒ 差 **74**。
  差额成因是 `是否可发现包` **按包前缀**排除整个 `支持库.适配层.*`。
- **根因**：排除的理由是「那是同一实现的第二条腿」——**但该理由只对真有孪生的能力成立**。
  按「末段能力名相同即同一实现」（`数据操作支持库.数据交换.解析YAML` ↔ `适配层.YAML提供者.解析YAML`）
  逐条核，74 条里 **12 条找不到任何同名孪生**：
  `Swift编译器提供者.编译源代码`、`代码地图提供者.查询项目地图状态`、`代码地图提供者.重建项目地图索引`、
  `密码签名.{公钥指纹,内容摘要,对称加密,对称解密,生成密钥对,签名,验证签名}`、
  `浏览器自动化.检查可用`、`适配层.TreeSitter提供者.解析语法树`。
  ⇒ 又一次「**可调但搜不到**」，与 2026-09-20 内部层那次**同一病根**（本仓记录为第 3 次复发）。
- **修法**：排除判据从**包前缀**下沉到**能力级**——`_构建能力索引原始` 分两遍走：
  第一遍正式包全量进面并收集**能力名集**；第二遍适配层逐个判，
  **同名孪生存在 ⇒ 排除**（真·第二条腿，防重复记录），**零孪生 ⇒ 进面**并带 `适配层=真` 标记
  （与 `内部层` 同档：进发现面但如实标注供取舍）。
- **修后实测**：搜索面 **678 → 690**，正好是那 12 条；差额 **74 → 62**（全部有同名孪生）。
- **判据**：`测试_能力目录.py::装配口径与搜索面差额测试` **新增方向三**「差额里每一条都必须在
  发现面存在同名能力」（补掉历史「记 `72/72 零漏网`、实际无判据支撑」那个洞）
  ＋ `test_适配层按同名孪生判据进出发现面`（三方向：进面的无孪生 / 有孪生的经典样本仍缺席 / 零孪生样本必须搜得到）。

## 五、修 D1/D2/D3 时当场撞到的两条（一并落盘）

### N6 单写者锁「读锁文件」非原子 ⇒ 并发启动的编译口被误报「未核验」

- **现场**：两个 `静态编译`（异步腿）先后提交，第二个在第一个仍在跑时启动，回
  `五态结论：未核验 —— 拒启（fail-closed）：同树已有编译口在跑，或判不出有没有`，
  `标准输出` 原文：`锁文件读不出（JSONDecodeError: Expecting value: line 1 column 1 (char 0)）：工程缓存/编译口单写者锁.json`；
  事后 `ls` 该锁文件 → **不存在**（第一个任务跑完已释放）。
- **根因**：守卫读锁文件时撞上**另一个写者正在写**（空文件/半截文件）⇒ `JSONDecodeError` ⇒
  只能回「判不出有没有」。方向是 fail-closed（安全的），但**结论文案误导**：现场看像「锁文件坏了」，
  实际是「另一个编译口正在跑」。
- **建议修法**：读锁文件先判 `st_size == 0` 或 `JSONDecodeError` ⇒ 短暂等待后重试一次再判；
  仍读不出时文案区分「**疑似并发写者**（锁文件正在被写）」与「**锁文件损坏**」两态，别合并成一句。
  **未修**（不在本轮租约内），登记待派活。

### N7 手写 md 会被 `拒绝手写md` 判红 —— 本件自身踩过一次

- **现场**：本件初版用终端 heredoc 落盘，`python3.14 -m 开发工具.MD文档生成 --拒绝手写校验` 判红：
  `[手写·新建且无写入凭据] 开发文档/分析/子代理MCP失败归因与精度维修_20260923.md —— 该文件本轮新建，当前内容不来自任何一次工具写入`；
