## 一、可行性证据（三条，全部实测）

### 1.1 工具描述**本来就能动态生成**（关键前提）

`开发工具/薄壳/薄壳服务.py:494`：

```python
@服务.list_tools()
async def 工具列表() -> list:
    """薄壳只暴露 3 个工具，不按角色过滤、不注入业务工具。"""
    return list(三个工具定义)
```

`@服务.list_tools()` 是**回调**（MCP 客户端每次 `tools/list` 都会重新调用它），
不是进程启动时冻死的常量。**现状返回的是模块级写死的 `三个工具定义`** ——
所以「动态」不需要改协议、不需要换 SDK，只需让这个回调按上下文组装。

取证：`grep -n 'list_tools\|三个工具定义' 开发工具/薄壳/薄壳服务.py`

## 二、华哥两条要求的落地形状

### 2.1 「提示词尽量是动态的」

现状：三个工具共 1320 字符描述，对谁调都一样。

**可动态的两个维度**（都从已有数据源取，不造新源）：

| 维度 | 数据源（现有） | 动态效果 |
|---|---|---|
| **本能力常用传参** | 调用账本 `常用参数组合`（已有能力） | 描述里直接给「照抄这组」，例：`执行命令` 最常用形状 = `命令:文本型\|工作目录:文本型\|超时秒:整数型\|项目根:文本型`（352 次） |
| **本能力真实参数形状** | 能力契约（`操作=能力详情` 已能读） | 参数名/类型/必填随能力变化，不再是散文 |

**实测样本（`执行命令` 的三种历史形状）**：

```
命令:文本型|工作目录:文本型|超时秒:整数型|项目根:文本型   352 次
命令:文本型|工作目录:文本型|项目根:文本型                   154 次
命令:文本型                                                   107 次
```

★ **这里抓到一个真事实**：`执行命令` 最高频的形状（352 次）**包含 `项目根`**。
华哥前一轮说「理论上 mcp 是默认绑定根目录的，不需要填写」—— 实测大家**每次都在填**，
因为底层没默认绑。这正是「纪律越长越是定义没收口的症状」的量化证据：
纪律里写着「必须显式给工作目录」，而账本显示 352 次里 `工作目录` 也是高频。

### 2.2 「调用的时候，默认给他返回调用的传参」

**这句话的准确含义（我的理解）**：调用某能力时，回执里**顺带给该能力的常用传参**，
不必再单跑一次 `常用参数组合`。

**为什么这正好击中痛点（实测）**：

| 调用方式 | 返回体量 |
|---|---|
| `常用参数组合(能力id='', 上限=8)` 全量 | **79198 字符** |
| 同上、裁到 2500 上限 | **只剩 47 字符**（连 `常用参数组合` 键都被丢了） |
| `常用参数组合(能力id='系统核心支持库.进程管理.执行命令', 上限=3)` + `值字段` | **846 → 703 字符** |

即：**「查常用传参」这件事现在要么爆上下文、要么拿不到**；
自带在调用回执里、且按该能力精确取，是真正的省。

**落地形状（候选，待裁）**：

```
调 capability_call(能力id='系统核心支持库.进程管理.执行命令', 参数={...})
回执里除现有字段外，增一个（或挂在值裁剪旁）：
  "常用传参": [
    {"入参形状": "命令:文本型|工作目录:文本型|超时秒:整数型|项目根:文本型",
     "调用次数": 352, "样例": {...}},
    …（默认 1–2 条，按次数降序）
  ]
```

**三个待裁点**：
1. **默认开还是默认关**：默认开则每次调用多 200–400 字符；默认关则没解决「要主动填」。
   （倾向：默认开 1 条、`返回上限字符` 不够时优先被裁——它是「怎么调」不是「调的结果」。）
2. **首次调用怎么办**：该能力从没被调过 ⇒ 账本无记录。候选是**如实回空**（不编造样例）
   或退到契约的 `调用示例`（能力详情已存在该字段）。
3. **冷启动噪声**：`反序列化JSON` 3520 次这种是内部高频（平台自己调的），
   不代表「Agent 该照抄」。是否需要区分「Agent 发起」与「内部调用」，待裁。

## 三、能不能「优化好」：结论与边界

**能。** 三条理由：

1. **协议层无障碍**：`list_tools` 是回调，动态化不用改 SDK、不用改网关。
2. **数据源现成**：调用账本（414 行真实数据）+ 能力契约（`能力详情` 操作已能读），
   不需要新建统计设施——**哲学 1.2/1.3 要求的「不另起一套」满足**。
3. **有真实改进空间（已量化）**：`常用参数组合` 全量 79198 字符 vs 精确取 703 字符，
   差 **113 倍**。

**边界（必须先说清，避免以后返工）**：

- **工具描述动态化的收益上限有限**：它只影响「调用方怎么调」，不影响「返回什么」。
  真正占上下文的大头是**返回体**（开工准备 15964 字符，58% 是纪律），
  那属调研件的方向 B/C，与本条是两件事。
- **描述不能变成第二份契约**：能力契约是权威（16 类型、必填、错误码），
  描述里只应给「常用形状 + 样例」，**不重复声明类型规则**（否则又是双源漂移，哲学 1.2）。
- **不改「固定」的那部分是对的**：如「能力id 要写真实 id」这类跨能力的硬规矩，
  本就该对谁都一样——动态化的是「这次这个能力怎么调」，不是把所有文字都换成变量。

## 四、还有一处**更根本**的发现（顺带报，不在本次范围）

实测 `tool_catalog` 的三个工具描述合计 1320 字符，而**同一个壳的
`tool_catalog` 工具本身即能返回完整工具面**（含 `入参` schema 与 `描述`）——
也就是说：**描述在 MCP 握手时已完整发给客户端一次，模型侧还有一份常驻**。
如果描述改为动态，还需确认两者不会打架（客户端可能缓存握手时的那份）。
这一点在动手前必须实测（不能假设客户端会重拉），推荐做法就是 1.2 的
`send_tool_list_changed` 通知 + 客户端重拉。
