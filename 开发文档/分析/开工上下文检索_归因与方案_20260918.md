## 四、方案：三条原子能力 + 一个状态机（**这是要新增的部分**）

现有 4 条是**通用检索**（切块/建库/写入/查询），但它们**不懂"坑"这个概念** ——
调用方得自己知道「去哪找、搜什么词、命中后怎么判」。这正是华哥说的
「**有状态机可以帮 Agent 省探索时间**」缺的那一层。

### 4.1 三条新原子能力（放 `项目文档支持库`，与现有 4 条同源同库）

| 能力id | 职责 | 关键参数 | 返回 |
|---|---|---|---|
| `项目文档支持库.建坑索引` | **喂料**：扫全仓权威 md → 抽坑条目 → 建/刷新索引 | `项目名`、`根目录`、`文档模式`、`重建` | `条目数`/`新增`/`更新`/`跳过`/`库文件` |
| `项目文档支持库.查开工上下文` | **取用**：给「我正要做什么」→ 返回相关坑 + 原文位置 | `项目名`、`本次任务`（自然语言）、`返回条数` | `坑列表`（症状/根因/判据/原文位置/命中分） |
| `项目文档支持库.记踩坑` | **回写**：把刚踩的坑结构化落盘（状态机入口） | `症状`、`根因`、`判据`、`原文位置`、`场景id` | `条目状态`/`落点` |

### 4.2 状态机（华哥点名要的「状态机」）

每条坑条目带**生命周期状态**，随实战演进：

```
        记踩坑（新坑产生）
              ↓
         [ 草稿 ]  ← 刚记下，还没被检索命中过
              ↓  被查开工上下文命中 ≥1 次
         [ 已用 ]  ← 已验证有用（有人靠它避开过坑）
              ↓  命中 ≥3 次且从未被推翻
         [ 已固化 ] ← 已升级为判据/门禁（坑不再可能复发）
              ↓  判据已进必经路径
         [ 已封存 ] ← 规则成立，条目只留索引（防回潮）
              ↓  前提失效（如能力已删除）
         [ 已失效 ] ← 明确标注，不再返回
```

**状态机省时间的三处**：
1. **查开工上下文** 只返回 `草稿/已用/已固化` 三态（`已失效` 不返回，避免误导）；
2. **命中计数**让「高频坑」浮到前面（排序 = 命中分 × 状态权重）；
3. **已固化**的条目只需返回一句「已由判据 X 强制，不用记」—— **省掉读原文的整段时间**。

### 4.3 数据落点（复用现有索引库，不新开事实源）

**复用** `工程缓存/运行数据/项目文档库.db`（现有 3 表：`项目登记`/`文档索引`/`块索引`），
**新增 1 表** `坑条目`（不新建库、不新建第二套检索）：

```sql
坑条目(条目id, 项目名, 场景id, 症状, 根因, 判据, 原文位置,
       状态, 命中次数, 首次命中时间, 最近命中时间, 创建时间, 更新时间)
```

### 4.4 开工时的固定动作（**一行 HTML 请求，不全量载入**）

```bash
curl -X POST http://127.0.0.1:40007/网关/调用 \
  -H 'Content-Type: application/json' -H 'X-System-Credential: <凭证>' \
  -d '{"操作":"调用能力","能力id":"项目文档支持库.查开工上下文",
       "参数":{"项目名":"系统工程平台","本次任务":"新增支持库能力并写验证场景"}}'
```

⇒ 返回 3–5 条相关坑（每条含**症状 + 判据 + 原文位置**），
**不载入 126KB 的项目说明、不载入 1065 行哲学**。

### 4.5 与「项目记忆」的边界（华哥明确：项目记忆是项目记忆）

| | 项目记忆（`任务记忆包`） | 本项目（开工上下文） |
|---|---|---|
| 内容 | 一次派发的**事实包**（路径/行号/契约字段） | **踩坑经验**（症状→根因→判据） |
| 生命周期 | 随一次派发走，用完即弃 | **长期累积 + 状态机演进** |
| 落点 | `工程缓存/任务记忆/<开工ID>.md` | `项目文档库.db` 的 `坑条目` 表 |
| 取用 | 任务信里一行提示 + 句柄 | 开工时一次 HTTP 检索 |
| 关系 | **并存**：任务记忆包给子代理「已知事实」，开工上下文给「历史坑」 | ← 不合并、不互相替代 |
