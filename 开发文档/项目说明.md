### 第 1 条 干净底座与唯一化（原第 7、9、10、11、14、17、22 条并入）

**落地记录（2026-09-15 实测）**：

- **恒假门禁（1.4 空转即杀）**：`平台控制面/发布管理` 的快照回滚校验要求 `清单.json`，现存 5 份快照只有 `摘要.json` + `核心.manifest` → 回滚判定**恒返回「快照损坏」**；处置：补真实清单或删该项，不许留恒假判定。
- **同一事实多套（1.3）**：`测试中心` 仍有 3 处同名双义表待收口（见 `未完成事项.md`）。

1.1 **干净底座优先**：遇到问题或需要决策时，第一问不是「怎么绕过」，而是「当前底座够不够干净、这套结构能不能真正解决」。能解决就按唯一链路修到底；解决不了就重构。判断标准只有两条：**结果一致、底座唯一**。（华哥 2026-09-14 裁决）

1.2 **不保留旧腿**：旧能力一旦被新实现取代，直接删除，不保留「兼容入口」「兼容壳」「旧名别名」；同一件事存在两套以上实现即视为缺陷，先收敛再继续；调用方要么走唯一新链路，要么明确失败。（华哥 2026-09-14 裁决）

1.3 **结果唯一即收口**：同一目的出现两套实现时，不看成「第二条路」，而看成本质上的**重复**——保留**最全面的那一个 + 归因用的原子能力**，其余全部蒸馏进唯一支持库；副本、克隆、旧版拷贝一律不许留。（华哥 2026-09-14·第二轮 裁决）

1.4 **空转即杀**：没有真实结果的判定项、死代码、恒真/恒空的门禁，直接删除——**没有结果的东西就不需要存在**。不许用恒绿项充当门禁，也不许因为「看着无害」而保留。（华哥 2026-09-14·第二轮 裁决）

1.5 **制品只留最新单版，旧版进归档**：制品库只维护最新版封装，**全局引用只指向新制品**，老制品移入归档库。请求与返回格式尽量固定；**非必填**字段的增删不影响旧引用（后台本来就补默认值）；**新增必填**字段用一次 HTML 多线程全量跑，看哪个请求失败就知道该修哪里，按点维修，效率最高。（华哥 2026-09-14·第二轮 裁决）

1.6 **临时脚本不留库**：探针、验收、一次性搬迁脚本一律不落在底座仓库，用完即删；仓库里出现一次性脚本按缺陷处理。底座只保留正式代码、权威文档和机器账本——“底座只保留最干净的状态”。（华哥 2026-09-14·第四轮 裁决）

1.7 **不做本地归档，旧版直接删**：成品做完本来就要上传到 GitHub，**GitHub 提交历史就是归档**；需要参考旧做法时从线上历史版本找回。因此本地**不建归档库、不写归档机制、不保留旧制品**，废弃的一律直接删除，不留第二条腿。（华哥 2026-09-14·第五轮 裁决）

### 第 2 条 分层与依赖归属（原第 12、13、16 条并入）

**落地记录（2026-09-15 实测）**：

- `运行核心/依赖防火墙.py` 的层表与 `_所在包是内部层` 未含 `平台控制面`；装配根改声明式（决策记录 0012）后必须同步登记该层，否则新纳入的包会被判成「其他层」。

2.1 **分层与归属固定**：支持库＝**最小原子能力**（连接池、句柄、重试这类底层机制全部归它，不下放到模块或业务）；模块＝组装原子能力解决一类问题；技能＝定义好的工作流；第三方与环境依赖＝**最底层的翻译层**。翻译层只翻译「我们真正用得上的原子能力」，第三方全量功能不必照搬。（华哥 2026-09-14·第二轮 裁决）

2.2 **依赖分两类，且必须本地具备**：① **第三方库**＝代码级依赖（要 `import` 的包），落在适配层提供者；② **环境依赖**＝运行级依赖（独立进程/服务/动态库/外部接口），必须有声明（版本、入口、端口、健康探针、启停、降级语义）。两类都必须「本地有」才算可用，**不允许连不上就豁免**。（华哥 2026-09-14·第二轮 裁决）

2.3 **依赖位置分两段，不新开并列顶层**：`支持库/适配层/` 一刀切成 **第三方翻译层**（要 import 的包）与 **环境依赖层**（独立进程/服务/动态库/外部接口），环境依赖段的每一项都必须带声明：版本、入口、端口、健康探针、启停、降级。不新开与 `支持库/适配层` 并列的顶层「依赖库」（那会成第二条腿）。（华哥 2026-09-14·第三轮 裁决）

2.4 **翻译器原则（内外之间只留一种形态）**：底座的一切**外部接触面**都必须经过**翻译层**，把外部形态翻译成底座统一的内部形态。两端各有一层：

- **对外一端（第三方库 / 外部系统）**：由 `支持库/适配层/` 的翻译层承担（见 2.1／2.3）—— 这是「支持库下面为什么还有一个第三方库」的答案：**它就是为了消灭外部形态的差异**，不是为了隔离而隔离；
- **对内一端（调用者 / 用户请求）**：由**网关入口的翻译层**承担 —— 用户按自己看得懂的方式传参，网关翻译成机器认识的规范形态，**实现层永远看不到用户原始形态**。

**目的（这才是重点）**：**底座内部（支持库／模块库／技能库）只需要面对唯一一种形态**，所以每个节点都干净整洁、可契约化、可验证；**调用者不需要管底座如何运行，只要按格式传参过来，后端就能成熟稳定地运行好**。用户请求**只有单一一个方式**——这就是"单一形态"在边界上的兑现。

**三条硬约束**：
① **不许新开第二条腿**：每条额外的"腿"都是一次翻译分叉，会让内部重新面对多种形态（呼应 1.2／3.1）；
② **翻译层不照搬全量**：只翻译「我们真正用得上的」那部分能力与形态（见 2.1）；
③ **翻译的重心只在边界**：外部形态的差异必须在**边界**被吃干净，不许往内部渗透 —— 实现层永远不需要判断"用户传的是中文还是英文"。

**实现口径**：翻译层**用成熟第三方实现，不自己造**（不写自研解析器）。详见《类型值的唯一形态》与「中文值形态归一化 = 网关的翻译层职责」。

（华哥 2026-09-16 定调：网关本质是翻译器；用户输入中文 → 网关翻译成通用支持的形态 → 系统认识；**代码只是一个翻译器，让机器认识**。）

### 第 3 条 失败与报错必须留痕（原第 8、15、24 条并入）

**落地记录（2026-09-15 实测）**：

- 两路子代理 503 中断：委托日志尾部仅 1 行、`git status` 工作树干净 → 判定为**探查阶段失败、零落盘**，取证后才原样重派（示范 3.1：先停手取证，不盲目重跑）。

3.1 **同一件事重复报错两次必须停下**：同一能力、同一接口、同一命令、同一现象连续两次失败或两次报错，立即停止重试，转入原理级调查 —— 先读真实日志、入参、出参、耗时和数据结构，定位根因，把根因和结论落盘到唯一权威文档，再决定修哪一层（实现 / 契约 / 装配 / 调用方）。禁止用「换个参数再试一次」「重跑一遍」「加个兜底」这类动作原地消耗 token。**华哥没有回复不是继续试错的理由，而是停手、把已知证据和待决问题写成结论的理由。**（华哥 2026-09-14 裁决）

3.2 **上游失败即明确报错，各修各的**：底座能力依赖的上游（业务项目侧服务、外部接口）坏掉时，底座**不兜底、不豁免、不降级掩盖**，一律返回明确的失败与错误码/错误说明；上游请求网关**必须带日志**，哪个坏了单独修哪一个。HTML 黑盒只验证真实返回、不涉及上游内部原理——上游侧通常只是重新调整参数的问题。（华哥 2026-09-14·第三轮 裁决）

3.3 **报错必须回填说明文档（一次命中）**：凡是「先把文档读完 → 再写代码 → 运行时报错」的情况，**都不许只改代码了事**。必须回头确认「是在哪一个位置看的说明文档」，判定那份文档**没有把具体开发规则写清楚**（缺段落、缺真实返回结构、只有结论没有可执行步骤），**先把缺失的规则补进那份文档，再修代码**。理由：同一个坑只有被写进文档，才不会犯第二次；**一次命中是核心目标，同一个问题尽量不允许重复犯第二次错**。三种常见缺口与补法：① **独立工具/脚本怎么合法调能力没写** → 补「装配与调用方式」段落（进程内必须经 `后端核心` 装配，直接 `获取能力调用器()` 会 `E未装配`）；② **真实返回结构与文档描述不符** → 补「返回结构」原文（照现场实测形状写，不许照印象写）；③ **只有结论没有步骤** → 补「命令 + 入参 + 期望返回」三段式。纪律：补文档与改代码**分开落盘、各自可验证**；文档补完必须回读，确认别人照着能一次做对。（华哥 2026-09-15·第六轮 裁决）

- `开发文档/规范/通用能力反馈接口与平台自治治理.md` 第四节原要求「自动过滤 API Key/Cookie/令牌」＝脱敏，与 9.1 冲突 → 已按 9.1 裁定：**底座原文存储、由调用方自理**；该文档已标「已变更」，实现侧改动与被摘任务同批（见 `未完成事项.md`）。

9.1 **0 加密**：能力不内嵌任何加密、假名化、脱敏、掩码逻辑（不 HMAC 主体、不白名单字段、不截断内容）。传入什么记录什么，原文存储。

9.2 **0 限制**：能力不做业务侧限制（如\"只记元数据\"\"不记内容\"\"元数据≤64字符\"）。调用者传什么就用什么。

9.3 **隐私/安全是上层业务的事**：V3 等业务端涉及隐私、风险、合规时，由**业务端主动要求并自理**（在调用前脱敏、在结果后加安全层）。底座不做任何\"为了隐私而限制\"。

9.4 **确定性优先**：同样的输入 → 同样的输出；能力行为可预期，不因环境/调用方不同而改变。

9.5 **相对安全，不做绝对安全（华哥 2026-09-16 裁决）**：底座面向**本地私有部署**（不是公网多租户服务器），因此安全是**相对安全**，不是绝对安全——**绝对安全会让能力萎缩、失去全通用性**；全通用的标准是**用户拥有绝对自主权**。底座只守一条底线：**不造成系统性破坏**（不许一击搞死宿主系统、清空整盘、杀关键系统进程）。底线之上，安全边界**由用户自由选择**：需要更严边界时，调用方**在传参时指定权限等级**（底座提供可选的收紧手段，不强制、不代替用户决策）。落地口径：① 隔离/白名单类机制一律定位为「**可选的收紧手段**」，默认不得牺牲能力；② 任何安全机制都必须在宣言与说明书里如实写明「这是相对安全」，**不许包装成绝对边界**；③ 防系统性破坏的底线护栏属**必须项**，优先级高于用户自主权。

**总纲**：底座本质是支持全部开发者的模块库，自身**不需要**隐私/安全/合规判断。底座能力**完全 0 加密、0 限制、0 业务假设**——只保证：可用、稳定、可靠、确定性。
> 例：审计账本能力只做\"记录事件+上限修剪\"，不判断该不该记、不加密主体；V3 若要求审计脱敏，在 V3 侧对传入字段先处理再调用。配置变更指纹只算改前/改后指纹并记录，不判断敏感值。

### 第 10 条 底座自我完备：缺什么补什么（原第 32、33、34、35、36 条并入）

**落地记录（2026-09-15 实测）**：

- 装配原先只认三个发现根（`支持库/模块库/技能库`），`平台控制面/` 与 `运行核心/` 全仓 **0 个 `包声明.json`** → 发布门禁/发布证据/指针/回滚/租约/作业/反馈 一批治理能力**在网关里调不到**。按 10.3「补进对应的那个库」：治理能力补在 `平台控制面`/`运行核心` 本层，装配根改**声明式**（决策记录 0012，在办）。

10.1 **先判定"是不是真的缺"**：调用方遇到的"做不到"必须归因清楚——是底座缺能力、网关未装配、契约不匹配，还是权限/路径问题。**只有确认是底座缺能力，才补进底座**。

10.2 **补成原子能力，不是补成特例**：新能力要最小、单一职责、可复用；命名与参数一眼能懂；不把业务语义塞进底座。

10.3 **补进"对应的那个库"**：能力归属按职责定位（例：`VACUUM` 压缩属 `数据库连接支持库.SQLite数据库`，因为它是对 SQLite 文件本身的原子操作，且 VACUUM **不能在事务内执行**，其余写能力都跑在事务里，调用方无法用它们完成压缩）。

10.4 **全套齐活才算补完**：能力定义（含参数/返回/错误码/行为）+ 包级入口注册 + 验证场景（正向真实调用）+ 说明书 + 按规则升包版本/重编译/摘要/依赖锁，缺一不可。

10.5 **补完必须真实验收**：走唯一网关真实调用，回报真实返回值；只写代码不算补完。

**总纲**：底座要**不断找出自己缺的原子能力，并把它补进对应的那个库**——缺的能力不是让调用方绕路或自己实现，而是成为底座里一个正规原子能力（契约、权限、场景、说明书全套）。
判定与落地口径：
> 例：`数据库连接支持库.SQLite数据库.压缩数据库`（2026-09-15 新增）——起因是运行态库删了过期行后物理空间不回收，平台只有"事务执行"而 VACUUM 不能在事务里跑；补成原子能力后，任何调用方（含 HTML 传参）都能正规压缩数据库文件。

### 第 11 条 环境与工具/架构准入判定（原第 37 条并入）

**落地记录（2026-09-15 实测）**：

- `rg` 全仓 **0.075s** vs `grep` **6.35s**（**85×**）→ **不装工具、改规则**（全仓搜索用 `rg`）。
- **装配冷启动 10.82s → 热 0.85s（12.7×）**：`环境管理器.校验环境` 原来每个包串一次解释器、且每轮真 `import` 全部第三方库（40 次共 6.95s）；改为「每提供者一次解释器 + 校验结果缓存（解释器指纹+包集合，默认 24h）」。
  **这不是"看起来快"**：同一台机、同一命令、同口径前后复量；诚实性反证也做了——塞一个不存在的模块仍返回 False 且不留缓存，`系统底座_环境校验缓存秒=0` 时关闭缓存仍逐项真校验。
- 本机**没有** `timeout`/`gtimeout` → 一律用 `python3.14 subprocess(timeout=…)`，不为此装 GNU coreutils（100MB+ 换可替代品）。
- 架构问题当场登记的执行样例：装配根硬编码 3 根 → 已登记并裁决为声明式（决策记录 0012），未用特例绕过。

11.1 **环境与工具能力的准入判定——「对比现状，是否更快、更稳定」**：
   - **缺能力先证不可替代**：能被已有能力替代的一律不装——包括「已装工具的正确用法」（如 `rg` 代替 `grep`）、标准库（如 `sqlite3`、`subprocess`）、底座能力。
   - **判定必须用数字**：装前量现状基线（耗时 / 失败率 / 步骤数），装后同口径复量；拿不出数字不许装，「感觉快」不算依据。
   - **已装未用等于没装**：工具装了、但用法规则没落到执行侧，等于没装（与第 24 条同源：文档写了却没写进入口 = 没写）。
   - **装了要能退**：新增环境依赖必须可回退、可追溯，记录「装了什么 / 为什么 / 实测多少」。
   - **环境依赖 ≠ 底座能力**：底座能力按第 32–36 条进对应的库；第三方环境依赖按第 13/16 条登记声明；两者不许混。
   - **判定范围含「不装」**：清理、收敛、改用法同样是提速手段，且往往比装工具收益大——先量「时间花在哪」，再决定装还是改。
   - **做新功能时必须先问架构（2026-09-15 华哥追加）**：写新能力/模块/技能/链路之前，先问一句「**有没有更快、更稳定的架构做法**」——不等出问题才想。至少对比「现状做法 ↔ 候选架构」两列：更少层、更少 IO、更少重复实现、失败面更小、边界更清晰；对比结论写进该包的 `说明/设计说明.md`（一两句也算数，但**必须留下**）。
   - **同一把尺**：快＝实测耗时/步骤数；稳＝失败面/可回退/边界明确。候选架构若只是"看起来更优雅"、不改变耗时与失败面，**不做**，并把「不做」也写进设计说明（不做的结论同样是结论）。
   - **架构问题当场暴露、当场登记**：若发现**现状架构本身**就是慢或不稳的根源（如全仓 97% 文件在缓存、制品堆积、同一事实三套实现、两条并行腿），按第 32–36 条补正或登记为架构级待决项，**不给它绕路、不用特例绕过**。

**总纲**：要不要给机器装一个新工具、新命令、新依赖，**唯一判据是「对比现状，是否更快、更稳定」**——不满足就不装，不因为「别人都有」「看起来方便」就装。
**实测记录（2026-09-15，本条的落地样例）**：

| 候选 | 现状基线 | 候选实测 | 结论 |
|---|---|---|---|
| 装 GNU coreutils（换 `gtimeout`） | `python3.14 subprocess(timeout=)` 已覆盖 | 无额外收益 | **不装**（100MB+ 系统依赖换可替代品） |
| 装 `fd` | `rg --files` 已覆盖（0.027s vs `find` 0.064s） | 无额外收益 | **不装** |
| 装 GNU `parallel` | 并行由子代理承担 | 无额外收益 | **不装** |
| **`rg`（本机已装，但子代理一直用 `grep`）** | `grep` 全仓 **6.35s** | `rg` 全仓 **0.075s**（**85×**）；同口径 1.8×（0.049s vs 0.087s） | **不装，改规则**：全仓搜索用 `rg`；`grep` 必须带排除 |

> 本例的教训正是本条与第 24 条要治的：**收益不在「装」，在「用」和「范围」**——全仓 158,218 个文件里 **154,395 个（97%）在 `工程缓存/`（4.9GB）**，`rg` 默认遵守忽略规则、`grep` 不遵守，差距全在这里。

### 第 12 条 审计与维修分三轮（原第 23 条并入）

12.1 **审计与维修分三轮（2026-09-15 华哥裁决，审计哲学条款）**：**第一轮只负责「找全所有问题」**；**第二轮负责「证真 + 精确定位修复落点 + 排序」**（每条给：证真命令、`文件:行号` 最小改法、影响面、是否共享文件、验证命令；并给出串行哪些、可并行哪些、开多少子代理、怎么验证）；**第三轮才是「把全部问题一次性修完」**。三条配套铁律：① **第二轮出排序时，主会话自己的工作项也要一起排进去**——子代理在忙时主会话**不必等待**，去做不冲突的事；② 维修期间**唯一约束是「不要同时改同一个文件」**，除此之外能开多少路就开多少路；③ **全部任务做完之前不跑验证**，期间只做语法合规（`py_compile`）与单文件轻检测，**等所有任务全部完成，才跑一轮测试**；发现的问题留到**下一轮**统一修，不在维修中途反复验证。

12.2 **一次性盘清、一次性全派、回来统一验收（2026-09-16 华哥裁决，12.1 的执行口径）**：第三轮的**派发本身也必须是「一次性」的**——凡是你心里已经有数的问题，就在**同一轮里全部丢出去维修**，不拆成「100 个任务分批次」。**即使其中一部分必须串行，那也只是「排队顺序」问题，不构成把后面的活扣在手里不派的理由**（你本来就知道怎么做，前置做完只是为了方便验收后面的；后面那部分依然要做，且可以现在就派出去排队）。配套三条：① **第二轮要先给「临时说法」**——每条问题的定性（实现错／场景数据错／环境未就绪／设计缺陷／越层）必须在派发前就落盘成结论，不拖着不表态；② **主会话不许「等前置」空转**——子代理在忙时，主会话做**不冲突**的工作项（补漏、写文档、补入口、修本域条目），把主会话自己的工作项一并排进同一轮；③ **维修期发现的非当前问题不打断当前轮**——先落盘，按同类批量扫描后随下一批统一收口，不在维修中途插入零散单点修复。

> **本条的直接教训（2026-09-16 实测）**：同一批债务被分四次派发（4 路 → 2 路 → 1 路 → 补派），两次派发之间主会话处于「等前置」状态；事后盘点显示，被中断时实际跑完的活远少于「一次性全派」本可达到的规模。华哥原话：「应该是发现的所有问题，然后你先给他一个临时的说法，然后一次性全部丢出去维修，然后回来再验收，而不是 100 个任务分批次。就算必须是串行的，那后面依然是要做的，你本来就知道怎么做的，只是说需要前置的弄好了，方便验收后面的。」

12.3 **子代理单任务规模：以 10 分钟为界，按「一个可独立验收的交付物」切（2026-09-17 华哥裁决，12.1/12.2 的配套粒度口径）**：派子代理时**不按「一整个债务段」派，按「一个交付物」派**——一个包、一份文档、一个门禁、一处缺陷的修复，各自一个任务。**单任务目标 10 分钟内完成；超过 15 分钟说明切得不够细，回去重切，不要硬塞。** 四条配套：① **大段债务必须拆成 N 个 ≤10 分钟的任务同时派**——这与 12.2「一次性全派」不矛盾：**全派说的是「派发时机一次到位」，不是「单个任务做大」**；② **派发前先自估时长**，估不准就先只派第一格探路，拿到真实耗时再按同一尺度切其余；③ **超时 ≠ 零产出**：子代理撞超时墙时往往已完成部分子任务，**必须先现场盘点落盘产物、逐条验收，再决定补派剩余**，不许不看现场就整批重派；④ **任务信里写清单式交付物**（一个编号一个可验收物），子代理每完成一个就能独立验收，而不是只有"全部做完"一个验收点。

> **本条的直接教训（2026-09-17 实测，全历史 262 个子代理任务统计）**：撞 `timeout` 的 **22 个任务 100% 都撞在 1800s 上限**（不是任务本身失败，是规模超出单次会话预算）；而**完成任务的中位耗时是 647s ≈ 10.8 分钟** —— 华哥说的「10 分钟以内」正是这个自然粒度。本轮正反例：同一批里最接近 10 分钟的任务（`640s`，只写一份处置方案 md）**一次过**；而把「C-7 建包 + C-12 补能力 + C-13 能力面 + C-8 出方案」**四件事塞进一个任务**的那路，跑满 1800s 超时，只完成其中两件（C-12、C-13），并把组件规范支持库停在半成品（新增 3 个实现文件、合规提取器待修）。华哥原话：「正常一个任务最好是控制在 10 分钟以内，就是子代理。你任务估计过大了。」

## 唯一调用腿（当前冻结）

```text
所有对内、对外、模块、项目、验证场景的业务能力执行
        → 调用能力(能力id, 参数)
        → 唯一能力调用服务
        → 唯一能力注册表/提供者路由
        → 受管执行单元
```

- **唯一业务执行入口**：`调用能力(能力id, 参数)`。
- **外部入口**：`POST /网关/调用`；MCP只负责把工具请求转到这个入口。
- **内部入口**：模块、项目适配层和验证器仍调用同一个唯一能力调用服务，不得直连注册表、Provider或实现目录。
- **HTTP连接器、进程内连接器、Provider生命周期管理**：只是运行核心的内部装配和资源治理，不是业务调用方可见的第二条腿；两者最终都必须回到唯一能力调用服务。
- **流式调用**：`/网关/流式`只是同一能力调用的流式传输外壳，不得复制一套能力注册、参数校验或执行语义。
- **平台控制面操作**：负责需求、权限、编译、发布和证据；其中“调用能力”操作必须转交唯一能力调用服务，不能另行执行。
- 能力搜索和契约查询只读，不属于能力执行入口。

本项目不保留同一能力的多套公开门面、测试专用执行器、浏览器自有执行语义或静默降级。发现调用路径不一致时，以本节和统一能力调用服务为准收口。

同一职责的内部实现也不得复制：相同能力必须合并为一个实现；不同能力若共享底层逻辑，应抽到唯一支持库；第三方能力只能经唯一Provider适配。当前代码中仍存在的历史包装或重复执行面，只能视为待收口债务，不得继续新增或作为新的正式入口。

# 编译与验证

```text
源码 / 契约 / 依赖
  → 统一编译器（目标依赖闭包指纹）
  → 命中缓存或生成新的不可变版本制品
  → 当前.json 选择稳定制品
  → HTML验证器启动制品并发起真实HTTP请求
  → 验证通过后才允许正式激活
```

编译器默认缓存目录为 `工程缓存/编译缓存/`，重复编译同一项目和目标且依赖内容未变化时直接命中；修改依赖后生成新的完整制品版本，旧版本保留用于回滚。可用 `--强制重新编译` 忽略缓存，使用 `--缓存根目录` 指定隔离缓存位置。

HTML验证器既可以接收显式制品目录，也可以接收编译器生成的稳定指针：

```bash
python3.14 -m 开发工具.HTML验证.验证器 --制品 <制品目录> --激活到 <制品部署目录>/当前.json
python3.14 -m 开发工具.HTML验证.验证器 --制品指针 <制品部署目录>/当前.json
```

第一条命令验证候选制品，只有验证成功才激活 `当前.json`；第二条命令只验证已经激活的稳定版本。HTML正式验证只启动 `运行入口/启动.py`，不直接读取开发源码；`--直连地址` 只用于开发诊断，不进入正式发布证据。


```bash

python3.14 -m 开发工具.HTML验证.验证器 --制品 <编译产物目录>
# 可选：显式覆盖场景级并发，范围 1 到 64；默认按 CPU 动态计算

# 服务模式：浏览器可视化验证页 http://127.0.0.1:45081/

```

开发期回归只运行本次改动对应的独立模块，不产生正式发布证据：

```bash
python3.14 -m unittest 测试中心.第一批维修.测试_HTML验证器
```

HTML 黑盒验证器单实例默认使用**动态端口**（`--端口 0`，由操作系统分配，制品句柄回收即释放端口，无固定端口占用竞态；华哥裁决 2026-09-08）；显式 `--端口` 仅用于诊断，端口冲突明确报错不静默换端口。多实例模式使用端口池 `45080-45180`，一次部署 N 个制品进程、各自独立端口、连接器按实例路由，实例间零端口竞争；发布门禁也使用动态端口 `0`，不占用固定端口，句柄回收即释放。场景之间默认按 CPU 动态并发（范围 1 到 64，本机 32 核默认 32），`--并发` 可显式覆盖；场景内前置→目标→清理仍严格串行，非线程安全外部提供者按资源键独占。验证器只认编译产物的真实 HTTP 状态码 + 返回值（成功/值/错误码/错误说明/请求id/耗时），不读取源码内部。验收以 HTML 高并发批量验证为唯一全量（unittest 只做开发期定向小单元冒烟，禁止全量）。

### 2. 搜索和调用能力

```bash
python3.14 开发工具/能力搜索/能力搜索器.py --能力 读取文件
```

统一调用铁律（华哥裁决 2026-08-30）：**所有能力无论对外暴露，还是被模块、能力或项目调用，调用方都只允许使用同一个 `调用能力(能力id, 参数)` 公开接口。** 进程内连接器与 HTTP 连接器只在装配层区分，调用方不得感知来源；禁止另开第二入口、旁路或直连内部实现。能力搜索和契约查询是只读发现接口，不属于能力执行入口。

HTTP 能力入口：

```text
GET  /能力/搜索
GET  /能力/契约/{能力id}
POST /网关/调用
```

请求和返回字段以 `公共契约/HTTP路由契约.json`、包内 `能力契约/` 和统一结果为准。

浏览器宿主只提供静态页面；页面执行转发到配置的统一 `POST /网关/调用`，自身不提供业务执行 POST。受管 HTTP Provider 使用内部 `POST /内部/能力调用`，轻代码编辑器使用受标记保护的 `POST /内部/工程请求`，二者都不是业务能力入口。流式服务使用 `/网关/流式`，生产默认要求凭证并记录有限审计摘要。

公开能力、跨模块、跨进程和跨项目调用，正式验收以真实 HTTP 黑盒请求为主：请求没有返回、返回结构或字段类型漂移、错误码不符合预期、业务值不正确，均直接判为失败。只保留少量无法通过公开 HTTP 合理验证的纯逻辑和协议底层测试，不为每个公开能力复制一套进程内单测。

## 选择支持库还是模块库

- 原子能力、单一第三方/系统边界、参数和错误转换：放支持库。
- 多个公开能力组合成业务流程：放模块库。
- 给 Agent 消费的可复用工作流（技能包的结构校验 / 受控执行 / 索引扫描）：放技能库。技能库是本平台的**第三根正式包根**，与支持库、模块库平级，包声明类型同为「支持库」，不另开 HTTP 入口，走底座唯一执行入口。
- 项目配置、权限、路径、版本和密钥引用：放项目适配层。
- 装配、调用、租约、超时、取消、释放和证据：由运行核心统一管理。
- 正式调用方只能经过统一 `调用能力(能力id, 参数)` 接口；包级公开入口只负责能力注册与装配，不作为调用方的第二执行入口。调用方不能导入 `实现/`、Provider 或第三方库。

### 支持库与第三方引用库的分层（华哥裁决 2026-08-27）

- **支持库 = 唯一的调用能力**：对外暴露统一中文能力接口，面向业务调用方；只做参数校验、编排和结果转换，不直接 import 第三方库。
- **第三方引用库（提供者） = 封装任何第三方**：只负责把第三方库/系统/外部协议汉化成稳定接口；不对外暴露，只受支持库门面调用。
- **唯一归属约束**：同一业务能力只允许一个正式公开owner；第三方引用库只能作为受管Provider存在，不得再次登记为公开owner或对外提供第二门面。
- **落地约束**：第三方引用库在 `支持库/适配层/` 下（受管Provider），或在 `支持库/后端/` 下以 `*提供者` 命名且不对外作为公开owner；支持库和模块只保存能力id与契约版本，经唯一能力调用服务执行。

## 当前不可用或不应使用

- `模块库/_模板`：仅模板，不是正式能力。
- `工程缓存/`：仅生成物、日志、摘要、受管制品和 Provider 环境；不作为源码导入路径。
- `开发文档/参考资料/外部源码研究/`：只读研究资料，不是正式包、运行时或能力目录。
- 直接调用包内实现、复制第二套网关、把流式 `调用id` 当资源句柄：均不受支持。

## 资源与项目适配

- 资源句柄是不透明查询键，由网关登记、授权、关闭并记录回收结果；不传递第三方对象、线程、连接或模块内部对象。
- 文件、目录、进程、临时目录和句柄都必须先登记，终态统一释放；原子写入使用临时文件、同步和替换，冲突返回版本冲突，不覆盖他人结果。
- 项目适配层只负责项目声明、模块绑定、版本/权限/路径和密钥引用；配置按默认值、项目文件、环境变量、启动参数、请求覆盖的顺序合并，敏感值不得写日志。
- 受管 Provider 缺失、版本不符、超时、取消、输出超限或资源未释放时，能力返回明确不可用/失败结果，不把“声明存在”当作可用。
- 资源释放统一返回三态：`已结束并已释放`、`结束请求已发出但未收敛`、`未找到且已幂等`。未收敛时保留权威资源账本和重试入口，不失效句柄、不启动替代资源，也不伪装成功；只有确认进程/线程结束并完成管道、临时目录等核对后，才删除记录并失效句柄。

## 记忆与项目状态边界

- **记忆支持库独立于大语言模型**：记忆是连接SQLite记忆库的独立能力；模型连接器只作为向量生成的上游能力，不改变记忆支持库的owner归属。
- 当前正式记忆包：`支持库/后端/记忆支持库/`，能力以其`包声明.json`、`能力定义.json`、`能力契约/参数契约.json`和正式索引为准；当前登记写入、追加、完成、删除、搜索、最近、列出、生成标识8项能力，不把未登记的“计划记忆”当成当前能力。
- **状态机不等于状态库**：`公共契约/句柄体系.py`及运行核心负责句柄、租约、资源生命周期和回收；项目协作状态、验证证据、文件账本等是运行治理数据，不能因为都使用SQLite或状态字段就合并为同一个记忆/状态能力。
- 外部项目普通记忆读写已核实为底座客户端薄壳；项目自身状态 SQLite 属于各自治理事实源，不作为普通记忆第二实现。
- 记忆能力若调用模型生成向量，调用方仍必须经统一`调用能力(能力id, 参数)`；禁止记忆实现直接导入模型连接器形成第二条执行路径。能力声明中的副作用必须如实区分读操作和写操作。

## 传参类型：句柄与 id（权威类型，防越过）

> 2026-08-26 华哥裁决，唯一权威类型约定。所有能力一次传参必须遵循，防止直接传 id 绕过能力进程。

### 1. 句柄 = 万能参数（一次传参必须用）

- **句柄指向「模块/支持库的某一个能力的进程/实例」**，由连接器创建返回。
- 多个连接 = 多个句柄，各自精准命中对应进程（如同时连 10 个库 = 10 个句柄）。
- 调用形式：`能力(句柄, 资源参数…)` —— 句柄是第一参数，定位能力进程。
- 句柄由 `公共契约/句柄体系.py` 管理：生成值为 1～999999 的整数；字符串仅兼容固定六位数字格式。状态机负责创建/有效/失效、租约、超时自动释放和显式释放（幂等）。

### 1.5 句柄超时（华哥口径，权威）

- **沉默超时**：句柄 N 秒无人调用 → 状态机主动回收并终止进程（会话存储/连接型）；不是常驻。
- **持续使用重置**：一直有人调用，每次调用都重置超时倒计时（永不静默过期）。
- **模块主动申报**：每个会启动句柄的支持库/模块必须申报「句柄超时秒」（它自身需要多久），写在 `包声明.json` 的 `句柄超时秒` 字段。
  - 常驻型（会话存储/模型连接）：申报大值（默认 1800 秒 = 30 分钟）。
  - 短暂型（word 读取、重排、删除守卫、模板渲染等）：申报小值（如 60 秒），用完自动过期。
  - **不申报 → 默认 30 分钟（1800 秒）**。
- **手动释放**：用户随时可调 `释放句柄` 立即终止（幂等）。
- **超时语义**：沉默到期 = 状态机主动退出进程（不是进程暴毙；暴毙是另一回事）。

### 2. id = 数据库主键（只作二次传参）

- **id 是句柄内的资源定位**（如 会话id、输入id、表主键），在句柄已指向能力进程后使用。
- **一次传参禁止直接传 id 绕过句柄**：直接传 id 等于跳过能力进程的治理/租约/生命周期，直连内部，视为多条腿，禁止。
- 正确：`执行SQL(句柄, sql语句)`、`会话存储.追加消息(句柄, 会话id, …)`。
- 错误：不拿句柄，直接 `执行SQL(连接id, …)` 绕进数据库内部。

### 3. 判定规则

| 场景 | 一次传参 | 二次传参 |
|---|---|---|
| 首次接触某能力实例 | 必须：连接器返回句柄 | — |
| 已持句柄、定位具体资源 | 句柄（第一参数） | id（资源定位） |
| 直接传 id 不传句柄 | ❌ 禁止（绕过能力进程） | — |

### 4. 落地范围

- 新增连接器型能力（会话存储、模型连接器、数据库等）一律：连接器返回句柄 → 操作持句柄 + 资源 id。
- 能力契约中的资源句柄统一使用整数型；句柄由句柄体系登记、授权、租约、释放和失效，不能把第三方对象或内部连接直接作为参数传递。
- 违反判定的调用直接返回 `句柄失效` 或 `参数不合法`，不降级执行。
- **资源回收由状态机统一维护（华哥口径 2026-08-26）**：会启动句柄的模块/支持库，启动时调 `句柄体系.登记资源()` 把资源（PID/端口/连接/临时文件）绑定到句柄；句柄失效（超时/释放/进程暴毙）时，状态机自动 `核查回收()` 所有绑定资源——杀进程树（killpg）、清端口、删文件、关连接，不旁路拼独立回收能力。连接器本身不再各自实现回收逻辑。

## 开发运维避坑规则（2026-09-05 实测沉淀）

以下规则是多次摸索/踩坑后确认的，供 Agent 开发时直接遵循，不必重新探索：

### 1. 包声明铁律（全平台装配/发现的硬约束）

- 任何 `包声明.json` 的 `类型` 字段**只能写** `模块`/`基础模块`/`功能模块`/`支持库` 之一；
  写成 `Provider` 等会让发现器崩（`ValueError: 包类型不合法`）。适配层 `*提供者` 包的类型是 `支持库`。
- 任何 `包声明.json` 的 `依赖` 字段**必须是对象数组** `[{"能力":"...","版本":">=1.0.0"}]`；
  写成字符串数组 `["包id"]` 会让依赖解析崩（`AttributeError: 'str' object has no attribute 'get'`）。
- 新增能力必须带完整参数契约；半成品（只有 能力id/名称 无参数）会破坏能力注册。
- **正式根清单是唯一事实源**：`公共契约/正式根.py` 的 `正式根名表`（支持库 / 模块库 / 技能库 / 平台控制面 / 运行核心）
  是「哪些顶层目录参与发现、统计、依赖锁定」的唯一出处；装配发现器、正式包索引、完整性摘要、依赖锁定一律读它，
  **禁止在各自代码里再硬编码根列表**。新增一个正式层只改这一处；根目录里**含 `包声明.json` 才参与**（空根自动跳过）。
  包类型口径：`模块库`＝模块，其余正式根＝支持库（`技能库`/`平台控制面`/`运行核心` 同此，单独成根只是目录上与支持库平级）。
  落点：`公共契约/正式根.py`、`运行核心/加载器/包发现/发现器.py:发现全部`（声明式，`额外根目录表=None` 时自动推导）。

### 2. Python 运行环境

- 平台正式命令统一 `python3.14`（homebrew，`python3.14`）。
- **跑平台命令前必须 `unset PYTHONPATH`**：Hermes 会话的 PYTHONPATH 会污染，
  导致 import 到 hermes venv 3.11 的包（pydantic_core/langsmith 等）报错。
- bash 不认中文变量名：`中文变量=值 命令` 会失败（"not a valid identifier"）；
  传中文环境变量用 `env '变量名=值' 命令`。
- `python3.14 -m py_compile` 检查语法；中文模块名测试必须用 `python3.14 -m unittest 测试中心.模块路径`，
  unittest discover 不认中文文件名。

### 3. 新增模块/支持库的标准流程

步骤 1：先落盘开发文档（`开发文档/临时文档/NN_*.md`）说明落点与契约。
步骤 2：参照现有同类包（如 `模块库/媒体转写`、`支持库/后端/转写支持库`）复制配套文件结构：
   `包声明.json`/`能力契约/参数契约.json`/`依赖契约/`/`权限契约/`/`配置契约/`/`能力数据/`/`说明/`/`验证场景引用.json`/`验证场景/`/`能力定义.json`/`实现/`/`__init__.py`。
步骤 3：类型名用正式口径：`文本型`/`整型`/`双精度数型`/`字典型`/`列表型`/`逻辑型`（不是 `文本`/`整数`/`字典`）；返回统一 `结果型`。

**类型值的唯一形态（2026-09-16 补，华哥指出）**

类型契约**分层**，必须分清，否则左右漂移：

| 层 | 写在哪 | 形态 |
|---|---|---|
| **类型名** | 契约的 `"类型"` 字段 | **中文正式名**（`公共契约/基础类型/类型表.py` 的 16 个）；短名（`文本`/`整数`）一律失败 |
| **类型的值**（代码里） | 正式 Python 代码 | **中文常量**：逻辑型一律用 `真`/`假`（`from 公共契约.基础类型.逻辑类型 import 真, 假`）；数值/文本等仍用 Python 原生字面量（`42`、`"…"`） |
| **类型的值**（JSON 里） | 参数 / 返回 / JSON 正文 | **JSON 原生形态**（不是中文）：`true`/`false`、`42`、`"…"` |

**逐类型值形态表（唯一口径）**

| 正式类型名 | JSON 里的值形态（括号内为代码里的等价物） | 反例（必须被拒） |
|---|---|---|
| 逻辑型 | `true` / `false`（Python `True` / `False`） | `"真"`、`"假"`、`"true"`、`1`、`0` → `参数不合法` |
| 文本型 | 字符串 `"…"` | 数字、`null` |
| 整数型 / 长整数型 | 整数 | 小数、字符串 `"42"` |
| 单精度数型 / 双精度数型 | 数 | 字符串 |
| 列表型 | 数组 | 字典型 |
| 字典型 | 对象 | 列表型 |
| 空值型 | `null` | 空字符串 |
| 结果型 | 信封 `{成功, 值, 错误码, 错误说明}` | 裸值 |
| 字节集型 | 冻结表示（`{"类型": "字节集型", "base64": "…"}`） | 裸 bytes |

**逻辑型的三层口径（唯一）**

| 层 | 怎么写 | 说明 |
|---|---|---|
| 文档 / 说明书 | `真` / `假` | 人读表述（如"传 `允许危险路径=真` 可跳过护栏"） |
| **正式代码** | `真` / `假` | **从 `公共契约.基础类型.逻辑类型` 导入的中文常量**；**禁止在正式代码里散写 `True`/`False`**（这就是英文漂移的起点） |
| JSON 契约 / HTTP 传输 | `true` / `false` | JSON 标准（JSON 无法表达中文）；调用方**必须传 `true`**，传字符串 `"真"` → `参数不合法`（实测） |

边界转换由 `逻辑类型.转JSON值` / `由JSON值` **显式**承担，不做隐式转换。迁移策略：**新代码一律用 `真`/`假`，存量代码渐进替换**（全仓 `True`/`False` 数量大，不要求一次性改完，但不许新增）。

**为什么不能让两边都行**：一旦同时接受 `true` 与 `"真"`，等于把"值的类型"变成两套（同一字段两种合法形态），类型校验退化为字符串猜测，最终所有类型的边界都会松动——**这就是"左右漂移"的起点**。只认一种形态，不认的明确失败。
步骤 4：`能力数据/能力搜索数据.json` 参数必须与契约一致（有对称门禁检查）。
步骤 5：完整性摘要用官方工具生成：`支持库/后端/组件规范支持库` 的 `生成完整性摘要`，不手写。
步骤 6：测试放 `测试中心/模块库/测试_XX.py`，用 unittest。若并发线有半成品包阻断全树装配，
   测试可改手动装配（只注册本模块依赖的包到能力注册表 + `注册能力调用器`），不依赖 `后端核心.启动()` 全树。

### 4. 模块组合支持库：调用器 vs HTTP连接器 两套模式

- **模块库 有两种调用底层的方式**，新增模块前先看同类：
  - 旧模式（媒体转写/媒体处理）：`设置HTTP连接器(HTTP连接器(...))` 注入，`_调用支持库` 走连接器。
  - 新模式（知识检索/直播逐字稿，官方模板生成器默认）：直接 `获取能力调用器().调用能力(能力id, 参数)`，
    运行核心装配时注入，无需手动设连接器。
- 能力注册表 + `注册能力调用器(唯一能力调用服务(注册表))` 是进程内测试/调用的标准装配。

### 5. 测试与验证节奏

- 小改只跑定向 unittest；同批改动跑受影响波次；阶段收口才全量；发布才跑门禁。
- 全树装配测试（`后端核心.启动()`）会扫 `支持库/` + `模块库/` + `技能库/` 全部包声明，
  **任何并发线的半成品包都会让它失败**——这是环境问题不是你的代码问题，用手动装配规避并记录。
- 能力搜索器 `python3.14 开发工具/能力搜索/能力搜索器.py --能力 <词>` 可确认能力注册与契约。
- 正式索引验证：`开发工具/项目编译/正式包索引.py` 的 `构建索引`/`能力所有者表` 查 owner 唯一与冲突。

### 6. HTTP 网关调用（唯一入口）

- 唯一对外端口 **40007**，唯一执行入口 `POST /网关/调用`，body `{"操作":"调用能力","能力id":"...","参数":{...}}`。
- 凭证走请求头 `X-System-Credential: <值>` 或 `Authorization: Bearer <值>`；**凭证必须纯 ASCII**（中文经 HTTP 头损坏 → 401）。
- 网关严格类型校验：`超时秒` 等双精度参数必须传 `30.0` 不是 `30`；类型不符返回 `参数不合法`。
  校验按**平台正式类型表**（`公共契约/基础类型/类型表.py`）**等宽执行**，只在网关**唯一校验点**做（`运行核心/统一网关/网关核心.py::网关核心._能力参数错误`），
  不在各能力里重复写；参数声明了不认识的类型时 fail-closed 报 `参数不合法`，不再静默放行。
- 健康检查 `GET /健康` 也需凭证头。
- **后台任务三操作**：`任务提交 / 任务查询 / 任务取消`（权限位「任务」）。**正式能力全部可作为后台任务提交**——数量按上面「唯一权威口径表」的运行时装配行取值（2026-09-17 00:04 实测 **648**；旧文写的 549、625 **都已过期**，该数随并发建包变化，**引用前重跑取证命令**），每个任务在独立进程里跑，客户端断线与网关重启都不改任务账本。长任务（>10 分钟）一律走这条路，不要用单次同步 `调用能力` 硬扛。
  - `任务提交`：`{"操作":"任务提交","能力id":"<能力id>","参数":{<能力自身入参>},"超时秒":<秒>}` → `值 = {"任务id":"…","状态":"运行中"}`。能力不存在/参数不合契约**在提交前**就被拒（`能力不存在` / `参数不合法`+具体参数名），不会产生一个生下来就失败的任务。
  - `任务查询`：`{"操作":"任务查询","参数":{"任务id":"…"}}` → `值` 含 `任务id/状态/结果/错误码/错误说明`。状态取值 `等待中 / 运行中 / 成功 / 失败 / 已取消 / 超时 / 崩溃`。失败任务的原错误码/说明**原样回带**。
  - `任务取消`：`{"操作":"任务取消","参数":{"任务id":"…"}}` → 终止完整工作进程组并确认退出。
  - 任务账本落 `工程缓存/任务状态/任务.jsonl`（已被 `.gitignore` 的 `工程缓存/` 覆盖，不进仓库；可用环境变量 `系统库任务目录` 改址）。
  - **边界**：任务 `超时秒` 上限 = 网关 `请求超时秒`（当前 1800 秒 = 30 分钟）；超过 30 分钟的任务需调大网关配置或给任务单独设上限。
  - **装配点**：`运行核心/任务调度/任务接入.py::构造任务系统`，由 `运行核心/启动运行核心网关.py` 在装配后接线并 `atexit` 关闭；启动日志会打印 `任务系统接入成功: N 个能力可提交为任务`。
- **SSE 流式调用**：`POST /网关/流式`（唯一 SSE 出口，`能力id` 固定为 `大语言模型支持库.模型连接器.生成对话`），body `{"能力id":"…","请求id":…,"参数":{…}}`，`参数` 支持 `句柄 / 消息列表 / 流式输出=true / 系统提示词 / 温度 / 最大令牌数 / 工具 / 响应格式 / 附加请求头`。
  - **生成参数不再被丢弃**：`温度 / 最大令牌数 / 工具 / 响应格式` 与非流式 `生成对话` **同名同义同校验**，按协议映射到上游——`chat_completions` → `temperature / max_tokens / tools / response_format`；`codex_responses` → `temperature / max_output_tokens / tools / text.format`。**不传即不下发**（行为与不支持的旧版逐字节一致）。
  - 三层通路：`运行核心/统一网关/本地网关.py`（HTTP 转交）→ `模型连接器.流式生成对话`（校验）→ `模型HTTP提供者.流式调用对话`（映射）。类型非法在连接器层即拒，回 `参数不合法` 流式错误事件，不发起上游请求。

## 网关常驻与运维（业务执行网关 40007）

40007 是唯一对外业务执行网关（`POST /网关/调用`），由 launchd 常驻管理（配置文件 `~/Library/LaunchAgents/com.huashi.gateway-40007.plist`）。

### 常驻配置（LaunchAgent）

```text

运行入口：运行核心/启动运行核心网关.py
```

> **⚠️ macOS 26.5 实测（2026-09-05）**：本机 launchd 的 KeepAlive 自动重启与 RunAtLoad 中途触发**均不可靠**
> （SIGKILL 网关后等 2 分钟不会自动拉起；`<true/>` 和 `{SuccessfulExit:false}` 两种写法都试过）。

> 因此网关崩溃后需要手动 kickstart，或加外部守护（每 30 秒探活 40007，挂了就 kickstart）。

### 启停与重启命令（macOS 26 实测有效）

```bash

launchctl kickstart -k gui/$(id -u)/com.huashi.gateway-40007

# 完全重新加载（plist 改动后）：bootout + bootstrap
launchctl bootout   gui/$(id -u)/com.huashi.gateway-40007
launchctl bootstrap gui/$(id -u) ~/Library/LaunchAgents/com.huashi.gateway-40007.plist

# 查看状态（第二列 PID，0=正常退出码，非 0=上次异常）

# 服务详情（runs/state/环境变量核对）
launchctl print gui/$(id -u)/com.huashi.gateway-40007

# 看日志
tail -50 /tmp/网关40007.log /tmp/网关40007.err
```

> **不要用 `launchctl load/unload`**（旧命令在 macOS 26 报 "Load failed: 5: Input/output error"）；
> 用 bootout/bootstrap/kickstart 三件套。

### 端口唯一性 ⚠️ 多会话冲突警告

40007 是唯一对外业务执行网关端口，**全机只能有一个实例监听**。多 Agent 会话并发开发时：
- 其他会话若把 plist 的 WorkingDirectory 改成自己的 `系统工程平台-live-*` 副本再起 40007，
  会让 launchd 网关装配的是副本能力集（缺正式目录新增能力），**排查时先查 `lsof -p <网关PID> | grep cwd` 确认工作目录**。
- 网关报 "端口占用或监听地址不可用" 而 `lsof -iTCP:40007` 为空时 = 有另一会话/进程刚释放端口或正在抢，
  用 `netstat -an | grep 40007` + `ps -eo pid,ppid,command | grep 启动运行核心网关` 全查。
- 改 plist 前先备份：`cp xxx.plist xxx.plist.bak_$(date +%Y%m%d_%H%M%S)`；改后必须 bootout+bootstrap+kickstart 才生效。

> 规则：**每个入口只留一种正确用法**；踩过的坑写在这里，避免重复踩。新增条目请附「现象 → 根因 → 正确用法」。

### 1. 重算完整性摘要

```python
import json
from pathlib import Path
from 支持库.后端.组件规范支持库 import 生成完整性摘要, 校验完整性摘要

目录 = Path("支持库/后端/文件系统支持库")
声明 = json.loads((目录 / "包声明.json").read_text(encoding="utf-8"))
新 = 生成完整性摘要(
    目录,
    包id=声明.get("包id") or 声明.get("提供者id") or 目录.name,
    版本=声明.get("版本", "1.0.0"),
)
(目录 / "完整性摘要.json").write_text(
    json.dumps(新, ensure_ascii=False, indent=2) + "\n", encoding="utf-8"
)
好, 问题 = 校验完整性摘要(目录)      # 期望 (True, [])
```

- **坑**：`生成完整性摘要` 是**关键字参数**入口（`目录, *, 包id, 版本`）。位置传参 → `TypeError: missing 2 required keyword-only arguments`；**更危险的是**：脚本报错但摘要没重算，带病提交后 `依赖生命周期审计` 才报「摘要漂移」。
- **坑**：模块**没有** `更新完整性摘要` 这个名字（`ImportError`）；生成器返回值就是完整摘要结构，直接按原排版（`indent=2` + `ensure_ascii=False` + 尾换行）写回即可。
- **纪律（已工具化，别靠记性）**：改过任何包内文件后，直接跑
  ```bash
  python3.14 -m 开发工具.全量重算摘要 --只报     # 先看有哪些漂移
  python3.14 -m 开发工具.全量重算摘要            # 再重算（扫遍全部正式根，含聚合父包）
  ```
  跑完复核应为 `全部闭合：无可重算项`。**不要手写「只算我改过的那几个包」的脚本** —— 那正是本仓反复漂移的原因。
- **纪律**：需要人工读数时，**必须**贴 `校验完整性摘要` 的 `(True, [])` 证据，不能只看「脚本没报错」。
- **坑（用「模拟平台」跑破坏性自检，会删掉本机真实环境）**：做平台分支的反向验证时，若把平台判定改成假的（`平台适配.是Windows → True` 或 `sys.platform="win32"`）**再真跑装配**，装配会按假判定认为「本机受管环境与当前平台不符」→ **删掉 `工程缓存/提供者运行环境/` 下有效的提供者 venv**（实测删掉了 `转写`、`MLXWhisper提供者` 两个），装配随即从「通过」变「故障」。
  - 后果可恢复（用官方入口重建 + 逐个校验解释器可导入），但会白烧时间，且**中途状态难以察觉**。
  - **防法（已实现于 `开发工具/环境自检.py`）**：平台判定与实际解释器布局矛盾时，**拒绝执行真实装配**（fail-closed，并写明「按错误平台跑会删掉本机受管环境」）。
  - **通用纪律**：任何「模拟平台/模拟环境」的测试，**不得让它触达真实的写/删路径**；要验平台分支，用「能力探测函数 + 桩」，不要「改平台判定后真跑全套」。

- **坑（批量改文件的「半成品」）**：跨平台收口是**批量替换**（形如把本地 `_终止进程组` 换成收口层调用），批量替换最容易留下两类半成品：
  1. **删了定义、留了调用** → 运行时 `NameError`（实测：`支持库/适配层/LibreOffice提供者/实现/文档转换.py` 被删掉 `_终止进程组` 后，`关闭()` 与超时路径仍调用它，`测试_LibreOffice受管池` 报 `NameError`）；
  2. **调了未导入的函数** → 同样 `NameError`，且 `py_compile` 与 `import` 都发现不了（实测：`开发工具/HTML验证/制品事实.py` 的 `_扫描制品能力`）。
  **自检口径**（已可脚本化）：用 AST 收集每个模块的定义/导入名，再找「以下划线开头、被调用、但本模块既没定义也没导入」的名字；再对改过的方法逐个**跑真实路径测试**，不能只做 `grep` + `py_compile`。

- **坑（本仓已踩两次）**：**改子包必须级联重算父聚合包**。父包的 `完整性摘要.json` 登记了**子包里的每一个文件**，所以「只算改过的那几个包」会漏掉父包 → 父包报 `文件摘要不一致: 子包/xxx.py`。仓库现有 **10 个聚合父包**（如 `支持库/后端/系统核心支持库`、`支持库/后端/大语言模型支持库`、`支持库/后端/文件系统支持库`）。
  自检口径：改完先跑一次全仓闭合统计（`支持库`+`模块库`+`技能库` 下 `rglob("完整性摘要.json")`，逐个 `校验完整性摘要`），**期望 `不闭合 0/121`**，而不是只看自己改过的那几个。

### 4. 跨平台收口层（唯一允许出现平台判断的地方）

```
公共契约/运行时/平台适配.py : 当前平台() / 是Windows() / 是POSIX() / 子进程组启动标志()
                              / 虚拟环境解释器路径() / 要求POSIX能力(名) / 内存峰值原始单位() / 句柄枚举目录表()
公共契约/运行时/进程终止.py : 进程存活() / 终止进程组() / 强制结束子进程() / 进程组号()
                              / 按组号探活() / 按组号终止()
```

- **纪律**：**调用点不许写平台判断**（`sys.platform` / `os.name` / `if 是Windows()`）；调用点也不该知道自己跑在哪个平台。若某处「必须加平台判断才能改通」→ 说明收口层接口不够，**补收口层，不许就地分叉**。
- **坑**：`os.getpgid(pid)` 在**组长被 `wait()` 回收后必失败**，但 `os.killpg(组号, 0)` 仍可用 → 「组长正常退出、同组子孙仍在」场景**必须用** `按组号探活/按组号终止`。
- **坑**：`强制结束子进程(裸 int)` 内部会 `waitpid` 回收，导致 `Popen.returncode` 退化为 `0` → **有句柄就传句柄**。
- **坑**：句柄判定**不要**写 `isinstance(进程, subprocess.Popen)`（收口层内部已改用鸭子类型）—— 在 `subprocess.Popen` 被打桩（`autospec`）时，`isinstance` 第二参不是类型会抛 `TypeError`，把收口层打崩、波及所有调用方。
