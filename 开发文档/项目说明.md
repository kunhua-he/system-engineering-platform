## 三、冷启动定义

全新 Python 进程、清空项目源码 `PYTHONPATH`、无测试预注册、无历史全局单例、只使用已安装制品与声明配置：
装配→注册→调用全链路成立。任何经 `sys.path` 拼接、包 `__path__`、源码目录、测试预注册、直接导入 `实现/` 或全局状态残留跑通的链路均不算完成。

## 四、幂等定义

同一包 id、版本、契约摘要、实现摘要完全一致可重放（重复装配结果一致）；任一不同必须冲突失败且不留半装配状态。

## 五、成功定义

能力确实经过生产注册表调用并返回统一结果+完整调用证据（请求id、模块版本、能力id、支持库包id、提供者版本、制品摘要、成功/失败、资源释放结论）。
仅导入、仅目录存在、直接调用实现、测试注入调用器均不算成功。

## 七、对外开发接入（S0.2 更新）

平台面向**所有软件开发场景**（桌面程序、Web 服务、业务系统、自动化工具、媒体处理、数据处理、智能代理 等）。核心是通用基础能力网关和可组合的支持库/模块库；智能代理 开发只是其中一个使用板块，不是平台边界。平台整体定位类似“易语言式的基础功能底座”：开发者只需要按统一契约组合能力，不需要重复理解和维护底层第三方库、系统 API、模型或原生扩展。

```text
         HTTP 能力网关（核心底座）
  搜索能力   查看契约   执行能力
    │          │          │
    ▼          ▼          ▼
  调用方：智能代理 · 业务程序 · 任何语言
```

网关之上三种用法：

```text
      HTTP 网关
      ┌─┬─┬─┐
      ▼ ▼ ▼
  MCP 适配  本地部署  直接 HTTP
  （可选）  （同一网关）  （curl/任意语言）
```

### 7.1 HTTP 能力网关 = 核心底座

- 纯 HTTP 接口，任何语言、任何工具可直接调用，不依赖 MCP 协议；
- 提供三件事：搜索能力、查看契约（使用声明）、执行能力；
- 执行返回统一结果（成功/值/错误码/错误说明）+ 完整证据链；
- 内部只走能力注册表与唯一能力调用器，禁止另起执行路径。

### 7.2 MCP = 网关上的可选适配层

- MCP 不再承载平台逻辑，只是把网关的"搜索/查看/执行"包装成 agent 工具；
- 仅在 agent 需要"强制注入工具"时使用，简化为一层薄映射；
- 无 agent 场景可完全不用 MCP。

### 7.3 本地部署

- 支持库/模块库可以复制到本地，但跨支持库、跨模块、跨执行单元的调用仍然经过本地 HTTP 网关；
- 本地网关只是运行在本机，不代表可以绕过网关直接导入其他包的实现；
- 同一个子项内部的私有函数、热循环和紧密协作对象可以直接调用；跨边界必须使用统一 HTTP 契约。

### 7.4 本地/云端调用语义一致

- 网关可运行在本机或云端；本地网关和远程网关都遵守同一份 HTTP 契约；
- 部署位置不同，不能改变跨支持库、跨模块必须经过网关的边界；
- 底层都是同一套装配与调用事实，调用方只看请求参数和返回参数。

### 7.5 开发工具链属性

- 面向开发过程（智能代理 开发、业务项目集成），不是单次调用；
- 搜索→查看契约→执行→结果与证据链，形成开发闭环。

### 7.6 单 HTTP 网关 + 多 提供者 插件运行时（架构决策）

平台采用**一个逻辑 HTTP 能力网关**，不为支持库、模块、模型、GPU、浏览器或第三方库分别建立对外网关。网关只是通信面和薄路由层，不拥有业务逻辑、提供者 内部对象或资源生命周期；提供者 的发现、装配、启动、健康检查、租约、缓存、排空、停止和崩溃回收由运行核心的 提供者 监督器/执行协调器负责。

```text
任意语言调用方
        │ HTTP / JSON / 制品引用
        ▼
8866 HTTP 能力网关（唯一通信入口）
        │
        ├─ HTTP 解析、请求 id、基础契约/大小校验
        ├─ 能力 id/版本路由、结果透传、流式转发
        └─ 不持有 提供者 对象，不负责 提供者 资源释放
              │
              ▼
运行核心/提供者 监督器（控制面，不对业务暴露）
        ├─ 选择/启动/健康/租约/缓存/排空/停止/崩溃回收
        └─ HTTP loopback（内部端口，不对外暴露）
              │
              ├─ 纯标准库 提供者（可按需进程内或独立进程）
              ├─ 不同语言/运行时的原生提供者
              ├─ GPU/ML 提供者
              ├─ 浏览器/WebView 提供者
              └─ 动态库/FFmpeg/数据库/外部协议 提供者
                       │
                       ▼
              受管第三方库、系统 API、设备或外部服务
```

#### 提供者 插件的统一边界

任何语言都可以成为 提供者，但必须实现同一份 HTTP 能力契约，而不是把任意代码直接塞进平台主进程。每个 提供者 至少声明：

- `provider_id`、版本、契约版本、能力 id 列表；
- 启动入口、健康检查、优雅停止、排空和崩溃重启策略；
- 输入/输出 schema、错误码、可重试、超时、取消和幂等语义；
- 最大请求体、并发、队列、内存、GPU、文件、临时目录和进程预算；
- 外部依赖、模型/驱动版本、权限范围和配置引用；
- 资源创建者、持有者、转移者、成功释放和异常释放责任；
- 证据字段：请求 id、能力 id、提供者 版本、制品摘要、退出码、释放结论。

网关与执行协调器/提供者之间只传统一请求/响应；调用方不需要知道提供者是什么语言、什么库或什么进程。跨支持库、跨模块、跨执行单元的调用也必须回到这条 HTTP 链路，不能通过语言 import、共享全局变量或裸指针旁路连接：

```text
请求：request_id + capability_id + contract_version
    + arguments + deadline + idempotency_key + resource_budget

响应：success + value + error_code + error_message
    + retryable + request_id + evidence + resource_release
```

大文件、媒体、模型输入和输出不得无限塞进 JSON 或内存；超过阈值时使用受管制品/临时文件引用、大小上限、校验摘要和最终清理，禁止用 Base64 把大对象无界放大。

#### 一个网关不等于一次性启动所有重资源

运行核心启动时扫描并校验全部插件声明，但 提供者 的执行策略分为：

```text
轻量纯计算：可常驻或进程内
普通外部库：按需启动/空闲排空
GPU/浏览器/原生扩展：按需启动或受控预热
高成本模型：按资源预算单实例/排队启动
```

“一个网关”只保证通信入口和传参方式不分叉；“多个执行单元”由运行核心监督，保证一个 提供者 崩溃、泄漏或第三方 ABI 出错时，不拖垮网关和其他能力。禁止因为追求“全部一起启动”而让 GPU、浏览器句柄、动态库或原生扩展互相污染。

#### 按请求启动、租约缓存和使用后释放

调用方只需要知道能力契约，不需要知道后端原理。对有状态或重资源 提供者，网关请求可以携带生命周期策略：

```text
一次性能力：请求到达 → 监督器启动 提供者 → 执行 → 关闭进程组 → 验证零残留

短时状态能力：申请 execution_id/lease
  → 多次 HTTP 调用同一执行单元
  → 显式 release 或空闲 TTL 到期
  → 排空 → 释放句柄/临时目录/端口/显存

缓存能力：按 提供者/版本/模型/配置摘要复用
  → 有界常驻时间、最大实例数、最大空闲时间
  → 命中继续使用
  → 超限或压力回收
```

浏览器内核、GPU 模型、ASR、OCR、FFmpeg 等默认采用按需启动或租约模式；调用方不持有底层对象，只持有受管的 `execution_id`/`lease_id`。租约过期后再次调用必须明确返回句柄过期，不能让资源偷偷复活。

#### 单链路不变式

```text
调用方
  → 唯一 HTTP 网关（只传参/转结果）
  → 运行核心执行协调器
  → 唯一能力注册表/提供者 路由
  → 一个能力对应的一个受管执行单元
  → 统一结果/事件/释放证据
```

禁止以下侧链：

- 正式代码直接 import C 扩展、GPU 库、浏览器内核或第三方 SDK；
- 每个模块自己启动一套 提供者 或自己维护端口；
- 同一个能力存在多个未声明的实现和错误码转换；
- MCP、HTTP、内部脚本分别拥有一套执行逻辑；MCP 只能是 HTTP 网关的薄适配层；
- 提供者 直接修改平台权威状态；状态变化必须回到公开能力、事件和证据链；
- 用测试预注册、源码路径注入、全局单例或历史缓存绕过网关和装配流程。

#### 与支持库/模块库的关系

- **支持库**拥有原子能力和 提供者 契约；原生扩展、动态库、GPU、浏览器内核可以属于底层支持库的受管 提供者，但不进入网关主进程。
- **模块库**拥有领域流程，只调用支持库公开能力；例如文档解析模块统一组合 PDF/DOCX/XLSX/PPTX 提供者，向上只返回统一文档结构。
- **运行核心**拥有插件发现、环境准备、独立进程、端口、健康、租约、缓存、超时、取消、崩溃回收和证据。
- **HTTP 网关**只拥有唯一通信入口、请求/响应传输、路由转发、基础协议校验和流式转发；不拥有 提供者 业务逻辑和资源。
- **项目适配层**只绑定模块版本、提供者 策略、配置、权限、路径和项目别名，不直接连接 提供者。

因此，平台可以兼容 Python、PHP、C/C++、Rust、Go、Node、GPU 服务和浏览器内核；调用方只需要知道“能力 id + 参数 + 返回契约 + 生命周期令牌”。兼容性来自**统一 HTTP 传参和运行核心的受管生命周期**，不是来自把所有代码装进一个 Python 进程，也不是让网关理解每个 提供者 的内部原理。

### 7.7 执行单元生命周期核心契约

生命周期与资源控制应成为平台级核心能力，但分成三层，不把所有职责塞进普通业务支持库：

```text
公共契约/执行单元契约
  ├─ ExecutionUnit / execution_id
  ├─ Lease / lease_id / owner / expires_at
  ├─ ResourceBudget / deadline / cancel_token
  ├─ 生命周期状态机、错误码、统一结果
  └─ 提供者 HTTP 请求/响应 schema

支持库/资源原子能力
  ├─ 进程组启动/终止/回收
  ├─ 端口申请/释放/占用探测
  ├─ 临时目录/文件/句柄安全释放
  ├─ GPU/浏览器/动态库探针
  └─ 原子写入、锁、快照、摘要

运行核心/提供者监督器
  ├─ 提供者 发现、环境准备、启动、健康检查
  ├─ execution_id/lease_id 分配、续租、排空、释放
  ├─ 按需启动、缓存复用、TTL 回收
  ├─ 超时、取消、崩溃重启、残留清理
  └─ 调用证据、资源释放证据、状态恢复
```

#### 生命周期状态机

```text
已登记
  → 环境就绪
  → 启动中
  → 健康
  → 空闲/占用
  → 排空中
  → 释放中
  → 已释放

启动中/健康/占用
  → 降级
  → 失败
  → 回收中
  → 已回收
```

固定不变式：

- 只有运行核心监督器能推进执行单元状态，提供者 不能自行声称“已释放”或“已恢复”；
- `execution_id` 标识一次受管执行单元，`lease_id` 标识调用方的持有权；句柄不能跨项目、跨所有者或跨版本复用；
- 释放必须幂等，重复释放返回明确结果，不重复 kill、close 或删除；
- 租约过期后句柄不可复活，再次调用必须返回 `EXECUTION_HANDLE_EXPIRED`；
- 提供者 崩溃先进入隔离/失败状态，再由运行核心回收进程组、端口、临时目录、句柄和显存；
- 任何“成功”都必须带资源释放结论；有残留时不能返回完整成功；
- 缓存复用不能绕过 提供者 版本、契约版本、配置摘要、资源 owner 和权限范围检查。

#### 生命周期对外 HTTP 契约

网关只转发这些公开动作，生命周期实际由运行核心执行：

```text
POST /执行单元/申请
  → 返回 execution_id、lease_id、能力契约、截止时间

POST /执行单元/{execution_id}/调用
  → 携带 lease_id、能力 id、参数、request_id、deadline

POST /执行单元/{execution_id}/续租
  → 校验 owner、lease_id、最大租期和资源预算

POST /执行单元/{execution_id}/释放
  → 排空、停止、释放所有资源，重复调用保持幂等

GET /执行单元/{execution_id}/状态
  → 返回状态、提供者 版本、资源摘要、最近错误和释放结论
```

一次性能力可以由网关直接提交 `生命周期=一次性`；浏览器、GPU、ASR、OCR、数据库连接等有状态能力必须先申请执行单元，再使用 `execution_id/lease_id` 调用。调用方不接触底层指针、端口、进程号、WebView、CUDA context 或数据库连接对象。

#### 资源释放验收矩阵

每类 提供者 都要证明以下四种终态：

| 终态 | 必须证明 |
|---|---|
| 正常完成 | 返回值正确，资源全部释放或按租约进入明确缓存状态 |
| 业务失败 | 错误码统一，临时资源/连接/句柄已释放，失败证据已记录 |
| 超时/取消 | 真实终止执行，排空队列，回收子进程/端口/临时目录，调用方收到可重试语义 |
| 提供者 崩溃 | 退出码/信号可见，进程组消失，句柄/端口/显存/临时目录无残留，执行单元进入失败或已回收 |

这套生命周期契约属于公共底座，不属于某一个文档解析、浏览器、模型或业务模块。模块只申请和使用执行单元，提供者 只实现能力，网关只传参，运行核心负责控制和回收。

### 7.8 对外只有“请求 → 返回”两步

从调用方视角，平台是被动式能力服务，不暴露 提供者 的内部原理和控制过程：

```text
调用方
  ① HTTP 请求：能力 id + 契约版本 + 参数
        ↓
   平台内部被动完成：校验/路由/启动或复用/执行/缓存或释放/恢复/记录证据
        ↓
  ② HTTP 返回：成功 + 值，或错误码 + 错误说明 + 可重试
```

调用方不需要知道：

- 提供者 的语言、库、进程、内部端口和启动命令；
- 是否使用了 GPU、浏览器内核、动态库、数据库连接或模型进程；
- 资源何时启动、是否命中缓存、何时释放、如何崩溃恢复；
- 内部线程、队列、句柄、临时目录和错误堆栈。

调用方只需要知道公开契约：

```text
能力 id
契约版本
请求参数
返回值
错误码/错误说明
可重试语义
```

有状态能力的 `execution_id`/`lease_id` 也只是平台发出的不透明句柄，调用方把它作为后续请求参数原样传回，不需要理解其对应的进程或底层对象。默认能力优先采用一次性调用；只有浏览器、GPU、模型、数据库连接等确实需要复用时，才由契约声明会话句柄。

平台内部可以有后台健康检查、TTL 回收、崩溃清理和异步索引，但这些属于底座的被动控制和资源治理，不改变调用方的“请求→返回”认知。异步任务、流式返回或轮询只是 HTTP 传输形态，不能把 提供者 内部状态暴露成业务方必须理解的第二套执行逻辑。

### 7.9 通用基础功能底座定位（易语言式目标）

本平台不是 智能代理 专用平台，也不是某个业务项目的工具集合。它要解决的是“常用基础功能被不同项目重复实现、重复接第三方、重复处理资源和错误”的问题，目标是形成类似易语言支持库的通用底座：功能按原子能力沉淀，复杂功能按模块组合，调用方只面对统一中文契约。

```text
任意软件
  ├─ 桌面程序
  ├─ Web 服务
  ├─ 业务系统
  ├─ 自动化工具
  ├─ 数据/文档/媒体程序
  ├─ 智能代理 与智能应用
  └─ 后续其他程序
          │
          ▼ 只传入参数，只接收返回值
唯一 HTTP 能力网关
          │
          ▼ 统一能力编号、契约、错误和证据
唯一能力注册表 + 唯一能力调用器
          │
          ├─ 支持库：一个原子功能一个权威归属
          │      ├─ 文件、文本、数据、时间、资源
          │      ├─ 文档、图像、媒体、网络、数据库
          │      └─ 外部命令、模型、原生库、系统能力
          │
          └─ 模块库：一个领域流程一个权威入口
                 ├─ 文件管理、文档读取、文档解析、文档生成
                 ├─ 图像处理、媒体处理、媒体转写、OCR
                 ├─ 网页分析、简单窗口、自修复工具
                 └─ 后续持续扩展的通用功能
          │
          ▼ 运行核心隐藏全部实现细节
提供者装配/进程监督/资源租约/缓存/超时/取消/释放/恢复
          │
          ▼
统一结果：成功/值/错误码/错误说明/可重试/证据
```

易语言式目标不是复制易语言的语法，而是继承其“能力集中、调用简单、底层复用、功能可组合”的工程体验：

- 开发者查到一个能力就能调用，不需要重新研究第三方库；
- 一个功能只有一个能力编号和一个契约 owner，不让多个项目各写一份；
- 一个系列功能由一个模块库负责，不让调用方自己拼出多条流程；
- 第三方差异下沉到提供者，调用方不感知 Python、PHP、C/C++、GPU 或浏览器原理；
- 资源、超时、取消、崩溃、回滚和证据由平台统一处理；
- 智能代理 只是能力调用方之一，和桌面程序、Web 服务、自动化工具遵守同一套契约。

### 7.10 两份权威能力目录

支持库和模块库的详细清单、功能和具体流程分别维护在：

- [`支持库总览.md`](支持库总览.md)：38 个支持库、151 项原子能力、第三方/系统/模型提供者边界和资源流程；
- [`模块库总览.md`](模块库总览.md)：11 个正式模块、46 项组合能力、模块依赖和领域流程。

这两份目录是本项目说明的下层权威目录，不与本文件平行竞争：本文件负责总架构和边界；支持库总览负责支持库事实；模块库总览负责模块事实；具体契约仍以各包内 `包声明.json` 和 `能力契约/参数契约.json` 为准。

### 7.11 通用开发接入最小流程

平台的接入对象可以是任何程序，不要求调用方属于智能代理领域：

```text
确认要做的基础功能
  → 能力搜索
  → 查看能力契约
  → 传入中文参数
  → 获得统一返回结果
  → 由平台内部完成提供者装配、资源治理和证据记录
```

网关固定提供三类中文路由：

| 路由 | 作用 |
| --- | --- |
| `GET /能力/搜索?关键词=读取文件` | 搜索已登记能力 |
| `GET /能力/契约/{能力id}` | 查看参数、返回、错误码和行为边界 |
| `POST /能力/执行` | 传入 `{"能力id","参数"}` 执行能力 |

启动脚本为 `MCP工具箱/启动能力网关.sh`，默认端口为 `8866`，也可以传入端口参数。调用方不需要启动某个第三方库的内部服务；需要启动的提供者由运行核心按请求、租约或缓存策略被动处理。

本地部署只是网关和提供者位于同一台机器；跨支持库、跨模块、跨执行单元仍然经过本地 HTTP 网关。同一子项内部才允许直接调用私有函数、内部对象和热循环；不能把“本地”当成绕过边界的理由。

### 7.12 平台长期边界

平台持续扩展通用基础能力，但不扩展为业务项目本身：

- 收拢可复用的文件、文本、数据、文档、图像、媒体、网络、数据库、系统和模型能力；
- 将第三方库、动态库、外部程序和原生扩展放入受管提供者；
- 让支持库和模块库可以下载、复制、装配和复用；
- 继续加强真实验证、资源零残留、契约一致性和发布门禁；
- 不承载任何业务项目代码、数据库、配置或运行数据；
- 不为不同调用方复制多套能力链、注册表、错误转换和资源控制。

### 7.13 原子能力唯一实现选型原则

平台不是“看到一个开源项目就接入一个项目”，而是从多个项目中提取同一种原子能力，经过统一契约和真实对比后，只保留一个权威实现。其他项目只作为源码参考、兼容适配或待核候选，不得因为名称不同就形成重复内核。

```text
多个开源项目/多个第三方库
          │ 提取同一种原子能力
          ▼
候选实现对齐同一份中文契约
          │
          ├─ 正确性：输入、输出、边界、错误码一致
          ├─ 性能：相同数据、相同机器、相同并发下实测
          ├─ 稳定性：长时间、重复调用、异常、超时、取消、崩溃
          ├─ 资源：内存、CPU、GPU、句柄、进程、临时文件零残留
          ├─ 安全：越界、注入、权限、第三方供应链和隔离边界
          ├─ 兼容：系统、架构、位数、版本、数据格式和许可证
          └─ 维护：源码质量、测试、活跃度、升级和替换成本
          │
          ▼
唯一权威原子内核
          │
          ├─ 支持库公开能力
          ├─ 一个能力编号和一个契约 owner
          ├─ 一个提供者实现和一条注册/调用链
          └─ 其他候选只保留参考、兼容层或待核状态
```

#### 不是按语言选型，而是按原子能力的稳定性选型

语言只是实现手段，不能把“C/C++、Rust、Go、Python、系统命令”本身当作架构层，也不能预设某种语言天然就是权威实现。选型对象应是具体能力，并优先比较哪种实现更稳固：

```text
访问一段内存
读取文件
计算摘要
解码一帧视频
转换一段编码
执行一次 SQL
启动并回收一个进程
渲染一页 PDF
识别一张图片
生成一个文档
```

例如：

- 内存访问、字节转换、图像像素、编解码等能力，可以比较 C/C++、Rust、Go 或其他实现，但最终以边界安全、所有权、异常释放和故障注入结果决定；
- 文件、网络、数据库等 I/O 能力，重点是连接、事务、超时、重试、断线、恢复和资源释放，不能只比较语言基准；
- 纯规则、配置和轻量数据处理，标准库实现可能已经足够稳定，不需要为了“底层”而重新写原生代码；
- 第三方库已经提供稳定内核时，平台不重复造内核，只做参数、错误、版本、资源和隔离适配；
- 某个项目只有命令表、元数据或空函数骨架时，它只能作为 ABI/契约参考，不能成为能力内核。

#### 高性能能力不能把热循环拆成大量 HTTP 请求

HTTP 网关是统一通信入口，但不意味着每一个字节、每一个像素或每一条记录都单独请求网关：

```text
错误方式：调用方
  → HTTP 请求一个字节/一行/一个像素
  → 网关
  → 提供者
  → 返回
  （网络和序列化开销淹没内核速度）

正确方式：调用方
  → 一次 HTTP 请求：批量数据/受管制品引用 + 参数
  → 网关转发
  → 提供者内部热循环
  → 一次返回批量结果/受管制品引用
```

因此，网关契约必须支持批量参数、输出大小上限和摘要校验。默认采用一次性传参、一次性返回；共享内存、受管文件或制品引用只能作为契约明确声明的大对象优化，不能由调用方自行把内部指针、内存地址或私有对象当作参数传递。调用方仍然只负责请求和接收返回，热循环、内存布局、线程和底层优化全部隐藏在同一子项内部的权威支持库/提供者内。

#### 稳定性第一，性能在达标后比较

语言和实现的性能差距如果没有达到实际业务可感知的程度，就不能为了理论速度牺牲稳定性。选型顺序固定为：

```text
先过：正确性、边界安全、错误闭环、资源释放、崩溃隔离
再比：版本兼容、部署难度、可观测性、测试完整度、长期维护
再看：吞吐、延迟、内存峰值、CPU/GPU 占用、并发扩展
最后裁决：许可证、供应链、替换成本和平台长期责任
```

稳定的权威实现通常具备：

- 状态少而清楚，初始化、运行、停止和释放都有固定顺序；
- 输入输出契约稳定，错误码不依赖日志文本或异常字符串；
- 资源所有权明确，重复释放、超时、取消和崩溃都有确定结果；
- 不依赖隐式全局单例，不把内部对象、指针和连接泄露给上层；
- 能在独立进程、不同版本和不同部署形态下复现；
- 有真实测试、故障注入、长时间运行和残留检查证据；
- 出现更好的实现时，可以在同一契约下替换，不影响模块和调用方。

任何候选实现只要存在以下问题，就不能因为基准速度快而成为权威内核：

- 越界、悬空指针、引用计数或句柄所有权无法证明；
- 超时、取消、崩溃后无法回收；
- 错误被吞掉、返回值不稳定或把失败包装成成功；
- 只能依靠全局单例，无法按项目/调用方隔离；
- 只能在一个旧系统或一个位数下工作，兼容边界未冻结；
- 许可证、第三方来源或更新责任无法确认。

### 7.14 跨边界调用硬规则与原子能力最小化

平台把“直接调用”和“网关调用”按边界固定分开：

```text
同一个子项内部
  → 私有函数/内部对象/热循环可以直接调用
  → 不经过 HTTP，避免把高频底层计算切碎

跨子项
  → HTTP 网关

跨支持库
  → HTTP 网关

跨模块
  → HTTP 网关

跨进程/跨语言/跨机器
  → HTTP 网关
```

这里的“子项”是一个经过装配、拥有明确契约和资源边界的最小执行单元，不是随意划分的文件夹。只要两个能力不属于同一个子项，就不能通过直接 import、共享单例、内部类实例、裸指针、数据库私表或隐藏回调相互连接。

```text
支持库/文件系统/读取文件
  → HTTP 网关
  → 支持库/资源管理/创建摘要

模块库/文档解析
  → HTTP 网关
  → 支持库/PDF文档/解析PDF
  → HTTP 网关
  → 支持库/资源管理/安全释放
```

即使调用双方部署在同一台机器、同一个 Python 解释器或同一个项目目录，也不能因为“本地调用更方便”就跨边界直连。这样才能防止：

- A 支持库反向依赖 B 模块，形成循环依赖；
- 模块绕过网关直接拿到第三方对象和内部句柄；
- 不同调用链各自翻译错误码，最终结果不一致；
- 资源创建者和释放者分离后无人负责；
- 一个项目的全局缓存、线程、数据库连接污染另一个项目；
- 未来拆成独立进程或远程服务时被隐式引用拖垮。

### 7.15 一次性传参返回优先，引用只作受控优化

原子能力的默认交互是：

```text
请求参数
  → 网关
  → 目标子项内部完成全部计算
  → 返回结果参数
```

不能为了“省一点传输”就默认把指针、内存地址、内部对象、临时路径或私有句柄传给调用方。只有在数据确实超过内联上限，且能力契约明确声明时，才允许返回受管制品引用；引用必须具备：

- 所属请求、项目和调用方；
- 内容摘要、媒体类型和大小；
- 访问权限和有效期；
- 读取/下载仍经过 HTTP 网关；
- 过期、释放、取消和崩溃后的清理责任；
- 不能转换成另一个子项的内部对象或裸指针。

“原子能力”不是把功能故意做得残缺，而是把计算机底层的一件事做成稳定、快速、可复用的最小单元。通过很多可靠原子能力组合，平台才能实现“把少变成多”：调用方看到的是简单功能，底座内部保持短路径、单责任和可验证。

### 7.16 第三轮通用源码研究形成的稳定性证据

近期对场景检测、视觉、语音、嵌入、数据集、知识检索、文档解析和向量存储项目进行第三轮映射后，反复出现的有效共性不是某种编程语言，而是以下结构：

```text
一个公开能力门面
  → 一个注册/路由 owner
  → 一个内部执行链
  → 一个统一结果结构
  → 一个资源生命周期 owner
  → 多种实现只在适配层替换
```

现场项目给出的可复用证据：

- `LanceDB`：Rust 核心负责表、查询、索引和错误，Python/TypeScript/Java 只是绑定或 SDK；这说明稳定性来自唯一核心和统一 `Table/Query/Result` 边界，不来自强制所有调用方使用同一种语言。
- `Docling`：`DocumentConverter` 统一入口，格式差异下沉到 backend，模型富化进入 pipeline，最终统一为 `DoclingDocument/ConversionResult`；这说明多格式能力应共享一个结果 owner，不能每种格式各自向上层泄露对象。
- `Ultralytics`：`Model` 门面通过 `task_map` 装配模型、训练器、验证器和预测器，结果收敛到 `Results`；训练、预测、导出和跟踪是上层模式，不能全部下沉为视觉原子能力。
- `FunASR`：`AutoModel` 和注册表负责模型装配，VAD、标点、说话人是可组合能力，Python、HTTP、WebSocket、gRPC、ONNX、Triton 是不同出口；平台应保留一条转写能力链，不能因为出口不同复制多套转写内核。
- `PySceneDetect`：视频读取、时间码和检测器在同一检测子项内部直接协作，CLI、外部 `ffmpeg` 和输出制品在边界外接入；这验证了“子项内部直连、跨边界统一通信”的性能与隔离平衡。
- `CVAT`、`FiftyOne`：领域对象、数据库/对象存储、队列、会话和 worker 分属不同 owner；任务状态和业务状态不能混成一个对象，更不能让上层直接持有数据库连接、worker 或媒体句柄。
- `KAG`、`LightRAG`、`GraphRAG`、`Haystack`、`llama_index`：都能提炼出检索、图、向量、文档和编排能力，但平台只应保留一个规范摄取链和一个规范检索链，不能按项目名称各建一套 RAG 内核。

因此，源码研究的交付物不是“接入项目清单”，而是：

```text
同一种原子能力的候选实现清单
  → 统一契约对齐
  → 稳固性和失败路径验证
  → 唯一 owner 裁决
  → 选定一个权威提供者
  → 其余实现降为兼容适配/研究参考/待核
```

本批次中因专属 MCP 项目错绑而阻断的 `TransNetV2`、`WhisperX`、`FlagEmbedding`、`HKUDS-VideoRAG`、`starsuzi-VideoRAG`，不计入已完成第三轮映射，也不因已有首轮 `ARCHITECTURE.md` 就假定其底座裁决已经完成。

### 7.17 线程控制是平台原子能力

线程不是各支持库和模块可以自行发明的私有实现。任何支持库如果各自创建线程、线程池、队列、取消逻辑和异常回收，最终会出现线程数量失控、队列互相嵌套、死锁、饥饿、重复释放、取消失效和资源互相污染。因此平台把线程控制收口为一个独立的原子能力，其他能力只能提交任务和读取统一状态。

```text
跨边界请求
  → HTTP 网关
  → 线程控制原子能力
  → 准入检查：CPU/内存/并发/优先级/截止时间
  → 有界队列
  → 统一线程执行器
  → 任务状态机与心跳
  → 执行目标子项内部的短路径工作
  → 结果/错误/证据
  → 取消、超时、异常、崩溃收口
  → join/释放/残留检查
```

线程任务统一状态机：

```text
created
  → admitted
  → queued
  → running
  ├─→ succeeded
  ├─→ failed
  ├─→ cancel_requested → cancelled
  ├─→ deadline_exceeded → timed_out
  └─→ worker_exception/provider_lost → crashed

succeeded/failed/cancelled/timed_out/crashed
  → draining
  → cleaned
  └─→ cleanup_failed（进入告警和残留治理，不得伪报成功）
```

线程控制原子能力至少统一提供：

- 有界工作线程数、最大队列长度和背压；
- CPU、内存、任务数和执行时间资源预算；
- 任务编号、幂等键、优先级、截止时间和取消令牌；
- `created/admitted/queued/running` 等状态查询和状态变更证据；
- 心跳、无进展检测、异常捕获和统一错误转换；
- 协作式取消、超时标记、排空、`join` 和线程池关闭；
- 任务异常与宿主异常隔离，不能让一个任务杀死网关或其他子项；
- 线程、队列、临时文件、句柄和子进程的终态对账。

“充分调用电脑性能”不是把线程数开到 CPU 核数以上，而是由运行核心根据环境指纹、CPU 逻辑核数、内存预算、任务类型和当前负载动态计算有界并发；线程池、队列和缓存都必须有上限。没有实测证据时，不宣称最佳线程数，更不能用无界队列掩盖吞吐不足。

线程不能安全地被任意强杀。纯计算任务应通过取消令牌和安全检查点协作退出；阻塞系统调用或原生库任务如果不能协作取消，必须转入受管独立进程，由运行核心终止进程组并验证零残留，不能在主进程里强拆线程栈。线程控制只拥有调度和收口责任，不拥有第三方对象、数据库连接、浏览器句柄或 GPU 上下文的跨边界所有权。

固定禁止项：

- 支持库自行创建无上限线程池；
- 模块之间互相传递线程对象、锁、队列或可变共享状态；
- 跨支持库直接调用另一方的私有线程函数；
- 用线程代替沙箱或进程隔离；
- 用 `daemon` 线程退出掩盖未释放资源；
- 取消只改一个布尔值却不等待、不中止阻塞提供者、不检查残留；
- 各模块分别维护一套“运行中/完成/失败”状态，形成多个任务事实源。

线程控制原子能力的权威 owner 是运行核心；公共契约只定义状态、预算、错误和释放语义；支持库只提供必要的原子执行动作；模块只提交领域任务。这样线程并发才是平台能力，而不是每个项目各自埋一颗定时炸弹。

### 7.18 数据库连接是有状态原子能力的典型

易语言式的数据库调用模型是正确方向：把底层数据库连接封装成一个可复用的句柄，后续执行 SQL、事务和关闭都围绕这个句柄完成。平台保留这个使用体验，但把句柄定义为不透明的连接租约，不把真实数据库连接、游标、线程或驱动对象交给调用方。

```text
调用方
  → HTTP：数据库.连接（地址、认证引用、数据库、端口、资源预算）
  ← HTTP：连接租约id + 状态 + 过期时间

调用方
  → HTTP：数据库.执行SQL（连接租约id、SQL、参数、截止时间）
  ← HTTP：统一结果（列、行、影响行数、错误码、证据）

调用方
  → HTTP：数据库.开始事务/提交/回滚/关闭（连接租约id）
  ← HTTP：状态和释放结论
```

数据库支持库内部才允许直接持有和使用真实连接：

```text
数据库支持库/提供者子项
  → 连接配置校验
  → 由专属执行单元独占真实连接；如需连接池，只能作为该 owner 内部实现
  → 连接健康检查
  → SQL 参数绑定
  → 查询/执行
  → 事务绑定到同一物理连接
  → 结果转换
  → 连接归还或关闭
```

职责必须分开：

- **数据库支持库**：连接、执行 SQL、查询、事务、参数绑定、结果转换和驱动错误转换；
- **运行核心**：连接租约、专属执行单元、超时、取消、空闲回收、提供者崩溃和残留检查；连接池上限只约束 owner 内部，不能把连接池对象暴露给上层；
- **线程控制原子能力**：控制数据库任务的准入、排队、并发、状态机和收口，不直接拥有连接；
- **模块库**：组合多个 SQL 能力完成一个领域流程，不直接导入 `pymysql`、`psycopg`、`sqlite3` 等驱动；
- **项目适配层**：只保存连接配置引用、权限和版本绑定，不保存密码明文，不创建连接。

数据库连接状态至少固定为：

```text
created → connecting → ready → executing → ready
                         │          │
                         │          ├─→ failed
                         │          ├─→ timed_out
                         │          └─→ cancel_requested → cancelled
                         │
                         └─→ closing → closed

ready → transaction_started → executing → committed/rolled_back → ready
```

事务期间必须把逻辑连接租约绑定到同一物理连接，不能让连接池在每条 SQL 之间随意换连接；事务提交、回滚、超时、取消和连接崩溃都必须有明确终态。一个连接租约默认限制同时执行的命令数，避免多个线程同时操作同一事务造成状态互相覆盖。

数据量不大时，查询结果直接一次返回真实行列数据；超过契约上限时，才返回受管结果制品引用。不能为了“节省传输”把游标、连接、内存地址或 ORM 对象引用给上层。多条必须连续执行的 SQL 可以通过一次“事务批量执行”请求提交，减少 HTTP 往返，但事务内部仍由数据库支持库独占控制。

固定禁止项：

- 模块直接调用数据库驱动的 `connect`；
- 调用方把真实连接对象、游标或线程传给另一个模块；
- 把一个连接租约同时交给多个不相关模块；
- 用连接池复用掩盖事务没有提交/回滚的问题；
- 记录地址、账号、密码或连接字符串到句柄、日志和证据；
- 连接超时后只返回失败，却不验证连接是否已归还或关闭。

### 7.19 有状态能力优先使用“一资源一执行单元”

对于数据库连接、浏览器、模型上下文、动态库句柄、设备会话等容易发生状态漂移、线程污染或释放不完整的资源，平台优先采用独立的资源 owner 执行单元，而不是让多个调用方共享一个全局连接或把资源对象到处传递：

```text
连接/会话请求
  → 运行核心拉起一个受管进程或受控线程
  → 执行单元独占真实连接、句柄和内部状态
  → 返回不透明执行单元id/会话句柄

后续调用
  → HTTP 网关携带会话句柄
  → 运行核心路由到同一个执行单元
  → 执行单元内部直接处理
  → 一次返回结果

关闭/用完
  → 停止接收新请求
  → 回滚/关闭内部资源
  → 退出线程或终止进程
  → 等待回收并验证零残留
```

这样做的核心不是“PID 更方便”，而是把所有权固定在一个 owner 上：

```text
一个执行单元
  → 一个真实资源 owner
  → 一个请求串行入口或明确并发策略
  → 一个关闭动作
  → 一个终态记录
```

调用方可以把返回值当作易语言式句柄使用，但对外不直接暴露裸 PID。PID 可能被操作系统复用，也不能单独证明它属于本次会话；平台内部应使用 `execution_id + 启动随机数/制品摘要 + 所属请求/项目` 绑定实际进程，并在每次调用前校验状态、权限和租约。对调用方而言仍然只是一个普通句柄，不需要理解这些内部字段。

执行单元分两种：

- **专属进程**：优先用于数据库驱动、浏览器、GPU、FFmpeg、动态库、Python 解释器和不可信/不稳定第三方代码；无法协作取消时，可以终止整个进程组，操作系统负责回收其连接、线程和地址空间；
- **专属线程**：只用于确认线程安全、可协作取消、不会加载高风险原生状态的轻量资源；关闭必须设置停止信号并等待 `join`，不能从外部强拆线程栈。

有状态能力的最小状态机固定为：

```text
created
  → starting
  → ready
  → serving
  ├─→ closing → stopped → cleaned
  ├─→ failed  → cleaned
  ├─→ timed_out → terminating → cleaned
  ├─→ cancel_requested → stopping → cleaned
  └─→ owner_crashed → invalidated → reaped → cleaned
```

“用完就炸掉”在平台里具体表示：显式关闭、租约到期、超时或 owner 崩溃后，执行单元不再接受调用；数据库事务回滚、连接关闭、临时目录删除、端口释放、线程 join 或进程组终止全部完成后，句柄失效。旧句柄绝不能因为 PID 被系统复用而重新指向新资源。

并不是所有原子能力都要单独拉进程：无状态、短小、低风险的纯计算可以在同一支持库子项内部直接执行；只有跨请求需要保持状态，或资源释放/崩溃风险高时，才使用“一资源一执行单元”。连接池不是默认架构，只能是某个专属 owner 为提高吞吐而采用的内部实现；外部永远只看到一个句柄。这样既保留易语言“连接得到句柄、句柄继续调用、关闭句柄释放”的简单模型，又避免共享引用和全局连接把系统拖进状态圈。

### 7.20 文档收口与后续研究节奏

当前阶段先停止无边界派发，优先完成权威文档收口。任何新源码项目在没有明确研究目标、能力缺口和文档 owner 前，不再新增架构文件或旁路报告。

```text
聊天架构决策
  → 区分平台总原则/支持库规则/模块规则/项目事实
  → 平台总原则写入本文件
  → 支持库与模块边界分别写入下层总览
  → 单项目源码事实写入项目根 ARCHITECTURE.md
  → 子代理回执、旧细探、临时报告只作待核材料
  → 人工回读、去重、冲突检查
  → 通过静态结构和现场状态验收
  → 再决定下一批研究或实现工作包
```

固定收口顺序：

1. **先收平台总原则**：请求→返回、同子项直连、跨边界 HTTP、默认传值、受控句柄、一资源一执行单元、线程/进程统一监督、稳定性优先和单一 owner。
2. **再收支持库/模块总览**：支持库只列原子能力和提供者边界；模块只列领域流程和组合关系；不在两个总览里重复写同一份契约。
3. **再收源码项目档案**：项目事实、源码路径、验证等级和剩余风险只留在各自 `ARCHITECTURE.md`；旧细探只有完成吸收和人工核对后才删除。
4. **最后做能力选型**：同一原子能力的多个候选先建立对比表，再用真实稳定性、资源、失败恢复、兼容和维护证据选一个权威实现，不按项目名称或语言直接接入。

阶段验收不再按“回执数量”计算，而按现场证据计算：

```text
已收口 = 权威文档已回读 + 冲突已处理 + 验证边界已标明
已完成研究 = 项目档案已写入 + 第三轮裁决已核对
已验证实现 = 真实注册表调用 + 真实返回 + 资源释放证据
待核 = 文件或结论存在，但缺少目标项目绑定、真实运行或失败路径证据
```

当前文档总原则已经收口，源码研究恢复采用每批 10 个真实工作包的滚动方式：回收一个、现场验收一个、确认落盘一个，再补一个；出现 503、429、持续冷却、任务级超时或无产出时停止加压，先处理失败和已落盘材料。

当前进入人工收口优先模式：后台子代理可以继续取证，但主协调者必须一个项目一个项目全文回读 `ARCHITECTURE.md`、旧细探和源码；确认吸收、去重、无漂移后，才删除对应旧细探。未经过主协调者肉眼回读的内容只能标记为待核，不能写成平台事实或完成数量。

华哥的原始架构表达单独保存在源码参考库 `开发文档/用户架构表达记录.md`，只记录原话，不加入助手推理；平台架构记忆仍以本文件、支持库总览、模块库总览和各项目根 `ARCHITECTURE.md` 为准。

### 7.21 现有易语言样本的选型结论

```text
iconv
  → 有真实编码转换内核 + 易语言 ABI 适配
  → 可作为“底层内核 + 薄支持库”正面样本

python-fne
  → 真实跨 ABI/解释器桥接
  → 可作为“跨语言桥接支持库”研究样本
  → 不应作为普通业务模块直接复制

jywke
  → 真实浏览器内核、窗口、JS、DOM、网络和事件链
  → 可拆成浏览器内核支持库 + 浏览器模块
  → 必须隔离动态库、窗口句柄和全局状态

egrid / opengl 等骨架项目
  → 可研究支持库注册、命令表、参数表和组件元数据
  → 当前没有真实后端实现时，不能作为底层能力内核
```

最终原则是：

> **一个原子能力只保留一个稳定达标、经过验证、可长期维护的权威实现；语言只是实现手段，性能是达标后的比较项，多个项目的差异只留在兼容适配层，不能让上层感知，更不能让不同项目各自重复造轮子。**

### 7.22 第三轮样本已核对的通用底座结论

本节只吸收父代理已经人工回读的源码档案，不把子代理自报或未运行测试当成验证通过。当前已核对的代表样本包括 EbbingFlow、HanaAgent、Hindsight、Mem0、QAnything、MemOS、RAGFlow 和 Verba。

#### 1. 多后端不等于多条业务链

这些项目普遍同时存在数据库、向量库、全文索引、图索引、对象存储、模型服务或多个语言运行时。可吸收的不是“每个后端各写一套流程”，而是：

```text
领域模块唯一写入/检索门面
  → 统一候选、文档、任务或结果契约
  → 支持库 provider 适配
  → 运行核心治理超时、取消、预算、租约和恢复
  → 统一网关返回结果和状态
```

主事实、审计账本、辅助索引、缓存和上下文窗口必须分开定义 owner。辅助索引允许降级和异步补偿，但不能取代主事实，也不能在失败时静默伪造成功。

#### 2. 异步队列确认不等于业务完成

Hindsight 的 `async_operations`/`WorkerPoller`、RAGFlow 的 Redis/MQ worker、MemOS 的 scheduler 和多个项目的 checkpoint 都表明：消息 ack、broker 可见性租约、数据库状态、业务提交是不同层次。

平台必须区分：

```text
消息已领取
  ≠ worker 仍存活
  ≠ 领域状态已提交
  ≠ 索引/制品已发布
```

任务契约至少需要 `operation_id`、`attempt`、`owner_id`、`lease_epoch`、截止时间、取消状态、部分结果、重试/死信和最终对账。传输层可以 at-least-once，但业务提交必须幂等，跨存储状态通过 outbox、补偿和重建收口。

#### 3. 适配层异构，统一转换只能有一个位置

Verba、QAnything、Mem0 和 RAGFlow 都显示不同 provider 的返回形状、错误、批量能力和降级行为可能不同。正确边界是：

- provider 只负责第三方调用、参数转换、资源释放和底层错误分类；
- 领域模块只在唯一组合点做一次统一结果转换、排序、父子块恢复或文档结构归一；
- 网关不再自行检索、拼装业务结果或维护第二张别名表；
- 缺能力必须返回明确状态，不能用空结果伪装正常成功。

#### 4. 原始证据和派生投影必须分层

EbbingFlow 的 SQL 原始消息/Neo4j 图谱/Chroma 向量、QAnything 的 MySQL/Milvus/ES、Hindsight 的 facts/observations/mental models、MemOS 的事件/投影和 RAGFlow 的文档/块/索引共同验证：

```text
原始输入/证据
  → 领域事实或文档中间表示
  → 可重建索引/图/向量/缓存
  → 检索结果/上下文/最终输出
```

索引、向量、图、缓存和摘要默认是派生物；删除、更新、重建和回滚必须有版本、来源、状态和可重放证据，不能只看“查询还能返回”判断一致。

#### 5. 高风险原生能力继续优先进程隔离

QAnything 的 OCR/PDF/模型服务、RAGFlow 的原生解析/沙箱、HanaAgent 的终端/MCP/插件、Verba 的外部模型与 Weaviate，以及各项目的 GPU/动态库边界，都支持当前平台规则：不可协作取消、可能崩溃、会加载原生扩展或持有复杂句柄的能力，不进入网关主进程；由受管独立进程承载，超时终止进程组，重启后按 operation 和租约恢复或隔离。

#### 6. 当前证据等级必须诚实

本轮人工核对主要属于 L0（源码/路径/契约存在）和部分 L1（源码中有可执行路径、测试源码存在）。这些项目本轮没有统一安装依赖、启动真实服务、连接外部数据库/模型或做故障注入，因此不能写成 L3/L4 已通过。后续进入平台选型时，优先对同类候选做真实小场景、超时/取消、崩溃恢复和零残留验证，再决定唯一 owner。

#### 7. 事件通知不等于事件账本

Elephant-Agent 的 `EventEnvelope`、`ToolLifecycleEvent` 和 `RecallRuntime.append_event()`、OpenHuman 的 TinyBus、Letta 的 stream/event、多个项目的内存队列都说明：事件对象、事件广播、运行日志和可恢复事实不是同一层。

```text
实时通知/指标
  ≠ 可重放事件
  ≠ 权威领域状态
  ≠ 崩溃恢复依据
```

平台必须分别声明：通知是否持久化、是否有序、是否可重放、是否幂等、是否允许丢失，以及真正的权威状态由哪个存储 owner 写入。没有落盘、版本、序列和恢复读取路径时，不得把 `append_event()`、event bus 或日志名称写成事件溯源已实现。

#### 8. 生产队列必须区分内存队列、传输队列和持久任务

OpenHuman 的 `RunQueue`/TinyBus、Letta 的 `QueueRuntime`、MIRIX 的 `QueueWorker`、Hindsight 的数据库 broker 和 Coze 的 Workflow 执行记录形成了明确分层：

- 内存队列适合当前进程内排队和背压，崩溃后可以丢失；
- 消息队列负责传输确认、可见性租约和重投，不等于业务提交；
- 持久任务表/执行记录负责状态、幂等、恢复和对账；
- 发送结果未知时必须保留 `send_attempt`/`UnknownAfterSend` 一类状态，不能因为连接断开就盲目重发。

运行核心必须把三者的 owner、容量、租约、重投、死信和恢复动作拆开，禁止用一个布尔“已完成”覆盖全部语义。

#### 9. 可选缓存和加速层永远不能成为第二事实源

MIRIX 明确 PostgreSQL 是权威持久化边界，Redis 是可选加速层；EbbingFlow、Mem0、QAnything 和 RAGFlow 也显示向量、图、全文索引、缓存和对象存储通常是可重建或辅助投影。

平台默认规则：

```text
权威状态/事实库
  → 事件或 outbox
  → 缓存/向量/全文/图/对象投影
```

缓存不可用时允许降级，但不能改变权限、事实、删除和事务语义；缓存命中不能绕过作用域检查；索引写失败不能伪造主事实已经完成。

#### 10. 多入口必须汇聚到一个领域执行内核

Coze Studio 的同步、异步、流式 Workflow 入口共享同一“版本读取→Schema→构图→Runner”链；OpenHuman 的 JSON-RPC/CLI、HanaAgent 的 REST/WS/CLI、Hindsight 的 REST/MCP/SDK 也体现相同方向。

协议不同不等于业务内核不同：

```text
REST / WebSocket / CLI / MCP / SDK
  → 唯一网关适配
  → 唯一领域模块入口
  → 唯一执行/写入/检索内核
  → 统一状态、结果、错误和释放
```

同步、异步、流式只改变交付方式，不得各自复制一套业务状态机和 provider 调用链。

#### 11. 旧仓库名称不能代替当前实现证据

Letta 当前参考仓库明确是 landing page，真正运行时在 `letta-code`；因此源码研究必须记录实际 checkout、分支、提交和项目定位。旧 V1、历史 Docker 镜像、论文、README 或高 star 数不能代替当前实现证据，也不能把历史实现直接作为平台候选。

## 第二轮横向研究输入：能力归属与架构补节点（2026-08-21）

`ARCHITECTURE.md` 的源码行号为准；本轮没有安装依赖、启动外部服务或做故障注入，
因此新增内容属于平台设计输入和待核项，不是已部署能力。

### 1. 支持库、模块库和运行核心的选择规则

判断一个候选能力放在哪里，按以下顺序裁决：

| 判断问题 | 归属 | 典型例子 | 不允许的做法 |
| --- | --- | --- | --- |
| 是否能脱离领域流程独立描述，输入/输出稳定，且只围绕一个外部边界或原子动作？ | 支持库 | 文档读取、文本分块、Embedding 调用、向量检索、重排、对象存储、模型 Provider 适配 | 把“导入知识库并发布索引”塞进支持库 |
| 是否需要组合两个以上能力，包含领域状态、步骤顺序、幂等或业务失败语义？ | 模块库 | 文档解析入库、混合检索、RAG 问答、媒体转写、工作流执行 | 让调用方自行拼接多条底层调用形成第二条流程 |
| 是否负责跨请求资源、租约、调度、取消、崩溃接管、统一调用证据或装配？ | 运行核心/平台控制面 | 持久任务、Provider 监督、租约心跳、能力注册表、制品激活、资源对账 | 让每个模块自建线程池、重试队列和恢复协议 |
| 是否只是绑定项目版本、权限、路径、密钥引用和中文别名？ | 项目适配层 | 某项目选择哪个 RAG 模块、哪个模型 Provider、哪个存储 | 在适配层导入第三方实现或直接持有连接 |

一句话规则：**单一原子边界进支持库，跨能力的领域流程进模块库，跨请求和跨组件
的治理进运行核心；项目差异只进项目适配层。**

### 3. 权威架构需要新增的运行核心节点

本轮不同项目虽然技术栈不同，但反复出现同一组不能下沉到普通支持库的治理缺口，
建议在运行核心目录与统一契约中显式建模：

```text
请求接收
  → 持久任务/操作记录（operation_id、幂等键、attempt）
  → 租约与心跳（owner_id、lease_epoch、截止时间）
  → 有界调度与 Provider 监督
  → 领域模块执行
  → 事实提交与派生索引/制品投影
  → 对账、重试/死信、取消收口、资源归零
```

建议新增或明确以下节点：

1. **持久操作记录与未知发送状态**：区分已接收、已领取、执行中、提交中、未知、成功、失败、取消和死信；不能用内存队列或一个 `completed` 布尔替代。
2. **统一租约/心跳/接管器**：记录 owner、epoch、最后心跳和截止时间；重启后只能按租约和幂等键接管，不能扫描“看起来卡住”的任务直接重跑。
3. **取消与截止时间协调器**：向模块、Provider、子进程和传输层传播取消；无法强杀的同步线程必须隔离并标记资源状态，不能把超时当成已停止。
4. **事实提交与派生投影对账器**：原始事实先提交，向量、全文、图、缓存、对象制品由 outbox/重建任务投影；部分成功、孤儿和删除滞后必须可列举。
5. **统一资源账本**：线程、进程、端口、临时目录、句柄、连接、缓存和后台任务都要有 owner、上限、终态和释放证据。
6. **证据与版本制品节点**：把源码证据等级、能力契约摘要、Provider 版本、请求结果和释放结论绑定到一次调用或一次发布，避免只记录日志文本。

这些节点属于运行核心/平台控制面，不应分别复制到知识库模块、媒体模块或 Agent
模块中。当前仓库已经存在 `运行核心/租约管理.py`、`运行核心/权威状态.py`、
`运行核心/任务调度/`、`运行核心/资源协调/` 和 `运行核心/统一网关/流式语义.py`
等实现入口；本节的“新增”是补齐统一契约、持久字段、调用关系和验收覆盖，**不是再建
一套同名目录或第二个状态源**。支持库只提供原子动作及底层错误转换；模块只声明所需状态
和补偿动作；运行核心统一负责准入、租约、调度、取消、恢复与证据收口。

### 4. 选择唯一实现的门槛

#### 4.1 源码参考到平台能力的审计收口

源码参考项目只能产生候选证据，不能直接成为平台实现或能力注册。一个项目只有完成
“全项目审计 → 证据分级 → 能力拆分 → 契约映射 → 资源/失败边界核对”后，才允许进入
支持库、模块库或运行核心的候选清单。单个函数、README 宣传、旧版本架构图和测试名称
都不能单独支撑归属决定。

```text
远程版本/提交核对
  → 全量目录与文件名盘点
  → 入口、数据模型、调用链、测试和部署边界取证
  → 唯一 ARCHITECTURE.md（上方流程图、下方分层与 file:line 证据）
  → 证据分级：源码事实 / 测试声明 / 实际验证 / 未确认风险
  → 原子能力、领域流程、治理职责三路拆分
  → 能力契约、提供者边界、资源预算、错误/取消/幂等映射
  → 复用裁决：支持库 / 模块库 / 运行核心 / 不吸收
  → 工作包、验证记录、版本制品和可回滚候选
```

审计文档必须满足以下最低事实要求：

- 覆盖项目整体运行方式，而不是只描述一个入口或一个算法；至少盘点目录、入口、核心
  数据结构、持久化、外部依赖、后台任务、测试和部署/协议边界。
- 每个关键结论尽量带当前提交下的 `文件:行号`；无法定位到源码的内容必须标为待核，
  不能写成已验证事实。
- 同一个开源项目只维护根目录唯一 `ARCHITECTURE.md`。临时细探材料吸收后删除或仅作
  施工记录，不得形成第二份架构事实源。
- 本地快照落后远程时，先在隔离目录获取最新提交并记录差异；禁止用未核对的旧快照覆盖
  当前唯一文档，也禁止把远程 README 当作源码实现证据。
- 没有 `.codegraph` 的项目可以建立项目本地代码地图作为检索加速，但代码地图是缓存，
  不得成为平台事实源，不得与系统工程平台 MCP 或其他项目索引混用。

能力归属的最终判定仍遵循以下顺序：单一稳定输入/输出和一个外部边界归支持库；跨多个
能力、带步骤和领域状态的流程归模块库；跨请求资源、租约、调度、取消、恢复、证据和
装配归运行核心；只绑定版本、权限、路径和别名的内容归项目适配层。若源码显示一个项目
同时承担多层职责，必须拆出候选边界，不能整仓复制成一个“大支持库”或“大模块”。

#### 4.1.1 源码研究证据控制面

源码参考研究本身也需要一个治理对象，但它不是运行时支持库、模块库或提供者。每个
参考仓的研究控制记录至少绑定以下事实：

- 远程地址、默认分支、当前提交、远程领先/落后关系和经代理获取的版本证据；
- 当前源码文件树、文件规模、`.codegraph` 状态、查询命令和代码地图可信度；
- 仓根唯一 `ARCHITECTURE.md`，顶部流程图、下方源码分层、关键路径 `file:line` 和未确认项；
- 证据等级（源码事实、测试源码、静态检查、真实运行、外部闭环）与对应命令/退出码；
- 子代理开工标识、反馈五字段、验证结果、剩余风险和下一次复审入口。

控制面只产生研究证据和候选能力映射，不注册能力、不启动提供者、不持有业务数据，也不

架构文档，再重新判断支持库/模块库/运行核心归属；未达到真实失败、资源释放和恢复证据的

#### 4.2 个人模型、记忆与 Agent 项目的拆分示例

本轮对 Second-Me、Hindsight、Elephant-Agent、OpenHuman、MIRIX 和 Hermes-agent 的全项目
源码审计表明，这些项目都是产品级组合体，不能按仓库名称直接注册为一个平台包。候选拆分
应保持以下 owner：

| 源码中反复出现的能力 | 平台归属 | 说明 |
| --- | --- | --- |
| 文档读取、分块、Embedding、向量/词法检索、单条事实写入、来源摘要、模型 Provider 适配 | 支持库 | 输入/输出可独立契约化；第三方差异和资源释放在 Provider 边界收口 |
| retain/recall/reflect、个人画像投影、Episode/Step 轨迹、上下文装配、RAG 问答、角色/空间协作 | 模块库 | 需要多个原子能力、步骤顺序、领域状态、来源或补偿语义；调用方不应自行拼流程 |
| durable inbox、任务 claim、租约心跳、取消传播、重试/死信、压缩代际、资源账本、证据投影 | 运行核心/平台控制面 | 跨请求、跨进程或跨 Provider 的治理；不能由每个记忆或 Agent 模块各自复制 |
| 某项目的 UI、品牌、用户字段、默认模型、渠道别名、部署配置 | 项目适配层 | 只绑定项目选择与权限，不导入第三方实现，不持有底层连接或对象 |

补充两类容易误判的源码形态：

- **多存储记忆引擎**（EbbingFlow 类）：SQL 原件、图事实、向量索引、CDC 位点和画像/摘要投影
  必须拆成不同支持库与记忆模块；不能把一个同时连接 SQL、Neo4j、Chroma 的仓库整体注册成
  支持库。原始消息和来源证据的 owner 必须先于图、向量、Episode/Saga 等派生投影确定。
- **外部 API 客户端/边缘集成仓库**（Supermemory 类）：本地 SDK、MCP Worker、Web 控制台和
  schema 只能证明契约与适配边界；没有本地服务端路由、数据库、队列和索引实现时，不得把它
  误判为完整后端 Provider。服务端能力必须列为外部 Provider/待核，并通过真实 API 与资源
  证据后才能进入平台候选。

因此，“哪个更好”不是在支持库和模块库之间二选一，而是先按原子能力、领域流程和治理
职责拆分，再由能力契约决定唯一 owner。一个开源项目可以同时贡献三层候选，但同一能力
只能有一个权威归属；无法证明错误、取消、幂等、资源释放和真实返回值的部分，只能保留为
参考或兼容适配，不得直接装配进正式注册表。

开源项目只能提供候选实现。对同一原子能力，必须先做能力契约对齐，再按以下顺序
筛选唯一 owner：

```text
契约覆盖
  → 失败/超时/取消语义
  → 幂等与恢复
  → 资源释放与隔离
  → 真实返回值与容量证据
  → 维护/版本/许可证与适配成本
```

速度、项目名称、Star 数、README 宣传或“能导入”均不能单独决定归属。未达到真实
失败路径、资源归零和跨后端一致性证据的候选只能标记为“参考/兼容适配/待核”，不能
注册为平台权威提供者。

### 4.3 新增源码样本的归属裁决

#### BlackMoonKernelStaticLib：旧 ABI 是支持库适配边界，不是模块

该仓库的真实代码是一组 Windows/易语言运行时核心静态库和 MFC/DLL/EXE 入口，不是一个
可以直接注册到平台的业务模块。`krnln/lib.h:804-805` 暴露 `GetNewInf` 元数据入口，
大量 `krnln/krnln_*.cpp` 以 `LIBAPI` 接收 `MDATA_INF`；`krnln/BlackMoonDll.cpp:11-31`
把 `E_Init`、`DllEntryFunc` 和 `E_DestroyRes` 绑定到 DLL 生命周期；
`krnln/EyComInit.cpp:13-31` 负责进程堆、COM、外部支持库和全局销毁回调。

平台拆分如下：

| 源码事实 | 平台归属 | 处理原则 |
|---|---|---|
| `MDATA_INF`、`LIBAPI`、`GetNewInf`、调用约定和宿主通知码 | 公共契约 + 易语言 ABI 支持库适配层 | 只保留字段/错误/释放转换，不把旧 ABI 暴露给正式业务代码 |
| 文件、注册表、网络、DLL、COM、媒体等单个命令 | 对应原子支持库/受管 Provider | 一个外部边界一个 owner，统一权限、超时、取消和结果转换 |
| `E_Init`/`E_DestroyRes`、全局文件链、用户 DLL 列表和外部库通知 | 运行核心资源监督 | 不能复制到每个模块；必须登记 owner、终态和释放证据 |
| MFC/Win32 入口、32 位汇编和栈保护 | 项目适配层/隔离执行单元 | 仅在 Windows 受管 Provider 中使用，不能宣称跨平台已验证 |

关键结论：源码中出现 `LIBAPI` 不代表能力已经安全、可恢复或可跨平台。`krnln/open.cpp`
会创建并登记 Windows 句柄，`BlackMoonCallUserDll.cpp:23-69` 会直接 `LoadLibrary`/
`GetProcAddress`；这些都必须经过独立支持库契约和运行核心资源账本，不能整仓注册为一个
“黑月模块”。当前档案位于源码参考库对应项目根 `ARCHITECTURE.md`，其源码证据和 Windows
实跑缺口是候选输入，不是平台运行事实。

#### Claude-Code：产品编排进模块，底层通道进支持库，治理进运行核心

Claude-Code 源码快照的完整调用链是 `src/main.tsx` → `QueryEngine.submitMessage` →
`query` → 权限裁决 → 工具执行 → JSONL 会话落盘/自动压缩。`src/QueryEngine.ts:130-207,335-463`
定义会话状态和先写 transcript 的边界；`src/utils/permissions/permissions.ts:473-548`
及 `src/tools/BashTool/bashPermissions.ts:1663-1876` 形成多路权限和 Bash 安全链；
`src/utils/sessionStorage.ts:532-686` 以每文件队列、100ms 排空和 100MB 分块落盘；
`src/services/compact/compact.ts:387-599` 负责压缩、摘要和上下文重建。

对应的平台归属是：

- JSONL 追加、文件队列、终端解析、HTTP/流式传输、凭证/CA 文件等稳定外部边界，拆为
  支持库原子能力；支持库只返回统一结果和资源释放结论。
- 会话编排、权限决策、工具编排、自动压缩、恢复和 Agent 任务流程，归模块库；模块只组合
  支持库能力，不把某个 CLI 或 UI 当成平台核心。
- 跨请求的会话租约、后台进程、MCP/LSP 连接、Bash 子进程、端口、超时、取消、崩溃接管
  和 JSONL 未知发送状态，归运行核心/平台控制面。`cleanup` 函数存在不能替代零残留实证。

该快照当前已经建立独立 `.codegraph`，但没有完整依赖锁、可运行测试和外部服务验证；因此
只能作为源码结构和失败边界参考，不能直接作为平台 Provider 制品。它说明“模块库更好”
不是把整仓放进模块，而是把领域流程提取出来；底层通道与生命周期仍按支持库/运行核心
分层，避免形成第二套会话、权限或资源状态源。

### 5. 第二轮源码取证的最低深度

仅阅读已有 `ARCHITECTURE.md` 不再满足深度研究。每个项目的单文档更新必须以当前源码为
事实入口，按以下顺序执行，且不生成“第一批/第二批”平行报告：

```text
源码树清单与数量
  → 按目录/包名解释职责
  → README/启动入口/配置入口
  → 数据模型与持久化边界
  → 两条以上真实调用链（读到函数体和异常路径）
  → 队列/并发/取消/超时/恢复/资源释放
  → 测试与调用链覆盖核对
  → 直接去重写入唯一 ARCHITECTURE.md
```

这套顺序的对象是**整个项目**：文档必须先回答项目由哪些子系统组成、如何启动和装配、
端到端数据怎样流过各边界、哪些入口共用同一执行内核、哪些目录只是示例/工具/测试，
再下钻函数体。单独把某个 `add`、`search`、`run` 或 Provider 写得很细，不能替代全局
架构；若仓库含多个复制出口、语言子项目、服务和 CLI，必须分别标注其是否共享运行时、
数据模型和状态源。

“文件名看过”只能作为导航证据；“文档写过”只能作为待核索引。最终结论必须能回到
当前源码路径和行号。目录规模大时允许按入口、数据模型、任务执行器、Provider 和测试
分层抽样，但必须记录未读范围和抽样理由，不能把抽样结果写成全库事实。

本轮主会话对平台自身代码地图的现场核对已经发现：HTTP 提供者和流式 HTTP 通道有真实
超时、响应上限、连接释放、客户端断开、取消幂等和终态回调实现，但代码地图未发现覆盖
这些符号的完整测试关系。该项应进入“运行核心网关测试覆盖”待核清单；不能因为已有慢速
测试文件或文档描述就宣称所有路径已被覆盖。
