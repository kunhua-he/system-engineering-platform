## 缺口：裁决窗口落盘却从不复用 → 长场次永远收不了口

**现象**：全量队列反复卡同一批长场次（凌晨cc 2.9 小时、俏小喵 80 分钟等），产出停在
`8/10 窗口成功、2 个失败`，质检门禁正确拦下 → HTTP 500 → 下次重跑**又从第 1 窗开始**。

**现场取证**（`精校缓存/俏小喵轻简护肤_2026-08-22_20-06-37/08_裁决/`）：

| 窗口 | 状态 | 说明 |
| --- | --- | --- |
| 窗口_0001~0008 | 完成 | 精校文本齐全（如窗口_0008 有 2731 字符） |
| 窗口_0009 | 失败 | `提供者不可用: 模型 HTTP Provider 不可用：timed out` |
| 窗口_0010 | 失败 | `句柄失效: 句柄已失效（释放），不能自动复活` |

**根因**：`精校裁决.裁决窗口列表` 每次调用都把**全部**窗口重跑一遍；
`全自动精校` 虽然把每个窗口的结果落到 `08_裁决/窗口_NNNN.json`，但**从不读回**。
长场次窗口多（29 窗）单轮十几分钟，几乎必然有个别窗口碰上瞬时超时/句柄回收 →
整场判失败 → 重跑从第 1 窗重来 → 又可能碰新的瞬时失败 → **收不了口**（实测反复卡十余小时）。

## 修法

1. `裁决窗口列表` 新增 `已有窗口` 入参：按「区间id + 起止秒一致（容差 0.5s）+ 状态=完成 + 精校文本非空」复用；
2. **只重跑缺失与失败的窗口**，再按原顺序拼回（复用产物与原窗口一一对应，顺序不变）；
3. 全部窗口都有完成产物时**不连模型**直接回传（省一次冷启）；
4. 返回里带 `复用窗口数 / 重跑窗口数`，并写进质检报告（`裁决窗口复用`）便于诊断；
5. `全自动精校` 新增 `_读已有裁决()`，把 `08_裁决/窗口_*.json` 读出来传给裁决阶段。

时间范围容差是必要的：窗口切分随分段变化，旧产物若对应不同时间范围就不能复用。

## 被否决的做法

- **放宽质检门禁**（允许「裁决失败 N 个窗口」交付）：否决。未精校内容混进交付稿属静默降级。
- **只加重试次数**：不解决根因。重试是在**同一轮**内重试，轮与轮之间仍全部重跑；
  实测重试 3 次仍会出现「本轮修好的窗、下轮新坏的窗」，长场次照样收不了口。
- **把失败窗口的原始底稿当成品**：否决 —— 那就是把「未精校」冒充交付。

## 另一处现场问题：并行会话争用网关（非缺陷，是协作纪律）

复验时发现网关反复消失，根因是**同仓另一个会话正在跑「网关优雅停机」的正式反向验证**
（`/private/tmp/系统平台临时脚本_20260918/反验_停机两拍.py`，红拍/绿拍各会 `pkill` 并重启网关）。
本批全量精校依赖同一 40007 网关，两者相撞会导致：
- 精校在途请求全断（调用方侧有「等网关恢复 + 重试本场」兜底，不会白跑，但会拖慢）；
- 我发起的 `kickstart` 与对方反验的启停互相打断，**双方验收都不可信**。

**处置**：让路 —— 等对方反验结束再补做本修复的真实链路验收；期间不再 kickstart 网关。

**可复用判据**：在同一仓库跑长任务时，动手 `kickstart` / `pkill` 网关前先查
`ps -ww -ax -o command | grep -E '反验|测试|kickstart'` 是否已有会话在启停同一服务；
有则让路或改期，不要在别人的验收窗口里动同一资源（依 `多会话并行开发规约` 的资源键串行原则）。
