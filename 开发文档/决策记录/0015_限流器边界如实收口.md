## 背景

外部评审对平台提了一批架构批评，其中一条是：

> 「名字是『项目、用户、能力、任务、提供者五维限流与并发治理』，听起来特别高级。实际上目前核心就是一个
> Python dict + 一把 RLock + counter + 固定窗口。单进程可以。多进程呢？重启以后呢？多实例呢？分布式呢？
> 都没有天然成立。所以最直白的攻击就是：**名字的抽象等级高于实现的可靠性等级。**」

**现象属实**（2026-09-17 逐项取证，见 （一次性核对脚本，已随该轮结论并入本记录后删除））：

- `运行核心/统一网关/限流器.py` 的模块首行只写「五维限流与并发治理」，没有任何边界说明；
- 五个维度不是五套机制，是**同一套固定窗口计数换了五个维度键**（共用同一个 `限流状态` 结构体、
  同一把 `锁`、同一份 `频率上限表`）；
- 状态全在进程内（`状态表` + `请求并发`/`任务数`/`流式连接数`），**不落盘、不进权威状态库**；
- 权威状态库（`工程缓存/*/权威状态.db`）实测 22 张表，**没有限流相关表**；
- `进入任务` / `进入流式` 收五个维度参数但**不参与判定**，且**全仓无调用方**。

真实风险不是「实现弱」，而是**边界没被写下来**：调用方会误以为限流跨重启/跨实例生效，
于是扩容或双开时静默拿到 N 倍配额。

## 决策

**选 (a) 修名字与文档，不改造机制**——对「单进程网关 + 本机私有部署」这个既有安全边界而言，
进程内固定窗口本就够用；本轮只把话说准：

1. `运行核心/统一网关/限流器.py` 模块说明改为「**进程内固定窗口**限流与并发治理（五维键）」，
   并逐条写明：进程内 / 固定窗口非滑动 / 五维不是五套机制 / 只适用单进程私有部署 /
   多实例需外部共享限流（本平台当前不提供）/ 对外契约不变。
2. 类 `限流器`、`限流状态` 与 `进入请求` / `进入任务` / `进入流式` / `状态快照` 各补一段如实说明，
   明确「哪几维真被比对」「哪两个闸门没有调用方」。
3. 新增包级边界权威 `运行核心/统一网关/说明/限流边界说明.md`（名字↔实现对照表、
   两轴对照、升级触发条件、可复跑核对命令）。
4. 本轮增过一份可复跑核对脚本（**一次性，已随结论并入本记录后删除**；复跑口径见下方命令段）：
   既有行为取证，又断言上述措辞必须存在（删掉即变红）。
5. `开发文档/当前流程图.md` 与 `开发文档/方案/底座升级方案.md` 里相关措辞补口径。

**不动的东西**（这一条同样是决策的一部分）：所有并发保护（`最大并发请求` / `单维度并发` /
`最大任务数` / `最大流式连接`）、错误码 `限流`、HTTP 429 与中文错误说明文案，**一行不改**。
收口措辞不得顺手削弱能力。

## 考虑过的其他做法

| 做法 | 否决原因 |
| --- | --- |
| (b) 把限流改成持久化/跨进程（SQLite 或共享内存） | 单进程私有部署下这是**为假想需求付真代价**：加 IO、加一致性、加故障面，换来的可靠性在本平台边界外才有意义。第 11 条 1 项「缺能力先证不可替代」——现有能力在本边界内不可替代性不成立，**不装** |
| 引入 Redis 之类的共享限流 | 同上，且引入外部依赖；本平台是**单机私有部署**，为了「名字听起来更硬」上中间件是本末倒置 |
| 直接把「五维」这个词全删掉 | 五维**不是错的**（`进入请求` 确实按五个维度键分别计数），删掉反而是另一种失真；正确做法是**说清它的等级**（维度键，不是五套机制/不是分布式治理） |
| 只改代码注释，不写决策记录 | 只改注释会随下次重构漂移；且说不出「为什么不改造」，下次评审会被同一句话再问一遍 |
| 一并改 `网关核心.py` 首行的「五维限流」 | 该文件不在本轮允许修改域内（写者降级纪律），措辞记为遗留，下次动该文件时顺手改 |

## 后果

- 好处：任何人读 `限流器.py` 第一屏就知道它是**进程内固定窗口**；扩容/双开前会先看到「需外部共享限流」的警告；
  「五维」这个词有了明确定义（同一机制的五个维度键），不再是可随意拔高的形容词。
- 代价与限制：机制本身没有任何增强——**多实例部署仍然不成立**，本平台也仍然不提供共享限流。
  这条边界现在是**写下来的**，不是补上的。
- 注意：固定窗口在边界前后各一波流量可合计打到上限两倍，这是固定窗口的固有语义（不是 bug），
  排期时要知道。
