# 0008 能力更新走热接入，不重启 40007 网关

> 状态：现行
> 日期：2026-09-10
> 决策人：华哥

## 背景

底座能力（支持库 / 模块）的代码变更，过去靠重启 `40007` 网关进程生效。华哥指出这样有真实代价：

> 「你继续开发的时候，尽量用热加载的方式更新能力，而不是重启后端。不然 40007 端口一重启，其他的就很容易出毛病。你直接用热加载的方式，也是同样的，不会杀其他进程，如果热加载还不行的，你可以维护热加载的方式先。」

`40007` 是全机唯一执行网关，被 V3 业务后端、Agent 工具面等多个调用方依赖；重启会中断在途调用、打断句柄与租约，并可能牵连依赖它的其他进程。

## 决策

**能力代码变更一律走「热接入」，不重启网关进程。**

实施细则：

1. 改完能力（含新增包、改实现、改契约）后，调用网关 `热接入` 操作即生效：
   `POST http://127.0.0.1:40007/网关/调用` body `{"操作":"热接入"}`（需 `X-System-Credential` 凭证）。
2. `热接入` 的语义（后端核心既有实现）：只发现**新增包 + 源码指纹变化的变更包**并增量装配；已装配包的运行态与句柄全部保留；变更包重载前先弹出旧模块；装配失败在临时注册表内回滚，不破坏线上能力。
3. **不重启**的理由：不杀其他进程、不断在途调用、不打断句柄/租约、不影响依赖 40007 的其他项目。
4. 只有热接入**确实无法覆盖**的变更（例如网关自身 `运行核心/统一网关/` 的进程内代码变更）才重启；那种情况按「维护热加载能力」优先处理，而不是随手重启。
5. 新增/删除**包目录**同样走热接入：新增会被发现装配，被删包会被卸载并从注册表移除。

## 考虑过的其他做法

1. **重启网关进程**：否决。中断在途调用与句柄/租约，且牵连其他依赖 40007 的进程。
2. **只改 Python 文件不触发装配**：否决。已装配包在内存里跑的是旧模块对象，不触发装配不会生效（热接入会按源码指纹识别变更包并重载）。
3. **为每次改能力做全量装配**：否决。全量装配耗时长且会动全部包状态，违反「只动变更」的最小影响原则。

## 后果

- 好处：能力迭代几乎零中断（实测单次热接入 **0.24 秒**）；在途调用与句柄不受影响；其他依赖 40007 的进程不受牵连。
- 代价与限制：热接入只覆盖包级代码与契约变更；网关进程自身的代码变更仍需重启。变更包重载期间该包能力有极短窗口，调用方按统一错误码重试即可。

## 验证方式

1. **实测记录（2026-09-10）**：在 `命令安全` 实现中临时加入一条测试模式 →
   调用返回 `危险=False`（旧代码）；调 `热接入` 后返回 `危险=True, 原因=热接入验证命中`（新代码）；
   网关进程号 `56707` 全程未变；还原后再热接入即回到旧行为。
2. 常规用法：改能力 → `{"操作":"热接入"}` → 真实调用校验新行为 → 完成。
3. `热接入` 返回 `{新增包, 变更包, 卸载包, 成功包, 失败包, 已注册能力数}`，可用于核对改动是否被识别。
