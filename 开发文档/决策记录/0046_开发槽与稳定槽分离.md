# 0046 开发版与交付版分离：一条腿 + 两个槽 + 一条晋升管线

> 最后更新：2026-09-18
> 口径：设计决策（依据审计报告 §12；现状为**实测**）
> 维护者：小马仔

## 决策

**应该分，但分的不是两套代码，而是同一份源码的两个成熟度状态**
（开发中的工作区 vs 已交付的不可变制品）。

- **腿只有一条**：一个源码主干、一套核心、一条发布管线；不维护两套代码、不开 stable 分支、不建第二个源码仓。
- **两个槽（运行位）**：开发槽跑源码工作区（随便改、随便崩）；稳定槽跑**激活指针指向的不可变制品**。
- **一条晋升通道**：源码 → 候选制品 → 黑盒门禁 → 激活制品 → 发 Release。
  「感觉稳定」不算，**通过同一套机器门禁后被晋升**才算。

## 二、★ 现状（实测，正是「污染」根源）

- 机制**已具备约九成**：内容寻址不可变制品仓库（含 `编译清单/制品来源/完整性摘要/运行入口`，
  且制品从自己目录启动、不回读开发源码树）、激活指针 `工程缓存/制品仓库/平台客户端环境/当前.json`、
  HTML 验证器支持「验候选 → 成功才激活」与「只验已激活件」、发布门禁 + 事务恢复 + 回滚 = 切指针、
  运行隔离零件（动态端口 / 多实例池 / `--缓存根目录`）。
- **关键缺口（实测 plist）**：launchd `com.huashi.gateway-40007` 的
  `WorkingDirectory = <源码开发目录>`、`ProgramArguments = python3.14 运行核心/启动运行核心网关.py`
  —— **真正被调用的在线服务直接跑开发工作区源码**，而工作区常态存在未提交在途改动。
  重启/热接入后，半成品可能直接进入在线服务。
- 缺一个与稳定槽物理隔离的标准「开发态启动」入口。

**★ 补充实测（本轮）**：制品内已含 `平台客户端/运行核心/启动运行核心网关.py`，
即**稳定槽所需的服务入口在制品里已经存在**，切换具备前提。

## 三、目标形态

| 维度 | 开发槽（dev） | 稳定槽（stable） |
|---|---|---|
| 跑什么 | 源码工作区（可变） | 激活指针指向的不可变制品（独立安装位） |
| 端口 | 独立开发端口（**永不占 40007**） | 固定 40007 |
| 缓存/数据 | 独立 `--缓存根目录` + 独立或副本数据 | 正式缓存根 + 正式数据 |
| 谁能改它 | 开发者随时改源码 | 只有「发布激活」能原子切换 |

**升级不停机、可回滚**：激活切换时「停止收新请求 → 有界排空在途 → 整组回收常驻提供者（复用 P0-1 收尾链）
→ 原子切指针 → 启新制品 → `/就绪` 通过才放流量」；新件就绪失败自动回滚旧指针。

## 四、对外可见性

**推荐**：一个公开仓、一条主干；稳定边界由 **GitHub Release（语义 tag + 自包含制品资产 + latest/prerelease）** 表达。
**别人消费的是制品不是源码**（制品自包含、不含在途半成品与 `.git` 历史，天然干净且减小泄露面）。

**明确不建议**：① **stable 分支**（决策 0020 / 哲学 5.3 已禁止为发布开版本分支；分支不隔离运行，
还会制造「当前实现是哪一份」的歧义）；② **双仓镜像**（等于第二条腿：双向同步、漂移、每次发版重新脱敏、成本翻倍）。

## 五、落地清单

E1（**最关键**）40007 launchd 从「跑源码」切到「跑激活制品安装位」；
E2 固化标准「开发态启动」入口并写进规范（「开发只在开发槽，40007 永远是激活制品」）；
E3 一个「发版」命令串起门禁→激活→观察→打 tag→建 Release；E4 README 确立「稳定面 = Releases/latest」契约；
E5 激活切换接优雅停机 + 整组回收 + 三个探针；E6 制品保留沿用哲学 1.7。

**反向验证（必做）**：① 开发槽跑崩，断言 40007 行为与版本完全不变；② 改源码不发布、重启 launchd，
断言稳定槽仍跑旧激活制品；③ 推不达标候选，断言门禁阻断、指针不切换；④ 激活坏制品，断言自动回滚且服务不中断。

## 六、本批处置与风险

E1 属**不可逆动作**（改本机长期运行配置 + 影响在线服务），且**必须在源码树干净、门禁通过之后**做
（否则等于把在途半成品固化进稳定槽）。⇒ 本批**先落决策 + 方案**，
待维修批全部收口、门禁通过后，由主会话亲自执行切换并现场验证（含四条反向验证）。
