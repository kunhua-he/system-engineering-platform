# 0044 语言选型与容器边界：主干不换栈、热点只走独立进程

> 最后更新：2026-09-18
> 口径：设计决策（依据审计报告 §10，本批只落决策）
> 维护者：小马仔

## 一、决策（四条）

1. **主干 1–2 年继续 Python 3.14 + 标准库**，不整体换栈、不引入第二门主干语言，守住「一条腿」。
2. Python 的两个真实弱点**就地解决**：打包/环境（可选 standalone Python）与 CPU 热点（先建基准，用数据定位）。
3. 任何新语言**只能以「独立进程 + 公开契约」出现在支持库/适配层的提供者位置**，
   不得进主干、不得静态链接进主进程、不得成为第二条调用腿。
4. **容器分场景**：个人/Apple-Metal 阶段不做；未来若出现「Linux 上的纯 CPU 服务/网关」侧再容器化那一层，
   模型层始终留宿主机。触发线 = 出现多台 Linux 服务器或环境不一致造成真实排障成本，且先经 0042 的路线 B 真机验收。

## 二、第一性判断

- **「Python 全控制」是伪命题**：进程/进程组/信号/端口/显存/GPU 的真正所有者是**内核与硬件**，
  任何语言（含 C/Go/Rust/Java）都必须发 syscall 进内核、经驱动到硬件。C 也不能「全控制」，
  换近 syscall 的语言消不掉这条依赖，只是少一层解释器。
- **对本质依赖只有三招，本项目已在用前两招**：① 收口（OS 差异只进 `平台适配.py` / `进程终止.py` 两处）；
  ② 架构规避（独立进程 + JSON 行契约 + 句柄 + 进程组回收）；③ 收窄/固定环境（支持矩阵 fail-closed）。
- **GPU/Metal 更不可能被语言接管**：能选的是「绑定哪家硬件生态」，是部署决策不是语言决策。
- **负载性质**：Python 主干是**编排/治理层**（I/O 密集），重计算在外部独立进程（llama-server/MLX）；
  GIL 不构成吞吐瓶颈；「多进程隔离 + 有界线程」正是 I/O 密集编排的正确形态。

## 三、容器边界（关键事实）

Mac 上 Docker/OrbStack 跑的是 **Linux 虚拟机**，而 macOS 虚拟化**没有把 Metal GPU 暴露给客户机的官方接口**
→ 容器内拿不到 Metal/MPS/ANE，模型只能退化为 CPU。
⇒ **最痛的「模型/显存/孤儿进程」恰恰是容器装不下也不解决的问题**（容器里照样要管进程组）；
容器能可靠打包的是**无 GPU 的编排/服务层**。
**收口层与容器互补不替代**：收口层解决跨内核家族（macOS↔Linux）差异；
容器解决同一内核家族内部的用户态一致性。

## 四、各语言定位（结论）

Python（标准库）= 编排治理主干，冻结；C = 仅在被基准证明的热点做独立进程小内核，**基准证明前不引入**；
Java = **纯亏不引入**（重运行时违背零依赖、现有中文资产作废、等于第二条腿）；
Go = 若从零写会考虑（单二进制部署舒服），**但现在不是从零，换栈严重不对等**；
Rust = 未来单个被证明的 CPU 热点候选，不作主干。

## 五、边界表（冻结）

| 职责 | 技术选择 | 位置 |
|---|---|---|
| 编排/治理/网关/状态/门禁证据 | Python 3.14 标准库（主干，冻结） | 运行核心 / 平台控制面 |
| 模型推理/语音转写（GPU） | 宿主机独立进程 + MLX/llama/Metal | 支持库提供者（独立进程） |
| 未来被基准证明的 CPU 热点 | Rust（首选）或 C，独立进程 + JSON 契约 | 支持库/适配层提供者 |
| Linux 纯 CPU 服务的部署打包 | 容器（未来，按触发线） | 制品/部署层，不动架构 |
| 跨平台差异 | 永远只在 `平台适配.py` / `进程终止.py` 两处 | 公共契约/运行时 |

## 六、决策顺序（固定）

**基准先行（B2）→ 无数据不引编译语言/容器 → 真要引入也只落在边界（独立进程/打包层），主干与契约不变。**
