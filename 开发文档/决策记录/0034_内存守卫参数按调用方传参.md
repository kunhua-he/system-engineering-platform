## 起因：全量队列整批 500，报「拒绝启动新模型」

现场 848 场队列在 01:06–01:33 连续失败，每场 6 秒即返回 `HTTP Error 500`。
从底座侧取到的原文是内存守卫拒绝：

```
系统内存压力：当前占用 63.8%，新连接预计 +21.2GB 将达 81%（安全阈值 80%），
拒绝启动新模型以防撑爆内存。请释放不用的模型连接（总 96.0GB / 可用 34.7GB）
```

## 两个必须分清的口径（我一开始也搞错了）

| 口径 | 取值 | 性质 |
| --- | --- | --- |
| `psutil.virtual_memory().percent`（= 活动监视器「内存」、底座守卫所用） | 63–73% | **标准口径**，反映真实占用 |
| `top` 的 `PhysMem used` | 85–95% | **宽口径**：含文件缓存与 inactive 页，macOS 随时可回收 |

**教训**：判断「内存是否吃紧」不能用 `top` 的 `PhysMem used`。正确做法是
`psutil.percent`（或活动监视器）+ `sysctl vm.swapusage` 余量 + `wired` 是否含可回收项。
本次一度把 91G/96G 当成「内存耗尽」，实际当时标准口径只有 73%，属误判。

## 真问题：守卫阈值是「策略」，不是「物理装不下」

守卫算术 = `(当前已用 + 新模型预计) / 总量 > 阈值(默认 0.80)` 即拒绝。
本机基线（Chrome 关掉后）约 61GB，模型预估 21.2GB，合计 82.2GB = 86% > 80% → 拒绝。
而机器实际装得下（96GB 里还剩约 14GB，实测模型加载后一切正常）。

**这不是物理不足，是默认阈值偏保守**（80% 阈值意味着基线必须 ≤ 55.8GB 才允许 21GB 模型）。

## 修法：按既有哲学——**调用方传参选边界，不改默认值**

守卫读取的三个键（`内存估算系数`、`内存安全阈值`、`模型大小字节`）此前只有 `模型大小字节` 能透传，
另两个调用方想调也传不进来（又一处「参数收了不用」）。本次在 `精校裁决.连接裁决模型` 的可选透传元组里
补上 `内存估算系数`、`内存安全阈值`，底座默认仍为 1.15 / 0.80 不变；由调用方按实测校准：

```python
裁决模型 = {..., "内存估算系数": 1.08, "内存安全阈值": 0.90}
```

- `1.08` = 实测标定（模型文件 19.8GB，真实 RSS 21.4GB；底座默认 1.15 会把 19.8GB 估成 22.8GB）；
- `0.90` = 本机实测下「能装下且不触发换页」的上限；只作用于本批任务的裁决连接。

**实测复核（当时误判，见文末纠正）**：四种参数组合（基础 / +系数 / +阈值 / 两个都加）全部 `成功=True`，
模型冷启后 RSS 21.2GB、驻留在网关名下（父进程 = 网关，非孤儿）。

## 现场纠正（2026-09-18 01:45）

按上面写法实际投入全量队列后，**整批 848 场秒失败**，从网关取到真实正文：

```
错误码: 裁决失败
错误说明: 提供者不可用: 裁决模型连接失败: TypeError:
          能力 大语言模型支持库.模型连接器.连接LLM 收到未知参数: ['内存估算系数', '内存安全阈值']
```

**两个错**：

1. `连接LLM` 的能力声明（`能力定义.json` 12 项 + 注册元组）**没有这两个参数**，
   传进去会被网关判「收到未知参数」——这正是本平台「改契约必须同步三处」的老坑。
2. 我先前那次「四种组合全部成功」的实测**不可采信**：当时模型实例已存在，
   调用命中的是复用路径，没走到参数校验。**验证必须在「目标状态」下做**
   （要验冷启动参数，就必须先卸掉实例），否则是假绿。

**当前结论**：调用方**不再传**这两个键（已回退），队列恢复；要真正启用「调用方传参选边界」，
需要按平台规矩把两个参数补进 `连接LLM` 的三处声明（能力定义 + 参数契约 + 注册元组），
已登记进 `开发文档/未完成事项.md`。在补齐之前，守卫只能用底座默认值（1.15 / 0.80）。

## 被否决的做法

- **直接把底座默认阈值从 0.80 调高**：会影响所有调用方（含 V3、其它业务），
  违反「扩展现有能力、默认行为不变」；正确做法是调用方显式传参。
- **不加载模型、降质量跑**：否决。裁决是精校的核心质量环节。
- **常驻占用内存不释放**：否决。同一天已有实证——4 个僵尸模型实例各攥 6.5GB wired
  导致模型被换页、速度掉到 8.6 tok/s（见决策记录 0019）。

## 顺带纠正的两处观测错误（自查）

1. `ps ... | grep php` 的聚合把路径含 `php` 的**其它**进程也算进来，一度报出「PHP-FPM 51 个进程占 12.85GB」，
   实测 PHP 只有 1 个进程 8MB。**聚合关键词必须精确匹配可执行名，不能拿子串扫全命令行。**
2. 「Chrome 18.9GB」也有同样问题；按精确匹配实测为 **11.1GB**。报数前应先做一次口径自检。
