# 0014 转码能力升级为硬编并支持音频直通与免 base64

> 状态：现行
> 提出：2026-09-16（直播存档批量压缩实战，华哥裁决「缺能力或效率低就升级成效率最高、最稳定的方式」）

## 背景

直播录像存档压缩需要把 1.1 TB 原始视频压到约 250 GB。调用现有 `媒体处理支持库.FFmpeg媒体.转码` 时实测发现三处硬伤：

1. **没有视频编码器选择**：命令为 `ffmpeg -y -i 输入 + 白名单参数 + 输出`，未指定 `-c:v`，对 mp4 落到 libx264 软编。M3 Ultra 上软编约 3.5x 实时，而 `hevc_videotoolbox` 硬编同片源实测 48x 实时（14 路并发下），相差一个数量级；1.1 TB 量级用软编不具可行性。
2. **改不了码率上限**：VideoToolbox 单独传 `-b:v` 会被忽略，必须 `-b:v + -maxrate + -bufsize` 三件套；白名单里没有后两项，无法表达三件套。
3. **音频必然重编码**：白名单只有「音频码率」，没有音频直通。已知「音频直通（`-c:a copy`）能保证语音零损失、不卡顿」是本场景的硬要求（华哥口径：画质可以降，语音不能卡），而重编码会引入额外损失。

另有一处效率问题：返回值固定携带 `字节b64`，即把整个输出文件读进内存再做 base64（体积 ×4/3）。存档场景输出本就落在磁盘指定路径（`输出路径` 参数），再回传一次纯属浪费——实测 200 MB 输出的 base64 字符串约 267 MB。

## 决策

**不新增重复能力，只扩展 `媒体处理支持库.FFmpeg媒体.转码` 的白名单与返回值**，保持「同一职责全平台只保留唯一一套」：

1. 编码选项白名单新增 6 项：`视频编码器`、`音频编码器`、`码率上限`、`缓冲`、`视频标签`、`预设`。原有 4 项（分辨率/视频码率/音频码率/帧率）行为不变。
2. 新增 `返回字节`（逻辑型，默认 `是`）。为 `否` 时返回值省略 `字节b64`，只回 `格式 / 字节数 / 输出路径`；已落盘场景不再做 base64。
3. 本期**不改**默认行为：不传 `视频编码器` 时仍是原来的不指定编码器（等价 libx264 软编），避免影响既有调用方。

高效压缩的推荐组合（写进契约说明与使用说明）：

```text
视频编码器=hevc_videotoolbox
视频码率=900k   码率上限=1100k   缓冲=2200k
帧率=15
视频标签=hvc1        # hevc 在 QuickTime/多数播放器正常播放的前提
音频编码器=copy      # 语音零损失
返回字节=false
```

**落地必须同步三处，只改契约 JSON 不生效**（本轮实测踩坑，见「后果」）：

| 位置 | 作用 |
|---|---|
| `支持库/.../FFmpeg媒体/实现/处理.py` 的 `编码选项表` | 参数生成与取值正则校验 |
| `支持库/.../FFmpeg媒体/__init__.py` 的 `注册能力` 参数元组 | **运行期参数白名单（漏改就报「收到未知参数」）** |
| `能力契约/参数契约.json`、`能力定义.json`、`包声明.json`、`能力数据/*.json`、`说明/*.md`、`完整性摘要.json` | 契约、目录、说明书与摘要 |

模块库门面（`模块库/媒体处理`）同源：`__init__.py` 的参数名列表要加，类型表由模块契约自动派生，不必手写。

## 考虑过的其他做法

1. **新增独立能力「视频压缩」** —— 否决。与 `媒体处理.转码` 属同质能力，违反唯一性；且会造成同一 ffmpeg 参数拼装逻辑维护两套。
2. **直接把默认编码器改成硬编** —— 否决。会静默改变所有既有调用方的输出编码（H.264 软编 → 硬编），画质与兼容性行为一起漂移，属于「信封只增不改不删」红线外的破坏性变更。
3. **调用方自行拼 ffmpeg 命令（脚本内直调）** —— 否决。这是第二执行腿，绕开唯一能力入口和统一治理；本轮已把批量脚本改为经网关调用，脚本不再出现 ffmpeg 命令行。
4. **给返回值加 `返回字节` 之外再暴露输出路径以外的传输方式** —— 暂不做。当前场景只需「文件已在磁盘」，无跨机传输需求，等出现真实需求再评估。

## 后果

- 好处：
  - 硬编一键可用，实测压缩 1.1 TB 量级的可行性从「不可行」变为「约 13 小时」；
  - 音频直通保住了「语音不卡」这一硬要求，且压缩后的素材仍可继续用于 ASR/精校（音频未被改动）；
  - 免 base64 让大文件调用不再产生 4/3 倍内存放大。
- 代价与限制：
  - 白名单由 4 项变 10 项，契约与说明书同步面变大；新增项必须三处同改，漏改的报错现象是**运行期「收到未知参数」**（契约 JSON 已改、`注册能力` 元组未改时），不是启动期报错，容易误判成契约没生效；
  - `最大输出字节` 属整数型且受 int32 上限约束，传 `4294967296` 会被判「必须是整数型」；调用方需传 ≤ 2147483647 的值；
  - 默认行为未改，调用方必须显式传参才能获得硬编，属于「约定优于默认」的取舍。
- 本轮未走通统一编译链路：`开发工具/项目编译/项目编译器.py` 要求「项目必须提供 项目声明.json 或 项目.json」，而本仓库根目录没有该文件（只有 `示例项目/*` 下有），能力变更无法用统一编译器编译。已登记进 `开发文档/未完成事项.md`。本轮以 `py_compile` + 网关重启 + 真实 HTTP 调用作为验证手段。

## 验证方式

```bash
# 1) 语法
python3.14 -m py_compile "支持库/后端/媒体处理支持库/FFmpeg媒体/实现/处理.py" \
                          "支持库/后端/媒体处理支持库/FFmpeg媒体/__init__.py" \
                          "模块库/媒体处理/实现/媒体处理.py" "模块库/媒体处理/__init__.py"

# 2) 摘要重算（改实现后必须）
python3.14 -m 开发工具.全量重算摘要

# 3) 重启网关后经唯一入口真实调用（中文路径必须百分号编码）
curl -X POST "http://127.0.0.1:40007/%E7%BD%91%E5%85%B3/%E8%B0%83%E7%94%A8" \
  -H 'Content-Type: application/json' -H "Authorization: Bearer <网关凭证>" \
  -d '{"操作":"调用能力","能力id":"媒体处理.转码","参数":{
        "文件路径":"<绝对路径>","输出格式":"mp4",
        "编码选项":{"视频编码器":"hevc_videotoolbox","视频码率":"900k","码率上限":"1100k",
                   "缓冲":"2200k","帧率":"15","视频标签":"hvc1","音频编码器":"copy"},
        "输出路径":"/tmp/出.mp4","超时秒":600.0,"最大输出字节":214748364,"返回字节":false}}'
```

判据：`成功=true`；返回值只有 `格式/字节数/输出路径`（`字节b64` 缺席＝免 base64 生效）；`ffprobe` 输出为 `hevc`、帧率 15、时长与源一致、音频流存在且未被重编码。

2026-09-16 实测：源 29 MB → 15.2 MB（`hevc 720x1280 15/1 0.77Mbps`，音频 aac 保留），HTTP 200、耗时 34.6 秒；批量经网关调用 426 MB → 151 MB（省 65%），时长一致、源已删。
