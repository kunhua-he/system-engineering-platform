## 裁决一：版本递增的判据＝**对外契约指纹是否变化**，不是「文件改没改」

**判定规则（唯一口径）**：

```
对一次改动，算本包（或本能力）的**对外契约面**：参数【名称 / 类型 / 必填 / 默认值】+ 返回类型
+ 错误码集合 + 副作用 / 资源类型 / 宿主 / 权限　——　**不含说明文案**（`说明`/`值结构` 等纯文档字段，
改它们不算契约变化；与决策记录 `0019` 第 3 项「值结构只作文档性描述」同口径）
        ↓
用 契约指纹() 算指纹，或用 检查契约兼容(旧契约, 新契约) 判定
        ↓
┌─ 指纹不变（完全兼容）→ **纯内部优化 / 性能 / 重构 / 改名（对外名不变）**
│     → 允许直接更新，**不要求版本号递增**，不产生兼容负担、不要求说明书版本行同步
└─ 指纹变化（不兼容或有新增对外面）
      → **必须递增版本**（能力级 / 包级按实际变化范围）
      → 旧版本按 `版本注册表` 引用保护保留；**无引用才允许清理**（`弃用清理.py` 已有流程）
```

**推论（直接解决现有债务）**：
- 说明书「包级版本单向滞后 102 包」：**若契约未变，版本行滞后不是缺陷**，不必为对齐而改版本；
  只有契约变过的包才需要同步版本行。→ 该债务按此口径重新定性（从「102 包欠账」降为「按契约变化逐包核」）。
- 边界能力（`_JSON`、`_flush_visible` 这类英文函数名）改名：**属内部优化**，不触发版本递增。
- 判据/类型名收口（如 `数值型` → 正式名）：**属对外面变化**（参数类型声明变了）→ 要按变化范围递增版本。

**被否决的做法**：
1. **「改了文件就要升版本」** —— 华哥明确指出这没必要；而且会把版本号变成噪声，
   真正需要版本区分的契约变化淹没在无意义的递增里（违反第 11 条：判定必须用数字）。
2. **给内部优化也保留一份旧版本** —— 制造无价值并存版本，污染能力数、门禁扫描与说明书对账。
3. **靠人工判断这次算不算契约变化** —— 已经有 `契约指纹()` 与 `检查契约兼容()` 两个机器判据，
   人工判断必然分叉，且违反「判据必须机器可验证」。

## 裁决二：**源码不保留版本**，版本控制只保留到编译产物

**裁决**：源码只保留**一条主干**；历史版本的载体是**不可变制品**（`工程缓存/制品仓库/平台客户端制品/平台客户端-<摘要16>`）
与**激活指针**（回滚 = 切换指针，不恢复源码旧版本）。**不保留源码的版本分支 / 旧版本源码副本。**

**三条依据**：
1. **已有机制就是这样**：现有回滚只切换不可变旧制品与激活指针，且已明文禁止「恢复源码 v0 分支或翻转废弃标记」
   （见 `AGENTS.md` 分层职责与哲学）。
2. **源码可从制品取回**：制品内本身就是完整的 `平台客户端/…` 源码副本（含包声明、能力契约、实现），
   所以「旧版本源码」并没有丢，只是不再作为第二份源码树存在于仓库里。
3. **保留源码版本会破坏唯一事实源**：源码树一旦出现 v0/v1 两个版本，就会出现「当前实现是哪份」的歧义，
   并必然有人直接 import 旧版本 —— 这正是「两条腿并存」问题的根源（本轮 D-1 就是它的一个实例）。

**GIT 的定位（不要混淆）**：git 保留的是**开发历史**（谁在什么时候为什么改），
不是**发布版本**。发布版本由不可变制品承担。两者互不替代。

**被否决的做法**：
1. **为每个发布版本在仓库里留一份源码副本** —— 与不可变制品重复，制造第二份事实源；
   且旧源码树会被人直接 import（已有前车之鉴）。
2. **用 git 分支/标签保存发布版本源码** —— 同样制造第二份真相；且回滚时要把制品与源码树同时对齐，
   引入「制品与源码不一致」的新故障类。
3. **回滚时恢复源码 v0** —— 已被明文禁止（制品不可变 + 指针回滚已足够）。

## 落地（工程动作）

1. **判据模块（新增，不改既有文件）**：`开发工具/契约编译/对外契约变更判定.py`
   - 输入：包目录（或制品目录）与「基线」= 当前**激活制品**内的同名包；
   - 输出：`{变更类别: 内部优化 | 契约变化, 变化明细: [...], 是否要求版本递增: bool, 兼容判定: ...}`；
   - 复用 `契约指纹()` 与 `检查契约兼容()`，**不另写第二套指纹算法**（唯一事实源）。
2. **门禁接入**（留待发布门禁串行轮，避免与在跑批次冲突）：契约指纹变化而版本未递增 → 判红（fail-closed）；
   指纹不变 → 明确报「内部优化，放行」。
3. **文档**：本条以 5.3 写入 `开发文档/项目说明.md` 设计哲学第 5 条；说明书版本行口径同步。
4. **验收口径**：三档真实对照——① 纯内部改动（改实现不改契约）→ 判「内部优化、不要求递增」；
   ② 改参数类型/新增必填 → 判「契约变化、要求递增」；③ 递增版本后 → 放行；
   并给出反向验证（把版本号改回 → 必须真判红）。
