## 一、问题（现场实测）

新建 `支持库/后端/项目文档支持库` 后，本地装配把它**整包跳过**：

```
[装配告警] 已跳过 支持库.后端.项目文档支持库｜装配前预检｜依赖锁为空（包与直接依赖均为空，禁止装配提供者）
状态: 运行中 能力数: 668 跳过包: 1
```

而 40007 网关热接入同一份源码是**成功**的（能力数 675）—— 两条装配腿对同一个包给出相反结论。

## 二、根因：架构不足，三处断链

判据本身**早就存在且唯一**：`运行核心/运行环境管理器/环境管理器.py.检查依赖锁内容`。
缺口在「表达不统一」与「判据没接到生成链」：

| # | 断链 | 现场证据 |
|---|---|---|
| 1 | **模板无条件生成空壳锁**：`支持库模板生成器.py` 的 `_数据表` 里 `依赖锁.json` 写死 `"包": []` / `"直接依赖": []`，与「无第三方依赖」的仓内口径相冲 | 模板刚生成的参照包带着空锁 |
| 2 | **`重建依赖锁` 从不判「锁该不该存在」**：幂等口径只管 `环境` 三元组与 `生成时间`，空锁被当合法锁刷新并盖章 | 空锁被写入 `生成时间` 与 `环境` |
| 3 | **判据只在装配期被调**：`检查依赖锁内容` 的调用点只有 `运行核心/加载器/生命周期管理/管理器.py:139`（装配预检）与 `环境管理器.py:307`；**组件合规 / 公开调用完整性门禁 / 环境自检 三环零调用** | 生成期可以产出「注定过不了装配」的产物而无人拦 |

全仓事实口径（实测）：**依赖锁存在 ⟺ 有第三方/外部依赖**
- `支持库/后端` 78 包：有锁 16（锁非空 15 + 空锁 1 即本项目文档支持库）、**无锁 62**
- `支持库/适配层` 17 包：17 份全有锁且非空

即：**无第三方依赖的正确表达是「不存在依赖锁.json」**，`检查依赖锁内容` 也明写「锁文件缺失 → 不在此判定（由调用方按『无第三方依赖』处理）」。空锁是**第三种表达**，且恰好是被装配 fail-closed 拒掉的那一种。

## 决策

### 3.1 表达收口：无第三方依赖不建锁

- 模板只在 `第三方说明` 非空时生成 `依赖锁.json`；无第三方**不生成该文件**（缺失就是无第三方的唯一表达）。
- `重建依赖锁` 增加空锁判定：**锁内容为空（包 + 直接依赖都空）→ 不写、如实报告「无第三方依赖，不建锁」**，并提示存量空锁应删除。

### 3.2 判据接线：生成链必须调同一个判据

把 `检查依赖锁内容`（**唯一实现，不另写一份判据**）接进 `开发工具/公开调用完整性门禁.py`：遍历正式包，凡返回非空错误码即计新增违规。
选它作为落点的理由：它是「新增违规即红、存量走基线」的门禁，天然适合拦「新包带空锁」这类回归；组件合规管的是九要素结构（依赖锁不在九要素里），环境自检管的是「锁与当前平台指纹是否一致」，都不判「锁该不该存在」。

### 3.3 为什么不在装配层放宽

把「空锁」改成放行，等于承认空锁合法，会让「无第三方」出现两种等价表达（缺失 / 空壳），后续任何按锁判断依赖的程序都要判两遍。**按哲学 1.3 结果唯一即收口：收口在表达侧（不建），不在判定侧（放宽）。**

## 考虑过的其他做法

| 做法 | 否决理由 |
|---|---|
| 装配层把空锁当「无第三方依赖」放行 | 承认第三种表达合法，等于把「同一件事两套表达」制度化（违反 1.3） |
| 给本项目文档支持库伪造一条第三方依赖把锁填满 | 假数据骗过门禁，且会让「依赖锁=有第三方」这条仓内铁口径出现反例 |
| 只删这一份空锁，不动模板与门禁 | 属单点修复：模板还会继续造空锁，门禁仍然不拦，同类缺陷必然复发 |
| 在编译器里判定依赖锁 | 依赖锁不是编译派生物（它不是从 `能力定义.json` 生成的），塞进编译器会让编译器职责越界 |
| 另写一份「空锁检查」判据 | 判据已有唯一实现（`检查依赖锁内容`），重写＝第二事实源（违反 4.4） |
