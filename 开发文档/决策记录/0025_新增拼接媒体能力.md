- 影响面：`支持库/后端/媒体处理支持库/FFmpeg媒体`（新增能力）、

## 背景：能力缺口是怎么暴露的

直播逐字稿精校（`直播逐字稿.全自动精校`）的入参是**单个源文件绝对路径**，而抖音直播
录像按「场次 = 多个分片（`_000`/`_001`/…）」存在 —— 全量 971 场里 **698 场是多分片**。
底座当时只有「合并文本文件」，**没有拼接媒体能力**，于是占 72% 的场次无法进入精校链路。

按平台铁律（能力缺口在底座补齐、不在调用方另起一套），在 FFmpeg 媒体支持库补一个
原子能力，而不是在业务脚本里直调 ffmpeg。

## 决策：concat demuxer + `-c copy`，不重编码

录制分片本身是完整 mp4，且同一场次的分片编码参数一致（同一录制档位、同分辨率/帧率）。
因此用 ffmpeg concat demuxer + 流复制：

- **秒级完成**：100+42 MB 两段实测 **0.4 秒**（重编码方案需要数分钟且吃 GPU）；
- **零画质损失**：`-c copy` 比特流原样搬运，画质与音频与源完全一致（逐字稿/精校依赖音频，不能受损）；
- **不吃 GPU**：与正在跑的批量转码、本地 LLM 推理不抢资源，可并行；
- **失败即明确失败**：分片编码参数不一致时 concat 直接报错，统一回报 `进程崩溃`，
  **不会产出看似成功的坏文件**（本库既有原则：失败必须明确，不许伪造成功）。

清单文件用 `-safe 0` 允许绝对路径；路径里的单引号按 concat 语法转义（`'` → `'\''`），
否则带引号的文件名会让清单被解析错位。

## 被否决的做法

1. **在业务脚本里直接调 ffmpeg concat**——就是第二执行腿，违反唯一调用入口；
2. **用 filter_complex concat 重编码**——慢（分钟级）、吃 GPU、有画质损失，全是白付的代价；
3. **转成 TS 再拼接**——多一次全量读写，对本场景（完整 mp4 分片）无收益；
4. **逐分片精校再拼文本**——丢跨分片上下文，逐字稿首尾会出现断裂的句子。

## 踩坑：模块库改能力必须同步「能力定义 + 契约」，否则整包被跳过

新增模块层门面时只改了 `__init__.py` 的注册元组，**没有同步模块的
`能力定义.json` 与 `能力契约/参数契约.json`**。模块的 `注册能力` 是拿契约里的类型表
逐个取值（`类型表[能力id][名称]`），契约里没有新能力 → `KeyError` → 注册抛错 →
装机时**整个「模块库.媒体处理」被跳过**，连原本正常的 `媒体处理.转码` 也一起不在册
（表面现象是「新能力不存在」，实际损失是整个包）。

正确顺序：**能力定义.json（唯一事实源）→ 跑 `能力定义编译器.编译能力定义()` 生成
参数契约/能力数据/包声明/摘要 → 再让 `__init__.py` 引用**。支持库与模块库都要走这一遍，
两侧的派生物都不能手写。

## 验证（真实 HTTP，非推断）

```json
// 入参：两个真实分片（105 MB + 42 MB，同一场次）
{"能力id":"媒体处理.拼接媒体","参数":{"文件列表":[…_000.mp4, …_001.mp4],
  "输出路径":"/tmp/拼接验证.mp4","输出格式":"mp4","超时秒":300.0}}

// 返回
{"成功": true, "值": {"字节数": 153,958,400, "输出路径": "/tmp/拼接验证.mp4"}}
```

- 耗时 **0.4 秒**；
- **时长校验：两段合计 2529.8 秒 → 拼接后 2529.8 秒（差 0.00 秒）**；
- 编码 `hevc 720x1280 15fps`、音轨 `aac` —— 与源一致，未重编码；
- 负向用例：不存在的分片 → `文件不存在`（校验生效）；装配能力数 658 → 664。

备份：`/tmp/底座拼接能力备份_20260917/`。

## 调用方约定

- `文件列表` 至少 2 项，顺序即拼接顺序，按分片序号升序传入；
- 建议 `返回字节=否`（整场动辄几百 MB，base64 会放大 4/3 且吃内存）；
- 拼接产物是**中间物**：整场精校完成后即可删除，不必长期保留（缓存目录由调用方管）。
