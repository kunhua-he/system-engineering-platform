# 0028 网关重启遗留模型孤儿 → wired 显存泄漏拖慢推理

- 日期：2026-09-17
- 状态：**已现场处置 + 调用方侧已加防护；底座侧根治待实施（已登记未完成事项）**
- 现象现场：全量精校（852 场）单场耗时从 7 分钟劣化到 30+ 分钟，模型生成速度掉到 8.6 tok/s

## 现象与测量

现场三组独立测量（都在同一时刻）：

| 指标 | 实测 | 正常参照 |
| --- | --- | --- |
| 模型生成速度 | **8.6 tok/s**（4 槽合计约 34 tok/s） | 该模型应 20+ tok/s |
| 模型进程 RSS | 从 32.9 GB 掉到 **14 GB** | 权重常驻约 21 GB |
| 系统 swap | **35.4 GB / 37.9 GB**（99%） | 趋于 0 |
| swapouts 速率 | **10616 页/秒（166 MB/s）** | 偶发（< 1 MB/s） |
| 系统 wired | **39.2 GB** | 与 GPU 实际在用（12.7 GB）相称 |
| GPU 驱动分配池 | 46–53 GB（在用仅 12.7 GB） | — |

即：**模型权重被换出到磁盘、每生成一个字都要读回**，速度掉到 1/3。

## 根因链（四步，缺一不成立）

```
① 网关被外部终止（退出码 15 = SIGTERM，来源未明）
   ↓
② 它启动的 llama-server 子进程成为孤儿（PPID=1）
   —— 「睡眠」（--sleep-idle-seconds 300）只卸权重，**进程仍攥着约 6.5 GB wired 显存**
      （Metal 上下文不释放，ps 里 RSS 显示 0，极易漏看）
   ↓
③ 网关重启后，内存里的模型实例索引（全局模型索引/本地进程表）随进程消失，
   下次 连接LLM 认为是「无实例」→ 再起一个新的；旧孤儿无人认领
   ↓
④ 每次网关重启漏一个孤儿：当晚 5 次重启攒 4 个 = **26 GB wired 被白占**；
   wired 不可换出 → 把模型自己的权重挤进 swap → 8.6 tok/s
```

## 现场处置（已验证）

杀掉 4 个孤儿（PPID=1 且命令行含本任务裁决模型路径），实测回收：

| 指标 | 处置前 | 处置后 |
| --- | --- | --- |
| wired | 39.2 GB | **12.8 GB** |
| GPU 驱动分配池 | 53.5 GB | 35.2 GB |
| swap 已用 | 35.4 GB | **21.7 GB**（系统自动回收 13.7 GB） |
| 可用内存 | 8.9 GB | **28.3 GB** |
| PhysMem | 94 G / 96 G | 75 G / 96 G |

**不需要重启机器**（一度以为需要）。清理后可用内存 42 GB，4 路精校继续跑。

## 调用方侧防护（已加）

精校看门狗每轮巡检先执行「孤儿模型回收」，判据三重且不按端口盲杀：

1. 进程名 `llama-server`；
2. 命令行含本任务的裁决模型路径（`~/Documents/AI模型/文本模型/Qwen3.6-27B-Q5_K_M.gguf`）；
3. **父进程为 1**（说明原来拥有它的网关已不在）。

第 3 条是关键：正常在用的实例父进程是网关，只有真正被遗弃的才会落到 1。实测回收 4 个孤儿。

## 底座侧根治（未完成，已登记）

调用方兜底不是终点。底座应做到「**启动时按状态机登记的归属回收上一进程遗留的模型子进程**」：

- 依据现成件：句柄系统已按 `登记资源(句柄id, 资源类型="进程", PID=进程.pid, 端口=端口)` 落库，
  权威状态账本天然持有「谁启动的、PID 多少、端口多少」，**不需要新造登记**；
- 缺口：网关启动流程没有做这一步，账本里的旧 PID 只在「宽限期后判死」路径被处理，
  而孤儿进程**并没有死**（只是没人用），所以判死路径不会碰它；
- 期望行为：网关启动时按账本取「资源类型=进程 且 所有者=本地模型-*」的旧记录，
  校验 PID 仍存活且**其父进程已不是本进程**（证明是新旧两代）后按归属杀掉；
- 顺带收益：V3/其它调用方重启网关时也不会再漏模型实例。

## 被否决的做法

- **重启机器**：一开始判断需要（swap 满、wired 高），实测发现 wired 的大头是可回收的孤儿，
  清完即恢复；重启会无谓中断微信容器与录制器。
- **按端口号盲杀 llama-server**：会误杀 embedding/rerank 等合法长驻服务（它们的父进程同样是 1），
  违反「按状态机登记的归属回收，禁止按端口盲杀」。
- **给模型加 `--mlock` 阻止权重被换出**：会把压力转嫁给其它应用（Chrome/容器），
  而且掩盖孤儿泄漏这个真问题。
- **降并发硬扛**：并发不是根因（GPU 早已 100%），降并发只延长时间、不解决换页。

## 附带发现（记录备查）

- 应用侧最大占用是 Chrome 家族 13.6 GB / 473 个进程（其中 150 个 Renderer、62 个 crashpad 句柄），
  属本机日常使用，未处置。
- 早前把 `top` 的 `PhysMem used`（含文件缓存）当作「内存耗尽」是误判：
  判断内存压力要看 **swap 余量** 与 **wired 里是否有可回收项**，不是看 used 百分比。
