## 一、逐件裁决

| 件 | 结论 | 落点 |
|---|---|---|
| **件1 能力 id 稳定** | **真缺口** ⇒ 立「id 只增不改」静态门禁 + 冻结基线清单（基线缺失必须 fail-closed）。**另：id 形态口径（499 裸族名 vs 5 带包前缀）属待裁，不由本决策定** | §8.3 第 29 项；形态口径见 §8.2 第 20 项 |
| **件2 契约 SemVer** | 机制**早已具备**（5.1 契约唯一 + 5.3 契约面指纹即递增判据 + 5.4 兼容/破坏/冻结三档），**只是消费者契约注册表 0 份登记** → 漂移门禁对真实包恒放行（机制空转，不是机制缺陷） | §8.3 第 30 项 |
| **件3 breaking change 保留旧版本** | **不做「同 id 多版本并存」** —— 它等于内部第二执行腿，撞 1.2① / 1.7 / 7.4。等价实现＝**新旧 id 并存**（旧 id 不变、新能力用新 id，D-12 已是先例）；要兼容长期在线的旧调用方，**只走 1.2② 边界协议映射三条件**（到期版本 + 使用计数 + 删除条件） | 已写入 `项目说明.md` 1.2 边界口径④ |
| **件4 Docker 一键装** | **不做 Dockerfile / docker-compose / CI** —— 本机私有部署，容器化收益不抵维护成本；**只做「单入口换机体检」**，且**体检必须复用既有分项判据**（README 三步 + `开发工具/环境自检.py` + 依赖锁 JSON + 提供者代码），不得自己重写判据（写死必假绿） | §8.3 第 29 项同批 |

## 二、被否决的做法（防重提）

```
✗ 能力级「同 id 多版本并存」
      —— 要改 契约.py 的注册表键 与 唯一能力调用.py 的调用签名，且直接违反 1.2①/1.7/7.4
✗ 为兼容旧调用方在注册表挂第二套实现
      —— 内部第二执行腿；要兼容只走 1.2② 的三个到期条件
✗ 引 Docker / CI 来兑现「一键装」
      —— 本机私有部署；换机体检用既有入口即可
✗ 换机体检脚本自己重写判据
      —— 判据来源散在 README / 依赖锁 JSON / 提供者代码三处，写死必假绿
```
