# 0058 决策模型接入底座（第四类模型）

<!-- 机器管理｜类型：仓库内其他文档｜生成器：开发工具.MD文档生成 -->

## 背景

底座模型连接器原来只有三类：LLM（对话）、向量（嵌入）、重排（排序）。Laya 决策模型
（421M，非自回归、一次前向产出「多选答案 + 标定置信度」）拿到手后没有安放位置 ——
它既不是生成式 LLM，也不产出向量或排序分，与已有三类的能力形状都不同。

判定为**真缺口**而不是「先跑通逐字稿再说」：仓库内搜「决策 / 推理 / 分类判断」全 0 命中，
`模型服务.py` 的实参清单实测为 `["LLM","向量","重排"]`。按平台哲学第 10 条
（缺什么补什么、补成原子能力），缺口就该在底座补齐，与某个上层用途是否立即要用无关。

同时它不能靠新建一套「决策模型托管」实现：底座已有完整 HF 模型托管链
（供应链校验 sha256 → 独立进程 + 动态端口 + 句柄 + 租约 + 空闲回收 + 看守），
决策模型正好是标准权重目录，只是加载器不认它。

## 决策

把「决策」作为底座**第四类模型**接入，复用既有 HF 托管链，只补分派：

- 对外只暴露 2 个能力：`连接决策模型(本地路径…) → 句柄`、`执行决策(句柄, 文本, 问题)
  → {选项, 概率, 置信度}`。其余（供应链校验、进程、端口、句柄、看守、回收）全部复用。
- 权重目录判据按**实体文件**：新增源格式 `RLCheckpoint`（`encoder/config.json`
  + 顶层 `*.safetensors`），不看目录名。平铺 HF（顶层 `config.json`）仍是 `HuggingFace`。
- 推理代码随权重包提供（`rl_agent_api.py` / `rl_common.py` 在包根），不在本仓；
  加载器先找包根、再退回权重目录自身，两处都没有即报错，不留空转分支。
- 权重必须登记进受管模型库清单（`模型制品清单.json`）：`模型供应链校验` 规则
  「受管模型根（`~/Documents/AI模型`）之下未登记即拒绝」，不登记连不上。

**置信度是本类能力的核心价值**：经严格真分数规则训练，统计上可信（实测对的
0.76~0.99、含糊文本 0.22），上层可据此决定「要不要人工兜底」——这是普通 LLM
的软性自述概率给不了的。

## 考虑过的其他做法

1. **不接入底座，只当逐字稿分类脚本用。** 否决：那是一次性脚本，能力不能复用；
   底座缺口仍在，下一个用决策模型的项目还要再写一遍进程/句柄/回收。
2. **新建一个「决策模型支持库」，自带一套进程与句柄管理。** 否决：同一件事两份
   实现，供应链校验、空闲回收、孤儿治理都要维护两套，正是平台反复收口的重复腿。
3. **给 `模型服务.py` 加决策分支就够了，不做源格式识别。** 否决：实测卡在
   `_识别模型源` 判「不支持」——决策权重包是 `encoder/` 子目录结构，没顶层
   `config.json`，识别不过就进不到加载，等于接不通。
4. **把 Laya 权重转成平铺 HF 目录以复用 HuggingFace 判据。** 否决：改权重布局是
   伪造「它就是普通 HF 模型」，与上游包结构漂移；且以后每换一版决策模型都要再转一次。

## 后果

- 好处：底座多一类原子能力，上层（逐字稿、话术质检、会话路由、合规判断等）都能
  经唯一网关调用；托管链一套，不新增维护面。
- 代价与限制：
  - 决策权重包的目录结构被底座认识了一个新形状（`RLCheckpoint`）——上游若改结构，
    判据要跟着改，这里没有魔法。
  - 决策模型只在 MPS/CPU 上跑（无 CUDA），冷启动约 20 秒，之后单次约 100~170ms。
  - 效果取决于标注数据与标签体系，底座只保证「能连、能调、资源能收」，不保证准确率。
