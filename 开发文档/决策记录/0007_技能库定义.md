# 0007 技能库定义

> 状态：**现行（2026-09-10 华哥确认"skill 本质上就是这样了"）**
> 日期：2026-09-10
> 决策人：华哥

## 背景

模块库和支持库都有正式定义，技能一直没有写进权威文档，但业务项目里已有 8 个技能包在按「六件套」结构运行。华哥要求把技能定义清楚，并明确**如何通过 GET / POST 传参、传什么、返回什么**。

## 一、技能的本质：三份东西，各给不同的人看

技能**不实现能力，只做编排**。一个技能包里同时装了三份东西，分别服务于三个不同的对象：

| 部分 | 落在哪个文件 | 给谁看 | 作用 |
|---|---|---|---|
| **提示词**（说明 + 触发条件 + 使用建议） | `SKILL.md` | **Agent 读** | 判断"这件事该不该用这个技能、什么时候用" |
| **契约**（参数 / 返回 / 错误码） | `契约.json` | **Agent + 执行器** | Agent 照它组装参数；执行器照它校验参数。**参数唯一事实源** |
| **流程**（分几步、每步做什么） | `工作流.json` | **执行器 + 校验** | 声明这条工作流怎么走 |
| **桥接脚本** | `scripts/` | **执行器** | 只做参数整理与委托，不实现业务 |
| **边界**（依赖、预算、目录、验证） | `依赖.json` + `验证声明.json` | 执行器 + 审计 | 依赖哪些能力、资源上限、怎么验证 |

**对外调用时，Agent 拿到的是「契约」，不是提示词。** 提示词只在 `tool_catalog` / `skill_inspect` 的说明字段里出现，帮 Agent 做判断。

## 二、调用链路（唯一一张主线图）

```text
【Agent】我要做一件事，先看有哪些技能可用
  │
  ▼
【① 工具目录 tool_catalog】—— 只读发现
  │  传入：分类（可"全部"）、关键词
  │  返回：可见工具与按需 Skill 的清单（名称 + 说明）
  │
  ▼
【② 技能查询 skill_inspect】—— 拿「这个技能到底怎么用」
  │  传入（四选一）：工具名 / Skill名称 / 能力标识 / 详细程度（简略·完整）
  │  返回（这就是「提示词 + 契约」的载体）：
  │    · 说明与触发条件        ← 提示词部分，给 Agent 判断
  │    · 参数表：名 / 类型 / 必填 / 枚举 / 默认值 / 说明
  │    · 返回表：字段 / 类型 / 说明
  │    · 错误码表：码 → 中文说明
  │    · 依赖边界、执行入口
  │
  ▼
【Agent 按契约组装参数】三件套
  │   能力标识（如 文档解析.PDF） + 参数对象 + 开工id
  │   参数对不上契约 → 不用走到执行就报错
  │
  ▼
【③ 能力执行 capability_execute】—— 唯一执行入口
  │  校验顺序：角色 → 开工 → 白名单 → 契约（类型 / 必填 / 枚举）
  │  失败直接报错：MISSING_CAPABILITY_ID / MISSING_WORK_ID / 参数不合法 …
  │
  ▼
【技能脚本执行器 · 受控沙箱】
  │  解析：按 索引.json 白名单定位技能包 → 读 契约.json → 取 scripts/ 入口
  │  审计：只许导入标准库与支持库包级公开入口；禁第三方、禁实现目录
  │  资源：RLIMIT 预算、环境变量白名单、超时、输出上限、进程组整树回收
  │
  ▼
【入口脚本】（委托 / 桥接，只做参数整理与委托）
  │
  ▼
【底座能力分发桥接】按 能力标识 找到真实能力
  │
  ▼
【底座能力】（支持库原子能力 / 模块库组合能力）—— 真正干活的地方
  │
  ▼
【统一信封返回】
    成功 / 值 / 错误码 / 错误说明
```

**两条腿对应两种调用方式：**

| 调用方 | 入口 | 传什么 | 返回什么 |
|---|---|---|---|
| Agent（MCP） | `capability_execute(能力标识, 参数, 开工id)` | 能力标识 + 参数对象 + 开工id | 统一信封 |
| 外部程序（HTTP） | `POST http://127.0.0.1:40007/网关/调用` | `{"操作":"调用能力","能力id":...,"参数":{...}}` | `{"成功","值","错误码","错误说明","请求id","句柄","耗时毫秒"}` |

**关键点**：技能本身**不另开 HTTP 入口**。技能就是一条能力，走底座唯一执行入口；技能包里只有"怎么用"的说明（提示词）、"参数边界"（契约）、"步骤"（流程）和"桥接"（脚本）。

## 三、技能包结构（现状实测，不用推翻）

`<技能根目录>/<分类>/<技能名>/` 六件套：`SKILL.md`、`契约.json`、`工作流.json`、`scripts/`、`验证声明.json`、`依赖.json`。

现有 8 个技能包：`_示范/纯文本统计`、`数据操作/建表迁移`、`数据操作/批量导入`、`文档解析/Excel解析`、`文档解析/PDF解析`、`文档解析/PPT解析`、`测试/批量并行验证`、`运维/发布门禁`。

## 四、已知缺口（下一步要补）

现状 `工作流.json` 的步骤是**自然语言**，没有绑定能力id —— 机器校验不了"这条流程的每一步是否真的指向一个存在的能力"。要落地"参数不对直接报错"，这一步得升级。

## 五、考虑过的其他做法

1. **技能就是一段提示词**：否决。没有契约和门禁，参数对不上发现不了，无法验证。
2. **技能对外返回整条流程让 Agent 自己跑**：否决。那样 Agent 就有了越界空间（自己决定步骤、自己拼参数），正是要消除的漂移来源；技能应由执行器按流程跑，Agent 只提供契约内参数。
3. **技能就是普通 Python 脚本**：否决。退化成"业务项目自建原子能力"，违反 0005 / 0006。
4. **技能等同模块库**：否决。模块库是「一个能力」，技能是「一套工作流（多步骤 + 提示词 + 边界）」，颗粒度与用途都不同。
5. **技能留在各业务项目**：否决。技能是可复用工作流，留在各项目会分叉出多套，违反唯一性铁律。

## 六、后果

- 好处：技能有正式定义后，可被统一注册、校验、执行、验证；Agent 只有「照契约传参」这一条路，没有越界空间；「什么时候用哪个技能」从口口相传变成可查契约。
- 代价与限制：现有 8 个技能包要按新定义补齐（流程步骤绑定能力id）；技能库本身作为底座一类包需要立项。

## 七、验证方式

1. **结构**：技能包六件套齐全（现有校验器已强制，缺失直接报错）。
2. **流程可校验**：`工作流.json` 每一步都能解析到真实存在的底座能力id（升级后新增校验项）。
3. **执行真实**：技能调用链路出现对底座能力的真实调用；技能脚本自身不实现业务逻辑。
4. **边界生效**：参数不符契约时，在执行前即报错，不进入脚本执行。

## 边界：按「谁在用」划，不按「谁实现」划（2026-09-10 华哥强调）

华哥口径：技能本质上是 **Agent 调用的**，所以重要的是**它的使用者**，或者说是**封装链路**——就像 Hermes 那样，**使用者和开发者是两码事**。这是**边界清晰**的问题。

### 一、三种角色，三套可见面

| 角色 | 是谁 | 能看见什么 | 能做什么 | 不能做什么 |
|---|---|---|---|---|
| **使用者** | Agent / 外部程序 | 技能清单、说明、**契约**（参数/返回/错误码） | 照契约传参；参数不对就报错 | 看不到流程细节、脚本、桥接、底座实现；不能自己定步骤 |
| **编排者** | 技能开发者 | 技能包全部文件 + 可用能力清单 | 写提示词、定契约、声明流程、写桥接脚本 | **不实现能力**；不能绕过契约私加参数 |
| **提供者** | 底座（支持库 / 模块库） | 自己的实现与提供者 | 提供能力实现；按能力id 被调用 | 不关心谁在调、不感知技能存在 |

### 二、三条边界线（缺一条就模糊）

```text
【使用者】Agent / 外部程序
  │  看得见：技能清单 + 说明 + 契约（参数表 / 返回表 / 错误码表）
  │  能做的：照契约传参
  │  看不见：流程细节、桥接脚本、底座实现
  ═══════════ 边界线 1：只走契约（使用者没有越界空间）═══════════
【编排层】技能（由技能开发者编写）
  │  组成：提示词(SKILL.md) + 契约(契约.json) + 流程(工作流.json) + 桥接(scripts/)
  │  能做的：把已有能力编排成一条工作流
  │  不做的：不实现能力、不新增原子能力
  ═══════════ 边界线 2：只编排不实现 ═══════════
【能力层】模块库（组合能力） / 支持库（原子能力）
  │  真正干活的地方；全平台唯一一套
  ═══════════ 边界线 3：实现对外不可见 ═══════════
【实现层】提供者 / 第三方库 / 本机工具（底座内部）
     外部任何角色都看不到这一层
```

### 三、和 Hermes 的对比：为什么这里必须更严

| | Hermes 技能 | 本项目技能 |
|---|---|---|
| 形态 | **纯提示词文档**（SKILL.md） | **受控能力包**（提示词 + 契约 + 流程 + 桥接） |
| 使用者拿到后 | 读了**自己决定怎么做** | **只能照契约传参** |
| 边界 | 模糊：Agent 有自由发挥空间 | 清晰：步骤由执行器按流程跑，Agent 没有越界空间 |
| 适用 | 通用 Agent 的灵活场景 | 大型集成任务，参数对不齐就会打架的场景 |

**这正是本项目要解决的**：单小任务 Agent 自由发挥很好用；大型集成任务因为上下文对不齐参数就会打架。所以技能**不能**做成"给 Agent 看的文档"，必须做成"受控的能力包"。

### 四、原子能力的边界会不会因为技能而模糊？不会

因为**技能不新增原子能力**：

- 技能里唯一新增的东西是**编排信息**（用哪些能力、什么顺序、什么门禁）——这是**声明**，不是**实现**。
- 真正干活的永远是底座的支持库 / 模块库能力，全平台唯一一套。
- **判定规则**（一句话分清）：
  - 能被「**传参调用并返回结果**」的 → 是**能力**（归支持库/模块库，在底座）
  - 告诉别人「**这件事怎么一步步做完**」的 → 是**技能**（编排声明，不实现东西）
  - 只在某个业务流程里成立、换个场景就没意义的 → 是**业务**（留在业务项目）

## 消费者清单（2026-09-10 华哥确认）

| 层 | 消费者 | 怎么消费 | 实测依据 |
|---|---|---|---|
| **技能** | **只有 Agent** | MCP `capability_execute` → 技能执行器 | 全仓**只有一处**调技能执行器：`MCP工具箱/运行时/工具注册/能力执行.py:277`；业务代码零直接引用 |
| **能力** | Agent **+ 业务代码** | Agent 走 MCP；业务代码走 `底座客户端` → 40007 | V3 有 **19 个文件**直接调底座 |
| **实现** | 无消费者 | 只有底座内部使用 | 提供者 / 第三方对外不可见 |

**因为消费者不同，契约要求也不同**：

- **技能契约可以服务 Agent**：可以带说明、触发条件（Agent 会读字、需要判断依据）。
- **能力契约必须中立**：纯传参、纯返回；不掺任何"给人看的话"，也不假定谁在调（Agent 和业务代码都要能用同一份契约）。

## 与 Hermes 技能的关键差异：脚本归谁（2026-09-10 华哥口径）

华哥口径：技能原则上只有 Agent 消费，**本质是提供一套可复用的工作流给 Agent 去判断，然后快速去执行能力**。这跟 Hermes 一样——Hermes 里用技能一般是「技能描述 + py 脚本」；但**我们的 py 脚本是封装好的**。

| | Hermes 技能 | 本项目技能 |
|---|---|---|
| 技能描述 | `SKILL.md`，给 Agent 读 | `SKILL.md` + `契约.json`（**机器可校验**） |
| py 脚本的性质 | **给 Agent 用的辅助脚本**：可选、可参考、可改写、可绕过 | **封装好的桥接脚本**：Agent 碰不到，由执行器在沙箱里跑 |
| Agent 自由度 | 高（读了描述自己决定怎么做） | **零**（只能按契约传参） |
| 谁在执行 | Agent 自己 | **受控执行器**（沙箱 + 门禁） |
| 脚本里装什么 | 做事逻辑 | **只做参数整理与委托**，真正干活调底座能力 |

**一句话总结本项目技能**：

```text
技能 = 给 Agent 的工作流说明书（提示词）
     + 机器可校验的契约（参数 / 返回 / 错误码）
     + 封装好的桥接脚本（Agent 碰不到）
     + 受控执行器（沙箱、门禁、资源预算）
```

Agent 只负责两件事：**判断该用哪个技能**、**按契约传参**。剩下全在边界之内完成。
