# 0007 技能库定义

> 状态：**草稿（待华哥评审）**
> 日期：2026-09-10
> 决策人：华哥

## 背景

模块库和支持库都有正式定义，**技能目前没有写进权威文档**，但业务项目里已经有 8 个技能包在跑，用的是「六件套」结构。技能运行机制（受控脚本沙箱）已按 0006 归底座；本条的待定问题是：**技能本身应该怎么定义**。

## 现状（2026-09-10 实测）

技能包 = `<技能根目录>/<分类>/<技能名>/` 下的六件套：

| 文件 | 作用 | 现有内容 |
|---|---|---|
| `SKILL.md` | 给人/Agent 看 | YAML 头（名称、分类、触发、能力标识、执行入口、依赖边界）+ 适用场景 + 调用步骤 + 验证建议 |
| `契约.json` | **参数唯一事实源** | 参数（类型/必填/枚举/默认值/说明）、返回、错误码 |
| `工作流.json` | 流程声明 | 入口脚本、入口类型、步骤列表（序号 + 动作） |
| `scripts/` | 入口脚本 | 现为「能力分发桥接」，只做桥接，不实现业务 |
| `验证声明.json` | 验证口径 | 无副作用、干跑无副作用、验证方式、验证声明 |
| `依赖.json` | 依赖声明 | 依赖的能力（能力分发桥接）、第三方依赖 |

现有 8 个技能包：`_示范/纯文本统计`、`数据操作/建表迁移`、`数据操作/批量导入`、`文档解析/Excel解析`、`文档解析/PDF解析`、`文档解析/PPT解析`、`测试/批量并行验证`、`运维/发布门禁`。

**关键观察**：现有 `工作流.json` 的「步骤」是自然语言（如「受控入口校验结构化迁移参数」），**没有绑定能力id**，属于"人看得懂、机器校验不了"。

## 建议的定义

### 一、技能库与模块库平级，但定位不同

```text
支持库（原子能力）      一个动作，最细颗粒
   ↓ 组装
模块库（能力组合）      一个能力，可被调用，一进一出
   ↓ 组装 + 流程 + 提示词
技能库（工作流）        一套流程：什么场景用、分几步、每步调什么能力、哪里需要人参与
```

- **模块库回答**「有没有这个能力」
- **技能库回答**「这件事该怎么一步步做完」

### 二、技能的正式定义：一套可复用工作流包，四要素

| 要素 | 内容 | 落在哪个文件 |
|---|---|---|
| 1. **触发** | 什么场景该用这个技能（给 Agent 的判断依据） | `SKILL.md` 头部 |
| 2. **流程** | 分步骤；每步写明 **调用哪个能力id + 传什么参数 + 产出什么 + 门禁条件** | `工作流.json` |
| 3. **契约** | 入参、返回、错误码（唯一事实源，不另立副本） | `契约.json` |
| 4. **边界与资源** | 依赖哪些能力、资源预算、目录范围、验证方式、能否干跑 | `依赖.json` + `验证声明.json` |

### 三、技能的本质

- 技能**不实现能力**，只做**编排**：把底座已有的支持库/模块库能力按顺序串起来，补上「什么时候用、人怎么参与、失败怎么办」。
- 技能的**提示词部分**给 Agent 看（判断与沟通）；**流程部分**给执行器看（步骤与门禁）。
- 技能脚本**只做桥接与参数整理**，真正干活一律调底座能力（现有包已经是这个形态：`入口类型 = 能力分发桥接`）。

### 四、技能库放哪

- 技能**运行机制**（沙箱、资源预算、进程回收、AST 审计）归底座 —— 已由 0006 决定。
- 技能**库本身**（注册、校验、发现、索引、说明书）作为底座的一类包，与支持库/模块库并列管理。

## 待华哥确认的 4 点

| # | 问题 | 我的建议 |
|---|---|---|
| 1 | 技能库是否与模块库平级（独立一类包）？ | 建议平级，但定位不同（模块库=能力，技能库=流程） |
| 2 | `工作流.json` 的步骤是否要**绑定能力id**？ | 建议要。这样流程可校验（每一步都指向真实存在的能力），也是"参数不对直接报错"的落地 |
| 3 | 技能是否允许带**提示词模板**（供 LLM 使用）？ | 建议允许，但模板属技能包内容，不能成为第二套契约来源 |
| 4 | 技能**包本身**归底座，还是包留业务项目、只把运行机制归底座？ | 建议整体归底座（技能是可复用的，不属于某个业务），业务项目只传参调用 |

## 考虑过的其他做法

1. **技能就是一段提示词**：否决。没有契约和门禁，参数对不上也发现不了，无法验证。
2. **技能就是普通 Python 脚本**：否决。那就退化成"业务项目自建原子能力"，违反 0005/0006。
3. **技能等同模块库**：否决。模块库是「一个能力」，技能是「一套流程（多步骤 + 人参与 + 提示词）」，颗粒度和用途都不同。
4. **技能留在各业务项目**：否决。技能是可复用工作流，留在各项目会分叉出多套（违反唯一性铁律）。

## 后果

- 好处：技能有正式定义后，可被底座统一注册、校验、执行、验证；「什么时候用哪个技能」从口口相传变成可查的契约；Agent 有明确边界（流程外的动作做不了）。
- 代价与限制：现有 8 个技能包要按新定义补齐（步骤绑定能力id、提示词部分规范化）；技能库立项本身是一批新工作。

## 验证方式

1. **结构**：技能包六件套齐全（现有校验器已强制，缺失直接报错）。
2. **流程可校验**：`工作流.json` 每一步都能解析到真实存在的底座能力id（升级后新增校验项）。
3. **执行真实**：技能调用链路里出现对底座能力的真实 HTTP 调用；技能脚本自身不实现业务逻辑。
