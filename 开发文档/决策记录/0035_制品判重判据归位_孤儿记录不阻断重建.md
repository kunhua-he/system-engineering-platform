# 0035 制品判重判据归位：孤儿记录不阻断重建

- 状态：**已生效**
- 日期：2026-09-18
- 适用：`平台控制面/包仓库/服务.py::构建制品` 的「同一包同一版本禁止双摘要」判重
- 依据：哲学 14.1②（判据归位）、14.3（反复犯错的开发要补底层）

## 现象

`客户端/构建平台客户端.py --安装` 连续失败，报
`入库失败: 同一包同一版本禁止双摘要（已存在 7062005744c9…）`；绕过后再报 `制品目录缺失`。

## 真因

判重判的是「状态库里有一条 `(包id, 版本)` 记录」，而**回收只删内容寻址目录、从不删状态库记录**
（记录是溯源证据）。于是「记录在、目录没了」是**正常产物**（一次回收就会产生），
却被判据当成一份活着的制品：重算出的新摘要与那条陈旧摘要不等 → 永久拒绝同版本入库。

实测规模：`制品` 表 **74 条记录里 73 条是孤儿**。且是**闭环死锁** —— `安装到环境` 报
「制品目录缺失（半成品）」并把修复出口指向 `重新入库`，而入库正被那条记录卡死。

## 决定

判重处**按磁盘目录真实存在**过滤，只对「已有一份**可用的**同版制品」做双摘要保护：

```python
可用表 = [记录 for 记录 in 已有表
          if (self.制品根目录 / str(记录.get("制品摘要") or "")).is_dir()]
```

孤儿记录**不再阻断重建**，同时**继续留在状态库**作为「曾经构建过什么」的溯源。

## 被否决的做法

1. **回收时同步删 `制品` 表记录**。否决理由：记录是**溯源证据**，删掉等于丢失「曾经构建过什么」；
   且回收是**旁路动作**，不该反向改写正式溯源（与「运行态入库、证据留文件」的分工相悖）。
2. **入库时把孤儿记录当冲突覆盖**。否决理由：为过门禁而放宽判据，会把**真双摘要保护**
   （同版不同内容必须拒绝）一起弄松 —— 那是资产完整性的一道闸门，不能为了让链路通而拆。
3. **保留判据不动、继续人工清库**。否决理由：那是每次制品操作都要人工介入的长期税，
   且「记录在、目录缺」是可预期的正常态，不该由人来兜。
