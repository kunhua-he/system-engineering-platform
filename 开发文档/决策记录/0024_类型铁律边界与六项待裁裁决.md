## 第一项：第三方 / 标准库 API 的布尔位 —— **豁免中文命名**（1573 处）

**裁决**：全中文命名铁律管的是**本仓自有的标识与对外契约面**，**不覆盖第三方与标准库 API 的签名位置**
（如 `os.walk(topdown=True)`、`subprocess.run(check=False)`、`open(..., closefd=)`）。
这些位置的 `True/False` 是**第三方协议的一部分**，改它们等于改对第三方的调用语义，还会让代码与第三方文档脱节。

**影响（真实数字）**：裸布尔分类里的「B类违反类型铁律」由 **3597 处** 降到约 **2024 处**（A类合法从 1623 升到约 3196）。
迁移工作面因此缩小约 **44%** —— 这就是本条裁决的收益。

**被否决的做法**：
1. 全量改名（含第三方 API 位）—— 破坏与第三方文档的对应关系，且**无任何收益**（第 11 条：判定必须用数字）。
2. 只豁免「标准库」不豁免「第三方库」—— 两者对本仓而言是同一类**外部协议边界**，分两套口径只会制造新的判据分歧。

## 第二项：网关 `必填 is True` —— **保留身份比较**

**裁决**：**保留** `is True`。它是对 `bool` 的**最严判定**；改成 `== True` 或真值判断都会**放松判据**
（`1`、`"x"`、非空列表都会被真值判断当成 True），直接违反第 7 条「类型漂移必须拦」。

**被否决的做法**：改 `== True`（允许 `1` 等于 `True`）；改真值判断（最宽，等于取消 bool 类型检查）。

## 第三项：3 个「契约零消费」类型（`字节型` / `日期时间型` / `单精度数型`）—— **保留 16 型，不删**

**裁决**：**保留**。类型目录是**冻结契约**（16 个正式类型名的唯一定义），它是**允许集合**而非能力清单；
「零消费」只说明**当前没有包用到**，不等于该类型无价值。删它等于改冻结契约 + 移除未来合法的类型选择。
**登记为待观测**：若长期（跨多个阶段）仍零使用，届时单独裁决是否收敛。

**被否决的做法**：「**空转即杀**」—— 把「凡缺乏即能力化缺失」的判据**错误外推**到类型目录。
那条裁决的对象是**能力**（没有的能力要补成能力），类型是**语法层允许值**，性质不同。

## 第四项：视图层英文错误码 —— **按 `0003` 汉化；确有外部依赖就用兼容映射**

**裁决**：**汉化**。决策记录 `0003` 明文「对外错误使用中文错误码与中文说明，不用英文枚举」，
且视图层是**对外面**（Agent 视图 / 普通用户视图）；文件注释自述「刻意的向后兼容键」**不能推翻既有裁决**
（自述不是裁决）。若确有外部依赖，则**保留旧键作兼容映射**（映射表写在视图层内部，**不进契约**）。

**被否决的做法**：以「注释自述是兼容键」为由整体保留英文码（让注释凌驾于决策记录之上）。
