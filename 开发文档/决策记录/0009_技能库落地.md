## 背景

决策记录 0006 定下「技能（Skill）是原子能力，归底座，全平台只保留一套」，
0007 定下技能库的定义与边界。本文记录技能库的**落地实现**：把 V3 自持的
受控脚本沙箱与技能包校验器下沉到底座，并补齐索引构建能力。

## 落地形态

**包位置**：`支持库/后端/技能库/`（包 id `支持库.后端.技能库`，类型 `支持库`）

为什么不放顶层独立目录：底座装配器的包发现只扫 `支持库/` 与 `模块库/` 两个根
（`运行核心/加载器/包发现/发现器.py`），新增顶层根需要改装配核心并重启网关。
放 `支持库/后端/` 下同样是一等公民、与模块库平级，且可走热接入立即投产。
以后若要独立顶层目录，只需在发现器加一个根，包本身不用动。

**能力清单**（4 个，均走底座唯一执行入口 `POST /网关/调用`，技能不另开 HTTP 入口）

| 能力 id | 用途 |
|---|---|
| `技能库.技能包.校验技能包` | 六件套结构校验 + 契约可读性，返回 `{通过, 技能目录, 来源, 缺失}` |
| `技能库.受控执行.运行技能包` | 结构校验 → 定位入口 → AST 导入审计 → 沙箱运行 |
| `技能库.技能索引.生成索引` | 扫描全部技能包，从各自 `契约.json` 派生索引，可选写回 |
| `技能库.技能索引.扫描技能包` | 按现有索引列出技能与结构问题 |

## 关键设计：全部参数化，底座不绑具体项目

V3 版执行器把「技能目录」写死在自己的仓库里，还有 V3 专属的应用层禁入清单。
底座版把这两样都变成调用方传参：

| 参数 | 谁传 | 作用 |
|---|---|---|
| `技能根目录` | 调用方 | 含 `索引.json` 的技能目录，V3 传自己的 `模块库/Skills` |
| `禁止导入前缀` | 调用方 | 项目级禁入模块前缀（V3 传自己的应用层顶层目录） |
| `项目根目录` | 调用方 | 脚本工作目录 |

底座内置的硬约束始终生效，调用方无法关闭：固定解释器、结构化 stdin/stdout、
超时后进程组回收（连孙进程）、stdout 上限、环境变量白名单、路径范围校验、
`RLIMIT_CPU`/`RLIMIT_FSIZE`、AST 导入审计（禁 `shell=True`、`eval/exec/compile`、
`__import__/importlib`、`subprocess/os` 命令执行、第三方库）。

## 过程中踩的两个底座契约坑（记录备查）

1. **包声明 `类型` 必须取四值之一**：`支持库/功能模块/模块/基础模块`。
   写成其他值（如 `技能库`）会让**装配器在发现阶段直接抛异常**，而热接入把该
   异常透传成网关的 `参数不合法`，表面上像请求参数问题，实际是包声明问题。
   **排查方法**：绕开网关脱敏，直接在进程内跑 `发现全部()`，一眼看到真实报错。
2. **能力函数必须返回 `结果` 对象**（`结果.成功结果(值)` / `结果.失败(错误码, 消息, 来源=, 详情=)`）。
   返回普通字典会被网关判为「返回结果不符合契约」。注意失败参数的字段名是
   **`详情=`**，写成 `详细信息=` 会抛 `TypeError` 被兜成「内部错误」。
   另外参数与返回值类型只能用 `公共契约/基础类型/类型表.py` 的**正式类型**
   （`对象型` 不在其中，要用 `字典型`）。
