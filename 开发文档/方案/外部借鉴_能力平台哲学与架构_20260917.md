# 第一部分：gRPC + Protobuf 契约演进哲学 & Buf 破坏性变更检测

## 一、Protobuf：为什么字段编号是契约主键

1. **编号而非名字才是线上身份。** 官方原文：复用编号会让解码产生歧义——"The protobuf wire format is lean and **doesn't provide a way to detect fields encoded using one definition and decoded using another**"。后果按严重度递进：调试工时 → parse/merge 报错（**最好情况**）→ 泄露 PII/SPII → 数据损坏。两大成因：**renumbering（重排编号）**与**删字段却不 reserved**。[来源: https://protobuf.dev/programming-guides/proto3/]

2. **删字段 = 删除 + 保留编号。** 官方把 "Removing fields is safe" 和 "**The same field number must not used again**" 绑在一句里，建议 `reserved` 或改名加 `OBSOLETE_` 前缀。`reserved` 拦编译期复用：`reserved 2, 15, 9 to 11;`（闭区间）；名字也能 reserved，但只影响 protoc 与 TextProto（C++/Go 会丢弃），**运行期 JSON 解析不受影响**；名字与编号不能同句写。[来源: https://protobuf.dev/programming-guides/proto3/]

3. **最佳实践第一条禁令：** "Don't re-use a tag number... Even if you think no one is using the field... there could be serialized versions of your proto **in a log somewhere**"。同页另禁：改字段类型、加 `required`。[来源: https://protobuf.dev/best-practices/dos-donts/]

4. **optional / repeated→packed 的 wire 兼容。** 官方规则：`string`/`bytes`/`message` 上 **singular 与 repeated 兼容**；**数值类型（含 bool、enum）不通用安全**： "Repeated fields of numeric types are serialized in the **packed** format by default, which will not be parsed correctly when a singular field is expected"。scalar→repeated 在 proto2 与 proto3 `[packed=false]` 下 OK（标量变成长度 1 的列表）。[来源: https://protobuf.dev/programming-guides/proto3/]
   **packed 本身不是破坏性变更**：encoding 文档写明 "Protocol buffer parsers **must** be able to parse repeated fields that were compiled as packed as if they were not packed, **and vice versa**. This permits adding `[packed=true]` to existing fields in a forward- and backward-compatible way"；proto2 补充：2.3.0 起才安全，**要当心仍在用旧版 protobuf 的老程序**。[来源: https://protobuf.dev/programming-guides/encoding/ , https://protobuf.dev/programming-guides/proto2/]
   另：**proto3 保留未知字段**（解析与再序列化都保留）。[来源: https://protobuf.dev/programming-guides/proto3/]

5. **字段/服务/方法增删各算什么**（官分三档）：
   - **Wire-unsafe**：改字段编号（"equivalent to deleting the field and adding a new field with the same type"）、把字段移入**已存在**的 oneof。
   - **Wire-safe**：加字段、删字段（编号不得复用）、enum 加值、单字段移入**新建** oneof、单字段 oneof 转 explicit presence、字段转同号同类型 extension。
   - **Wire-compatible（有条件、可能丢数据）**：int32/uint32/int64/uint64/bool 互通、sint32↔sint64、string↔bytes（需合法 UTF-8）、fixed32↔sfixed32、map↔对应 repeated message。官方明确：**schema 若发布到组织外部，一般不应做此类变更**，因为无法管理对方升级时机。[来源: https://protobuf.dev/programming-guides/proto3/]
   - **wire-safe ≠ 对代码安全**——"any wire-safe changes may be a breaking change to application code in a given language"（如 enum 加值会让穷举 switch 编译失败）。[来源: https://protobuf.dev/programming-guides/proto3/]

6. **JSON 是另一套规则且更脆。** 官方原文：ProtoJSON "**does not support unknown fields**, and it **puts field and enum value names into encoded messages which makes it much harder to change those names later. Removing fields is a breaking change that will trigger a parsing error**"。ProtoJSON 下「改编号是安全的（编号不出现在 JSON）但**依然强烈不建议**」。[来源: https://protobuf.dev/programming-guides/json/]

## 二、官方 breaking 清单与 googleapis AIP

7. **AIP-180 是 Google 自己的 breaking 清单**，先定义三条兼容轴：Source（老代码能编译且能在新客户端库上跑）、Wire（老代码能与新服务端正确通信，含序列化/反序列化预期匹配）、Semantic（老代码仍收到「合理开发者会预期」的结果）。总纲："Existing client code **must not** be broken by a service updating to a new minor or patch release. Old clients **must** be able to work against newer servers (with the same major version number)." [来源: https://google.aip.dev/180]
   具体禁令（比 protobuf.dev 更严）：**现存组件不得删除或改名**（"Renaming a component is semantically equivalent to 'remove and add'"）；**不得在文件间移动组件**（同包内移动 wire 兼容，但 C++/Python 的 include/import 会断）；**不得把字段移入或移出 oneof**（Go stub 上是破坏性变更）；**不得改字段类型，哪怕新类型 wire 兼容**——"because type changes alter generated code in a breaking way"；**不得改资源名**（连大版本也不能改）；**不得改字段值的格式/构造算法**（含 OUTPUT_ONLY），改了必须开新 API 版本。[来源: https://google.aip.dev/180]
   AIP-180 自限适用范围："This guidance assumes that APIs are intended to be called from a range of consumers, written in multiple languages and **with no control over how and when consumers update**"；范围更小的 API 应自行评估兼容要求——这是「严格度定多高」的官方判断依据。[来源: https://google.aip.dev/180]

8. **AIP-185（版本化）**：所有 Google API 接口**必须**有 major version，编码在 **protobuf package 末尾**（REST URI 路径首段）；不兼容变更走 AIP-180/181；**同一 API 的不同版本必须在单个客户端应用内可并存一段时间**，老版本须经充分沟通的弃用期；alpha/beta 用 channel-based（推荐）/interface-based/release-based/visibility-based 四策略，beta 建议 180 天过渡。[来源: https://google.aip.dev/185 , https://google.aip.dev/181]
   AIP-185 的 IBV 模式还规定：请求用 `X-Goog-Api-Version` header 或 `$apiVersion` 查询参数带版本；生产者须在 RPC/字段/枚举值上**注解其存在的版本区间**（API screens）。即「同一份 schema 内做元素级版本可见性」，而非切包。[来源: https://google.aip.dev/185]

9. **proto2/proto3→Editions 迁移**：官方明确 "Editions **won't break existing binaries** and don't change a message's binary, text, or JSON serialization format"、"While the generated code changes... **the wire format does not**"——语法代际升级是生成代码层变更，不是 wire 层。[来源: https://protobuf.dev/editions/overview/]
   proto2 的 `required` 被标为 **Strongly Deprecated / "Required Is Forever"**："It is nearly impossible to safely change a field from `required` to `optional`"，且给 enum 加值会让老客户端视作缺失，导致 required 校验失败。[来源: https://protobuf.dev/programming-guides/proto2/]

## 三、gRPC：为什么不自动版本协商

10. **协议层不带版本协商，版本即包名。** PROTOCOL-HTTP2 定义 `:path` 为 `"/" Service-Name "/" {method name}`，Service-Name 是 **IDL 层服务全名**（例 `/google.pubsub.v2.PublisherService/CreateTopic`）——版本是包名的一部分，不是独立协商字段。[来源: https://github.com/grpc/grpc/blob/master/doc/PROTOCOL-HTTP2.md , https://grpc.io/docs/what-is-grpc/core-concepts/] 这与 AIP-185「major version 编码在 package 末尾」是同一机制的两面。[来源: https://google.aip.dev/185]

11. **gRPC 自身的版本化只管运行时库，不管你的 API。** 官方 Versioning Guide：遵循 semver，major bump 必须不破坏与其他实现的 wire 兼容——"**no backward incompatible protocol changes are allowed**: old clients must continue interoperating correctly with new servers and new servers with old clients"；新语言实现从 v0.x 起步、1.0 才 GA；破坏性 API 变更必须提 gRFC 文档说明迁移成本/收益/对老 major 的支持计划。[来源: https://github.com/grpc/grpc/blob/master/doc/versioning.md]

12. **接口版本化在 protobuf 层用 option 承载。** `google/api/client.proto` 在 `ServiceOptions` 上定义 `option (google.api.api_version)`，注释原文："The API version of this service, which should be sent by **version-aware clients** to the service. This allows services to abide by the schema and behavior of the service at the time this API version was deployed. **The format of the API version must be treated as opaque by clients**."[来源: https://github.com/googleapis/googleapis/blob/master/google/api/client.proto] 注：googleapis 中并**无** `google/api/versioning.proto`（探明 404），版本化规则由 AIP-185/181 与该 option 承载。

13. **Service Config 的作用域是「服务器名」，不是契约级。** 官方原文："A service config is **associated with a server name**. The name resolver plugin, when asked to resolve a particular server name, will return both the resolved addresses and the service config." 它承载**客户端行为参数**（LB 策略、method 级 timeout、retry 等），匹配粒度 `{service, method}`，以 JSON 下发，**与 schema 版本无关，也不参与版本协商**。[来源: https://github.com/grpc/grpc/blob/master/doc/service_config.md , https://github.com/grpc/grpc-proto/blob/master/grpc/service_config/service_config.proto]

## 四、Buf：把兼容性变成可执行的规则阶梯

14. **`buf breaking` 定位**：把当前 schema 与任一历史版本（Git ref / BSR 模块 / tarball / zip / Buf image）对比，"reports any changes that would break **clients, servers, or the code generated from those schemas**"。两个入口：`--against <input>` 与 `--against-registry`（每个命名模块对 BSR 最新发布比对）。官方破坏性示例即编号级：`int32 id = 1` → `string id = 1`，报 `FIELD_SAME_TYPE`——"Tag `1` now carries an incompatible wire type, so every existing client and every serialized message already in flight becomes unreadable." [来源: https://buf.build/docs/breaking/ , https://buf.build/docs/breaking/usage/]

15. **四级严格度阶梯（Buf 最核心的设计）**：`FILE`（默认、最严，按文件检测生成代码破坏，C++/Python 必须用）→ `PACKAGE`（按包检测，允许同包内移动定义）→ `WIRE_JSON`（二进制或 JSON 编码破坏，官方称**推荐的最低级别**）→ `WIRE`（仅二进制）。"**Passing a stricter category implies passing every looser one**: schemas that pass `FILE` also pass `PACKAGE`, `WIRE_JSON`, and `WIRE`." [来源: https://buf.build/docs/breaking/ , /breaking/rules/]
   选择依据：FILE/PACKAGE 保护生成代码（删 enum 值 wire 完全兼容，但引用 `Arena_ARENA_FOO` 的 Go 代码编译失败）；WIRE/WIRE_JSON 适合「你控制所有客户端 / 单体仓库 / 你就是自己的客户端 / 想让客户端构建先炸而非运行时报错」。[来源: https://buf.build/docs/breaking/rules/]

16. **规则粒度到字段/编号级，与 protobuf 官方规则一一映射**：`FIELD_NO_DELETE_UNLESS_NUMBER_RESERVED`（WIRE, WIRE_JSON）——"checks that message field is deleted without reserving the number... reusing these numbers in the future is likely to result wire incompatibilities"；`FIELD_SAME_TYPE` vs `FIELD_WIRE_COMPATIBLE_TYPE`（后者按官方兼容表放行 int32↔uint32↔int64↔uint64↔bool、sint32↔sint64、fixed32↔sfixed32、string→bytes，但 **bytes→string 报错**，因无法知道实际数据是否合法 UTF-8）；`FIELD_SAME_CARDINALITY`(FILE/PACKAGE) vs `FIELD_WIRE_COMPATIBLE_CARDINALITY`(WIRE)；`FIELD_SAME_JSON_NAME`；`RPC_NO_DELETE`/`SERVICE_NO_DELETE`/`PACKAGE_SERVICE_NO_DELETE`（删 RPC 不是 wire 破坏但源码可能引用，应改用 `option deprecated = true`）；`RPC_SAME_REQUEST_TYPE`/`RPC_SAME_RESPONSE_TYPE`/`RPC_SAME_CLIENT_STREAMING`/`RPC_SAME_SERVER_STREAMING`（四类全含）；`RESERVED_MESSAGE_NO_DELETE`/`RESERVED_ENUM_NO_DELETE`（**删 reserved 也报错**）。[来源: https://buf.build/docs/breaking/rules/]
   边界也写明："The rules above cover **every field on a standard FileDescriptorSet**... **Custom options are intentionally out of scope**: their effects are user-defined, so a generic compatibility rule can't reason about them."（要查自定义 option 语义需写 Buf check plugin）[来源: https://buf.build/docs/breaking/rules/]

17. **`buf lint` 是另一件事，但共用类别心智模型**：lint 走 `MINIMAL`→`BASIC`→`STANDARD`（默认）阶梯，"Anything passing `STANDARD` also passes `BASIC` and `MINIMAL`"，另有两个正交类别 `COMMENTS`、`UNARY_RPC`。其中 `PACKAGE_VERSION_SUFFIX`、`RPC_REQUEST_RESPONSE_UNIQUE`（每个 RPC 必须有唯一请求/响应消息，理由："Sharing a Protobuf message between RPCs means **every change to that message ripples across every RPC that references it**"）、`STABLE_PACKAGE_NO_IMPORT_UNSTABLE`（v1 包不得 import alpha/beta 包）都直接服务演进可控性。[来源: https://buf.build/docs/lint/rules/]

18. **BSR 对象模型 = 「谁在用哪个版本」的可追溯性**：
   - **commit**：不可变快照，"identified by a **digest**"，内含 schema/文档/依赖清单/Buf 配置/可选 VCS backlink。"Commits have **no parentage** on the BSR"——没有祖先图；**提交永不删除**；内容相同则 digest 相同，BSR 去重为同一个 commit。
   - **label**：指向 commit 的**可变指针 + append-only 历史**（"A label is a mutable pointer to a commit plus the append-only history of every commit it has ever pointed to"），是 Git 分支与 tag 合一的单一标记；**label 不能删只能归档**——"Because generated SDKs resolve label names from package managers, **deleting a label would break downstream builds** in ways a VCS branch deletion never does"。默认 label 名 `main`，不可归档。
   - **引用**：`buf.build/org/module:<commitID>` 钉不可变点，`...:<label>` 跟随可变点，`buf.lock` 锁定。
   [来源: https://buf.build/docs/bsr/commits-labels , https://buf.build/docs/bsr/module/dependency-management]
   - **谁在用**：每个模块 BSR 仓库有 **Deps tab**，同时列 direct/indirect dependencies 与 **Used by**——"Used by shows dependents across any of this module's labels and commits, each pinned to the dependent's latest commit on its default label." [来源: https://buf.build/docs/bsr/module/dependency-management]
   - **BSR 侧强制**：breaking change check 可对 default label 的推进入口强制 `FILE` 或 `WIRE_JSON`；"On buf push, **the BSR's policy always wins** for pushes that advance the default label. If buf.yaml disables breaking-change checks entirely, the BSR still enforces its policy." 违反时：开评审流 → commit 进 pending、default label 不前进；关评审流 → push 直接拒绝。可开 Unstable packages 放行 `v1alpha1`/`v1beta1`/`v1test`（**`foo.alpha.v1` 不算**）。[来源: https://buf.build/docs/bsr/checks/breaking/]
   - **唯一性检查**：push 若引入与其他模块重复的类型名或 .proto 路径，在 push 时**直接拒绝**、不进入评审流（否则 reflection / SDK 索引无法消歧）；官方修复法是包命名约定 `<organization>.<purpose>.<version>` 并让文件路径对齐包名。[来源: https://buf.build/docs/bsr/checks/uniqueness/]

19. **`buf dep` 依赖治理**：`buf dep graph`（依赖图）、`buf dep update`（更新 buf.lock 钉住的依赖）、`buf dep prune`（剪掉未使用依赖）。外部依赖在 `buf.yaml` 的 `deps` 声明、`buf.lock` 钉住；引用形式 `module[:commitID|:label]`，**不写冒号即解析到 default label 上最新已批准的 commit**，写 label 则跟随该 label 当前位置。[来源: https://buf.build/docs/reference/cli/buf/dep/ , https://buf.build/docs/bsr/module/dependency-management]

## 五、两种契约演进哲学的对照与代价

**A 派：字段级兼容规则驱动增量演进（Google / gRPC / Protobuf / Buf 主流路线）**
- 哲学：**契约身份 = 符号全名 + 字段编号**；兼容性是**可判定的规则集**（加字段安全、删字段必须 reserved、改号禁止、改类型分三档），版本号只在规则被打破时才需动大版本。
- 适用场景：契约被组织外、多语言、无法强制升级的消费者长期持有；新旧端需在生产**长时间灰度混跑**；schema 需被逐条审计。
- 代价：① **规则复杂且分档**（wire-safe / wire-compatible / source-breaking / JSON-breaking 四类判定互不相同，Buf 因此必须有 4 级阶梯，protobuf.dev 也承认 "This can be tricky in practice"）；② **wire 安全 ≠ 用户安全**——删 enum 值 wire 完全兼容却让 Go 代码编译失败，AIP-180 因此把「改类型」一刀切禁止，比 protobuf 官方更严；③ **可读性被编号绑架**，重排与重命名受限，只能靠 `OBSOLETE_` 与 `reserved` 累积债务；④ 需持续工具链投入（buf breaking + CI + BSR 策略）；⑤ 边界之外**查不出来**——Buf 明说 custom options 在范围外，AIP-180 的语义兼容、字符串长度上限、资源名格式只能人工判断。归根结底：**必须假设存在你控制不到的消费者**。

**B 派：结构指纹（哈希）驱动版本跃迁（自研能力操作系统路线）**
- 哲学：**契约身份 = 整份结构（规范化后）的哈希**；指纹一变即为新契约，不做字段级语义解释，也不判定「变兼容了没有」。
- 适用场景：单团队内网、消费者可枚举、能强制升级；契约量大（如 664 个能力）需靠机器自动发现「谁变了」而非人肉审规则；侧重「**变更可发现、可追溯、可回滚**」而非「**变更可放行**」。
- 代价：① **假阳性爆炸**——重排、改名、注释乃至无关字段顺序都产出新指纹，指纹若不规范化，版本号会被噪音淹没；② **过度破坏性**——指纹一变即升版本，会把官方认定为 wire-safe 的「加字段」也变成版本跃迁，丧失「加字段不升版本」这一最大演进红利；③ **对未知消费者无保护**——哈希只说明「契约变了」，说不出「会弄坏哪类客户端」，而 Buf 的 `FILE`/`WIRE_JSON` 阶梯正是回答后者；④ **无法表达有意的兼容窗口**——AIP-185 要求不同版本能在同一客户端应用内并存过渡，纯指纹模型若不并行保留旧指纹发布态就做不到平滑迁移；⑤ **缺少「谁在用哪个版本」的注册中心**——BSR 的 commit/label/Used-by 三件套承担的正是这个角色，若无等价物，指纹变化时无法反查影响面。
- **可用折中**：指纹留作**变更检测与追溯锚点**（Buf 的 commit 本就按内容算 digest 并去重，「指纹」在官方模型里是一等公民），但**放行判定**改用 Buf 式分级规则（至少区分 WIRE 与 FILE 级），并对已发布契约启用「加字段不升版、删/改编号必须升版」的字段级白名单。

**一句话对照**：Buf/AIP 是「**默认允许演进，用规则守住少数红线**」，代价是规则体系与工具链成本；指纹路线是「**默认拒绝演进，用哈希暴露一切差异**」，代价是噪音、假阳性与影响面分析缺失。二者不互斥——指纹适合**变更取证与去重**，字段级规则才是**放行与拦截的判据**。

# 第二部分：插件/扩展体系与能力可发现性

对照对象：自研「给 Agent 用的能力操作系统」（664 个能力，只暴露搜索/调用/目录 3 个工具，搜索硬编码 100 条上限）。

## A. 插件体系：第三方如何安全扩展而不污染内核

### A1. VS Code Extension API

- 能力声明与执行代码分离：contribution points 是写在 package.json `contributes` 字段里的纯 JSON 声明（contributes.commands、contributes.views、contributes.languageModelTools 等几十项），扩展靠注册贡献点扩展功能面，而不是往内核塞代码。[来源: https://code.visualstudio.com/api/references/contribution-points]
- 懒加载靠 activation events：`activationEvents` 声明"什么事件发生时我才有权被加载"（onLanguage、onCommand、onView、onStartupFinished、`*` 等）。官方理由：Markdown 扩展只在用户打开 Markdown 文件时才应加载，避免不必要的 CPU/内存开销。[来源: https://code.visualstudio.com/api/references/activation-events]
- 隔离靠独立进程：Extension Host 单独承载扩展（local/web/remote 三种，Node.js 或浏览器 WebWorker 运行时）。官方明确列出"VS Code 的 Extension Host 阻止扩展：影响启动性能 / 拖慢 UI 操作 / 修改 UI"——隔离保护的是内核的启动速度、响应性与界面。[来源: https://code.visualstudio.com/api/advanced-topics/extension-host#stability-and-performance]
- 运行位置显式协商：manifest 的 `extensionKind` 让扩展声明偏好（如 ["workspace"] 表示必须访问工作区内容，["ui","workspace"] 表示偏好 UI 侧）。[来源: https://code.visualstudio.com/api/advanced-topics/extension-host]
- API 稳定性与 Proposed API 的择时：官方原话是"我们非常重视 Extension API 兼容性……一旦引入某个 API，就无法再轻易修改它"。于是把不稳定 API 放进 Proposed API：随时可变、仅在 Insiders 可用、不得用于已发布扩展；本地开发需在 package.json 写 `enabledApiProposals` 并以 `--enable-proposed-api=<ID>` 启动，成熟后才转正。[来源: https://code.visualstudio.com/api/advanced-topics/using-proposed-api]
- 兼容边界由扩展自己申明：`engines.vscode` 声明兼容的 VS Code 版本范围，不能写 `*`。[来源: https://code.visualstudio.com/api/references/extension-manifest]

### A2. Kubernetes：CRD / Operator / Aggregation Layer

- 允许第三方定义新资源类型，目标是"不修改 Kubernetes 自身代码就扩展集群行为"：CRD 让用户不新增 API server 就能创建新类型；Aggregation Layer 把第三方 API server（APIService）作为下级挂在主 API server 之后代理。[来源: https://kubernetes.io/docs/concepts/extend-kubernetes/api-extension/custom-resources/ , https://kubernetes.io/docs/concepts/extend-kubernetes/api-extension/apiserver-aggregation/]
- 内核只白给通用能力：CR 一旦安装即自动获得 CRUD、Watch、核心 API server 的认证/授权（RBAC）、Finalizers、Admission Webhooks，kubectl 与 dashboard 也能显示。[来源: https://kubernetes.io/docs/concepts/extend-kubernetes/api-extension/custom-resources/#common-features]
- 第一道防污染闸是 schema 与剪枝：`apiextensions.k8s.io/v1` 强制 structural schema（根节点与每个字段都要有非空 type）；API server 不认识的字段在落 etcd 前被 prune（文档例子中 `someRandomField` 直接消失），第三方无法往存储层塞任意数据。[来源: https://kubernetes.io/docs/tasks/extend-kubernetes/custom-resources/custom-resource-definitions/#field-pruning]
- 第二道闸是 Admission Webhook：mutating 先跑（可改对象、打默认值），validating 后跑（可拒绝请求）；需要看到终态的策略必须用 validating，因为对象可能被 mutating 改过。[来源: https://kubernetes.io/docs/reference/access-authn-authz/extensible-admission-controllers/]
- 声明式 reconcile：CR 本身只能存取结构化数据，配上 custom controller 才是"真正的声明式 API"——你声明期望状态，控制器把当前状态对齐；Operator 就是"以 CR 为操作对象的控制器"，它只是 API 的客户端，通常跑在控制面之外。[来源: https://kubernetes.io/docs/concepts/extend-kubernetes/operator/]
- 版本演进有硬规则：`spec.versions` 中"有且只有一个版本必须标记为 storage version"，served 控制是否对外服务；跨 schema 变更要用 conversion webhook（ConversionReview 往返），无 schema 差异用 None 策略；自 v1.19 起可把某版本标 deprecated 并自定义 deprecationWarning，请求该版本时以响应头返回警告。[来源: https://kubernetes.io/docs/tasks/extend-kubernetes/custom-resources/custom-resource-definition-versioning/]
- 弃用有全局规则：《Kubernetes Deprecation Policy》规定 API 元素只能靠递增版本移除（Rule #1）、不能弃用为更不稳定的版本（Rule #3）、GA 版本在同一 major 内不得移除（Rule #4a）。[来源: https://kubernetes.io/docs/reference/using-api/deprecation-policy/]
- 扩展自身有性能义务：Aggregation Layer 要求扩展 API server 的 discovery 请求 5 秒内往返。[来源: https://kubernetes.io/docs/concepts/extend-kubernetes/api-extension/apiserver-aggregation/]

### A3. Backstage Plugin

- 旧前端系统是"插件包 + 应用编排"：把各类插件组合成一个 SPA，前端包与后端包分开。[来源: https://backstage.io/docs/plugins/]
- 新前端系统把 App 建成一棵 extension 树：每个 extension 有唯一 ID，格式 `[<kind>:][<namespace>][/][<name>]`，kind 由 blueprint 固定、namespace 默认取插件 ID；扩展间通信单向——子扩展用 output 产出数据，父扩展用 input 接收；input 可设 singleton、optional，以及 `internal: true`（只允许本插件的扩展接入，其它插件接入会被忽略并告警）——这就是插件级的"内核拒绝被污染"。[来源: https://backstage.io/docs/frontend-system/architecture/extensions]
- 低阶 `createExtension` 不鼓励直接使用，官方推荐从 blueprint 创建（在包 API 中找 `*Blueprint` 导出，通常在 `*-react` 包）。[来源: https://backstage.io/docs/frontend-system/architecture/extension-blueprints]
- 扩展可带 `if` 条件（基于 featureFlags / permissions 的 FilterPredicate，支持 $all/$any/$not），实现按权限与开关装配能力。[来源: https://backstage.io/docs/frontend-system/architecture/extensions]

### A4. 可对比：Chrome 与 Eclipse 的权限声明模型

- Chrome：在 manifest 声明意图，分五类——`permissions`（触发警告）、`optional_permissions`（运行时授权而非安装时）、`content_scripts.matches`、`host_permissions`、`optional_host_permissions`；官方定位是"权限限制扩展被恶意代码攻陷后的破坏范围"，部分权限在安装前或运行时弹窗征求同意；权限清单逐条标注触发什么警告。[来源: https://developer.chrome.com/docs/extensions/develop/concepts/declare-permissions , https://developer.chrome.com/docs/extensions/reference/permissions-list]
- Eclipse：extension point 是插座、extension 是插头；插件要允许别人扩展自己就声明 extension point，point 声明契约（XML 标记 + Java 接口），被扩展方对扩展方"除了契约之外一无所知"；schema 只用于开发期校验与文档生成，官方明确它**不做运行时校验**，部署的插件里甚至可以没有 schema 文件。[来源: https://help.eclipse.org/latest/topic/org.eclipse.pde.doc.user/concepts/extension.htm , https://raw.githubusercontent.com/eclipse-platform/eclipse.platform/master/docs/FAQ/FAQ_What_is_an_extension_point_schema.md]
- A 部分共性：能力面=声明式元数据（contributes / CRD schema / extension ID+input / manifest permissions）；执行体=隔离位置（Extension Host / 独立 controller 或 extension apiserver / 独立插件包）；内核只做通用能力（认证授权、CRUD、生命周期、剪枝与校验）。第三方越界的结果是：被剪枝、被 webhook 拒、或被 internal input 忽略。

## B. 能力可发现性：能力上千时怎么被找到

### B1. OpenAPI 目录/索引

- spec 规定用于发现的元数据：`operationId` 是"唯一标识该操作的字符串，必须在 API 内唯一"，工具和库可用它唯一定位操作；`tags` 数组用于"按资源或任意限定符对操作做逻辑分组"，顶层 tags 顺序可供解析工具决定展示顺序；`servers` 提供目标服务器连接信息，路径会拼接 server url 形成隐式连接。[来源: https://spec.openapis.org/oas/latest.html]
- 渲染器只是消费这些元数据：Redoc CE 采"三栏布局：导航、详细文档、请求与响应示例"；Scalar 一行 `Scalar.createApiReference('#app', { url: '<OpenAPI 文档>' })` 拉起。[来源: https://redocly.com/docs/redoc , https://scalar.com/products/api-references/getting-started]
- 为什么需要 API catalog：一个 OAD 可拆成多文档，多文档解析属 implementation-defined，跨文档要靠 operationId、tag 名称、server URL 等隐式连接；API 一多，必须有集中编目层回答"有哪些 API、谁负责、在哪、怎么连"。[来源: https://spec.openapis.org/oas/latest.html]

### B2. Backstage Software Catalog 的可发现性设计

- catalog 是"追踪全部软件的所有权与元数据"的集中系统，元数据 YAML 与代码同仓、被采集后可视化；官方口径是让一个团队管 10 个服务变容易，让公司管上千个成为可能。[来源: https://backstage.io/docs/features/software-catalog/]
- 描述符格式本身就是可发现性字段集：信封 `apiVersion`/`kind`；metadata 下 name/namespace/title/description/labels/annotations/tags/links；`relations` 是只读关系列表（如 ownedBy），官方要求以 relations 而非 `spec.owner` 作为所有权权威来源（owner 可能来自 CODEOWNERS 而非 YAML）；`status` 用各自 type 前缀上报。[来源: https://backstage.io/docs/features/software-catalog/descriptor-format]
- 搜索是独立子系统、可换引擎：支持 Elasticsearch/OpenSearch、Lunr、Postgres，可用 collators 把插件内容编入索引，Software Catalog 与 TechDocs 已原生接入。[来源: https://backstage.io/docs/features/search/]

### B3. Kubernetes Discovery API 与 Aggregated Discovery

- Discovery API 只发布"能力清单"而不发 schema：每个资源给出名称、集群/命名空间作用域、端点 URL 与支持动词、别名、group/version/kind；完整 schema 属于 OpenAPI 文档，体量显著更大。[来源: https://kubernetes.io/docs/concepts/overview/kubernetes-api/#discovery-api]
- 老问题的量化：KEP-3352 开篇写明所有客户端必须逐 group-version 请求才能发现可用 API，"这造成请求风暴，并成为延迟与限流的来源"，最多约 80 个请求、多数对象小于 1,024 字节；kubectl 的 CachedDiscoveryClient 用 6 小时不刷新的缓存缓解，代价是新鲜度可疑。[来源: https://www.kubernetes.dev/resources/keps/3352]
- 解法是把发现聚合成两个文档：`/api` 与 `/apis` 两个端点即可拿到全部资源，"大幅减少获取 discovery 数据所需的请求数"；需带 `Accept: application/json;v=v2;g=apidiscovery.k8s.io;as=APIGroupDiscoveryList`，不带则退回非聚合文档；支持 ETag 与 protobuf；由 AggregatedDiscoveryEndpoint 特性门控，已是稳定支持。[来源: https://kubernetes.io/docs/concepts/overview/kubernetes-api/#aggregated-discovery]
- 对照来看，CRD 会把自己 structural 的 OpenAPI v3 校验 schema 发布为 OpenAPI v3/v2，供 kubectl 做客户端校验与 `kubectl explain`——即"清单层"与"细节层"分开提供。[来源: https://kubernetes.io/docs/tasks/extend-kubernetes/custom-resources/custom-resource-definitions/#publish-validation-schema-in-openapi]
- 同类模式也在 MCP 协议里：客户端用 `tools/list` 发现工具，该操作支持分页（cursor/nextCursor），清单变更可通过 listChanged 发 `notifications/tools/list_changed`。[来源: https://modelcontextprotocol.io/specification/2025-06-18/server/tools]

### B4. 上下文预算策略：能力不该一次性进上下文

- 问题被量化（Anthropic tool search 页）：工具定义全部预载有两个后果——上下文膨胀（GitHub/Slack/Sentry/Grafana/Splunk 这类多服务器组合在模型干活前就吃掉约 55k tokens）与选择准确率下降（可用工具超过 30–50 个后，模型挑对工具的能力开始退化）。[来源: https://docs.claude.com/en/docs/agents-and-tools/tool-use/tool-search-tool]
- 官方机制：工具定义仍全部随请求发送，但对不需预载的设 `defer_loading: true`（至少留一个非延迟，通常是搜索工具本身，并建议保留最常用的 3–5 个）；模型用 tool search 检索（regex 变体写 Python 正则，BM25 变体用自然语言），API 返回 `tool_reference` 块并自动展开成完整定义，默认最多 5 条（limit 上限 10,000）；被延迟的工具不进 system prompt 前缀，因此 prompt caching 不受影响；也可用自定义搜索工具返回 tool_reference 做向量检索。[来源: 同上]
- 另一条路是把工具做成文件树/代码 API：Anthropic《Code execution with MCP》给出 150,000 → 2,000 tokens（省 98.7%）的对比，并提出两个可迁移手法——progressive disclosure（模型按需读文件，或用 `search_tools` 检索）；以及 search_tools 的 detail level 参数（只要名字 / 名字+描述 / 完整定义含 schema）。[来源: https://www.anthropic.com/engineering/code-execution-with-mcp]
- 原则性表述：上下文工程要"找到让期望结果概率最大的那组最小高信号 token"，采用 just-in-time 检索（Claude Code 用 glob/grep 按需取文件）。[来源: https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents]
- OpenAI 的多工具建议（function calling 指南原文）："初始可用函数保持少量以提高准确率……任一时刻一轮开始时可用函数尽量少于 20 个，虽然只是软性建议；用 tool search 把体量大或不常用的工具面延迟掉，而不是一次性全暴露"；并建议用 namespace 按域分组（如 crm / billing / shipping）帮助模型在不同系统间选择。[来源: https://platform.openai.com/docs/guides/function-calling , https://platform.openai.com/docs/guides/tools]

## 能力多到装不下时的取舍

1) 别把上限硬编码进搜索。K8s 的教训是"清单聚合、细节按需"：把 664 条能力的索引（名称/标签/归属/一句话）做成少数几次请求就能拿全的聚合文档，把细则（参数 schema）留到调用前才拉。硬编码 100 条既不是聚合也不是分页，Agent 只见 15% 的宇宙。[来源: kubernetes-api#aggregated-discovery, keps/3352]
2) 检索在服务端做，返回"指针"而不是全文。Anthropic 的 `defer_loading` + `tool_reference` 是现成范式：搜索返回引用，用时再展开，同时保住 prompt 前缀缓存；OpenAI 的经验值是"一轮开始 <20 个函数"。若 100 条上限本意是控上下文，正确形态是"每轮只展开命中/最常用的 3–5 个 + 游标分页 + 总数"。[来源: tool-search-tool, function-calling]
3) 分层披露与分组优于抹平列表。三类现成元数据足以把 664 拆小：命名空间/域（OpenAI namespace）、标签（OpenAPI tags 的逻辑分组语义）、关系与归属（Backstage relations + owner/tags，以 relations 为权威）。让 Agent 先按域收敛，域内再检索。[来源: function-calling, spec.openapis.org/oas/latest.html, backstage descriptor-format]
4) 发现层要支持增量变更，而不是每次全量重扫。MCP 用游标分页 + listChanged 通知，K8s 用 ETag；能力注册表也应支持"版本/游标 + 变更通知"。[来源: MCP server/tools, kubernetes-api#aggregated-discovery]
5) 内核保护与能力发现须同时设计。VS Code 用独立 Extension Host 保证扩展不拖慢启动、不改 UI；K8s 用 structural schema + pruning + admission webhook 保证第三方数据进不了核心存储；Chrome 用权限声明与安装/运行时警告控制破坏面；Eclipse 明确 schema 只做开发期校验。对能力操作系统的含义：能力注册要带权限/作用域声明，越权调用在内核侧拒绝，而不是靠提示词约束。[来源: extension-host, custom-resource-definitions, declare-permissions, eclipse FAQ]
6) 成本递减的修补顺序：先把 100 上限改成"游标分页 + 总数 + 精简字段默认返回"，再加 detail level（name / name+desc / full schema），最后加一次服务端检索（BM25 起步即可，Anthropic 的 BM25 变体说明不需要向量库也能显著改善）。[来源: tool-search-tool]
