## 〇、设计宗旨：按目的做，缺什么自动补什么

> 本节是 2026-09-18 晚华哥口述的**原始目的**，是本文唯一需求来源。

### 0.1 目的（一句话）

```text
用户只要输入 url 和 key 就行 —— 缺的参数，底座自己补齐。
```

### 0.2 流程（华哥口述原样落地）

```text
                    用户输入
              ┌──────────────────┐
              │ url（必有）       │
              │ key（必有）       │
              │ 模型（可能没给）  │
              │ 协议（可能没给）  │
              └────────┬─────────┘
                       │
                       ↓
        ┌──────────────────────────────────┐
        │ 第一步：获取模型                   │
        │   没给模型 → 向端点取模型清单       │
        │   给了模型 → 跳过，直接用           │
        └──────────────┬───────────────────┘
                       │
                       ↓
        ┌──────────────────────────────────┐
        │ 第二步：拿模型去试协议             │
        │                                  │
        │  给了协议？                        │
        │    是 → 只打这一个（不走串行）      │
        │    否 → 三种串着打，命中即停        │
        └──────────────┬───────────────────┘
                       │
          ┌────────────┴────────────┐
          ↓                         ↓
   ┌─────────────┐          ┌──────────────────┐
   │ 有 1 个成功  │          │ 3 个全失败        │
   │ → 返回成功   │          │ → 返回 3 个失败   │
   │ + 另两个的   │          │ + 各自的失败原因  │
   │   失败原因   │          │                  │
   └─────────────┘          └──────────────────┘
```

**华哥原话**：「这个本质上用户只要输入 url 和 key 就行；当然如果输入了模型，输入了协议，
那就不用去走串行了。等于说缺了参数，就需要自动获取完成。**这样子才是原子能力**。」

### 0.3 这条宗旨带来的三个设计决定

| # | 决定 | 理由 |
|---|---|---|
| 1 | **入口只有一个**，参数除 url 外全选填 | 调用方给多少用多少，缺的自动补 |
| 2 | **失败要分开报**，不能笼统"不通" | 「其他两个失败的就说一下失败的原因」 |
| 3 | **命中即停** | 「如果是有其中一个成功的，就返回」——不为没用的协议白花时间 |

**⇒ 上一版方案（扫端口自动发现）已废弃**：
那是按「参数」设计（扫哪些端口），不是按「目的」设计；且它的场景是给**人**省手填，
而底座用户是 agent。详见同目录 `本机推理端点自动发现方案_20260918.md`（状态：已废弃）。

## 一、实测：这条流程真能跑通（原型已验证）

### 1.1 原型跑通结果（四场景）

原型脚本：`开发文档/分析/素材_DGX-Spark本地算力视频_20260918/原型探针.py`

| 场景 | 输入 | 结果 | 耗时 |
|---|---|---|---|
| **A** 最省事 | 只给 url+key（8328） | 自动取到模型 `grok-4.5`；三协议都不通（**如实报 404**） | 22 ms |
| **B** 最省事 | 只给 url+key（本地 61449） | 自动取到模型 `Qwen3.6-27B-Q5_K_M.gguf`；**命中 chat_completions** | 1030 ms |
| **C** 给全了 | url+key+协议=anthropic | **只打一枪**（试了 1 种，不串行） | 399 ms |
| **D** 全失败 | 假地址 | **返回三个失败**，各带原因（连接失败） | 快 |

⇒ 四个场景都符合 §0.2 流程，**华哥的设计可直接实现**。

### 1.2 实测踩到的三个坑（都会让探针变成"假探针"）

```text
★ 坑一：第一步「取模型」必须用 GET，不能用 POST
   实测同一端点：
     GET  /v1/models → 200 ✅
     POST /v1/models → 404 ❌（llama-server 的 POST 走 chat 路由，不认 /models）
   ⇒ 硬要求，写错第一步就整个失败。

★ 坑二：状态码判不出协议 —— 必须看响应体特征
   本地 llama-server 是「宽容服务器」：/chat/completions、/responses、/messages
   全回 200（不认识的路径也照接）。
   实测三协议响应体特征（唯一可靠判据）：
     chat_completions   → 有 choices[]
     codex_responses    → 有 output[]（且无 choices）
     anthropic_messages → 有 content + type

★ 坑三：/models 通 ≠ 该端点能聊
   实测 8328：
     GET /v1/models               → 200（模型 grok-4.5）
     GET /hermes-chat/v1/models   → 200（模型 deepseek-v4-flash-0731）★ 两个根路径模型不同
     POST /v1/chat/completions    → 404
     POST /hermes-chat/v1/chat/completions → 200 ✅（真正能聊的是这个）
   ⇒ 「取到模型」不代表「能聊」；两步结果必须分开如实报，
     不能因为第一步成功就宣布可用。
```

**坑三的处置口径**：探针**不猜根路径**（猜就是瞎试），而是
① 直接用调用方给的 `url`；② 若三协议全 404，如实报「该 url 下三协议均不存在」，
并把**试过的完整路径**列出来，供调用方换 url 重试。

### 1.3 华哥另一个问题：本地模型端口能不能固定？

**能。** 源码实证（`实现/模型连接器.py` 608–615 行）：

```python
def _分配端口(端口: int | None) -> int:
    if isinstance(端口, int) and 端口 > 0:
        return 端口          # ← ★ 给了就用（可固定）
    import socket
    with socket.socket() as 套接字:
        套接字.bind(("127.0.0.1", 0))
        return int(套接字.getsockname()[1])   # ← 没给才随机
```

能力契约里 `端口` 参数：`类型=整数型，必填=False，说明=服务端口`。

⇒ **端口完全可固定**：调用 `启动本地模型` 时显式传 `端口` 即可。
当前端口飘来飘去（55334→61449）是**因为调用方没传**，底座走了随机兜底的正常行为，
**不是 bug**。

> 要长期固定，在启动处显式传端口（如 `8050`）即可 ——
> 与华哥既有习惯一致（`启动-Qwen3.8-27B-UD-Q4_K_M.command` 里就写了 `服务端口=8050`）。

## 二、要做的能力

### 2.1 P0 · `探测模型端点`（建议做）

| 项 | 内容 |
|---|---|
| 能力 id | `大语言模型支持库.模型连接器.探测模型端点` |
| **参数** | `url`（文本型，**必填**）<br>`api_key`（文本型，选填）<br>`模型`（文本型，选填，**缺省自动取**）<br>`协议`（文本型，选填，**缺省自动试三种**）<br>`超时秒`（整数型，选填，默认 15） |
| **返回** | `可用`（逻辑型）<br>`命中协议`（文本型；全失败时 = `都不通`）<br>`模型`（文本型，实际用的模型名）<br>`模型清单`（列表型，第一步取到的全量）<br>`响应毫秒`（双精度数型）<br>**`逐项结果`**（列表型，每项含 `协议`/`状态码`/`可用`/`判据`/`请求路径`）<br>**`诊断`**（列表型，如「自动取到模型：[…]」） |
| 错误码 | `参数不合法`（url 非法）<br>`端点不可达`（连接层失败）<br>`鉴权失败`（401/403） |
| 行为 | 只读、幂等、**有轻微副作用（消耗少量 token）**、超时可重试 |

**实现要点（照 §0.2 流程 + §1.2 三个坑）**：

```text
第一步 · 取模型（仅当调用方没给模型）
    用 GET {url}/models          ★ 必须 GET（坑一）
    取到 → 用清单第一个；取不到 → 用占位名继续（不中断流程），写进「诊断」

第二步 · 试协议
    给了协议 → 只打这一个（不串行）
    没给     → 三种按序打，★ 命中即停
    判可用：HTTP 200 不够，要看响应体特征（坑二）
      chat_completions → choices[] ；codex_responses → output[] ；anthropic_messages → content+type

返回
    有成功 → 可用=真、命中协议=该协议；另两个失败原因照样放进「逐项结果」
    全失败 → 可用=假、命中协议=都不通；三项失败原因全返回（不吞）
```

**命名与形态对齐现有惯例**：底座已有 **22 处探针能力**
（`检查提供者` / `检查可用性` / `版本探针`，实测全是探本机工具），
本能力沿用同一形态（`可用` + 详情字段），只是从「探本机工具」扩到「探模型端点」。

## 三、实测支撑的两条硬约束（路由必守）

| 约束 | 实测依据 | 落到代码 |
|---|---|---|
| **本地不常驻** | 十分钟内端口变两轮（8000/8016/30001/11434 → 55334 → 61449） | 本地模型**按需拉起**，不写常驻路由表 |
| **本地窗口小，接不住 agent 请求** | 发 100K tokens → `exceed_context_size_error`，`n_ctx=32768` | 路由**必须带上下文门槛**，超门槛排除本地 |

> 华哥：「agent 的上下文很离谱……像 hermes、codex、claude 动不动就几百 K 的请求，
> 本地也跑不过来，一个你好估计都要 3 分钟才有回复」——**已实测坐实**。
> 本地方向只对上下文不大的场景有意义（如 V3 自建 agent）。

## 四、明确不做（记录理由，防重复提议）

| 不做 | 理由 |
|---|---|
| 扫端口式「自动发现」 | 按参数而非按目的设计；且是给「人」省手填（agent 不需要） |
| 跨机算力池 / 多矩阵 | 华哥：「就这台电脑，也拉不起多少模型」、**「无法验证」**；`项目说明.md` 明文「分布式不在范围内」 |
| 隐私路由 / 敏感分类 | 哲学第 9 条「0 业务假设」；9.3「隐私是业务端的事」 |
| 本地常驻路由 | 华哥：本地没有常驻 LLM，没必要 |
| 替用户决定用哪个模型 | 华哥：「用什么模型，本质上是用户去配置的」 |
| 探针「猜根路径」 | 猜就是瞎试；如实报试过的路径，让调用方换 url（§1.2 坑三处置口径） |

## 六、验收判据（把「能不能验证」说清）

### 6.1 探针怎么验（可完整验证 ✅）

```text
正向 · 真实端点：
  ① 只给 url+key 探本地端点 → 应命中 chat_completions，并回带真模型名
  ② 只给 url+key 探 8328    → 应「取到模型 grok-4.5，但三协议 404」如实报（§1.2 坑三）
  ③ 给全 url+key+协议       → 应「只试 1 种」（验证不串行）
  ④ 故意给错 key            → 必须报「鉴权失败」，不是笼统「不通」
  ⑤ 故意给错端口            → 必须报「端点不可达」
  ⑥ 给非模型 HTTP 服务      → 报「200 但响应体无该协议特征」

夹具 · 可重复（平台无关）：
  ⑦ 用 验证夹具/模型HTTP服务.py 起假端点 → 三协议各验一遍
  ⑧ 反向验证：把夹具改成只认 anthropic → 探针必须只报 anthropic

判据：不是「能连通」，而是**每种失败都报出正确的失败类型**（不许笼统「不通」）
```

### 6.2 路由怎么验（P1，只验可验证的）

```text
能验：
  · 固定候选 + 固定任务 → 排序稳定（纯函数可重复）
  · 上下文超门槛 → 本地候选被正确排除（依据：实测本地窗口 32768）

不能验（故不做）：
  · 「哪个模型答得好」——需人工评估，无法自动判定
  ⇒ 这正是华哥说多矩阵「无法验证」的同一类问题
```
