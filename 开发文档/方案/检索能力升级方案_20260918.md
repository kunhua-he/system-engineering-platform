## 一、华哥原话与需求拆解

> 「我觉得搜索能力，是否可以选择搜索内容，还是选择简洁，或者选择标题。」
> 「选择简介，标题，内容，等等的这种。」
> 「然后如果你搜索的词没搜到的，你就加多一个可以做多一个原子能力。搜到这个文件之后，可以加上他的搜索词，慢慢完善。就是你一开始搜到时候没搜到的词。这样子越用就越好用了。本质上是一个不断的完善的过程。」

| 华哥说的 | 本质需求 | 现状 |
|---|---|---|
| 可以选搜内容 / 简洁 / 标题 | **返回粒度可选** | `能力目录.搜索能力` 已有三档（名称 / 名称+说明 / 完整契约）＝标杆；`项目文档支持库.查询索引` **无粒度档**，永远只回 180 字片段 |
| 一次没搜到就加上搜索词 | **未命中登记** | 全仓**没有**这个信号——搜不到＝空列表，无任何留痕 |
| 慢慢完善、越用越好用 | **自动扩词闭环** | 无，每次从零试词 |

## 二、为什么这是真缺陷（不是加功能）

Agent 检索一次的代价＝**一次往返 + 一轮思考**（实测单次往返 1.8–2.7 秒）。当前形态逼出三类浪费：

1. **粒度不可选** → 要标题只给片段、要全文给不了，Agent 只能再读文件（占本批工具调用的大头）。
2. **一次只试一组词** → 搜不到就换词重来，每次都是完整往返。
3. **搜不到不留痕** → 同一个词下个会话、下个子代理还要再撞一次；**教训不沉淀**（哲学 14.3：反复犯错的开发要补底层）。

## 三、落地方案（三期，只增不改）

### 三期总览

| 期 | 内容 | 落点 | 是否有第二腿 |
|---|---|---|---|
| **一** | `查询索引` 加 **返回粒度**（标题 / 简介 / 内容 / 完整） | `项目文档支持库/实现/索引库.py` | 否，改现有能力加参数 |
| **二** | `查询索引` 加 **搜索词**（一次传多组，各组独立打分，返回最优组） | 同上 | 否，同一能力 |
| **三** | 新增 **2 条能力**：`登记未命中词` / `列出未命中词`；查询时**自动扩词** | 新增 `实现/未命中词.py` + 索引库表 | 否，新增能力不是新腿 |

### 3.1 返回粒度（第一、二期）

**四档**，取值与语义（对齐 `能力目录.搜索能力` 已有的三档命名习惯，此处按文档检索场景扩为四档）：

| 档 | 回什么 | 用在什么场景 |
|---|---|---|
| `标题` | 文档相对路径 / 标题 / 命中块数 | 先看有哪些文档相关，最省 token |
| `简介`（默认） | 上档 + 起始行 / 结束行 / 块类型 / 片段（180 字） | 判断要不要深入 |
| `内容` | 上档 + **完整块文本**（截断上限由参数给） | 直接拿正文，省一次读文件 |
| `完整` | 上档 + 命中词列表 / 覆盖率 / 评分 / 扩词来源 | 排查为什么排这个序 |

**为什么默认 `简介`**：与改前返回**逐字段一致**，老调用零行为变化（哲学 1.2 只增不改）。

### 3.2 多词择优（第二期）

新增参数 `搜索词`（列表型）：**每项是一组词**，各组独立检索、独立打分，**返回评分最高的那一组**结果。

```
搜索词 = [["开通", "流程"], ["签约", "步骤"], ["入驻"]]
```

- 不传 `搜索词` → 用 `关键词` 当**唯一一组**（老行为，逐字段不变）。
- 传了 → `关键词` 只在返回里原样带回，不参与检索。

**评分口径（复用现成字段，不自创）**：现成已有 `命中词数` 与 `命中次数`，本方案在其上补一个**覆盖率**，三项定序：

```
评分 = (覆盖率, 命中词数, 命中次数)    覆盖率 = 本组命中词数 / 本组词数
```

**选「组」的判据**：先比该组**最优块评分**，相同再比**命中块总数**，再相同按组序取先（稳定，不随机）。

### 3.3 未命中词闭环（第三期）

**新增一张表**（复用现有 `项目文档库.db`，不新建库）：

```sql
CREATE TABLE IF NOT EXISTS 未命中词(
  项目名 TEXT NOT NULL, 原始词 TEXT NOT NULL, 建议词 TEXT NOT NULL,
  命中次数 INTEGER NOT NULL DEFAULT 0, 登记时间 REAL NOT NULL, 更新时间 REAL NOT NULL,
  PRIMARY KEY(项目名, 原始词));
```

**两条新能力**（`项目文档支持库` 内，包内文件 `实现/未命中词.py`）：

| 能力 | 参数 | 语义 |
|---|---|---|
| `登记未命中词` | 项目名 / 原始词 / 建议词 / 库文件 | UPSERT：同一项目同一原始词覆盖更新（幂等）。**建议词必填**——只登记"没搜到"没有意义，必须带上"那该搜什么" |
| `列出未命中词` | 项目名 / 库文件 | 列该项目的未命中词（按命中次数降序），供 Agent 一次补齐 |

**自动扩词（关掉闭环的那一环）**：`查询索引` 在**某组词零命中**时，先查 `未命中词` 表有没有该组的建议词；有则该组**用建议词重查**，命中后返回里标注 `扩词来源`（`原始词 → 建议词`）。

- **扩词只对"零命中的那一组"生效**，不做全局替换（防把本来对的词也改掉）。
- 扩词是**只读动作**，不改表、不写盘；`命中次数` 只在**调用方显式调 `登记未命中词`** 时累加——**平台不自作主张记账**。

### 3.4 为什么用「建议词」而不是「同义词表」

- 同义词表是**静态**的、要人预先维护全；建议词是**按需长出来**的，跟着真实检索失败积累——这才是华哥说的「慢慢完善」。
- 存 `原始词 → 建议词` 的**实测映射**，可直接审计「哪些词我们一直搜不到」，比抽象的语义词表信息量大。
- 放**数据表**而非代码常量：改词只改数据（与 `判据.json` 同哲学）。

## 四、被否决的做法（记录取舍，防后人重走）

| 做法 | 为什么否决 |
|---|---|
| **新建一个独立的「检索支持库」** | 现有 `项目文档支持库.查询索引` 就是干这个的，新建库＝同一件事两套实现（违反哲学 1.2 不保留旧腿） |
| **把 `关键词` 参数直接改成收列表** | 破坏老调用（哲学：只增不改）。加**新**参数 `搜索词` 与老参数并存 |
| **用 LLM 给搜索词打分** | 检索不该付一次 LLM 调用的代价（`索引库.py` 首行已明写此口径）；且慢、不可复现 |
| **搜不到时自动写 `未命中词` 表** | 写动作由**只读能力**暗自发生产生副作用，违反「副作用：只读」契约面；改由调用方显式登记 |
| **全库重建为向量索引** | 本需求是「粒度 + 择优 + 沉淀」，不是「语义召回」；引向量＝换问题，另立项目 |
| **扩词时把全部组都替换** | 会把本来命中的组也改坏；只对该零命中的那一组生效 |

## 五、影响面与验收

**改动文件**（全部在 `支持库/后端/项目文档支持库/` 内 + 项目文档）：

| `说明/使用说明.md` | 加参数表行 + 新能力说明（**版本号必升**，否则门禁报「能力级版本不一致」） |
| `完整性摘要.json` | 重算（**带精确路径**，禁跑不带参数的全量重算） |
| 本方案文档 | 状态从「方案」改「已落地」并附实测 |

**验收口径**：
1. **老调用零行为变化**：不传新参数时返回**逐字段**与改前一致（构造同一库两种调用比对）。
2. **四档粒度各自真跑**，返回字段集合与本文表格逐条对上。
3. **多词择优真跑**：构造「A 组部分命中、B 组全命中」的库，确认回的是 B 组且 `生效搜索词` 正确。
4. **闭环真跑**：搜一个不存在的词 → 零命中 → 登记建议词 → 再搜 → **自动扩词命中**且标注来源。
5. **反向验证**：摘掉评分排序 → 测试必红；还原 → 必绿。
6. 门禁 + 编译器无新增违规。
