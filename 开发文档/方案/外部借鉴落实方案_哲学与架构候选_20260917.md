## 〇、一页结论

### 0.1 本项目四个卡点（实测数据）

```
卡点 A｜生成物手工同步：改 1 源文件要联动 6 份生成物；139 包 ≈ 834 同步点；
        历史提交信息里「漂移 85 次 / 重算摘要 50 次 / 父包 42 次」
卡点 B｜规则有、判据有，但无强制点：
        「契约变更判定」有哲学 5.3 + 判据模块 + 单测 → 发布门禁 0 命中；
        「测试体系门禁」有判据 + CLI → 发布门禁明文「需单独手工执行」
卡点 C｜门禁「通过」语义分裂：一个「通过」同时表示「零违规」（56 项）与
        「未比基线更差」（测试伪装 271 项 / 公开调用 23 项）
卡点 D｜反向证明不足：缺「故意弄坏 → 必须报红」体系；
        实测 264/742 个正向步骤只验形状（35.6%）；能力零验证场景 = 0 条（664/664 全覆盖）
```

### 0.2 ★ 活的证据（本会话实测，非推断）

```
发布门禁（HEAD c9f84c3d）：发布状态 **通过**，72 项 ✓ / 0 红
测试体系门禁（HEAD 76ae77c6）：**失败** —— 1 项新增红
   （190 测试文件 / 2139 用例 / 真跑 189-190 通过 / 耗时 184 秒）
⇒ **"发布门禁通过"不等于"仓库健康"**：那道真正在跑 2139 个用例的门禁，
  压根不在发布链里，而它当时是红的。
```

### 0.3 外部处方（35 个项目精读后，四个卡点的答案都已存在）

| 卡点 | 外部一致处方 | 代表项目 |
|---|---|---|
| A | 生成↔校验配对命令；判据=「跑完生成器后无 diff」；生成物带**输入指纹**；标记「勿手改」 | kyverno `verify-codegen`、please hash-based、buf `DO NOT EDIT`、terraform `objchange` |
| B | 规则写成一等公民；**门禁加"元检查"**（所有判据必须被正式入口引用）；例外贴规则写理由；工具自测 | dependency-cruiser、ArchUnit、OPA、conftest |
| C | 同一套规则 + **severity 两档**；三档阈值 **high/low/break**（break 默认 null 显式配置）；输出结构化变更摘要 | dependency-cruiser `error`/`warn`、stryker `high/low/break`、conftest 双跑、terraform `change_summary` |
| D | 样本写成规则的**接口义务**；**元测试自动遍历全部规则×全部样本**；正例+反例配对；变异得分+阈值 | cosmic-ray `examples()`、stryker、pitest |

### 0.4 ★ 三条"元教训"（跨卡点，最重要）

```
① 判据存在 ≠ 有人强制。pre-commit 实测可被 `git commit --no-verify` 完全绕过
   ⇒ 任何"靠记得跑"的检查都不算强制点；强制点必须在必经路径/服务端。

② "样本/证据"应是**接口义务**，不是另维护的一张表。
   cosmic-ray 的算子必须实现 `examples()`，元测试自动遍历所有算子×全部样本
   ⇒ 忘带样本 = 元测试失败。**这才是"不挤牙膏"的机制内核。**

③ 用**连续量 + 分档**表达质量水位，不用"通过/失败"二值。
   stryker high/low/break；dependency-cruiser error/warn；conftest 双跑
   ⇒ 本项目「通过」一词必须拆，"是否阻断"要成为显式配置。
```

# 一、哲学补充候选（8 条，逐条给可直接写进哲学的文本）

> 格式：**条款文本**（可直接采用）｜**外部依据**（原文/文件行号）｜**为什么补**｜**与现有哲学的关系**

## P-1 【契约兼容性分级】→ 补进第 5 条

**条款文本**：
> **5.4 契约兼容性按包分档**：每个包在 `包声明.json` 里声明自己的契约兼容档位 ——
> **冻结档**（对外契约面任一变化都必须升大版本）／**兼容档**（允许新增可选参数、新增错误码；
> 禁止改类型、删参数、改必填）／**开发档**（允许任意变化，但仍记录指纹）。
> 档位是**包的属性**，不是全局一刀切。

**外部依据**：
- buf `buf.yaml`：`breaking: use: [WIRE_JSON]` —— 兼容级别是**连续谱**：
  `FILE < PACKAGE < WIRE < WIRE_JSON < BASIC < DEFAULT < MINIMAL`，用户选一档。
- kyverno `AGENTS.md` API Design Rules：「**New attributes can be added without a new version**」
  （新增属性不需要新版本）+「Attributes cannot be deleted or modified in a version」。

**为什么补**：本项目现状是**一档到底**（对外契约面任一变化即需升版本）——
简单，但无法表达"这个包还年轻、允许破坏" vs "这个包已冻结、一个字段都不能动"。
且 kyverno 的做法更符合直觉：**新增可选参数不算破坏性变更**。

**与现有哲学的关系**：与 6.1「阈值不设硬门禁，只按改动频率与读取成本」**同一种思路**——
按实际情况分档，而不是一个绝对阈值。

## P-2 【废弃必须有到期承诺】→ 补进第 1 条 1.2

**条款文本**：
> **1.2 补充：保留旧物的三件套**。任何被保留的兼容映射 / 旧入口 / 旧字段 / 旧别名，
> 必须**同时**登记三样：① **到期版本**（哪个版本移除）② **使用计数**（还有人用吗）
> ③ **删除条件**（满足什么就删）。三者缺一，该保留项**即视为违规**（不是"暂缓"，是"违规"）。

**外部依据**：
- kyverno：`Attributes cannot be deleted or modified in a version; **deprecate and remove after
  3 minor releases**` —— 量化到"3 个小版本"。
- 报告2 §8.4 建议：「边界协议兼容映射：允许，但必须有**到期版本、使用计数和删除条件**」。

**为什么补**：哲学 1.2 说"不保留旧腿、直接删除"，但决策记录 0024 又允许为真实外部依赖保留
旧错误键兼容映射 —— **两者之间缺一条可执行的量化规则**（这也正是报告2 指出的"哲学冲突 C"）。

## P-3 【规则必须能指出"谁在强制它"】→ 新增第 13 条

**条款文本**：
> **第 13 条 规则三要素（判据 / 强制点 / 反向试验）**：本项目的每一条规则，
> 都必须能回答三个问题：
> ① **判据实现在哪**（`文件:函数`）② **强制点在哪**（哪个门禁的哪一项，或"人工治理"）
> ③ **反向试验在哪**（哪个"故意弄坏 → 必须报红"的样本）。
> **三者缺一即为"纸面规则"**，由发布门禁的「规则自检」项报红。
> **强制点的定义**：位于必经路径（发布门禁 / CI）上的检查；
> **"靠开发者记得单独跑"的脚本不算强制点**。

**外部依据**：
- OPA：策略即代码（rego）+ **策略自带测试**（`build/policy/pr-check/pr_check_test.rego`）+
  接在 CI 必经路径（`build/policy/` 由 workflow 调用）。
- conftest `.github/workflows/pr.yaml`：门禁在**必经路径**上，且有 6 个可借鉴机制。
- **pre-commit 的反面实证**：它是客户端钩子，仓库内搜 `no-verify` **0 命中**，
  `git commit --no-verify` 可完全绕过 ⇒ **本地钩子不是强制点**。

**为什么补**：这是本项目**最缺的一条**。实测：
「契约变更判定」模块全仓引用只有 README / 方案文档 / 测试，**发布门禁 0 命中**；
「测试体系门禁」有完整判据 + CLI，但发布门禁明文写着「需单独手工执行」。
⇒ 规则不是没有，是**没人强制**。补上这条，"纸面规则"就会在提交时自己冒出来。

## P-4 【门禁结论四态，"是否阻断"是显式配置】→ 新增第 14 条

**条款文本**：
> **第 14 条 门禁结论四态**：门禁结论只能是以下四者之一，**四者不得共用一个词**：
> **干净通过**（零违规）／**债务冻结**（未比存量基线更差，且基线只减不增）／
> **未核验**（该检查本次没跑到）／**失败**（超出基线或阻断项违规）。
> **"是否阻断"是显式配置项**（可为"不阻断"），不得用「未新增即放行」隐含。

**外部依据**：
- dependency-cruiser：**同一套规则**，两档预设 ——
  `recommended-strict.cjs`（全部 `severity="error"`）与 `recommended-warn-only.cjs`（全部 `warn`）。
  规则本体只有一份（`recommended.cjs`），档位是配置层映射。
- stryker schema：`mutationScoreThresholds = { high: 80, low: 60, break: null }`
  —— **三档 + `break` 默认 null（不阻断）**，即"默认只报告，想阻断就显式配数字"。
- conftest workflow：同一工具跑两遍 —— `continue-on-error: true`（警告级）+
  `--enable-category bugs`（阻断级）。

**为什么补**：直接解决卡点 C。现状一个「通过」同时表示零违规与"未比 271 更差"，
且"是否阻断"是**隐式的**（"未新增就放行"）。

## P-5 【生成物必须可机器校验一致】→ 补进第 7 条（编译与验证铁律）

**条款文本**：
> **7.9 生成物三律**：
> ① **生成物带输入指纹**（源内容摘要 + 生成器版本 + 契约版本），写进生成物自身；
> ② **生成物标记「勿手改」**（机器可识别）；
> ③ **发布门禁的唯一判据**：跑完全部生成器后，**工作区必须无差异**（`git status` 干净）；
> 有差异 = 有人改了源没重算，或有人手改了生成物。**两类都判红**。

**外部依据**：
- kyverno：`make verify-codegen`（表格描述原文 "**Verify generated code is up to date (CI check)**"）；
  Pre-PR 硬要求「Run `make codegen-all-code` then `make verify-codegen`」；
  判据原文「**ensure it exits cleanly with no git diff**」。
- please AGENTS.md 原文：「Caching is hash-based, not timestamp-based: hashes cover rule definition,
  config, sources, and secrets. **Anything that changes what a target produces must be folded
  into its hash**」。
- terraform `AssertObjectCompatible(schema, planned, actual)`：**实际必须与计划兼容**。
- buf：大面积 `DO NOT EDIT` 标记；kyverno 明文「**Never edit files matching `zz_generated.*`**」。

**为什么补**：卡点 A 的根治。现状靠"记得跑"，实测漂移 85 次。
且本项目**已有** `全量重算摘要 --只报`（能力上等价于 verify-codegen），
**只是没进发布门禁** —— 补这条等于把它接上。

## P-6 【样本是规则的接口义务】→ 补进第 12 条（审计与维修）

**条款文本**：
> **12.5 规则的破坏样本是接口义务**：每个门禁检查项必须自带
> ≥1 个「**应被拦住**」的样本与 ≥1 个「**不应被触发**」的样本；
> 并由**元测试自动遍历「全部检查项 × 全部样本」**。
> **新增检查项不带样本 = 元测试失败**（不是"后续补"，是"当场红"）。

**外部依据**：
- cosmic-ray `src/cosmic_ray/operators/number_replacer.py`：
  每个算子必须实现 `@classmethod def examples(cls)` 返回 `Example(变异前, 变异后)` 对；
  `tests/unittests/operators/test_operator_samples.py` 原文：
  ```python
  OPERATOR_PROVIDED_SAMPLES = tuple(
      Sample(operator_class, example)
      for operator_class in map(get_operator, operator_names())   # 遍历所有已注册算子
      for example in operator_class.examples())                    # 取每个算子自带样本
  ```
  并有正例 `test_mutation_changes_ast` + 反例 `test_no_mutation_leaves_ast_unchanged` 配对。
- ArchUnit：`@ArchTest` 让**规则本身就是测试**；`archunit-self-test-library` 里
  ArchUnit **用自己测自己的架构**（`ArchUnitArchitectureRules.java` 开头注释
  "Structural rules that the ArchUnit Core must fulfill."）。

**为什么补**：卡点 D 的根治，而且**比"手工维护破坏矩阵"强得多**：
样本是接口义务 ⇒ 自动强制；元测试遍历 ⇒ 新增规则忘带样本立刻失败。

## P-7 【豁免必须带理由且贴着规则写】→ 补进第 1 条（例外纪律）

**条款文本**：
> **1.8 例外必须自证**：任何依赖豁免 / 门禁豁免 / 存量登记，都必须在**规则侧**写明理由。
> 无理由的豁免判违规。豁免数据形态从 `{路径: 可依赖层}` 升级为
> `{路径: {可依赖层: [...], 理由: "..."}}`。

**外部依据**：
- ArchUnit `ArchUnitArchitectureRules.java` 原文（例外贴着规则，且写明为什么）：
  ```java
  // This is a conscious exception, to allow a more concise API. Otherwise, the configuration of the
  // ClassResolver would need to be moved to `importer` making it harder to use,
  // or we would need to remove the bound from Class<? extends ClassResolver>, which also makes the
  // API harder to use
  .ignoreDependency(ArchConfiguration.class, ClassResolver.class);
  ```
- ArchUnit 另有 `@ArchIgnore` 注解（豁免显式标注在规则处，而不是集中在一个 JSON 里）。

**为什么补**：本项目 `依赖防火墙.文件级豁免表` 已是"数据化例外"（比代码 if 好），
但**表里没有理由字段**：
```python
文件级豁免表 = {"运行核心": {"运行核心/启动运行核心网关.py": frozenset({"后端核心"})}}
```
看不出来"为什么这个文件可以例外"。而集中式基线（271 项 / 23 项）也有同样问题：
**看规则的人看不到它被豁免了**。

## P-8 【确定性按能力类别】→ 修正第 9 条 9.4

**条款文本**（替换 9.4）：
> **9.4 确定性按能力类别**：能力按确定性分为四类，在能力定义里声明：
> ① **纯确定性**：相同显式输入 → 相同输出（可写值断言）
> ② **可重放**：返回中记录随机种子 / 时钟 / 模型或提供者版本 / 上游摘要（可复算）
> ③ **外部观测**：只保证契约、错误语义与证据，**不保证值重复**（网络 / 浏览器）
> ④ **有副作用**：额外声明幂等键、重放语义、状态版本

**外部依据**：报告2 §8.2（并纠正我此前的误判 —— 该条写作「同样的输入 → 同样的输出」，
在 `项目说明.md:239`）；平台正式能力确含随机数/时间/网络/浏览器/LLM 五类。

**为什么补**：9.4 现在是**无条件规则**，但五类能力天然不满足它。
补四分类后，"验证该验到什么程度"就有了依据 —— 直接解决
「264/742 步只验形状」里"哪些是本来验不了、哪些是真欠账"的分派问题。
