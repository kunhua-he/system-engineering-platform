## 一、先看诊断：卡点不是"不够努力"，是三个结构性原因

### 卡点 1：**生成物手工同步 —— 这是 90% 返工的直接来源**

实测：改 1 个源文件（如 `能力定义.json`），要手工联动 **6 份生成物**：
```
包声明.json / 能力契约/参数契约.json / 能力数据/Agent查询数据.json
能力数据/能力搜索数据.json / 说明/使用说明.md / 完整性摘要.json
```
139 个包 ≈ **834 个必须与源保持同步的文件**。

**后果（真实数据）**：884 个提交里，提交信息出现
`漂移 85 次 / 重算摘要 50 次 / 父包 42 次 / 摘要不闭合 4 次` ——
**这不是"谁不小心"，是结构上必然出错**：只要靠人记得跑生成器，就一定会漏。

**修法方向**：这 6 份**全部改为按需生成或提交时自动生成**（或：源 + 生成器版本 + 内容摘要三件一起校验，人工不许编辑生成物）。
→ **这是投入产出比最高的一件事，应当排第一。**

### 卡点 2：**规则有、强制没有 —— 所以"发现一批、补一批"永远补不完**

实测三条：
```
「契约变化必升级版本」：有哲学(5.3) ✓ 有判据(对外契约变更判定.py) ✓ 有测试 ✓ → 发布门禁 0 命中 ✗
「测试桩不覆盖生产路径」：有判据 ✓ 有门禁 ✓ → 但 271 项存量可"未新增"就通过
「公开调用完整性」：有判据 ✓ 有门禁 ✓ → 但 23 项存量可带病通过
```
**后果**：每加一条规则，只加了"判据"，没加"强制点"。于是要靠**外部审计报告**来发现漏了 → 审计一次补一批 → 再审计再补。**这就是挤牙膏的机制**。

**修法方向**：建立「**规则 → 强制点 → 证据**」三元组总账，**缺哪一列都算不合格**，由门禁自证。
→ 这正是报告2 建议的「哲学—门禁—证据总账」，与我原本提的方向同构。

### 卡点 3：**哲学/文档空间在膨胀，且已有互相冲突的条款**

实测：
```
项目说明.md 被提交 86 次；未完成事项.md 被提交 147 次（9-16 单日 49 次）
决策记录 27 份（9-17 一天新增 15 份）
哲学 12 条含 49 个条款；已发现直接冲突：1.5「旧版进归档」vs 1.7「不做本地归档、旧版直接删」
```
**后果**：文档在增长，但**没有去重与冲突消解机制**，越写越难维护 —— 正是华哥说的「乱到七彩」。

## 二、方案总纲：四件事，按依赖顺序

```
第 1 件  哲学去重 + 冲突消解 + 废止声明机制（先把规则空间弄干净）
            ↓
第 2 件  哲学总账（规则 → 强制点 → 证据 三元组，机器可校验，唯一事实源）
            ↓
第 3 件  生成物自动化（消灭 834 个手工同步点 → 拆掉返工的地基）
            ↓
第 4 件  门禁自证 + 破坏试验常态化（让总账自己会红）
```

**为什么是这个顺序**：第 1 件不做，第 2 件就是给乱空间建索引；第 2 件不做，第 3、4 件没有依据（不知道哪些生成物/门禁是"必须的"）。

## 三、第 1 件：哲学去重 + 冲突消解 + 废止声明

### 3.1 「废止声明」是什么意思（华哥说不理解，这里说清）

**废止声明 = 一句话写明「这条已被哪条取代、从什么时候起不再执行」**。

现状问题：`项目说明.md` 里 1.5 和 1.7 直接对立，但**没有一句话说 1.5 作废了**。后来人（或 Agent）读到 1.5，会照它建归档库 —— 而 1.7 说"不做归档"。**两条都写着，谁也不知道听谁的。**

废止声明的三种写法（推荐第 3 种）：
```
写法 A（删掉旧的）：  直接把 1.5 删除 → 但会丢失历史，且历史文档引用 1.5 会悬空
写法 B（标注作废）：  在 1.5 上方加一行「> ⚠️ 本条已被 1.7 取代（2026-09-14），不再执行」
写法 C（推荐）：     B + 保留原文但加删除线 + 在条款末尾写「废止于 1.7」
```
**为什么推荐 C**：满足你"哲学空间干净"的诉求（读到就知道作废），同时**历史可追溯**（知道当初为什么这么定、后来为什么改）。这正是"不要留流水账"与"不要丢历史"的平衡点。

### 3.2 执行内容

| 步骤 | 做什么 | 产出 |
|---|---|---|
| 1 | **全量条款抽取**：把 12 条 / 49 条款 + 散落在决策记录里的裁决，抽成结构化清单 | `哲学条款清单.json`（条款编号 / 原文 / 来源 / 日期 / 状态） |
| 2 | **去重扫描**：找"同一条规则写了两遍"（如 1.2 不保留旧腿 / 1.3 结果唯一即收口 / 8.2 能力唯一权威 三者高度重叠） | 去重合并建议表 |
| 3 | **冲突扫描**：找"两条规则互斥"（已知 1.5 vs 1.7；另需机械扫其余 49 条款） | 冲突清单 + 每个冲突的**待裁选项** |
| 4 | **裁决**：能按哲学判的我判（写明依据），涉及你原始意图的列给你（预期 3–5 条） | 裁决记录 |
| 5 | **重写哲学正文**：合并去重后的条款，**每条带废止声明位**（无废止就显式写"现行"） | 新的 `项目说明.md` 哲学章 |
| 6 | **旧编号对照表更新**：现有旧→新表（37 条已并成 12 条）需再加一层"本轮合并"映射 | 对照表 |

### 3.3 我需要你定的（第 1 件内）

- **哲学空间上限**：现在 12 条 49 项。**要不要设硬上限**（如「主条 ≤ 12、每条子项 ≤ 6」）？设了之后新增条款必须先合并旧条款 —— 这是防膨胀最有效的机制。
- **决策记录的去向**：27 份、一天新增 15 份。要不要**规定"决策记录只能是短篇"**（如 ≤ 50 行：背景 5 行 / 裁决 3 行 / 被否决做法 3 行 / 影响面 3 行）？长分析一律进方案目录。

## 四、第 2 件：哲学总账（唯一事实源，机器可校验）

### 4.1 形态（吸收报告2 的建议 + 我们自己的口径）

一份 **`开发文档/哲学总账.md`**（人读）+ 一份 **`开发文档/哲学总账.json`**（机器读，md 由它生成）：
```
规则id | 承诺（一句话） | 哲学依据 | 判据实现（文件:函数） | 强制点（哪个门禁/哪一项）
       | 证据等级 | 失败策略（阻断/告警） | 反向试验（故意弄坏→必须报红） | 状态
```

### 4.2 关键：总账自己也要被门禁检查（这是"不挤牙膏"的机关）

发布门禁新增一项「**总账自证**」，逐条检查：
```
① 每条现行哲学都必须有判据实现，或**显式标注「人工治理」**（不许留空）
② 声称机器可验证的条款，必须有强制点
③ 强制点函数必须真实存在、且被正式入口调用（防"写了没接"）
④ 每个阻断项必须有 ≥1 个反向破坏用例（防"判据假绿"）
⑤ 检查器结果必须绑定当前候选制品摘要（防"证据不知对应哪个版本"）
⑥ 门禁状态四态：干净通过 / 债务冻结 / 未核验 / 失败 —— PASS_NO_REGRESSION 不得冒充 PASS_CLEAN
```
**⑥ 直接解决报告指出的「门禁通过存在歧义」**：现在一个"通过"同时表示"零违规"和"没比基线更差"，
拆成四态后，数字上就骗不了人。

### 4.3 我需要你定的

- **存量债务怎么办**：公开调用 23 项 + 测试伪装 269 项，现在靠"未新增"放行。
  **要不要给存量设收敛期限**（如：每条存量必须登记"计划何时清"；逾期未清则门禁转红）？
  不设期限的话，271 项会永远停在 271（这正是审计报告批评的点）。
- **总账 vs 项目说明.md 的分工**：我建议 **总账=机读的唯一事实源，项目说明.md 的哲学章=人读版**（由总账生成，不手写），避免两套并存。你认不认这个分工？

## 五、第 3 件：生成物自动化（**投入产出比最高**）

### 5.1 现状与目标

```
现状：改 1 文件 → 手工同步 6 份生成物（139 包 ≈ 834 个同步点）→ 漂移 85 次/历史
目标：生成物"要么自动生成、要么被门禁强制校验"，人工**物理上无法**产出漂移
```

### 5.2 三条可选路线（我推荐 A+C）

| 路线 | 做法 | 优点 | 代价 |
|---|---|---|---|
| **A（推荐）** | **提交时自动生成**：加一个 git pre-commit 钩子（或提交前唯一入口），自动跑生成器 + 摘要重算，生成物与源同一次提交 | 人不用记；物理上不可能漂移 | 需处理"生成器本身有 bug"的连锁 |
| **B** | **生成物不入库**：只在编译/构建时生成，仓库里不存 `包声明.json` 等派生物 | 最干净（少 834 个文件） | 与现有"制品=完整源码副本"设计冲突，改动面极大 |
| **C（推荐，与 A 并行）** | **校验拦在门口**：门禁加一项「生成物必须等于按当前源重算的结果」，不等就红，并打印重算命令 | 不改现有流程，立刻止住漂移 | 仍需人跑，但**不会再漏**（漏了就红） |

**推荐 A+C 组合**：A 让人不用记，C 兜底防"绕过钩子"。

### 5.3 生成物清单（先盘清再动手）

需先产出「**生成物地图**」：每份生成物 ← 哪个生成器 ← 依据哪些源文件 ← 谁在校验它。
现有的已知生成器：`能力定义编译器`、`说明书生成器`、`完整性摘要生成器`、`聚合契约解析`、
`重建依赖锁`、`全量重算摘要`。**需核实是否还有手工维护的"伪生成物"**（该自动却手写的）。

## 九、这件事做成之后的判据（怎么算"做好了"）

```
□ 同一规则在仓里只有一处成文（去重完成）
□ 哲学正文零冲突条款（每条要么现行、要么带废止声明）
□ 总账里每条规则都能指出「谁在强制它」，指不出的显式标「人工治理」
□ 门禁自证通过：不存在"有判据没强制点"的规则（或有显式豁免 + 到期日）
□ 生成物漂移归零：门禁拦截，且提交时自动生成
□ 每个阻断项都有破坏用例，且破坏用例真的能让门禁变红
□ 门禁"通过"能区分"干净通过"与"债务冻结"
□ 新增一条规则的成本：改总账一行 + 接门禁一项 + 加破坏用例一个（可预期、不膨胀）
```

**最后这条是"不挤牙膏"的判据** —— 当新增规则变成三件确定的小事，而不是"写一堆文档、靠审计来查漏"，
这个项目就从"每次审计都在补"转成"规则进来即闭环"。
