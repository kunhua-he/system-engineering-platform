### 冲突组 B：确定性 vs 相对安全（**同一条内两条并列**）

| 条款 | 原文要点 |
|---|---|
| **9.4** | 同样的输入 → 同样的输出；能力行为可预期，不因环境/调用方不同而改变 |
| **9.5** | 相对安全，不做绝对安全（安全不是绝对的） |

**为什么是问题**：9.4 写成了**无条件规则**，但平台正式能力里有随机数 / 取当前时间 / 网络请求 /
浏览器导航 / 大模型生成对话 —— 这些**天然不满足** 9.4。

**修法（报告2 建议）**：把"确定性"从绝对规则改成**能力类别**：

| 类别 | 要求 |
|---|---|
| 纯确定性 | 相同显式输入必须相同输出（可写值断言） |
| 可重放 | 返回中记录随机种子 / 时钟 / 模型或提供者版本 / 上游摘要（可复算） |
| 外部观测 | 只保证契约、错误语义与证据，**不保证值重复**（网络 / 浏览器） |
| 有副作用 | 额外声明幂等键、重放语义、状态版本 |

**额外收益（重要）**：本批实测「742 个正向步骤里 264 步只验形状（35.6%）」——
分类之后能精确分派：外部观测类**本来就验不了值**（合理），其余该补关键值断言（真欠账）。

**待裁**：采纳四分类？能力定义里是否要新增"确定性类别"字段（**会动契约，需你批**）？

## 五、废止声明的写法（华哥问「是什么意思」，这里给样例）

**废止声明 = 一句话写明「这条被哪条取代、从何时起不再执行」**。

现状问题：1.5 和 1.7 都在，**没有一句话说 1.5 作废** → 后来人读到 1.5 会去建归档库。

**推荐写法（C 型：标作废 + 保留原文 + 写废止于哪条）**：

```markdown
1.5 ~~**制品只留最新单版，旧版进归档**~~：原意是「制品库只维护最新版封装，老制品移入归档库」。
> ⚠️ **本节已于 2026-09-17 被 1.7 + 5.3 取代**：本地不建归档库（1.7），
> 但**被引用的旧版本必须保留**（5.3②）。现行口径 = 「当前激活 1 份 + 保留仍被引用/回滚窗口内的不可变版本 +
> 过期无引用即删」。本节仅作历史留档，**不再执行**。
```

**为什么推荐 C**：
- 满足"哲学空间干净"（读到就知道作废，不会照它做）
- 同时**历史可追溯**（知道当初为什么这么定、后来为什么改）
- 与你的"不要流水账"不冲突：**废止声明是一行结论，不是过程记录**
