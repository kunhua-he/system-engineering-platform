# 一、★★★ cosmic-ray：**样本是规则的"接口义务"，元测试自动遍历**（本卡点最核心的机制）

## 1.1 变异算子的接口里强制自带样本

`src/cosmic_ray/operators/number_replacer.py` 原文：
```python
OFFSETS = [+1, -1]                              # 数值变异：+1 / -1 两个方向

class NumberReplacer(Operator):
    @classmethod
    def examples(cls):                          # ★ 不写 examples() = 实现不完整
        return (
            Example("x = 1", "x = 2"),          # 变异前 → 变异后
            Example("x = 1", "x = 0", occurrence=1),
            Example("x = 4.2", "x = 5.2"),
            Example("x = 1j", "x = (1+1j)"),
        )
```

## 1.2 元测试自动遍历「所有已注册算子 × 其全部样本」

`tests/unittests/operators/test_operator_samples.py` 原文：
```python
OPERATOR_PROVIDED_SAMPLES = tuple(
    Sample(operator_class, example)
    for operator_class in map(get_operator, operator_names())   # ★ 遍历**所有已注册算子**
    for example in operator_class.examples()                     # ★ 取它自带的样本
)

def test_mutation_changes_ast(sample):                # ★ 正例：变异必须真的生效
    assert mutant.get_code() == sample.example.post_mutation_code

def test_no_mutation_leaves_ast_unchanged(sample):    # ★ 反例：不应用变异时不得改动
    assert mutant.get_code() == sample.example.pre_mutation_code
```

**为什么这比"手工维护一张破坏矩阵表"强得多**：
```
① 样本是**接口义务** —— 不是"另找一个地方补一张表"
② 元测试**自动发现新算子**（遍历 operator_names()）—— 新增算子时测试自动覆盖它，
   **忘了带样本 ⇒ 元测试直接失败**。这才是"不挤牙膏"的机制内核
③ **正例 + 反例配对** —— 既证"该拦时能拦住"，又证"不该动时不动"（防误报）
```

# 二、★★★ stryker：**变异得分三档阈值**（顺带解决卡点 C）

`packages/api/schema/stryker-core.json` 原文：
```json
"mutationScoreThresholds": {
  "properties": {
    "high":  { "default": 80 },
    "low":   { "default": 60 },
    "break": { "oneOf": [{"type":"null"},{"percentage"}], "default": null }
  }
}
```
语义：
```
score ≥ high(80%)  → 绿（干净）
score ≥ low(60%)   → 黄（警告：质量下滑但可接受）
score < break      → 红（阻断）
★ 关键：**break 默认 null = 不阻断** —— "默认只报告，想阻断就显式配一个数字"
```
**⇒ 对卡点 C 的价值**：本项目「通过」一词同时表示"零违规"与"未比基线更差"，
stryker 的形态给出更好的表达：用**连续量 + 三档**，且"是否阻断"是**显式配置**。

# 三、★★★ LitmusChaos：**探针（Probes）= 验证"故障真的生效了"**（本卡点另一个关键视角）

## 3.1 四种探针类型（`子代理草稿_20260917/chaos/lc-probes.md` 原文）

```
- httpProbe : To query health/downstream URIs          （查健康/下游 URI）
- cmdProbe  : To execute any user-desired health-check function implemented as a shell command
- k8sProbe  : To perform CRUD operations against native & custom Kubernetes resources
- promProbe : To execute promql queries and match prometheus metrics for specific criteria
★ 其中 **httpProbe 与 k8sProbe 是完全声明式的**；cmdProbe 需用户给 shell 命令；
  promProbe 需 promql 查询 —— **声明式优先，命令式兜底**
```

## 3.2 ★★★ 五种探针模式（**这是"正例+反例"的完整形态**）

```
- SoT        : Executed at the **Start of Test** as a **pre-chaos check**   ← 前置：确认"本来是好的"
- EoT        : Executed at the **End of Test** as a **post-chaos check**    ← 后置：确认"确实坏了"
- Edge       : Executed both, before and after the chaos                    ← 前后都做
- Continuous : 在故障注入期间持续执行（带 polling interval）
- OnChaos    : 仅在故障持续期内持续执行
```

**★★★ 对本项目的直接价值（这条我原先没想到）**：
```
本项目要"故意弄坏 → 必须报红"。但**只验证"报红"是不够的**，还要验证：
  ① 弄坏之前，门禁**本来是绿的**（否则"红"可能因为环境本来就坏 → 假红）
  ② 弄坏之后，门禁**确实变红**（否则"绿"是空转 → 假绿）
  ③ 恢复之后，门禁**回到绿**（否则门禁有粘滞 → 不可用）
Litmus 的 SoT/EoT/Edge 就是这个三段式的现成范式：
  SoT   → 断言"当前是绿的"（前置探针）
  EoT   → 断言"破坏后是红的"（后置探针）
  恢复  → 断言"恢复后回到绿"（本项目应补的第三段）
```

## 3.3 探针的公共属性（可直接抄成"破坏样本"的字段）

```
probeTimeout           : 探针执行的时限
retry                  : 首次失败后重跑几次才判失败   ← 防抖动误判
interval               : 重试间隔
probePollingInterval   : 连续模式的轮询间隔
initialDelay           : 初始等待
★ stopOnFailure        : true/false —— **探针失败后是否停止故障执行**
                        ⇒ 就是本项目"是否阻断"的显式开关
```
**⇒ 可落地**：本项目破坏样本的字段可照此设计：
`{ 样本id, 目标检查项, 破坏手法, 期望结果, 前置断言, 恢复断言, 超时, 重试, 失败后是否中断 }`。

# 五、卡点 D 的完整处方（外部一致）

```
问题：门禁多，但缺"故意弄坏 → 必须报红"的证明体系
处方（外部一致，且是**自动化**而非手工矩阵）：
  ① ★ 把"样本"写成规则/算子的**接口义务**（cosmic-ray 的 examples()）
  ② ★ 元测试**自动遍历全部规则 × 全部样本** → 新增规则忘带样本 = 自动失败
  ③ ★ 正例 + 反例配对；并照 Litmus 的 SoT/EoT 补**前置断言与恢复断言**
     （前置：本来是绿的；后置：破坏后是红的；恢复：回到绿）
  ④ ★ 用变异得分（连续量）+ 三档阈值表达质量水位（stryker high/low/break）
  ⑤ ★ "是否阻断"/"失败是否中断"是**显式配置**（stryker break 默认 null；
     Litmus stopOnFailure）
```

> **与第六份材料的分歧（如实标注）**：该材料主张「故障注入测试 → 未来再说」，
> 理由是"单用户场景下华哥自己跑一遍就知道对不对"。
> 本轮研究认为这**不是同一个问题**：破坏样本的意义不是"测给谁看"，
> 而是"**证明门禁拦不拦得住**"。实证：本项目发布门禁报"通过"，
> 而测试体系门禁实际是红的 —— 那不是"没人看"，是"没人强制 + 没证明拦得住"。
> **建议：'给单用户看的测试'可以省；'给门禁自己证明有效的破坏样本'不能省。**
