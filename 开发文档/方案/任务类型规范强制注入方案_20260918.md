## 〇、一页结论

```text
要解决什么：「同一个开发规范，靠主代理记性记得注入」→ 漏注入就必然重踩。
  实测证据（2026-09-18 夜间）：主会话连派 6 路（20:19–20:46）全部没建任务记忆包，
  挂在记忆包上的「通用开工纪律」一次都没到达子代理
  → 该批 terminal 读文件 418 次（上批 252）、全仓 grep 117 次（上批 75）。

为什么放底座（不是 Hermes）：底座是给所有 Agent 用的，Hermes 只是接入方之一。
  规范注入做成底座能力后，任何接入方（Hermes / Claude Code / Codex / 未来自研）
  调同一个入口即得同一份规范，不依赖某一家客户端的记性。

落点（复用，不新建第二条腿）：`模块库/开工编排.开工准备` —— 它已是「开发统一开工入口」，
  一次返回开工上下文（项目根边界校验 / Git 指纹 / 证据账本 / 代码地图可用性）。
  把「本次任务属于哪类 + 该类规范」并进它的返回，接入方开工即得，无需额外调用。

为什么省 token：规范按「任务类型」切片，只返回命中的那一类（实测单类 300–600 字符），
  不返回全量哲学（126KB 项目说明与 1065 行哲学均不载入）。
```

## 一、缺口是什么（现场取证）

### 1.1 现状：规范靠「主代理记性」，漏了就重踩

| 事实 | 取证 |
|---|---|
| 通用开工纪律挂在任务记忆包上（读时才附） | `开发工具/任务记忆/任务记忆.py:82-95`：`读()` 返回 `通用开工纪律 + 记忆正文` |
| 本批 6 路**全部没建记忆包** | `find 工程缓存 -path '*任务记忆*' -newermt '2026-09-18 20:00' -type f` → **0 份**（19 点那批有 32 份） |
| 结果：姿势型黑洞全面反弹 | 巡检 21:00 实测：terminal 读文件 **418**（19:30 为 252）、全仓 grep **117**（75）、一次性 python **104**（72） |

⇒ 结论：**规范注入不该依赖主代理记性**。必须由「执行任务的那个入口」强制带回。

### 1.2 底座已有地基（不新造）

| 已有件 | 现场 | 能复用什么 |
|---|---|---|
| `模块库/开工编排.开工准备` | `模块库/开工编排/实现/开工编排.py:192` | **开发统一开工入口**，一次返回开工上下文 —— 这就是注入点 |
| `项目文档支持库.查开工上下文` | 实测返回 1923 字符 / 5 条坑 | 已有「按任务检索历史坑」，含 `场景id`（= 任务类型维度） |
| `开发文档/规范/踩坑条目.json` | **23 条 / 14 个场景id** | `场景id` 天然就是任务类型分类 |
| `AGENTS.md` 子代理继承协议 | 条目 1–9 | 已有任务信必带条款，但**靠人写进提示词** |

⇒ 缺的不是机制，是**把「任务类型 → 该类规范」固化进开工入口**。

## 二、设计（三个原子件，全部在底座内）

### 2.1 任务类型字典（数据文件，不是代码）

`开发文档/规范/任务类型规范.json` —— 一类一条，五键齐全（与踩坑条目同体例）：

| 键 | 说明 |
|---|---|
| `任务类型` | 稳定标识（如 `改能力契约` / `加新能力` / `写验证场景` / `修缺陷` / `改文档` / `派活`） |
| `识别词` | 用于把「本次任务」文本映射到本类（双字滑窗同 `查开工上下文` 口径，**不调大模型**） |
| `强规范` | 该类**必须照做**的条目（短句、可执行，不写「注意一下」） |
| `判据` | 每条强规范配套的可执行命令或真源位置（与踩坑条目同一口径） |
| `原文位置` | 需要细节时的跳转点（省 token：平时不读） |

**为什么放数据文件**：规范改一句只改数据，不改代码；与既有 `方案文档生命周期判据.json` / `踩坑条目.json` 同模式（本项目已有此惯例）。

### 2.2 取规范：把「任务类型 → 强规范」并进 `开工准备` 的返回

`开工准备` 新增一个**只读子步骤**（在现有 ⑥ 组装之后）：

```
输入：任务（已必填）→ 用 识别词 匹配任务类型
输出：开工上下文 里新增两键
  「任务类型」：命中的类型（可能多条，按相关度降序）
  「强规范」  ：命中的该类强规范条目（含判据 + 原文位置）
```

**硬约束（防退化成「全量载入」）**：
- 只返回**命中的类型**，一类最多 `返回条数`（默认 3）条，超限按相关度截断并如实标 `是否截断`；
- 未命中任何类型时**明确返回空 + 提示去补字典**（不静默返回空数组冒充「无规范」）；
- 不改 `开工准备` 现有返回键的语义（**只增不改**，老的 `开工上下文` 字段逐字兼容）。

### 2.3 缺类时能自己长：扩词闭环

复用 `项目文档支持库` 已有的「未命中词」模式（`登记未命中词` / `列出未命中词`）：
`开工准备` 匹配不到类型时，接入方可调 `记踩坑` 或补字典；字典项 `识别词` 可增补。
**不在检索失败时偷偷写库**（`开工准备` 保持只读语义）。

## 三、接入方怎么用（以 Hermes 为例，底座不关心是谁）

| 步骤 | 动作 |
|---|---|
| 1 | 主代理派活前调 `开工编排.开工准备(项目根=…, 任务="<这次要做什么>", 修改路径=[…])` |
| 2 | 把返回里的 `任务类型` + `强规范`（通常 300–600 字符）**原样贴进子代理的 context** |
| 3 | 子代理完工回报；主代理按 `判据` 字段核真（不采信自述） |

**省 token 的关键**：贴进去的是「命中的那一类」而不是全量规范；细节走 `原文位置` 按需跳转。
