## 一、要解决什么（华哥原话口径）

> 「针对不同项目，可以快速的查询这个项目的文档。这个支持库不是查询 txt/word/pdf 的那种，而是纯粹的针对于项目开发维护的……现在的文档并没有规范，我希望是把规范做好，然后后续找文档，不会让 agent 自己去乱飞……包含目录树等这些东西给他架构好，然后包含写文档的规范……agent 传参过去，就是需要按照规范去写，符合规范的就落盘，不符合规范的就单独返回不合规范的方式……文档在本地保存一份 md，然后要入库这个小 db 里面，这样子搜索速度比较快，后台单独拉一个线程去处理入库……一个是写文档，一个是搜索项目文档的能力……这里需要加上一个项目登记的功能，这个是后台处理的。」

拆成四件事：

| # | 能力 | 一句话 |
|---|---|---|
| 1 | **项目登记** | 登记一个项目：项目名、根目录、文档根、文档规范引用。后台处理，登记后同一项目反复可用 |
| 2 | **写文档** | 传参 → 按规范校验 → 合规才落盘成 md + 入库；不合规**不落盘**，单独返回违规范清单 |
| 3 | **查文档** | 按项目 + 关键词快查，返回可回溯的「文件路径 + 行号 + 片段」 |
| 4 | **查记忆** | 按项目 + 关键词查该项目历史记忆（复用既有记忆支持库，不重造） |

## 三、新增落点（唯一新增，不重复造）

### 3.1 支持库：`支持库/后端/项目文档支持库`（原子）

| 能力 id | 作用 | 为什么是原子 |
|---|---|---|
| `项目文档支持库.切块` | 把文档正文按 Markdown 结构切成块（标题/段落/代码/表格），附行号区间 | 纯计算，无状态，可被任何调用方复用 |
| `项目文档支持库.校验规范` | 按**规范文件**逐条校验文档正文，返回违规范条目清单（含条目号、说明、定位行） | 规范判据集中一处，改规范只改数据不改代码 |
| `项目文档支持库.建索引库` | 初始化索引库表结构与索引（幂等） | 建表是原子动作 |
| `项目文档支持库.写入索引` | 写入/更新一个项目的文档索引记录（文档级 + 块级） | 写是原子动作，不等同业务语义 |
| `项目文档支持库.查询索引` | 按项目 + 关键词查询索引，返回文件路径/行号/片段 | 读是原子动作 |

### 3.2 模块：`模块库/项目文档`（组合）

| 能力 id | 编排 |
|---|---|
| `项目文档.登记项目` | 校验项目根存在 → 规范文件存在 → 写项目登记表（幂等：同项目名覆盖更新） |
| `项目文档.写文档` | **校验规范 → 不合规直接失败并返回违规范清单（不落盘）** → 合规则原子写入 md → 后台入库 |
| `项目文档.查文档` | 按项目 + 关键词查索引 → 回带文件路径与行号；索引空时回退到真实搜索（不返回假空） |
| `项目文档.查记忆` | 委托 `记忆支持库.搜索记忆`（带项目过滤），不重造记忆 |

### 3.3 数据库（运行态一律入库，哲学定盘 2026-09-15）

库文件位置：`<运行数据根>/项目文档库.db`（经 `公共契约/运行时/运行缓存.py` 的 `解析运行数据根`，**禁止裸拼 `工程缓存`**）。

```sql
-- 项目登记表
CREATE TABLE IF NOT EXISTS 项目登记(
  项目名 TEXT PRIMARY KEY,
  项目根目录 TEXT NOT NULL,
  文档根相对路径 TEXT NOT NULL,
  规范文件 TEXT NOT NULL,
  登记时间 TEXT NOT NULL,
  更新时间 REAL NOT NULL);

-- 文档索引表（文档级）
CREATE TABLE IF NOT EXISTS 文档索引(
  项目名 TEXT NOT NULL,
  文档相对路径 TEXT NOT NULL,
  标题 TEXT NOT NULL,
  文档类型 TEXT NOT NULL,
  内容摘要 TEXT NOT NULL,
  段数 INTEGER NOT NULL,
  字节数 INTEGER NOT NULL,
  文件修改时间 REAL NOT NULL,
  入库时间 REAL NOT NULL,
  PRIMARY KEY(项目名, 文档相对路径));

-- 块索引表（检索粒度）
CREATE TABLE IF NOT EXISTS 块索引(
  块id INTEGER PRIMARY KEY AUTOINCREMENT,
  项目名 TEXT NOT NULL,
  文档相对路径 TEXT NOT NULL,
  起始行 INTEGER NOT NULL,
  结束行 INTEGER NOT NULL,
  块类型 TEXT NOT NULL,
  块文本 TEXT NOT NULL);
```

索引：`文档索引(项目名, 入库时间 DESC)`、`块索引(项目名, 文档相对路径)`。

**检索口径**：与记忆支持库 `仅关键词` 同哲学——**默认纯 SQLite + 字符串匹配，不调用大模型与向量**。结构化查文档不该付一次 LLM 调用的代价；将来要语义检索再按需加向量列，不预先造。

## 四、规范校验怎么落地（不动运行时性能）

华哥要的是「符合规范的就落盘，不符合的单独返回不合规范的方式」。**规范判据必须数据化**，不能把规则硬编进代码：

**规范文件**：`开发文档/规范/Markdown 文档体例规范.md`（已存在，本方案的实施对象之一）。
**机器判据**：同目录 `Markdown 文档体例判据.json`（本方案新增），把该规范的**可机器判定项**抽成数据：

| 判据 id | 判据 | 严重级 |
|---|---|---|
| `单H1` | 真 H1 数 = 1（跳过代码块） | 阻断 |
| `围栏配对` | 行首围栏数为偶数 | 阻断 |
| `元信息头` | 前三行含「最后更新 / 口径 / 维护者」 | 阻断（权威文档与包级说明） |
| `链接文字一致` | `[X](Y)` 的文字 X = Y 的文件名 | 建议 |
| `链接可达` | 相对链接目标文件存在 | 建议 |
| `禁裸编号` | 非清单场景不得出现裸编号 | 建议 |

**为什么不把判据写在 Python 里**：规范改一句就要改代码、重编译、重测。写成 JSON 后，改规范＝改数据，`校验规范` 读数据执行，判据与规范同源、不会漂移。这是哲学 5.1（契约唯一）+ 4.4（不新开事实源）的落地。

## 五、后台入库（华哥明确要求）

**做法**：`写文档` 分两段——
1. **落盘（同步，必须成功）**：文件写入成功即返回成功，**不因为入库失败而回滚文件**。
2. **入库（后台线程，失败可重跑）**：起一个后台线程做切块 + 写索引；线程内异常**只记录不抛给调用方**，并登记索引待补清单。

**为什么允许入库滞后**：落盘是用户可见结果，入库是可重跑的派生数据。把两者绑成事务会让人等一个不必要的 IO，且入库失败时用户已拿到文件却被判失败。**口径：文件是权威，索引是派生**——索引丢了可从文件重建（提供 `项目文档.重建索引` 作为兜底，本批不强制做）。

**有界要求**（哲学：所有线程必须有界）：后台线程**非守护、单次执行、有超时上限**（默认 30 秒），完成即退出；不做常驻线程池，不用队列跨调用存活。

## 六、验收口径（真实 HTTP，不跑全量 unittest）

| # | 验收项 | 怎么验 |
|---|---|---|
| 1 | 项目登记幂等 | 连续登记两次同项目，第二次返回「已存在并更新」；查询可见 |
| 2 | **不合规写入必须被拒** | 传一份没有 H1 的正文 → 返回失败 + 违规范清单；**现场确认文件未落盘** |

## 九、明确不做（防后患）

| 不做 | 理由 |
|---|---|
| 在薄壳里加 `document_read` / `memory_query` 门面工具 | 违反薄壳零业务语义定位（AGENTS.md 明文），会让薄壳跟着能力改名漂移 |

| 用向量/大模型做默认检索 | 结构化关键词查询不该付 LLM 代价；要语义检索再按需加 |

| 让入库失败回滚已落盘文件 | 文件是权威、索引是派生；派生失败不该毁掉用户可见结果 |

## 十一、补充：清单条目管理（2026-09-18 华哥提出）

> 华哥原话：「你这个就不能封装个原子能力去处理吗？**貌似本来就需要的吧**？」
> 触发场景：维护者在**手工 patch** `开发文档/未完成事项.md`（唯一债务清单）——增删改条目、调顺序、
> 守编号不复用——**当场就把第 53 项插错了位置**。手工 patch 结构化清单正是「该用能力」的场景。

### 11.1 复用决策（现场实测，2026-09-18）

| 搜索词 | 现状 |
|---|---|
| 清单 / 条目 / 插入行 / 追加行 | **无**「清单条目增删改/排序」能力 |
| Markdown | 只有 `办公文档支持库.轻量文本解析.解析Markdown块` 与 `项目文档支持库.切块`（切块产出的是「块」，不含表格行的结构化） |
| 表格 | 全是 PDF/xlsx 域（`PDF文本表格.提取表格`、`办公文档支持库.表格公式.*`），**不处理 markdown 表格** |
| 去重 | 只有 `数据操作支持库.数据集合.列表去重`（对列表，不对清单文本） |

**结论**：缺能力，且属既有域内补齐（不新建包）——落 `项目文档支持库`（它已管文档切块/规范校验/索引/项目登记）。

### 11.2 新增原子能力（3 个，纯计算无状态）

| 能力 id | 参数 | 返回 | 说明 |
|---|---|---|---|
| `项目文档支持库.解析清单` | `正文` | `表头`、`条目列表`（每项含 `行号`/`列值`/`原始行`）、`条目数` | 把 markdown 表格清单解析成结构化条目；分隔行与表头识别，非表格文本如实报告 |
| `项目文档支持库.改清单条目` | `正文`、`操作`（增/删/改）、`定位`、`条目`、`插入位置` | `新正文`、`变更说明`、`条目数` | 增/删/改一条；`插入位置` 支持「尾部」或「某编号之后」；**编号不复用**：新增必须由调用方给编号，能力不自动生成（防与「缺号即从未存在过」的规则打架） |
| `项目文档支持库.校验清单` | `正文`、`必填列`、`编号列` | `通过`、`问题列表` | 编号唯一性、编号格式、必填列非空、表格结构完整 |

### 11.3 明确不做

| 不做 | 理由 |
|---|---|
| 自动排序 | 清单的业务顺序是**人工判断**（优先级/分组语义），机器排序会把「按处置方式分类」的编排打乱；且排序本身是一行 `sorted`，不值得做成能力 |
| 自动生成编号 | 与「编号四位递增且不复用、缺号即从未存在过」的既有规则打架（体例规范第七节）；编号必须由维护者给 |
| 新建 `清单支持库` | 属既有域（项目文档），新建包＝不必要的能力面扩张（7.7 只在「能力面上不存在」时才补，这里是域内补） |
| 让它保有一份清单副本 | 清单正文是文件事实，能力只做纯文本变换，**不留状态**（哲学 1.1） |
