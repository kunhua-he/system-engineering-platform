## 二、核心机制拆解

### 2.1 ★★★ GitHub Rulesets：平台层面就区分 `Evaluate` 与 `Active`

**原文**（GitHub 官方文档，抓取自 GitHub Docs）：
> "**For rulesets in evaluate mode, a status check will run on the targeted branch but will not be
> required to pass.**"
>
> "### Using \"Evaluate\" mode for ruleset workflows
> If a ruleset workflow runs in \"Evaluate\" mode and passes, you can set the ruleset workflow to
> \"Active\" mode and merge your pull request without triggering a new workflow run.
> If you open a pull request before you create the ruleset in \"Evaluate\" mode, you can still merge
> the pull request since **the ruleset is not enforced**."

**⇒ 机制解读**：
```
平台厂商（GitHub）把「检查跑了但不拦」做成了一个**一等公民的状态**（Evaluate），
与「检查跑了且拦」（Active）**明确区分**，并且在文档里说清 Evalueate 的后果
（"仍可合并，因为规则集不被强制执行"）。

这正是本项目卡点 C 需要的语义：**"跑了但没拦"必须是一个显式状态**，而不是
"未比基线更差 → 判通过"这种**把两个意思塞进一个词**的做法。
```

**另一条关键信息（required workflows 的注意事项）**：
> "If you create a rule while a pull request is open, the required workflow will not run automatically.
> To trigger the required workflow, push a new commit…"
> "**Ruleset workflows do not run on events triggered by the `GITHUB_TOKEN`.**"
> "Status checks are not indexed for rulesets defined above the repository level.
> **You must manually enter the exact check name expected.**"

**⇒ 对本项目的启示（三条都是"强制点的边界条件"）**：
```
① 强制点有「生效时机」问题：规则在 PR 打开后创建 → 那次 PR 不会被拦。
   ⇒ 本项目的门禁也要写清"哪些变更落在门禁的生效范围内"（否则会有漏网窗口）。
② 强制点有「触发源」问题：用平台自身 token 触发的事件不跑强制工作流。
   ⇒ 本项目要确认"门禁是否会被所有类型的提交触发"（含脚本/自动化提交）。
③ 强制点有「名字必须精确」问题：跨层定义的检查必须手工填精确的检查名。
   名字写错 = 静默不生效（最危险的一类失效）。
   ⇒ 本项目的门禁项名字应机器生成/校验，避免"改名后强制点静默失效"。
```

### 2.2 ★★★ Palantir policy-bot：**策略即代码 + 模拟接口 + 默认宽松**

**它的定位原文**：
> "`policy-bot` is a GitHub App for **enforcing approval policies** on pull requests.
> It does this by **creating a status check, which can be configured as a required status check**."
> "Behavior is **configured by a file in each repository**."（策略即数据，随仓库走）

**它的能力原文**：
```
- Require reviews from specific users, organizations, or teams
- Apply rules based on the files, authors, or branches involved in a pull request
- Combine multiple approval rules with `and` and `or` conditions
- Automatically approve pull requests that meet specific conditions
```

**★ 规则的「四要素」（原文，这是本项目"总账"字段的直接参照）**：
```
Each rule has four components:
1. **Name**. … Try to pick names that make sense to humans and **explain the purpose of the rule**.
   A good name can complete the sentence "This pull request is approved if …"
2. **Predicates**. A rule is only active when all of its predicates are true.
   If any predicate is false, **the rule is skipped and does not influence the policy**.
   （谓词：规则"何时生效"—— 支持"只有重要文件变更时才要求特定团队审批"）
3. **Options**. Options control the behavior of the rule.（是否请求评审、推翻旧批准等）
4. （Requirements/审批要求 —— 文档该段被截断，但语义明确）
```

**★★★ 它的「Simulation API」（这是卡点 D 的服务端形态）原文**：
> "It can be useful to **simulate how Policy Bot would evaluate a pull request if certain conditions
> were changed.** For example: adding a review from a specific user or group, or adjusting the base branch.
> An API endpoint exists at `api/simulate/:org/:repo/:prNumber` …
> **Simulations using this endpoint will NOT write the result back to the pull request status check
> and will instead return the result.**"

示例请求体：
```json
{ "ignore_comments": {"users": ["ignored-user"], "teams": [...], "organizations": [...], "permissions": ["admin"]} }
```

**⇒ 对本项目的直接价值（两条）**：
```
① ★★★ 「模拟接口」正是本项目"破坏试验"该有的形态：
   给一个**构造出来的变更**，问"策略会怎么判"，**不写回真实状态**。
   ⇒ 本项目可落地：门禁支持 `--模拟` 模式（给构造的变更样本 → 返回判定结果，
     不改工作区、不写基线、不动制品）。这样 56 个检查项的破坏样本可以安全地跑。
② ★★ 规则四要素里的 **Predicates（规则何时生效）** 是本项目缺的一维：
   本项目门禁项是"无条件全量跑"；policy-bot 支持"只在特定文件变更时才要求"。
   ⇒ 可落地：门禁项带"生效谓词"（如"仅当 支持库/** 变更时才跑契约兼容检查"），
     既省时间，也让"为什么这次没检查"有明确答案。
③ 它的 **"Disapproval is Disabled by Default"**（默认禁用否决）体现同一原则：
   **默认宽松、显式收紧** —— 但**宽松是一个显式默认值，不是"没实现"**。
```

② 它把"是否要求代码审查"当成一个可判定项 —— 对应本项目「多会话并行开发规约」里

③ 它检查"仓库里有没有二进制产物"（Binary-Artifacts）—— 与本项目"工程缓存无 Python 源码"

### 2.6 ★ pre-commit 的**局限**（反面，但同等重要）

```
实测：pre-commit 是**客户端钩子**框架；仓库内搜 `no-verify` **0 命中** → 它不防绕过。
`git commit --no-verify` 可完全跳过所有钩子。
```
**⇒ 结论**：本地钩子只能算"早发现"，**不是强制点**。强制点必须在
**服务端 / CI 必经路径**上（GitHub required status check、组织级 required workflow）。

# ★★★ 补充：tach —— **「豁免自身也要被检查」**（本项目哲学的直接机器化）

> 来源：`tach`（gauge-sh/tach，4.1MB，第二批下载）。这是本轮**最精准命中本项目哲学**的外部发现。

## 原文（`docs/usage/configuration.md` 与 `src/config/rules.rs`）

```toml
# tach.toml
[rules]
unused_ignore_directives = "error"           # ← ① 没被用到的豁免指令 = 报错
require_ignore_directive_reasons = "error"   # ← ② 豁免必须带理由   = 报错
```
文档原文（三条，**连默认值都是分级的**）：
```
- `unused_ignore_directives` (default: warn):
    catch `tach-ignore` comments which are unused
    (e.g. do not suppress any errors or warnings)
- `require_ignore_directive_reasons` (default: off):
    require every `tach-ignore` comment to have a reason
- `unused_external_dependencies` (default: error):
    catch declared 3rd party dependencies which are not imported in your code
```
源码：`src/config/rules.rs`（`RuleSetting::warn()/off()` 逐条可配）、
`src/checks/ignore_directive.rs`（真实检查实现）。

## ★★★ 三条规则逐一对照本项目

| tach 的规则 | 本项目对应哲学 | 现状差距 | 可落地改法 |
|---|---|---|---|
| **① 没被用到的豁免 = 报错**<br>`unused_ignore_directives` | **哲学 1.4「空转即杀」**（"没有结果的东西就不需要存在"） | ★★★ **正是本项目最大的缺口**：存量基线 271 项 / 23 项只管"只减不增"，**修好的存量如果不删，会永远挂在计数里**，没人发现它已经不需要了 | 门禁加一项：**存量基线里"已不再被触发"的条目，必须删除，否则报错**（"豁免本身也要被检查"） |
| **② 豁免必须带理由**<br>`require_ignore_directive_reasons` | 本轮新增候选 **P-7 例外必须自证** | 本项目的豁免（依赖豁免表 / 存量基线）**没有强制要求理由** | 与 P-7 合并：豁免数据结构加 `理由` 字段，门禁校验"无理由判违规" |
| **③ 声明了但没用的第三方依赖 = 报错**<br>`unused_external_dependencies` | 同上（哲学 1.4） | 本项目有"依赖锁/依赖契约"，但**未检查"声明了却没被 import"** | 依赖生命周期审计可加此判据（现在审计的是"有没有越层"，不是"有没有空转"） |

## ★ 另一个设计细节：**默认值也分级**

```
能机器确定对错的（空转、未使用）  → 默认 error（直接拦）
需要人判断的（豁免理由）          → 默认 off（先不拦，允许开启）
```
**⇒ 可落地**：本项目门禁项默认值的设定原则可照此 ——
"能机器判定"的默认为阻断，"需人判断"的默认可关闭但可显式开启。

## 为什么这条特别重要

```
本轮我提的 P-7（豁免带理由）与哲学 1.4（空转即杀）**原本是两条独立的原则**，
而 tach 把两者做成了**同一套豁免检查机制的两面**：
    豁免必须①有理由 ②在被触发（否则就是空转，必须删）
⇒ 这把「例外纪律」从"靠人自觉登记理由"升级成"**机器强制**"，
  直接补上本项目 271 项存量基线的最大漏洞：**修好的存量不会被自动挤出去**。
```
