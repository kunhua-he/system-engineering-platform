## 四、依赖关系与冲突点（决定并发编排）

```
裁决①（能力 id 统一）—— 独立，但**引用面最广**（约 5100 处）⇒ 与其他两条同时改会互相踩
裁决②（架构拓展）
   ├─ ⑧⑨ 接口抽象 ── 独立，无行为变更
   ├─ ①② 配置收口 + 迁移通用件 ── 独立
   ├─ ③ 请求 id 贯穿 ── ★ 会在「统一返回信封」上与裁决①的引用点重叠
   ├─ ④⑥ ── 独立
   └─ ⑤⑦ ── ⑤ 依赖能力目录（与①同为能力面）；⑦ 动契约与状态库
裁决③（故障注入样本）—— 独立（只碰 开发工具/ + 测试中心/），**全程可并行**
```

**冲突点只有两处**（必须错开或串行）：

1. **裁决①的引用点** vs **裁决②③的「统一返回信封」**（`请求id` 字段）—— 同在 `*.py` 调用点与场景 JSON；
2. **裁决①的包结构** vs **裁决②⑤的能力分类树**（都按包 id 派生）。

⇒ **编排原则：裁决③全程并行；裁决②先做不冲突的 ⑧⑨①④⑥；裁决①单独一批独占引用面；②的 ③⑤⑦ 在①之后。**

**并入的原有依赖纪律**（来自被取代的 v2.0）：

- **门禁接线必须先于表达收口与补能力** —— 门禁没接线时，收口与补能力会被后来的改动重新打散；
- **重构必须在表达收口之后** —— 表达未统一时做重构必然返工；
- **每次改动动手前先认领**（`开工编排.开工即占`）：同一份文件也能上锁，谁先拿到谁先改；没认到就有界等待重试。
