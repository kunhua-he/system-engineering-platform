## 一、华哥原话与需求拆解

> 「搜索我觉得反而是最好是更加准确为主。里面是可以配置很多玩意来加速的。例如说小的 em 模型。反正我电脑也快，常驻一个很小的向量模型（准度可以的话，毕竟本质上是代码，语义漂移范围不多，应该小的也够用）。」
> 「其次就是类似于代码地图这样子的。可以快速搜索代码，已经有的原子能力。」
> 「然后再下一个就是看代码或者是看文件目录树的这种原子能力，应该大部分都有的。」
> 「我更加期望的是，完完全全使用 mcp，agent 本质上是思考+搜索+调用；这样子最大化的防止漂移。」
> 「也可以看看别人开源的代码，怎么快速索引到的。」

| 华哥说的 | 本质需求 | 为什么重要 |
|---|---|---|
| 搜索以**准确**为主 | 召回要准，不是要快；快靠索引结构与缓存，不靠牺牲准度 | 搜索不准 → Agent 反复试词、反复读文件 = 真正的 token 黑洞 |
| 常驻**小向量模型**够用 | 代码语义漂移范围小，小嵌入模型足够 | 本机已有 BGE-M3；代码场景不需大模型 |
| 像**代码地图**那样快速搜代码/搜已有原子能力 | 两类索引：**能力索引** + **符号索引** | 开工第一件事就是「有没有现成承载」，搜不到就重造 |
| 看代码 / 看**文件目录树**的原子能力 | 目录树是一次拿多层树，不是逐层递归 | 现在只有单层 `列出目录`，看一棵树要 N 次往返 |
| **完完全全用 MCP** | Agent 只做「思考 + 搜索 + 调用」 | 一用终端/原生文件工具就**脱离契约与日志**，是漂移的最大来源 |

**华哥的核心命题**：把「搜索」从「碰运气的关键词试错」升级为「确定性的多路召回」，且**每一路都必须是 MCP 原子能力**。

## 三、开源做法调研（华哥要求「看看别人怎么快速索引到的」）

### 3.1 业界标准：aider 的 repo map（tree-sitter + PageRank）

| 阶段 | 做法 |
|---|---|
| 1 符号抽取 | tree-sitter 解析每个源文件，抽出**定义（def）与引用（ref）**标签 |
| 2 建图 | 加权有向图：节点=文件/符号，边=def/ref 关系 |
| 3 排序 | **Personalized PageRank**：把「当前正在编辑的文件」当作个性化向量，×50 权重，使其依赖链上浮 |
| 4 预算渲染 | 按排名渲染符号签名，**二分找最大可容纳集**，卡在 token 预算内 |
| 5 缓存 | 本地 SQLite 缓存标签，增量更新 |

**变体**：`repo-mapper`（Rust）加了 **focus（锚点）**——从锚点做 Random Walk with Restart，锚点及其依赖锥排最前；`goldfish`（Go）、`sourcemap-cli` 是同一算法的移植。

**对我们的意义**：aider 证明了三件事——① 索引可以**完全不用 LLM**（确定性、可复现）；② 「谁重要」可以用图算法算出来，不需要模型猜；③ token 预算必须**显式**，否则上下文被打爆。

### 3.2 结构化代码索引（arXiv 2606.22417）

该文标题即结论：**Code Isn't Memory**——代码不该塞进记忆/向量库，应该建**结构化索引**（文件依赖图 + 符号级事实），检索时按结构命中，而非靠语义相似。

**对我们的意义**：语义向量只应做**召回补充**（自然语言→候选），最终判据必须是**结构事实**（符号/关系/行号）。这与华哥「准确为主」完全一致。

### 3.3 本机已有参考的定位（防误用）

`github 源码参考/00_catalog/代码地图/` 是**人工编写的结构导航 Markdown**（每仓一节、只记结构事实），**不是机器索引**，也不能当检索库用。它的价值是给「定位」字段供料。

| 选项 | 结论 | 理由 |
|---|---|---|
| 接入 Jev 云端 | **否决** | 闭源 waitlist、无权重、云端调用＝第二执行腿，违背底座「本地私有部署、唯一调用入口」定位；且评测与权重均未公开，无法验收 |
| 吸收 Jev 的**范式** | **采纳（且已在进行）** | 「判别而非生成、返回标定置信度、schema 保证、按置信度分流」正是底座缺的**第四类模型**；开源复刻 Laya 已落地 |
| 用 Laya 做**检索意图路由** | **采纳（本方案第五期）** | 华哥说 agent = 思考 + 搜索 + 调用；「思考该走哪条搜索腿」就是决策模型的位置——它比 LLM 快 100×、可复现、且高置信区间准确率 82.4% 已可用 |

**必须写明的风险（不包装）**：
1. 57.8% 的整体准确率**不到可用线**；可用的是**高置信区间**（82.4%），所以用法必须是「置信度 ≥ 阈值才自动走，低于阈值交回 LLM 或人」——这恰好就是 Jev 官方推荐的用法。
2. 瓶颈是**标注质量与标签边界**，不是算力（32 秒训完即证）。上量前先把标签体系划清楚、类别做均衡（已实测：类别不均衡会让模型把样本押到最大类）。
3. 「零幻觉」只保证**输出形状合法**，不保证判断正确——路由错了要能回退。

### 5.1 第一期：目录树（G1）

**能力**：`文件系统支持库.文件操作.目录树`

| 参数 | 类型 | 语义 |
|---|---|---|
| `目录路径` | 文本型（必填） | 树根 |
| `最大深度` | 整数型 | 默认 3；0=不限 |
| `包含文件` | 逻辑型 | 默认 真；假＝只要目录骨架 |
| `名称模式` | 文本型 | 可选 glob（如 `*.py`） |
| `排除目录` | 列表型 | 默认 `.git/__pycache__/工程缓存/node_modules/.venv` |
| `条数上限` | 整数型 | 默认 500；**超限如实截断并回 `已截断=真`**，不静默 |
| `含大小` | 逻辑型 | 默认 假 |

**返回**：`{树文本, 节点数, 目录数, 文件数, 已截断, 截断处}`——`树文本` 用缩进树形，**一次调用拿整棵树**。

**为什么值得做**：这是华哥点名要的、也是最便宜的一条（纯路径遍历，无新依赖）。它同时消掉一个漂移源——Agent 想看结构时不再去用终端 `ls -R`/`find`。

### 5.2 第二期：仓库地图（G3，对标 aider repo map）

**能力 1**：`代码解析支持库.仓库地图.建符号图`
- 入参：`仓库根` / `排除目录` / `语言集` / `库文件`
- 做法：复用现有 `语法索引.批量解析语法`（tree-sitter / ast，确定性）抽出 def/ref → 建加权有向图 → 落 SQLite（nodes/edges 与现有代码地图同构，便于复用查询能力）
- 出参：`{节点数, 边数, 文件数, 耗时秒, 跳过清单}`

**能力 2**：`代码解析支持库.仓库地图.取仓库地图`
- 入参：`仓库根` / `锚点`（文件或符号，可多个）/ `token 预算` / `库文件`
- 做法：Personalized PageRank（锚点作个性化向量；**无锚点＝全局排名**）→ 按排名渲染「文件 + 符号签名」→ **二分卡预算**
- 出参：`{地图文本, 收录文件数, 收录符号数, 预算, 已用预算, 是否截断}`

**为什么是「建图」与「取图」两条而不是一条**：建图是**重活且可缓存**，取图是**轻活且每次参数不同**。拆开后，同一份图可以服务多次不同锚点/不同预算的取用——这是 aider 缓存设计的同一思路。

### 5.3 第三期：代码语义索引（G2）

**能力 1**：`代码解析支持库.语义索引.建代码索引`
- 入参：`索引根` / `库文件` / `嵌入模型名`（默认 bge-m3）/ `排除目录` / `批大小`
- 做法：`按规则切块`（复用）→ `生成嵌入`（复用）→ 落 SQLite（块文本 + 向量 + 文件路径 + 起止行）
- **嵌入结果同时写 `嵌入缓存`**（复用，避免重复算）
- 出参：`{块数, 文件数, 命中缓存数, 新算数, 耗时秒, 跳过清单}`

**能力 2**：`代码解析支持库.语义索引.查代码块`
- 入参：`索引根` / `查询` / `库文件` / `顶部数量` / `文件模式` / `最小分数`
- 做法：查询向量化 → 余弦召回 topN → **关键词/符号精排**（召回宽、精排严，对应华哥「准确为主」）
- 出参：`{候选列表[{文件路径, 起始行, 结束行, 块类型, 分数, 向量分数, 关键词分数, 片段}], 命中数, 召回数}`

**边界（写死防误用）**：语义索引只做**召回补充**，最终位置必须回 `读取文件` 按行区间取真实内容——**不以向量相似度当事实**（对齐 arXiv 2606.22417「代码不该当记忆」）。

### 5.4 第四期：统一检索入口（G4）

**能力**：`模块库.统一检索.检索`

| 参数 | 类型 | 语义 |
|---|---|---|
| `查询` | 文本型（必填） | 自然语言或符号/正则 |
| `范围` | 文本型 | `能力` / `符号` / `代码块` / `文本` / `文档` / `自动`（默认 `自动`） |
| `项目根` | 文本型 | 平台根（能力/文档两路需要） |
| `顶部数量` | 整数型 | 默认 10 |
| `细节级别` | 文本型 | `索引` / `摘要` / `完整`，默认 `摘要` |

**自动路由判据（确定性，不用模型）**：

| 查询形态 | 走哪路 |
|---|---|
| 含 `/` 或 `::` 或 `_` 或全英文标识符 | **符号**（代码地图） |
| 形如正则（含 `\|`/`*`/`.*`/`^`） | **文本**（正则搜索） |
| 含「能力」「怎么做」「有没有」 | **能力**（能力目录） |
| 含「文档」「方案」「规范」「说明」 | **文档**（项目文档索引） |
| 其余自然语言 | **代码块**（语义索引）+ 关键词并行，合并去重 |

**返回统一结构**：`{命中列表[{来源, 位置, 摘要, 分数, 建议下一步}], 路由, 各路耗时, 是否降级}`——`建议下一步` 直接给可调用的能力 id + 参数骨架（把「搜到即会用」做实）。

**为什么是门面层而不是新腿**：它**不自己实现任何检索**，只做路由 + 调用 + 合并（合法的门面层，与支持库的「门面→提供者」同构）。

### 5.5 第五期：决策层路由（G5，Jev 范式的落点）

1. **先真跑通**：为 `连接决策模型` / `执行决策` 补验证场景，跑通「启动 Laya multilingual → 一次前向 → 返回选项 + 置信度」，清掉门禁 2 项红。
2. **再接路由**：四期入口的「自动路由」在**确定性判据给不出唯一答案时**（如多路都命中、或查询形态模糊），交 `执行决策` 判：问题类型 `choice`、选项＝各路候选、要求返回置信度。
3. **置信度分流（写死）**：置信度 ≥ 阈值（初值 0.7）→ 自动采用该路；低于阈值 → **并行跑前两路并合并**（退回确定性策略，不猜）。

**为什么值得**：华哥说「agent 本质是思考+搜索+调用」。目前「思考」全靠 LLM 每轮生成——慢、贵、不可复现。选路这种**有限选项的判别**正是决策模型的靶心（对比 LLM 快 100×、可复现、且不生成文字就不会漂移）。

## 六、被否决的做法（记录取舍，防后人重走）

| 做法 | 为什么否决 |
|---|---|
| **接 Jev 云端 API** | 闭源 waitlist、无权重、云端＝第二执行腿，违背本地私有部署与唯一调用入口 |
| **新建独立「检索支持库」** | 六路检索能力已分散在既有包内；新建库＝同一件事两套实现（违反只保留一条腿） |
| **把代码塞进向量库当唯一索引** | arXiv 2606.22417 的核心结论：代码要**结构化索引**，语义向量只做召回补充；且相似度不能当事实 |
| **用 LLM 做检索排序/选路** | 慢、贵、不可复现；选路是有限选项判别，交决策模型才对（第四期先确定性判据，第五期才用决策模型兜模糊） |
| **引第三方代码索引工具**（zoekt/aider 本体） | 引入第二套进程/存储/契约，且要维护外部依赖；底座已有 tree-sitter/networkx/嵌入/重排/切块，自己拼即可 |
| **目录树用终端 `ls -R`/`find` 代劳** | 这正是华哥要消除的漂移源：脱离契约、脱离日志、无参数校验、无条数预算 |
| **统一入口直接用 LLM 生成检索计划** | 同上；且 LLM 生成的动作无法保证是**已注册能力**（决策模型有 schema 保证，LLM 没有） |
| **给决策模型设低阈值追求自动化** | 57.8% 整体准确率不到可用线；低阈值＝把错判自动化，必须阈值分流 + 可回退 |

| 三 | `代码解析支持库.语义索引` | 新建子包（2 条能力 + 包声明 + 说明书 + 注册） |
| 四 | `模块库.统一检索` | 新建模块（1 条能力 + 包声明 + 说明书 + 注册） |
| 五 | `大语言模型支持库.模型连接器` | 补验证场景引用（不改契约） |

**新能力一律走唯一调用入口**，不新增第二执行腿；每期完成后跑编译器（只编本次变更单元）+ 受影响说明书同步。

### 7.2 验收口径（每期独立）

1. **能力真跑**：按唯一网关 HTTP 调用，返回结构与本方案表格逐条对上。
2. **反向验证**：关键判据（如预算截断、置信度分流、精排）去掉后必须失败，还原后必须通过。
3. **准度抽样（主指标＝精确率，华哥 2026-09-21 定口径）**：构造已知答案的样本集，量
   **精确率 = 命中题数 / 全部返回条数**——返回 10 条里只中 1 条就是 **10%**，
   只返回 1 条且中才是 **100%**。同时报 **首条准确率 P@1** 与 **召回率**，三个数一起看：
   「有没有命中」只是召回，**不能当准度**（它把「返回一堆只中一条」和「只返回一条且中」当成同一结果）。
   期望返回条数（调用方本来想要几条）作为可扫参数（`--期望条数`）。
   **基线工具与首份实测矩阵见 `开发文档/归档/202609_检索准度基线.md`（归档件，只作历史取证）。**
4. **漂移消除证据**：同一批任务分别用「MCP 单路」与「统一入口」跑，比对**调用次数**与**首条准确率**。
5. **精确率不得回退（硬门禁）**：每落地一期都要重跑 `开发工具/检索准度基准.py`，
   新路**不得拉低**既有路的精确率；四期统一入口的精确率**必须高于单路最高者**，
   且必须自带条数控制——不能把几路结果直接拼接（那会把各路「给多」的毛病叠加，精确率雪崩）。

### 7.3 首份基线对方案的硬约束（2026-09-21 实测所得）

| 路 | 实测性格 | 对本方案的约束 |
|---|---|---|
| 能力层·搜索能力 | 又准又克制（期望 1 条时精确率/首条/召回均 1.0） | **不动** |
| 符号层·代码地图 | 找得到但爱给多（召回 0.8→0.933 时精确率 0.8→0.45） | 二期仓库地图的 PageRank **必须把首条准确率（当前 0.8）推上去**，并自带条数控制 |
| 文本层·正则搜索 | 克制但漏（精确率 0.9、召回仅 0.6） | 正则口径太窄（漏 class/异步/非 Python），统一入口**必须靠其它路补齐召回** |

5. **门禁**：编译器 + 公开调用完整性门禁无新增违规；五期完成后 G5 的 2 项红必须清零。
6. **HTML 黑盒全量**：新增能力用 HTML 通过 GET/POST 并发请求编译制品验证（唯一正式验收链）。

### 7.4 不做什么（防范围蔓延）

- 不改现有六路能力的既有语义（只增不改）。
- 不为检索引入新的第三方服务或云端依赖。
- 不把「搜索快」当目标——目标是**一次搜准**，省下的往返就是省下的 token。

## 八、与既有能力的边界（不越权、不重叠）

| 既有 | 边界 |
|---|---|
| `能力目录.搜索能力` | 搜**平台能力**。统一入口的「能力」路**转调它**，不重写 |
| `项目文档支持库.查询索引` | 搜**项目文档**。统一入口的「文档」路转调它 |
| `模块库.知识检索.检索知识` | 搜**指定目录文档**。与本期代码语义索引**职责不同**（文档 vs 代码），**不合并** |
| `代码解析支持库.代码地图` | 已有 SQLite 符号查询。二期建图**与之同构**，查询能力**复用不重造** |
| `文件系统支持库.内容检索.正则搜索` | 最准的一路，统一入口**原样转调** |
| `代码解析支持库.语法索引` | 一期/二期**只消费**它的语法事实，不复制解析逻辑 |

## 九、分期执行顺序与理由

```
一期 目录树 ────────────► 立刻可用，消掉「看结构就去用终端」的漂移
                            │
二期 仓库地图 ◄────────────┘ 复用一期的目录遍历 + 既有语法索引
                            │
三期 代码语义索引 ◄──────────┘ 复用二期的文件清单 + 既有切块/嵌入
                            │
四期 统一检索入口 ◄──────────┘ 前四路齐了才做门面（先有腿再收口）
                            │
五期 决策层路由 ◄────────────┘ 入口有了才有「选路」这个决策点
```

**为什么这个顺序**：每期只依赖前面已跑通的东西，不存在「为了做 A 先做 B 又回去改 A」；且**一期就见效**（目录树当天可用），符合华哥「一次做透但不挤牙膏」的要求——方案一次出全，交付按期可验。

## 十、待华哥确认的三个点

1. **期数优先级**：是否按一→五顺序推进（可先只做一、二期）。
2. **决策模型阈值**：初值 0.7（低于它退回确定性合并）是否合适。
3. **索引落盘位置**：代码索引与符号图库默认放 `工程缓存/`（运行态，不入库），是否符合预期。

> 除上述三点外，其余技术取舍本方案已按设计哲学自裁，不再回问。
