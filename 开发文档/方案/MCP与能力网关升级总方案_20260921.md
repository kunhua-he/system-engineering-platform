## 零、判据（唯一，且有先后）

华哥 2026-09-21 定：
> *"我们一直的口径都是这个，你不要说是否收益最高，而是**是否足够稳定，足够高效**，这个才是评判的标准。"*

**判据只有两条，且顺序不可换：**

| 顺序 | 判据 | 硬检查项 | 不达标怎么办 |
|---|---|---|---|
| **先** | **稳定性** | ① 不引入新的不确定性（并发/时序/双写/双轨）② **只增不改**既有默认行为 ③ 一处改动、**可单点回退** ④ **无假绿空间** ⑤ 不新增第二腿/映射层/兼容壳 | **直接排除或降级 —— 不管它省多少往返** |
| **后** | **高效性** | ① 减少**往返次数**（首要）② 减少单次耗时 ③ 更容易**一次命中** | 过不了稳定性，高效性再高也不做 |

**为什么稳定必须在前**：不稳定的改动会把「一次往返」变成「反复排查」，**高效性直接变负**。

## 二、全层方案（每条**只选一种做法**，并给稳定性 / 高效性论证）

### A 层 —— 往返次数与签名自描述

#### A1 薄壳一次只许调 1 个工具

| 项 | 内容 |
|---|---|
| **选定做法** | 薄壳加 **`工具清单`**（列表型，只增）→ 能力注册表加 **`可否并行`（缺省 `假`）** → 调度层**读写门闸**（可并行拿读锁、其余拿写锁）→ 结果**按提交顺序**回灌 |
| **为什么不选「缺省并行」** | 缺省并行会让 745 个能力里**所有写类瞬间进入并发**，撞车概率爆炸。**缺省假 = fail-closed**：不声明任何能力时，行为与今天**逐字一致**（零风险上线）；只有显式声明过的能力才并行 |
| **稳定性** | ✅ 默认行为不变（`可否并行` 缺省假 ⇒ 现状就是串行）；✅ 写类漏标 ⇒ 仍串行，**不会撞车**；✅ 旧 `工具` 字段保留为单元素 ⇒ 旧调用方无感；✅ 门闸是单点，可回退 |
| **高效性** | ✅✅ **直接砍往返次数**：一次 turn 收多个能力。这是本方案里唯一能减少**「同一轮内」**往返的一条 |
| **外部依据** | `openai/codex`：`router.rs:233-237` `.unwrap_or(false)` **缺省不并行**；`parallel.rs:124,179-183` `Arc<RwLock<()>>` 读锁并行/写锁独占；`turn.rs:2503` `FuturesOrdered` 按提交顺序回灌；`registry.rs:520` 逐工具声明。MCP server **默认串行、需显式 opt-in**（`rmcp_client.rs:2186` vs `:2408`）。**协议层批量是官方删掉的**（`2025-06-18/changelog.mdx:12`）⇒ 客户端自己拼是唯一路 |
| **落点** | `开发工具/薄壳/工具清单.py`（工具定义 + `工具清单` 入参）、`开发工具/薄壳/薄壳服务.py`（调用入口 + 门闸）；能力注册表侧 `可否并行` 字段落点待 §七 回填 |
| **判据** | ① 不传 `工具清单` 时行为与今天**逐字一致**；② 传 3 个可并行能力 ⇒ 总耗时 < 串行；③ 传 2 个写类能力 ⇒ **串行执行**（门闸生效） |

#### A2 签名不自描述 → 第一跳必错

> ⚠️ **本条已被 §八 8.1 第 1 条加深**：现场实测 `工具清单.py:152` 的 `参数` **连 `properties` 都没有** ⇒
> 猜参数名**是结构必然，不是概率问题**。**根因修复见 §八 8.3 新增项 A2c**（让薄壳够得到已存在的结构化契约面）。

| 项 | 内容 |
|---|---|
| **选定做法** | **不动工具描述长度**；改**错误体四段式**（错误码 + 原文回显 + 候选签名 + 规则原文），见 B2 |

| **高效性** | ✅ 省掉「猜 → 失败 → 再猜」的往返（实测**猜参数名错 3 次**） |
| **外部依据** | `Aider-AI/aider` `editblock_coder.py:84-114` 四段式 + `find_similar_lines` → "Did you mean…" + `base_coder.py:100` 硬上限 3 次反思 |
| **落点** | 网关错误体构造（与 B2 同处，待 §七 回填） |
| **判据** | 传一个写错的参数名 ⇒ 返回体里出现**候选正确签名**（多候选全列，不猜） |

#### A2b 枚举取值不可见（★ 本层最该先做）

| 项 | 内容 |
|---|---|

### ★ 批 4 落地时的三条现场事实

### ★ 批 3 落地时对原方案的两处纠正

**1. L7 的第②层「缺省不校验」是刻意的 opt-in，不是缺陷。**
原方案（§八 8.2 #2）把 `文件租约申请.py:122 校验指纹: Any = 假` 写成缺口。现场核实：
`开工即占` **早就有 `校验指纹` 形参**（`开工编排.py:607`），且 `is 真` 时才传下去；
`_拆路径条目` 也已支持 `{"路径", "指纹"}` 认知条目并归一格式。
这是「认领是『我先站住』、不是『内容必须与我的认知一致』」的**有意设计**
（源码注释原文），改成缺省校验会变更既有行为 ⇒ **不动**。

**2. L7 的第③层（写路径接线）按稳定性判据「本批不做」。**

### ★ 批 2 落地时的两条现场事实（改变了原判）

**1. L9 不是「兼容性装饰」，它真的会改变行为 —— 且这正是它的价值。**
实测：mcp SDK 在 `server/lowlevel/server.py` 用
`jsonschema.validate(instance=arguments, schema=tool.inputSchema)` **执行工具 schema**。
故加了 `additionalProperties: false` 后，传错参数名会**当场报错**而不是被静默忽略。

**但这是个行为变更**，原方案没写清楚：薄壳**工具层**从「忽略未知参数」变成「拒绝」
（能力层仍是忽略，两层不同 —— `网关参数校验面.py` 的忽略口径不受影响）。
原方案把它归为「只增」，实际是「工具层由宽变严」；方向正确（正是治「猜参数名」），但**必须知道**。

**2. L10 的落点比原判深：SDK 对「返回 list」的路径固定 `isError=False`。**
实测 `server.py`：`CallToolResult(content=list(unstructured_content), isError=False)` ——
只有 **inputSchema 校验失败**（`_make_error_result`）与 **handler 抛异常**两条路会置 True。
⇒ 业务失败（含 `参数不合法`）在 MCP 链路上**完全不可见**，模型于是反复重试同一错误。
改法：薄壳返回 `CallToolResult` **对象**，SDK 对 `isinstance(results, CallToolResult)` 原样返回。

### ★ 落地时又踩到一个「假绿」形态（值得进规约）

**stdout 非 tty 时 Python 用块缓冲，脚本异常退出不 flush ⇒ 全部 print 丢失**，
`sh -c "… | tail"` 的退出码又是 `tail` 的 **0** ⇒ 现场是「**无输出、退出码 0**」。
实测踩到：`自测_stdio客户端.py` 第一次真退出码是 **1**（`JSONDecodeError`），但外层读到的是 0、正文空。
⇒ 两条改法已落地：① 自测脚本头部写明**必须带 `-u`**；② 用 `> 文件; echo $?` 取真退出码，
**不拿管道/`tail` 的退出码当结论**。

**落地时发现并已修的三处自身缺陷**（记下来，避免下一轮重犯）:

1. 白名单只改了 `工具清单.py` 的 `enum`、**漏改** `薄壳服务.py` 的 `薄壳允许操作` —— 两处必须同源

2. 说明的保底键序**反了**：按原优先级「截断说明 / 丢弃说明」先被丢掉、留下的是套话 `提示` ——
