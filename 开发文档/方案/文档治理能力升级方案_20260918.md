## 一、归因：最底层逻辑

**一句话**：**规范 → 判据 → 能力 → 门禁，是一条四环链。缺任一环，规则就退化成纸面。**

```
规范（文本：人读的规则）
  → 判据（数据：可机器判定的规则投影）
    → 能力（接口：任何调用方经唯一入口可用）
      → 门禁（必经路径：不跑就红）
```

### 1.1 实证对照（同一天、同一个仓库）

| 规则 | 规范 md | 判据数据 | 能力 | 门禁 | 结论 |
|---|---|---|---|---|---|
| **Markdown 文档体例** | ✅ `规范/Markdown 文档体例规范.md` | ✅ `规范/Markdown 文档体例判据.json` | ✅ `项目文档支持库.校验规范` | ✅ 已接线 | **四环齐 → 能被机器判** |
| **方案文档生命周期**（2026-09-18 新立） | ✅ `规范/方案文档生命周期规范.md` | ❌ **无** | ❌ **无** | ❌ 无 | **只有第一环 → 纸面** |

### 1.2 第二层归因：不是「缺校验器」，是**缺集合级粒度**

现有 `支持库/后端/项目文档支持库`（10 条能力、997 行实现、405 行测试）**能力粒度只到单份文档**：

```
入参实测：全部首参为「正文:文本型」
判据类型实测（规范校验.py 执行表，4 种）：
    行正则计数 / 围栏配对 / 头部包含 / 链接文字一致
    —— 全部只在一个文档内部自证，不涉及文档之间的关系
```

**而「文档互踩」的本质恰恰是跨文档关系**：

| 互踩形态 | 判据需要读什么 | 现有能力能否表达 |
|---|---|---|
| 编排冲突 / 自称唯一 | **一批**文档的 H1 标题 | ❌ 不能 |
| 悬空引用 | 文档 A 的链接 → 文件 B 是否存在 | ❌ 不能 |
| 隐形债 | 子方案出现「待办」→ 债务清单有无对应登记 | ❌ 不能 |
| 状态取值非法 | 单份文档的状态行 | ⚠️ 勉强（需新增判据类型）|

### 1.3 第三层归因：手写判据 = 重复发明 + 随机出错

**2026-09-18 实测代价**（全部发生在本轮互踩收敛中）：

| 现象 | 真实原因 |
|---|---|
| 首版判据 `grep '唯一入口'` **报 22 份假阳性** | 把「见 XX 入口」的**合规引用**当成了「自称」 |
| 状态判据写成 `grep '^> 状态：'` **能被 `已删除` 骗过** | 只查「存在」不查「取值 ∈ 枚举」 |
| 收敛完自检才抓到**规范里指着已删文件** | 悬空引用没有机器判据 |
| 债务账目重算前是 **9 条、实物 11 条** | 跨文档登记没有机器判据 |

**两个判据缺陷都是反向验证抓出来的** —— 说明「手写判据」这条路本身不可靠：
判据写完没有自带样本、没有元测试、下次还得重写一遍。

**∴ 归因结论**：这不是「改几行 grep」的问题，是**底座缺一类原子能力**（集合级文档判据），
按哲学 14.3「反复犯错的开发要补底层」，应**升级现有库**而不是继续手写。

## 二、升级方案（补能力，不新建腿）

**落点**：`支持库/后端/项目文档支持库`（**升级现有包**，不新建库 —— 单腿原则）。

**为什么选它**：它已是「项目文档治理」的归口（切块 / 校验规范 / 索引 / 登记 / 清单），
集合级判据是它的**同类扩展**，不是新域。

### 2.1 新增 2 条原子能力

| 能力 id | 原子动作 | 入参要点 | 返回要点 |
|---|---|---|---|
| `项目文档支持库.扫描文档集合` | 按根目录 + 文件名模式扫出一批文档，**只读** | 根目录 / 文件名模式（如 `*.md`）/ 豁免目录列表 / 是否读正文 | 文档清单（相对路径 / 行数 / 字节数 / 正文（可选）/ 修改时间）|
| `项目文档支持库.校验集合判据` | 按**集合级判据文件**逐条校验一批文档 | 根目录 / 判据文件 / 文件名模式 / 豁免目录列表 | 违规范条目（判据id / 严重级 / 说明 / 文件 / 行号）+ 驳回项数 |

**原子性说明**：扫描与校验分开 —— 扫描可被其它能力复用（如索引入库前取清单），
校验不自带隐式扫描（判据文件决定它要读什么）。

### 2.2 新增 4 种判据类型（数据驱动，不硬编）

**判据仍来自 JSON 文件**（沿用现有 `校验规范` 的口径：规范改一句 → 只改数据）。

| 判据类型 | 参数 | 语义 | 治哪种互踩 |
|---|---|---|---|
| `集合唯一` | 模式 / 期望 / 跳过围栏 | **全仓**命中文档数必须等于期望 | 自称唯一（编排入口只允许 1 份）|
| `引用可达` | 无 | 文档内本地链接的目标**文件必须存在** | 悬空引用 |
| `跨文档配对` | 触发模式 / 登记文件 / 登记模式 | 文档命中「触发模式」时，**登记文件**必须含对应登记 | 隐形债（子方案有待办 → 债务清单须登记）|
| `状态枚举` | 行前缀 / 取值枚举 | 该前缀行的取值必须 ∈ 枚举 | 状态取值非法 |

**判据的组合性**：4 种新类型 + 原 4 种 = **8 种**，全部数据驱动、全带实现、未实现的类型**明确报错不假装通过**
（沿用现有 `_跑一条` 的口径）。

### 2.3 同步产出 3 件

1. **判据文件** `开发文档/规范/方案文档生命周期判据.json` —— 把新规范的可机器判定部分落成数据
   （含「唯一真源」字段指向规范 md，与体例判据同形制）；
2. **测试** `测试中心/支持库/测试_项目文档支持库_集合级.py` —— 每条新判据：正向 1 + 反向 1
   （反向＝必须真打红，沿用现有测试风格：`test_未闭合围栏被阻断_反向验证`）；
3. **接线** 发布门禁新增「防回潮 · 文档生命周期」检查项（判据只调本能力，**不另立第二套扫描**；
   配置「干净通过」态、基线 0，与既有五项同口径）。

### 2.4 明确不做

| 不做 | 理由 |
|---|---|
| **新建一个「文档治理支持库」** | 与 `项目文档支持库` 职责重叠 ⇒ **第二条腿**（华哥裁决①明令） |
| **把判据硬编进代码** | 现有 `校验规范` 已确立「判据来自数据文件」的口径；硬编会让规范与判据漂移 |
| **校验能力内部自带扫描** | 隐式 IO 让调用方无法预知读了多少文件；扫描独立成能力，可复用可测 |
| **把「修复」也做进能力** | 能力只**判**不**改**（与现有 10 条一致）；改动留给调用方与 `改清单条目` 这类纯变换能力 |
| **在峰值期跑全量回归** | 哲学 12.1③；本批只跑定向测试 + 反向验证 |
