## 三、逐件落地方案

### ① 统一配置加载器

**目标**：全仓**唯一**配置加载入口；调用方不感知来源（文件/环境变量/提供者配置）。

**现状问题**：`支持库/适配层/配置读取/` 与 `项目适配层/配置适配/` **两套并存** —— 违反哲学 1.3。

**落点**：新建 **`支持库/后端/配置支持库/`**（或归入现有 `支持库/适配层/配置读取/` 升格为正式支持库）。
对外**唯一能力**：`配置支持库.配置读取.读取配置`（参数：来源标识 + 键路径 + 默认值；返回：值 + 来源 + 是否默认）。

**收口要求**：
- 分两段（与 `依赖分两段` 同款）：**公共段**（全项目可见键）+ **项目段**（项目适配层注入）；
- 优先级固定：**项目段 > 环境变量 > 默认值**，且**来源必须回传**（调用方能看到值从哪来）；
- 缺失必填键 → **fail-fast 中文错误码**（不得静默用默认值）；
- 旧的两处入口**删除**（不留别名，单腿）。

**门禁**：新增判据「配置读取调用点只允许 1 处公开入口」接进发布门禁。

---

### ② Schema 迁移（通用件）

**目标**：把现有 `_迁移到130/_140/_150` 的模式**升级为通用迁移框架**，凡有版本化存储的包都能复用。

**落点**：新建 **`支持库/后端/迁移支持库/`**，对外能力 `迁移支持库.迁移.执行迁移`：
- 参数：`当前版本`、`目标版本`、`迁移步骤表`（版本 → 步骤函数名）、`存储`；
- 返回：`已执行步骤`、`起止版本`、`是否已最新`；
- **幂等**：已最新则直接返回（不重复执行）；**失败即停**并回报失败版本与原因；
- **必须写迁移证据**（照 `_写迁移证据` 现有范式）。

**要求**：`平台控制面/平台状态` 改为**调用**该支持库（现有三段迁移逻辑迁过去），不保留两份实现。

### ③ 请求 id 贯穿

**目标**：一次外部调用从**网关入站**到**能力执行**到**证据落盘**，全程**同一个请求 id**。

**现状**：`独立进程.py` 有 `请求id`（提供者隔离层），但网关层、能力调用层、证据层的 id **各自生成**。

**落点**：
1. **入口生成**：`运行核心/统一网关/网关核心.py` 收到请求即生成 `请求id`（若入参带了则沿用 —— **可追溯**）；
2. **全程透传**：网关 → 能力调用器 → 提供者进程 → 能力实现 → 返回信封，**每层原样带**；
3. **契约冻结**：统一返回信封的 `请求id` 字段**必须有值**（现状部分能力缺 —— 见 §8.5 第 4 条「缺字段 `['值','请求id','耗时毫秒']`」实证）；
4. **证据关联**：证据链（`追加证据`）记录 `请求id`，可一路追到具体调用。

**判据**：新增门禁「统一返回信封必含非空 `请求id`」（可基于现有验证器做，不另写扫描）。

### ④ 任务队列上限

**目标**：任务（长任务/后台任务）队列**全局有界 + 每类有界**，满载如实拒绝（不静默丢弃）。

**现状**：并发控制支持库有信号量/线程池；`超时执行.py` 有有界准入（线程侧）。**缺的是「任务队列」这一层**（排队中的任务数无上限）。

**落点**：`运行核心/任务调度/任务系统.py` 增加**队列容量闸门**：
- 参数：`队列上限`（默认保守值）、`满载策略`（拒绝 / 阻塞等待，**默认拒绝**）；
- 满载返回中文错误码 + 当前排队数（**可诊断**）；
- 队列长度、拒绝次数进证据（**可观测**）；
- 复用 `并发控制支持库` 的容量闸门原语，**不另造一套**。

### ⑥ 结构化日志

**目标**：全仓日志**统一结构**（可查询、可聚合、有界），替换散落的 print。

**现状**：`事件日志.py` 已有（写入/查询/聚合错误码/最近失败），但**调用方仅 4 处** —— 大量地方仍用 `print`。

**落点**：
1. **统一结构**（字段固定）：`时间`、`级别`、`来源`（包/能力）、`请求id`、`事件类型`、`说明`、`明细`；
2. **推广**：把 `开发工具/` 与 `运行核心/` 的关键路径 `print` 改为经事件日志（**不追求一次全改**，
   按「谁出问题谁先接」推进）；
3. **有界**：现有分片机制保留（`分片路径表`），确认**总量有上限**；
4. **不引入第三方**（只允许标准库）。
