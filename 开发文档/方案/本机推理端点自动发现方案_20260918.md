### 0.4 ∴ 真正要回答的问题（不是「怎么发现端口」）

```text
★ 核心问题：底座的「模型」到底是什么角色？

  路线1【管道】   底座只负责「连得上、连得稳」
      调用方告诉它 url + 模型名，它照做 —— **现状就是这样，没缺口**
      那视频三层对底座基本都无价值，本方案应当作废

  路线2【有账可查】底座知道「有哪些模型、各自什么特点」，能被查询
      这才是视频第 ③ 层的底座版：**不是替 agent 发现，而是让 agent 查得到**
      ★ 前提：需要一份「模型能力台账」——谁擅长什么、怎么连、什么限制
      ★ 而这份台账**由 agent 自己写**（写 JSON 本来就快）
      ★ 底座要做的是：把 agent 写的台账**存得住、查得出、用得上**

  路线3【调度】   底座按任务自动挑模型
      比路线2更进一步（要判断"这个任务该用谁"）
      ★ 但「挑」涉及取舍（快/准/贵/隐私），隐私部分归业务端
      ⇒ 底座最多给「候选 + 特点」，**不替调用方拍板**
```

**⇒ 我的理解偏差**：上一版把视频第①层（省人手填）当成底座缺口，
**方向从头就错**——底座用户是 agent，agent 不缺「替它发现」这个动作。

**⇒ 现在真正该先定的是**：底座要不要有「模型能力台账」（路线2），
以及「发现/扫描端口」是否连作为**补台账的辅助手段**都不需要。

## 一、缺口是什么（现场取证）

### 1.1 底座当前只知道「自己拉的」模型

```bash
curl -s -X POST http://127.0.0.1:40007/网关/调用 \
  -H 'Content-Type: application/json' -H "Authorization: Bearer <网关凭证>" \
  -d '{"操作":"调用能力","能力id":"大语言模型支持库.模型连接器.资源快照","参数":{}}'
```

实测返回（2026-09-18 20:27）：

```text
系统内存：总 96.0GB / 可用 40.1GB / 占用 58%
活跃连接：LLM(本地)=1，LLM(云端)=4，连接总数=5
```

⇒ 底座**确实**在管本地模型（1 个本地 LLM 连接），说明「管模型」这条链是通的。
它管的是**通过 `启动本地模型` 由它自己拉起、并绑定了句柄**的那些。

### 1.2 但外部已在跑的端点它看不见

```bash
for K in 端点池 已运行 局域网 发现模型服务 选择模型 切换 难度; do
  curl -s -X POST http://127.0.0.1:40007/网关/调用 -H 'Content-Type: application/json' \
    -H "Authorization: Bearer <网关凭证>" \
    -d "{\"操作\":\"调用能力\",\"能力id\":\"能力目录.搜索能力\",\"参数\":{\"关键词\":\"$K\"}}" \
  | python3 -c "import json,sys; print(len((json.load(sys.stdin).get('值') or {}).get('能力列表') or []))"
done
```

实测：**全部 0 条**。

⇒ 后果：任何**不是底座自己启动**的推理服务（用户手动跑的 ollama、llama-server、
公司现有推理机、DGX Spark 那类外部节点），底座要调用它，调用方必须**人工知道端口并手填 url**。
这正是视频里作者抱怨的那件事（「想连上还得费半天功夫」）。

### 1.3 缺口边界（明确不管什么）

| 不做什么 | 为什么 |
|---|---|
| 不判「请求能不能上云」 | 违背哲学第 9 条（0 业务假设）与 9.3（隐私是业务端的事） |
| 不做跨机 / 分布式算力池 | `项目说明.md` 明文「多实例、分布式不在范围内」 |

## 二、可行性实测（三条决定性证据）

### 2.1 证据一：纯标准库能发现局域网服务（零第三方依赖）

底座铁律「只允许 Python 标准库」。实测用 `socket` + 组播 `224.0.0.251:5353`
手搓 DNS 报文，**真发现了局域网里的实体设备**：

| 探测的服务类型 | 结果 |
|---|---|
| `_services._dns-sd._udp.local` | ✅ 有应答（918 字节） |
| `_http._tcp.local` | ✅ 有应答 |
| `_ipp._tcp.local` | ✅ 有应答，**解析出局域网内真机 HP LaserJet Pro MFP M126nw**（含 mac 地址） |
| `_ollama._tcp.local` | ❌ 无应答 |
| `_localai._tcp.local` | ❌ 无应答 |

命令：`python3.14 测mdns标准库.py`（脚本见 `开发文档/分析/素材_DGX-Spark本地算力视频_20260918/`）

**两条结论**：
1. 自动发现**不需要第三方库**，符合底座铁律，也不用走适配层提供者；
2. **目前没有 AI 服务的通用 mDNS 约定**（`_ollama` / `_localai` 都没人广播）——
   所以本方案的**主体不做 mDNS**（那是跨机方向），只做**本机端点发现**。

### 2.2 证据二：本机端点扫描极快

命令：`python3.14 测端点扫描.py`（39 个候选端口，`socket.connect_ex` + 探活 `/v1/models`）

实测结果：

| 项 | 值 |
|---|---|
| 39 端口串行探测 | **0.00 秒**（平均 0.1 ms/端口） |
| 探活 `/v1/models` | **0.01 秒** |
| 合计 | **0.02 秒** |

⇒ 远低于华哥「单步测试超 2 分钟就是 bug」的红线，也不构成任何性能负担。

### 2.3 证据三：底座能接管已在跑的端点（现成的路，不重复造）

`连接LLM` 只传 `url` 就能接管外部端点，实测连上 ollama 并真实推理：

```text
连接LLM(模型=qwen2.5-14b:latest, 部署形态=本地, url=http://127.0.0.1:11434/v1)
→ 成功=True，句柄=532602
生成对话 → 回复='明白了，如果你有任何问题或需要帮助的地方，请随时告诉我！…'
         → 用量={"prompt_tokens":24,"completion_tokens":21,"total_tokens":45}
释放句柄 → 成功=True，且 ollama 进程本身未被杀掉（无孤儿进程、无副作用）
```

反向验证（防假绿）：传不存在的句柄 `999999` → `成功=False`、`错误码=句柄失效`。
⇒ 校验真的在起作用。

**所以本方案不是新增「连接」能力，而是补「发现」这一环，把结果喂给已经能用的 `连接LLM`。**

## 三、方案（建议新增两条原子能力）

### 3.1 能力一：`发现本机端点`（P0，主能力）

| 项 | 内容 |
|---|---|
| 能力 id | `大语言模型支持库.模型连接器.发现本机端点` |
| 参数 | `候选端口列表`（列表型，选填，缺省用内置候选表）<br>`探测超时毫秒`（整数型，选填，默认 250）<br>`含探活`（逻辑型，选填，默认 `true`） |
| 返回（值结构） | `端点列表`（列表型）：每项含 `端口`、`url`、`可用`、`模型列表`、`识别类型`（LLM/向量/重排/未知）、`响应毫秒`<br>`扫描端口数`（整数型）、`耗时毫秒`（双精度数型） |
| 错误码 | `参数不合法`（候选端口含非法值） |
| 行为 | 只读（`修改输入=假`）、幂等（同输入同结果，取决于当时谁在跑）、超时可重试 |

**关键设计口径**：

1. **只连回环地址** `127.0.0.1`，**绝不扫局域网网段** —— 守「单机」定位，也避免变成端口扫描器。
2. **先 connect 再探活，两段分明**：`connect_ex` 判端口通不通（快）；通了才发 `/v1/models`（慢）。
3. **不猜模型类型用名字猜**：按返回的模型名 + 端点特征给「识别类型」建议，**并明确标注为提示而非判定**（模型名可能任意）。
4. **无副作用**：不发推理请求、不写盘、不起进程、不占显存（照 `硬件画像探针` 六条机制）。
5. **端口候选表要有界**：内置常见推理端口（1234/5000/8000-8020/8080/8090/11434/30000-30002 等），
   加上 `环境配置` 里已声明的端口，**不遍历 1-65535**。

### 3.2 能力二：`选择端点`（P1，待确认需求后再定）

| 项 | 内容 |
|---|---|
| 能力 id（暂定） | `大语言模型支持库.模型连接器.选择端点` |
| 参数 | `端点列表`（列表型，必填，来自能力一）<br>`需要类型`（文本型，选填：LLM/向量/重排/任意）<br>`需要上下文长度`（整数型，选填）<br>`排除端口列表`（列表型，选填） |
| 返回 | `选中端点`（字典型）、`候选数`（整数型）、`选择理由`（文本型） |
| **边界** | **只做中立的技术匹配**（类型、上下文、可用性），**不含任何隐私/合规/成本判断** |

> P1 是否立项**必须先确认需求**（哲学第 10.1 条：先判定是不是真的缺）。
> 若确认只需 P0（发现即够用，调用方自己选），则 P1 不做。

### 5.4 真实验收（唯一标准）

对**编译产物**跑真实 HTTP（不是源码直调）：


且必须**现场跑一次真实发现**：

1. 本机确认有端点在跑（`curl http://127.0.0.1:<port>/v1/models` 回 200）；
2. 调 `发现本机端点`，确认清单里**真的列出了它**（含正确端口与模型名）；
3. 拿清单里的 url 调 `连接LLM` + `生成对话`，确认真实推理返回；
4. 反向：停掉端点后重跑，确认它**从清单消失**。

## 六、风险与对策

| 风险 | 对策 |
|---|---|
| 端口候选表太宽 → 被当成端口扫描器 | **只连 127.0.0.1**、候选表有界、并发有界（照 `资源预算`） |
| 探活拖慢调用 | 已实测 0.02 秒；连接超时设 250ms，探活超时 2 秒，全程有界 |
| 模型名任意，识别类型会猜错 | 字段名用「识别类型」并**在说明里写明是提示非判定**，调用方自行确认 |
| 与 `启动本地模型` 抢占端口 | 发现是**只读**，不占端口、不起进程；两者天然不冲突 |
| 重复实现（已有 `_等待本地健康`） | 抽成共用函数，**不新写第二份探活**（哲学 8：能力唯一性） |
| 口径漂移（把本机发现说成跨机） | 说明与说明书里**明写「仅本机回环」**，不宣称局域网能力 |
