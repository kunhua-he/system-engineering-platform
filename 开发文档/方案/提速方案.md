## 二、第 0 层：网关热接入（已落地）

> **本节已按 2026-09-16 口径重写。** 原第 0 层「MCP工具箱 热加载」的载体 —— `MCP工具箱/热重载.py`、`MCP工具箱/项目服务.py`、工具 `reload_tool_modules` —— 已随 `MCP工具箱/` 整目录于 **2026-09-15 删除**（实测：`find . -name '热重载.py' -not -path './工程缓存/*'` 无命中、`ls MCP工具箱` 报 `No such file or directory`、`git log --oneline --diff-filter=D -- 'MCP工具箱/*'` 得到删除提交）；原文那套「比源码时间戳 + 拓扑序重载」**已不存在**，不要再照它操作。

### 现象（现在仍然成立的那一半）

"改完代码必须重启"这件事，在本仓现在只剩**网关 40007** 一处：网关启动时一次性装配全部包；改了包（新增包 / 改实现 / 改契约）不通知它，线上就仍是旧能力，重启又会打断正在跑的调用。

### 改法：网关热接入（唯一口径）

改完能力**不重启进程**，发一条网关操作 `热接入`：

```bash
curl -X POST http://127.0.0.1:40007/网关/调用 \
  -H 'Content-Type: application/json' -H "Authorization: Bearer $TOKEN" \
  -d '{"操作":"热接入"}'
```

语义（`开发文档/决策记录/0008_能力更新走热接入不重启网关.md`，实读）：只发现**新增包 + 源码指纹变化的变更包**并增量装配；已装配包的运行态与句柄全部保留；变更包重载前先弹出旧模块；装配失败在**临时注册表内回滚**，不破坏线上能力。

### 实测（2026-09-16 现场）

| 验证项 | 结果 |
|--------|------|
| 热接入真实返回 | `{"新增包":0,"变更包":1,"卸载包":0,"成功包":["支持库.后端.媒体处理支持库.FFmpeg媒体（变更）"],"失败包":[],"已注册能力数":625}` |
| 单次耗时 | **316.85 毫秒** |
| 网关进程 | 未重启（`lsof -nP -iTCP:40007 -sTCP:LISTEN` 始终同一 PID 82241） |
| 装配结果 | 能力数 625、失败包 0 |

### 风险

极低。热接入是既有的后端核心能力（增量装配 + 失败回滚 + 保留句柄与运行态）；本方案只负责把它当"改完就发一次"的纪律用起来。

### 剩余边界（与旧口径的差别）

- **覆盖范围比旧热加载更宽**：决策记录 0008 明写「新增包、改实现、改契约」都走热接入；旧那套只覆盖"改实现"，且「新增/删除工具、改参数表仍需重启管理端」这条**已随管理端删除而失效**。
- 真正还要重启进程的只剩：**网关自身代码变更**，以及换端口/换凭证一类**部署配置**变更 —— 这类走第六节的凑批纪律。

## 三、提速项 1：全仓扫描（已落地）

### 现象

依赖防火墙（进发布门禁，每次发布都跑）全仓审计要 **11.25 秒**。它是最慢的一项全仓检查。

### 原因（已用源码定位，非猜测）

`运行核心/依赖防火墙.py` 原先这样取文件：

```python
for 文件 in sorted(实际目录.rglob("*.py")):
    if "pycache" in str(文件) or "工程缓存" in str(文件) or "测试中心" in str(文件) \
            or "示例项目" in str(文件) or "验证器" in str(文件) or "开发文档" in str(文件):
        continue
```

排除清单本身没错，但**排除发生在遍历产出之后**：`rglob` 已经把全仓 **72678 个 `.py`** 全部枚举、排序完，其中 **71775 个在 `工程缓存/`** 里（各虚拟环境与编译制品）。真正要解析的只有 583 个文件，**语法解析只占 0.42 秒** —— 11 秒里九成以上是白跑的文件遍历。

### 改法

改成**在进入目录时就剪枝**，不落进被排除的目录：

```python
排除片段表 = ("pycache", "工程缓存", "测试中心", "示例项目", "验证器", "开发文档")

def _遍历待审计源码(根: Path) -> list[Path]:
    for 当前根, 子目录名表, 文件名表 in os.walk(根):
        子目录名表[:] = [名 for 名 in 子目录名表 if not any(片段 in 名 for 片段 in 排除片段表)]
        ...
```

**为什么语义完全等价**：原是"整条路径含某片段就跳过"。一条路径含某片段，当且仅当它某个目录名或文件名自身含该片段。所以"目录名/文件名任一含片段就剪掉"与原先**筛出的文件集合逐条相同**，只是不再往下走。

### 实测

| 口径 | 改前 | 改后 |
|------|------|------|
| 全仓耗时 | **11.249 秒** | **1.020 秒（11 倍）** |
| 审计文件数 | 583 | 583（**一致**） |
| 违规清单 | 0 条 | 0 条（**逐条一致**） |

定向测试 `测试中心.开发工具.测试_依赖生命周期审计` 通过。这次提速直接落到每次发布必经的门禁上。

> **2026-09-16 复测**（现场，同一入口 `运行核心/依赖防火墙.py::审计依赖(系统根)`）：待审计文件 **645**（比当时的 583 多，因为此后新增了包）、遍历耗时 **0.127 秒**、全仓审计 **1.232 秒**、违规 **0 条**。剪枝口径仍然生效，`_遍历待审计源码` 的 docstring 就是这条口径的权威说明。

### 同一类病的第二处：判定"不改"

`开发工具/复用审计/能力调用图审计.py` 有一模一样的写法（`实际目录.rglob("实现/*.py")`），传**系统根**时 7.53 秒。但查过全部调用方：

- `开发工具/复用审计/运行能力调用图审计.py` 传的是命令行给的目录；
- 两个测试传的是 `模块库` / `模块库根`。

**没有任何真实调用方传系统根** —— 7.53 秒只是合成测法，实际路径上它只扫 `模块库`（0.09 秒）。改没被触发的代码等于加一条永不执行的路径，**故不改**。

### 一个"可选但不划算"的选项

有人建议给依赖防火墙加**落盘缓存 + 内容指纹失效**。可以，但**暂不做**：现在 1.02 秒里 0.42 秒是语法解析，剩下的摊在路径与包声明读取上；落盘缓存要靠内容指纹判断失效，等于**新增一个"缓存过期"故障面**去换不到 1 秒。不符合"稳定可靠十分重要"。若以后全仓文件数翻几倍，再议。

## 四、提速项 2：长任务（待落地）

长任务指直播逐字稿的"全自动精校"：75 分钟场，纯模型裁决耗时在**十分钟级以上**。已核实的当前事实（均从源码读出）：

- 窗口裁决并发默认 **3**（`实现/精校裁决.py`，同一句柄可并发）；
- 疑难说明每窗最多 **40 条**、单条最长 **120 字**（`实现/窗口切分.py`）；
- 复核证据每窗截断到 **2500 字**（`实现/复核编排.py`）；
- 加帽之前的历史实测是单窗请求体 **2575~10339 字**，约 600 字输入要 39 秒（来源：`窗口切分.py` 注释、`开发文档/未完成事项.md` P2 条）。

下面三项按**"先做最稳的"**排序，每项都写明风险与验证方法。

### 2a　裁决结果复用（先做，质量零影响）

**现象**：`实现/全自动精校.py` 只**写** `缓存/裁决/窗口_XXXX.json`，**从不读回**。同一段音频跑两次、同一场次跨多次运行、或不同场次出现相同话术，每次都要把模型重跑一遍。

**原因**：只写了落盘，没做"已有就复用"的判断。

**改法**：照抄同一模块里**已经存在**的复用写法 —— `实现/复核调度.py::_读已有复核` + `续跑=True`（文件在、区间 id 一致、轮次非空 → 直接复用）。给裁决窗口加同型读回，键取**输入指纹**（窗口底稿文本 + 疑难说明 + 证据 + 提示词 + 模式，取内容摘要）。指纹一致 → 复用；任一变化 → 重算。

**为什么质量零影响**：同输入同配置必然同输出，复用取的正是上次那次的产物；指纹把"输入变了"这件事挡在外面。

**预期收益**：重复跑（调试、返工、跨场次相同话术）时**跳过整个模型调用**，这部分从"分钟级"变成"毫秒级"。首次跑无收益。

**风险**：低。唯一要小心的是**指纹必须覆盖全部影响输出的入参**，漏一个就会把旧结果错当新结果用。

**怎么验**：同一输入连跑两次，第二次必须命中复用且产物逐字节相同；改动任一入参（如换提示词）后必须重算而非复用。

### 2b　请求体再瘦（后做，有质量风险）

**现象**：单窗请求体现由"底稿文本 + 疑难说明（≤40 条×120 字）+ 证据（≤2500 字）"拼成，其中**疑难说明把窗口文本又抄了一遍**（同一段文字在"底稿文本"里已出现，在"疑难说明"里再出现一次）。

**改法（按风险从低到高）**：

提速项 2b-1：**只去重、不减信息**：疑难说明只保留"时间点 + 原因 + 文本短前缀"，不再整条抄一遍全文 —— 模型靠时间点在底稿里定位即可。这是**纯压缩，零信息损失**。
提速项 2b-2：每窗疑难条数 40 → 8（保留最疑难的，排序已按"原因条数降序"）。
提速项 2b-3：证据 2500 → 1200 字。

提速项 2b-1建议做；提速项 2b-2、2b-3**必须 A/B 实测**：它们是**有损**的，减的是模型判疑难时能看到的线索，可能把"能揪出的错"变成"揪不出"。

**风险**：中。精校质量是这个模块的命根子，宁可慢也不能漏错。

**怎么验**：取同一真实场次、同一模式，改前改后各跑一次，**逐窗口比对精校文本差异**，再人工抽查被改动过的窗口是否变差。质量不降才留，降了就退回。

### 2c　窗口并发 3 → 5（最后，先测）

**现象**：窗口裁决默认并发 3（`精校裁决.py`）。

**为什么排最后**：本模块**已有一次实打实的反面教训** —— 提交 `85a2940` 标题就是"并发场次默认改回 1 —— 实测场间并发反而更慢"。原因是提供端并发上限有限（MLX Whisper 资源预算为 1），盲目压并发会撞上游限流（503）反而整体更慢。

**改法**：**先测再改**。加一次 3 / 4 / 5 的对照实测，看是否触发上游 503、看总耗时是否真的下降；只有**明确不触发限流且总耗时下降**时才提默认值。窗口并发与场间并发不是同一回事，但同一个上游，必须用数据说话。

**风险**：中。可能反而更慢，且失败发生在长场次跑到一半时。

## 五、提速项 3：进程冷启动（大部分本来就常驻）

### 现象

"冷启动慢"多半是**误判**：平台该常驻的本来就已经常驻 ——

| 已常驻的东西 | 说明 |
|--------------|------|
| 网关 40007 | 常驻进程（`lsof -nP -iTCP:40007 -sTCP:LISTEN` 有命中；**PID 随每次重启变化**，2026-09-16 23:56 实测为 29372，不要照抄旧 PID），且有**热接入**：改包后发 `{"操作":"热接入"}` 增量重装配（脚本入口 `运维脚本/热接入.py`），2026-09-16 实测单次 **316.85 毫秒**、**不重启进程**（见 `开发文档/决策记录/0008_能力更新走热接入不重启网关.md`） |
| 代码地图 | 常驻的单个 SQLite（`.codegraph/codegraph.db`，实测 34,689,024 字节 ≈ 33.1 MiB），已有节点/边/文件指纹 |
| 平台状态库 | 常驻的单个 SQLite（包落点实测为目录 `平台控制面/平台状态/`：`实现/状态存储.py`；旧的单文件路径 `平台控制面/平台状态（包）` **已不存在**） |

> 旧表里还有一行「管理端 8766｜常驻进程；工具实现改动现已热加载」，**该服务与 `MCP工具箱/` 已整体删除（2026-09-15）**，行已移除。

### 真正缺的是什么

**缺的不是"再起一个常驻"，而是"审计工具去读这些常驻，而不是每次重新算一遍"。** 下面两个缺口里，第一个已经补上了：

提速项 3-1：~~**代码地图没有 Python 直读器**~~ **已落地（2026-09-16 实测）**：代码地图现在有正式支持库包 `支持库.后端.代码解析支持库.代码地图`（1.0.1），暴露 `代码解析支持库.代码地图.查询节点` / `代码解析支持库.代码地图.查询关系`；实现 `实现/只读连接.py` 用标准库 `sqlite3` 以 `mode=ro&immutable=1` 只读打开（不建 WAL/-shm 旁文件、不写别人的索引目录）。经 40007 实调 `查询节点`（参数 `代码地图路径=.codegraph/codegraph.db`）返回 `成功=true`、`耗时毫秒=124.2`。旧描述里的 `MCP工具箱/项目服务.py` 已随目录删除。
提速项 3-2：**长任务不再占用同步调用**。旧口径说"本仓没有后台作业能力、45 个工具里没有 `tool_job_submit`"——**该口径整体失效**（8766 管理端与那套工具已删除）。现在长任务走**网关任务三操作**：`任务提交`（当场返回任务 id）→ `任务查询`（轮询状态：等待中/运行中/成功/失败/已取消/超时/崩溃）→ `任务取消`，三者实测都在 `运行核心/统一网关/网关核心.py:52-53` 的允许操作表内。注意它们是**网关操作名**，不是工具名，也不是能力 id。用法见 `开发文档/规范/网关调用最小示例.md`「长任务：提交 → 轮询 → 取消」。

### 改法优先级

提速项 3-3：**立刻用**：长命令（全量冒烟、发布门控、并行测试、静态检查、模块热插拔检查）**与别的会话错峰跑**（别同时触发），减少网关侧排队；量级到十几秒以上的活改走网关 `任务提交`（第 3-2 条），别再同步硬扛。
提速项 3-4：**已落地**：代码地图只读直读已作为正式能力落地（`代码解析支持库.代码地图.查询节点` / `查询关系`，标准库 `sqlite3`，见第 3-1 条）；审计工具可以直接调它，不必自己起 codegraph 进程。口径更新：正式根下的 `.py` 实测 **645** 个（旧文写的 564 已过期）。
提速项 3-5：**不建议做**：再复制一份仓库副本搞"离线环境"。平台是"网关 40007 + 数据库 + 编译产物"一体的，副本里跑不了验证，改完还要合回主仓、合并照样冲突。详见 `开发文档/规范/多会话并行开发规约.md`。

## 六、重启纪律（与热接入配套）

现在需要重启的只剩**网关自身代码变更**与**部署配置变更**（换端口/换凭证）；能力代码（新增包/改实现/改契约）一律走 `热接入`，即时生效、不打断在跑调用。另外：旧文括号里提到的**文件租约强制化**、**收口指纹修复**两项改动，其载体（`MCP工具箱/` 下的文件租约与项目服务）**已整体删除**，不再属于本方案范围。

规矩：

规则 1：**能热接入就不重启**（改能力 → 发一次 `{"操作":"热接入"}`，再核对返回的 `已注册能力数` 与 `失败包`）。
规则 2：**必须重启的，凑成一批、一次性重启** —— 不随改随重启，重启前先确认无在跑任务。
规则 3：**重启前先确认无在跑长任务**：网关侧有长任务（`任务查询` 能查到 运行中）时禁止重启（2026-09-10 两次实测教训，见 `未完成事项.md`）。
规则 4：**批次内的改动全部落盘、编译通过后再重启**，重启后立即做一次冒烟复核（`GET /健康` 带凭证应为 200）。

## 环境与工具：装还是不装（2026-09-15 实测判定，依据第 11 条 1 项）

**判据**：对比现状，是否更快、更稳定；拿不出数字不许装。

### 实测数据

| 项 | 现状 | 候选 | 差距 | 结论 |
|---|---|---|---|---|
| 全仓搜索同词 | `grep -rn` 全仓 **6.35s** | `rg` 全仓 **0.075s** | **85×** | **改规则**（不装，`rg` 本机已装 `/opt/homebrew/bin/rg`） |
| 同范围搜索（都带排除） | `grep` 0.087s | `rg` 0.049s | 1.8× | 差距不大，**范围才是主因** |
| 文件列举 | `find` 0.064s | `rg --files` 0.027s | 2.3× | 可用 `rg --files` 替 `find` |
| 限时执行 | `python subprocess(timeout=)` | GNU `gtimeout` | 无 | **不装 coreutils** |
| 并行执行 | Hermes 子代理 | GNU `parallel` | 无 | **不装** |

### 真正的耗时来源（2026-09-15 实测）

- 全仓 **158,218 个文件 / 5.0GB**，其中 **154,395 个（97%）在 `工程缓存/`（4.9GB）**；源码本体只有约 40MB。
- `工程缓存/` 构成：**提供者运行环境 4.4GB**、**制品仓库 352MB**、HTML验证证据 74MB、验证缓存 13MB、编译缓存 12MB。
- **制品堆积**：`工程缓存/制品仓库/平台客户端制品/` 现存 **18 份**平台客户端制品（每份 15–16MB，合计约 280MB）——**每重编一次多一份，无回收**。老制品对运行态无用（激活指针只指一份），但会拖慢全仓扫描、占盘、干扰取证。
- 结论：对本项目而言，**收益最大的动作是「全仓搜索用 `rg` + 带排除」和「回收过期制品」**，而不是安装新命令。

### 已落地规则

- 全仓/大范围搜索**一律用 `rg`**；必须用 `grep` 时**必须带** `--exclude-dir=.git --exclude-dir=工程缓存 --exclude-dir=__pycache__ --exclude-dir=.venv --exclude-dir=node_modules`。
- 制品回收走平台自身的资源回收能力（不在本文件手工删文件）；过期制品清理列进 `未完成事项.md`。
