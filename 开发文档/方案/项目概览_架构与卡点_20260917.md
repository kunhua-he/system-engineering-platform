```
  · 缺「故意弄坏 → 必须报红」的体系
  · 多数正向步骤只验类型/字段形状（要数字：读 HTML 验证证据 json）
  · 能力零验证场景：实测 0 条（664/664 全覆盖；旧值 158 系算法漏读已纠偏）
```

## ★ 活的证据（本会话实测，最硬的一条）

```
同一仓库、相邻时点：
  发布门禁      → 发布状态：通过      72 项 ✓ / 0 红
  测试体系门禁  → 失败！1 项新增红
                  190 测试文件 / 2139 用例 / 真跑 189-190

⇒ 「发布门禁通过」≠「仓库健康」
  那道真正在跑 2139 个用例的门禁，压根不在发布链里，而它当时是红的。
```

```
  │                             · 三档阈值 high / low / break
  │                             · break 默认 null（不阻断）是显式配置
  │
  └─ D 反向证明 ───────────── cosmic-ray
                                · 样本是算子的「接口义务」examples()
                                · 元测试自动遍历「全部算子 × 全部样本」
                                · 忘带样本 = 自动失败
                              LitmusChaos
                                · 探针 SoT/EoT：破坏前确认是绿的、
                                  破坏后确认是红的
  ↓
落到本项目就三句话：
  ① 判据 = 跑完生成器后「无 diff」；生成物带输入指纹
  ② 强制点必须在必经路径；「跑了但没拦」是显式状态
  ③ 样本是接口义务，元测试自动遍历
```

## 三条"元教训"（这轮最值钱的）

```
① 判据存在 ≠ 有人强制
   pre-commit 实测可被 git commit --no-verify 完全绕过
   ⇒ 任何"靠记得跑"的检查都不算强制点

② 样本/证据应该是「接口义务」，不是另维护一张表
   cosmic-ray 的算子不写 examples() 就是实现不完整；元测试遍历所有算子
   ⇒ 忘带样本 = 自动失败。这才是"不挤牙膏"的机制内核

③ 用连续量 + 分档表达质量水位，不用"通过/失败"二值
   stryker high/low/break；dependency-cruiser error/warn；conftest 双跑
```
