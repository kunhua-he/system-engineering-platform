### 1.2 发布门禁的 56 个检查项：**57 项全部默认阻断**

```
检查() 签名：def 检查(名称: str, 通过: bool | None, 详情: str = "", 强制: bool = True)
实测：显式 强制=False → 仅 1 项（"契约声明一致（注册口径，只报）"）
      其余 56 项全部用默认值 强制=True（阻断）
```

**⇒ 结构上"门禁是严格的"** —— 但问题不在单点严格性，而在**两处"整体降级"**：

```
① 测试伪装门禁：接入口径 = 「只报告 + 硬限制不得增加」
   判据 `计数 <= 存量违约上限(271)`；实测当前 269 项 → 判绿
   ⇒ 一个"通过"实际含义是「没比历史更差」，不是「零违规」

② 公开调用完整性门禁：同形，存量基线 23 项，基线外新增才红
```

**⇒ 这正是报告②说的「三种绿色用同一个『通过』词」的具体落点。**
**⇒ 与已落盘的 B2（门禁语义分裂）同源，本轮补上了精确数字与实现位置。**

### 1.3 门禁之间的**重叠/依赖关系**（新发现，**已确认**）

```
发布门禁
 ├─ 直接内含 56 项（含 HTML 黑盒、依赖锁、签名、平台治理…）
 ├─ 接入 测试伪装门禁（经 `校验测试伪装()`，只报告 + 硬上限 271）
 ├─ 接入 公开调用完整性门禁（经 `运行公开调用门禁`，存量基线 23）
 └─ ✗ 未接入 测试体系门禁
```

**★ 实测确认（一条命令定死）**：
```
发布门禁 主函数 epilog 原文自述：
  「本门禁不执行全量 unittest（**测试体系门禁仍需单独手工执行**，
    它含 2026-09-17 新增的「真跑」项）」

而 `测试体系门禁.py` 自带完整判据 + argparse CLI（413 行、13 函数、5 处检查）
⇒ **这是"有判据、无强制点"的第二个实例**（与 B1「契约变更判定未接门禁」同型）。
```

**⇒ 影响**：发布门禁跑绿 ≠ 测试体系没问题 —— 因为**它压根不在发布门禁的执行链里**。
**⇒ 与 B2「门禁通过语义分裂」叠加后**，一个"发布门禁通过"实际可能同时意味着：
① 56 项真过了；② 测试伪装"没比 271 更差"；③ 公开调用"没比 23 更差"；
④ **测试体系门禁根本没跑**。

> **这条是本轮最有价值的发现**：它不是"某个判据写错了"，而是**"验收链有缺口"** ——
> 四道门禁里有一道从不参与发布判定，而文档与 README 都写着"发布门禁通过"。

## 七、★ 活的证据：发布门禁通过的同时，测试体系门禁是红的（2026-09-17 实测）

### 7.1 实测记录（两份门禁，同一仓库、相邻时点）

```
发布门禁（HEAD c9f84c3d 时跑）  → 发布状态: 通过    72 项 ✓ / 0 红
测试体系门禁（HEAD 76ae77c6 时跑）→ 失败：1 项新增红
   [红·新增违规] 测试中心.第一批维修.测试_模型连接器通用协议 — 退出码 1
   Ran 14 tests in 7.078s   FAILED (failures=1)
```

**⇒ 结论**：**「发布门禁通过」并不等于「仓库健康」** —— 因为测试体系门禁
（190 个测试文件、2139 个用例、真跑 189/190 通过）**压根不在发布门禁的执行链里**。
这正是 §1.3 推断的「验收链有缺口」，本轮拿到了**活的证据**。

### 7.2 那条红的根因（**本会话自己引入的，已定位到具体提交**）

```
期望调用: 启动本地模型(..., 参数={'协议': 'codex_responses'}, 超时秒=60)
实际调用: 启动本地模型(..., 参数={'协议': 'codex_responses', '上下文长度': None}, 超时秒=60)

根因：提交 `c0735582`（模型连接器「参数收了不用」修复）在 `连接LLM` 里
      新增了 `参数={"协议": 协议, "上下文长度": 上下文长度}`（模型连接器.py:446），
      但 `测试_模型连接器通用协议.py:203` 的 `assert_called_once_with()` 期望值没跟着更新。
```

**这条红本身就是「生成物/期望值未随源同步」的又一实例** —— 与本批卡点 A 同源
（改源 → 有生成物/期望值要跟着改 → 漏了）。**说明该问题形态会反复出现，不是个别现象。**

### 7.3 这条证据对决策的意义

```
① 它把 §1.3「有判据、无强制点」从"推断"升级为"实测"：
     四道门禁里有一道从不参与发布判定，而 README 与文档都写着"发布门禁通过"。

② 它也证明**测试体系门禁本身是有效的**（它真的抓到了我引入的红）——
     所以正确处置不是"删掉它"，而是"把它接进必经路径"。

③ 按本轮约束（华哥：不维修，只审计），**本条只登记不修**。
     登记位置：§8.3 待修（修法两件：① 修那条测试期望；② 把测试体系门禁接入发布门禁或
```
