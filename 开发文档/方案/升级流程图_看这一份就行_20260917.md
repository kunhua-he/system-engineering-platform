# 图 2｜升级前 vs 升级后（一眼对照）

```
【生成物】（卡点 A）
    现在     改 1 个源文件 → 手动联动 6 份生成物
             139 个包 ≈ 834 个同步点；靠记性 → 漂移 85 次
    升级后   跑一条命令 → 门禁校验「重算后无 diff」
             生成物带输入指纹，能报出「哪个输入变了」

【规则】（卡点 B）
    现在     有哲学 5.3 ✓  有判据模块 ✓  有单测 ✓
             但发布门禁 0 命中 ✗（靠人记得跑）
    升级后   发布门禁有强制点 ✓
             忘了接门禁 = 门禁自己报红

【门禁结论】（卡点 C）
    现在     一个「通过」同时表示两件事：
                 ① 零违规      ② 未比基线更差
    升级后   四个词，各是各的：
                 干净通过 / 债务冻结 / 未核验 / 失败
             「是否阻断」是显式配置项（可设"不阻断"）

【反向证明】（卡点 D）
    现在     缺"弄坏→报红"体系
             264/742 步只验形状；158/664 能力零场景
    升级后   每个检查项自带样本（接口义务）
             元测试自动遍历全部项 × 全部样本；漏带样本 = 自动失败
             破坏前断言绿 / 破坏后断言红 / 恢复后断言回绿

【架构】
    现在     轻量能力也 fork 进程（约 20MB/次）
    升级后   加「执行模型: 线程|进程」→ 轻量走线程池，快约 10 倍
```

# 图 3｜四个卡点的升级动作（逐个：现状 → 改什么 → 升级后）

```
【卡点 A】生成物手工同步
  现状
    · 改 能力定义.json → 要手动跑 5 个生成器，联动 6 份生成物
    · 靠记性；顺序还有讲究（先子包后父包）
    · 实测漂移 85 次 / 重算摘要 50 次 / 父包 42 次
  改什么
    ① 新增「一键再生成」入口：把 5 个生成器的顺序固定下来
    ② 6 份生成物头部加标记：勿手改｜生成器=X｜输入指纹=Y
    ③ 发布门禁加一项「生成物新鲜度」：
         判据 = 跑完全部生成器后，git status 必须干净
  升级后
    改 1 个源 → 跑 1 条命令 → 门禁自己证明"文件与源一致"
    不一致就报红，并指出是哪份生成物、哪个输入变了

【卡点 B】规则没有强制点
  现状
    · 判据模块写好了（对外契约变更判定 / 测试体系门禁 / 公开调用门禁）
    · 但发布门禁里 0 命中，或明文"需单独手工执行"
  改什么
    ① 发布门禁加一项「判据引用自检」（元检查）：
         扫全部判据模块 → 逐个查"是否被发布门禁或 CI 引用"
         没被引用的 → 报红（或白名单+理由）
    ② 「测试体系门禁」接进发布门禁（它现在跑 2139 个用例，却不在发布链里）
  升级后
    新增判据没接门禁 = 门禁自己报红
    "发布门禁通过"这句话，才真的等于"仓库健康"

【卡点 C】门禁「通过」语义分裂
  现状
    · 56 项严格检查判「零违规」，也输出"通过"
    · 271 项存量 / 23 项存量判「未比基线差」，也输出"通过"
  改什么
    ① 门禁结论改四态，四态各有其词，不共用
    ② 输出结构化变更摘要（对齐 terraform change_summary）：
         { 能力新增/移除/契约变更/生成物变化/依赖变化/文件增减 }
         { verdict: 干净通过N / 债务冻结M / 未核验K / 失败0 }
         { 制品摘要：前一版 → 本版 }
    ③ 加 --模拟 模式：构造变更 → 问"会怎么判" → 不写回真实状态
  升级后
    看门禁输出就知道"这次改了什么、判了什么、拦没拦"

【卡点 D】反向证明不足
  现状
    · 门禁项 56 个，但没一个能证明"它真的拦得住"
    · 264/742 步只验形状；158/664 能力零场景
  改什么
    ① 每个门禁项自带 ≥1 个「应被拦住」样本 + ≥1 个「不应触发」样本
    ② 元测试自动遍历「全部检查项 × 全部样本」
    ③ 样本声明三段断言（对齐 Litmus 探针）：
         前置：当前是绿的（防假红）
         后置：破坏后是红的（防空转）
         恢复：恢复后回到绿（防粘滞）
  升级后
    新增检查项不带样本 = 元测试失败
    每个门禁项都有"拦得住"的实证
```

# 图 5｜三个核心机关的升级细节（升级的"发动机"）

```
【机关 1】规则三要素（P-3）—— 让"纸面规则"自己冒出来
  一条规则 =
     ① 判据实现   ← 文件:函数
     ② 强制点     ← 哪个门禁的哪一项（或"人工治理"）
     ③ 反向试验   ← 哪个破坏样本
  缺任何一列 → 门禁的「总账自证」项报红
     外部依据
       · OPA：策略即门禁 + 策略自带测试 + 接 CI 必经路径
       · pre-commit 的反面：本地钩子可被 --no-verify 绕过

【机关 2】门禁四态（P-4）—— 让"通过"不再骗人
  四个词，永不共用一个词：
      干净通过 / 债务冻结 / 未核验 / 失败
  「是否阻断」= 显式配置项（可设"不阻断"）
     外部依据
       · dependency-cruiser：同一套规则 + error / warn 两档预设
       · stryker：high / low / break 三档（break 默认 null = 不阻断）
       · GitHub Rulesets：Evaluate 模式 = 跑了但没拦（官方一等公民状态）
       · conftest：同一工具跑两遍（警告级 + 阻断级）

【机关 3】生成物三律（P-5）—— 让漂移物理上不可能
  ① 生成物带输入指纹（源摘要 + 生成器版本 + 契约版本）
  ② 生成物带「勿手改」机器可识别标记
  ③ 判据 = 跑完全部生成器后，工作区无 diff
     外部依据
       · kyverno：make verify-codegen，判据原文 "exits cleanly with no git diff"
       · please：任何影响产物的都要折进 hash
       · terraform：AssertObjectCompatible(计划, 实际)

【机关 4】样本是接口义务（P-6）—— 让"拦不住"自己暴露
  每个检查项必须实现 取样() → 返回"应拦"/"不应触发"样本
  元测试遍历「全部检查项 × 全部样本」
     外部依据
       · cosmic-ray：examples() 是算子接口义务 + 元测试遍历全部算子
       · ArchUnit：@ArchTest（规则即测试）
       · Litmus：探针 SoT/EoT/Edge（破坏前断言绿 / 破坏后断言红）
```

# 图 6｜升级验收路线（每步怎么证明升级成了）

```
批 1 哲学            → 哲学正文零冲突条款；每条要么现行、要么带废止声明
                       验：机械扫"冲突对"归零；条款数从 49 降到约 42

批 2 总账            → 每条规则都能指出"谁在强制它"
                       验：总账自检项跑通；指不出强制的规则全部显式列名

批 3 门禁自证        → 不存在"有判据没强制点"的规则
                       验：① 发布门禁跑出四态而非二值
                           ② 判据引用自检项有输出（含白名单+理由）
                           ③ 故意摘掉一个门禁项引用 → 门禁报红

批 4 生成物          → 改源不改生成物 → 门禁必红
                       验：① 改 1 个包内文件不重算 → 报"新鲜度不一致"
                           ② 手改一份生成物 → 报"被手改"
                           ③ 正常重算 → 无 diff，通过

批 5 自动生成        → 人不用记
                       验：改源后一条命令 → 生成物全部同步；git 干净

批 6 破坏样本        → 每个门禁项有"拦得住"的实证
                       验：① 元测试遍历全部项×全部样本，全过
                           ② 新增一个检查项不带样本 → 元测试报红
                           ③ 抽查 3 项：破坏前绿 / 破坏后红 / 恢复后绿

批 7 代码修复        → 28 项真缺陷清零
                       验：① 高危两条做故障注入复现（改前会丢数据/丢环境）
                           ② 装配 664 能力、跳过包 0
                           ③ 环境自检退出码 0、摘要全闭合

全局                 → 制品重编 → HTML 黑盒 → 发布门禁 → 破坏矩阵
                       验：发布门禁四态输出；测试体系门禁也在链里（不再手工）
```

# 需要你拍板的（升级的前置）

```
① 哲学空间设不设硬上限（如主条 ≤12、子项 ≤6）
② 决策记录要不要限短篇（≤50 行）
③ 废止声明写法（推荐：标作废 + 保留原文 + 写废止于哪条）
④ 总账 vs 项目说明 的分工（推荐：总账=机读唯一源，哲学章由它生成）
⑤ 存量债务设不设收敛期限（不设的话 271 会永远停在 271）
⑥ 生成物路线（推荐 A+C：提交时自动生成 + 门禁校验兜底）
⑦ 批 7 代码缺陷是否先修不等总纲（推荐：先修那两条高危）
⑧ 卡点 D（破坏样本）做还是先放未来
    第六份材料主张"未来再说"；本轮研究主张"不能省"——理由见图 3 卡点 D
⑨ 契约兼容分档（冻结/兼容/开发）是否采纳
⑩ 兼容档位是否写进包声明（会动契约）
```
