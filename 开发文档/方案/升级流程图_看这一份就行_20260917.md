# 图 2｜升级前 vs 升级后（一眼对照）

```
【生成物】（卡点 A）
    现在     改 1 个源文件 → 要手动跑多个生成器、联动多份生成物
             顺序有讲究（先子包后父包）；全靠记性
             要数字：`ls <包目录>/*.json | wc -l`
    升级后   跑一条命令 → 门禁校验「重算后无 diff」
             生成物带输入指纹，能报出「哪个输入变了」

【规则】（卡点 B）
    现在     判据模块写好了（有实现、有单测）
             但发布门禁不调用它 → 靠人记得跑
             要数字：`rg -n '^\\s*(from|import)' 开发工具/发布门禁/运行发布门禁.py`
    升级后   发布门禁有强制点
             新增判据没接门禁 = 门禁自己报红

【门禁结论】（卡点 C）
    现在     一个「通过」同时表示两件事：
                 ① 零违规   ② 未比基线更差（债务冻结）
    升级后   五个词，各是各的：
                 干净通过 / 债务冻结 / 只报告 / 未核验 / 失败
             「是否阻断」是显式配置项（可设"不阻断"）

【反向证明】（卡点 D）
    现在     缺"弄坏→报红"体系
             多数步骤只验类型/字段形状，没验业务结果
             要数字：`工程缓存/HTML验证证据/<摘要>/验证证据_*.json`
    升级后   每个门禁自带样本（接口义务）
             元测试自动遍历全部项 × 全部样本；漏带样本 = 自动失败
             三段断言：破坏前绿 / 破坏后红 / 恢复后回绿

【执行模型】
    现在     轻量能力也 fork 进程
    升级后   加「执行模型: 线程|进程」→ 轻量走线程池
             （量化收益须现场基准测试，本文件不写倍数）
```

# 图 3｜四个卡点的升级动作（逐个：现状 → 改什么 → 升级后）

```
【卡点 A】生成物手工同步
  现状
    · 改 能力定义.json → 要手动跑多个生成器，联动多份生成物
    · 靠记性；顺序有讲究（先子包后父包）
    · 历史证据：提交信息里大量"漂移/重算摘要/父包"字样
        取证：`git log --oneline | rg -c '漂移|重算摘要|父包'`
  改什么
    ① 新增「一键再生成」入口：把生成器顺序固定下来
    ② 生成物头部加标记：勿手改｜生成器=X｜输入指纹=Y
    ③ 发布门禁加「生成物新鲜度」：
         判据 = 跑完全部生成器后，工作区必须无 diff
  升级后
    改 1 个源 → 跑 1 条命令 → 门禁自己证明"文件与源一致"
    不一致就报红，并指出是哪份生成物、哪个输入变了

【卡点 B】规则没有强制点
  现状
    · 判据模块写好了（对外契约变更判定 / 能力调用图审计 / 反向破坏 …）
    · 但发布门禁不 import 它们 → 零调用
        取证：`rg -n '^\\s*(from|import)' 开发工具/发布门禁/运行发布门禁.py`
        判断法：**看 import，不看字面出现** —— 发布门禁里"反向破坏""确定性"
                "测试体系门禁"都字面出现过，但全是帮助文本/枚举清单，零调用
  改什么
    ① 发布门禁加「判据引用自检」（元检查）：
         扫全部判据模块 → 逐个查"是否被发布门禁引用"
         没被引用的 → 报红（或白名单 + 理由）
    ② 「测试体系门禁」接进发布门禁
  升级后
    新增判据没接门禁 = 门禁自己报红
    "发布门禁通过"这句话，才真的等于"仓库健康"

【卡点 C】门禁「通过」语义分裂
  现状
    · 严格检查判「零违规」，输出"通过"
    · 存量基线判「未比基线差」，也输出"通过"
    · 一个词两种含义 → 无法区分"真干净"和"带着债"
  改什么
    ① 门禁结论改五态，各有其词，不共用
    ② 输出结构化变更摘要（对齐 terraform change_summary）：
         { 能力新增/移除/契约变更/生成物变化/依赖变化/文件增减 }
         { verdict: 干净通过N / 债务冻结M / 只报告K / 未核验J / 失败0 }
         { 制品摘要：前一版 → 本版 }
    ③ 加 --模拟 模式：构造变更 → 问"会怎么判" → 不写回真实状态
  升级后
    看门禁输出就知道"这次改了什么、判了什么、拦没拦"

【卡点 D】反向证明不足
  现状
    · 门禁项不少，但没几个能证明"它真的拦得住"
    · 许多步骤只验形状，没验业务结果
  改什么
    ① 每个门禁项自带 ≥1 个「应被拦住」样本 + ≥1 个「不应触发」样本
    ② 元测试自动遍历「全部检查项 × 全部样本」
    ③ 样本声明三段断言（对齐 Litmus 探针）：
         前置：当前是绿的（防假红）
         后置：破坏后是红的（防空转）
         恢复：恢复后回到绿（防粘滞）
  升级后
    新增检查项不带样本 = 元测试失败
    每个门禁项都有"拦得住"的实证
```

# 图 5｜核心机关的升级细节（升级的"发动机"）

```
【机关 1】规则三要素（P-3）—— 让"纸面规则"自己冒出来
  一条规则 =
     ① 判据实现   ← 文件:函数
     ② 强制点     ← 哪个门禁的哪一项（或"人工治理"）
     ③ 反向试验   ← 哪个破坏样本
  缺任何一列 → 门禁的「总账自证」项报红
     外部依据
       · OPA：策略即门禁 + 策略自带测试 + 接 CI 必经路径
       · pre-commit 的反面：本地钩子可被 --no-verify 绕过

【机关 2】门禁五态（P-4）—— 让"通过"不再骗人
  五个词，永不共用一个词：
      干净通过 / 债务冻结 / 只报告 / 未核验 / 失败
  「是否阻断」= 显式配置项（可设"不阻断"）
     外部依据
       · dependency-cruiser：同一套规则 + error / warn 两档预设
       · stryker：high / low / break 三档（break 默认 null = 不阻断）
       · GitHub Rulesets：Evaluate 模式 = 跑了但没拦（官方一等公民状态）
       · conftest：同一工具跑两遍（警告级 + 阻断级）

【机关 3】生成物三律（P-5）—— 让漂移物理上不可能
  ① 生成物带输入指纹（源摘要 + 生成器版本 + 契约版本）
  ② 生成物带「勿手改」机器可识别标记
  ③ 判据 = 跑完全部生成器后，工作区无 diff
     外部依据
       · kyverno：make verify-codegen，判据原文 "exits cleanly with no git diff"
       · please：任何影响产物的都要折进 hash
       · terraform：AssertObjectCompatible(计划, 实际)

【机关 4】样本是接口义务（P-6）—— 让"拦不住"自己暴露
  每个检查项必须实现 取样() → 返回"应拦"/"不应触发"样本
  元测试遍历「全部检查项 × 全部样本」
     外部依据
       · cosmic-ray：examples() 是算子接口义务 + 元测试遍历全部算子
       · ArchUnit：@ArchTest（规则即测试）
       · Litmus：探针 SoT/EoT/Edge（破坏前断言绿 / 破坏后断言红）

【机关 5】豁免自身也要被检查 —— 补上存量基线最大漏洞
  ① 豁免必须带理由（无理由 = 报错）
  ② 已不再被触发的豁免 = 空转 = 报错要求删除
  ③ 默认值分级：能机器判定的默认 error，需人判断的默认 off
     外部依据
       · tach：unused_ignore_directives（默认 warn）
              require_ignore_directive_reasons（默认 off）
              unused_external_dependencies（默认 error）
     为什么重要
       存量基线现在只管"不得增加" → 修好的存量若不删，会永远挂着，
       没人发现它已经不需要了
```

# 图 6｜升级验收路线（每步怎么证明升级成了）

```
批 1 接线      → 改契约不升版本 → 发布门禁报红
                 验：故意把某能力参数类型改掉且不递增版本 → 门禁红
                 验：出现第二套实现 → 门禁红
                 验：破坏门禁自身 → 反向破坏用例红

批 2 生成物    → 改源不改生成物 → 门禁必红
                 验：① 改 1 个包内文件不重算 → 报"新鲜度不一致"
                     ② 手改一份生成物 → 报"被手改"
                     ③ 正常重算 → 无 diff，通过
                 验：改源后一条命令 → 生成物全部同步；git 干净

批 3 破坏试验  → 每个门禁项有"拦得住"的实证
                 验：① 元测试遍历全部项×全部样本，全过
                     ② 新增一个检查项不带样本 → 元测试报红
                     ③ 抽查 3 项：破坏前绿 / 破坏后红 / 恢复后绿

批 4 豁免自检  → 制造一个空转豁免 → 门禁要求删除
                 验：豁免无理由 → 报红；豁免已不触发 → 报红

批 5 收口      → 四个判据全绿
                 验：四判据逐条跑通并出总账

并行 代码修复  → 高危两条做故障注入复现（改前会丢数据/丢环境）
                 验：① 故障注入复现成功
                     ② 环境自检退出码 0、摘要全闭合
                        （数字现场取值：`python3.14 开发工具/环境自检.py`）

全局           → 制品重编 → HTML 黑盒 → 发布门禁 → 破坏矩阵
                 验：① 发布门禁输出五态（不是二值）
                     ② 测试体系门禁在链里（不再手工）
                     ③ 黑盒证据：`工程缓存/HTML验证证据/<摘要>/验证证据_*.json`
                        （场景数/步骤数/失败数现场读该文件，不抄旧值）
```
