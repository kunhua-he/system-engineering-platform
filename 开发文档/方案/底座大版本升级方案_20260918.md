## 一、这一版要解决什么（一句话）

**把底座从「能自证」推进到「机器强制」** —— 同一件事只有一种表达，判据住在它该管的那一层并在产出点执行，门禁覆盖真实必经路径。

**为什么是这个主题**：盘点 §8.3 待修 49 条 + §8.4 大项 9 条，逐条归因（哲学 14.1）后，**四类反复出现**：

| 归因 | 实测条数（示例） | 本质 |
|---|---|---|
| ② **架构错位**（判据住错层 / 表达不统一 / 门禁没接） | 依赖锁空锁、两处同名 `当前.json`、包根 vs 目录契约件、旧能力 id 残留、`追加字节数` 名实不符、18 条半强制 | **同一件事多种表达 + 判据只挂下游** |
| ① **原子能力不足** | 清单条目管理、记忆派发、激活指针 3 条、能力搜索硬上限 | 能力面缺东西 |
| ③ **单点缺陷** | 解压回滚删原文件、`原子落盘` 先删旧环境、A1 嵌套事务、SSRF 未绑定、4 处无界登记表 | 就地修即可 |
| **重构类（骨架重排）** | D-1 适配层唯一化、E-6 裸布尔、E-8 类型体系、D-6/D-5/D-14 | 不是缺陷，是**形态升级** |

**结论：③ 单点缺陷走日常维修即可（本轮已派 23 路覆盖 27 条）；① 补能力面；真正决定"这一版成不成"的是 ② 与重构类。**

## 二、版本范围（进 / 不进）

```text
进 v2.0：
  ① 门禁接线      —— 18 条半强制 → 机器强制（§8.4 第 5 项「卡点 B」，最要紧）
  ② 表达收口      —— 把所有「同一件事多种表达」清零（②类错位逐条收口）
  ③ 能力面补齐    —— 清单条目管理（已派）、记忆派发（已立项）、激活指针 3 条、能力搜索分页
  ④ 重构三件      —— D-1 适配层唯一化 / E-6 裸布尔迁移 / E-8 类型体系收口（风险最高，放最后）
  ⑤ 文档总纲      —— 架构文档总纲级重写 + 测试中心按能力域归口

不进 v2.0（另议）：
  · 业务侧任何东西（V3 / 人脉数据系统 / 俏小喵课件站）—— 底座与业务切割，业务数据不倒灌
  · 新的第三方接入（没有真实调用方就不接）
  · 只报告类项目（如说明书分母口径），随对应批次捎带，不单独立项
```

## 三、批次与依赖（唯一主线）

```text
批 0  收口当前轮（不属 v2.0 内容，是 v2.0 的起点）
     本轮 23 路回传 → 逐份现场验收 → 全仓统一重算摘要 → 债务清单校正 → 提交
     └─ 出口判据：工作树干净 + 装配跳过包 0 + 门禁无新增违规 + 摘要全仓闭合

批 1  门禁接线（18 条半强制 → 机器强制）              ★ 最要紧，先做
     判据本体都已在（缺的是"接到必经路径上"）：
       · 三项防回潮（裸布尔 / 非正式类型名 / 英文错误码）→ 发布门禁
       · 能力 id「只增不改」+ 冻结基线（基线缺失 fail-closed）
       · 场景覆盖率、说明书字段、消费者契约「必须有登记」的反向断言
       · 判据归位之后新增的每一条，都必须同批接进发布门禁
     └─ 出口判据：一条判据一个「故意弄坏必报红」样本，元测试遍历「全部检查项 × 全部样本」

批 2  表达收口（②类错位清零）
     逐条把「同一件事多种表达」收敛成一种，并**在生成侧堵住**（哲学 14.2）：
       · 「无第三方依赖」只允许一种表达（不建锁）——已修，列为样板
       · 两处同名 `当前.json` schema 收口为一套；制品积压接进必经路径
       · 包根契约件 vs 目录契约件（模板侧已修，存量已修）
       · 旧能力 id 残留、`追加字节数` 名实不符（只改能力定义，派生物跑编译同步）
       · 4 处无界登记表统一为有界 deque
     └─ 出口判据：每条给出「收口前两种表达 → 收口后一种表达」的前后对照 + 一条防复发门禁

批 3  能力面补齐（①原子能力不足）
      已派/已立项：清单条目管理（在跑）、记忆派发（已立项，待实现）
      待立项：3 条激活指针能力、能力搜索分页（去硬编码上限 100）
     └─ 出口判据：新能力经 40007 真实 HTTP 验收（不再只跑单测）
     └─ 依赖：批 1 的"能力登记门禁"先就位，新能力才不会被漏登记

批 4  重构三件（骨架重排，风险最高 → 放最后）
      D-1 适配层唯一化 → E-6 裸布尔迁移 → E-8 类型体系收口
      （各自方案已出：适配层唯一化迁移清单 / 裸布尔迁移分批方案 / 类型体系收口盘点）
     └─ 出口判据：每批独立可回滚；真实 HTTP 批量并发为主验收链，单测只作辅助
     └─ 顺序理由：D-1 动依赖形态（影响面最大），E-6/E-8 动类型表达（在 D-1 稳定后做才不会被返工）

批 5  文档总纲
      架构文档总纲级重写（华哥："一次性把架构文档做好，不然每次都挤牙膏升级"）
      + 测试中心 30 个阶段目录按能力域归口
     └─ 出口判据：权威文档少而稳；每条规则能回答 13.1 三问（判据/强制点/反向试验）
```

**批次依赖一句话**：`批 0 → 批 1 → 批 2 → 批 3 → 批 4 → 批 5`，其中 **批 1 必须先于批 2/3**（门禁没接线时，收口与补能力都会被后来的改动重新打散）；批 4 必须在批 2 之后（表达不统一时做重构会返工）。

## 四、每一批的通用验收口径（不逐批重复）

| 层级 | 判据 |
|---|---|
| 单文件 | `python3.14 -m py_compile`，且**每处修复配反向验证**（故意弄坏一次、确认真的变红） |
| 工作包 | 定向 unittest 模块入口（不跑全量） |
| 批次收口 | 全仓统一 `开发工具/全量重算摘要` → **不闭合 0/N** |
| 正式验收 | **HTML 真实 HTTP 并发黑盒**（唯一允许的"全量"）+ 发布门禁 |
| 装配 | `后端核心(系统根).启动()` → 跳过包 **0**、能力数含本批新增 |

## 五、明确不做（防后患）

| 不做 | 理由 |
|---|---|
| 为"更快做完"把批 1 与批 2 并行 | 门禁没接线时，收口会被后续改动反复打散（1.3 结果唯一即收口：先定判据，再改内容） |
| 在批 4 之前顺手做局部重构 | 表达未统一时重构必然返工（本轮已有实例：改实现没同步契约导致 8 处口径不一致） |
| 用单测全绿代替真实 HTTP 验收 | 7.3：后端怎么实现 HTML 不需要知道；正式判据只认真实状态码与返回值 |
| 把"只报告"项目升级成硬门禁 | 13.2 门禁五态：「是否阻断」是显式配置项，存量未清就装硬卡子会长期满屏红 |
| 一次性跨批全派 | 12.2 的「一次性全派」指**同一批内**全派；跨批并行会打乱依赖（本方案第三节已给顺序） |
