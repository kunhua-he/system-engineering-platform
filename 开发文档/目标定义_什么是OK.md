# 二、OK 的四个判据（全部机器可判，不靠感觉）

```
① 规则可强制
     判据   每条规则能指出"谁在强制它"（判据模块 + 强制点）
     现状   49 条款：8 条机器强制 / 18 条半强制 / 24 条人工 / 3 条纸面
     目标   纸面规则 = 0
     ⇒ 允许"人工强制"，但必须写明强制者和证据

② 门禁自证
     判据   每个门禁都有"故意弄坏 → 必须报红"的证据（三拍）
     现状   0 个门禁有破坏试验；发布门禁真实强制面只有 5 个检查器
     目标   未自证门禁 = 0
     ⇒ 三拍 = 破坏前是绿 / 破坏后红 / 恢复后回绿

③ 生成物不漂
     判据   跑完生成器后 git diff 必须为空
     现状   改 1 个源文件要手工联动多份生成物（每包 10+ 份 json）
     目标   复算后 diff = 0，且报出"哪个输入变了"

④ 结论不含糊
     判据   门禁结论落在四态之一，不共用"通过"一词
     现状   当前"通过"混用（带着存量基线也报成功）
     目标   干净通过 / 债务冻结 / 只报告 / 未核验 / 失败 —— 五态分明
```

**⇒ 四条全绿 = OK 阶段。任意一条不绿 = 还没到。**

# 四、明确"不做"的（防乱飞）

```
✗ 不扩能力数量
     能力已全域覆盖（注册表与场景求交，差集为空），够用。先做闭环，不加数量。
✗ 不改架构分层
     现架构（六层 + 唯一网关 + 唯一调用腿 + 内容寻址制品）已被多份外部审计
     明确认可为"上游水平"，**不动**。
✗ 不动唯一调用腿 / 唯一网关
     调用能力(能力id, 参数) 是冻结契约，本轮不碰。
✗ 不为"完美"重写已有实现
     对外契约变更判定(44KB)、能力调用图审计、破坏验证 —— **全是现成的**，
     只缺接线。重写 = 制造第二套实现 = 违反哲学 1.3。
✗ 不引新框架/新依赖来做治理
     用底座自己的门禁体系；外部 35 个项目的机制只做"思想借鉴"。
✗ 不做"绝对安全"
     哲学 9.5：相对安全；底座只守"不造成系统性破坏"一条底线。
✗ 不引 Web 框架 / 不做服务化拆分（2026-09-17 点名）
     Flask / FastAPI、拆微服务、Alembic ORM、兼容 MCP JSON-RPC —— 四项**明确不做**。
     理由：本平台是本机能力总线（单机私有部署、唯一网关传参），不需要 Web 框架层、
     不需要进程拆分、不需要 ORM 迁移链、也不需要替外部协议做兼容壳。
```
