# 编译产物深化设计草案（简化版）

> 状态：第一批实现已落地；后续继续补充正式黑盒与发布门禁收口。
> 时间：2026-09-08
> 范围：系统工程平台底座的“源码 → 独立产物 → HTML请求 → 增量重编译”链路。

## 先说人话

华哥要的不是每次都拿源码临时运行，而是像易语言一样：

```text
源码
  ↓ 编译
独立产物
  ↓
外部程序直接使用产物
```

底座对应为：

```text
页面 / 模块 / 能力 / 支持库源码
  ↓ 编译
独立平台产物
  ↓
HTML / 外部项目 / Agent 直接请求产物
```

以后修改源码时，编译器先判断：

```text
这个源码或它引用的内容有没有变化？
  ├─ 没变化：直接使用之前的产物
  └─ 有变化：重新生成一个新的产物版本
```

HTML 永远只访问产物，不直接访问源码。

但它现在更像：

```text
每次重新打包出来的独立目录
```

还不是完整的：

```text
有版本、有缓存、有指纹、有回滚的稳定制品
```

# 三、具体产物是什么

## 1. 第一阶段产物

第一阶段选择：

```text
独立目录型稳定产物
```

它不是单个 `.exe` 或 `.dll`，但运行逻辑上已经等价于一个独立模块：

```text
开发源码不能直接被外部请求
编译产物可以直接启动
外部请求只进入产物HTTP服务
产物版本可以保留和回滚
```

当前先不急着做 `.exe` / `.dll`，因为底座里有 Provider、独立进程、系统命令和模型资源。先把“独立产物”这条链做稳定，再考虑把整个目录进一步封装成 `.pyz` 或可执行文件。

## 2. 一个稳定产物应该包含什么

```text
稳定产物/<项目id>/<制品指纹>/
├── 公共契约/
├── 后端核心/
├── 运行核心/
├── 前端核心/
├── 支持库/
├── 模块库/
├── 前端/编译页面/
│   ├── index.html
│   ├── 其他页面.html
│   ├── 路由表.json
│   └── 编译制品.json
├── 运行入口/
│   ├── 启动.py
│   ├── 启动网页.command
│   └── 启动网页.bat
├── 编译清单.json
├── 依赖锁.json
├── 制品来源.json
└── 制品完整性摘要.json
```

## 3. 产物和源码的关系

```text
源码：
  可以修改
  可以继续开发
  是编译输入

产物：
  编译后生成
  固定版本
  只读
  是运行输入

HTML：
  不读源码
  不读开发态对象
  只请求产物
```

# 四、缓存应该怎么判断

## 1. 不按文件名判断

不能只看“文件时间有没有变”，因为文件可能被恢复、复制或时间不准确。

应该看文件内容指纹：

```text
文件内容
  ↓ sha256
文件指纹
```

## 2. 不只看一个源码文件

例如修改一个支持库实现，可能影响多个模块和页面，所以要看完整依赖关系：

```text
当前目标
  ↓
目标引用的能力
  ↓
能力所属模块或支持库
  ↓
模块依赖的支持库
  ↓
Provider和运行核心
  ↓
全部依赖文件
  ↓
完整依赖闭包指纹
```

## 3. 命中缓存的条件

必须同时满足：

- 项目id相同；
- 编译目标相同；
- 目标直接和递归依赖相同；
- 依赖文件内容指纹相同；
- 编译器版本相同；
- 公共契约版本相同；
- 固定运行时版本相同；
- Provider版本和生命周期契约相同；
- 产物完整性摘要校验通过；
- 产物启动入口仍然存在。

任何一项不满足，就重新编译。

## 4. 哪些变化会触发重新编译

```text
只修改开发文档 / 测试 / 日志
  → 不影响运行产物
  → 继续命中缓存

修改页面
  → 重新生成受影响页面产物

修改模块
  → 重新生成引用这个模块的目标产物

修改支持库
  → 重新生成所有依赖这个支持库的目标产物

修改Provider
  → 重新生成使用这个Provider的目标产物

修改公共契约或运行核心
  → 相关运行时版本变化
  → 相关产物重新编译
```

# 五、版本和当前指针

## 1. 产物版本不是源码版本

```text
源码版本：开发人员现在正在修改的内容

产物版本：某一次编译后、经过验证、可以运行的固定内容
```

同一份源码可以产生多个产物版本：

```text
源码版本A → 产物A
源码版本B → 产物B
源码版本C → 产物C
```

产物 A、B、C 都可以保留，互不覆盖。

## 2. `当前.json`

它只负责告诉系统“现在用哪个产物”，不保存业务数据：

```json
{
  "项目id": "示例项目",
  "编译目标": "某个能力或页面",
  "当前制品指纹": "abcdef1234567890",
  "制品相对路径": "版本/abcdef1234567890",
  "状态": "已验收"
}
```

## 3. 激活规则

```text
新产物生成
  → 新产物自检
  → 新产物独立启动
  → HTML真实请求
  → 返回值正确
  → 资源正常回收
  → 发布门禁通过
  → 才能修改当前.json
```

如果新产物失败：

```text
当前.json 不变
旧产物继续可用
新产物标记为失败候选
```

# 六、HTML到底访问什么

HTML 访问的不是：

```text
✗ 开发源码目录
✗ 支持库源码文件
✗ Python模块对象
✗ 开发网关里的临时能力
```

HTML 访问的是：

```text
✓ 当前稳定产物目录
✓ 产物自己的启动入口
✓ 产物自己的页面
✓ 产物自己的 HTTP /网关/调用
✓ 产物返回的真实JSON
```

外部请求路径：

```text
HTML / 外部项目 / Agent
        ↓
当前稳定产物
        ↓
产物HTTP服务
        ↓
产物内部的统一能力调用
        ↓
真实结果
```

所以正式逻辑是：

```text
源码 → 编译 → 稳定产物 → HTTP请求 → 返回结果
```

而不是：

```text
HTML → 源码 → 临时解释 → 返回结果
```

# 七、第一阶段只实现这些内容

```text
1. 给编译目标建立完整依赖闭包
2. 给依赖闭包建立文件级内容指纹
3. 建立不可变产物目录
4. 建立编译缓存索引
5. 建立缓存命中和失效原因
6. 建立当前稳定版本指针
7. HTML验证器只启动稳定产物
8. 产物运行时禁止回读开发源码
9. 制品损坏时禁止命中缓存
10. 修改页面、模块、支持库后验证影响范围
11. 保留旧制品用于回滚
```

第一阶段暂不做：

```text
1. 不马上引入PyInstaller
2. 不马上引入Nuitka
3. 不马上生成DLL
4. 不马上生成EXE
5. 不改变40007唯一业务执行接口
6. 不改变8866能力发现职责
7. 不改变8766 MCP治理职责
8. 不把缓存变成第二套能力登记事实源
```

# 八、验收标准

## 编译器

```text
第一次编译
  → 生成独立产物

第二次完全不变的编译
  → 几乎立即命中缓存
  → 返回同一个制品指纹
  → 不重新清理和复制全部目录

修改无关文件
  → 当前目标仍命中缓存

修改页面
  → 页面相关目标重新编译
  → 无关目标继续命中

修改模块或支持库
  → 依赖它的目标重新编译
  → 无关目标继续命中

手工修改产物
  → 完整性校验失败
  → 禁止命中缓存
```

## 产物

```text
产物可以单独启动
产物不读取开发源码
产物能返回页面
产物能处理 /网关/调用
产物返回统一结果
产物关闭后无残留进程和端口
```

## HTML

```text
HTML只访问产物
HTML能看到真实HTTP状态码
HTML能看到真实成功/值/错误码/错误说明
HTML不依赖源码目录
```

## 版本

```text
新版本验证失败 → 旧版本不受影响
新版本验证成功 → 当前.json切换到新版本
当前版本出现问题 → 当前.json切回旧版本
```

# 九、单腿审计裁决

这份设计要成立，必须把下面几件事分开，不能混在一起：

```text
依赖判断：编译器判断哪些内容变了
        ↓
产物生成：生成一个全新的完整稳定产物
        ↓
产物运行：只启动这个产物
        ↓
HTTP验证：只请求这个产物
        ↓
版本激活：验证通过后切换当前指针
```

## 1. 正式执行只有一条腿

```text
HTML / 外部项目 / Agent
        ↓
稳定产物启动器
        ↓
产物自己的 HTTP 网关
        ↓
POST /网关/调用
        ↓
统一能力调用服务
        ↓
支持库 / 模块库 / Provider
```

以下入口不属于第二条业务执行腿：

- `8866`：只读能力搜索和契约查询；
- `8766`：MCP治理工具适配层；
- 项目适配层的 HTTP 连接器：只是调用 40007 的连接器；
- 浏览器页面里的 `fetch`：只是请求当前产物的 HTTP 接口；
- HTML 验证器的并发请求：只是验证同一个产物；
- 测试中的随机回环网关：只属于测试装配，不属于正式发布入口。

产物内部如果保留两层 HTTP，也必须明确它们不是两套执行：

```text
外层页面宿主
  → 只返回 HTML、接收浏览器请求、转发 JSON
  → 不注册能力、不执行能力、不维护第二套Provider

内层产物网关
  → 唯一处理 /网关/调用
  → 转入统一能力调用服务
  → 承担真正业务执行
```

因此这是：

```text
两层传输
一条执行腿
```

如果后续能让页面宿主和执行网关合并而不破坏边界，可以合并；如果暂时保留，必须在制品清单中把它标成“页面转发层”，不能称为第二业务网关。

当前 HTML 验证器代码仍支持 `直连地址`，它可以连接一个已经运行的本地地址而不启动制品。

这个能力可以保留，但必须明确：

```text
直连地址
  → 只用于开发调试 / 已运行服务排查
  → 不能作为正式发布验证入口
  → 不能生成正式发布成功证据
  → 不能切换当前.json
  → 不能替代“启动指定稳定产物”
```

正式发布链只能是：

```text
读取稳定制品
  → 启动稳定制品
  → 请求稳定制品
  → 验证稳定制品
  → 关闭稳定制品
```

## 3. “增量”只发生在编译决策，不在线修改产物

不能把增量编译理解成：

```text
当前正在运行的产物
  → 在线替换其中一个文件
  → 继续对外服务
```

正确理解是：

```text
依赖没有变化
  → 直接复用旧的完整产物

依赖发生变化
  → 生成一个新的完整产物目录
  → 新产物独立验证
  → 验证通过后切换当前指针
```

因此当前稳定产物永远不被原地修改，避免运行中的版本被一半替换。

## 4. 第一阶段产物不是二进制文件

第一阶段的“独立产物目录”仍然可能包含 Python 文件。它解决的是：

```text
运行时不再读取开发源码树
运行时只读取编译器选定并复制进来的固定内容
HTML只请求固定产物
产物可以保留、验收、切换、回滚
```

它暂时不解决“别人完全看不到 Python 实现”。如果以后需要类似易语言 `.exe/.dll` 的二进制封装，再在这条稳定产物链上增加：

```text
稳定目录产物
  → .pyz / zipapp
  → macOS可执行文件
  → Windows exe / DLL
```

不能在第一阶段同时改变运行边界和封装格式，否则会把 Provider、系统命令、模型资源和进程生命周期问题混在一起。

## 5. 源码指纹只做编译和溯源，不做运行依赖

当前代码中，编译器和 HTML 验证器都会读取工作区字节指纹。深化后要区分：

```text
源码依赖闭包指纹
  → 用于编译器判断缓存是否命中

来源提交 / 工作区指纹
  → 只写入制品来源，作为审计溯源

产物完整性摘要
  → 用于运行前和验证前确认产物没有被修改
```

HTML启动产物时，不应因为开发源码目录后来又改了无关文件，就改变已经生成的稳定产物运行结果。

## 6. 正式产物只保留一个启动入口

正式产物的启动契约固定为：

```text
运行入口/启动.py
```

`启动网页.command` 和 `启动网页.bat` 只是调用这个唯一入口的操作系统快捷方式，不是第二套启动逻辑。

正式 HTML 验证器不应在多个候选启动器中猜测选择；找不到 `运行入口/启动.py` 就直接阻断。

## 7. 第一版不要虚构“文件级局部编译”

第一阶段先实现可靠的：

```text
依赖闭包变化判断
  → 缓存命中或失效
  → 重新生成一个完整新产物
```

不要一开始就宣称“只重新生成某一个 Python 文件”。因为支持库之间可能存在导入、注册、契约和 Provider 关系；如果反向依赖图还不完整，局部替换容易造成半套产物。

第一阶段的快来自：

```text
没变化 → 不编译，直接命中旧完整产物
有变化 → 只为受影响目标生成新完整产物
```

而不是把正在运行的产物拆开热补丁。


```text
源码是生产资料
编译器是生产设备
编译产物是运行事实
HTML是黑盒验收入口
当前.json是稳定版本选择器
旧产物是回滚依据
```

第一阶段确定采用：

```text
独立目录型不可变产物
+ 完整依赖闭包指纹
+ 内容寻址缓存
+ 当前稳定版本指针
+ HTML只访问产物
```

一句话：

```text
以后不是“HTML去访问源码”，而是“源码先编译成稳定产物，HTML只请求稳定产物”。
```
