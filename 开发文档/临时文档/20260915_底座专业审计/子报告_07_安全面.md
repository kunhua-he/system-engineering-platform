## S-02 · 跟随重定向不做逐跳 SSRF 校验 → 可打到被禁目标

**级别**：重要（真实可达，已复现）
**影响**：`发送请求` 默认跟随 HTTP 重定向，但 `_校验协议与SSRF` 只在请求前对**初始 URL** 跑一次。重定向目标不重新校验，攻击者用「合法初始 URL → 302 到内网/元数据地址」即可穿透 SSRF 防线。代码注释（`:166-168`）把逐跳校验的责任推给调用方，但**默认值恰恰是跟随**（`跟随重定向=None`，`if 跟随重定向 is False` 不成立）。

## S-04 · SSRF 守卫未接线：强校验实现 0 生产调用方，弱实现才是唯一防线

**级别**：重要（静态确认，真实架构缺陷）
**影响**：仓库里有两套 SSRF 判定，**较强的那套从不被 HTTP 客户端调用**：
- `网络通信支持库.出站安全.校验出站URL`（含云元数据封锁、运营商 NAT `100.64.0.0/10`、IPv4-mapped IPv6、内嵌凭据拒绝、DNS 解析带超时、协议白名单）：全仓**零生产调用方**，只有自身契约/场景 JSON 引用。
- `网络请求._校验协议与SSRF`（轻量自研版）：只做 `scheme in (http,https)` + `socket.gethostbyname` 单次 IPv4 解析 + `is_loopback/is_private/is_link_local/is_reserved/is_multicast`，**没有**运营商 NAT 段、没有"始终封锁 IP 列表"、没有 IPv6 路径、且**检查与连接是两次独立解析**（`gethostbyname` 校验、`urlopen` 再解析一次）→ DNS rebinding TOCTOU。

结果是防线出现"两套实现 + 强的那套空转"的漂移，与 S-02 叠加后实际强度远低于设计预期。

- `支持库/后端/网络通信支持库/请求/实现/网络请求.py:39-58,50`（弱版；`:50 socket.gethostbyname`）
