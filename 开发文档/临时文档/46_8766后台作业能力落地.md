# 46 8766 后台作业能力落地

## 阶段一：问题 → 方案 → 影响范围

### 问题（华哥 P1 痛点原文）

> 「另一个会话一开发我就卡一下」——一个会话裸跑长工具（发布门控、并行测试、静态检查）
> 会把另一个会话的调用**堵在队里**。

### 机制（本次现场核实，非推测）

`MCP工具箱/项目服务.py:532` 的 `调用工具` 是 `async def`，但**函数体全是同步调用**：

| 长工具 | 同步阻塞点 |
|---|---|
| `verify_and_record` | `_运行验证` → `subprocess.run`（跑 unittest，可达分钟级） |
| `run_release_gate` | 起发布门禁子进程 |
| `validate_module_compliance` | 13 场景真实调用合规扫描 |

8766 是 `uvicorn` **单事件循环**（`项目服务.py:888 主程序HTTP`），MCP StreamableHTTP 的每个工具调用
都由 SDK 在**同一个事件循环**上 `await`。同步阻塞 → **该会话的调用把事件循环占死**，
其他会话（另一台 Claude Code 连同一 8766）的请求全部排队，表现即「卡一下」。

### 方案

按 `未完成事项.md` P1 条目既定方向补「提交作业 + 轮询 + 可取回」模型。

**与 40007 侧方案的差异（环境不同，非重新设计）**：40007 是同步多线程进程（`启动运行核心网关.py`
`while True: sleep`），其 `任务进程池` 用 `multiprocessing` **fork** 子进程执行、可 killpg 真取消；
8766 是 **asyncio** 进程，在事件循环里 fork 有已知死锁风险，故本批用**线程池**（长工具本质是
`subprocess.run` 等 IO 密集调用，线程足够，且无 fork 风险）。状态机与终态名与 40007
`任务系统.py` **逐字对齐**（等待中/运行中/成功/失败/已取消/超时/崩溃）。

**能力边界（如实声明，不夸大）**：
- 取消是**尽力取消**：未开始的可真取消（`Future.cancel`）；已运行中的只能标记并丢弃产出
  （线程无法中断阻塞中的 `subprocess.run`）。
- 超时由目标工具自身参数负责（如 `verify_and_record.timeout_seconds`）；作业层不假装能中断线程。
- 作业状态落 `工程缓存/作业状态/作业.jsonl`（`.gitignore` 已覆盖 `工程缓存/`），
  8766 重启后非终态作业收敛为「崩溃」，与 40007 同语义。

### 方案要点

1. 新增 `MCP工具箱/作业系统.py`：线程池 + 状态机 + 原子落盘 + 提交/查询/取消/列出。
2. `项目服务.py` 新增 3 个工具：`tool_job_submit` / `tool_job_query` / `tool_job_cancel`
   （中文名 `提交作业` / `查询作业` / `取消作业`，进 `工具名映射.py`）。
3. 执行器由 `项目服务.py` 注入（避免循环 import）：线程内 `asyncio.run(调用工具(名, 参))`
   取回 `[TextContent]` 转 dict。
4. 拒绝作业工具嵌套提交（防递归）。

### 影响范围

只动 `MCP工具箱/`：新增 `作业系统.py` + `测试中心/MCP工具箱/测试_作业系统.py`；
改 `项目服务.py`（3 个 Tool 定义 + dispatch 分支 + 分类表）与 `工具名映射.py`。
不碰 40007、不碰任何支持库能力、不改 MCP 协议。

新增工具属「**需要重启 8766**」的类别（工具表变更，热重载不覆盖），
按重启纪律与其它待重启项**凑一批**，且重启前确认无在跑长任务。

## 阶段二：实际结果 → 调用方式

### 落地内容

| 文件 | 变化 |
|---|---|
| `MCP工具箱/作业系统.py` | 新增（~300 行）：线程池 + 七态状态机 + 原子落盘 + 提交/查询/取消/列出 |
| `MCP工具箱/项目服务.py` | 加 3 个工具定义 + 3 个分发分支 + 分类「作业」；执行器由本文件注入 |
| `MCP工具箱/工具名映射.py` | 加 中文名 `提交作业` / `查询作业` / `取消作业` |
| `MCP工具箱/热重载.py` | 加 `_重载锁`（RLock）串行化重载：作业线程与事件循环会并发重载同一模块 |
| `测试中心/MCP工具箱/测试_作业系统.py` | 新增 16 个用例，全过 |

### 调用方式

```python
# 1. 提交（长活立即转后台，当场拿作业id）
提交作业(工具="run_release_gate", 参数={"包目录": "支持库/直播逐字稿"})
# → {"成功": true, "作业": {"作业id": "0fbdd772a0784792", "状态": "运行中", ...}}

# 2. 轮询（给作业id查单个；不给则列最近 20 条，不含结果全文）
查询作业(作业id="0fbdd772a0784792")
# → {"成功": true, "作业": {"状态": "成功", "结果": {...}, "已运行秒": 6.78}}
# 终态：成功 / 失败 / 已取消 / 超时 / 崩溃

# 3. 取消（尽力：未开始直接取消；运行中只标记并丢弃产出）
取消作业(作业id="0fbdd772a0784792")
```

作业工具**不可嵌套提交**（`tool_job_submit` / `tool_job_query` / `tool_job_cancel` 提交即被拒）。

### 证据

**单测**：`python3.14 -m unittest 测试中心.MCP工具箱.测试_作业系统` → 16/16 通过。
覆盖：提交即返回、运行中报「已运行秒」、执行器抛异常判失败、失败字典判失败、参数用完即清、
未开始真取消、运行中尽力取消、终态取消幂等、未知作业id、空工具名/未注入执行器拒绝、
防递归、重启收敛为「崩溃」、超长结果落盘截断（内存留全文）、列表倒序限量。

**端到端（真实分发入口）**：经 `调用工具` 提交 `role_profile` 作业 → 轮询到「成功」并取回真实结果；
中文名「提交作业」可调用；递归提交被拒；终态取消幂等。

**防堵 A/B（同一工具 `validate_module_compliance`，模块「直播逐字稿」）**：

| 走法 | 事件循环最大停顿 | 工具本身耗时 |
|---|---|---|
| 直接调（旧行为） | **0.226 秒**（就是被占住的那一下） | 0.226 秒 |
| 走作业（新行为） | **0.143 秒** | **6.784 秒** |

即：一个跑了近 7 秒的工具，事件循环最长只停顿 0.143 秒——不再把别的会话堵在队里。

### 如实声明（未做到的部分）

- **取消不能打断已在跑的子进程**：线程无法中断阻塞中的 `subprocess.run`，运行中取消只是
  打标记 + 丢弃产出。真要硬中断，得回到 40007 那种独立进程 + killpg 模型（本批不做）。
- **超时不归作业层管**：作业不设看门狗，超时仍由目标工具自身参数决定（如
  `verify_and_record.timeout_seconds`）。
- **并发默认 1（串行队列）**：`默认最大并发数 = 1`，超出的作业排队「等待中」。
  本模块只解决「长活别占事件循环」，**不引入工具级并发**——五十来个工具是否线程安全
  未逐一验证，多个作业同时改写共享缓存 / 权威状态会出新竞态。确认某类工具可并发后，
  可用 `最大并发数` 显式调大。
