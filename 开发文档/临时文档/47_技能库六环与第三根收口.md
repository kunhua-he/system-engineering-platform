# 47 · 技能库六环补齐与「第三根」全底座收口

## 阶段一：开始前

### 背景

`技能库/后端/技能库` 已在 `4be53bb` 归位为顶层第三根（与 `支持库`、`模块库` 平级，包声明类型
同为「支持库」）。但归位只改了「目录在哪儿」，没有让底座各处**一致地认得**它：

- 运行时发现器 `发现全部(支持库根, 模块根, 技能库根)` 已有第三个可选参数（`后端核心.py:236,272`
  已在传），但**大量下游调用方仍只传两个根**；
- 技能库自身六环不全（缺 `验证场景引用.json` / `验证场景.json` / 验证夹具 / `完整性摘要.json`）；
- 包声明、能力契约、能力搜索数据是归位前的旧版，与能力定义唯一事实源不一致。

本批目标：**把技能库当正式包根这件事，在底座全链路（发现 → 依赖 → 验证 → 编译 → 制品 →
门禁 → 测试）里做齐**，顺带修掉因此暴露出的底座既有缺陷。

### 发现的底座缺陷（动手前记录）

| # | 缺陷 | 现象 | 性质 |
|---|------|------|------|
| 1 | `正式包索引` 聚合父包判据过宽 | `if 子声明: continue` 把**自带 `能力定义.json` 且含子包**的真实包（如 `代码解析支持库` 含 `语法索引`）整包丢弃 → 索引 543 条 vs 运行时 549 条，6 个能力凭空消失 | 既有严重缺陷 |
| 2 | `固定运行时目录` 漏 `平台控制面` | 项目编译器编出的**每一个**制品，`启动.py` 一 import 就 `ModuleNotFoundError: No module named '平台控制面'`（`运行核心/统一网关/本地网关.py:20` 依赖它） | 既有严重缺陷（全制品不可运行） |
| 3 | `能力定义编译器` 仍生成 `验证场景引用.json` | 生成的是旧版 `{场景id,目标,范围}` 三键格式，**不是合法 v1 引用**，会把作者手写的合法文件覆盖成非法文件；`d973a83` 已停生成但文档字符串与测试没跟 | 陈旧残留 |
| 4 | `测试_模型协议别名.py` 被反向破坏门禁误判 | 该测试必须直读连接器内部 `协议别名` 表做协议漂移守卫，属门禁白名单应覆盖的「Provider 内部协议测试」 | 门禁白名单缺项 |
| 5 | `测试_项目适配层.test_有效绑定` 硬编码版本 | `文件操作` 已升 1.1.0（`724550c`），测试仍断言 1.0.0 | 陈旧断言 |

### 解决方案

**（1）第三根一致化**（把所有 `发现全部(...)` 与「根目录扫描元组」补上技能库）

| 文件 | 改动 |
|------|------|
| `项目适配层/依赖锁定/依赖锁定.py` | 提供者查目录的根元组 `("支持库","模块库")` → 加 `"技能库"`；`发现全部` 补第三参 |
| `项目适配层/依赖锁定/传递闭包.py` | 同上（`_提供者目录` + `校验传递闭包`） |
| `MCP工具箱/发布治理.py` | `校验依赖闭包` / `依赖裁决` 两处 `发现全部` 补第三参 |
| `开发工具/统一验证/统一验证器.py` | 新增 `技能根目录`，4 处 `发现全部` 补第三参 |
| `开发工具/组件规范/完整性摘要.py` | `扫描正式包` 根元组加 `"技能库"` |
| `开发工具/更新完整性摘要.py` | `目标目录` 加 `"技能库"` |
| `开发工具/公开调用完整性门禁.py` | `扫描段` 加 `"技能库"`，文档字符串同步 |
| `客户端/构建平台客户端.py` | `顶层包表` 加 `"技能库"`（否则制品里没有技能库、命名空间也不重写） |
| `测试中心/第一批维修/测试_能力唯一事实源.py` | `发现全部` 补第三参（正式集合与运行时集合才能逐项相等） |
| `测试中心/第一批维修/测试_句柄与数值契约冻结.py` | 3 处根循环加 `"技能库"` |
| `测试中心/开发工具/测试_完整性摘要统一.py` | 根循环加 `"技能库"` |

**（2）修底座缺陷**

- 缺陷 1：聚合父包判据改为**与运行时发现器一致**——
  ```
  子声明 = [路径 for 路径 in 包路径.rglob("包声明.json") if 路径.parent != 包路径]
  if 子声明 and not (包路径 / "能力定义.json").is_file():
      continue
  ```
  即：**只有「无 `能力定义.json` 且含子包」的目录才是聚合视图**；自带 `能力定义.json`
  的包即便含子包，仍是真实能力 owner。
- 缺陷 2：`固定运行时目录` 补 `"平台控制面"`。
- 缺陷 3：编译器文档字符串改为「不生成 `验证场景引用.json`」并写明理由；`生成验证场景引用`
  改为恒返回 `None`（保留定义只为让「不生成」有单一落点）；删掉 `漂移检测.py` 与测试里
  已无用的 import；测试断言由 `assertIn` 改 `assertNotIn`。
- 缺陷 4：门禁 `允许` 集加 `测试_模型协议别名.py` + 注释。
- 缺陷 5：`test_有效绑定` 改为从 `包声明.json` 读版本并断言相等，不再硬编码。

**（3）技能库自身六环**

- `能力定义.json` 为唯一事实源 → 重编译出 `包声明.json` / `能力契约/参数契约.json` /
  `__init__.py` / `能力数据/能力搜索数据.json` / `能力数据/Agent查询数据.json` /
  `完整性摘要.json`。
- **手写** `验证场景引用.json`（合法 v1：`契约版本` + `验证场景引用[{场景文件}]`）与
  `验证场景.json`（10 步场景）+ `验证夹具/`。
- `技能库/实现/技能库.py` AST 审计加固：新增 `硬禁止调用链`（`os.system`/`os.popen`/
  `os.fork`/`os.spawn*`/`os.exec*`/`pty.spawn` 等），并让 `from os import system` 形式的
  别名也参与调用链比对。

### 影响范围

- **零回归**：各调用方新增的根都是**过滤器**——`生成依赖锁定` 只保留绑定包，未绑定的技能库包
  不会进锁定结果；统一验证器新增通过项；门禁新增扫描段但这批技能库包**已补齐六环**。
- 制品体积：平台客户端制品多一个顶层包，属预期。
- 不涉及数据库、不涉及端口、不涉及运行中服务配置。

### 明确保留、不动

1. **`支持库/适配层/*提供者` 缺 `验证场景引用.json`**（统一验证器 `--范围 结构` 唯一失败项）。
   适配层 Provider 按设计**不在六环公开边界内**（有自己的依赖/运行时门禁），两套答案都说得通 →
   保留现状，记录待华哥裁。
2. **V3 `后端服务/应用层/服务/代理/OpenCode代理.py:20`** 仍硬编码
   `https://opencode.ai/zen/go/v1/chat/completions`。指令①点名的 `OpenAI提供商.py` 已满足
   「端点一律由配置给、不内置默认」；`OpenCode代理` 是**独立代理服务**，其上游是否也改配置化
   待定 → 保留，记录。

### 调用方式

无需新增调用入口。第三根的影响只体现在**能力发现范围**上：

```
发现全部(支持库根, 模块根, 技能库根)     # 运行核心.加载器.包发现.发现器
```

技能库能力经既有网关/注册表链路调用，能力 id 形如 `技能库.<相对路径>.<能力名>`。

### 生效条件

- 技能库能力的**发现**改动对进程即时生效（下次 `发现全部` 即含技能库）。
- **平台客户端制品**需重新构建才含技能库（`客户端/构建平台客户端.py`）。
- 管理端（8766）持有的进程需重启才用上新的发现/门禁代码。
