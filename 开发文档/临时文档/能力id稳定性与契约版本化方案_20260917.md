## 三、件 3｜breaking change 保留旧版本 —— **包级已有，能力级不该做（撞哲学）**

**(a) 包级多版本并存：已有。** `平台控制面/包仓库/版本仓库.py:38 def 版本路径(包id, 版本)` 每 `(包id, 版本)` 独立目录 / `:41 def 已安装(包id, 版本)` / `:44 def 安装` / `:123 def 删除` / `:131-132 if 回滚任务数 > 0: return False, f"仍有 {回滚任务数} 个回滚任务，禁止删除"`。

**(b) 请求级引用计数锁：已有。** `运行核心/能力调用/控制调用/证据链.py:159 class 版本锁定` / `:160 """请求/长任务版本锁定：结束后才减少旧版本引用。"""` / `:164 引用计数: dict[str, int]  # "包id@版本" → 引用数` / `:188 def 可删除` / `:189 """引用数为零才允许删除。"""` → **"旧版本保留到最后一个调用方结束"已实现**。

**(c) 但调用侧不吃版本，"同能力 1.x 与 2.x 并存"运行期不可能。** `唯一能力调用.py:198 实现 = self.注册表.获取(能力id)`；`契约.py:169-170 def 获取(能力id) -> 能力实现 | None: return self._实现表.get(能力id)` 单值返回；调用签名 `唯一能力调用.py:175 def 调用能力(self, 能力id, 参数, …)` **无版本参数**。

**(d) `依赖锁.json` 不是能力版本锁（须纠正的常见误读）。** 读 `支持库/适配层/Tesseract提供者/依赖锁.json` 顶层键 → `['包','提供者id','直接依赖','依赖闭包','环境','生成时间','说明']`，**无能版本字段**；内容为 `{"名称":"tesseract","版本":"5.5.2","来源":"外部应用"}` + `"环境": {"Python":"3.14.4","操作系统":"macOS","CPU":"arm64"}` + `"说明":"精确锁定，禁止范围版本"` → 锁的是**第三方/外部依赖与运行环境指纹**，与能力版本无关。

**(e) 回滚能力：已有。** `平台控制面/发布管理/二阶恢复.py:37 def 幂等恢复校验(状态, 发布id, 期望版本, …)` / `:65 raise AssertionError(f"指针未落在明确激活版本: {指针}")` / `:6 落点唯一：指针明确旧版或新版…（无半激活）`；`迁移互斥编排器.py:88 连接.rollback()  # 整体回滚到迁移前（半状态防护）`；`发布管理/__init__.py:22 激活发布版本` / `:24 回滚发布`。

**(f) 与本项目哲学正面冲突。** `开发文档/项目说明.md` 第 1 条：`1.2 不保留旧腿`——`旧能力一旦被新实现取代，直接删除，不保留「兼容入口」「兼容壳」「旧名别名」…调用方要么走唯一新链路，要么明确失败`；`1.5 制品只留最新单版，旧版进归档`——`非必填字段的增删不影响旧引用；新增必填字段用一次 HTML 多线程全量跑…按点维修`；`1.7 不做本地归档，旧版直接删`——`GitHub 提交历史就是归档…不建归档库、不写归档机制、不保留旧制品`。

**结论**：件 3 = **包级已有等价机制，能力级不该做**；外部评估这条**与项目定位冲突，不应照做**。

## 六、方案（按优先级）

**P0｜能力 id「只增不改」静态门禁**（对件 1，真缺口）
- **要不要做**：做，这是四件里唯一必须新造的。
- **代价**：低。1 份机器账本（基线清单 JSON）+ 1 条只读校验；**不改任何既有 id**。
- **最小可行形态**：冻结全仓能力 id 基线（键 = 能力id，值 = 归属包id）；门禁两条规则 ①基线中已存在的 id **不得消失、不得改名** ②新 id 允许新增（只增不改）。挂在**既有** `开发工具/发布门禁/` 同层，复用 `第十四阶段门禁.py:72` 同款 `_调用治理能力` 通道，**不新建第二条门禁腿**（哲学 1.2 禁第二腿、1.4 禁空转门禁）。
- **验收**：正向不改 id → exit 0；**反向故意改一个 id** → 非零退出且指名「旧 id / 新 id / 归属包」；基线文件缺失或读空必须**明确失败**，不得返回"无变更"假绿（对齐 `消费者契约注册表.py:28` 那条 fail-open 教训）。禁用 HTML 黑盒验证器（7.3/7.5）。

**P1｜消费者契约注册表填表**（对件 2，补数据不造机制）
- **要不要做**：做。机制（登记/漂移/门禁）与门禁接线都已存在，只缺真实数据（现 0 份）。
- **代价**：中低。**不全量**——按实测引用面只覆盖对外公开能力，先从引用数 ≥5 的 id 起（最热 34 文件）。
- **最小可行形态**：走既有唯一入口调用 `平台控制面.能力目录.登记消费者契约`（`消费者契约注册表.py:118`），**不新增登记 API**；一次性登记脚本用完即删（哲学 1.6），**只留数据不留脚本**，数据落注册表运行期存储目录。
- **验收**：`判定契约漂移(能力id, 当前契约)` 返回 `漂移数 > 0` 且逐项含 `消费者id/期望值/实际值`；`判定契约门禁` 返回 `是否阻断=True`；**反向改一个参数名 → 门禁必须变红**（同时验证"表真的填进去了"而非仍恒放行）。

**P2｜命名规范一次收口**（件 1 的前置，只记录不迁移）
- **要不要做**：做，但只做"定规范 + 列存量偏差"。

**P3｜一键安装 → 换机体检单入口**（件 4 该做的一半）
- **要不要做**：做「单入口体检」；**不做 Docker/CI**。

**P4｜能力多版本并存 —— 不做（明确取舍）**
- **要不要做**：**不做**，除非华哥先裁决推翻哲学。
- **冲突点**：①对抗 `项目说明.md` **1.2 不保留旧腿**（禁兼容入口/兼容壳/旧名别名）②对抗 **1.7 不做本地归档，旧版直接删**（GitHub 历史即归档）③对抗 **1.5 制品只留最新单版** ④技术上要改**契约层定义**：`契约.py:138`「同一能力 id 只允许一个提供方」+ `:141 _实现表: dict[str, 能力实现]` 须变 `dict[(id, 主版本), 能力实现]` ⑤调用侧须新增版本参数 → 等于改 **7.4 统一调用接口铁律**（唯一签名 `调用能力(能力id, 参数)`）。

## 八、剩余风险

1. **P0 基线冻结时点**：若在命名规范未裁决前冻结，会把两套口径一起冻进去，之后 P2 定规范反被基线锁死。**建议 P2 先出结论，再冻 P0 基线**。
2. **P0 门禁漏网面**：能力 id 也内嵌在 `说明/使用说明.md`、`权限契约.json`、`验证场景引用.json`、`完整性摘要.json`（件 1f 实测 11 处/包）。基线门禁若只扫 `能力定义.json`，会漏"定义没改但消费者内嵌串被改"。**建议同时扫消费者文件里的 id 字面量**。
3. **P1 覆盖度不可验满**：注册表 0 份登记的现状下门禁 fail-open。填表后新包若忘登记会**对新包静默放行**。建议配套"公开能力必须有登记"的反向断言，否则收益随新包落地逐月衰减。
4. **P3 脚本会再腐烂**：四类前置的判据来源分散在 README、依赖锁 JSON、提供者代码三处；脚本写死判据后，提供者侧判据演进会让脚本变"假绿"。**建议脚本复用既有分项体检能力（`README.md:92` 提及），不自己重写判据**。
5. **件 3 的哲学裁决未留出口**：若未来真出现"必须同 id 多版本"的硬需求（外部 Agent 长期在线、无法同批升级），当前哲学**没有出口**（1.2/1.7 是"直接删除"）。建议作为**待裁决项**登记，而不是等出事再改哲学。
6. **外部评估口径本身有偏**：评估者按"开源 Gateway / 多租户 Agent 平台"通用画像给建议（SemVer + 保留旧版 + Docker 一键装）。本项目是**本机私有部署 + 单机多项目 + 唯一底座**，件 2/3/4 的建议至少一半**错位**。后续再收到同类评估，应先做这道"画像对齐"过滤。
