### 2.3 返回字段与错误码

- 统一信封固定为 `请求id / 操作 / 成功 / 值 / 错误码 / 错误说明 / 句柄 / 耗时毫秒`（`网关核心.py:98-117`，HTTP 写回见 `本地网关.py:853`）。
- **三操作都没有自己的返回字段契约**：`允许字段表` 只约束入参，`_执行` 分支把回调返回值直接塞进 `响应.值`，不做结构校验（`网关核心.py:554`）。唯一例外是 `激活版本查询`，它把返回值**强制重塑**为两键字典：

```python
请求.操作 == "激活版本查询" → 值 = {"能力id": 参数.get("能力id",""),
                                    "激活版本": 查询结果.get("激活版本")}
```
（`网关核心.py:551-553`）——这反证原设计里被注入的回调应返回**含 `激活版本` 键的字典**，其余键在 `激活版本查询` 路径被丢弃。

- 错误码：**没有任何专用错误码**，全部复用 `公开错误说明表`（`网关核心.py:36-55`）。三操作实际只会走到三条：

| 场景 | 内部触发 | 公开错误码 | HTTP 状态码 |
|---|---|---|---|
| 未装配（当前生产实际状态） | `_执行` 抛 `ConnectionError("查询服务未接入")` → `处理` 捕获 | `提供者不可用` | 503 |
| 参数含不允许字段 | `_操作参数错误` 返回非空 → `_设置失败("参数不合法")` | `参数不合法` | 400 |
| 操作名不在允许表（若将来删除操作名） | `ValueError("未知操作")` | `参数不合法` | 400 |

（映射依据：`网关核心.py:360-364`、`:547-549`、`:565-566`、`:586-589`；状态码表 `本地网关.py:840-853`。）

### 2.4 只读探针实测（内存复现，无落盘）

```
未装配 | 版本查询       | 参数={}                                  → 成功=False 错误码=提供者不可用
未装配 | 激活版本查询   | 参数={'能力id':'支持库.后端.文件系统.读取文件'} → 成功=False 错误码=提供者不可用
未装配 | 诊断查询       | 参数={}                                  → 成功=False 错误码=提供者不可用
未装配 | 版本查询       | 参数={'包id':'x'}                         → 成功=False 错误码=参数不合法「不支持字段 包id」
未装配 | 诊断查询       | 参数={'记录id':'x'}                       → 成功=False 错误码=参数不合法「不支持字段 记录id」

注入假查询回调后：
  版本查询     → 回调收到参数 {}                → 值 = 回调返回值原样（含 激活版本/版本表/诊断 等任意键）
  激活版本查询 → 回调收到参数 {'能力id':'a.b.c'} → 值 = {'能力id':'a.b.c','激活版本':'1.2.0'}（其余键被丢弃）
  诊断查询     → 回调收到参数 {}                → 值 = 回调返回值原样
```

**结论（实测支撑）**：
1. 三操作在**当前生产装配下恒返回 503 `提供者不可用`**（`启动运行核心网关.py:24-25` 不注入回调）。
2. `版本查询` 与 `诊断查询` 语义上**完全同一条路**：参数都为「无」、返回值都原样透传，二者只有操作名不同。
3. `诊断查询` 在语义上与「版本」无关，却被强制塞进名为 `版本查询` 的回调，**自相矛盾属实**；两者共用入口不是笔误，而是这条历史残留的核心缺陷。
4. `版本查询` 是一个**网关注入回调装配面**，即「网关内部第二装配面」——与底座铁律「所有能力只经唯一 `调用能力(能力id, 参数)`」直接冲突。

## 五、收敛方案：唯一原子能力

### 5.1 分层硬约束（决定能力放哪里，必须先看这条）

实测：`grep -rn "from 运行核心\|from 平台控制面" 支持库/ 模块库/ --include="*.py"` → **零命中**。
即：**支持库与模块库一律不得导入运行核心/平台控制面**（符合 AGENTS.md 分层：公共契约 → 支持库 → 模块库 → 项目适配层 → 正式代码 → 运行核心 → 平台控制面）。
而版本注册表/热切换（运行核心）、激活指针/状态快照/监督报告（平台控制面）都在上层。

⇒ 唯一原子能力**不能**直接在支持库实现里 `import 热切换`。必须走底座既有两条合法通道之一：
1. **提供者装配**（推荐）：能力包只声明契约与参数，真实数据由装配层通过提供者注入（既有同类机制：`平台控制面/提供者/注册表.py:23-45` 的「能力id → 调用函数」注册、`支持库/适配层/提供者注册表/标准提供者.py:38-75` 的提供者声明注册、`后端核心/后端核心.py:138-147` 的 `注册能力(能力id, 实现函数)` 运行期注册）。
2. **只读资源路径入参**：能力只按路径读持久事实（如 `平台状态` SQLite、`版本注册表.json`、事件日志目录），与 `添加 数据库连接支持库` 现有「路径一次传参」风格一致（例 `支持库/后端/数据库连接支持库/SQLite数据库/包声明.json:12-15`）。

### 5.5 备选设计与取舍（供拍板）

| 方案 | 形态 | 优点 | 代价 |
|---|---|---|---|
| **A（推荐）** | 1 个能力 + `查询项` 枚举 3 值 | 一次收敛、一个能力id、一个事实源入口、网关一行分派 | 能力内部按枚举分派，属于「组合查询能力」，粒度偏粗 |
| B | 3 个能力（`查询平台版本`/`查询激活版本`/`查询运行诊断`）+ 网关 1 个操作按枚举转发到 3 个能力id | 粒度最细、各自契约独立 | 网关要维护枚举→能力id 映射（第 4 处映射表）；三份六环；与「一个查询一个原子」的干净度取舍需华哥定 |
| C | 保留 `版本查询`，仅把 `诊断查询` 拆出去 | 改动最小 | 仍是「网关注入回调第二装配面」，违反总铁律，**不建议** |

> 判据（华哥 2026-09-14）：「是否足够干净的底座、能否解决」——按此，A 或 B 都可，C 不合格。
