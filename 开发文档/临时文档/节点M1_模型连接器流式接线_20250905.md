## 发现的问题
- `生成对话` 仍是统一结果入口，不能在不改变旧行为的前提下直接承担有限事件迭代。
- H 节点已提供 `流式调用对话(配置, 消息列表, 系统提示词)`，但模型连接器包没有把句柄账本接到该 Provider 入口。
- 连接句柄已经保存规范化协议、`url` 和 `api_key`，可以在连接器内部边界复制配置后交给 H，不需要新增路由或修改普通网关。

## 解决方案
- 新增包级 `流式生成对话(句柄, 消息列表, 系统提示词, 流式输出=True)`；严格校验整数句柄、非空消息、布尔流式语义和 LLM 连接类型。
- 从有效句柄账本读取完整连接配置（包含协议、模型、url、api_key），调用 H 节点 `流式调用对话`，通过 `yield from` 原样转发有限增量/完成/错误事件；外层迭代器关闭会关闭 Provider 上游迭代器。
- 句柄失效、参数错误、不支持连接类型和 Provider 调用异常均返回单个结构化错误事件；既有 `生成对话` 未改动，仍返回普通 `结果`。
- 只在模型连接器包级 `__init__.py` 公开该入口，不登记为能力、不增加 HTTP 路由。

## 下一节点路由接线要求
- 下一节点只需在既有统一流式 HTTP 生命周期内调用包级 `流式生成对话`，把三类事件按既有网关写回契约逐事件转发；不得重新调用 `生成对话(..., 流式输出=True)`，不得聚合成普通 `结果`。
- 路由层必须把客户端断开/取消映射为返回迭代器 `.close()`，并继续消费或明确关闭上游；连接器本节点不创建 HTTP 路由、不承担客户端会话和取消协议。
- 路由层应保留 `句柄失效`、`参数不合法`、`不支持流式连接类型` 和 Provider `错误`事件，不把错误转成假的完成事件。
- `chat`/`res` 短协议在连接阶段已归一为 `chat_completions`/`codex_responses`，下一节点沿用句柄配置，不再重复猜测协议。
