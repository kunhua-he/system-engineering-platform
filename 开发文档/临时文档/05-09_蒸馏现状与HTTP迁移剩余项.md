## P1：LibreOffice profile 锁冲突与高并发权威调度未完成

LibreOffice/文档转换属于典型的进程外共享资源：同一个 user profile 不能被多个进程并发打开，否则会出现 profile lock、临时文件互相覆盖、请求卡死或结果串写。简单把 HTTP 线程数提高到 100～200 不能解决这个问题。

冻结落点：

```text
唯一 POST /网关/调用
  -> 唯一能力注册表/证据链
  -> 能力分配池（按能力 id 和资源键调度）
  -> LibreOffice 受管进程池
       每个进程绑定唯一临时 profile 目录
       一个 profile 同时只允许一个任务
       进程异常/超时后销毁 profile 和进程，再补充新池成员
```

必须满足：

- profile 目录由服务端生成并登记，调用方不能传入或复用 profile 路径；任务结束后无论成功、失败、超时都清理并留证据。
- 分配池使用有界队列和固定最大进程数；队列满时统一返回 `限流`/`资源繁忙`，不能无限创建 LibreOffice 进程。
- 同一文件、同一输出路径或同一转换资源键必须串行；互不相关的资源键可并行。
- 每项任务带请求 id、幂等键、租约和取消状态；重试只能重新分配新 profile，不能复用已污染进程。
- 权威事实仍只有一个注册表、一个账本和一个网关；分配池是内部执行器，不得再暴露独立 HTTP 业务接口。
- 需要补真实 HTTP 多线程验收：并发提交 100～200 个转换请求，校验无 profile lock、无输出串写、无孤儿进程/目录，且每个请求的请求 id、结果摘要和资源释放记录一一对应。

当前状态：上述分配池和 profile 隔离尚未落地，现有 LibreOffice 能力不能宣称支持 100～200 并发。

## 本轮并发审计：强制串行与必要互斥（2026-08-29）

### P0：Provider 单进程通信锁把同一 Provider 的所有任务压成单通道

证据：`运行核心/加载器/提供者隔离/独立进程.py:75-77,182-189`。JSON 行协议通过
`_通信锁` 包住整段 stdin 写入到 stdout 读取；而
`运行核心/运行环境管理器/提供者生命周期.py:88,273-319` 的进程表按
`提供者id -> 一个独立进程` 管理。因此同一 Provider 的 10 个不同请求，即使网关
线程和限流器允许并发，也会在同一把通信锁上逐个等待。这个锁对单个进程是必要的，
但“每 Provider 只启动一个进程”不是必要约束，已成为吞吐瓶颈。

落点：把受管执行单元改为“Provider 进程池”，池成员各自拥有独立 stdin/stdout
通道；请求按资源键分配，单个成员仍保持一问一答串行。池大小受资源预算约束，
同一不可并发资源（例如同一 LibreOffice profile/同一输出路径）使用资源键互斥，
不同资源键可落到不同成员并行。禁止直接移除 `_通信锁`，否则会造成响应错位。

### P1：SQLite 数据库提供者显式使用两个 `max_workers=1` 执行器

证据：`平台控制面/提供者/数据库提供者.py:33-37`，查询和事务分别只有一个
工作线程；`平台控制面/提供者/数据库提供者.py:71-98,116-149` 又用同一把
`_锁` 包住连接获取与 SQL 执行。结果是同一数据库实例的查询全部排队，事务与查询
也不能形成真正的并发流水线。SQLite 写事务确实需要串行化，但只应串行“写事务/
同一连接”，不能把独立只读查询和不同数据库句柄全部压成一列。

落点：数据库能力按“每任务/每连接”建立受控连接池；读查询使用有界读工作单元，
写事务按数据库资源键单独排队；同一连接继续保持串行，跨连接/跨库并行。必须补
并发读、写互斥、超时中断和关闭回收测试，不能简单把 `max_workers` 改成无限大。

### P1：任务进程池当前是正确的“每任务独立进程”，但默认活动数仅 4

证据：`运行核心/任务调度/任务进程.py:70-90,107-146`。任务确实一任务一进程，
但 `最大活动数=4、最大排队数=16` 会让第 5 个任务进入等待队列；这不是错误的全局
串行，而是有界容量。若要承载 100～200 个 HTTP 请求，应通过资源预算调大池或
快速返回“资源繁忙”，不能让 HTTP 工作线程长时间同步等待提交截止。

### P1：并发控制支持库的线程池入口实际退化为串行

证据：`支持库/后端/并发控制支持库/实现/并发控制.py:107-129`。
`线程池执行` 在循环中对每个 `池.submit(...).result()` 立即等待，后一个任务要等
前一个任务完成才会提交，线程池即使创建了多个工作线程也只能一次执行一个任务。

落点：先批量 `submit` 全部合法任务，再按原输入顺序收集 Future 结果；超时/取消时
对未开始任务执行取消并回收，保留有界任务列表。补充两个耗时任务的并行耗时断言，
防止未来回归成逐项等待。

### P1：HTTP 线程模型会先创建线程、再用信号量拒绝

证据：`运行核心/统一网关/本地网关.py:65,91-109` 和
`支持库/后端/HTTP服务支持库/实现/HTTP服务.py:15-22,99-106,139-164`。
两处都使用 `ThreadingHTTPServer/ThreadingMixIn`，连接到达时先创建请求线程，
线程内部才尝试非阻塞信号量；突发 100～200 连接会制造同量短命线程，可能先耗尽
线程/文件描述符，再得到“限流”。这不是业务串行，但属于电脑资源不稳定风险。

落点：在服务前增加有界连接/工作线程执行器或监听层 accept 限制，使线程创建本身
受预算控制；拒绝应在有界入口完成。保留现有信号量作为业务并发二次保护。

### P2：并发控制支持库的信号量获取没有超时/取消边界

证据：`支持库/后端/并发控制支持库/实现/并发控制.py:89-95` 直接调用
`对象.acquire()`。资源耗尽时调用线程会永久阻塞，无法响应请求截止、取消或服务
停止；锁获取虽支持 `超时秒`，信号量却没有同等契约。

落点：为 `获取信号量` 增加可选超时秒（默认应为非阻塞或有限预算），返回“未获取/
超时”统一结果；在 HTTP/任务取消路径传递截止时间，禁止无限等待。

### 必须保留的互斥（不是缺陷）

- `运行核心/统一网关/网关核心.py:297-335` 仅对同一请求 id 串行等待；不同请求 id 在锁外执行。
- `运行核心/统一网关/限流器.py:124-146,157-165` 的锁只保护计数和状态快照，不包住实际能力调用。
- `后端核心/后端核心.py:150-181` 的请求锁只更新活动/失败计数，不包住实现调用。
- `支持库/后端/大语言模型支持库/模型连接器/实现/模型连接器.py:499-503` 的本地启动锁只防止同一路径重复启动；模型调用本身不应复用该锁。
- `支持库/后端/文件系统支持库/文件操作/实现/文件系统.py:234-274` 的临时资源锁只保护登记表；实际读文件在锁外。

### 审计结论

当前“HTTP 多线程”并不等于“能力高并发”：网关层可并发，但 Provider 层是单进程
单通道，SQLite 提供者还是双单线程执行器；这两处是现阶段最主要的吞吐和长队列来源。
正确目标是“每个受限资源内部串行、不同资源键并行”，通过 Provider/数据库分配池
实现，而不是删除所有锁或把线程数盲目调到 100～200。上述两项改造完成并经真实 HTTP
并发压测前，不能宣称平台已支持 100～200 并发。

## 进程结束后的资源释放专项审计（2026-08-29）

### 当前已做到的部分

- Provider 独立进程在优雅停止/强制终止后会等待退出，并关闭 stdin/stdout/stderr；任务进程池会 terminate/kill、join 工作进程并关闭 Pipe。
- 任务终态发布前先回收工作器，临时 JSON 使用同目录临时文件 + `os.replace`，异常路径会删除残留临时文件。
- Provider 管理器提供 `清理全部`/`零残留核对`，会检查子进程、管道、调用线程、登记临时目录和日志上限。

### P1：数据库关闭使用 `shutdown(wait=False)`，不能证明线程和 SQL 已释放

证据：`平台控制面/提供者/数据库提供者.py:151-160`。关闭时先关闭 SQLite 连接，随后对查询/事务执行器调用 `shutdown(wait=False)`。若 Future 仍在运行，后台线程可能继续访问已关闭连接、持续占用线程；当前返回“句柄已释放”不等于执行器线程已退出。

落点：关闭流程先拒绝新任务，再对执行器执行有界等待；超时后中断 SQL，确认 Future 结束，仍无法结束则记录“资源释放失败”并阻断假绿。补充关闭期间并发查询/事务、线程数归零和连接不可再用测试。

### P1：HTTP 服务停止不等待活动请求线程

证据：`支持库/后端/HTTP服务支持库/实现/HTTP服务.py:108-113` 使用 `daemon_threads=True`，`停止()` 只调用 `shutdown()` 和 `server_close()`，不 join 已创建的请求线程。`运行核心/统一网关/本地网关.py:65-83` 同样只等待 serve_forever 线程。停止返回后，慢请求仍可能写 socket、继续执行能力或持有文件句柄。

落点：停止时进入排空态、拒绝新请求，记录活动请求并在有界截止内 join；超时取消/终止对应工作单元并报告未释放资源。停止验收必须包含活动连接数、请求线程数、socket 和能力句柄归零。

### P2：模型连接器释放路径未同步保护进程表

证据：`支持库/后端/大语言模型支持库/模型连接器/实现/模型连接器.py:506-529` 的 `_终止本地进程` 直接操作 `本地进程表` 并 kill/wait，而写入（:487-489）与过期回收没有统一锁；并发释放、过期回收、启动失败回滚可能造成重复 kill 或状态/PID 不一致。

落点：进程表取出与状态迁移在同一锁内完成，实际 kill/wait 放锁外；最终核对 PID 已退出并从句柄体系注销。补充并发释放、过期回收、启动失败三路交叉测试。

### 结论：现状是“多数路径有清理”，不是“完美释放”

Provider/任务工作器的正常、超时、取消路径已有较完整回收；但数据库执行器非等待关闭、HTTP 停止不等待活动请求、模型进程表缺少统一同步，仍不能承诺进程结束后线程、socket、连接、句柄和子进程 100% 归零。统一关闭契约应包含：停止排空、有界 join、失败显式报告、零残留核对。
- 未通过或未完成：完整发布门禁；全模块 HTTP 集成矩阵；唯一网关收口；句柄租约原子事务；身份 fail-closed。

## 资源释放专项审计（2026-08-29）

本轮只审计“进程结束后是否收敛释放”，未修改源码。结论是：文档转换、任务进程池和多数受管外部命令已有基本 `finally`/进程组回收，但平台还不能宣称“所有进程结束后完美释放”。以下问题需要修复并增加残留验证。

### P0：通用进程管理启动进程未建立独立进程组，却用 `killpg` 终止

证据：`支持库/后端/系统核心支持库/进程管理/实现/进程管理.py:42-44` 的
`subprocess.Popen` 没有 `start_new_session=True`；`终止进程:55-69`（强制分支）和
`释放句柄:142-147` 却对该 PID 调用 `os.killpg(os.getpgid(...), 9)`。在 POSIX 上这会把
子进程放入父进程同一进程组，`killpg` 可能误杀网关/测试进程自身；非强制分支又只终止
父进程，子孙进程可能残留。`释放句柄` 还在锁内执行杀进程，遇到异常/系统调用阻塞会
拖住所有句柄操作。

落点：启动时 `start_new_session=True`（Windows 使用独立进程组等价策略）；终止和释放
统一走“TERM→有界等待→KILL→再次 wait”并确保先确认进程组归属；从锁内移出阻塞的
wait/kill，最终再以短锁删除句柄。`执行命令:105-112` 使用 `shell=True` 且超时只返回
错误，不执行进程组终止，同样存在 shell 子孙泄漏，应改为参数列表或超时 killpg。

### P1：HTTP 服务停止关闭套接字但不等待服务线程退出

证据：`支持库/后端/HTTP服务支持库/实现/HTTP服务.py:99-103` 启动守护线程；
`停止:108-114` 仅调用 `shutdown()`/`server_close()`，没有对 `self._线程` 执行
有界 `join`，也没有清除线程引用或验证线程已死亡。停止返回时仍可能有请求线程在运行，
并发信号量/处理器栈和文件描述符尚未完全收敛；重复启动时旧线程的退出时序可能与新实例
交错。统一网关的流式服务虽在 `运行核心/统一网关/流式HTTP.py:470-480` 关闭服务，
同样未 `join` 其 `self.线程`。

落点：停止时先阻止新请求，再 `shutdown`/`server_close`，对服务线程 `join(timeout)`；
超时记录“停止未收敛”并保持非零诊断，禁止静默视为成功。增加重复启动/停止、并发请求中
停止、线程数和监听 FD 前后快照测试。

### P1：并发控制线程池释放为 `shutdown(wait=False)`，未确认任务结束

证据：`支持库/后端/并发控制支持库/实现/并发控制.py:132-143` 在释放句柄时调用
`ThreadPoolExecutor.shutdown(wait=False)`，既不取消排队任务，也不等待运行任务退出；句柄
从 `资源表` 删除后，后台线程仍可能继续访问文件、网络或外部应用。若调用方立即停止服务
或复用同一路径，会出现资源占用和结果晚到。`线程池执行:124` 逐项 `.result()` 的问题
另见前文并发审计。

落点：释放协议应先拒绝新提交，再 `shutdown(wait=True, cancel_futures=True)`（或明确有界
等待后报告未收敛），资源表删除必须发生在收敛确认之后；为运行中任务、排队任务和释放
并发竞态增加测试，并核对线程枚举无残留。

### P2：独立 Provider 关闭路径能关管道，但“进程对象”不置空且管理器无批量收口

证据：`运行核心/加载器/提供者隔离/独立进程.py:244-297` 的优雅/强制停止会等待并

`进程管理器:312-323` 只登记进程，没有 `关闭全部`/析构收口。调用方若遗忘 `停止`，
对象销毁不保证子进程回收；崩溃重启和重复关闭也缺少全局残留断言。

落点：关闭后保存退出码并将进程引用置空，管理器提供幂等 `关闭全部` 并在宿主停止钩子调用；

### P0：模型连接句柄“访问超时”路径不会释放本地模型进程

### P1：模型过期回收在全局锁内执行阻塞式进程终止

落点：锁内仅摘除过期记录并收集回调，释放进程放到锁外；为回调失败保留可观测的

# 进程结束后的资源释放专项审计（2026-08-29）

## 结论

当前实现**不能证明进程结束后必然完美释放资源**。正常优雅停止路径大体会关闭 `stdin/stdout/stderr`，但异常、崩溃重启、强杀失败和临时目录删除失败路径存在“记录已清空、真实资源仍在”的假释放。

## 发现项

### P0：清理全部在强杀失败时丢弃进程引用，可能留下活进程/进程组

- 证据：[运行核心/运行环境管理器/提供者生命周期.py:497-513](~/Documents/Agent/PHP/系统工程平台/运行核心/运行环境管理器/提供者生命周期.py:497)。`清理全部` 调用 `停止提供者` 后无论返回成功与否都继续 `self._进程表.clear()`；而 `独立进程.强制终止()` 在 [运行核心/加载器/提供者隔离/独立进程.py:268-297](~/Documents/Agent/PHP/系统工程平台/运行核心/加载器/提供者隔离/独立进程.py:268) 可能返回失败（进程组在两次 wait 后仍未回收）。
- 后果：进程仍活着时，管理器已删除唯一引用；后续 `零残留核对()` 无法遍历该进程，形成假阴性；进程组、子进程和外部句柄可能长期残留。
- 建议落点：只有确认 `poll()!=None` 且三管道均 closed 后才从进程表移除；失败项保留为故障记录并继续重试/报警，不能清空事实表。

### P1：崩溃自动重启覆盖旧 `Popen`，旧管道未确定关闭

- 证据：[运行核心/加载器/提供者隔离/独立进程.py:226-242](~/Documents/Agent/PHP/系统工程平台/运行核心/加载器/提供者隔离/独立进程.py:226)。`崩溃检测()` 发现旧进程退出后直接 `self.启动()`；`启动()` 在 [152-158] 创建新的 `Popen` 并覆盖 `self.进程`，但崩溃分支没有先调用 `_关闭管道()`。
- 后果：旧 `stdin/stdout/stderr` 的关闭依赖 Python 垃圾回收，不能作为确定性资源释放；高频崩溃重启会造成 FD 峰值。旧 `_读取缓冲` 也未清空，新进程可能继承旧半行/迟到响应，造成协议串读。
- 建议落点：重启前 `旧进程._关闭管道()`，显式 `wait()`/确认退出；重启成功后重置 `_读取缓冲=b""`。若旧进程未确认退出，禁止覆盖引用并报告故障。

### P1：`_终止并重启` 不检查强杀结果即弹出旧进程并启动新进程

- 证据：[运行核心/运行环境管理器/提供者生命周期.py:463-472](~/Documents/Agent/PHP/系统工程平台/运行核心/运行环境管理器/提供者生命周期.py:463)。忽略 `进程.强制终止()` 返回值，随后无条件 `self._进程表.pop()` 和 `启动提供者()`。
- 后果：强杀失败时旧进程/进程组仍占用 profile、端口、FD 或临时目录，新进程可能与旧进程并存，破坏“唯一权威”和资源上限。
- 建议落点：强杀失败时保留旧对象、进入故障态，不启动替代进程；只有确认进程组退出且管道关闭后才允许重启。

### P1：临时目录删除失败被静默吞掉，登记先清空造成不可追踪残留

- 证据：[运行核心/运行环境管理器/提供者生命周期.py:488-495](~/Documents/Agent/PHP/系统工程平台/运行核心/运行环境管理器/提供者生命周期.py:488)。先把 `_临时目录表=[]`，再 `shutil.rmtree(..., ignore_errors=True)`，返回值只返回尝试过的路径，不表示已删除。

### P1：超时路径可能保持“运行中”并继续执行旧任务，资源释放无硬截止

## 释放语义冻结：只有“已结束”才能释放（2026-08-29）

### 唯一规则

资源的释放接口只能接收一个已经确认结束的执行单元。`terminate/kill`、发送取消信号、
关闭 socket 或从字典删除句柄，都只是“请求结束/开始回收”，不代表资源已经释放。
只有 `进程.poll()!=None` 或 `线程.is_alive()==False`，并且关联管道、socket、Future、
临时目录等资源完成核对后，才能调用唯一的“结束收口”接口。

```text
运行中
  -> 请求结束（取消/TERM）
  -> 有界等待
  -> KILL/强制终止（仍未结束则失败）
  -> 确认线程/进程已结束
  -> 唯一结束收口：关闭资源、失效句柄、删除账本记录
```

### 禁止行为

- 进程仍存活时从进程表删除引用；否则后续零残留检查会失去观察对象。
- 强杀返回失败时启动替代进程；否则会出现新旧进程并存。
- Future/线程仍运行时 `shutdown(wait=False)` 后返回“已释放”。
- 临时目录删除失败仍清空登记表或使用 `ignore_errors=True` 后报告成功。
- 句柄超时只做 `pop/失效`，不执行其释放回调。

### 当前违反点

- `运行核心/运行环境管理器/提供者生命周期.py:497-513` 清理全部时无论停止成功与否都清空进程表。
- `运行核心/运行环境管理器/提供者生命周期.py:463-472` 忽略强制终止结果即移除旧进程并重启。
- `支持库/后端/并发控制支持库/实现/并发控制.py:132-143` 线程池释放使用非等待关闭。
- `支持库/后端/大语言模型支持库/模型连接器/实现/模型连接器.py:146-155` 句柄超时只失效，不调用本地模型释放函数。

### 对外结果契约

释放接口必须返回三态而非简单布尔值：`已结束并已释放`、`结束请求已发出但未收敛`、
`未找到且已幂等`。第二态必须保留资源账本、PID/线程标识和重试入口，禁止伪装成成功；
只有第一态才允许删除唯一权威记录。所有宿主停止、超时、取消、崩溃重启路径统一走该
收口接口，并由零残留核对作为最终验收条件。
