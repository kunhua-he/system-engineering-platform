## 一、裁决依据（不逐条问，按哲学直接定）

**问题**：`平台控制面/` 与 `运行核心/` 全仓 **0 个 `包声明.json`、0 个 `能力定义.json`**，而装配只认三个发现根（`支持库`/`模块库`/`技能库`）→ 落在两层的功能面（发布门禁 / 发布证据 / 指针 / 回滚 / 能力租约 / 作业域 / 开发反馈 / 观测域）**有实现、无能力id、网关调不到**（B5 的 `平台控制面.能力反馈.复核开发反馈` 实测：装配里「反馈」命中 **0**）。

**裁决：装配根改为「声明式」——凡正式目录（`支持库/`、`模块库/`、`技能库/`、`平台控制面/`、`运行核心/`）内含 `包声明.json` 的目录都参与装配。**

依据（`开发文档/项目说明.md`）：

- **第 26 条（能力唯一权威，杜绝旁路）**：治理类功能若只能跑脚本/服务，AI 就多一条执行腿 = 变相旁路 → 不许。所以「删工具改走脚本」的方案直接否决。
- **第 34 条（补进「对应的那个库」）**：能力归属按职责定位，平台治理的职责就在 `平台控制面` → 它必须能登记为正式包。
- **第 35 条（全套齐活才算补完）**：能力定义 + 包级入口注册 + 验证场景 + 说明书 + 升版/重编译/摘要，缺一不可 → 必须有 `包声明.json` 才能「包级入口注册」。
- **第 36 条（补完必须真实验收）**：走唯一网关真实调用 → 必须落进装配。
- **第 37 条（架构问题当场暴露、不给它绕路、不用特例绕过）**：把根列表写死成 3 个，本身就是特例；「只加平台控制面一根」也是特例补丁 → 改为声明式扫描，特例消失。
- **既有先例**：`技能库` 当年就是「单独成根、与支持库/模块库平级」（`项目说明.md` 第 325 行），同一手法。

## 四、验收口径（收口只跑一轮）

1. **定向**（每个工作包）：`python3.14 -m unittest 测试中心.<受影响模块>` + `py_compile`。
2. **波次**：受影响模块合并后跑一次。
3. **HTML 全量**：只对**编译产物**发真实 GET/POST 并发，只看状态码+返回值。
4. **正式发布**：`python3.14 开发工具/发布门禁/运行发布门禁.py`，只跑一次。
5. 装配计数与包口径必须**实测重算**（`find 支持库 模块库 技能库 平台控制面 运行核心 -name 包声明.json | wc -l`），文档里的数字标「实测」并给取证命令。
