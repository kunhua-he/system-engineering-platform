## 0. 分类口径（五选一 → 三分类汇总）

| 代号 | 分类建议（与批1口径对齐） | 判据（引 `开发文档/新建支持库与模块指南.md` 分层归属表） |
|---|---|---|
| A | **落支持库原子能力** | 「最小原子能力」：一个包只做一件事，可被无数模块复用；纯函数/无副作用优先 |
| B | **落模块库** | 「组装能力（多能力组合成一个业务动作）」，且**只经** `获取能力调用器().调用能力(能力id, 参数)` |
| C | **落技能库技能包** | 「固定工作流（先做什么后做什么）→ 技能库 或 Agent 技能，**不新增底座能力**」 |
| D | **留薄壳** | 工具只做入参归一化+派发，实现（含自建落点）搬到原子能力/运行核心 |
| E | **直接删**（合并） | 哲学第 10 条：同一目的已有实现 → 保留最全面的那个，其余蒸馏掉 |

**三分类汇总：原子层 A = 3｜组合层 B = 1｜工作流层 C = 2｜薄壳 D = 3｜删除 E = 1。**

## 3. 不确定项（需华哥/下一批定夺）

1. **观测域怎么落**：`task_observation` 的事件流（4410 行、每工具调用必写）改入运行库，是新增 `观测` 域，还是并入现有 `任务` 域？新增域触发表结构=支持库改动+全书同步，量级不小。
2. **验证账本（`验证历史.jsonl`）算不算运行态**：它被 `公开能力.py`（能力验证状态）、`协作状态.py`（收口比对）双消费，是**跨工具共享的底座运行态**，但既不在运行库 6 域、也没有独立域。若要「运行态一律入库」，需要新域 + 与 `发布` 域（平台控制面自己的 `发布` 表，同名双义）划清边界。本批**未定**。
3. **三套指纹收敛到哪一套**：`协作状态.计算代码指纹`（目录内容 sha256 前 16 位）、`发布治理.当前工作区指纹`（git status 变更文件字节）、`开发工具/项目编译.工作区指纹`（`git ls-files --others` 全量字节，单次约 7 秒）。`未完成事项.md:139` 已说明「收口指纹绑定偏弱（不含命令/环境），判定为非假绿、保留」。上收时保哪一套需拍板。
4. **`verify_and_record` 的「壳边界」**：把执行核改走 `技能库.受控执行.运行技能包` 会改变**执行语义**（沙箱/环境白名单 vs 现在的 `subprocess.run(cwd=项目根)` 直跑），且命令形态（`python3.14 -m 测试中心.X`）需技能包支持「非 scripts 入口」。属**行为变更**，需在技能包设计时单独验证，不建议同批静默替换。
5. **`tool_job_submit` 与 40007 任务系统合并的可行性未证**：40007 按 **能力id** 执行（`任务接入.py` 注册执行器），8766 作业按 **MCP 工具名**执行（`_作业执行` 走 `调用工具`）。两者执行面不同，合并需先定义「统一作业执行器」抽象——本批只给方向，未验证可合并性。
6. **`register_task` 的身份缺口**：它未过 `_有效开工id`，可登记任意 16 位 hex work_id（`协作状态.py:55-60` 只做格式校验）。是否属**安全项**（伪造协作身份污染 26 行台账）需确认后单独修，本批未动代码。

## 5. 一句话结论

这 10 个工具**都不是**「另建一套表/文件」的野路子——`register_task`/`collaboration_status`/`delivery_closeout`/`tool_job_submit` 已经走 `底座运行.db`（协作状态/作业域）和唯一 SQLite 原子能力；**漏网的是两个文件落点**：`task_observation`（`工程缓存/MCP任务观测/事件.jsonl`）与 `verify_and_record`（`开发文档/项目证据/验证历史.jsonl`），它们与「运行态一律入库」定盘不符。**唯一真重复是 `register_requirement`**（同一目的已有 `平台控制面/需求登记.py` 写权威状态库）。8766 侧应只剩「查询/调用」薄壳 + 2 个技能包。
