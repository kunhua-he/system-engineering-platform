## 四、对主任务第二问的明确结论

**「工作区提交能不能直接拆成调 Git/文件能力」→ 能，而且必须拆。** 证据链：

1. **底座已有同义原子能力**：`支持库/后端/版本控制支持库/Git操作/能力定义.json`（包 v1.1.3）里 `版本控制支持库.Git操作.提交`（“git add 指定路径 + git commit 最小原子提交；路径越界 → 路径越界”）、`.创建工作区`、`.查询工作区`、`.关闭工作区` 四个与 `workspace` 的四个操作**一一对应**，且 `.提交` 自带「路径越界」校验（比 MCP 版 `工作区管理.py:377` 的"校验提交根"白名单更底层）。
2. **工具层现在是第二套实现**：`工作区管理.py:90 _运行` 直接 `subprocess.run(["git",...])`，**全程没经 `公共契约.能力契约.调用器`**（`grep` 全文件无 `调用能力`/`真实调用能力`）；连分支名正则（`_校验分支:35`）都与 `Git操作.校验分支名` 重复。
3. **不需要固化成技能**：提交是"一条命令 + 一个白名单前置检查"，不是"多步 + 校验 + 回退"——底座能力已经负责回退语义（失败返回错误码，`git` 自身原子性）。**只有两段需要另作处理**：`合并`（底座缺原子能力，先补能力）和 `关闭前的资源联动清理`（真多步工作流 → 技能库）。
4. **对比 `apply_file_patch`（打补丁）**：它已经是正确样板——真调 `文件系统支持库.文本补丁.应用精确替换`，MCP 层只留路径越界 + 租约前置。**工作区应当被改造成同样的形态**，而不是保留（或重写）裸 git 子进程。

**一句话给华哥**：工作区提交不用做成技能，也不用新增底座能力——`Git操作` 里已经有"提交"了，MCP 这层该做的是**把裸 git 子进程换成调那条能力**（外加补"切换分支/合并"两条），剩下的"关闭前清理"才进技能库。
