## 一、统计口径（先看这里，所有数字都按此口径）

### 1.1 数据源与判定方式

| 项 | 口径 |
|---|---|
| 判定"用过一次" | `事件.jsonl` 中出现一条 `{"事件":"工具完成","工具":<名>}` 记录即计 1 次。该记录由 `MCP工具箱/项目服务.py:970` 在**每次 `call_tool` 分发完成后无条件写入**（含参数非法、工具不存在等失败分支，走的是同一行）→ **覆盖"调用尝试"而非"成功调用"** |
| 记名字段 | 写入的是**归一化后的名字**（`项目服务.py:622` `名称 = 中文名到协议名.get(名称, 名称)` 之后）。2026-09-11 前后老版本未归一化，故历史记录里混有中文名，本统计已做别名归一（见 1.3） |

| **有效次数\*** | 其中"带开工上下文"（`开工id` 非空）的条数。无开工id的调用来自探针/端到端测试/无会话的手工 curl（全局 811/4037 条，占 20.1%）。**判"真实人在用"看这一列** |
| 时间戳 | 记录内为 UTC ISO8601，本报告全部换算为 **CST（UTC+8）** |

## 九、证据可信度说明（必读）

**可信的部分（可直接作删除依据）**

1. 工具级频次只有一个来源但覆盖完整：写入点在 `项目服务.py:970`，位于分发 `try/except` 之后，**成功、参数非法、未知工具名都会写一行**，所以"0 条"等于"真的没被调用过"，而非"失败没记录"。
2. 主证据文件未触发轮转（957 KB vs 8 MiB 上限），窗口 **08-03 → 09-15 连续 44 天**，中途空档日都有前后记录夹住 → 空档是真空档。
3. 僵尸判定做了**双向验证**：既用归一化后的协议名做集合差集，也对 8 个僵尸的工具名 + 中文名在原始文件里做全文 `grep -c`，结果全部为 0。
4. **僵尸判定双源一致**：2026-09-15 现场向运行中的 8766 调 `tools/list`（server_version 1.28.1）返回 50 名，与 09-12 快照**逐名完全相同**，减日志已用名后的差集仍然是同样 8 个 → 结论不依赖任何单一快照。

**不可信 / 不能推出的部分**

1. **窗口下限是 2026-08-03**，这是观测功能上线日，不是"MCP 从这天开始用"。08-03 之前是否调用过**无证据、不得写成"从未"**。
2. **客户端身份没有记录**：事件里只有 `开工id` / `任务id` / `角色`（254 条任务开始全部记 `平台维护者`，单网关模式角色已名存实亡）。"谁在用"只能精确到**开工id/任务粒度**，无法区分 opencode / Hermes / 手工调用。本报告用"有效次数（带开工id）"近似"真实会话使用"。
3. **成功/失败不可分**：`工具完成` 记录未落 `退出码/错误码`（`任务观测.py::工具事件` 支持这俩参数，`项目服务.py:970` 未传）。所以"次数"= 调用尝试次数，**含失败与误用**。
4. 旁证源窗口都短于主证据：`安全审计.jsonl` 只覆盖 **09-11 20:51 之后**；`mcp_http_8766.log` 只到 **09-11 22:37**。它们**不能**用来反推 09-11 之前的工具使用。
5. 灰色量：`tool_catalog`(240) 与 `role_profile`(236) 的绝大多数是**自动化发现**（无开工上下文 220/212），把这两个当作"人在用"会严重高估。
6. 时间戳字段混用：主证据记录内 `时间` 是 UTC，同文件另有本地 `时间戳`（epoch）；本报告统一按 UTC→CST 换算，选取窗口边界时未用 `monotonic` 字段。
