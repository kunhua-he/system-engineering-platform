# 批量开发流程与资源释放收口

## 发现的问题

- 上一轮 10 个模块 HTTP 黑盒化已经完成，但执行过程中反复运行全量发布门禁，验证粒度过大，导致同一批改动重复等待。
- 项目 MCP 已具备 `project_context`、代码地图、`mcp_feedback`、`verify_and_record` 和分级验证计划能力，但这套过程需要作为项目级开发技能固定下来。
- 资源释放专项仍需继续核对：提供者停止/强杀后只能在确认进程结束时移除权威记录；线程池、模型连接句柄的释放必须避免“已返回成功但后台仍在运行”的假收口。

## 解决方案

- 将开发过程沉淀到项目 MCP 记忆：先开工上下文和代码地图，再冻结工作包；小改只做定向测试，一批改动做受影响阶段，全部完成后才做一次全量和发布门禁。
- 本轮优先处理资源释放边界，按同类问题批量检查提供者生命周期、并发控制和模型连接器；不直接删除必要互斥，不以关闭字典记录代替真实资源结束。
- 所有修改先走代码地图定位，验证只使用项目统一入口；验证成功后先提交 MCP 反馈，再由 `verify_and_record` 记录成功证据。

## 影响范围

- 项目 MCP 记忆：批量开发与分级验证流程。
- `运行核心/运行环境管理器/提供者生命周期.py`：提供者进程停止、强杀、重启、清理和资源终态。
- `支持库/后端/并发控制支持库/实现/并发控制.py`：线程池句柄释放与失败结果。
- `支持库/后端/大语言模型支持库/模型连接器/实现/模型连接器.py`：句柄超时、释放回调和模型资源终态。
- 对应 `测试中心/` 定向测试与项目 MCP 验证账本。

---
## 实际结果

- 已把“项目 MCP 开工上下文 → 代码地图 → 工作包定向验证 → MCP 反馈 → 成功验证入账”的开发流程写入项目记忆：`开发文档/项目记忆/批量开发流程与分级验证.md`。
- 修复模型连接器与并发控制的句柄表整数/字符串漂移；对外返回字符串句柄，公共状态机继续使用整数 id。
- 模型连接器释放回调改为锁外执行；释放失败保留连接账本和“释放失败”状态，允许后续重试；只有真实回调成功才失效句柄。
- 本地模型进程强杀失败时保留进程表记录，不启动替代进程，也不伪装为已释放。
- 线程池关闭采用有界等待；超时返回“资源未收敛”并保留账本，收敛后重试才能完成句柄失效。
- 新增 `测试中心/支持库/测试_模型连接与并发释放.py`，覆盖 3 个释放终态场景。

## 调用方式

- 工作包验证：`python3.14 测试中心/运行测试.py --测试文件 测试中心/支持库/测试_模型连接与并发释放.py --并行数 0`
- 受影响验证波次：`python3.14 测试中心/运行测试.py --测试文件 测试中心/支持库/测试_模型连接与并发释放.py 测试中心/运行核心/测试_提供者生命周期.py 测试中心/运行核心/测试_句柄账本持久化.py 测试中心/运行核心/测试_资源句柄网关.py 测试中心/资源并发/测试_资源并发.py --并行数 4`
- 结果：新增工作包 3/3 通过；受影响验证 5 个测试文件全部退出码 0；静态编译和 `git diff --check` 通过。
- 当前边界：本轮未跑常规全量和正式发布门禁，避免把工作包验证误当阶段收口；待本批代码提交并完成后续批次，再按阶段收口执行。
