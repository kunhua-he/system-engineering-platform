## 一、五维机制的取证结论（照代码现场，不照注释）

**总判定：五维 = 同一套「进程内固定窗口计数 + 进程内并发计数」换了五个维度键。
没有持久维，没有跨进程维，没有滑动窗口。**

| 维度 | 状态存在哪 | 由谁比对 | 跨重启 | 跨进程/多实例 |
| --- | --- | --- | --- | --- |
| 项目 | 内存 `self.状态表[("项目", 项目id)]`（`限流器.py:115-116` 建键、`:91` 声明） | 仅 `进入请求`（`:173` 频率、`:168` 并发） | 不保留 | 不生效 |
| 用户 | 内存 `self.状态表[("用户", 用户id)]`（同一次调用的 `_维度表`，`:97-109`） | 仅 `进入请求` | 不保留 | 不生效 |
| 能力 | 内存 `self.状态表[("能力", 能力id)]`（同上） | 仅 `进入请求` | 不保留 | 不生效 |
| 任务 | 内存 `self.状态表[("任务", 任务id)]`（同上） | 仅 `进入请求`；`进入任务`（`:203-211`）**只比对全局 `任务数`** | 不保留 | 不生效 |
| 提供者 | 内存 `self.状态表[("提供者", 提供者)]`（同上） | 仅 `进入请求` | 不保留 | 不生效 |

补充事实（都有 `文件:行号` 落点）：

- **五维共用一套结构**：`频率上限表`（`限流器.py:78-84`）只是给同一个 `限流状态` 结构体
  （`:21-28`）配了五个上限数字；判定逻辑一份（`进入请求` 内 `:168-176`），不是五套。
- **维度键非必建**：`_维度表`（`:97-109`）用 `if 键` 过滤空串——调用方不传 `提供者`，该维**不存在**（不是放行也不是拒绝）。
- **窗口是固定还是滑动**：`_状态`（`:111-125`）：`现在 - 状态.窗口开始 >= self.窗口秒` 时
  `窗口开始 = 现在; 窗口计数 = 0` —— **整窗清零，固定窗口**。窗口边界前后各一波可合计到上限两倍。
- **状态是否持久**：全部是实例属性——`状态表`（`:91`）、`请求并发`/`任务数`/`流式连接数`（`:88-90`）；
  源码里没有任何 `sqlite3` / `pickle` / `open(` / `shelve` / `mmap` 痕迹（核对脚本断言）。
- **权威状态库里有没有限流表**：**没有**。2026-09-17 只读实测
  `工程缓存/平台控制面/权威状态.db`（335872 字节）共 22 张表：
  事务、信任、元信息、制品、占用租约、发布、句柄、回收证据、工作包、引用计数、核心快照、
  激活指针、租约、策略、能力反馈、能力条目、角色授予、证据、资源版本、进程、锁、需求
  —— **无任何「限流 / rate / 限速」相关表**。`工程缓存/运行数据/权威状态.db` 为 4096 字节空库。
  ⇒ **没有任何一个维度是持久的**（含拒绝记录：`拒绝记录` 是 `deque(maxlen=拒绝记录上限)`，`:92-94`，只在内存）。
- **实例从哪来**：`网关核心.py:701` `self.限流器 = 限流器实例 or 限流器()` —— **每个网关实例一个限流器**，
  多进程/多副本就是各发一份配额。锁是 `threading.RLock`（`:87`），**只管线程不管进程**。
- **`进入任务` / `进入流式` 全仓无调用方**：`rg "进入任务|进入流式"`（排除 `工程缓存/`）只命中定义处
  （`限流器.py:203/217`），且它们收的五个维度参数**不参与判定**。
  流式真正的并发上限另有实现：`运行核心/统一网关/流式HTTP.py:228` `_并发信号量`（与本闸门独立）。

## 二、名字 ↔ 实现对照表

| 名字里的说法 | 实现里的实况 | 判定 |
| --- | --- | --- |
| 「五维」 | 五个维度**键**，共用同一套固定窗口计数 + 并发计数（同一 `限流状态` / 同一 `锁` / 同一判定代码） | **字面真、抽象高**：维度键不同 ≠ 机制不同 |
| 「五维限流」 | 只有 `进入请求` 路径真比五维；`进入任务`/`进入流式` 不比维度且无调用方 | **部分真**（任务维/能力维在闸门层面没生效） |
| 「治理」 | 只有拒绝计数与拒绝记录（内存 deque，上限 10000） | **词大于实**：没有配额分配、没有优先级、没有退避协商 |
| 「并发治理」 | 全局并发 + 单维度并发两个整数闸门，一把 RLock | **真**（保护能力存在且生效，不得删） |
| 「限流」（窗口语义） | **固定窗口**（整窗清零），不是滑动窗口、不是令牌桶、不是漏桶 | **真**，但窗口形态没被写下来 |
| 「限流」（可靠性语义） | **进程内**：不落盘、不进权威状态库、不跨重启、不跨实例、不跨进程 | **过去没写下来**，这才是真问题 |
| 「限流」（对外契约） | 错误码 `限流` → HTTP 429 + 固定中文说明 | **真**，契约不得改 |

**逐维真假**：项目 / 用户 / 能力 / 任务 / 提供者 —— **五维都是真的**（`进入请求` 确实分别计数、分别判上限），
只是：①机制是同一套；②任务维与能力维只在 `进入请求` 生效，独立闸门（`进入任务`/`进入流式`）没生效。

## 三、收口选择：**(a) 修名字与文档，不改机制**

理由（第 11 条 1 项「缺能力先证不可替代」+ 本平台安全边界是本机私有部署）：

1. **机制对本边界够用**：单进程网关 + 本机私有部署下，进程内固定窗口正是目标形态——零 IPC、零网络、零一致性代价。
   改成 SQLite/共享内存/Redis 是**为假想需求付真代价**（加 IO、加故障面），本平台当前没有多实例需求与证据。
2. **真问题是「边界没写下来」**：模块首行只写「五维限流与并发治理」，抽象等级高于实现可靠性等级，
   调用方会误以为跨重启/跨实例生效，扩容或双开时静默拿到 N 倍配额。**本轮收口的就是这一句。**
3. 因此：**改措辞与文档，一行实现逻辑都不改**；并发保护、429 契约、中文文案全部保持原样。

## 五、剩余风险

1. **多实例部署仍然不成立**（机制未变）：出现多进程/多副本、或配额要跨重启延续、或限流要作为
   SLA/计费口径时，必须落地外部共享限流——**平台当前不提供**。触发条件已写进 `限流边界说明.md`。
2. **`运行核心/统一网关/网关核心.py:1` 仍写「五维限流」**：该文件不在本轮允许修改域内（写者降级纪律），
   措辞未动；语义上不算错（网关确实按五维键调 `进入请求`），但读的人容易再次高估，已在说明文档记为遗留。
3. **固定窗口边界效应**：窗口边界前后各一波流量可合计打到上限两倍。不是 bug，是固定窗口固有语义；
   单机私有部署影响有限，已写进说明文档供排期参考。
4. **`进入任务` / `进入流式` 无调用方**：属"留口子"而非"在生效"，已加注释说明；若将来有人接上，
   必须补五维比对，否则「任务维/能力维」名义存在、实际不生效。
5. **行号会漂移**：本文件与说明文档里的行号均为 2026-09-17 快照；核对请以符号名（`状态表` / `_状态` /
   `进入请求`）为准，核对脚本已按符号名而非行号断言。
