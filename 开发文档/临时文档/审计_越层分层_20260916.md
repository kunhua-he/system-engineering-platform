- **建议修法**（二选一，推荐 a）：

### 第 4 条（反向越层，同时也是「错层」）

- **位置**：`模块库/组件生成/实现/组件生成.py:120` `from 开发工具.组件规范.模块模板生成器 import 生成模块模板`。
- **实测证据**：`组件生成`（模块库正式模块）的唯一模板实现来自终端层；下游闭包实测 **17 个生产文件**（15 个在 `开发工具` 内 + `模块库/组件生成/__init__.py` 与 `模块库/组件生成/实现/组件生成.py`）。
- **判据**：`允许依赖表["模块库"] = {公共契约, 支持库}` —— 模块库不得依赖 开发工具；且 开发工具 是**终端层**，定义上「没有任何一层被允许依赖它」。若要放行，就是在终端层之下再造一个「下层」，终端的语义即被破坏。
- **根因（不是调用方错，是被调用方位置错）**：`开发工具/组件规范/` 里这批代码**根本不是工具**——`模块模板生成器.py` 只导入 `公共契约.基础类型.结果类型` + `公共契约.版本规则.契约版本` + 同目录 `组件规范`；`完整性摘要.py` 只导入 `公共契约.正式根`；零第三方、零宿主、零 I/O 编排。这是标准的「支持库原子能力」，却被放在终端层，于是把生产层逼成了反向依赖。
- **建议修法**：把 `开发工具/组件规范/` 整目录下沉到 支持库 层（建议 `支持库/后端/组件规范支持库/`），按正式包补齐九要素（`包声明.json`/`能力契约`/`依赖契约`/`配置契约`/`权限契约`/`实现`/`验证场景`/`说明`/`完整性摘要`），暴露包级公开入口；然后 `模块库/组件生成` 改为从 `支持库.后端.组件规范支持库` 导入——**这条授权本来就已在层表里**（`模块库: {公共契约, 支持库}`），改完不吃新授权。
- **影响面**：1 条红消除；7 个文件（`完整性摘要.py`/`组件规范.py`/`模块模板生成器.py`/`支持库模板生成器.py`/`技能模板生成器.py`/`核心快照模板.py`/`说明书生成器.py`）需迁址 + 建包；下游 17 个生产文件的 import 路径需同批改（15 个在工具层内，改动零风险）。

### 偏差 C：表的唯一事实源地位被代码内联豁免打破

- **位置**：`运行核心/依赖防火墙.py:395-397`
  ```python
  if (来源层 == "运行核心"
          and str(文件.relative_to(系统根)) == "运行核心/启动运行核心网关.py"
          and 顶层 == "后端核心"):
      continue
  ```
- **实测**：`运行核心/启动运行核心网关.py` 是唯一一处 运行核心 → 后端核心。
- **判据**：`允许依赖表["运行核心"] = {公共契约, 支持库}` 不含 后端核心。豁免按「文件名白名单」写在审计函数体里，改文件名即静默失效，且下一轮审计读表的人看不到这条允许方向。
- **建议修法**：把「启动编排边界」这一事实也登记进表（如 `允许依赖表` 旁加 `文件级豁免表: dict[str, set[str]]`，键=相对路径、值=允许的目标层集合），审计函数只读表，不再内联文件名。
- **影响面**：1 个文件 3 行；不改行为，只把豁免从「代码」搬到「表」。

### 偏差 D：模块库 → 支持库 授权空转

- **实测**：`允许依赖表["模块库"]` 授权了 `支持库`，全仓实测 **0 处** 使用。
- **判据**：层表按「最小授权」原则登记（表内注释第 65-66 行自述「按最小授权登记；不开放任意层导入」），一条空转授权与该原则不符；而模块库**真正**需要的能力（模板生成器）恰恰在未授权的 开发工具 里。
- **结论**：这不是「表该收紧」，而是**能力放错了层**——授权早已准备好接收它，只是能力没搬过来。
- **修法**：随 一.4 下沉 `开发工具/组件规范/` → 支持库，这条授权立刻由空转变为在用。

### 偏差 E：前端核心 的授权全部空转

- **实测**：`前端核心` 下只有 3 个 .py（`浏览器交互.py`/`前端核心.py`/`渲染提供者.py`），**不导入任何其他层**。
- **判据**：`允许依赖表["前端核心"] = {公共契约, 运行核心}` 两条均 0 使用。要么是「预留授权」（应加注释注明预留期），要么前端核心尚未接入。
- **建议修法**：加注释标注「预留」，或按实际收口为 `set()`；不要留一条无声的空授权。

### 偏差 F：头注释与 允许依赖表 描述不一致（同文件内两个口径）

| 文件头注释（`依赖防火墙.py:3-11`） | 允许依赖表（第 57-75 行） |
|---|---|
| `前端核心 -> 公共契约和私有引导适配器` | `{"公共契约", "运行核心"}` —— 无「私有引导适配器」这个层 |
| `后端核心 -> 公共契约和私有引导适配器` | `{"公共契约", "运行核心"}` —— 同上 |
| `模块库 -> 公共契约和公开能力调度` | `{"公共契约", "支持库"}` —— 无「公开能力调度」 |
| `运行核心 -> 公共契约和支持库公开入口` | `{"公共契约", "支持库"}` —— 一致 |

- **判据**：同一文件里「注释描述的方向」与「表里的方向」不是同一个东西；后续按注释改表必然改错。
- **建议修法**：把第 3-11 行注释改成由 `允许依赖表` 自动渲染（或直接删注释，只留表 + 一句「表即唯一事实源」）。
- **影响面**：1 文件；纯文档漂移。

### 偏差 G：`其他` 层不在表内，豁免内联

- **位置**：`运行核心/依赖防火墙.py:399-400` `if 来源层 == "其他": continue  # 工具/门禁/验证 文件可依赖任意层`。
- **实测**：`层名称表` 有 `"其他"` 键，`允许依赖表` **没有**。落进「其他」的顶层目录实测为：`客户端`、`启动监督器`、`运维脚本`、`测试中心`、`示例项目`、`工程缓存`、`开发文档`（另加 `.git`/`.codegraph`/`.pytest_cache`/`.ruff_cache`）。
- **判据**：`客户端`（构建平台客户端）、`启动监督器`、`运维脚本` 是**生产用途目录**，却享有「可依赖任意层、完全不受方向审计」的待遇；其中 `客户端/构建平台客户端.py:411,458` 直接 `from 开发工具.项目编译.项目编译器 import …`、`:612` `from 平台控制面.包仓库.平台客户端制品 import …` —— 同样是「生产依赖终端层」的形状，只因落在「其他」层而全数放行。
- **建议修法**：给 `允许依赖表` 补一个显式的 `"其他"` 键（值 = 全集或显式枚举），把「工具/门禁/验证不受方向限制」这条语义写入表；同时确认 `客户端`/`启动监督器`/`运维脚本` 是否应登记为层。
- **影响面**：不影响当前 4 条红，但决定下一批「生产 → 工具」反向依赖会不会在无审计区再次长出来。

### 偏差 H：标准/白名单注释陈旧（易误导改表）

- `依赖防火墙.py:71-73` 注释仍在说「`开发工具/开发入口.py`…存量直引 `MCP工具箱.发布治理`」「MCP工具箱 登记为层之后，这里必须同批放行」——`MCP工具箱` 已于 2026-09-15 随 D 清场删除，该注释描述的层已不存在。

- **修法**：删/改这两段注释，避免下一轮按它改表。

|---|---|---|

| `项目编译` | 公共契约(1) | **部分**（#5） |
| `契约编译` | 公共契约(4) | 否——产出契约编译产物，属门禁链 |
| `能力网关` | 公共契约(1) | 否——网关宿主 |
| `轻代码前端编辑器` | 公共契约(1) | 待定（无外部下游） |
| `HTML验证`/`说明书生成`/`快速编译`/`能力搜索` | 公共契约/支持库/运行核心 | 否——门禁/验证链 |
| `发布门禁`/`复用审计`/`组件合规`/`统一验证`/`统一能力入口`/`薄壳` | 后端核心/运行核心/项目适配层/模块库/平台控制面/支持库 | 否——工具/宿主，本就该在终端层 |

结论：**「本该在下层却挂在上层」的模块共 5 组**（1 个包 `组件规范/` 的 7 个文件 + 1 个 `项目编译/项目编译器.py`），其余 `开发工具` 子包位置正确。

## 四、“同包入口导实现”的口径不一致（各审计器判定对照）

### 背景口径（唯一权威说法）

`运行核心/依赖防火墙.py:321` 自述：「强制拒绝 1：跨包导入 `实现/` 目录（**同包 `__init__` 导自身实现是合法入口模式**）」，同包判定按**路径段逐段相等**（第 323-328 行），文件包段为空则不放行。

全仓实测「同包入口导实现」共 **521 处**（`支持库`：适配层各 `*提供者/__init__.py`、`后端/各支持库/**/__init__.py`；`模块库`：`组件生成`/`知识检索`/`图像处理`/`直播逐字稿` 等；`技能库`：`技能库/后端/技能库/__init__.py`；`平台控制面`：`能力反馈`/`能力目录`/`统一入口`/`授权`/`发布管理`/`提供者`/`包仓库`/`备份恢复`/`平台状态`）。跨包 `实现` 直连实测 **0 处**。

### 四个审计器的判定对照

| # | 审计器 | 作用域 | 「同包 `__init__` 导自身 `实现/`」判定 | 实测证据 |
|---|---|---|---|---|
| 1 | `运行核心/依赖防火墙.py:321-330` | **全部 10 层**（剪枝 测试中心/示例项目/开发文档/工程缓存），635 文件 | **豁免**：路径段逐段相等即同包，放行 | `审计依赖()` 4 条违规中 **0 条**属「实现目录」类 |

### 硬对抗实例（同一行代码，一个放行、一个判红）

样本：`模块库/能力目录/实现/能力目录.py:58` → `import 模块库.能力目录.实现.能力索引`

取证：`python3.14 /tmp/口径对照.py`（只读；`fw.审计依赖` / `mk.审计模块边界` / `tg.审计模块库`）

```
[依赖防火墙]         违规: []                                    ← 放行
[能力调用图审计]      能力目录 相关违规: []                        ← 放行
[模块合规]           成功: False  错误码: IMPORT_VIOLATION
                     {'文件':'模块库/能力目录/实现/能力目录.py','行':58,
                      '模块':'模块库.能力目录.实现.能力索引','类别':'白名单外导入'}   ← 判红
[模块合规._分类导入]  '模块库.能力目录.实现.能力索引' -> {'类别': '白名单外导入'}
```

- **判据差异**：防火墙/能力调用图审计按「**路径段**」认同包；模块合规按「**根目录名 + 白名单**」分类，`模块库.*` 直接落进「白名单外导入」，从不做同包判断。
- **建议修法**：以 `运行核心/依赖防火墙.py` 的口径为唯一权威（它自述为「唯一 AST 依赖审计」）。在 `模块合规.py` 增补同一套 `_同包实现()` 判定（或直接 `from 运行核心.依赖防火墙 import` 复用），并**把作用域对齐到包级 `__init__.py`**——否则「同包入口导实现」这一模式在模块合规里不但不豁免，还根本不在扫描范围内，两个审计器覆盖的不是同一批文件。
- **影响面**：口径对抗实例实测 **1 处**（`模块库/能力目录/实现/能力目录.py:58`）；作用域差异影响 **18 个模块包**（模块库全部包级 `__init__.py` 均不在 模块合规 扫描范围内，却都在 能力调用图审计 范围内）。另：模块合规 还有 6 条 `格式解析原子操作`（`json.loads/dumps`）同类违规，属「行为调用图」口径，与本次越层无关，另计。

### 附带发现：跨审计器的**陈旧行号引用**

`开发工具/复用审计/能力调用图审计.py:106` 的 docstring 写「与 `运行核心/依赖防火墙.py:261-269` 同口径」——`依赖防火墙.py` 现共 408 行，同包判定实际在 **321-330 行**，261-269 早被后续改动顶走。

- **建议修法**：引用改为 `依赖防火墙.py 同包判定（强制拒绝 1）` 的函数/规则名，不写行号；或直接 `from 运行核心.依赖防火墙 import` 复用同一判定函数，从根上消灭「两处实现同一口径」。
- **影响面**：1 处注释；但正因为它靠「同口径」自我背书却不复用代码，才长出了第 3 号审计器的分歧。

## 五、结论与收口建议（按性价比排序）

| 优先级 | 动作 | 消除 | 改动面 |
|---|---|---|---|
| **P0** | `允许依赖表["开发工具"]` 补 `"平台控制面"` | 越层 3/4 条 | 1 文件 1 行 |
| **P0** | 把 `运行核心 → 后端核心` 的文件级豁免搬进表（新增 `文件级豁免表`） | 偏差 C，恢复「表=唯一事实源」 | 1 文件 ~5 行 |
| **P1** | `开发工具/组件规范/` 整目录下沉 `支持库/后端/组件规范支持库/`，补齐九要素 | 越层第 4 条 + 错层 #1–#4 + 偏差 D（空转授权转在用） | 7 文件迁址 + 建包；下游 17 文件改 import |
| **P1** | `模块合规._分类导入` 复刻 `依赖防火墙` 的同包实现判定，作用域对齐包级 `__init__.py` | 口径不一致（1 处硬对抗 + 18 个模块包作用域差） | 1 文件 |
| **P2** | 允许依赖表补 `"其他"` 键；确认 `客户端`/`启动监督器`/`运维脚本` 是否登记为层 | 偏差 G（无审计区） | 1 文件 + 决策 |
| **P2** | `项目编译/项目编译器.py` 同批下沉或显式登记 | 错层 #5（潜在第 5 条越层） | 1 文件 |
| **P3** | 清理头注释与 `MCP工具箱` 残留注释；`前端核心` 授权标注「预留」 | 偏差 F/H/E | 纯文档 |

**一句话**：4 条越层里 3 条是「层表漏补一个正式根授权的登记副作用」；第 4 条不是调用方错，是 `开发工具/组件规范/` 这批纯能力（含唯一摘要生成器）挂错了层——把它下沉到 支持库，既消掉唯一一条「生产 → 工具」反向依赖，又把层表里空转的 `模块库 → 支持库` 授权变成在用，还能顺带统一各审计器对「同包入口导实现」的判定。
