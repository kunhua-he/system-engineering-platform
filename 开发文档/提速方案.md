## 二、第 0 层：热加载（已落地）

### 现象

平台所有管理端（协议名 MCP）的改动都被"必须重启"卡住：管理端启动时把全部工具实现一次性顶层导入，之后改源码不重启就不生效。所以每次修工具，都要重启一次共享的管理端进程 —— 而管理端是**全机单进程共享**，重启会打断别的会话正在跑的工具。

### 原因

`MCP工具箱/项目服务.py` 用一组顶层导入把工具实现拉进内存（`from .协作状态 import 收口登记` 这一串），内存里那份和磁盘上的源码不再同步。

### 改法

新增 `MCP工具箱/热重载.py`，并在 `项目服务.py` 的**工具调用入口**比一次源码时间戳：

- **拓扑序重载**：只认同包依赖形式（`from .X import ...`），按"被依赖者在前"排序后再重载。顺序不能错 —— 先重载依赖方、后重载被依赖方，依赖方拿到的仍是旧的被依赖对象。
- **精确回填**：只把模块**自己定义**的函数/类换进入口全局（判据是该对象的 `__module__` 指向本模块），避免把模块内部 import 进来的同名符号（如 `pathlib.Path`）误覆盖到入口模块的同名全局上。
- **失败不炸、可自愈**：重载失败不抛错、保留旧实现、**不更新快照**，所以源码修好后的下一次变更会自动重试。
- **刻意不做的边界**：不重载入口自身、不重载其他包（`公共契约` / `运行核心` / `平台控制面`）。**工具的新增/删除/参数表变更仍需重启** —— 热加载只覆盖"改了实现"这一种最频繁的情况。

同时暴露一个手动开关：工具 `reload_tool_modules`（中文名"热重载工具模块"），可主动触发一次并返回本次重载了哪些模块。

### 实测

| 验证项 | 结果 |
|--------|------|
| 拓扑序 | 17 个工具模块排序完成；3 条同包依赖边（使用反馈→验证门禁、验证门禁→发布治理、测试资源→工作区管理）前置关系全部正确 |
| 改源码即时生效 | 追加一行后调用，返回 `['使用反馈']`；新定义进入模块；入口全局的函数对象已换成新对象 |
| 坏源码 | 返回空、**不抛错**、旧实现保留 |
| 修好自愈 | 坏源码恢复后下一次调用自动重载成功 |
| 副作用 | 探针文件内容已原样还原，`git status` 该文件无脏改 |

### 风险

极低。热加载只读源码时间戳与重新执行模块；失败路径已实测为"保旧不炸"。

### 剩余边界

新工具、删工具、改参数表 → 仍要重启。**所以重启这件事不做成"随改随重启"，而是"凑齐一批、一次性重启"**，见第六节。

## 三、提速项 1：全仓扫描（已落地）

### 现象

依赖防火墙（进发布门禁，每次发布都跑）全仓审计要 **11.25 秒**。它是最慢的一项全仓检查。

### 原因（已用源码定位，非猜测）

`运行核心/依赖防火墙.py` 原先这样取文件：

```python
for 文件 in sorted(实际目录.rglob("*.py")):
    if "pycache" in str(文件) or "工程缓存" in str(文件) or "测试中心" in str(文件) \
            or "示例项目" in str(文件) or "验证器" in str(文件) or "开发文档" in str(文件):
        continue
```

排除清单本身没错，但**排除发生在遍历产出之后**：`rglob` 已经把全仓 **72678 个 `.py`** 全部枚举、排序完，其中 **71775 个在 `工程缓存/`** 里（各虚拟环境与编译制品）。真正要解析的只有 583 个文件，**语法解析只占 0.42 秒** —— 11 秒里九成以上是白跑的文件遍历。

### 改法

改成**在进入目录时就剪枝**，不落进被排除的目录：

```python
排除片段表 = ("pycache", "工程缓存", "测试中心", "示例项目", "验证器", "开发文档")

def _遍历待审计源码(根: Path) -> list[Path]:
    for 当前根, 子目录名表, 文件名表 in os.walk(根):
        子目录名表[:] = [名 for 名 in 子目录名表 if not any(片段 in 名 for 片段 in 排除片段表)]
        ...
```

**为什么语义完全等价**：原是"整条路径含某片段就跳过"。一条路径含某片段，当且仅当它某个目录名或文件名自身含该片段。所以"目录名/文件名任一含片段就剪掉"与原先**筛出的文件集合逐条相同**，只是不再往下走。

### 实测

| 口径 | 改前 | 改后 |
|------|------|------|
| 全仓耗时 | **11.249 秒** | **1.020 秒（11 倍）** |
| 审计文件数 | 583 | 583（**一致**） |
| 违规清单 | 0 条 | 0 条（**逐条一致**） |

定向测试 `测试中心.开发工具.测试_依赖生命周期审计` 通过。这次提速直接落到每次发布必经的门禁上。

### 同一类病的第二处：判定"不改"

`开发工具/复用审计/能力调用图审计.py` 有一模一样的写法（`实际目录.rglob("实现/*.py")`），传**系统根**时 7.53 秒。但查过全部调用方：

- `开发工具/复用审计/运行审计.py` 传的是命令行给的目录；
- 两个测试传的是 `模块库` / `模块库根`。

**没有任何真实调用方传系统根** —— 7.53 秒只是合成测法，实际路径上它只扫 `模块库`（0.09 秒）。改没被触发的代码等于加一条永不执行的路径，**故不改**。

### 一个"可选但不划算"的选项

有人建议给依赖防火墙加**落盘缓存 + 内容指纹失效**。可以，但**暂不做**：现在 1.02 秒里 0.42 秒是语法解析，剩下的摊在路径与包声明读取上；落盘缓存要靠内容指纹判断失效，等于**新增一个"缓存过期"故障面**去换不到 1 秒。不符合"稳定可靠十分重要"。若以后全仓文件数翻几倍，再议。

## 四、提速项 2：长任务（待落地）

长任务指直播逐字稿的"全自动精校"：75 分钟场，纯模型裁决耗时在**十分钟级以上**。已核实的当前事实（均从源码读出）：

- 窗口裁决并发默认 **3**（`实现/精校裁决.py`，同一句柄可并发）；
- 疑难说明每窗最多 **40 条**、单条最长 **120 字**（`实现/窗口切分.py`）；
- 复核证据每窗截断到 **2500 字**（`实现/复核编排.py`）；
- 加帽之前的历史实测是单窗请求体 **2575~10339 字**，约 600 字输入要 39 秒（来源：`窗口切分.py` 注释、`开发文档/未完成事项.md` P2 条）。

下面三项按**"先做最稳的"**排序，每项都写明风险与验证方法。

### 2a　裁决结果复用（先做，质量零影响）

**现象**：`实现/全自动精校.py` 只**写** `缓存/裁决/窗口_XXXX.json`，**从不读回**。同一段音频跑两次、同一场次跨多次运行、或不同场次出现相同话术，每次都要把模型重跑一遍。

**原因**：只写了落盘，没做"已有就复用"的判断。

**改法**：照抄同一模块里**已经存在**的复用写法 —— `实现/复核调度.py::_读已有复核` + `续跑=True`（文件在、区间 id 一致、轮次非空 → 直接复用）。给裁决窗口加同型读回，键取**输入指纹**（窗口底稿文本 + 疑难说明 + 证据 + 提示词 + 模式，取内容摘要）。指纹一致 → 复用；任一变化 → 重算。

**为什么质量零影响**：同输入同配置必然同输出，复用取的正是上次那次的产物；指纹把"输入变了"这件事挡在外面。

**预期收益**：重复跑（调试、返工、跨场次相同话术）时**跳过整个模型调用**，这部分从"分钟级"变成"毫秒级"。首次跑无收益。

**风险**：低。唯一要小心的是**指纹必须覆盖全部影响输出的入参**，漏一个就会把旧结果错当新结果用。

**怎么验**：同一输入连跑两次，第二次必须命中复用且产物逐字节相同；改动任一入参（如换提示词）后必须重算而非复用。

### 2b　请求体再瘦（后做，有质量风险）

**现象**：单窗请求体现由"底稿文本 + 疑难说明（≤40 条×120 字）+ 证据（≤2500 字）"拼成，其中**疑难说明把窗口文本又抄了一遍**（同一段文字在"底稿文本"里已出现，在"疑难说明"里再出现一次）。

**改法（按风险从低到高）**：

提速项 2b-1：**只去重、不减信息**：疑难说明只保留"时间点 + 原因 + 文本短前缀"，不再整条抄一遍全文 —— 模型靠时间点在底稿里定位即可。这是**纯压缩，零信息损失**。
提速项 2b-2：每窗疑难条数 40 → 8（保留最疑难的，排序已按"原因条数降序"）。
提速项 2b-3：证据 2500 → 1200 字。

提速项 2b-1建议做；提速项 2b-2、2b-3**必须 A/B 实测**：它们是**有损**的，减的是模型判疑难时能看到的线索，可能把"能揪出的错"变成"揪不出"。

**风险**：中。精校质量是这个模块的命根子，宁可慢也不能漏错。

**怎么验**：取同一真实场次、同一模式，改前改后各跑一次，**逐窗口比对精校文本差异**，再人工抽查被改动过的窗口是否变差。质量不降才留，降了就退回。

### 2c　窗口并发 3 → 5（最后，先测）

**现象**：窗口裁决默认并发 3（`精校裁决.py`）。

**为什么排最后**：本模块**已有一次实打实的反面教训** —— 提交 `85a2940` 标题就是"并发场次默认改回 1 —— 实测场间并发反而更慢"。原因是提供端并发上限有限（MLX Whisper 资源预算为 1），盲目压并发会撞上游限流（503）反而整体更慢。

**改法**：**先测再改**。加一次 3 / 4 / 5 的对照实测，看是否触发上游 503、看总耗时是否真的下降；只有**明确不触发限流且总耗时下降**时才提默认值。窗口并发与场间并发不是同一回事，但同一个上游，必须用数据说话。

**风险**：中。可能反而更慢，且失败发生在长场次跑到一半时。

## 五、提速项 3：进程冷启动（大部分本来就常驻）

### 现象

"冷启动慢"多半是**误判**：平台该常驻的本来就已经常驻 ——

| 已常驻的东西 | 说明 |
|--------------|------|
| 网关 40007 | 常驻进程，且有**热接入**：改包后 `运维脚本/热接入.py` 增量重装配，单次约 0.2 秒，**不重启进程**（见 `开发文档/决策记录/0008`） |
| 管理端 8766 | 常驻进程；工具实现改动现已热加载（第 0 层） |
| 代码地图 | 常驻的单个 SQLite（`.codegraph/codegraph.db`，约 34.7MB），已有节点/边/文件指纹 |
| 平台状态库 | 常驻的单个 SQLite（`平台控制面/平台状态.py`） |

### 真正缺的是什么

**缺的不是"再起一个常驻"，而是"审计工具去读这些常驻，而不是每次重新算一遍"。** 举两个具体缺口：

提速项 3-1：**代码地图没有 Python 直读器**。`MCP工具箱/项目服务.py` 里要用代码地图，靠 shell 出去调外部命令；而那张 SQLite 用 Python 自带的 `sqlite3` 就能**只读直读**（表里已有 `content_hash` / `size` / `node_count`，天然可做"文件变了没"的判断）。接上之后，"某文件是什么结构/被谁调用"这类查询不必再起进程。
提速项 3-2：**长工具仍同步占管理端线程**。管理端是**全机单进程共享**：一个会话裸跑慢工具，会把另一个会话的调用堵在队里 —— 这才是"另一个会话一开发我就卡一下"的头号真因（不是文件冲突）。**本仓当前没有后台作业能力**（8766 管理端注册的 45 个工具里没有 `tool_job_submit` 之类，全仓也无作业/job 能力），所以现在只能靠**错峰**缓解（别同时裸跑长工具），根治要从零补一个"提交作业 + 轮询 + 可取回"的异步模型（属新能力，见 `多会话并行开发规约.md` 第五节第 6 行）。

### 改法优先级

提速项 3-3：**立刻用**：长命令（全量冒烟、发布门控、并行测试、静态检查、模块热插拔检查）**与别的会话错峰跑**（别同时触发），减少管理端排队。零代码改动（本仓无后台作业能力，见上）。
提速项 3-4：**待做**：给审计工具加代码地图只读直读（用 `sqlite3` 直读那 564 个正式源码文件的节点/边）。
提速项 3-5：**不建议做**：再复制一份仓库副本搞"离线环境"。平台是"网关 + 管理端 + 数据库 + 编译产物"一体的，副本里跑不了验证，改完还要合回主仓、合并照样冲突。详见 `开发文档/多会话并行开发规约.md`。

## 六、重启纪律（与热加载配套）

热加载把"必须重启"的场合压缩到两类：**新增/删除工具** 与 **参数表变更**；另外本方案涉及的 **文件租约强制化**、**收口指纹修复** 也都落在管理端。

规矩：

规则 1：**能热加载就不重启**（改工具实现 → 走热加载）。
规则 2：**必须重启的，凑成一批、一次性重启** —— 不随改随重启。
规则 3：**重启前先确认无在跑长任务**：网关侧有长任务时禁止重启（2026-09-10 两次实测教训，见 `未完成事项.md`）；管理端重启会打断别的会话正在跑的工具。
规则 4：**批次内的改动全部落盘、编译通过后再重启**，重启后立即做一次冒烟复核。

## 环境与工具：装还是不装（2026-09-15 实测判定，依据第 11 条 1 项）

**判据**：对比现状，是否更快、更稳定；拿不出数字不许装。

### 实测数据

| 项 | 现状 | 候选 | 差距 | 结论 |
|---|---|---|---|---|
| 全仓搜索同词 | `grep -rn` 全仓 **6.35s** | `rg` 全仓 **0.075s** | **85×** | **改规则**（不装，`rg` 本机已装 `/opt/homebrew/bin/rg`） |

| 并行执行 | Hermes 子代理 | GNU `parallel` | 无 | **不装** |

### 真正的耗时来源（2026-09-15 实测）

- 全仓 **158,218 个文件 / 5.0GB**，其中 **154,395 个（97%）在 `工程缓存/`（4.9GB）**；源码本体只有约 40MB。
- `工程缓存/` 构成：**提供者运行环境 4.4GB**、**制品仓库 352MB**、HTML验证证据 74MB、验证缓存 13MB、编译缓存 12MB。
- **制品堆积**：`工程缓存/制品仓库/平台客户端制品/` 现存 **18 份**平台客户端制品（每份 15–16MB，合计约 280MB）——**每重编一次多一份，无回收**。老制品对运行态无用（激活指针只指一份），但会拖慢全仓扫描、占盘、干扰取证。
- 结论：对本项目而言，**收益最大的动作是「全仓搜索用 `rg` + 带排除」和「回收过期制品」**，而不是安装新命令。

### 已落地规则

- 全仓/大范围搜索**一律用 `rg`**；必须用 `grep` 时**必须带** `--exclude-dir=.git --exclude-dir=工程缓存 --exclude-dir=__pycache__ --exclude-dir=.venv --exclude-dir=node_modules`。
- 制品回收走平台自身的资源回收能力（不在本文件手工删文件）；过期制品清理列进 `未完成事项.md`。
