## 一、git 命令行为实测（本机真实执行结果）

实验均在仓库根执行，文件样本：
- 干净文件：`测试中心/运行测试.py`
- dirty 文件：`MCP工具箱/协作状态.py`（工作区已修改未提交）
- untracked 文件：`开发文档/临时文件/20260819-测试加速方案.md`

### 1.1 干净文件

```
$ git rev-parse :测试中心/运行测试.py
948ef5f6f468debdb7ebdddd417371b84a521a08
$ git hash-object 测试中心/运行测试.py
948ef5f6f468debdb7ebdddd417371b84a521a08
$ git rev-parse HEAD:测试中心/运行测试.py
948ef5f6f468debdb7ebdddd417371b84a521a08
```

三者一致。**干净文件用 `rev-parse :路径` 取到的就是工作区内容的 blob hash（index == HEAD == 工作区）**，且不需要读文件内容（从 index 拿 hash），这正是省读盘的来源。

### 1.2 dirty 文件（已修改未提交，未 add）

```
$ git rev-parse :MCP工具箱/协作状态.py
37d16bfcdf0c81803b44e96d6157b7fd325f466c   ← index 版本（= HEAD 版本，未 add 时 index 还是旧内容）
$ git hash-object MCP工具箱/协作状态.py
c4d258dd78c359e8edbcd1f09a969d9e6cfc632b   ← 工作区实际内容
$ git rev-parse HEAD:MCP工具箱/协作状态.py
37d16bfcdf0c81803b44e96d6157b7fd325f466c
```

**文档论断正确**：dirty 文件 `:路径` 返回的是旧 index 版本，与工作区内容不一致 → 若直接使用会缓存误判。必须现场哈希兜底。

### 1.3 dirty+staged（add 后再修改，MM 状态）

```
$ git rev-parse :MCP工具箱/协作状态.py    → 4ecc1a1d...（staged 版本，即 add 时的内容）
$ git hash-object MCP工具箱/协作状态.py   → dd03b56d...（工作区实际内容）
$ git rev-parse HEAD:...                 → 37d16bfc...（HEAD 版本）
```

三个值各不相同。**staged 后再次修改的文件，`:路径` 返回 staged 版本，仍然不是工作区内容**。结论不变：只要 `git status` 判定该文件非干净（M/A/MM/AM 等任何变更态），一律现场哈希。

### 1.4 untracked 文件

```
$ git rev-parse :开发文档/临时文件/20260819-测试加速方案.md
fatal: ambiguous argument '...': unknown revision or path not in the working tree.   ← 退出码 128
$ git hash-object 开发文档/临时文件/20260819-测试加速方案.md
e8eb96bf0e4fd60b10a9854385cdbd6db6db15a7   ← 正常返回，退出码 0
$ git ls-files 开发文档/临时文件/...        ← 空输出，退出码 0（不报错）
```

**文档论断正确**：untracked 文件 `:路径` 直接报错（退出码 128），必须现场哈希。

### 1.5 关键补充发现（文档未覆盖）

1. **路径基准是仓库根**：在 `测试中心/` 子目录下执行 `git rev-parse :运行测试.py` 会 fatal（退出码 128），必须用 `:测试中心/运行测试.py`。实现时必须把绝对路径换算成相对仓库根路径，不能依赖 cwd。
2. **`git hash-object` 也要读整个文件**：它只是计算 blob hash（不 `-w` 不写对象库），读盘开销与 sha256 现场计算完全相同。**git 指纹复用的真实收益只来自干净文件免读盘**（用 index 里的 blob hash），dirty/untracked 现场哈希仍然全量读盘。文档"判定成本从 O(全仓文件) 降到 O(变更文件数)"应修正表述为「干净文件读盘成本降为 0，仅变更文件读盘」。
3. **批量获取更优**：`git ls-files -s` 一次返回全部已跟踪文件的 index blob hash（每行 `模式 hash 阶段<TAB>路径`），untracked 不列出（空输出、退出码 0）。比逐文件 `git rev-parse :路径`（N 次 subprocess）高效得多。推荐实现：一次 `git ls-files -s` 建 路径→hash 映射 + 一次 `git status --porcelain -z` 取 dirty/untracked 清单，两者交集外（干净文件）直接用映射值。
4. **git hash 是 SHA-1 40 位，现摘要机制是 SHA-256 前 16 位**：直接混用会让同一文件在「干净（git hash）」与「dirty（sha256）」状态间切换时指纹不同 → 缓存键抖动（只致失效，不致假绿）。若要"跨分支/跨提交天然复用"，应统一格式（如统一截断 16 位），且整个指纹方案要么全用 git、要么全用现场，不能同一路径两种算法。

## 二、`测试中心/运行测试.py` 摘要实现与 git 指纹侵入点

### 2.1 现状实现

- `_文件摘要(文件)`（运行测试.py:62-64）：`hashlib.sha256(文件.read_bytes()).hexdigest()[:16]` —— 全量读盘。
- `_目录摘要(目录)`（运行测试.py:67-75）：`目录.rglob("*")` 遍历全部文件逐个读 bytes，排除 `pycache`/`工程缓存`/`完整性摘要.json`，sha256 滚动。**目录枚举 + 全量读盘**。
- 调用点：
  - 阶段摘要（107-122 行）：测试文件摘要（112）、依赖顶层包目录摘要（115）、运行测试.py 自身摘要（117）、验证器/ 目录摘要（119）、缓存结构版本、Python 版本。
  - 运行环境摘要（125-145 行）：依赖锁文件摘要（134）、外部程序用 `stat`（st_size:st_mtime_ns，非 read_bytes）。
- 缓存键：`阶段摘要 = f(测试文件内容, 依赖目录内容, 引擎自身, 验证器, 缓存结构版本, Python版本)`。

### 2.2 侵入点评估（git 指纹替换）

- **侵入点极小**：只有 `_文件摘要` 与 `_目录摘要` 两个函数需要改，所有调用方（阶段摘要/运行环境摘要）签名不变。
- 替换方案：`_文件摘要` 内先查「干净文件 → git ls-files 映射」，命中即返回 git blob hash（建议统一截断 16 位）；未命中（dirty/untracked）现场 sha256。`_目录摘要` 内逐文件同样走该逻辑。
- **必须保留的假绿链路**：`_目录摘要` 当前用 `rglob` 全量枚举目录——**untracked 新文件（新测试文件/新源码）即使不在 git 里也参与目录摘要**。若改为纯 git ls-files 枚举，新增文件不被感知 → 依赖目录摘要不变化 → **缓存误命中（假绿）**。因此目录摘要必须继续 rglob 枚举，只对「枚举到的已跟踪且干净文件」免读盘；untracked 文件继续现场哈希。这是本审计最重要的风险提示，文档未点明。
- 性能上限说明：目录枚举（rglob）本身仍在，git 指纹只省「干净文件的 read_bytes」；`_目录摘要` 的收益小于 `_文件摘要`。
- 风险等级：低侵入、中收益；实现要点是「干净判定必须用 git status 而非猜测」「untracked 必须参与摘要」。

### 3.3 并行日志审计

- 8 个 `并行_*.log`（静态契约/项目装配/平台控制面/权威状态/组件合规/结构迁移/资源并发/反向破坏）为并行实验时 shell 重定向的 unittest 输出（内容为 `test_... ok`），**运行测试.py 无任何写入并行日志的代码**（全仓 grep 无命中）。
- 结论：属于实验残留，不是方案产物。若方案要正式保留并行日志，应写入专用目录（如 `验证运行/` 内）并纳入 GC（按年龄或条数上限）；当前散落工程缓存根目录、无回收，与「资源必须有界」铁律冲突。

### 3.4 GC 策略建议

按引用 + 按访问时间双策略（互补）：

1. **按引用（必做）**：文件级缓存文件名 = 测试文件相对路径哈希；每次 GC 扫 `测试中心/**/测试_*.py` 构建现存测试文件路径集合，缓存目录中路径哈希对应文件已不存在的 → 删除。测试文件删除/改名/重构即清，实现简单、无假命中。
2. **按访问时间（推荐 30 天）**：缓存 json 内记录「最后命中时间」；GC 按 `atime/缓存内时间戳` 淘汰超过阈值未命中的条目。文档「30 天未命中删除」合理。
3. **兜底清理**：
   - 并行日志：超过 N 天（如 7 天）自动删除；或由 GC 脚本统一清理当前实验残留。
   - `验证运行/` 下超过 N 天的任务目录：这些是临时工作目录（工作包并行 8 位任务id 已有 rmtree 兜底；32 位 hex 的 统一验证 工作区残留漏网），按目录年龄兜底删除。
4. **边界**：只清理 验证缓存/、验证断点（过期失败）、并行日志、验证运行/ 临时目录；不得触碰 提供者运行环境/、制品仓库/、发布证据/、核心快照/。

## 五、独立建议

1. **git 指纹实现采用「一次 ls-files + 一次 status」构建映射**，不要逐文件 subprocess `rev-parse`（干净文件 N 次进程启动反而慢）。`git ls-files -s -z` 拿全部 index hash，`git status --porcelain -z` 拿 dirty/untracked 清单，干净 = 在 ls-files 且不在 status。
2. **路径基准坑**：所有 git 命令用 `cwd=系统根` 执行，路径统一转仓库根相对路径（中文路径注意 subprocess 参数直接传，不用 shell 拼接）。
3. **指纹算法统一**：git blob hash（SHA-1）与 sha256 混用会导致键抖动。建议统一为「干净文件取 git hash 截断 16 位、dirty/untracked 取 sha256 截断 16 位」并接受状态切换时的键变化（只致失效、不致假绿）；或更保守：全部 sha256，仅用 git 判定干净态省读盘（不省计算）。两种都安全，前者收益大。
4. **untracked 必须参与目录摘要**（假绿防线）：目录摘要继续 rglob 枚举，untracked 新文件现场哈希——这是 git 指纹方案正确性的前提，实现期必须有对应测试（新增 untracked 源码文件 → 缓存必须失效）。
5. **GC 落地时机**：与文件级缓存（补充优化 3）同步落地，按引用策略在「测试文件集合扫描」时顺带完成，成本近零；按访问时间策略由独立 GC 步骤（如 `--gc` 或空闲时触发）执行，不阻塞验证。
6. **工程缓存 3.0G 的大头是提供者 venv 与制品仓库，不是验证缓存**：GC 方案不要试图「清 3G」；验证缓存 GC 的实际收益是控制数量而非体积。
7. 文档「补充优化 4（已并入主方案）」中 `计算并行数` 的 32 上限（运行测试.py:268）与方案「全部核心」冲突，实现时必修——本条为顺带确认，不在本审计主范围。
