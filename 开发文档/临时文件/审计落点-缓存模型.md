## 一、主方案缓存模型核对

### 声明 1："验证缓存.json 是整体覆盖写" —— **属实**

运行测试.py:48 定义 `缓存文件路径 = 系统根 / "工程缓存" / "验证缓存.json"`；
运行测试.py:176-178 `写入缓存`：

```python
def 写入缓存(缓存: dict) -> None:
    缓存文件路径.parent.mkdir(parents=True, exist_ok=True)
    缓存文件路径.write_text(json.dumps(缓存, ensure_ascii=False, indent=2), encoding="utf-8")
```

直接 `write_text` 整体覆盖，无临时文件、无 os.replace、无锁。

佐证：同一文件内 `写入断点`（L189-191）与 `_写清理失败证据`（L300-302）均已使用
"临时路径 + `临时路径.replace(正式路径)`"的原子写模式，唯独 `写入缓存` 未采用——
原子写先例就在同文件内，方案改动完全符合项目既有惯例。

### 声明 2："并行后缓存只剩 5 个阶段" —— **机制解释成立；数字本身无法从当前状态复核**

机制（读-改-写整体覆盖 + 无锁，运行测试.py:629 读一次 / L695-701 每阶段写回整个 dict）：
8 个并行进程各以 `--阶段 X` 运行完整主函数 → 各自读到旧缓存（若此前串行留下 N 项）→
跑完自己阶段 → 写回"旧 N 项 + 自己阶段"= N+1 项 → 无互斥、最后写者赢 → 丢失其他进程写入。
若并行前缓存恰有 4 个旧阶段，8 进程各写回 5 项，最终只剩 5 项——与文档描述数字自洽。

佐证并行实测确实发生过：
- `工程缓存/并行_{阶段}.log` 共 8 个，时间 2026-08-19 12:02-12:03
- 并行_静态契约.log 末行：`Ran 624 tests in 71.002s` + `门禁通过：共 624 个测试全部成功（复用 0 个阶段缓存，总耗时 71.84 秒）`
- 并行_项目装配.log 末行：`Ran 93 tests in 70.877s` + `门禁通过：共 93 个测试全部成功（复用 0 个阶段缓存，总耗时 71.14 秒）`
- 与文档 L14"8 阶段并行 77 秒"吻合；两日志末行均含"复用 0 个阶段缓存"，说明并行进程中缓存被整体读写

复核限制：当前 `工程缓存/验证缓存.json` 为 12 阶段齐全（时间戳 12:08-12:16，晚于并行实测
12:02-12:03），即并行实测后又跑了一次串行全量覆盖恢复，"只剩 5 个阶段"的时刻快照已不可见。
结论：**机制解释成立，数字可自洽但不可复核，建议文档保留"实测"表述但补充机制推导**。

### 声明 4：改 验证缓存/{阶段名}.json + os.replace 能否解决并发覆盖 —— **成立，但有三个实现边界**

成立的依据：
- 每阶段独立文件 → 8 个并行进程写不同文件，天然无同文件竞争；
- `os.replace` 在同一目录内为原子替换（读方要么看到完整旧文件、要么看到完整新文件，不会看到半截内容）；
- 项目已有 tmp+replace 惯例（L189-191、L300-302），方案可行。

实现边界（文档未提，建议补充）：
1. **读取逻辑必须同步改造**：`读取缓存`（L167-173）与主函数 L629 需改为"遍历 验证缓存/*.json 合并为 dict"；`计算断点续跑阶段`（L480-506）读的也是合并后缓存；
2. **同阶段并发写仍需"最后写者赢"语义**：若两个全量运行并发执行同一阶段（如两个终端同时跑全量、或嵌套并行的同阶段进程），仍会写同一文件。内容幂等（同摘要同环境写同样内容）时安全，不同环境摘要互相覆盖时旧环境摘要阶段可能误复用——建议写入前做"先读后比"或接受最后写者赢并在命中判定中靠环境摘要兜底；
3. os.replace 跨文件系统（EXDEV）才非原子，此处同目录无虞。

## 二、文件级缓存方案审计（补充优化 3）

### 2.1 sys.addaudithook 观测文件访问 —— **可行，限制经实验确认**

Python 3.14 实测（`audit实验.py`，100 次事件）：
- `open` 事件参数 = (路径, mode, flags)：内置 `open()` 时 mode 为 'w'/'r' 等可读字符串，可直接区分读写；
- `os.listdir` / `os.scandir` 事件均有记录，路径参数清晰；
- 子进程**不继承**父进程 hook（实测子进程只输出自己安装 hook 后的事件）——文档 L83"子进程内读的文件父进程观测不到"属实；
- 性能：实测 100000 次 open+read 带 hook 共 1.357s（约 13.6µs/次，回调仅为 append）。若回调做路径规范化 + JSON 序列化 + 写共享文件，预计放大 2~5 倍。测试场景每文件运行期文件操作几百~几千次 → 毫秒~几十毫秒级，可接受。

**文档未提的重要限制（须补）**：
- Python 3.14 无 `sys.removeaudithook`，hook 一经添加**不可移除**、全局生效（影响所有线程）。
  → 方案必须绑定"每测试文件独立子进程"执行方式（hook 随进程退出消失），与现有工作包子进程模式（运行测试.py:365-416）天然一致；**禁止**在常驻守护进程（工程化补充 2）或主进程安装 hook，否则记录污染 + 永久性能损耗。
- `os.open` 直接调用时 mode 参数为 `None`，需解码 flags（低位掩码 O_RDONLY=0 / O_WRONLY=1 / O_RDWR=2 / O_CREAT=64 / O_APPEND=1024…），文档未提该分支；
- C 扩展直接 syscall 读文件不可见（文档 L106 已提，属实）；
- import 平台代码会产生大量读事件（几十模块 → 数百 open），会占审计记录配额。

### 2.2 "写入不计入依赖"的实现难度 —— **中等；但"写后读回=依赖"存在根本语义矛盾**

可实现的部分（实验证实）：
- "只写" vs "写后读回"可通过事件序列区分：仅 `open('w')` vs `open('w')` → `open('r')`。

不可实现的部分（实验证实，`audit实验2.py`）：
- "写带时间戳日志后读回（内容不影响断言）"与"写配置文件后读回（内容影响断言）"的 open 事件序列**完全相同**（w → r），audit hook 只能看到访问事件、看不到读回内容是否参与断言。

**文档内在矛盾（须修正）**：
- L63-65 主张"带时间戳的产物每次内容都变，若算依赖会永久假失效"（所以排除只写）；
- L64 又主张"只有之后被测试读回的文件才算依赖"。
- 若测试"写带时间戳日志 → 读回验证可读"（常见模式），该文件同时命中"应排除"与"应算依赖"两条规则，冲突未解——按文档字面执行会永久假失效（每次运行内容不同 → 依赖摘要必变 → 永不命中）。

**独立建议（判据修正）**：依赖判定改为"**测试开始前已存在的文件 + 本次运行被读**"，或等价地"读事件路径**排除测试临时根目录（TMPDIR）**下的文件"：
- 测试自身在 TMPDIR 内创建的产物，内容变化是测试自身行为，不应触发失效；
- 测试开始前已存在、被读取的文件（源码/配置/数据），内容变化才是外部因素，应触发失效；
- 该判据比"写后读回"更准确、实现更简单（TMPDIR 由现有工作包机制已注入，运行测试.py:374）。
- 兜底：测试**修改已存在文件**（open 'w' 命中测试前已存在路径）属于异常行为，可标记弱依赖并记录，宁多跑。

### 2.3 审计记录 200KB 上限 —— **合理**

- 实测每事件约 100~150 字节（路径 + 事件名 + mode），200KB ≈ 1300~2000 条事件；
- 单测试文件运行期：import 平台代码数百条 + 测试逻辑几十~几百条，通常远低于上限；
- 超限截断 + 标记"弱依赖"符合"资源必须有界"铁律，且宁多跑不错过，安全方向正确。
- 建议补充：截断点本身要写进缓存项（弱依赖标记），命中判定遇弱依赖直接重跑；200KB 对 import 重的测试文件偏紧但安全，无需调大。

### 2.4 依赖清单存"文件摘要表"的存储/比对开销 —— **可接受，粒度反而比现状细**

- 存储：每测试文件依赖 ~200 文件 × {路径(~50B) + 摘要(16 hex)} ≈ 14KB/缓存；600+ 测试文件总量约 8~9MB，可接受；
- 比对：命中判定只哈希"该测试实测依赖的文件"，现状是对整个顶层包目录全部文件哈希（运行测试.py:67-75），文件级粒度更细、开销更低；
- 残留问题：全命中时所有依赖文件仍要全部重新读盘哈希（O(依赖总数)），文档工程化补充 1（git 指纹）是对症解，已识别、方向正确；
- 摘要表跨测试重复存储（600 测试依赖清单有交集），可内容寻址去重（工程化补充 4），非必须。

## 三、缓存结构版本 bump —— **必要但非关键**

- 运行测试.py:53 `缓存结构版本 = "2.0.0"`，属实；
- 阶段级缓存（{阶段名: {...}}）与文件级缓存（{哈希: {...}}）**存储路径不同**（`验证缓存.json` / `验证缓存/{阶段名}.json` vs `验证缓存/文件/{哈希}.json`），新逻辑天然读不到旧文件——bump 的实质作用是防御性语义标记，而非防误读；
- 文档 L33"损坏/缺字段自动失效机制复用现有逻辑"属实：`阶段缓存可复用`（L152-155）对缺"成功"/"摘要"/"测试数"字段的缓存项返回 False 失效；
- 补充：文件级缓存落地后**不得再读旧阶段缓存路径**（旧 验证缓存.json / 验证缓存/{阶段名}.json 应清理），否则旧阶段缓存与文件级缓存并存产生两套失效路径，文档未明确；
- 测试锚点：测试_零测试门禁.py:131-140 直接断言 `阶段缓存可复用`（慢速层强制慢速、环境摘要变化、时间戳过期），动态引用 `运行测试.缓存结构版本`，bump 版本号不会破坏该测试，但它会因签名变化（如新增参数）而需同步调整。

## 七、独立建议（基于实际代码核对的判断）

1. **缓存原子写优先级高于一切**：改动面最小（写入缓存 3 行 + 读取合并 + 断点续跑读取点），且同文件已有原子写先例，无新风险，应作为落地步骤 1 立即执行。
2. **文件级缓存的依赖判据建议用"TMPDIR 排除法"而非"写后读回法"**：更简单、更准确、无语义矛盾；TMPDIR 已由现有工作包机制注入（运行测试.py:374）。
3. **环境摘要的修复要同时覆盖"扩展外部程序清单"和"非敏感阶段校验"两个维度**，只做清单扩展仍留非敏感阶段假绿口。
4. 缓存结构改造时补一条定向测试（缓存写入/读取/并发覆盖），当前缓存读写无任何直接测试覆盖，属测试盲区。
