## 一、方案文档「失败与断点语义」节（144~149 行）四条声明核对

### 声明 1（方案文档 146 行）：并行阶段失败 → 立即终止其余仍在运行的并行阶段（终止进程组），不再执行后续环境敏感阶段，整体返回非零。

**核对结果：属实（作为目标态），实现机制在现有代码中需新增。**

- 现有 `主函数`（运行测试.py:645~705）是**串行 for 循环**：任一阶段失败 → `写入断点` → `return 1`，后续阶段根本不启动。"失败后不再产生新的阶段成功结果"这一点上，串行（不启动后续）与并行（终止运行中阶段）语义**兼容**。
- 兼容性差异点（文档已部分承认）：串行下失败阶段之后的阶段从未运行过；并行下"失败前已完整成功的阶段"会留下缓存。声明 2 已承认可复用，不冲突。
- **现状没有"失败即终止其余阶段"的实现**：工作包并行 `并行执行指定测试文件`（运行测试.py:419~465）用 as_completed 收集全部结果后统一判定，任一文件失败**不会**提前终止其他在跑文件（全部跑完才判定）。并行阶段方案要求新增"任一失败 → 立即终止其余 in-flight 子进程"的协调逻辑，属新增代码。
- "不再执行后续环境敏感阶段"：并行 8 阶段失败时环境敏感阶段尚未启动，串行下 return 1 也不会执行，两者一致，无冲突。

### 声明 2（方案文档 147 行）：多阶段同时失败 → 收集全部已失败并行阶段，断点记录第一个失败阶段；--继续 按"第一个失败阶段及之后"回退（断点前完成且证据有效的并行阶段可复用）。

**核对结果：自洽，但依赖两个文档未显式写明的关键前提，且"第一个"存在定义歧义。**

自洽性依据（代码实测）：
- 断点结构（运行测试.py:181~191）为 `失败阶段`（单个阶段名）+ `阶段列表`（完整阶段名列表），能容纳"记录第一个失败阶段"，**无需改断点结构**。
- `计算断点续跑阶段`（运行测试.py:480~506）：从失败阶段位置起跑，**向前**逐个检查上游阶段缓存是否可复用，不可复用则回退起点。测试用例佐证：`test_断点从失败阶段继续`（缓存命中甲→从乙起）、`test_断点在上游摘要变化时自动回退`（甲摘要变→回退全表）。
- 因此"并行部分成功部分失败 → --继续 精确回退"自动成立：位置在断点阶段之前的失败/被终止阶段**无成功缓存** → 触发向前回退被覆盖；位置在断点阶段之后的重跑；已完整成功的阶段缓存有效被跳过复用。

**前提 1（关键，文档未显式说明）**：失败/被终止阶段必须**不写成功缓存**。现状满足（仅 `wasSuccessful()` 才写缓存，运行测试.py:695~701；被终止进程退出码非 0 不写）。这是向前回退精确性的基石，文档应显式声明。

**前提 2**：成功并行阶段写缓存必须原子（方案文档"缓存原子写"配套已含），且**读取端必须同步改造**：`读取缓存`（运行测试.py:167~173）目前只读单文件 `验证缓存.json`，并行落地时必须聚合读取 `验证缓存/{阶段名}.json` 目录。方案文档只写了写入端（第 29 行），未提读取端。

**歧义（需定义）**："第一个失败阶段"按"时间最早失败"还是"阶段顺序位置最靠前"？
- 若按位置最靠前记录：续跑起点最小，范围最小且不漏，最优。
- 若按时间最早记录：位置更靠前但更晚失败的阶段会被起点略过，靠向前回退兜底（安全但可能多跑）。
- 两种都安全，但文档必须定义，推荐"阶段顺序表中下标最小的失败阶段"。
- **另需区分"真实失败"与"被终止"**：终止后收集失败集合时，被终止阶段退出码非 0（信号杀死）会被误纳入。断点失败阶段应选**真实失败**（门禁失败非零退出）中位置最靠前者，不能把被终止阶段记为失败阶段。

### 声明 3（方案文档 148 行）：--阶段 波次语义不变（固定顺序串行）；全量验收默认 8 阶段并行；新增 --并行阶段 不改变 --阶段 语义。

**核对结果：属实，与 AGENTS.md 一致。**

- 现有 `筛选阶段`（运行测试.py:468~477）保持阶段顺序表原始顺序，主循环串行 → "固定顺序串行"属实。
- AGENTS.md 第 51 行"合并波次 | 只跑受影响的 --阶段，保持固定阶段顺序"，方案文档表述完全一致。
- AGENTS.md 验证分级表（44~53 行）只约束各级别"跑什么命令、跑一次"，**未规定常规全量/正式发布的串并行形态**，因此"阶段收口 8 阶段并行""正式发布常规可并行"不违反 AGENTS.md。
- 存疑/缺失：`--并行阶段` 的语义完全未定义——多值如何排序？是否仅限非敏感阶段？与 `--阶段`/`--继续`/`--范围 全部` 的组合行为（冲突 or 叠加）？需在方案文档补充，否则实现期歧义。

### 声明 4（方案文档 149 行）：门禁语义不变：任一失败、零测试、导入失败、未解释跳过、缓存假绿均返回非零。

**核对结果：属实（"缓存假绿"一项存疑/夸大）。**

- 任一失败（运行测试.py:682）、零测试（676）、导入失败（686）、未解释跳过（690）均有现成门禁分支，失败均写断点并返回 1。属实。
- **"缓存假绿"无显式检测器**：现有仅有"正式实现引用审计"（运行测试.py:564~571）与缓存摘要/结构校验（`阶段缓存可复用` 运行测试.py:148~164）**间接**防假绿，没有独立的"缓存假绿检测"门禁函数。声明 4 把"缓存假绿"列为既有门禁语义属夸大，应改为"缓存摘要/结构校验"或明确"文件级缓存落地后新增假绿检测"。

## 三、并行后断点续跑漏洞检查（任务 3）

1. **缓存写入竞态**：整体覆盖写（运行测试.py:176~178）→ 方案配套"缓存原子写"解决（落地步骤 1 先行，顺序正确）。**补充漏洞：读取端（运行测试.py:167）未提聚合改造**（见声明 2 前提 2）。
2. **`--继续` 续跑并行策略未定义**：续跑阶段是并行还是串行，方案文档未定义。若续跑默认并行，向前回退逻辑仍适用（每阶段独立缓存判定）；若串行天然安全。**建议方案文档明确**：`--继续` 沿用断点记录时的并行策略（保守可先串行）。
3. **被终止阶段整体重跑**（阶段级粒度）：被终止阶段即使部分测试已通过也整阶段重跑，属阶段级缓存粒度设计而非漏洞，但方案文档应显式说明（文件级缓存落地后粒度变细）。
4. **"第一个失败阶段"位置/时间歧义 + 真实失败/被终止区分**：见声明 2。
5. **主进程崩溃不写断点**：Ctrl+C/主进程被杀时断点未写，现状同样如此，非新增漏洞。并行协调主进程为**单一断点写者**（终止子进程后统一写），无写竞态，但注意"先终止全部子进程 → 再写断点"的时序。
6. **阶段子进程化缺失 teardown 保障（重要）**：现状阶段在**主进程内**执行 unittest（运行测试.py:681），无独立临时根/资源清单。并行阶段子进程化后必须参照工作包模式（`_运行单文件子进程` 运行测试.py:365~416）配套独立临时根 + 资源登记 + teardown + 清理失败证据，否则违反"资源必须有界"铁律。方案文档落地步骤 2 未提。

## 四、"立即终止其余并行阶段"（终止进程组）实现机制可行性（任务 4）

**结论：可行，机制在项目内已成熟。**

- `_终止进程组`（运行测试.py:306~319）：先 `os.killpg(SIGTERM)` 宽限 5s 再 `SIGKILL`；配合 `start_new_session=True`（运行测试.py:387）使子进程成独立进程组组长（组号==pid），killpg 可靠。
- 同模式在项目内广泛使用并验证：平台控制面/统一入口.py:321、支持库/适配层/系统探针.py:158、PyMuPDF提供者（实现/提供者.py:40）、MCP工具箱/测试资源.py:271、慢速层强杀测试（第十三/十四阶段）等。
- 需要新增的点：
  1. 阶段并行 = 把阶段改为独立子进程（现主进程内跑 TextTestRunner）；
  2. "失败即终止"调用点（现 `_终止进程组` 仅用于 `subprocess.TimeoutExpired` 超时分支）；
  3. as_completed 循环内检测到失败 → 终止其余 in-flight 子进程；
  4. 区分"真实失败（非零退出）"与"被终止（信号退出）"，供断点失败阶段选择；
  5. 阶段级 teardown（临时根/资源清单，参照工作包模式）。
- 风险：并行子进程 stdout 交错，建议每阶段输出独立文件、全部结束后按阶段顺序回放（工作包模式已有 -8000 截断先例可参考）。
