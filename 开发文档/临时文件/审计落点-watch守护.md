## 一、对照 AGENTS.md 硬规则的兼容性检查

### 1.1 "所有线程、进程、队列、缓存、日志、临时文件、句柄和终态记录必须有界" —— 文档只提了目标，缺实现机制

文档 L132③ 写"生命周期必须有界（空闲自动退出 / 手动停止）"，审计发现：

- 项目**没有 daemon 化进程与 pid 文件管理的实现先例**（grep 守护进程/daemon/pid 文件无平台实现；`.codegraph/.gitignore` 里的 daemon.pid 是 codegraph 工具的，非平台）。
- 有界需要落成具体机制：pid 文件（原子写 + 退出清理）+ 空闲超时（如 30 分钟无变化自动退出）+ SIGTERM/SIGINT 优雅停止 + `停止` 子命令。这些机制项目内无现成可复用。
- **比生命周期更严重的是"旧代码假绿"正确性问题（文档完全未提）**：守护进程"预热解释器 + import 缓存"意味着进程内固化了一份平台代码快照。平台代码一旦更新（watch 场景这正是常态），守护进程仍用旧 import 缓存跑测试 → 基于旧代码出证据。本项目已有直接前车之鉴：`开发文档/项目证据/MCP使用反馈.jsonl` 记录"8766 端口被旧代码常驻进程占用导致首次冒烟命中旧实例（tools/list 仅 28 工具）"，升级建议明确"常驻进程缺少版本/代码指纹自检与热重启机制，代码更新后静默服务旧行为"。平台的"证据可信度由代码地图、当前 Git/工作区指纹和真实成功验证计算"原则下，**守护进程跑出的旧代码证据不可信 = 假绿**。
- 结论：**"预热 import 缓存"与平台证据可信度原则根本冲突，必须从方案中删除**；守护进程只做调度（见第四节），不 import 平台代码。代码变化时依赖"每测试文件独立子进程"全部冷启动（子进程天然 import 新代码），守护进程自身零代码状态。

### 1.2 "已有全量运行时禁止重复启动" —— 互斥必须双向，且现状无互斥机制

文档 L132① 提"文件锁或端口哨兵"。审计发现两个问题：

- **现有 `运行测试.py` 根本没有全量互斥**：主函数无任何锁（审计落点-缓存模型.md 已确认"两个终端同时跑全量仍会写同一文件"）。AGENTS.md 该铁律目前靠协作约定/发布流程保障，不是代码机制。watch 落地必须**同时**给 `运行测试.py` 手动全量入口加同一把锁，否则只锁 watch 侧无效（手动全量照常与 watch 并发抢端口/数据库/缓存）。
- 锁方案选型：**flock（fcntl.flock）文件锁优于端口哨兵**。理由：全量的真实进程/网关/浏览器阶段本身占用端口，哨兵端口与测试端口存在冲突面；flock 与测试端口无耦合。项目内无 flock 先例（现有"锁"全是业务语义锁：依赖锁.json/租约锁/sqlite 写锁/能力占用唯一索引），属新增机制，但标准库自带、无第三方依赖。
- 锁的获取时机：全量入口启动即拿锁（含 `--测试文件` 工作包？否——工作包只跑指定文件无端口/数据库冲突，但会写验证缓存，为保守可只在常规/慢速/全部范围拿锁）；watch 触发调度前拿锁；拿不到返回"已有全量运行中"。

## 二、项目内文件监听/watch 类实现盘点 —— **无可复用**

- grep `watchdog|inotify|文件监听|watch模式|守护进程|常驻`：全部 .py 零命中（仅测试方案文档自身含"watch 模式"字样）。
- codegraph 探索"watch 文件监听 watchdog 文件变化 守护进程"：无相关符号。
- 项目内的"轮询/监视"均为**进程状态轮询**（运行核心/任务调度/任务进程.py 的单轮询监视线程、平台控制面/统一入口.py 的超时判定），非文件监听。
- 可借鉴的只有"有界生命周期"代码风格：任务进程.py 的"单轮询监视线程 + 停止事件 + is_alive 重建 + 停止后不再启动"模式，可作为守护进程监视线程的实现参照，但文件监听逻辑需从零写。

## 三、冷启动开销组成（Python 3.14 实测，本机 macOS）

### 3.1 `--测试文件` 工作包模式：冷启动极小，不是瓶颈

| 场景 | 总耗时 | 测试执行 | 冷启动（import+加载） |
|---|---|---|---|
| 空解释器基准 | 0.021s | - | - |
| import 运行测试.py 模块级（含顶层包目录表 iterdir） | 0.031~0.076s | - | - |
| 测试_验证门禁.py（轻 import） | 0.763s | 0.694s | **0.069s** |
| 测试_演示文稿.py（import 公共契约/支持库/运行核心全链） | 5.183s | 5.060s | **0.123s** |

**import 全套平台代码只有 ~0.1s**。文档 L130"起解释器、import 全套平台代码"是冷启动主要成本的描述与实测不符。

### 3.2 常规全量"代码没动"场景（文档 1.36s）：实测完全复现并定位到元凶

只读调用 `运行测试.py` 模块函数实测（不触发真实测试）：

| 启动项 | 耗时 |
|---|---|
| 加载模块 + 顶层包目录表 iterdir | 0.031s |
| 收集阶段文件（12 阶段 rglob，84 个测试文件路径） | 0.032s |
| 阶段依赖目录表（读全部测试文件文本） | 0.008s |
| 阶段摘要（全部测试文件 + 依赖目录 hash） | 0.245s |
| 审计工程缓存正式实现引用 | 0.016s |
| **运行环境摘要** | **1.026s** |
| 合计 | ≈ 1.36s（与文档"代码没动 1.36s"吻合） |

**运行环境摘要占 75.4%（1.026s），内部再分解：**

| 子项 | 耗时 |
|---|---|
| sys.version + platform.platform() + machine() | 0.017s |
| `系统根.rglob("*依赖锁*.json")` 全仓扫描 | **0.998s（97%）** |
| 外部程序（python/soffice/psql）stat | 0.000s |

- rglob 全仓扫描的代价：本仓排除缓存后 .py 文件 554 个，全树遍历（含大量工程缓存/生成物）约 1 秒/次。
- 依赖锁实际分布（19 个）：**18 个全部在 `支持库/适配层/*/依赖锁.json`（同一棵目录树）+ 1 个 `示例项目/适配层示例/依赖锁定.json`（注意文件名是"依赖锁定"）**。收窄为两个定点 glob（`支持库/适配层/*/依赖锁.json` + 示例项目那一个）即可把 0.998s 降到可忽略——**不需要常驻进程，改扫描范围即可**。

### 3.3 冷启动结论（直接否定 watch 的预热对象）

- watch 要"预热解释器 + import 缓存"省掉的是 ~0.1s（import）——**错靶**。
- 真正 1 秒级冷启动开销是 rglob 依赖锁全仓扫描（0.998s）+ 阶段摘要全量 hash（0.245s）：
  - rglob：收窄扫描范围（~5 行改动）或缓存锁文件清单即可消灭，零新机制；
  - 阶段摘要 hash：靠文件级缓存 + git 指纹复用（工程化补充 1）消灭，已在方案内。
- **没有任何冷启动项需要常驻进程才能消灭**。

## 四、watch 与文件级缓存（补充优化 3）的关系 —— 调度层与判定层互补，但不得自带依赖图

- 互补关系：文件级缓存（补充优化 3）解决"改 1 文件后跑哪些"（查实测依赖表，失效 3~10 个测试）；watch 解决"何时自动跑"（检测变化触发）。watch 是调度层，文件级缓存是判定层，**watch 依赖文件级缓存已落地才有意义**（没有依赖表时 watch 只能整阶段重跑，收益归零）。
- **watch 不得自带"依赖图"（文档 L130 措辞）**：依赖判定唯一来源必须是文件级缓存的运行时实测记录（sys.addaudithook 观测）。watch 若再建一套静态依赖图，与实测记录天然不一致（静态 import 分析猜不到动态导入/子进程读取），会产生"watch 认为不相关没跑、实际测试读到了"的假绿。文档 L130"预热解释器 + import 缓存 + 依赖图"中的"依赖图"应删掉。
- **audit hook 边界（审计落点-缓存模型.md 已确认）**：Python 3.14 无 `sys.removeaudithook`，hook 一经添加不可移除、全局生效，**禁止装在常驻守护进程或主进程**。watch 必须保持"每测试文件独立子进程"执行（复用现有 `--内部测试文件` 子进程入口 + TMPDIR 注入机制，运行测试.py:365-416），hook 随子进程退出消失。守护进程只负责"检测变化 → 查文件级缓存依赖表 → 调度独立子进程"，自身不执行测试、不装 hook、不 import 平台代码。

## 五、标准库实现文件监听的实现成本（只允许标准库，watchdog 不可用）

- watchdog/pyinotify/fsevents 绑定均为第三方，违反 AGENTS.md"只允许 Python 标准库"铁律；第三方即使封装进支持库/适配层也不改变"文件监听是开发工具核心功能、不应引入第三方"的定位。
- **唯一标准库方案：轮询（polling）**。快照比对 `os.stat`（mtime_ns + size），间隔 0.3~0.5s。
- 规模与开销估算（实测）：测试文件 159 + 全仓 .py 554 ≈ 700 文件，stat 约 10-20µs/次 → ~14ms/轮询，0.3s 间隔下 CPU 占比约 5%，可接受。
- **三条必须遵守的实现边界**：
  1. **启动时建一次文件快照清单，之后只 stat 清单内文件——严禁每轮 rglob 全仓扫描**（实测 1s/次，比轮询本身贵一个数量级）；
  2. 新增文件检测：stat 目录 mtime（目录 mtime 在子文件增删时变化），只 stat 目录树（顶层包目录 + 测试中心子目录，几十个），发现变化时重建快照清单；
  3. 防抖 + 排队：文档 L132② 已提，但**队列必须有界（AGENTS.md"所有队列必须有界"）**——文档未提队列上限。建议：变化事件队列上限（如 64 条），超限合并为一个"待全量"标记，不无限积压。
- 总实现成本评估：生命周期（pid + 信号 + 空闲超时）+ 双向 flock 互斥 + 轮询快照 + 防抖/有界队列 + 调度子进程 + 停止命令 + 对应测试，预计 300~500 行 + 一组定向测试。**中等偏高，且正确性风险（旧代码假绿）集中在设计层而非实现层**。

## 七、独立建议

1. **优先级倒挂修正（最高优先）**：先修 `运行环境摘要` 的 rglob 全仓扫描（运行测试.py:131）——收窄为 `支持库/适配层/*/依赖锁.json` + `示例项目/适配层示例/依赖锁定.json` 定点 glob，约 5 行改动，"代码没动"从 1.36s 降到 ~0.4s。**这是所有加速项里性价比最高的一项，且不需要任何新机制**。环境摘要本身也可缓存成文件（其因素变化极低频：Python 版本/依赖锁/外部程序升级，每次全量只 stat 缓存文件），叠加后降到 ~0.01s。
2. **watch 降级为"步骤 5（文件级缓存）稳定后评估的可选项"**：文件级缓存已把"改 1 小文件"压到 5~10s（补充优化 3 预期表），watch 再省的是冷启动中剩余的 ~0.4s + 免敲命令的便利性。常驻进程引入的旧代码假绿风险、双向互斥改造、有界生命周期复杂度，与这个边际收益不成比例。**落地顺序建议：步骤 1~5 → git 指纹复用（工程化补充 1）→ 慢测试先行（3）→ 内容寻址缓存（4）→ 最后评估 watch（2）**。
3. 若最终仍做 watch：按第五节三条边界 + 第六节修正清单实现，其中"双向 flock + 运行测试.py 手动入口同步加锁"顺带把 AGENTS.md"已有全量运行时禁止重复启动"从协作约定变成代码机制，属于规则落地的正向改进，独立于 watch 也值得做。
4. 阶段摘要 hash（0.245s）与 rglob 属于同类问题（O(全仓文件) 的读盘开销），git 指纹复用（工程化补充 1）是对症解，方向正确，应排在 watch 之前。
