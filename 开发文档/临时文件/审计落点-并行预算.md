### 1.3 "全局并发预算 / 嵌套共享一个池"的实现可行性（新增分析）

**可行性：高，但必须选对形态。**

- **方案 A（推荐）：主进程唯一全局 ThreadPoolExecutor + 叶子任务扁平化。**
  所有"文件子进程任务"（阶段并行里的阶段、补充优化 1/2 的文件）统一提交到**一个**池，`max_workers = 全局预算`；"阶段"只是任务的分组标签（任务结果携带阶段名），不占额外 worker 槽位。
  - 天然满足"总并发 ≤ 预算"：池的 max_workers 即硬上限，8×N 爆炸结构上不可能；
  - 慢测试先行调度可全局按耗时降序提交，无需分层排序；
  - 复用现有 `_运行单文件子进程`（365-416）与 `_清理工作包临时根`，改动集中在主循环重构；
  - 代价：需要把现阶段的 `TextTestRunner.run(阶段套件)` 改为"阶段 → 文件任务提交"，并处理失败语义（任一阶段失败 → `future.cancel()` 未启动任务 + `_终止进程组` 已运行子进程，文档 L146 已声明该语义）。
- **方案 B（不推荐）：8 阶段各自独立进程、内部再各起一个池。** 需要 multiprocessing 共享信号量做跨进程预算，池套池易失控，复杂度显著高于 A 且与现有线程池架构割裂。

**修正建议（精确到位置）：**
- L114："必须共享一个全局并发池"→ 建议补一句实现形态："以主进程唯一 ThreadPoolExecutor 为全局池（max_workers=全局预算），阶段与文件统一为扁平叶子任务提交，避免池套池"。
- L114："总子进程数 ≤ os.cpu_count()"→ 改为"**同时运行**的子进程数峰值 ≤ 全局预算"。

## 三、M3 Mac Studio 核数感知

### 3.1 实测数据

- 机器：Apple M3 Ultra
- `sysctl hw.perflevel0.logicalcpu` = **24（性能核）**，`hw.perflevel1.logicalcpu` = **8（能效核）**
- `os.cpu_count()` = **32**（逻辑核，含能效核），`os.available_cpu_count()` = 32（Python 3.14）

### 3.2 "按性能核数可选排除能效核"是否值得做

**判断：不值得默认做，可作为可选开关保留。**

1. **收益重复**：排除能效核的唯一实质收益是避免"超时敏感测试在能效核上变慢导致误判"——但补充优化 2（L45）已把超时类/计时类测试全部串行化，与能效核无关；其余测试无计时断言，能效核慢一点不影响正确性。
2. **浪费吞吐**：测试是短突发负载，32 核（含 8 能效）并行比 24 核（纯性能）吞吐更高；排除能效核是把 8 个核闲置。
3. **平台耦合**：macOS 获取 P/E 核数需 `sysctl hw.perflevel*`（外部命令）；Linux/Windows 无 perflevel 概念，需跨平台兜底，与"只允许标准库"约束冲突风险高（subprocess 调 sysctl 在字面上合规，但代码复杂化）。
4. **当前 32 上限与 32 核恰好平齐**（见 §1.2-2），排除能效核反而把并行度降到 24，低于现有 `计算并行数` 给出的 32，属于倒退。

**修正建议**：L114"（按性能核数，可选排除能效核）"改为"默认 `os.cpu_count()` 全部逻辑核（含能效核）；排除能效核仅作可选开关且默认关闭（收益有限，且 32 上限下排除反而降低并行度）"。

## 四、慢测试先行调度（工程化补充 3）与全局预算的关系

### 4.1 核对结果

**属实，两者正交无冲突。**

- **全局预算** = 并发上限（同时最多 N 个子进程）；**慢测试先行** = 提交/调度顺序（谁先占 worker 槽）。
- 在"单全局池扁平化"（§1.3 方案 A）下，按实测耗时**降序 submit** 即可实现"最慢先启动、快的填缝"，天然全局最优；无需额外机制。
- 文档 L112"所有并行点（阶段并行 / 文件级并行 / 真实进程部分并行 / 慢测试先行调度）统一按此分配"——把"并发上限"与"调度顺序"混在同一句，建议拆分表述，避免实现歧义。

### 4.2 依赖关系（文档未写明）

- 慢测试先行**依赖耗时画像数据**（补充优化 5，L118-120 提供）。落地顺序应为：先画像（补充优化 5）→ 再先行调度（工程化补充 3）。文档落地步骤 L168 把工程化补充列为"1~5 稳定后逐步叠加"，未显式声明该依赖。
- **修正建议**：L134-136 补一句"需先落地补充优化 5 耗时画像；无画像数据时按文件大小/历史缓存耗时降序兜底"。

## 五、独立建议（基于实际代码核对的判断）

1. **实现形态选"单全局池扁平化"**：阶段并行 + 文件并行全部扁平为主进程唯一 ThreadPoolExecutor 的叶子任务（复用 `_运行单文件子进程`），预算由 `max_workers` 天然硬约束。这是满足"总并发 ≤ 预算"且复杂度可控的唯一推荐路径；文档 L114 应写明该形态，避免实现者走"池套池 + 跨进程信号量"的弯路。
2. **移除 32 上限要谨慎**：文档 L116 说"必须移除或提高该 32 上限"。建议改为"上限 = 全局预算 = os.cpu_count()"（即保留"有界防冲垮"语义、取消 32 魔数），而不是简单删掉上限——AGENTS.md"并发有界"精神仍应保留。当前 M3 Ultra 32 核下两者等价，改动风险低。
3. **静态契约阶段的并行收益预期需重估**：47 个文件中至少 15 个是外部程序/固定端口/子进程型，按资源键严格核对后真正可并行的比例可能低于文档预期，71s → 20-30s 的目标可能达不到。建议在落地步骤 3 前先输出"静态契约 47 文件资源键核对表"，用事实校准收益。
4. **真实进程阶段并行粒度缺口**：补充优化 2 说"逐测试核对"，但现有基础设施（`_运行单文件子进程`）是**文件级**并行；真实进程阶段仅 2 个文件（57 用例），若按文件级并行收益为零，必须新增"测试方法级子进程任务"才能兑现"逐测试并行"。文档未明确该粒度差距，落地步骤 4 前需决策：a) 文件内按测试方法拆分任务（新增机制）；b) 维持文件级并行（则该阶段收益≈0，需下调预期）。
5. **断点写协调与失败语义**：文档 L146-147 的"终止其余 + 记录第一个失败阶段"在单池扁平化下实现为：任务携带阶段标签，失败时 `cancel()` 未启动任务 + 终止已运行同阶段/跨阶段子进程；断点写入加"首个失败者"仲裁（见 §2.2-遗漏 4）。
6. **验证命令建议**：实现后验收用 `python3.14 测试中心/运行测试.py --范围 常规`（阶段并行生效）+ `--测试文件 ... --并行数 N`（工作包回归）+ 慢速层按需 `--范围 慢速 --强制慢速`。
