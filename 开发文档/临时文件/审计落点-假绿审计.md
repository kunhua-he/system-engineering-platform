## 一、实验记录（Python 3.14.4 实测）

### 1. sys.addaudithook 捕获能力

| 验证项 | 结果 | 证据 |
|---|---|---|
| 捕获 open（内置） | ✅ 触发 `open` 事件 | 参数 `(路径, mode字符串, flags)` |
| 区分读/写 | ✅ | `'r'`→读、`'w'`/`'a'`→写、`'r+'`→读写；`os.open` 时 `mode=None` 但 `flags & 0o3`：0=只读/1=只写/2=读写 |
| 捕获 os.listdir | ✅ | 事件名 `os.listdir`，参数 `(路径,)` |
| 捕获 os.scandir | ✅ | 事件名 `os.scandir`，参数 `(路径,)` |
| 捕获 os.walk | ✅（间接） | os.walk 内部走 scandir，经 `os.scandir` 事件暴露 |
| **os.stat 类存在性探测** | ❌ **盲区** | `os.stat`/`os.path.exists`/`os.path.isfile`/`os.path.getsize`/`Path.exists`/`Path.is_file` **均不触发任何 audit 事件** |
| import 事件 filename | ⚠️ **为 None** | `import` 事件参数 `(模块名, None, sys.path, sys.meta_path, sys.path_hooks)`——**filename 恒为 None**，不能靠 import 事件取路径 |
| 间接 import（A→B） | ✅ 捕获 | 模块 B 的 `.py` 经 `open` 事件记录（**依赖捕获完全依赖 open 事件**） |
| 动态 import（importlib） | ✅ 捕获 | 同样走 open 事件 |
| 网络访问 | ✅ 可捕获 | `socket.__new__` / `socket.connect` 事件（弱依赖检测可用） |
| fd 型 open 事件 | ⚠️ 噪音 | `subprocess` 管道产生 `open(3, 'r', ...)`，path 为 int **无法映射路径** |

### 2. 子进程是否继承 hook（关键边界）

| 方式 | 结果 | 证据 |
|---|---|---|
| `subprocess.run/Popen`（exec 型） | ❌ **不继承** | 子进程内读文件，父进程 hook 看不到（实测子进程独立注册才记录到 9 条；父进程只见 `subprocess.Popen`/`_posixsubprocess.fork_exec` 事件本身） |
| `os.fork`（不 exec） | ⚠️ 继承但隔离 | fork 后子进程内父 hook 仍生效，但事件写子进程**写时复制私有副本**，父进程看不到（父进程 open 事件数=0） |
| sitecustomize 注入 | ✅ 可行但噪音巨大 | 经 `PYTHONPATH/sitecustomize.py` 注入成功，但子进程解释器启动自身产生 **104978 行** open 事件（加载标准库），必须路径过滤后才可用 |

### 3. hook 是否可移除

- ❌ **不可移除**：`sys.addaudithook` 返回 None；官方无移除接口。
- ⚠️ 同一函数重复注册会**重复触发**（实测注册 2 次后单次 open 触发数倍增）→ 运行测试.py 若在文件级独立进程中注册，进程隔离可避免叠加；同进程多次注册必须防重（用模块级单例标记）。

### 4. 性能开销（10万次 open+read 实测）

| 场景 | 耗时 | 说明 |
|---|---|---|
| 无 hook（独立解释器） | 1.356s | 基线 |
| 带 hook（记录全部事件） | 1.352s | **几乎无差异**：open 本身约 13.5μs/次占主导，audit 开销可忽略 |

- 内存：10 万条事件 ≈ **22MB**（单条约 223 字节）；JSON 序列化约 94 字节/条。
- ⚠️ 文档机制⑦"记录文件 200KB 上限" ≈ **仅 2000 条事件**——一个测试 import 平台代码就要 open 几百个文件（.py/.pyc），加临时文件读写**很容易超 2000 条** → 大量测试落入弱依赖 → 缓存收益大幅缩水。**必须按路径去重后再记摘要**（同一文件多次 open 只记一次，事件数=不同文件数，通常 <100）。

## 二、核对结果

### 1. 假绿防线 5 条逐条核对

| 防线 | 结论 | 缺陷/修正 |
|---|---|---|
| 1. 依赖实测记录非猜测 | ⚠️ 方向对，有 3 个缺口 | ① **pyc 假绿路径（实测确认）**；② fd 型 open 事件（int 路径）需忽略；③ stat 类存在性探测无事件（见防线 3） |
| 2. 文件级内容摘要双向钉死 | ✅ 成立 | 内容 sha256 摘要，无模糊地带 |
| 3. 极端情况保守兜底 | ⚠️ 检测手段未定义 | 网络事件可用 audit 捕获（socket.connect）→ 应记录并标弱依赖；stat 类探测无法用 audit 检测 → 建议静态扫描测试源码中 `exists()/is_file()/getsize()` 调用，命中即标弱依赖；C 扩展读文件只能靠"测试 import 含 C 扩展库 → 弱依赖"静态规则 |
| 4. 环境摘要覆盖外部程序 | ❌ **实现缺口** | 见下节"环境摘要" |
| 5. 门禁语义不变 | ✅ 成立 | 零测试/导入失败/未解释跳过/缓存假绿检测不变 |

### 2. 间接 import 是否被捕获（任务点 3a）

✅ **被捕获**，但机制与文档表述不同：依赖捕获**完全依赖 open 事件**（import 事件 filename=None 不可用路径）。实测 import 模块A（A import B）时模块 B 的 `.py` 被 open 事件记录。

### 3. 环境摘要只含 soffice/psql 是否够（任务点 3b）

❌ **不够**。实测测试中心外部程序调用频率：

| 外部程序 | shutil.which 出现次数 | 调用位置 |
|---|---|---|
| soffice | 7 | 支持库/模块库（静态契约阶段） |
| textutil | 4 | 启动监督器（未进常规阶段） |
| tesseract | 4 | 支持库/模块库（静态契约阶段） |
| ffmpeg/ffprobe | 各 2 | 模块库/支持库（静态契约阶段） |
| security | 1 | 慢速层 |
| psql | 1 | 慢速层 |
| docker | 1 | 运行核心 |
| sw_vers/pgrep/lsof/git/sleep/ps | 若干 | 各阶段 subprocess 命令 |

**关键缺陷**：非环境敏感阶段（静态契约/组件合规/结构迁移/权威状态/资源并发/平台控制面/反向破坏/项目装配）命中缓存时**不校验环境摘要**——`阶段缓存可复用`（运行测试.py:158-164）只在 `阶段名 in 环境敏感阶段` 内比对环境摘要。而静态契约阶段（支持库 16/29 + 模块库 4/12 测试文件）**实际调用 soffice/tesseract/ffmpeg/ffprobe**。即使按文档要求"扩展全部外部程序"，现有复用逻辑也不比对 → **外部程序升级/PATH 变化 → 静态契约阶段缓存仍命中 → 假绿**。

> 修正建议：① 运行测试.py:158 处放开——非环境敏感阶段也校验环境摘要（或按阶段声明其依赖的外部程序）；② 环境摘要外部程序清单从静态扫描 `shutil.which("X")` 与 audit 的 `subprocess.Popen` 事件动态收集补全（至少 soffice/tesseract/ffmpeg/ffprobe/textutil/docker/psql/security/sw_vers）。

### 4. 非环境敏感阶段是否校验环境摘要（任务点 3c）

❌ **不校验**（代码确认，见上节）。这是防线 4 落空的结构性原因。

### 5. pyc 假绿路径（任务点 3a 延伸，本次审计最重要新发现）

**实测**：
- 第一次 import：open `.py`（编译）+ 写 `.pyc`
- 第二次 import（pyc 新鲜）：**只 open `.pyc`，不 open `.py`**

**后果**：若实现按"实测依赖"记录，第二次运行时依赖清单里是 `__pycache__/X.cpython-314.pyc` 而非 `X.py`。若实现排除 `.pyc`/`__pycache__`（符合"工程缓存可删除"精神），则 `.py` 源码依赖**缺失** → 改 `.py` 源码 → 缓存不失效 → **假绿**。

> 修正建议（机制②必须补充）：审计 open 事件时把 `__pycache__/X.cpython-314.pyc` **规范化为源 `X.py`**（去 `__pycache__` 段、去 `.cpython-314` 后缀、`.pyc→.py`），依赖清单恒存 `.py` 路径+摘要。这样无论 pyc 新鲜与否，改源码必失效。

### 6. 真实进程阶段弱依赖兜底是否导致文档预期失效（任务点 4）

- 文档预期表"改 1 个小文件（真实进程依赖）≈180s"与"真实进程 57 个测试基本全是子进程型 → 全部弱依赖 → 有效期大幅缩短"**自洽**（子进程审计未实现前，整阶段重跑 ~180s）。
- ⚠️ **风险点**：当前真实进程阶段是环境敏感阶段，缓存有效期 = `运行证据有效秒` = **7 天**（运行测试.py:54）。若文件级缓存落地时"弱依赖有效期大幅缩短"未给出**具体 TTL**，实现者沿用 7 天 → 子进程型测试改动后仍命中 7 天缓存 → **假绿**。
- > 修正建议：弱依赖 TTL 必须显式定义（建议 ≤1 小时，或子进程审计未实现时真实进程阶段**不进文件级缓存**）；文档"未实现前维持环境敏感短效缓存"应写明确切秒数，与现有 7 天口径区分。

## 三、修正建议汇总（文档需修订处）

1. **机制②补 pyc 规范化**：`__pycache__/X.cpython-*.pyc` → 源 `X.py`，依赖清单恒存 `.py`。（防假绿，最重要）
2. **机制②补临时目录排除**：`mkdtemp`/`TMPDIR`/`工程缓存/验证运行` 等 UUID 临时路径**不得计入依赖**（否则 round-trip 测试"写→读回"依赖 UUID 路径 → 永久假失效，缓存收益归零）。目录扫描事件只记录系统根内的目录。
3. **机制⑦上限按"去重后的不同文件数"**：200KB 上限前先按路径去重；否则 2000 条事件上限（实测 94 字节/条 JSON）会把所有常规测试打入弱依赖。
4. **防线 3 补检测手段**：网络事件（socket.__new__/socket.connect）audit 可捕获 → 记录即标弱依赖；stat 类存在性探测无事件 → 静态扫描测试源码 `exists()/is_file()/getsize()` 命中即标弱依赖；C 扩展读文件 → "import 含 C 扩展库"静态规则标弱依赖。
5. **防线 4 补两处**：① 环境摘要外部程序清单扩展（soffice/tesseract/ffmpeg/ffprobe/textutil/docker/psql/security/sw_vers，按 audit Popen 事件 + 静态 which 扫描收集）；② 非环境敏感阶段也要校验环境摘要（改 运行测试.py:158 条件）。
6. **弱依赖 TTL 显式化**：文档给出具体秒数（建议 ≤3600s），与现有 7 天 `运行证据有效秒` 区分。
7. **fd 型 open 事件**（path 为 int）一律忽略，不计入依赖、不触发弱依赖（subprocess 管道内部噪音）。

## 四、独立建议（超出文档范围的观察）

1. **子进程注入的落地形态**：sitecustomize 注入实测可行但产生 ~10.5 万行噪音（解释器启动加载），必须①路径过滤（只记 系统根/测试中心，排除标准库/临时目录）②仅记录 `open`/`os.listdir`/`os.scandir` 三类事件并**按路径去重**后写共享记录文件；对覆盖 env/使用非本解释器的子进程注入会失效，仍须弱依赖兜底。
2. **运行测试.py 现有阶段缓存的环境摘要缺陷应先行修复**：这是本次审计发现的**现网已存在**的假绿路径（非敏感阶段不校验环境摘要），与测试加速方案无关，建议立即修（运行测试.py:158 放开非敏感阶段校验）。
3. **审计记录自身不得触发审计**：hook 内写记录文件会触发新的 open 事件形成递归/污染——应在 hook 内只 append 到内存列表（或仅在去重表命中新路径时再写），记录文件写入放在测试结束、hook 不感知路径过滤之外完成。实测 sitecustomize 注入方案里写记录文件的 open 事件被自身记录（首行就是记录文件自身）——必须按路径忽略记录文件。
4. **import 事件 filename=None 的教训**：任何"静态 import 分析"都必须以 open 事件为事实来源，import 事件只能用于标记"发生了动态导入"。
5. **并行与审计叠加**：文件级独立进程天然隔离 hook 状态（不可移除特性+同进程多文件会叠加事件），与补充优化 1/2 的独立进程设计一致，无需额外处理；但子进程注入时注意父进程与子进程记录文件分文件（按 PID/文件哈希命名），避免并发写同一记录文件。
