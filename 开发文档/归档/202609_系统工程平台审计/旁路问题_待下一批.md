## B1　个人蒸馏支持库.查询上下文 —— 无法写出正向场景

- **现象**：`支持库/后端/个人蒸馏支持库/验证场景.json` 中 `查询上下文` 只有负向步骤（`成功=false / 状态码=500 / 错误码=个人蒸馏不可用`）。

- **待决选项（下一批择一）**：

## B8　收口登记（delivery_closeout）指纹算法与证据生产者不一致 —— 任何真实工作包都无法收口

- **来源**：2026-09-11 热接入子包归属修复工作包（`8790f58431944669`）收口时实测。
- **现象**：`delivery_closeout` 恒定返回
  `{"错误码":"EVIDENCE_MISMATCH","阻断标记":["证据指纹不匹配"]}`，即使刚刚用
  `verify_and_record` 记录了退出码 0 的通过证据。
- **根因**：两个模块各自实现"工作区指纹"，算法不同且键名不同：
  - **生产者**：`MCP工具箱/项目服务.py::_代码指纹` → `sha256(git status --porcelain=v1 -z)`，
    **64 位十六进制**，写入证据的 `工作区指纹` 字段。
  - **消费者**：`MCP工具箱/协作状态.py::收口登记` → `计算代码指纹(worktree路径)`，
    **文件内容摘要取前 16 位**，读证据的 `指纹` 键（`_读取验证证据` 把 `工作区指纹`
    映射成 `指纹`）。
  两者取值域完全不同（64 位 git 状态摘要 vs 16 位内容摘要），**恒不相等**，
  故任何带验证证据的工作包都收口失败。
- **为何既有测试没发现**：`测试中心/MCP工具箱/测试_协作状态.py` 的
  `_写验证(...)` 直接**伪造**证据并传入 `计算代码指纹(...)` 的值（第 68~70、257 行），
  即测试是按消费者口径写的，与真实生产者 `verify_and_record` 的产物不一致 ——
  属**假绿**测试，掩盖了集成缺陷。
- **旁证**：`工程缓存/协作状态/` 下所有记录的最后一次成功收口停在 2026-09-02；
  提交 `e616e74`（"修复MCP三处自卡点……①协作状态指纹排除项目证据/临时文件（收口死循环解除）"）
  只把 `项目证据` 加进 `_排除片段表` 让内容摘要稳定，**没有消除算法不一致**，死锁依旧。
- **待决（二选一，需平台维护确认）**：
  1. **推荐**：`_运行验证` 额外写入 `"指纹": 计算代码指纹(项目根目录)["指纹"]`，
     使证据同时携带两种指纹，消费者不动、`测试_协作状态.py` 不动，最小改动。
  2. 或把 `收口登记`（及 `_聚合一条` 的阻断标记）统一改用
     `发布治理.当前工作区指纹`，与全平台"真实工作区指纹"口径对齐，
     但需同步改 `测试_协作状态.py` 的证据构造。
- **为何未修**：改动落在 `MCP工具箱/`，**需重启 8766 MCP 服务进程**（PID 77503，`--http --端口 8766`，
  多会话共享）；另有并行会话正在使用该 MCP，与本工作包边界不符，按旁路顺延。
- **影响**：**平台级——所有工作包收口全部失效**，不属于任何单个包。
