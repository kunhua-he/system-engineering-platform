- 来源：`~/Downloads/e.7z`

```text
  ├─ 编辑接口元数据：命令、数据类型、属性、事件、常量、依赖
```

### 三类扩展的边界

```text
编辑期扩展                  编译期扩展                  运行期扩展
MacroProcessor              CompileProcessor            GetNewInf + 命令函数
     │                           │                            │
     ├─即时值/数组                ├─程序信息/常量              ├─命令执行
     ├─IDE 辅助                  ├─输出目标                    ├─对象生命周期
     └─短生命周期内存             └─编译上下文                  └─外部库/系统 API
            │                           │                            │
            └───────────────都必须经过宿主校验和生命周期管理───────────────┘
```

## 关键契约

1. 支持库以 `GetNewInf` 导出函数返回 `LIB_INFO`，由 IDE 读取统一元数据。
2. `.fne` 带编辑信息和运行支持代码；`.fnl` 带编辑信息但无运行代码；`.fnr` 只提供运行代码；`.lib` 用于静态链接。
3. 支持库元数据包含 GUID、版本、最低 IDE/核心版本、名称、说明、能力分类、命令表、数据类型表、常量表、依赖文件和操作系统位图。
4. 命令执行通过命令索引映射到函数指针；对象数据类型附带构造、析构、拷贝、方法、属性和事件描述。
5. 插件以 DLL 导出窄接口（示例为 `MacroProcessor`），输入输出使用明确的数据类型标签；插件自己负责临时内存的生命周期。
6. 编译链把“编辑元数据”“运行实现”“静态链接实现”分离，使 IDE 能加载声明而最终程序只携带运行所需部分。

### 命令索引是 ABI，不是普通列表

```text
支持库第一次发布
  → 命令/方法按顺序登记
  → 工程和编译结果保存全局命令表索引
  → 后续版本只能在末尾追加
  → 已废弃项目只能隐藏，不能删除或重新排序
```

Delphi EDK 明确说明：旧源程序和已编译程序都可能记录命令/方法在全局表中的索引；插入或删除会使旧索引指向错误实现。Delphi 版用命令/方法版本号稳定排序，C/C++ 版则要求维护原始数组位置。这是整个生态最重要的兼容性约束之一。

### 类型与数据内存模型

```text
系统基本类型
  ├─ 数值：BYTE/SHORT/INT/INT64/FLOAT/DOUBLE
  ├─ 逻辑：BOOL
  ├─ 日期：DATE/DOUBLE
  ├─ 文本：指针 + 运行时管理的字符串数据
  ├─ 字节集：长度 + 数据
  └─ 子程序指针/语句类型

自定义复合类型
  ├─ 类型标志编码“系统/用户/支持库”来源
  ├─ 类型索引编码所属支持库和类型编号
  ├─ 小于 4 字节成员按 4 字节对齐
  ├─ 数组携带维数和每维长度
  └─ 生命周期通过构造/析构/拷贝命令回调
```

`MDATA_INF`/`MDATA` 是命令 ABI 的统一容器：同一命令可按参数标志接收立即值、变量地址、数组、任意类型或返回值。文本、字节集、复合类型和窗口单元都不是裸 JSON 值，而是由运行时约定所有权和释放路径的内存布局。

### `LIB_INFO` 的实际职责

```text
LIB_INFO
  ├─ 身份：格式号、GUID、主/次/构建版本
  ├─ 兼容性：最低 IDE 版本、最低核心库版本、OS 位图
  ├─ 展示：库名、说明、作者、分类
  ├─ 类型：自定义数据类型、成员、属性、事件、构造/析构/拷贝
  ├─ 命令：命令定义数组 + 命令执行函数数组
  ├─ 扩展：AddIn、SuperTemplate、通知回调
  ├─ 常量：预定义常量和资源
  └─ 依赖：支持文件列表
```

这不是“插件描述文件”，而是一个同时服务编辑器、编译器和运行时的 ABI 元数据入口。新平台应将其拆成可审计的声明文件与受管执行入口，避免 C ABI 结构体直接成为跨进程协议。

## IDE 与编译器扩展

归档还提供两类不同的扩展面，不能合并成一个插件接口：

- IDE/宏插件：DLL 导出 `MacroProcessor`，处理带数据类型标签的即时值、数组、文本和字节集；插件保留的临时内存必须在下一次调用或卸载时释放。
- 编译前插件：DLL 导出 `CompileProcessor`，接收 `COMPILE_PROCESSOR_INFO`，通过回调修改程序名称、作者、版本、数值/日期/逻辑/文本/图片常量，或决定输出文件名。插件可以按纯程序名筛选目标工程。

`sdk/cpp/elib/PublicIDEFunctions.h` 还定义了按功能号分组的 IDE 操作：光标移动、结构节点导航、插入/删除子程序和数据类型、撤销重做、窗口/资源编辑等。这说明易语言的工程模型不是文本编辑器，而是“结构化工程树 + 稳定编辑命令协议”。

对轻代码平台的直接启示：

1. 编辑器应操作结构化中间表示，文本/图形界面只是视图；Agent 可以直接生成同一中间表示。
2. 扩展协议至少拆为编辑期、编译期、运行期三类，分别声明权限、输入输出契约和生命周期。
3. 编译期扩展只能修改经过校验的项目元数据和常量，不能直接改写任意产物或绕过发布门禁。
4. 工程文件可以使用二进制或数据库存储，但必须同时提供版本化、可迁移、可审计的公开中间表示。

## 工程与模块系统

### `.e8` 项目配置层

`.e8` 是 ANSI INI 风格的可读项目配置，不是源码本体。它把一个或多个 `.e/.ec/.txt` 源合并到一次编译上下文，并覆盖程序设置与用户常量：

```text
读取 .e8
  ├─ [settings] source=...（可重复）
  ├─ 解析相对路径并合并源文件
  ├─ 若存在 .ec，先清理 .e 内原有模块引用
  ├─ 去重启动窗口/启动子程序
  ├─ [AppSettings] 决定 WinEXE/WinDLL/LinuxConsoleELF 等目标
  ├─ 写入名称、版本、作者、图标、输出文件和插件
  └─ [user_consts] 创建/覆盖编译常量
       └─ 常量折叠 → 条件编译式裁剪代码
```

### `.ec` 模块、`.epk` 易包和 `.npk/.run` 外部制品

```text
.ec 易模块
  ├─ 可被多个工程导入
  ├─ 保存子程序、类、资源和支持库引用
  ├─ 可设置密码/加密，限制在其它模块中继续使用
  └─ 通过 e8 source 或 IDE 导入

.epk 易包
  ├─ 由 el.exe 负责打开/安装包格式
  ├─ 可输出类的方法
  └─ 与易模块协作，作为可分发的复用包

.npk / .run / 外部 DLL/OCX
  ├─ 厂商控件、COM、运行库或外部协议资源
  ├─ 由工程引用和安装器打包
  └─ 不属于语言核心 ABI，但会决定真实运行依赖
```

### `.ec` 是什么：易模块的逻辑构成

`.ec` 不是一个文本源码目录，也不是已经链接完成的 EXE。它是可被多个工程引用的专有工程容器。公开 SDK 和样本能确认它保存“可复用程序结构 + 支持库引用 + 资源/编辑信息”这一逻辑层，但不能把容器中每个二进制字段直接命名为确定语义。

```text
.ec 易模块
  ├─ 文件头
  │    └─ CNWTEPRG                         已确认的工程容器魔数
  ├─ 工程身份候选
  │    ├─ 模块名称/作者/版本/说明
  │    ├─ 模块密码/加密状态候选
  │    └─ 模块 GUID 或引用标识候选
  ├─ 结构节点候选
  │    ├─ 程序集/子程序
  │    ├─ 类、方法、属性、事件
  │    ├─ 参数、变量、常量和数据类型
  │    └─ 可导出的公共方法/类方法
  ├─ 依赖边
  │    ├─ 引用的支持库 GUID/版本/命令索引
  │    ├─ 引用的其他 .ec 模块
  │    └─ 外部 DLL/OCX/NPK/RUN/资源文件
  ├─ 资源与编辑状态候选
  │    ├─ 窗体/组件树和属性块
  │    ├─ 图片、声音、帮助或附属数据
  │    └─ 编辑器定位、结构索引等恢复信息
  └─ 编译输入边界
       ├─ 作为 .e8 source 合并输入
       ├─ 作为 IDE 工程模块引用
       └─ 进入编译器后转为当前工程的统一中间结构
```

#### `.ec` 的导入流程

```text
工程发现 module.ec
  │
  ├─ 读取魔数/版本/完整性
  │    ├─ 不匹配 → 拒绝导入
  │    └─ 匹配但版本未知 → 只读或迁移模式
  │
  ├─ 读取模块身份
  │    ├─ 名称/版本/GUID 冲突检查
  │    ├─ 密码模块 → 请求密码或受控解密能力
  │    └─ 签名模块 → 验证签名和来源
  │
  ├─ 读取依赖
  │    ├─ 支持库 GUID → 与已登记 .fne/.fnl 匹配
  │    ├─ 其他 .ec → 递归解析并检测循环
  │    └─ DLL/OCX/NPK/RUN → 生成外部依赖清单
  │
  ├─ 合并结构节点
  │    ├─ 公共类/方法进入可见 API
  │    ├─ 私有节点只在模块内部可见
  │    ├─ 命名冲突 → 按模块作用域隔离或阻断
  │    └─ 启动窗口/启动子程序 → 按工程规则去重
  │
  └─ 登记工程引用
       ├─ 模块文件指纹、版本和来源
       ├─ API/依赖摘要
       └─ 编译上下文锁定，不因目录中另一个同名模块静默漂移
```

#### `.ec` 已确认与未确认边界

| 层次 | 当前能确认的内容 | 不能直接宣称的内容 |
| --- | --- | --- |
| 容器身份 | `.ec` 属于 `CNWTEPRG` 工程容器族 | 全部头部字段的确切类型和校验算法 |
| 复用语义 | 可作为 `.e8 source` 或 IDE 模块导入；可保存类/子程序/资源/支持库引用 | 每个字节区块对应的 AST 节点编号 |
| 安全语义 | 版本记录说明支持模块加密/密码和签名认证 | 加密算法、密钥派生和解密协议 |
| 编译语义 | 模块会参与合并、命令索引和依赖解析 | 完整链接/重定位/优化过程 |
| 迁移能力 | 可提取魔数、字符串、GUID、支持库名和结构标记 | 无原版行为样本时的无损反编译 |

### `.epk` 是什么：可装载易包的构成

`.epk` 与 `.ec` 的边界是“模块工程复用”与“运行/分发装载”。`epackage.exe` 在编译时封装 EXE 型易语言执行代码，`dll_pkg.dll` 封装 DLL 型执行代码，`el.exe` 负责按命令行启动或安装易包。

```text
易包生成
  │
  ├─ 输入
  │    ├─ 编译后的易语言执行代码
  │    ├─ 公共类/方法导出声明
  │    ├─ 常量、变量、窗体/资源和帮助
  │    ├─ 支持库/核心库依赖
  │    └─ 重定位与导出信息
  │
  ├─ 选择封装器
  │    ├─ EXE 型 → epackage.exe + epackage.asm
  │    └─ DLL 型 → dll_pkg.dll + dll_pkg.asm
  │
  ├─ 写入 EPK 容器
  │    ├─ 头部/格式标记
  │    ├─ 依赖记录：核心库 GUID、版本和能力行
  │    ├─ const 段：常量
  │    ├─ var 段：变量/运行数据
  │    ├─ form 段：窗体/组件资源
  │    ├─ help 段：包内帮助或说明
  │    ├─ code 段：可装载执行代码
  │    └─ reloc1/export：重定位或公共类/方法导出标记
  │
  └─ 输出
       ├─ my.epk
       ├─ 外部依赖清单
       └─ 可由其他工程/易模块调用的包入口
```

#### `.epk` 的装载流程

```text
el <package.epk>
  │
  ├─ LoadEPKFromCmdLine()
  │    └─ 解析命令行和包路径
  ├─ LoadEPKFile()
  │    └─ 读取完整文件并建立内存映射/缓冲区
  ├─ LoadEPKData()
  │    ├─ 校验头部、段偏移和长度候选
  │    ├─ 读取核心库/支持库依赖
  │    ├─ 分配 const/var/form/help/code 段
  │    ├─ 处理 reloc1 或 export 标记
  │    └─ 任一段非法 → “Load EPK data invalid”并停止
  ├─ 解析运行入口
  │    ├─ EXE 包 → 启动执行代码
  │    ├─ DLL 包 → 注册包内导出/类方法
  │    └─ 与 .ec 配合 → 暴露公共类方法给调用工程
  ├─ 运行期
  │    ├─ 绑定核心库和支持库
  │    ├─ 初始化对象/窗口/资源
  │    └─ 记录包句柄、引用计数和错误状态
  └─ 卸载
       ├─ 停止线程/事件
       ├─ 释放代码、资源和依赖引用
       └─ 清理重定位表/导出表/包句柄
```

当前静态证据已确认段名、依赖记录、装载入口和错误分支；段内字段的完整偏移表、压缩/加密、校验和及重定位算法仍是候选，不把 `.epk` 称为已完整逆向格式。

### `.npk` 是什么：COM/OCX 类型描述包

`.npk` 不是易语言执行包。它的主要作用是把外部 COM/OCX/TypeLib 的类型信息翻译成 IDE 能显示的控件、接口、属性、方法、事件和常量。

```text
外部 OCX/TypeLib
  │
  ├─ 类型库身份
  │    ├─ TypeLib GUID
  │    ├─ 版本号/语言
  │    ├─ ProgID/文件名
  │    └─ OCX/COM 注册信息
  │
  ├─ .npk 描述层
  │    ├─ `@@ Lang` 语言/编码段
  │    ├─ `@@ TypeLib` 类型库段
  │    ├─ `@@ OCX` 控件段
  │    ├─ `@@ Interface` 接口段
  │    ├─ 接口方法和 DISPID
  │    ├─ 属性读写方向和参数类型
  │    ├─ 事件名称、参数和回调映射
  │    └─ 常量/枚举/索引信息
  │
  ├─ IDE 登记
  │    ├─ 生成支持库/控件树节点
  │    ├─ 设计器显示属性和事件
  │    └─ 代码编辑器显示调用签名
  │
  └─ 运行期
       ├─ 检查 OCX/DLL 是否安装和注册
       ├─ 创建 COM 实例并绑定接口
       ├─ 通过 DISPID 调用方法/属性
       └─ 按事件连接点接收回调
```

归档样本直接显示：`dm.npk` 有 TypeLib/OCX/Interface 和 `dmsoft`，`jmail.npk` 有 JMail 4.0 与 `POP3.Connect`，`wmp9.npk` 有 Windows Media Player 9 和 COM GUID。因此 `.npk` 更接近“外部协议适配描述”，不是核心运行库；新平台应把它归入受管 COM/外部协议 Provider。

### `.run` 是什么：运行时实现制品

`.run` 文件是支持库运行链中的外部运行制品，通常不提供完整 IDE 编辑信息；它们和 `.fne/.fnr/.lib` 的关系是“设计期声明/运行实现/静态实现”三分，而不是同一文件的不同压缩格式。

```text
工程使用某个运行能力
  │
  ├─ IDE 从 .fne/.fnl 得到命令/类型/属性/事件
  ├─ 编译器把能力调用写入目标代码
  ├─ 依赖解析器发现对应 .fnr/.run/.dll/.npk
  ├─ 动态目标
  │    ├─ 将运行制品复制到输出目录或安装包
  │    ├─ 写入加载顺序和版本指纹
  │    └─ 启动时由核心库/系统加载
  └─ 静态目标
       ├─ 选择对应 static_lib/*.lib
       ├─ 经 linker 合并到 EXE/DLL
       └─ 仍可能需要外部 DLL/OCX/资源
```

归档中的 `.run` 包括 `com.run`、`cominf.run`、`mp3.run`、`ocx.run`、`odbcdb.run`。它们的具体内部格式不是公开 ABI；能确认的是它们位于运行/链接旁路，并分别对应 COM 信息、媒体、OCX 或 ODBC 等外部能力。解析器应先做文件指纹、依赖归属和装载声明，不能把 `.run` 内部猜成 JSON 或普通 DLL。

### 外部 DLL、OCX、TypeLib 与资源文件

```text
支持库/工程声明外部依赖
  │
  ├─ 记录文件名、GUID/CLSID、版本和平台
  ├─ 记录加载方式
  │    ├─ 普通 DLL：LoadLibrary/导出函数
  │    ├─ OCX：注册表/COM 激活/窗口句柄
  │    ├─ TypeLib：接口元数据和 DISPID
  │    └─ 资源目录：media/cfg/theme/字体/模型/图片
  ├─ 设计期
  │    ├─ .fne/.npk 将外部能力映射到命令/控件/属性/事件
  │    └─ IDE 只保存引用和设计数据，不应把 DLL 内存状态写入工程
  ├─ 编译期
  │    ├─ 检查文件存在、架构、版本和导出/注册状态
  │    ├─ 将运行依赖加入制品清单
  │    └─ 静态库/导入库加入 linker 输入
  ├─ 安装期
  │    ├─ 复制 DLL/OCX/资源
  │    ├─ 必要时注册 COM/OCX
  │    └─ 生成卸载清单和版本冲突记录
  └─ 运行期
       ├─ 按依赖顺序加载
       ├─ 创建对象/绑定函数或接口
       ├─ 处理错误、超时和释放
       └─ 卸载时撤销事件连接并释放句柄
```

外部依赖的真实边界必须单独记录：`OgreDll` 需要整套 DLL、`media` 和 `cfg`；`eTools/iDraw` 搭配 SQLite、浏览器引擎和编辑插件；硬件样例还需要驱动、OCX 和设备状态。只复制 `.fne` 或 `.ec`，不能得到可运行产品。

`ecom/` 还暴露了生态层的依赖治理问题：同一模块按文件名并置多个版本（例如精易模块 6.7、7.7.5、8.0.5、8.2.5、8.3.0、11.0.5、11.1.5），也有按日期命名的个人模块。目录没有统一 manifest 或依赖锁，版本选择主要靠人工。它是“可复用模块仓”而不是可解析的包仓库，解释了为什么新平台必须把版本、能力、来源和冲突处理提升为机器契约。

### 工程目录不是单一源码树

样本中一个可运行工程通常由以下旁路共同组成：

```text
工程目录
  ├─ .e 主工程
  ├─ .ec 模块
  ├─ .e8 配置/多文件合并/条件常量
  ├─ .edb/.edt 数据库或教程/资源索引
  ├─ .npk/.run/.dll/.ocx 外部组件
  ├─ .ini/.xml 配置和用户数据
  ├─ help/ 文档
  ├─ setup/ 安装器输入
  └─ 输出 exe/dll/临时调试文件
```

## 工程文件观察

`.e`、`.edb`、`.edt` 等工程文件不是纯文本：`.e` 以 `CNWTEPRG` 开头，后续为专有二进制结构；`.edb/.edt` 用于资源/数据库或教程目录等辅助工程数据。静态样本显示同一工程目录会把源码工程、资源数据库、外部 DLL、帮助文档和构建脚本放在一起。

这类格式适合兼容旧 IDE，但不适合作为新平台唯一事实源。新平台应保留：

```text
公开项目 IR（JSON/数据库，可迁移、可校验）
  ├─ 项目元数据与版本
  ├─ 节点树：模块、子程序、变量、资源、事件
  ├─ 能力调用：能力 id、参数契约、错误处理
  ├─ 编译目标与提供者锁
  └─ 编辑/编译/运行证据
```

## 专有工程格式的自研解析进展

本节记录实际写出的批量扫描逻辑和可重复结果，不把“提取到字符串”夸大成“已经反编译源码”。扫描器对每个文件执行：魔数检查、固定头字段统计、小端整数候选识别、可打印字符串/GB18030 字符串提取、GUID/支持库名归集，并对多个版本快照做同路径差分。

### `.e/.ec/.fd1` 容器

```text
偏移 0x00
  CNWTEPRG                         ← 统一工程数据库魔数
偏移 0x08..0x0f
  版本/格式族的稳定字节序列          ← 不同文件按工程类别出现少量变体
偏移 0x10..0x17
  多数样本稳定的公共字段              ← 继续作为候选头，不命名为确定语义
后续区域
  支持库名、GUID、工程名、命令名、资源名和代码相关字符串
  二进制结构、长度表、压缩/加密字段仍需版本化验证
```

对当前 5.95 快照，`.e/.ec` 共 1,436 个，全部以 `CNWTEPRG` 开头；头部第 16 至 23 字节在样本中保持公共序列。另有同源 E5.9 快照：同一相对路径的 521 个 `.e`、29 个 `.ec`、2 个 `.epk` 和 3 个 `.e8` 与当前快照逐字节相同，说明工程格式跨这两个版本保持稳定，但仍不能由此推出所有字段含义。

### `.epk` 段表

```text
EPK 文件
  → 头部（部分样本为 WJ，部分样本头部全零）
  → 0x24 附近的小端头字段和三组偏移/长度候选
  → 依赖记录：krnln、核心 GUID、版本/能力行
  → 段记录：const / form / help / code / var / reloc1 或 export
  → 代码、资源、帮助和重定位数据
```

`myepk6.epk`（1,223 字节）和 `my_epk20.epk`（770 字节）均在相同的头部布局位置出现 `0x93`、段偏移/长度候选和 `krnln\r<GUID>\r5\r3\r` 依赖记录；前者可见 `@reloc1`，后者可见 `export`。`epackage/source/el.asm` 明确公开 `LoadEPKData`、`LoadEPKFile`、`LoadEPKFromCmdLine`，并校验“Load EPK data invalid”。因此 EPK 可以确定是带运行装载标记点的自描述执行包装格式，不是普通 ZIP；段内字段和重定位算法尚未完整解码。

### 解析结论

```text
可以稳定解析
  魔数、文件类别、版本快照差异、依赖 GUID、段名、可读工程字符串

暂不能安全解析
  所有字段语义、源码 AST、压缩/加密、校验和、重定位表达式、授权数据

继续研究的正确路径
  同路径多版本差分
    → 以 e8/帮助/SDK 的已知名称做锚点
    → 记录字段偏移和长度候选
    → 用原版生成的成对样本做单变量变更
    → 只有行为和字节差分同时稳定才升级为确定字段
```

这已经超出“只看目录和字符串”的层次，但在没有原版 Windows 编译器的情况下，不能把候选字段直接写成公开格式规范。

## 全量旁路审计

归档不是一个只包含编译器的安装目录，而是“核心程序 + 开发 SDK + 社区模块 + IDE 增强插件 + 用户状态 + 硬件/授权工具”的混合快照。顶层同时存在 `e.exe`、`el.exe`、`epackage`、`setup`、`lib`、`ecom`、`samples`、`tutorial`、`clr`、`vreport` 和 `wizard`，所以真实工程能力不能只从 `e.exe` 的导入表推断。

```text
核心主链
  e.exe → 支持库/工程加载 → 编译器 → linker → EXE/DLL/ELF
       │                         │
       │                         ├─ 编译前插件
       │                         └─ tools/link.ini 链接后动作
       ▼
运行旁路
  krnln.fnr/fne → 外部 DLL/OCX/COM → 注册表/系统 API/硬件

开发旁路
  eTools/iDraw → JSON/INI 配置 → IDE 面板、提示、配色、自动保存、模块更新
  ecom/samples → .ec/.epk/.e8 → 可复用模块、样例和发行包

授权/敏感旁路
  支持库 GetNewInf 授权检查 → 认证/签名/硬件代码
  加密狗驱动、正版验证程序、补丁程序 → 不属于公开架构契约
```

### 可审计的旁路

| 旁路 | 归档证据 | 架构结论 |
| --- | --- | --- |
| IDE 用户状态 | `lib/eTools/Data/Config.ini`、`Compile.ini`、`Plugin.ini` | 窗口位置、收藏、最近编译目标和插件状态持久化在用户态，工程复现不能只复制源码 |
| IDE 扩展配置 | `lib/eTools/Set/*.json`、`lib/iDraw/Set/*.json` | 扩展通过声明式表单、快捷键、重启标志和颜色配置注入 IDE |
| 静态链接旁路 | `tools/link.ini` | linker、命令行、警告策略、中间文件保留和最多 100 个 `post_link_actionX` 均可被配置 |
| 外部控件 | `lib/*`、`.ocx/.npk/.run`、帮助目录 | 支持库只是发现/编译入口，真实运行还依赖外部二进制和系统注册状态 |
| 文档旁路 | `help/<库>/index.htm`、`cmd*.htm`、`dt*.htm`、`pty*.htm`、`fevt*.htm` | 命令、类型、属性、事件的用户契约主要由独立 HTML 文档承载 |
| 样例旁路 | `samples/`、`tutorial/` | 样例同时承担回归测试、教学、硬件适配和 ABI 使用示范，不能把样例当作核心实现 |
| 授权旁路 | `sdk/cpp/docs.txt`、`licHtmlView`、顶层验证程序 | 授权失败可以表现为支持库不可发现；授权检查与能力发现发生在同一入口 |

### 敏感资产的处理边界

顶层还包含 `易语言5.95破解补丁.exe`、`正版验证.exe`、`正版验证-新版本多窗口.e`、`InstDrv_32bit.exe` 和 `InstDrv_64bit.exe`。本文只记录它们的存在及其与授权/驱动旁路的关系，不执行、不修改、不分析绕过逻辑；它们不能作为 IDE、编译器或运行时公开契约的证据。

## IDE、编译器和 UI 的证据化模型

没有 `e.exe` 的 UI 源码，因此窗口坐标、内部类名和消息循环不能声称已恢复。但 UI 契约可以由三个互相独立的证据面交叉确认：`PublicIDEFunctions.h` 的编辑功能号、Delphi EDK 的组件接口、`lib/eTools/Set/*.json` 的实际面板配置。

```text
IDE 壳
  ├─ 工作夹/工程树
  │    ├─ 程序结构：程序集、窗口、子程序、变量、常量、资源
  │    ├─ 支持库：类别、命令、数据类型、属性、事件
  │    └─ 外部文件、模块、易包
  ├─ 代码编辑器
  │    ├─ 结构节点导航、插入/删除、撤销重做
  │    ├─ 命令/参数提示、自动补齐、跳转定义、跳回
  │    ├─ 搜索替换、行号、条件编译标记
  │    └─ 源位置与运行时错误映射
  ├─ 窗口设计器
  │    ├─ 组件树、父子容器、设计态/运行态
  │    ├─ 固定属性 + 自定义属性
  │    ├─ 事件表、事件参数和事件回调
  │    └─ 属性块保存/恢复与图标资源
  ├─ 输出/调试面板
  │    ├─ 编译器和 linker 输出
  │    ├─ 错误定位、临时调试目录、DLL 状态
  │    └─ 插件可以接管或扩展输出/提示面板
  └─ 扩展与设置
       ├─ 配色、快捷键、自动保存、模块引用更新
       ├─ 编译器/编译前插件
       └─ 数字签名、支持库配置和安装
```

`PublicIDEFunctions.h` 还明确暴露编译目标操作：普通 Windows EXE/控制台/DLL/易模块、Linux 控制台 ELF/易模块，以及对应静态编译入口。这说明编译器不是单一“生成 EXE”按钮，而是一个目标矩阵和统一项目模型的调度器。

从完整功能号分组可以进一步还原主窗口的状态机：`FNST_MOVE` 负责语句、参数、子程序树和光标导航；`FNST_MODIFY` 负责插入/删除/剪切粘贴、窗口控件网格/对齐/尺寸；`FNST_DOCUMENT` 负责新建、打开、保存、另存为、自动备份和外部文件记录；`FNST_OTHER` 负责工作夹/输出/命令/组件面板、资源编辑、帮助、向导、OCX 打包、库刷新和插件标签页；`FNST_RUN` 负责单步调试、断点、变量查看、普通/静态/易包编译以及 Windows/Linux 目标矩阵。

```text
IDE 主窗口状态机
  当前工程/活动节点
       │
       ├─ 程序结构节点 → 代码编辑器/跳转/提示/撤销
       ├─ 窗口或组件节点 → 窗体设计器/属性表/事件表/预览
       ├─ 资源节点 → 图片/声音/常量/数据编辑器
       ├─ 支持库节点 → 命令/类型/帮助/安装/刷新
       └─ 运行状态 → 输出面板/调试器/断点/变量查看
```

`FN_ADD_TAB`、易格式剪贴板和当前活动节点查询说明插件可把自定义面板嵌入同一个 IDE 状态机，而不是只能启动外部工具。

### 声明式 IDE 增强层

`lib/eTools/Set/*.json` 把大量 IDE 增强设置写成声明式表单：`checkbox`、`select`、`text`、`file`、`textarea`、`color`、`card`、`hr`，并用 `union/punion` 控制条件显示、`restart` 标记重启生效。`EditEx.json` 覆盖符号补齐、括号高亮、快捷键、行移动和参数跳转；`提示输出扩展.json` 覆盖输出保留、时间、定位列表、颜色和命令提示；其它配置还覆盖自动备份、智能编译、代码视图、鼠标手势、批量资源和模块引用更新。

```text
插件目录/配置
  → 声明设置表单与默认值
  → eTools/iDraw 生成设置面板
  → 用户态 INI/JSON 保存状态
  → 重启标记/条件联合控制行为
  → IDE 工作夹、编辑器、输出面板或编译流程
```

这是一套轻量的“配置驱动插件 UI”架构，但配置文件本身包含外部 URL、命令执行和用户状态，不能直接视为可信策略。新平台应将设置 schema 与执行权限分离，所有命令动作通过能力契约登记。

目录盘点还显示 `lib/eTools` 与 `lib/iDraw` 存在两套高度相似的插件/配置树；插件旁边有 `Cmd` 命令工具、`linklib` 运行依赖、Node/SQLite/wke 等边车，以及 `SciLexer`、输出控件、资源/主题/窗口尺寸模块。这不是单一 DLL 插件，而是“IDE 宿主 → 插件 DLL → 命令工具/边车进程 → 用户态配置”的多层系统；两套树并存也意味着升级时存在状态和版本分叉风险。

### 帮助系统是可寻址契约库

`help/` 不是一份长手册，而是按支持库分目录的机器可寻址文档数据库。每个库通常有 `index.htm`，再以稳定编号组织 `ctN.htm` 命令类别、`dtN.htm` 数据类型/控件、`ptyN.htm` 属性、`fevtN.htm` 事件和 `const.htm` 常量，并链接样例。归档共有 7,635 个 HTML/HTM 文件、85 个 CHM 和 3 个图片文件，核心库目录 `krnln` 有 1,198 个页面。

```text
支持库包
  ├─ ABI 元数据（命令/类型/属性/事件）
  ├─ help/index.htm
  │    ├─ ctN 命令类别
  │    ├─ dtN 数据类型/窗口单元
  │    ├─ ptyN 属性
  │    ├─ fevtN 事件
  │    └─ const 常量
  └─ samples/ 样例与设计数据
```

编号化帮助与命令/类型稳定索引相互呼应；新平台应让能力契约同时生成机器 schema、IDE 提示、Agent 说明和用户文档，避免文档与实际注册表漂移。

组件设计态的可证实调用顺序为：`PFN_CREATE_UNIT` 创建实例，`PFN_GET_PROPERTY_DATA` 读取属性，`PFN_NOTIFY_PROPERTY_CHANGED` 响应修改，`PFN_GET_ALL_PROPERTY_DATA` 将完整属性打包，之后再次创建时把该数据块传回；运行态组件通过 `EVENT_NOTIFY/EVENT_NOTIFY2` 和 `NRS_EVENT_NOTIFY*` 将事件转发给语言程序。属性块是扩展持久化的核心，而不是 UI 的临时状态。

## 版本演进与兼容策略

顶层 `readme.txt` 的版本记录给出一条稳定的演进主线：5.3 引入易包与外置封装源码；5.5 开放 IDE 接口、IDE 就绪通知和 `.ec` 作为 `.e8` source；5.6 引入多文件外部记录、易模块加密；5.7 增强跳转/搜索、编译插件和 `NL_ADD_NEW_ELEMENT`；5.8 修复静态重定位并提供错误源位置；5.9 增加签名认证、模块/支持库搜索；5.92 引入条件编译；5.93 引入行号和全局搜索替换；5.95 继续在旧 ABI 上做 UI 和 PNG 修复。

```text
稳定旧 ABI
  → 增加通知码/功能号
  → 增加文件格式或配置旁路（e8、epk、插件 JSON）
  → 保留旧命令索引，废弃命令改为隐藏

```

这解释了它为什么能在多年维护中继续加载旧支持库，也暴露了维护成本：功能号、命令数组、插件通知和用户态配置都是隐式 ABI，任何重排或清理都可能破坏历史工程。

## 支持库授权与三套制品

`sdk/cpp/samples/licHtmlView/HtmlView.cpp` 给出了比一般目录观察更明确的授权边界：同一套源代码分别构建 `.fne`、`.fnr` 和 `.lib`；`GetNewInf` 在未授权时可以返回空白/受限编辑元数据，但运行版和预编译代码仍可使用。授权保护的是编辑接口发现和开发能力，不等同于把运行时执行整体加密。

```text
同一支持库源代码
       │
       ├─ 普通动态构建（无宏裁剪）
       │    └─ .fne：编辑元数据 + 运行实现
       ├─ __COMPILE_FNR
       │    └─ .fnr：运行实现 + 最小运行类型信息
       └─ __E_STATIC_LIB
            └─ .lib：静态链接实现，隐藏编辑元数据/GetNewInf

GetNewInf
  ├─ 授权通过 → 完整 LIB_INFO/LIB_INFO2
  └─ 授权失败 → 空白或受限编辑面；运行/静态路径仍按其制品职责工作
```

静态编译手册还规定：动态支持库在编译阶段返回命令名、通知函数名和依赖库，编译器生成 COFF `.obj`，`resym` 重命名私有符号，最后由第三方 linker 与 `xxx_static.lib` 合成 EXE/DLL。`.run` 库通过 `xxx_LoadLibrary/xxx_FreeLibrary/xxx_GetProcAddress` 这组三个 C 符号提供运行期装载。这里存在“编辑声明、运行实现、静态实现、链接辅助信息”四个不同职责，不能压缩成一个包类型。

## 数据 ABI、宿主分配器与错误通道

支持库命令的参数并非 JSON 或 C++ 值拷贝，而是 `MDATA_INF`/`MDATA` 这种带数据类型标签、变量地址、数组标志和复合数据指针的统一容器。`sdk/cpp/elib/fnshare.cpp` 和 `sdk/delphi/e.pas` 规定，支持库写回文本、字节集、复合对象或数组前，必须通过 `NRS_MFREE/NRS_FREE_ARY` 释放旧所有权，再用 `NRS_MALLOC` 或对应通知分配新内存；运行时错误通过 `NRS_RUNTIME_ERR` 上报。

```text
命令调用
  → 参数标签（立即值/变量地址/数组/复合对象）
  → Provider 检查实际数据类型与数组维度
  → 宿主分配器分配/释放结果
  → NRS_RUNTIME_ERR 统一报告错误
```

这是旧架构最容易被低估的边界：跨 DLL 的所有权并不由 C++ 类型系统保证，而由通知协议和调用约定保证。新平台应把它改造成跨进程序列化值、租约资源句柄和明确的释放证据，避免复用裸指针。

## 窗口组件的三层生命周期

Delphi EDK 的 `elib.pas` 说明窗口组件不是一个简单的 HWND 包装，而是三层对象的桥：语言运行时的 `HUNIT`/`FormID+UnitID`、核心的 MFC `CWnd`、以及 Provider 内部的 VCL `TWinControl`。`ELib_CreateControl/ELib_RegControl` 负责注册和挂载；`SetProp/GetProp` 在 HWND 上保存容器、原窗口过程和重建状态；销毁时必须先分离/删除 CWnd，再释放 VCL 控件。

```text
设计器/运行时 HUNIT(FormID, UnitID)
             │
             ▼
      核心 CWnd / HWND 句柄地图
             │
             ▼
      VCL TWinControl / 容器控件
             │
             ├─ WM_*、键盘、鼠标、焦点、滚轮
             ├─ WU_INIT/WU_SIZE_CHANGED/重建通知
             └─ WM_NCDESTROY → 分离 CWnd → NRS_UNIT_DESTROIED → delete
```

`ELib_ChildNewProc` 将窗口消息转成 `EVENT_NOTIFY2`；`CM_RECREATEWND` 会抓取并恢复子控件，容器通过 MFC 消息反射处理子控件通知。组件契约还要求 `WS_CHILD|WS_CLIPSIBLINGS`、虚析构和 `PostNcDestroy` 清理。跨 DLL 的父子控件关系因此依赖句柄地图和消息反射，不能把“组件树”误解为单一内存对象树。

## `.npk` COM/OCX 描述层

归档中的 `.npk` 与 `.epk` 不是同一种包：`.npk` 是可读的 COM/OCX 安装与设计期描述，头部包含 `@@ Lang/TypeLib/OCX/Interface`，条目由 `##1`/`##0` 包围，记录 TypeLib/OCX 的 GUID、版本、ProgID，以及接口的类型、DISPID、属性、事件和常量索引。它把外部 COM 类型库映射进 IDE 命令/属性/事件面板；`.epk` 则仍是未完全解码的二进制易包。

```text
OCX/TypeLib
  → .npk 描述（GUID/版本/接口/属性/事件）
  → 注册表/控件安装检查
  → IDE 设计器与支持库命令表
  → 运行期 COM/OCX 实例
```

这条链是重要旁路：控件升级必须按 GUID 检测旧包并保留 DISPID 映射，不能只看文件名；新平台应把外部协议适配成显式 Provider 和版本锁。

## 对系统工程平台的可迁移部分

| 易语言概念 | 平台对应物 | 迁移原则 |
| --- | --- | --- |
| `LIB_INFO` | 包声明 + 能力契约 | 元数据先于实现发现，统一版本/GUID/依赖/平台声明 |
| `.fne/.fnl/.fnr/.lib` | 编辑描述、运行提供者、制品层 | 不把编辑面、执行面和构建制品混为一层 |
| `GetNewInf` | 包级公开入口/注册表装载器 | 只允许一个权威注册表，重复注册必须摘要一致 |
| 命令函数指针表 | 唯一能力调用器 | 调用方只传能力 id 和契约参数，不直接触碰实现 |
| DLL 支持库 | 受管提供者 | 原生扩展隔离进程，统一错误、超时、取消和释放证据 |

| `el.exe/epackage.exe` | 制品构建/发布控制面 | 编译、打包、激活、回滚使用不可变制品和指针 |

### 映射到新轻代码平台

```text
易语言工程树/支持库
          │ 迁移为
          ▼
平台项目 IR
  ├─ 项目/模块/页面/流程节点
  ├─ 能力调用和参数契约
  ├─ 事件、资源、状态和权限
  ├─ 编译目标与提供者锁
  └─ 编辑、编译、运行证据
          │
          ├─ 用户 IDE：拖拽/表单/流程编辑
          ├─ Agent：直接生成/修改 IR
          ├─ 编译器：IR → 可验证执行计划
          └─ 网关：执行计划 → 唯一能力调用器 → Provider
```

关键变化是：易语言用函数指针和 DLL 连接能力；新平台用版本化契约、HTTP/进程边界和受管 Provider 连接能力。用户开发和 Agent 开发因此共享同一份 IR、同一套编译校验和同一条运行证据链。

## 静态编译双阶段机制

```text
动态支持库 .fne
  ├─ 完整编辑元数据
  ├─ GetNewInf / 命令表 / 类型表
  ├─ 编译时响应 NL_GET_CMD_FUNC_NAMES
  ├─ 编译时响应 NL_GET_NOTIFY_LIB_FUNC_NAME
  └─ 编译时响应 NL_GET_DEPENDENT_LIBS
          │提供符号名和依赖
          ▼
易语言编译器输出 COFF .obj
          │
          ├─ .lib 静态实现
          ├─ .res 资源
          ├─ 依赖 static_lib/<库名>/ 下的其它库
          └─ resym 重命名私有符号，降低冲突
          ▼
第三方 linker（VC98/GCC/其它配置）
          ▼
静态 EXE/DLL：运行时不再依赖非系统动态库
```

静态库与动态库通常共享一套源代码，用 `__E_STATIC_LIB`/`__COMPILE_FNR` 做编译分支。静态库要隐藏 `LIB_INFO`、编辑定义和 `GetNewInf`，但动态库必须保留完整元数据。`.run` 库还要提供 `xxx_LoadLibrary/xxx_FreeLibrary/xxx_GetProcAddress` 三个 C 符号入口。

## 运行时、窗口组件与资源生命周期

```text
工程加载支持库
  → 创建窗口单元/普通数据类型
  → PFN_CREATE_UNIT / PFN_GET_INTERFACE
  → 属性编辑器读写连续属性数据块
  → 组件事件填充 EVENT_NOTIFY/EVENT_NOTIFY2
  → NRS_EVENT_NOTIFY* 通知运行时
  → 用户事件处理子程序
  → PostNcDestroy / NRS_UNIT_DESTROIED
  → 释放组件、文本、字节集、数组和临时资源
```

窗口组件必须声明固定属性（位置、尺寸、标签、可见、禁用、鼠标指针等），支持设计态和运行态，容器组件还要处理跨组件通知。Delphi 文档特别指出：不同 DLL 中封装的 VCL 控件无法自然形成跨库父子关系，且非核心支持库之间不能互相引用自定义组件/类型，这是旧架构的真实边界。

## 可执行制品的运行加载器

汇编源码揭示了最终制品并不是把全部运行时静态塞进程序，而是保留一个很薄的启动壳：

```text
E-EXE 启动壳
  → 先在 exe 同目录查找 krnln.fnr
  → 找不到则读取 HKCU\Software\FlySky\E\Install\Path
  → 加载安装目录下的 krnln.fne
  → GetProcAddress("GetNewSock")
  → 发送 ITL_RUN_APP
  → 运行时返回真实入口偏移
  → 以入口偏移执行用户程序
```

```text
E-DLL 启动壳
  → 加载 krnln.fnr/fne
  → GetNewSock(ITL_NOTIFY_DLL_EXIT)
  → GetNewSock(ITL_LOAD_DLL_APP2)
  → 接收程序头、退出清理函数和 DLL 载入 id
  → DLL_PROCESS_DETACH 时先执行用户清理
  → 通知核心 DLL 退出
  → FreeLibrary(krnln)
```

```text
EPK 启动器
  → 加载 krnln.fnr/fne
  → GetProcAddress("LoadEPKFromCmdLine")
  → 由核心解释命令行中的 epk
  → 失败时释放核心库并返回错误
```

这说明“编译产物”和“运行核心”是可替换的两个层：程序壳负责定位核心和转交入口，核心负责真正装载代码/模块/易包。新平台应把这个关系显式化为制品引用和运行时协议，不使用固定内存偏移或注册表路径。

演进规律很清楚：核心 ABI 尽量不动，通过通知码、附加文件、插件、配置文件、静态库分支和隐藏旧命令扩展能力。这种“外加扩展、保留旧索引”的策略是其长期兼容性的主要来源，也是新平台应在契约版本和迁移器中明确实现的策略。

## 开放性审计：有意义的旁路与风险

| 旁路 | 观察 | 对架构的意义/风险 |
| --- | --- | --- |
| `.e8` | 可读 INI，合并多个源、覆盖常量、选择目标 | 这是早期的项目配置/条件编译层，值得借鉴；也会造成源与配置分离漂移 |
| `.ec` | 二进制模块，可加密、可引用支持库 | 复用边界清晰，但不可审计、迁移和差异合并困难 |
| `.epk` | 独立易包，可与模块输出类方法 | 类似组件包/SDK 包；格式和装载权限需显式化 |
| `.npk/.run/.ocx` | 外部控件和运行库 | 真实依赖常在工程旁路，安装器必须有完整清单 |
| 编译前插件 | 可改程序信息、常量、输出目标 | 强能力扩展；必须隔离权限和产物写入边界 |
| IDE 公开功能号 | 可插入/删除/导航结构节点 | 说明 IDE 是结构化编辑宿主，不是文本宏工具 |
| 静态链接后动作 | `link.ini` 支持 post-link_action | 构建后命令可执行任意程序，必须受发布门禁约束 |
| 运行时通知 | `PFN_NOTIFY_LIB`、事件通知、延迟释放 | 组件与宿主之间有双向生命周期协议，异常释放风险高 |
| 用户缓存/配置 | `lib/eTools/Data/*.ini`、插件 JSON | IDE 行为依赖用户态状态，重现和迁移需要分离工作区状态 |
| 数字签名/授权 | 支持库和模块可签名/认证，加密狗授权 | 安全状态与功能发现耦合，授权失败可能表现为空支持库 |

### IDE 到底怎样读取和载入：证据化顺序

SDK 文档明确确认：支持库是 DLL，必须导出 `GetNewInf`；`.fne` 带编辑接口信息，`.fnl` 带编辑信息但无运行代码，`.fnr` 不带完整编辑信息而供已编译程序运行；开发者把 `.fne` 复制到 `lib/` 后，需要在“工具 → 支持库配置”中选择加载并重新启动 IDE。下面把明确契约和合理推断分开表达。

```text
阶段 0：启动前路径准备
  e.exe
    ├─ 确定安装根目录、lib/help/plugins/tools 路径
    ├─ 读取 CONFIG.ini、配色、插件和最近工程状态
    └─ 读取“已启用支持库”配置

阶段 1：候选发现
  lib/
    ├─ *.fne/*.fnl → 设计期候选
    ├─ *.fnr       → 运行期候选，不作为 IDE 命令来源
    ├─ *.npk/.run  → 外部控件/运行资源候选
    └─ help/附属 DLL → 说明与依赖索引

阶段 2：打开设计期支持库
  对每个启用的 .fne/.fnl
    ├─ LoadLibrary（或等价动态加载）
    ├─ GetProcAddress("GetNewInf")
    ├─ 调用 GetNewInf() → PLIB_INFO
    └─ 入口不存在/返回空 → 不登记该库

阶段 3：校验 LIB_INFO
  PLIB_INFO
    ├─ 格式号、GUID、主/次/构建版本
    ├─ 最低系统版本、最低核心库版本、OS 位图
    ├─ 无运行代码/无编辑信息/数据库库等状态位
    ├─ 自定义数据类型、元素、属性、事件、构造/析构
    ├─ 命令类别、命令描述数组、命令函数数组
    ├─ 常量数组、AddIn/SuperTemplate 信息
    ├─ szzDependFiles 外部支持文件依赖
    └─ pfnNotify 生命周期和系统通知入口

阶段 4：授权、依赖和冲突
    ├─ GetNewInf 授权通过 → 返回完整编辑信息
    ├─ GetNewInf 授权失败 → 返回空白编辑信息，IDE 隐藏库
    ├─ GUID/格式号重复 → 选择启用版本或阻断
    ├─ 依赖缺失 → 标记不可运行或阻断
    └─ OS/核心版本不满足 → 不加入当前目标能力集合

阶段 5：登记 IDE 能力
    ├─ GUID → 库槽位
    ├─ 库槽位 + 命令索引 → CMD_INFO/提示/参数
    ├─ 库槽位 + 类型索引 → 属性/事件/元素
    ├─ 常量/类别 → 命令面板和编辑器候选
    ├─ help/<库>/ → 帮助链接和说明入口
    └─ LBS_IDE_PLUGIN → IDE 就绪后发送 NL_IDE_READY 等通知

阶段 6：工程绑定
    ├─ 工程读取库 GUID/版本/命令索引
    ├─ GUID 找到库槽位，索引找到当前定义
    ├─ 类型/属性/事件索引绑定到设计器
    └─ 索引越界/契约不兼容 → 显示错误，禁止静默重排

阶段 7：编译和运行
    ├─ 动态目标 → 将 .fnr/.dll/.run/.npk 加入制品清单
    ├─ 静态目标 → 选择 .lib/static_lib 并交给 linker
    ├─ 运行 EXE/DLL → 重新载入运行实现和外部依赖
    └─ 退出/卸载 → NL_FREE_LIB_DATA、NL_UNLOAD_FROM_IDE、延迟释放
```

### IDE 载入后的登记表

```text
宿主库登记表
  ├─ 库槽位 0：系统核心库 krnln
  ├─ 库槽位 1..N：其他支持库 GUID/版本/状态
  └─ 每个库槽位
       ├─ PLIB_INFO 原始元数据
       ├─ 自定义数据类型数组
       ├─ 命令类别/命令数组/函数数组
       ├─ 常量与帮助索引
       ├─ 依赖文件清单
       └─ 通知/释放回调

工程节点
  ├─ 命令引用 = 库槽位 + 稳定命令索引 + 参数编码
  ├─ 类型引用 = 库槽位 + 类型索引
  ├─ 属性引用 = 类型索引 + 属性索引
  ├─ 事件引用 = 类型索引 + 事件索引
  └─ 外部资源引用 = 路径/标识 + 版本/哈希候选
```

`GetNewInf`、`LIB_INFO`、`szzDependFiles`、通知号和“工具 → 支持库配置”的复制/重启步骤是 SDK 明确证据；`e.exe` 内部是否使用线程池、磁盘缓存或具体配置文件名没有源代码，因此这里不把这些实现细节写成确定事实。

### 支持库到底是什么

支持库不是单个 DLL，也不是单纯的命令帮助。一个典型能力至少由以下层组成：

```text
支持库声明/编辑层 (.fne 或 .fnl)
  ├─ 库身份：名称、GUID、版本、作者、OS 位图
  ├─ 命令：参数、返回值、默认值、提示、分类
  ├─ 数据类型：成员、属性、事件、构造/析构/拷贝
  └─ 常量、图标、帮助链接、依赖声明
          │ IDE 装载
          ▼
运行实现 (.fnr 或 .fne 内含运行部分)
  ├─ 命令函数和对象生命周期
  ├─ 核心库/系统 API/第三方 DLL 调用
  └─ 事件通知、延迟释放和资源回收
          │ 编译
          ├─ 动态运行：.fnr/.dll/.run/.ocx/.npk
          └─ 静态运行：.lib + linker + 外部依赖
```

归档中实际出现的支持库制品为：`.fne` 92 个、`.fnr` 7 个、`.npk` 3 个、`.run` 5 个、`lib/` 树内 11 个关联 `.lib`，以及 153 个配套 DLL。`.fne` 数量与“能力数量”不等价：例如 `CnCalendar/`、`eTools/`、`iDraw/`、`ExuiKrnln/`、`OgreDll/` 同时包含支持库、插件、运行库和第三方依赖。

### 核心支持库与普通支持库的区别

`krnln`、`cncnv`、`dp1`、`json` 等靠近运行核心；`iext*`、`vclbase`、`ExuiKrnln` 是 UI/对象模型基础；`eDB`、`internet`、`eMMedia` 等是领域能力；`eTools`、`iDraw`、`CodeStyleEdit` 更像 IDE 扩展。它们都使用支持库 ABI，但权限、生命周期和部署依赖不同，不能在新平台里合并为一个“插件目录”。

### IDE 扩展与用户态内容

`lib/eTools/` 和 `lib/iDraw/` 不是普通业务支持库目录：它们各自有 `Data/`、`Plugin/`、`Set/`、`Config/`、`Theme/`、`Notes/` 等树。`eTools/Plugin/Plugin.ini` 登记了 `p_Basic`、`p_Kernel`、`p_BasicEx`、`p_AutoSaveBack`、`p_CodeView`、`p_EditEx`、`p_IntelligentCompile` 等基础插件，另有搜索增强、整体替换、拖放增强、行号、组件树、颜色选择、模块引用更新等用户插件。由此可见，易语言的“内容”还包括 IDE 用户工作台状态，不能只备份 `.e` 文件。

### 帮助内容不是附件，而是能力目录

`help/` 下的 HTML 按支持库分目录，常见文件族有：


## 自研解析器实测收口

为验证“不是只能看目录和字符串”，本轮用 Python 标准库写了一次性解析器（未落盘为平台代码，避免把研究脚本变成第二个事实源）。解析器逐文件分块读取直到 EOF，并对全部字节计算 SHA-256；随后按文件类型执行魔数识别、编码候选解码、GUID 正则提取、ASCII/UTF-16 字符串段提取、结构标记扫描和跨扩展名计数。逐文件结果曾写入临时 `/tmp/e语言全量解析结果.jsonl`，不是平台事实源。


因此本研究目标可以标记为“架构与公开契约挖掘完成，专有二进制格式逆向未完成且不作为平台前置条件”。后续自研平台应采用公开、版本化、可迁移的 IR；旧 `.e/.ec` 只作为受限导入源，解析失败必须输出字段级阻断项，不能猜测后继续编译。

## 已知未证实项

- `.e/.ec/.epk` 的完整二进制字段、校验和、加密算法和版本兼容表未在 Mac 上动态验证。
- `e.exe` 内部解析器、编译器优化器和调试器实现没有源代码，不能仅凭 SDK 反推出全部行为。
- 归档中的第三方控件、加密狗驱动和用户模块可能有独立协议，不应当当成易语言核心契约。

## 不应照搬的部分

- 不复制 PE32、VC98、DLL 全局状态或裸函数指针作为平台公开接口。
- 不把支持库实现源码、第三方库和业务代码混在同一目录树。
- 不用动态导入、`sys.path` 拼接或第二套网关模拟“自动加载”。
- 不把 `.e` 二进制工程文件当成平台契约；平台契约必须是可校验的结构化 JSON/公开 Python 入口。

## 证据与结论

- `sdk/cpp/docs.txt` 明确描述 `GetNewInf`、`LIB_INFO`、`.fne/.fnl/.fnr/.lib` 四类边界及 OS 能力位图。
- `plugins/source/e_plugin.cpp` 与 `.def` 展示了窄插件导出、数据类型标签和插件内存释放责任。
- `epackage/readme.txt` 与 `epackage/source/*.bat` 展示了运行时打包器和独立汇编/链接构建链。
- `linux/readme.txt` 与 `linux/*.so` 展示同一能力模型的 Linux 运行库变体。
- `sdk/static_docs/index.html` 展示 COFF/`resym`/静态库依赖和 `.run` 装载符号；`sdk/cpp/samples/licHtmlView/HtmlView.cpp` 展示授权与三套制品的实际分支。
- `sdk/delphi/elib.pas`、`sdk/delphi/docs/main.html`、`sdk/delphi/samples/myfne/mypanel.pas` 展示组件创建、属性 blob、事件桥和销毁顺序。
- `lib/eTools/Set/*.json`、`lib/eTools/Data/*.ini` 展示配置驱动的 IDE 扩展面板、用户态状态、自动保存和智能编译旁路。
- `.npk` 文本样例（如 `lib/dm.npk`、`lib/jmail.npk`）展示 COM/OCX 的 GUID、DISPID、属性和事件描述；`.epk`/`.e`/`.ec` 的二进制字段仍未完整解码。

## 继续细拆：从目录到节点、端口和状态

```text

输入 = 文件/配置/能力请求/宿主回调
变换 = 解析/校验/绑定/编译/执行
输出 = 内存对象/索引/制品/诊断/证据
生命周期 = 发现 → 装载 → 使用 → 释放 → 失效
```

```text
  ├─ 回调节点：宿主通知、创建对象、执行命令、释放对象
  ├─ 授权节点：签名/认证/加密狗状态（归档可见，内部算法未证实）
  └─ 变体节点：IDE 编辑态、动态运行态、静态链接态、Linux 运行态
```

```text
支持库发现
  → 文件名候选
  → PE/ELF/文本/静态库分类
  → 入口符号探测（如 GetNewInf）
  → 读取库信息
  → 依赖文件解析
  → 平台/版本/授权过滤
  → 注册能力索引
  → 可供 IDE、编译器和运行时分别查询
```

### 3. 工程对象节点

```text
工程
  ├─ 工程元数据：名称、版本、目标类型、输出目录
  ├─ 库引用：库 GUID、显示名、版本约束、槽位号
  ├─ 模块集合：主程序、.ec、内部模块、外部模块
  ├─ 子程序集合：名称、参数、返回值、可见性、导出标志
  ├─ 数据类型集合：基础类型、库类型、自定义类型、数组/指针
  ├─ 窗体集合：控件树、属性、事件、资源引用
  ├─ 资源集合：图片、声音、数据文件、嵌入二进制
  ├─ 编译设置：动态/静态、调试/发布、字符集、目标平台
  └─ 诊断状态：解析错误、缺库、版本冲突、脏标记、上次构建结果
```

### 4. 命令、类型、属性和事件的最小关系

```text
库槽位
  ├─ 命令索引 → 命令签名 → 参数编码 → Provider 调用入口
  ├─ 类型索引 → 类型布局 → 构造/复制/销毁策略
  ├─ 属性索引 → getter/setter → 属性 blob 编码
  └─ 事件索引 → 事件签名 → 宿主回调 → 用户子程序
```

这里的“索引”是宿主登记关系的架构模型；公开 SDK 能证明入口、能力和回调边界，不能证明 `.e` 文件内部每一个字节的实际编号方式。

### `.ec` 字节级候选布局（样本交叉结果）

对归档中多个 `ecom/*.ec` 和 `samples/易包/使用易包输出类/my_ec20.ec` 做 `xxd` 交叉比较，能确认共同的文件事实，但不能据此宣称完整私有格式：

```text
偏移       样本观察                         当前解释边界
0x00       43 4e 57 54 45 50 52 47          ASCII 魔数 CNWTEPRG，确定
0x08       19 73 11 15                      共同版本/构建候选，字段语义未证实
0x0c       62/63/64 ce xx 0a                类型/版本变体候选，不能直接当版本号
0x10-0x2f  重复的 19 73、00 02 等序列       固定头/编码表候选
0x30       01 00 00 00 等                   标志或表计数候选
0x3c       ef/ee/e9 03 xx 00                模块类别/计数候选
0x40       3c 00 00 00                      固定头长度候选
0x60-...   多个小端整数                      索引/块计数候选
```

```text
读取 .ec
  → 读取至少 0x40 字节，校验 CNWTEPRG
  → 以小端整数读取候选字段，但全部标记“候选”
  → 从 0x40 之后寻找单调、非重叠的 offset/length 对
  → 每个候选块做边界、重叠、整数溢出和摘要校验
  → 只有与同版本样本、公开导出接口或行为样本同时吻合时
       才提升为语义字段
  → 否则保留 RawBlock，不生成可执行模块节点
```

这一步的价值是能写出安全解析器，而不是凭几个整数“解密”模块。解析器必须支持未知版本、截断文件和未来字段，并输出偏移证据供 Windows 行为样本继续验证。

### `.epk` 目录候选与加载前校验

两个样本的头部都在 `0x24` 处出现 `93 00 00 00 01 00 00 00 03 00 00 00`，随后是多组小端整数和 `krnln` 字符串。一个样本以 `WJ` 开头，另一个开头为零，因此不能把 `WJ` 当作所有 EPK 的必需魔数。

两个真实样本（`myepk6.epk` 1223 字节、`my_epk20.epk` 770 字节）的候选字段可进一步记录为：

```text
0x24 = 0x93       元数据段指针候选
0x28 = 1          格式版本候选
0x2c = 3          条目数候选
0x34 = 0x00010006 标志候选
0x3c = 0x3f6/0x226 载荷或文件尾候选
0x40-0x54         多组偏移/长度候选
0x58              krnln、摘要样式串和说明文本
后续记录          const、form、help、code、export
```

```text
EPK 目录候选
  ├─ 核心运行库元数据：krnln + 摘要
  ├─ const：常量/启动参数
  ├─ form：窗体/组件资源
  ├─ help：帮助说明
  ├─ code：易代码
  └─ export：类/函数导出
```

这些是跨样本稳定的结构候选，不是完整私有格式规范；解析器必须保留原始段、偏移和长度，未经边界与摘要验证不得提升为可执行节点。

```text
EPK 读取门
  → 文件大小/摘要/最小头长度检查
  → 读取 0x24 附近的目录版本/条目数候选
  → 对每个 offset + length 做文件内边界检查
  → 检查条目是否重叠、是否指向 krnln/运行库/用户载荷
  → 校验载荷摘要或失败即阻断
  → 解析 EXE/DLL 包类型
  → 仅在入口和依赖都成立时交给加载器
```

```text
EPK 载荷
  ├─ 核心运行库条目：krnln.fnr / krnln.fne
  ├─ 运行库摘要：样本中可见十六进制文本串
  ├─ 用户易代码/类/资源条目
  └─ 入口/偏移候选
```

`epackage/source/*.asm` 直接确认加载器的回退顺序与一次初始化/退出回调；`0x24` 后每个字段的完整语义仍需更多已知输入输出样本，不应在新平台中兼容这些私有偏移，而应设计公开的 manifest + 段目录格式。

```text
外部制品
```

## 自研解析器：从字节候选到可迁移 IR

当前解析器已经能完成全量读取、摘要、魔数、字符串、GUID 和结构标记索引；要继续“拆到最细”，下一步应固定为分层解析，而不是继续增加正则关键词。

```text
第 0 层：文件事实
  路径、大小、摘要、mtime、读取错误、文件类型
      ↓
第 1 层：容器事实
  魔数、版本候选、段边界候选、压缩/加密候选
      ↓
第 2 层：符号事实
  GUID、库名、入口、导出名、依赖名、字符串段
      ↓
第 3 层：结构候选
  字段、代码、窗体、变量、运行时、帮助、常量、导出块
      ↓
第 4 层：语义候选
  工程、模块、子程序、类型、命令、属性、事件、资源
      ↓
第 5 层：可迁移 IR
  节点 id、节点类型、输入端口、输出端口、依赖、权限、诊断
      ↓
第 6 层：验证
  与公开 SDK、帮助、样例和原版行为样本交叉验证
```

每个 IR 节点至少保留以下字段，解析失败不得丢失原始证据：

```text
节点
  ├─ id / 类型 / 父节点 / 顺序
  ├─ 原始文件 / 偏移候选 / 长度候选 / 摘要
  ├─ 输入端口 / 输出端口 / 依赖节点
  ├─ 公开名称 / 内部名称候选 / 版本约束
  ├─ 能力 id / 参数 schema / 返回 schema
  ├─ 权限、资源预算、超时、可取消性
  ├─ 证据来源、可信级别、解析器版本
  └─ 错误码、阻断原因、人工复核状态
```

### 解析器的拒绝规则

```text
无法确定边界       → 保留候选范围，不生成可执行节点
无法确定类型       → 生成未知节点，禁止编译
依赖 GUID 无法匹配 → 生成缺失依赖诊断，禁止静默替换
属性/事件签名冲突  → 生成契约冲突，禁止继续绑定
摘要不一致         → 生成制品损坏诊断，禁止装载
只有字符串无结构   → 仅进入搜索索引，不进入 AST/IR
```

## 对新 Agent 轻代码底座的直接映射

```text
易语言对象             → 新平台对象
工程/模块/.ec          → 版本化项目 IR / 模块包
支持库槽位             → 能力注册表中的能力版本
命令/类型/属性/事件     → 可搜索、可校验的能力契约
GetNewInf/LIB_INFO      → Provider 清单与健康检查
窗体设计器             → UI/Agent 资源图与事件图
智能编译               → 增量计划编译 + 影响范围诊断
.fnr/.run/.lib          → 动态、受限进程、静态或远程 Provider 制品
eTools/iDraw 用户态     → IDE 工作区状态与可迁移设置
e.exe 消息循环          → 前端宿主 + 事件总线
加密狗/授权             → 独立授权能力，不参与基础能力发现
```

Agent 入口应与普通用户入口共享同一 IR 和能力目录：

```text
普通用户拖拽/填写 ─┐
                   ├→ 结构化 IR → 校验 → 执行计划 → 统一网关 → 证据
Agent 生成/修改 ───┘
```

因此底座最小闭环不是“生成代码”，而是：

```text
能力搜索
  → 取得公开契约
  → 生成或编辑 IR
  → 锁定版本、权限和资源预算
  → 编译成执行计划
  → 申请执行租约
  → 网关调用 Provider
  → 记录统一结果和证据
  → 释放资源并关闭租约
```

## 本轮边界

本轮已把研究从“目录清单”继续下钻到节点、端口、状态、载入门和解析拒绝规则；其中 SDK、文件样本和公开文本直接支持的内容仍是证据，`.e/.ec/.epk` 的具体字节布局、e.exe 私有线程/缓存和授权内部协议仍是架构重建或未证实项。要把这些未证实项再下钻，必须增加原版在 Windows 上的行为样本（空工程、加库、加控件、编译、运行、卸载各一组），而不是靠猜测填表。

```text

  ├─当前项目/当前模块/当前节点
  ├─文档版本与脏标记
  ├─选区、光标、折叠和断点
  ├─库槽位与能力目录版本
  ├─当前编译上下文 id
  ├─运行会话 id、进程 id、取消令牌
  └─诊断集合与证据链接
```

### F5 的 UI 状态机

```text
空闲
  → 保存脏文档
  → 生成编译请求
  → 编译中（按钮变为停止，输出面板增量刷新）
      ├─失败 → 错误列表定位源节点 → 回到空闲
      └─成功 → 启动/复用运行会话
                    ├─运行中：F5 变为重启/停止
                    ├─断点命中：切换调试布局
                    ├─运行错误：定位源位置/调用栈
                    └─退出：收集日志和耗时 → 回到空闲
```

## 为什么 F5 很快：证据、重建与实现建议

### 已有公开证据

静态编译手册明确描述：易语言编译器先生成“易格式编译数据”，再交给目标平台的封装/载入工具；静态路线才继续生成 COFF OBJ 并交给第三方链接器。SDK 还区分编辑态 `.fne`、运行态 `.fnr` 和静态链接 `.lib`，说明编辑信息和完整链接制品不是每次运行都必须重新生成。

### 高可信的 F5 快速路径重建

```text
F5
  → [1] 保存当前脏文档
  → [2] 计算受影响节点（当前模块/依赖闭包/资源变更）
  → [3] 复用已注册支持库和命令/类型表
  → [4] 复用未变化模块的解析结果、类型结果和中间表示
  → [5] 只编译变化部分
  → [6] 生成易格式编译数据/调试位置映射
  → [7] 复用核心运行库和外部依赖
  → [8] 创建新进程或重启轻量运行壳
  → [9] 注入/装载本次编译数据
  → [10] 启动入口，回传日志和调试状态
```

这条路径解释了为什么编辑一个小子程序后 F5 仍然很快：它避免了静态链接器、完整资源重打包、所有支持库重新发现和 IDE 全进程重启。是否存在真正的函数级热替换、常驻编译器进程或内存映射缓存，公开资料没有直接证明，不能写死为易语言事实。

### 与完整构建的差异

```text
F5 预览/调试                         正式构建/发布
  ├─优先动态运行库 .fnr/.dll/.run       ├─可能选择静态 .lib
  ├─允许临时输出目录和调试映射           ├─完整资源、版本、签名和安装清单
  ├─按变化范围编译                       ├─全量依赖闭包和链接
  ├─启动本地运行壳                       ├─生成最终 EXE/DLL/EPK/安装包
  └─退出即可丢弃                         └─制品不可变、可发布、可回滚
```

### 可测量的速度来源

```text
总耗时 = 保存 + 解析/绑定 + 代码生成 + 封装 + 进程启动 + 运行库装载

优化目标
  ├─保存：增量写入、后台落盘
  ├─解析：模块/库索引缓存，按摘要失效
  ├─绑定：命令签名和类型表缓存
  ├─代码生成：按模块/函数缓存 IR 和调试映射
  ├─封装：预建运行壳，替换数据段而非重建全部文件
  ├─进程启动：短生命周期运行子进程，或保留受控宿主
  └─装载：依赖摘要命中时复用已准备的 Provider 环境
```

### 新平台应采用的 F5 设计

```text
编辑器保存
  → 内容寻址摘要
  → 依赖图计算受影响节点
  → 增量编译缓存查询
      ├─命中：取不可变中间制品
      └─未命中：只编译失效节点
  → 拼装执行计划
  → 启动隔离运行会话
  → 统一网关执行
  → 返回日志、断点事件、资源统计和证据
```

缓存必须以“源码摘要 + 能力契约版本 + Provider 版本 + 编译选项 + 目标平台 + 编译器版本”为键；不能只按文件名或时间戳判断有效。运行会话必须有取消、超时、资源上限和确定性释放，不能为了速度把第三方库和用户代码留在 IDE 主进程。

### 如何验证易语言自身的 F5 机制

如果以后拿到 Windows 原版环境，可以用六组最小实验区分上述假设：

```text
A. 空工程连续 F5       → 测启动壳/运行库是否复用
B. 只改注释            → 测是否跳过代码生成
C. 只改一个子程序      → 测模块/函数级增量范围
D. 只改窗体属性        → 测资源和初始化序列增量范围
E. 增删一个支持库      → 测能力目录与依赖是否全量重建
F. F5 与正式编译对比    → 测动态路径和静态链接路径差异
```

每组记录文件时间、临时制品、子进程树、DLL 装载、CPU/磁盘耗时和输出摘要，才能把“高可信重建”升级为原版行为证据。

## 黑盒过程架构：不破解也能确定到什么程度

“逆向”不等于破解。对工程架构最有价值的是观察公开输入、状态变化、制品和回调边界；不需要解密授权、修改保护或还原私有算法。当前归档已经包含足够的源码和接口，可以把下面这些层确定下来：

```text
可直接确定                         仍需黑盒实验确认
  SDK 的编辑/运行/静态三态边界         e.exe 内部线程调度
  支持库入口、通知和回调               具体增量失效算法
  编译前插件输入/输出                  是否常驻编译器进程
  编译器可修改的程序信息/常量          是否函数级热替换
  e_debug 临时制品目录                 内存映射/磁盘缓存细节
  .e8 多源合并规则                     F5 每一步的实际耗时占比
  调试/运行功能组                      私有错误恢复和重启策略
```

### 已从源码和版本说明确定的事实

```text
版本说明 readme.txt
  ├─ 调试临时文件固定进入系统临时目录/e_debug
  ├─ 修复调试结束后 DLL 未释放的问题
  ├─ 增加“以指定类型编译/运行”菜单
  ├─ 增加编译前插件和外部编译插件接口
  ├─ .e8 是 Ansi INI，可指定多个 source 并合并打开
  ├─ 编译时可显示易模块中的错误位置
  ├─ 5.0 引入第三方链接器静态编译
  └─ 4.13 更新说明明确写出“大幅提高编译速度”
```

对应原始证据：`readme.txt` 的 111、114、127、133-148、301-307、390-396 行（按 GB18030 解码后的版本说明计数）。这已经证明 F5 不是一个不可拆的黑盒：它至少有独立的调试临时产物、运行类型选择、支持库装载和编译前扩展阶段。

### 编译前插件的真实契约

`samples/编译前插件/src/CompilerPluginsPublic.h` 和 `CompilerPlugins.cpp` 不是演示性质的空壳，而是完整的输入/输出边界：

```text
编译器
  → LoadLibrary 编译插件
  → 查找 CompileProcessor
  → 传入 COMPILE_PROCESSOR_INFO
      ├─ 发布/调试标志
      ├─ 易包标志
      ├─ 源文件名/纯文件名
      ├─ 系统版本、系统类型、语言版本、应用类型
      └─ 程序信息结构
  → 插件通过回调修改
      ├─ 程序名称/作者/版本/保存路径
      ├─ 数值、日期、逻辑、文本和字节集常量
      └─ 失败返回 FALSE，中止该编译前处理
  → 编译器继续生成目标
```

这说明编译器在真正生成目标前，持有一个可被扩展处理的“编译上下文”，而不是按键后直接把编辑器文本传给链接器。新平台应把这个上下文显式建模为不可变输入快照和可审计变换列表。

### IDE 插件的真实功能分组

`sdk/cpp/elib/PublicIDEFunctions.h` 将 IDE 公共操作按功能号分组，其中明确存在：

```text
FNST_EDIT      编辑和文档修改
FNST_DOCUMENT  文件/文档操作
FNST_DEBUG     调试操作
FNST_RUN       运行操作
FNST_ADDIN     IDE 插件操作
```

`sdk/cpp/elib/lib2.h` 同时定义 `PT_EDIT_VER`、`PT_DEBUG_RUN_VER`、`PT_RELEASE_RUN_VER`，以及 `NL_IDE_READY`、`NL_RIGHT_POPUP_MENU_SHOW`、`NL_FREE_LIB_DATA`。这组接口把 IDE、支持库和运行版本拆成了明确的生命周期协议：编辑态需要完整命令/属性/事件描述，调试运行态保留运行所需类型信息，发布态只保留运行所需数据。

### F5 的确定版流程模型

结合上述源码，F5 至少可以确定为以下流程，而不再只是猜测：

```text
F5
  → 保存或读取当前源工程
  → 选择“调试运行”目标类型
  → 创建 e_debug 临时目录中的调试产物
  → 执行编译前插件链
  → 生成易格式编译数据/调试信息
  → 准备调试运行态支持库（.fnr 或动态依赖）
  → 启动调试程序
  → 运行态加载支持库和外部 DLL
  → 错误位置映射回 .e/.ec 源节点
  → 退出时释放调试 DLL 和临时文件
```

这里“生成易格式编译数据”由静态编译技术手册明确支持；“F5 一定复用未变化函数的机器码”目前没有源码证据，不能继续保留为确定事实。更准确的结论是：它通过专门的调试产物、动态运行态和不走完整静态链接的路径降低了启动成本；是否还有模块/函数级增量缓存，需要运行实验或 e.exe 私有符号才能确认。

### 支持库为什么能保持稳定

稳定性主要来自契约分层和兼容规则，而不是支持库内部没有变化：

```text
支持库源码
  ├─ 编辑接口：命令/类型/属性/事件/帮助
  ├─ 运行接口：命令实现、对象布局、生命周期
  ├─ 静态接口：符号名、通知项、依赖静态库
  └─ 版本/平台/授权声明
          ↓
宿主按 GUID、版本、OS 能力和通知协议装载
          ↓
旧工程继续使用旧索引和旧签名
新能力只能追加或通过兼容映射引入
```

版本说明还明确记录：新版支持库可被旧版 IDE/程序使用，旧版支持库也可被新版使用，只是旧版不支持静态编译；同时提醒全局命令表插入/删除会破坏历史索引。因此新平台必须禁止原地重排能力索引，采用稳定能力 id、版本化契约和显式迁移表。

### 对我们平台的落地结论

```text
IDE UI
  → 统一工作区状态 + 结构化 IR + 可观察编译状态
编译器
  → 编译上下文快照 + 编译前变换插件 + 目标类型选择
F5
  → 调试专用临时制品 + 动态 Provider + 源位置映射
正式发布
  → 完整依赖闭包 + 静态/远程制品 + 签名和不可变发布
支持库
  → 编辑契约、运行契约、静态契约三套明确边界
兼容
  → 稳定能力 id，不删除/重排旧索引，只追加版本和迁移
```

因此，黑盒部分可以继续做，但下一步应该是“行为观测矩阵”，不是破解：监控 F5 前后 `e_debug` 文件、子进程、DLL 装载、文件时间和输出日志，用 A-F 六组实验把增量范围和复用策略测出来。源码已经把架构边界揭示得足够清楚，剩下的黑盒主要是性能实现细节。

## e.exe 静态证据：F5 不是猜出来的

本轮对归档中的 `e.exe` 做了 PE 导入表、字符串和文件摘要复核。样本为 PE32 GUI Intel 80386，SHA-256：

```text
368cbbd323d2c5bc00f0c072b116333f75339fc0742e238d3e5e6ff17abe1409
```

### 调试器进程控制证据

`e.exe` 从 `KERNEL32.dll` 导入了以下与调试器直接相关的 API：

```text
创建/等待
  CreateProcessA
  CreateThread
  WaitForDebugEvent
  ContinueDebugEvent

进程内存与线程控制
  ReadProcessMemory
  WriteProcessMemory
  GetThreadContext
  SetThreadContext
  SuspendThread
  ResumeThread

文件映射与临时制品
  GetTempPathA
  GetTempFileNameA
  OpenFileMappingA
  MapViewOfFile
  VirtualAlloc
  VirtualFree

动态依赖
  LoadLibraryA
  FreeLibrary

调试结束
  DebugActiveProcessStop（字符串引用）
```

这组导入足以确定：F5 至少是“IDE 创建/控制被调试进程 + 调试事件循环 + 读写被调试进程内存/线程上下文 + 动态装载运行依赖”的本地调试架构，而不是简单执行一个已经存在的 EXE。`WaitForDebugEvent` 与 `ContinueDebugEvent` 还表明 IDE 具备调试事件泵；`Get/SetThreadContext`、`Read/WriteProcessMemory` 表明断点、单步、变量/栈读取等能力有进程级实现基础。

### 编译/运行边界证据

`e.exe` 的 ASCII 字符串包含：

```text
RunPrg
Can't locate "RunPrg" function!
CompileProcessor
__HIDDEN_TEMP_MOD__
e_debug
krnln.fne / krnln.fnr
ocx.run / com.run / odbcdb.run / mp3.run
(*.fne;*.fnr) / *.epk

```

这些字符串与 SDK 和样例源码互相印证：IDE 有独立的运行入口解析、编译前处理插件、隐藏临时模块、调试目录、动态支持库以及 EPK/链接器分支。它们不能证明某个具体字符串对应的私有函数实现，但足以证明 F5 的职责边界和制品类别。

### 因此 F5 的更准确内部图

```text
IDE 主进程
  ├─ 工程/编辑状态
  ├─ 编译上下文构造
  ├─ CompileProcessor 插件链
  ├─ 临时文件和共享映射准备
  ├─ CreateProcessA 启动被调试程序
  ├─ WaitForDebugEvent 事件泵
  ├─ Read/WriteProcessMemory 变量/断点/调试数据通道
  ├─ Get/SetThreadContext 单步/寄存器/断点控制
  ├─ LoadLibraryA 装载 .fnr/.dll/.run
  └─ FreeLibrary/DebugActiveProcessStop 结束清理
          │
          ▼
被调试程序
  ├─ 易格式编译数据/调试映射
  ├─ krnln.fnr 和其它运行支持库
  ├─ 用户 DLL/OCX/COM 依赖
  └─ 源位置、异常和退出状态回传
```

### 关于“快”的证据边界修正

现在可以确定 F5 快的结构性原因：它使用独立调试运行态和临时制品，绕过正式发布的静态链接/安装流程；同时 IDE 保持支持库目录、运行依赖和调试控制面在本地进程内。仍不能仅凭导入表确定的，是“是否复用上次编译的中间结果”和“是否函数级增量编译”。这两个问题必须通过对 `e_debug` 文件的两次 F5 差异、文件时间、子进程创建次数和 CPU/磁盘采样来确认。

## 支持库稳定态的源码级结论

支持库的稳定性并不是“十年不改代码”，而是把变化隔离在版本化契约后面：

```text
编辑态 .fne
  ├─ LIB_INFO/GUID/版本/OS 能力
  ├─ 命令、类型、属性、事件、帮助
  └─ IDE 通知和设计器回调

调试运行态 .fnr/.dll
  ├─ 运行命令实现
  ├─ 最小数据类型信息
  ├─ 运行对象/窗口生命周期
  └─ 动态依赖和释放

静态态 .lib
  ├─ 命令符号名
  ├─ 静态库依赖列表
  ├─ PFN_NOTIFY_LIB 通知处理
  ├─ 资源名前缀和符号冲突规避
  └─ 链接后独立运行
```

SDK `lib2.h` 中的 `__COMPILE_FNR`、`__E_STATIC_LIB` 分支和静态编译手册对动态/静态版本的说明，直接支持这三层分工。其稳定策略可以迁移为：

```text
能力 id 永不复用
  → 新命令只追加，不插入旧索引中间
  → 契约版本单调递增
  → 旧版本保留兼容适配器
  → 编辑态、调试态、发布态分别声明最小能力
  → Provider 依赖和资源释放成为装载契约的一部分
```

这比单纯把所有能力塞进一个插件 DLL 更稳定，也更适合 Agent 生成和用户编辑共用同一底座。

## 函数级静态重建结果

为了避免“只看导入表”的过度推断，本轮使用 Rizin 对 `e.exe` 做了交叉引用和函数反汇编。以下地址是该样本的虚拟地址，属于当前样本证据，不是公开 ABI：

```text
0x004040b0  被调试进程创建函数
  ├─ 初始化 STARTUPINFO 和 PROCESS_INFORMATION
  ├─ 组装命令行/启动参数
  ├─ 调用 CreateProcessA
  ├─ 保存进程/线程句柄
  └─ 失败时关闭句柄并返回错误

0x0042f228  调试事件处理函数
  ├─ WaitForDebugEvent
  ├─ 按事件类型分支（可见比较值 2、3、4、5、6、8）
  ├─ GetThreadContext
  ├─ ReadProcessMemory
  ├─ 处理断点/异常/线程或进程状态
  ├─ ContinueDebugEvent 或关闭句柄
  └─ 持续循环直到退出/停止调试

0x00437bc0  编译前插件装载函数
  ├─ 遍历 plugins\\ 候选目录
  ├─ LoadLibraryA
  ├─ GetProcAddress("CompileProcessor")
  ├─ 传入编译上下文
  ├─ 处理插件成功/失败返回
  └─ FreeLibrary
```

因此可以把 F5 内部结构写成函数级流程：

```text
编译/准备阶段
  → 0x00437bc0 扫描并执行 CompileProcessor 链
  → 生成调试目标和临时文件
  → 0x004040b0 创建被调试进程
  → 0x0042f228 进入调试事件循环
  → 断点/异常/线程事件读取进程状态
  → 继续运行、停止或退出
  → 释放 DLL、句柄和临时制品
```

这个结果已经超过“架构推断”，但仍然保持边界：函数地址、局部变量布局和事件分支是样本级逆向证据；跨版本稳定的公开契约仍只能使用 SDK 中的 `CompileProcessor`、`NL_*`、`LIB_INFO` 等定义。

## `.e8` 是项目控制面，不只是配置文件

样例 `samples/e8/test1.e8`、`test2.e8` 和 `ManyFiles/TestManyFiles.e8` 是可读的 Ansi INI，但它们实际承担了项目装配入口的职责：

```text
.e8
  ├─ [settings]
  │   ├─ source = .e / .ec / .txt（可重复）
  │   └─ 相对路径以 .e8 所在目录为基准
  ├─ [AppSettings]
  │   ├─ type：WinEXE / WinConsoleEXE / WinDLL / WinECom
  │   │        LinuxConsoleELF / LinuxECom
  │   ├─ 程序名称、说明、作者、版本、版权
  │   ├─ plugins、EnableExportPublicMethod、icon
  │   └─ OutputFileName
  └─ [user_consts]
      ├─ 打开时创建不存在的常量
      ├─ 存在时覆盖常量值
      └─ 常量条件可在编译期裁剪代码
```

多源 `.e8` 的真实合并规则也由样例注释明确给出：

```text
读取 source[1..n]
  → 解析每个 .e/.ec/.txt
  → 若包含 .ec，先清除所有 .e 中原有模块引用
  → 合并代码和声明
  → 自动滤除重复的“启动窗口/启动子程序”
  → 应用 AppSettings 和 user_consts
  → 建立临时工程上下文
  → 进入 IDE 编辑或编译流程
```

这说明易语言已经把“源代码”和“构建控制面”分离：`.e/.ec` 是内容，`.e8` 是可复现装配描述。新平台应把它升级为显式 `项目清单.json`，将源输入、目标类型、能力版本、编译插件、常量覆盖和输出制品全部纳入摘要。

## 安装器和易包：生产者/消费者成对演进

### EPK 封装链

归档 `epackage/readme.txt` 和 `epackage/source/epackage.asm`、`dll_pkg.asm`、`el.asm` 明确了三段职责：

```text
易语言编译输出
  → epackage.exe：封装 EXE 类型易语言执行代码
  → dll_pkg.dll：封装 DLL 类型易语言执行代码
  → .epk：易包载荷/标记点/依赖
  → el.exe：读取 .epk 并启动
```

EPK 的封装格式允许修改 `source` 目录中的源码来建立自定义封装格式，但必须保持功能和标记点数据一致。这意味着标记点/载荷协议是“封装器和启动器共同维护”的内部契约，不能只改一端。

### 安装包链

```text
mksetup.e / mksetup.exe
  ├─ 组织文件列表
  ├─ 选择动态或静态安装模板
  ├─ 处理模板和预览
  ├─ 选择 XP 风格依赖
  └─ 生成安装包

setup.tpl / setup.exe / setup_jt.exe
  ├─ 解析安装包
  ├─ 写入文件和快捷方式
  ├─ 登记控制面板卸载
  ├─ 只删除安装时生成的文件
  └─ 处理 xplib.fne 的去重

uninstall.tpl
  └─ 生成卸载程序
```

`setup/readme.txt` 明确要求：如果 `mksetup.e` 增加安装包字段，必须同步修改 `setup.e` 的解析逻辑；修改源码后还要重新编译并覆盖 setup 目录中的 EXE，同时保留最新 `setup.e` 供系统分析依赖。这是一个非常重要的工程规律：

```text
安装包格式生产者
  ↔ 安装包格式消费者
  ↔ 模板/运行壳
  ↔ 依赖清单和卸载清单
```

新平台的发布系统也必须把制品格式、安装器、卸载器和模板放在同一个版本契约下，禁止只升级打包器而不升级解析器。

## 支持库 ABI 深挖：稳定态到底稳定在哪里

### 制品状态不是文件后缀，而是能力裁剪

SDK 文档明确区分以下制品：

```text
.fne
  = 编辑接口 + 运行实现
  = IDE 可载入，也可作为动态运行库

.fnl
  = 编辑接口
  = 只用于 IDE/编译阶段，不提供运行实现

.fnr
  = 运行实现 + 最小运行类型信息
  = 程序运行阶段使用，不携带完整编辑信息

.lib
  = 静态链接实现
  = 不包含命令/属性/事件编辑描述，由动态库在链接期间提供辅助信息
```

对应源码条件为 `__COMPILE_FNR` 和 `__E_STATIC_LIB`：

```text
完整源码
  ├─ __COMPILE_FNR → 去掉命令/事件/属性编辑描述，只保留运行类型信息
  ├─ __E_STATIC_LIB → 去掉 GetNewInf、编辑表和 DLL 全局状态
  └─ 默认 → 生成 .fne 编辑+运行版本
```

这解释了稳定性：同一能力被拆成不同部署阶段的最小制品，不要求每个运行程序携带 IDE 元数据，也不要求 IDE 直接执行静态库。

### `LIB_INFO` 是支持库的根契约

```text
GetNewInf()
  → LIB_INFO
      ├─ LIB_FORMAT_VER
      ├─ GUID（稳定身份）
      ├─ 主/次/构建版本
      ├─ 最低系统版本、最低核心支持库版本
      ├─ 状态位：可运行、无编辑信息、数据库、OS、IDE 插件、LIB_INFO2
      ├─ 自定义数据类型表
      ├─ 命令/方法定义表与实现函数指针
      ├─ 常量表、插件函数表
      ├─ PFN_NOTIFY_LIB（不可为空）
      └─ 依赖文件串 szzDependFiles
```

宿主稳定识别支持库依赖 GUID 和格式版本；显示名、文件名和路径都不能作为唯一身份。新平台应等价实现：

```text
ProviderManifest
  ├─ 能力 id（不可复用）
  ├─ 契约版本
  ├─ 最低运行核心版本
  ├─ 目标平台/架构
  ├─ 编辑能力、调试能力、发布能力
  ├─ 依赖制品和资源
  ├─ 生命周期通知
  └─ 统一结果/错误/释放协议
```

### 命令 ABI 不是只有函数指针

`CMD_INFO` 同时描述人类可读语义和编译器生成代码所需信息：

```text
CMD_INFO
  ├─ 中文名/英文名/解释
  ├─ 全局命令或对象方法
  ├─ 隐藏、错误、Release 禁用、追加参数、数组返回标志
  ├─ 对象构造/复制/析构标志
  ├─ OS 能力掩码
  ├─ 返回 DATA_TYPE
  └─ 参数 ARG_INFO[]
```

对象构造、复制、析构命令每种类型最多一个，编译器会据此自动生成生命周期调用。这是轻代码平台必须保留的语义：节点不仅要有“执行函数”，还要声明复制、销毁、资源所有权和平台限制。

### 参数和内存所有权是 ABI 的核心

```text
命令参数通道
  ├─ 立即数
  ├─ 单变量
  ├─ 整数组
  └─ 命令返回值

参数约束
  ├─ AS_RECEIVE_VAR
  ├─ AS_RECEIVE_ARRAY
  ├─ AS_RECEIVE_ALL_TYPE
  └─ AS_RECEIVE_VAR_OR_OTHER
```

`MDATA_INF` 的 union 覆盖整数、浮点、日期、文本、字节集、子程序、HUNIT、复合对象和数组，并规定了写回方向：文本/字节集输入只读；需要返回或写回时必须使用宿主分配器；旧值释放要走 `NRS_MFREE`，新值分配走 `NRS_MALLOC`，数组走 `NRS_FREE_ARY`。返回 `_SDT_ALL` 时不能携带宿主无法安全自动释放的复合/数组。

```text
Provider 返回文本/字节集
  → 使用宿主分配器
  → 返回统一数据描述
  → 宿主读取
  → 宿主通过 NRS_MFREE 回收

Provider 返回数组
  → 写入元素数和元素区
  → 宿主按类型释放
  → NRS_FREE_ARY 完成整体回收
```

这类所有权规则比函数名更重要；新平台不应跨进程传裸指针，而应把它转换为序列化值或租约资源句柄。

### 窗口对象、属性和事件 ABI

```text
LIB_DATA_TYPE_INFO
  ├─ 普通数据类型
  ├─ 窗口类型
  ├─ 容器/TAB 类型
  ├─ 功能提供者类型
  ├─ 不可聚焦/枚举/消息过滤标志
  ├─ OS 能力掩码
  ├─ 属性表
  ├─ 事件表
  ├─ 元素成员表
  └─ pfnGetInterface
```

Delphi EDK 又把窗口对象拆成可观察生命周期：

```text
创建控件
  → ELib_CreateControl 生成 HUNIT
  → HUNIT 与 HWND/WinControl 建立映射
  → SetProp 保存 PWndPropData
  → 属性读写通过 TPropReader/TPropWriter 二进制流
  → VCL 鼠标/键盘/焦点消息转 EVENT_NOTIFY2
  → NotifySys 转发到易语言事件
  → 销毁时 DETACH → DELETE → 释放属性和对象数据
```

属性流是带长度、位置和内存流边界的序列化协议；事件参数通过 `EVENT_ARG_INFO2` 描述类型和 `EAS_BY_REF` 写回语义。新平台可以直接借鉴为：

```text
组件 = 类型契约 + 属性 schema + 事件 schema + 状态序列化 + 资源句柄
```

### 生命周期通知表

```text
NL_FREE_LIB_DATA       → 释放库级资源
NL_GET_CMD_FUNC_NAMES  → 静态链接查询命令实现符号
NL_GET_NOTIFY_LIB_FUNC_NAME → 查询通知函数符号
NL_GET_DEPENDENT_LIBS  → 查询静态库依赖
NL_UNLOAD_FROM_IDE     → IDE 卸载，可返回延迟释放
NL_IDE_READY           → IDE 已就绪
NL_RIGHT_POPUP_MENU_SHOW → 右键菜单扩展点
NL_ADD_NEW_ELEMENT     → 动态增加 IDE 元素
```

这是一条完整生命周期协议，而不是若干散落回调。稳定态的真正边界是：身份、版本、能力掩码、所有权、释放通知和兼容索引都显式化。

## 授权门控：元数据可见性发生在库装载前

SDK 样例 `samples/licHtmlView/HtmlView.cpp` 显示，支持库的 `GetNewInf` 会读取模块目录下的授权文件（样例为 `HtmlView.elic`），再决定返回哪一份 `LIB_INFO2`：

```text
IDE/编译器 LoadLibrary 支持库
  → 调用 GetNewInf
  → 支持库读取本地授权文件
  ├─ 授权用户名非空
  │    → 返回完整命令表、类型表、编辑信息和运行函数
  └─ 未授权
       → 返回空白 LIB_INFO2
       → 填硬件码/授权状态
       → 宿主看不到可编辑能力
```

FNR 版本还会保留运行类型数组，但将命令类别和命令表置空，并设置 `LBS_NO_EDIT_INFO`。因此“能运行”和“能被 IDE 编辑”是两个独立权限面；这是架构观察，不是破解建议。新平台应将授权/许可证解析放在 ProviderManifest 装载阶段，返回明确的 `编辑能力/调试能力/发布能力`，不让编辑器在运行时猜测权限。

## 编译与 F5 运行链

### 动态运行链

```text
点击 F5
  → 保存当前工程/触发自动保存门控
  → 读取工程配置、模块引用和支持库元数据
  → 生成编译器中间数据
  → 解析命令/属性/事件为内部调用描述
  → 编译为临时运行制品
  → 装载 krnln.fnr 或 krnln.fne
  → 装载所需 .fne/.fnr 支持库
  → 建立数据类型、命令函数和通知回调表
  → 启动进程/调试宿主
  → 失败时保留错误定位和中间产物（按 link.ini 配置）
```

### 静态发布链

```text
源码/中间数据
  → 编译器生成 COFF OBJ
  → 向动态支持库查询命令函数名、通知函数名和依赖
  → 第三方 linker + 各支持库 xxx_static.lib/.res
  → EXE/DLL
  → 运行时只保留系统依赖，不再要求非系统支持库动态装载
```

源码通过 `__E_STATIC_LIB`、`__COMPILE_FNR` 把同一支持库裁剪成编辑+运行、运行、静态链接三种目标；`resym.exe` 为 COFF LIB/OBJ 的外部符号批量加库名前缀，避免多个支持库冲突。`.run` 运行库约定导出 `xxx_LoadLibrary`、`xxx_FreeLibrary`、`xxx_GetProcAddress`，由宿主按名解析，初始化和释放不依赖 C++ 名字修饰。

### 为什么 F5 看起来快

源码能确认的优化点是“减少每次运行的工作面”，不能据此断言具体线程数或缓存算法：

```text
F5
  ├─ 复用已解析的工程/模块/支持库索引
  ├─ 只编译变化的编辑单元或生成最小中间数据
  ├─ 使用已有 .fne/.fnr 运行库，不重新构建支持库
  ├─ 链接阶段按配置决定是否保留 obj/res/lib
  └─ 直接启动轻量运行宿主
```

`tools/link.ini` 还定义 linker 类型、输出路径、额外参数、错误阈值、中间文件保留和编号化后置动作；GUI 后置动作使用 `START` 避免阻塞 IDE。具体增量编译缓存命中策略、进程复用和调试器内部线程仍未从归档源码中证实，应标记为待 Windows 行为实验。

## 编译前插件：编译器的稳定扩展点

```text
编译器
  → LoadLibrary CompilerPlugins.dll
  → GetProcAddress("CompileProcessor")
  → 传入 COMPILE_PROCESSOR_INFO
      ├─ 源文件名/纯文件名
      ├─ Release/EPackage/目标系统/应用类型
      ├─ 程序元信息
      └─ 常量读写回调
  → 插件按文件过滤目标
  → 写入数值、日期时间、布尔、文本、字节集常量
  → TRUE 继续编译；FALSE 终止并报告失败
```

这说明 IDE/编译器允许受控的“编译前处理器”，但扩展契约是固定结构和回调表，不是插件直接改编译器内存。新平台可把它对应为版本化 `CompileHook`，输入只读编译上下文，输出为受校验的 IR 变换或常量注入。

## 面向新平台的最小稳定底座

```text
项目描述
  → 工程/模块/组件/资源 manifest
  → 版本化 IR 与公开能力索引
  → 编辑器 schema（命令、属性、事件、类型）
  → 编译器管线（IR → 校验 → 目标制品）
  → 运行核心（能力装载、调度、资源所有权）
  → 调试宿主（日志、断点、重启、证据）
  → 发布器（制品、依赖、安装记录、回滚指针）
```

每个扩展点都必须同时声明：稳定 id、契约版本、目标平台、编辑/运行/发布能力、依赖、初始化/释放、错误和资源所有权。这样才能兼容 agent 开发与用户开发，并把“快”建立在索引复用、增量 IR 和轻量宿主上，而不是依赖不可控的全局状态。

## `.e8` 工程控制文件：读取顺序已由样例确认

归档中的 `samples/e8/*.e8` 是明文 INI/CRLF 文件，不是不可解析的二进制容器。样例直接显示工程控制面：

```text
.e8
  ├─ [settings]
  │    └─ source=e8test.e
  ├─ [AppSettings]
  │    ├─ type/name/explain/author/version
  │    ├─ plugins
  │    ├─ EnableExportPublicMethod
  │    ├─ icon
  │    └─ OutputFileName
  └─ [user_consts]
       └─ 整数/日期/字符串/逻辑常量赋值
```

`ManyFiles/TestManyFiles.e8` 进一步确认多源读取算法：

```text
读取 .e8 所在目录
  → 以 .e8 目录为基准解析 source 相对路径
  → 按 source 顺序读取多个 .e/.ec/.txt
  → 发现任一 .ec
       → 合并前删除 .e 中原有模块
       → 以 .ec 模块作为合并模块来源
  → 对重复子程序/命令自动添加冲突标记
       ├─ _重复子程序
       └─ _重复命令
  → 合并 AppSettings 覆盖项
  → 注入 user_consts
  → 交给语法/对象树/编译阶段
```

因此新平台的项目解析器应先解析文本 manifest，再展开相对路径和源列表，最后做模块优先级、冲突诊断和用户常量注入；不要把“工程文件”误建模成单个源码文件。

## F5 调试器：已确认是外部进程调试模型

根目录 `e.exe` 的静态导入表和字符串提供了比“F5 很快”的猜测更可靠的边界：

```text
IDE/e.exe
  → CreateProcessA 启动目标进程
  → WaitForDebugEvent 等待调试事件
  → GetThreadContext 读取线程上下文
  → ReadProcessMemory / WriteProcessMemory 检查或修改目标内存
  → ContinueDebugEvent 继续目标执行
  → DebugActiveProcessStop 结束附加/调试
  → FreeLibrary / LoadLibraryA 管理运行库
```

同时存在 `e_debug`、`CompileProcessor` 和 `*.fne;*.fnr` 字符串。由此可确认：F5 至少包含“编译前插件 + 外部进程调试器 + 支持库装载”三条边界；不能仅凭导入表断言增量缓存、热替换或固定线程数。新平台应把调试器做成独立宿主，通过受控协议传递断点、事件、堆栈和变量，避免编辑器进程直接承担目标程序崩溃风险。

## 公开 IDE 扩展接口：代码窗口是结构化虚拟对象

公开 `eide` 项目（视觉/插件扩展项目，不是官方 `e.exe` 私有源码）在 `EIDE_Virtual.h:84-169` 暴露 `IEIDE_CodeManage`：

```text
代码子窗口 HWND
  → 创建并初始化 IEIDE_CodeManage
  → 光标/选区读写
  → GetLineInfo 读取行标签、变量资源和行模型
  → GetCodeDataOffset 读取 name/type/public/remarks/array/return/optional/static
  → GetCodeText 读取宿主文本
  → 插件绘制、检查、定位或 FN_INSERT_TEXT 写回
  → 宿主 alloc/free 成对回收文本
  → destroy → 删除代码管理对象
```

`ECodeType` 明确区分结构、成员、全局变量、程序集、子程序、参数、局部变量、代码、常量、图片和声音；这说明 IDE 编辑器操作的是结构化行模型，而不是简单文本框。

插件消息链由 `NES_RUN_FUNC` 统一分发，并通过 `IDC_EIDE_GETCODEMANAGE` 获取代码对象：

```text
IDE 消息/MDI 切换/选区变化
  → 插件事件分发
  → 获取 CodeManage
  → 读取行/字段偏移/UI 参数
  → 绘制或诊断
  → FN_GET_PRG_TEXT 两阶段取文本
       先取 m_nBufSize → 宿主 alloc → 再填充 → free
```

`EIDE_CodeManage.cpp` 的实现会用机器码特征扫描和 `thiscall` 适配 5.5/5.6/5.7 私有对象；因此稳定契约只能取方法语义和所有权，不能取对象地址、字段 offset、签名扫描或参数数量。新平台应采用版本化虚拟接口、能力探针、版本矩阵和未命中即关闭的失败策略。

## 无头编译验证：临时制品和原子提交

公开 `e-packager` 的 `AutoLinkerCompileCheck.cpp` 给出了一条可迁移的编译事务证据。它不能证明官方 IDE 内部完全相同，但证明了同类工程可以把编译验证从编辑器进程隔离出去：

```text
工作区
  → 读取/重建 .e 或 .ec bridge
  → 创建隐藏临时输出目录
  → 运行 AutoLinkerTest.exe headless-compile
       ├─ CREATE_NO_WINDOW
       ├─ stdout/stderr → launcher.log
       ├─ timeout 1..3600 秒
       └─ target=EXE/Console/DLL/ECOM
  → 解析 result.json
       ├─ launcher exit = 0
       ├─ ok = true
       └─ artifact_verified = true
  ├─ 成功 → MoveFileExW(REPLACE_EXISTING|WRITE_THROUGH) 原子替换目标
  └─ 失败/超时 → TerminateProcess → 删除临时制品 → 保留诊断
```

这条流程比“编译成功就直接覆盖输出”更适合作为新平台底座：编译、验证、提交必须是三个阶段，提交只接收已验证的不可变制品；任何失败都不能破坏上一次可运行版本。

## 编译前语义检查：先建全局符号，再检查方法体

公开 `e-packager` 的源码预检/语义校验（`SourcePreflightValidator.cpp`、`SourceSemanticValidator.cpp`）还揭示了编译器应有的阶段边界：

```text
文本/工程包
  → 预检全局页、数据类型页、DLL 页、常量页
  → 逐个程序页做语法/结构检查
  → 建立 resources
  → 收集全局、结构、DLL、常量和程序源
  → 收集窗体符号
  → 加入内建可调用项
  → 收集依赖
  → 校验跨页名称
  → 校验声明类型
  → 逐程序、逐方法校验方法体
  → 表达式解析器处理调用和参数
  → 输出 files/lines/errors/warnings 结构化诊断
```

报告最多保留 40 条诊断，说明诊断收集有界；新平台应把全局符号、跨页引用、类型检查、方法体控制流和表达式解析拆成可复用阶段，避免每个 UI 面板各自实现一套编译逻辑。

## `.npk`：COM/OCX 包装层其实是可读的翻译与屏蔽清单

归档中的 `lib/dm.npk`、`lib/jmail.npk`、`lib/wmp9.npk` 是 GBK 文本、CRLF 文件，头部直接规定了记录语法：

```text
@@ Lang = xxxx
  → 当前翻译语言
@@ TypeLib = {GUID},版本,保留字段,名称
  或 @@ OCX = {CLSID},名称
  → 二选一，分别描述类型库或组件
@@ Interface = ...
  → 内部接口映射，禁止随意修改
##1 原名 = 翻译名
  → 输出到支持库的命令/属性/事件
  → 后续文本是说明、签名和示例
##0 原名
  → 屏蔽该项目，不输出到包装支持库
```

```text
NPK 导入
  → 解码 GBK 文本
  → 读取 TypeLib/OCX 身份
  → 解析 Interface 的 GUID、DISPID/成员索引和对象名
  → 读取 ##1 的公开项目与说明
  → 应用 ##0 屏蔽规则
  → 生成易语言命令、属性、事件和帮助条目
  → 编译/运行时由 COM 适配层实例化真实对象
```

这证明“外部 COM 能力”并非直接把任意 Dispatch 暴露给 IDE，而是经过一层可审计的公开面裁剪。新平台可把它对应为 `外部协议描述文件 → 能力契约生成器 → 受限适配器`；屏蔽规则、成员索引和文档应进入版本化 manifest，并在生成前做 GUID/DISPID 冲突检查。

## SDK 深挖：静态编译不是“把 DLL 换成 LIB”

本节依据归档 `sdk/static_docs/index.html:25-271`、`sdk/cpp/docs.txt:73-175`、`sdk/cpp/docs.txt:422-520` 和 `sdk/cpp/samples/licHtmlView/HtmlView.cpp:402-428` 整理。它揭示了支持库从编辑期到发布期的真实调用顺序。

### 动态库是编辑描述提供者，静态库是实现提供者

```text
开发者编译支持库源码
  ├─ 默认构建 → xxx.fne
  │    ├─ 导出 GetNewInf
  │    ├─ 返回完整 LIB_INFO
  │    ├─ 提供命令/方法/参数/属性/事件/类型描述
  │    └─ 提供运行实现，供 IDE 和动态运行程序使用
  ├─ __COMPILE_FNR → xxx.fnr
  │    ├─ 保留最小运行类型信息
  │    ├─ 不携带完整编辑描述
  │    └─ 只给已经编译的程序加载
  └─ __E_STATIC_LIB → xxx_static.lib
       ├─ 不保留 GetNewInf、定义表和实现函数数组
       ├─ 实现函数改成 C 符号并加库前缀
       ├─ 供静态链接器选择并合入最终 EXE/DLL
       └─ 发布前用 resym 处理内部符号
```

静态编译时不是静态库自己描述命令。编译器先加载对应的 `.fne`，向动态库发送通知取得符号名和依赖，再在 `.lib` 中按这些符号查找实现：

```text
源代码/IR
  → 从 .fne 取得命令定义与实现函数顺序
  → PFN_NOTIFY_LIB(NL_GET_CMD_FUNC_NAMES)
       → ["xxx_cmdA", "xxx_cmdB", ...]
  → PFN_NOTIFY_LIB(NL_GET_NOTIFY_LIB_FUNC_NAME)
       → "xxx_ProcessNotifyLib"
  → PFN_NOTIFY_LIB(NL_GET_DEPENDENT_LIBS)
       → "xxx\\a.lib\\0xxx\\b.lib\\0\\0"
  → 从 xxx_static.lib 与依赖目录查找 COFF 符号
  → 生成调用代码并链接
  → 运行时不再需要编辑描述
```

证据要点：`index.html:162-163` 明确说动态库在静态编译时充当辅助信息提供者，真正链接对象是静态库中的符号；`index.html:169-176` 明确要求静态库移除定义信息，避免符号冲突和文件膨胀。

### 三个静态编译通知的严格契约

```text
NL_GET_CMD_FUNC_NAMES (14)
  → 返回 char*[]/文本指针数组
  → 数组顺序必须和命令/方法定义数组一一对应
  → NULL 命令也必须占位，不能改变索引

NL_GET_NOTIFY_LIB_FUNC_NAME (15)
  → 返回本库通知函数的 C 符号名
  → 链接器据此把系统通知入口接入静态库

NL_GET_DEPENDENT_LIBS (16)
  → 返回以 NUL 分隔、双 NUL 结尾的静态库列表
  → kernel32/user32/gdi32 等系统库不必列出
  → NULL/NR_ERR 表示没有额外依赖
```

```text
编译器收到通知
  ├─ 返回为空/顺序不一致 → 不能安全映射实现，静态链接失败
  ├─ 返回第三方依赖 → 在 static_lib/xxx/ 下解析
  └─ 返回命令符号 → 按调用约定推导 COFF 装饰名并查找
```

这里有一个容易被忽略的兼容性边界：静态版要求库名此前缀只能由小写字母、数字、下划线组成，不能数字开头；中文文件名要用 UTF-8 十六进制前缀，但文档同时说明当时静态编译暂不支持中文文件名（`index.html:63`）。新平台应把 `能力 id` 与展示名彻底分离，并在构建开始时拒绝不合法制品 id，而不是到链接阶段才报错。

### `resym` 是发布阶段的符号隔离器

```text
xxx_static.lib / OBJ
  → resym all
  → 读取 COFF 符号表
  → 保留 xxx 前缀及其大小写变体
  → 对其余符号统一加 prefix
  → 输出新 LIB/OBJ
  → 放入 static_lib
```

直接证据（`index.html:189-219`）：

```text
resym all infile=".../xxx.lib" outfile=".../xxx_static.lib" prefix=xxx
  ├─ all 模式：除指定例外外全部重命名
  ├─ prefix 以 _static 结尾时，自动视为 xxx_
  ├─ sym/symregex/symfile 可声明不得重命名的符号
  ├─ infile 必须为 COFF LIB/OBJ
  └─ 工具明确警告：转换可能改变功能，结果不作担保
```

这说明它的“稳定态”依赖构建后处理，而不是只依赖源码命名。对应新平台的做法应是：

```text
编译器输出
  → 符号清单审计
  → 公开入口白名单
  → 私有符号命名空间化
  → 二进制摘要
  → 依赖闭包检查
  → 才能签名/发布
```

### `.run` 静态库有自己的三函数加载器

静态文档 `index.html:222-233` 对 `.run` 给出了额外 ABI：

```c
extern "C" BOOL xxx_LoadLibrary();
extern "C" void xxx_FreeLibrary();
extern "C" void* xxx_GetProcAddress(const char* lpProcName);
```

其调用顺序为：

```text
静态链接程序启动
  → xxx_LoadLibrary()
       ├─ 初始化第三方库/线程局部状态/函数表
       └─ 返回 FALSE → 启动失败
  → xxx_GetProcAddress("函数名")
       └─ 返回实现地址（应有名称到地址缓存）
  → 业务命令执行
  → xxx_FreeLibrary()
       └─ 清理句柄、线程、缓存、第三方运行库
```

`.run` 因此不是普通资源文件，而是“静态链接下的受控运行时提供者”。新平台应把它映射为受管执行单元：加载、能力解析、调用、释放四步必须有状态机，禁止在任意业务节点中隐式加载动态库。

## EPK 启动器与 E-DLL：从样例能还原出的边界

### EPK 启动器的查找与失败路径

`epackage/source/el.asm:37-131` 是可读的 MASM 启动器。它没有自己解析 EPK，而是先找到核心支持库，再调用导出的 `LoadEPKFromCmdLine`：

```text
启动 el.exe
  → 取当前可执行文件目录
  → 尝试加载同目录 krnln.fnr
  → 失败则读取 HKCU\\Software\\FlySky\\E\\Install\\Path
  → 规范化尾部反斜杠
  → 回退加载安装目录 krnln.fne
  → GetProcAddress("LoadEPKFromCmdLine")
  → 调用 LoadEPKFromCmdLine()
  ├─ 返回非零 → 进入易包运行
  └─ 返回零 → FreeLibrary + MessageBox("Load EPK data invalid!") + 返回 -1
```

源码还保留了两个同类接口的原型注释（`el.asm:45-50`）：

```text
LoadEPKData(name, memory, size)
LoadEPKFile(file, optionalName)
LoadEPKFromCmdLine()
```

这暴露出三种装载入口：内存制品、文件制品、命令行批量/参数制品。新平台的包加载器应统一成同一内部入口，外面只做来源适配：

```text
文件/内存/命令行
  → 标准化 PackageSource
  → 校验格式、版本、摘要、签名
  → 分配包实例 id
  → 注册公开能力/类
  → 执行初始化
  → 返回可调用句柄
```

### E-DLL 的懒加载、入口偏移和退出通知

`epackage/source/dll_pkg.asm:28-212` 不是普通 DLL 入口，它保存了一个小型加载状态：程序 id、清理函数地址、退出通知地址、核心库句柄和入口偏移。

```text
DLL_PROCESS_ATTACH
  → 只返回成功，不立刻加载核心库

第一次调用导出桩 ESub_Caller
  → 若 dwAppHeadereAddress == 0
       → EEXE_Loader
       → 同目录 krnln.fnr，失败再注册表 Path/krnln.fne
       → GetProcAddress("GetNewSock")
       → 调用 ITL_NOTIFY_DLL_EXIT(1002)
            → 得到 DLL 退出通知函数地址
       → 调用 ITL_LOAD_DLL_APP2(1003)
            → 得到程序加载 id
       → 根据返回地址 + ENTRY_POINTER_OFFSET 取真实应用入口
       → 保存清理函数、应用头地址、退出通知地址
  → 将本次 eax（相对入口偏移）加应用头地址
  → 跳转真实入口
```

```text
DLL_PROCESS_DETACH
  → 若有清理地址，调用清理
  → 若有退出通知地址，传入程序 id 通知核心
  → FreeLibrary(krnln)
```

这里可以解释“运行很快”的一部分：DLL attach 只做最小工作，真正的核心加载延迟到第一次调用；核心库句柄和入口地址缓存后，后续调用直接跳转，不重复解析。它不是证明全部 F5 使用热缓存，但确实证明了 E-DLL 的懒初始化和一次性入口缓存。

### 普通 E-EXE 的入口过程

`epackage/source/epackage.asm:28-132` 对普通 E-EXE 展示同样的路径：

```text
启动 E-EXE
  → 当前目录 krnln.fnr
  → 注册表安装路径 krnln.fne
  → GetNewSock
  → 发送 ITL_RUN_APP = 1000
  → 返回应用入口偏移
  → 加 ENTRY_POINTER_OFFSET
  → 跳转应用入口
  → ExitProcess(0)
```

失败时先 `FreeLibrary`，再弹出错误并返回 -1。这个错误边界应在新平台变成结构化启动诊断：来源路径、制品类型、解析阶段、缺失符号和可恢复性，而不是只显示一个通用消息框。

## Delphi/VCL 控件：窗口句柄与语言对象的双向桥

依据 `sdk/delphi/elib.pas:26-163`、`sdk/delphi/elib.pas:171-225` 和 `sdk/delphi/elib.pas:500-770`，控件支持库不是单纯返回一个 HWND，而是维护三层身份：VCL 控件、容器窗口、语言侧 `HUNIT`。

### 创建、注册和映射

```text
IDE/运行核心请求创建组件
  → ELib_CreateControl(ControlClass, style, parent, x,y,cx,cy,...)
  → 创建 TWinControl
  → 可选创建 Container/Form 作为父容器
  → ELib_RegControl 注册到易语言对象系统
  → 取得 HUNIT
  → SetProp(HWND, "dywt.com.cn/elib/vcl/wnd_prop_name", PWndPropData)
  → 建立 HUNIT ↔ HWND ↔ TWinControl ↔ Container 映射
```

`WndPropData` 同时记录 `Control`、容器子控件、旧窗口过程、焦点/鼠标状态、FormID/UnitID（`elib.pas:171-195`），因此窗口属性不能只靠全局字典；它必须随窗口句柄销毁而移除。

### 属性是长度受限的二进制流

```text
IDE 写属性
  → ELib_TPropWriter 创建 TMemoryStream
  → WriteInt/Bool/Double/String/Font/Strings/MemoryStream
  → GetDataAddress + GetDataLength
  → 通过属性接口发送 HGLOBAL/缓冲区

IDE 读属性
  → ELib_TPropReader(DataAddress, DataLength)
  → 维护 FPosition
  → 每次读取检查边界
  → 恢复 VCL 值
```

`TAttachedMemoryStream`（`elib.pas:69-75`）明确说明可附着已有内存但不可改变大小；这是一种借用缓冲区语义。新平台要把“借用”和“拥有”写进资源契约，防止插件释放宿主内存。

### 事件转发与消息代理

```text
Windows/VCL 消息
  → Container/Control 窗口过程拦截
  → 根据消息类型组装 EVENT_ARG_INFO/EVENT_ARG_INFO2
  → NotifySys(NRS_EVENT_NOTIFY2, EventData)
  → 核心查找 HUNIT、FormID、UnitID
  → 调用语言事件处理子程序
  → 将 EAS_BY_REF 参数写回控件状态
```

控件容器会在焦点、显示、启用、鼠标消息之间做转发；Delphi 注释特别指出“Panel 容器转发 WM_LBUTTONDOWN 会破坏 Click 事件”，所以 `NeedClick` 不是装饰参数，而是消息路由策略：

```text
需要 Click 事件
  → 不把 WM_LBUTTONDOWN 转发给父 Panel
只需要底层鼠标消息
  → 转发 WM_LBUTTONDOWN
```

### 销毁顺序是协议的一部分

```text
控件销毁/重建
  → 截断旧窗口过程
  → NotifySys(NAS_DETACH_CWND_OBJECT, HUNIT)
  → 释放/移除 HWND 属性数据
  → 如为容器：NAS_DELETE_CWND_OBJECT
  → 释放 VCL Child/Container
  → 语言侧收到单元销毁事件
```

源码中 `NAS_DETACH_CWND_OBJECT` 总在 `NAS_DELETE_CWND_OBJECT` 之前，说明“解除绑定”和“删除语言对象”是两个不同阶段。新平台组件生命周期应至少拆成 `创建 → 附着 → 可用 → 分离 → 删除`，不可把分离和删除合并成一个不幂等的回调。

## 安装器与制品资产：构建器和安装器是成对版本

`setup/readme.txt:1-23` 说明安装目录内有两套互相配合的源码/制品：

```text
mksetup.e / mksetup.exe / mksetup.dll
  → 组织用户安装包
  → 写入 setup.exe 所需的包数据

setup.e / setup.exe / setup.dll
  → 执行用户安装
  → 注册程序、快捷方式和卸载信息

setup.tpl / uninstall.tpl
  → 安装器/卸载器模板
```

其维护顺序是：修改 `mksetup.e` 后必须同步修改 `setup.e`，重新编译后把新的 EXE 和源码一起放回 setup 目录；否则安装器可能缺少支持文件或执行数据不匹配。对应新平台的发布流程应把打包器版本、安装器版本、卸载器版本和制品 manifest 绑定为一个发布事务：

```text
制品构建
  → 生成 manifest/摘要/依赖闭包
  → 打包器按同一 manifest 生成安装包
  → 安装器校验 manifest 后落盘
  → 写安装记录/卸载记录
  → 激活版本指针
  → 卸载只删除当前事务登记的文件
```

## 本轮补充后的确定性边界

```text
已由源码/SDK直接确认
  ├─ .fne/.fnr/.lib 的阶段分工
  ├─ 静态编译三类通知与符号映射
  ├─ resym 的 COFF 符号隔离规则
  ├─ .run 三函数加载/释放/查找 ABI
  ├─ EPK 的同目录优先、注册表回退和命令行加载入口
  ├─ E-DLL 懒加载、入口偏移缓存、清理/退出通知
  ├─ Delphi 控件的 HUNIT/ HWND/容器三向映射
  ├─ 属性长度流、借用内存流和事件消息代理
  └─ 安装器与打包器源码/制品必须同步

仍未能从归档直接确认
  ├─ IDE 对全部 .fne 的实际排序和缓存淘汰策略
  ├─ 编译器内部 IR 的字段级二进制布局
  ├─ EPK 内部压缩/签名字段的完整规范
  ├─ F5 是否复用 OBJ、LIB 或进程快照
  └─ 私有加密狗/授权服务的实现
```

未确认项不应作为新平台设计的依赖；应以可观测、可替换、可回滚的公开契约替代。

## 公开 e-packager 的工程模型：把“快”拆成可验证的复用层

公开 `e-packager` 项目不是官方 `e.exe` 源码，因此本节只作为独立实现的架构证据，用来验证哪些设计可以稳定落地。它的 `ProjectBundle` 把工程拆成可持久化对象，而不是把整个 `.e` 当作不可分割字节串：

```text
ProjectBundle
  ├─ 工程身份：sourcePath/sourceFileKind/name/version
  ├─ 依赖：ELib/ECom、GUID、版本、路径、公开符号
  ├─ 源码：sourceFiles、四类固定源码表
  ├─ 窗体：formFiles、windowBindings、过滤器树
  ├─ 资源：Image/Sound、logicalName、稳定 key、二进制
  ├─ 原生保真：nativeSourceBytes、section 快照
  └─ 摘要：nativeBundleDigest
```

### 复用路径

```text
读取 .e/.ec
  → 有界 ByteReader 解析 section
  → 建立 ProjectBundle
  → ComputeBundleDigest
  → 目录工程/编辑器修改
  ├─ 摘要未变
  │    → CanReuseNativeBundleSnapshot
  │    → 直接复用原生字节
  └─ 摘要变化
       → 清除快照复用状态
       → Document/RestoreDocumentModel
       → 按 section 顺序重建
```

这提供了比“每次 F5 全量重编译”更具体的性能设计依据：把稳定部分的解析结果、原生段快照和依赖索引缓存起来，只在摘要覆盖的输入发生变化时重建。它不能证明易语言官方 IDE 使用同样算法，但可作为自研平台的可测量实现：每次复用都必须记录命中原因、摘要和失效原因。

### 依赖与资源变更为什么必须使快照失效

```text
新增 .ec/.fne/图片/声音
  → 等价性去重
  → 更新依赖/资源清单
  → ClearNativeByteReuseState
  → 重建常量、资源和引用索引
  → 写工作区
```

如果新增资源后仍沿用旧原生快照，生成结果会丢失新增常量或段；因此“缓存”必须有明确的失效触发器，不能只按文件修改时间猜测。

### 公开实现与官方实现的证据边界

```text
官方 SDK/归档
  → 证明 ABI、制品后缀、通知、加载器和样本字节

公开 e-packager/eide
  → 证明一种可运行的工程对象模型、语义检查、依赖导出和原子回包方案

不能直接推出
  → 官方 e.exe 内部使用相同类名、缓存键、线程数或快照算法
```

文档后续引用 `ProjectBundle`、`SourcePreflightValidator`、`AutoLinkerCompileCheck` 时，均应保留“公开实现参考”标签，避免把第三方兼容项目误写成官方源码。

## 公开 IDE API 的状态机证据：功能不是菜单，而是可组合命令域

归档中的 `sdk/cpp/elib/PublicIDEFunctions.h` 将 IDE 能力编码成分层编号。它不是 UI 文案表，而是插件调用宿主的稳定命令面：高 8 位先区分功能域，中间位区分子域，低位才是具体操作。

```text
功能编号 dwFuncNO
  ├─ FNT_MOVE       → 光标、滚动、参数展开、子程序跳转
  ├─ FNT_EDIT       → 块操作、插入/删除/撤销/重做/预编译
  ├─ FNT_DOCUMENT   → 新建、打开、关闭、保存、另存
  ├─ FNT_OTHER      → 面板、库管理、帮助、重链、书签
  └─ FNT_EAPP       → 调试、运行、插件附加

插件调用
  → NES_RUN_FUNC 通知
  → dwParam1 = 功能编号
  → dwParam2 = 两个 DWORD 参数槽
  → 宿主按当前状态/活动编辑窗口判断是否执行
  → 返回 BOOL；未实现或功能被禁用时返回失败
```

### “当前活动窗口”是状态上下文，不是全局文本

`FN_GET_ACTIVE_WND_TYPE` 明确返回当前活动编辑器类型：主程序、窗体、自定义数据类型、全局变量、DLL 命令、常量、图片资源、声音资源。于是同一个“插入/删除/预编译”命令，必须先绑定活动文档上下文。

```text
宿主状态
  ├─ 活动文档类型
  ├─ 当前行/列/参数展开状态
  ├─ 只读/锁定状态
  ├─ 当前选择区
  ├─ 是否有未保存修改
  └─ 当前运行/调试状态

插件请求 FN_INSERT_NEW / FN_REMOVE / FN_PRE_COMPILE
  → 检查活动窗口类型
  → 检查只读、锁定、运行中限制
  → 应用文档事务
  → 更新行号/符号索引/撤销栈
  → 需要时触发预编译
  → 返回成功或保持原状态
```

这对新平台的启示是：命令不能直接修改 AST；必须经过“活动文档 + 编辑事务 + 状态门禁”，否则 Agent 与人工 UI 同时操作时会产生不可复现的覆盖。

### 预编译与编译是两个不同状态

公开编号单独提供 `FN_PRE_COMPILE`、`FN_FORCE_PROCESS`、`FN_SET_AND_COMPILE_PRG_ITEM_TEXT`，又提供 `FN_COMPILE`、`FN_COMPILE_AND_RUN` 及具体制品编译命令。这说明“编辑文本变成可检查语义”与“生成可运行制品”不是一次操作。

```text
编辑状态
  → FN_SET_AND_COMPILE_PRG_ITEM_TEXT
      ├─ 写入当前程序项文本
      ├─ 可选触发预编译
      └─ 返回预编译是否成功

预编译状态
  → FN_PRE_COMPILE / FN_FORCE_PROCESS
      ├─ 更新当前程序项的结构化行/参数/符号
      ├─ 建立或刷新错误位置
      └─ 不承诺生成 EXE/DLL

可编译状态
  → FN_COMPILE_STANDARD / FN_COMPILE_STATIC / FN_COMPILE_EPACKAGE
  → FN_COMPILE_WINDOWS_EXE/DLL/ECOM
      ├─ 读取已处理的程序项和依赖
      ├─ 生成目标格式
      └─ 失败时保留编辑状态，不替换旧制品
```

### 编译目标本身就是显式状态分支

```text
RunCommand
  ├─ FN_COMPILE                 → 默认编译
  ├─ FN_COMPILE_AND_RUN         → 编译成功后运行
  ├─ FN_END_RUN                 → 结束正在运行的目标
  ├─ FN_PUBLISH                 → 编译并发布
  ├─ FN_COMPILE_STANDARD        → 标准运行库目标
  ├─ FN_COMPILE_STATIC          → 静态库/静态链接目标
  ├─ FN_COMPILE_EPACKAGE       → EPK 包目标
  ├─ FN_COMPILE_WINDOWS_EXE_AND_RUN / DLL_AND_RUN / ECOM_AND_RUN
  ├─ FN_COMPILE_WINDOWS_EXE / DLL / ECOM
  └─ FN_STATIC_COMPILE_WINDOWS_EXE / DLL
```

新平台应把这些目标建成不可混淆的 `构建配置 id`，而不是依靠“当前按钮”推断：

```text
构建配置
  ├─ 运行模式：调试 / 发布
  ├─ 目标制品：可执行文件 / 动态库 / 模块 / 包
  ├─ 链接模式：运行库 / 静态
  ├─ 入口策略：运行 / 不运行
  ├─ 资源策略：嵌入 / 外置
  └─ 诊断策略：断点信息 / 最小发布信息
```

## 公开接口给出的 IDE 状态转移图

以下是从功能编号与回调语义归纳出的可验证状态机；“归纳”表示状态名称是新平台表达，不声称官方源码使用这些类名。

```text
未打开
  │ FN_NEW_FILE / FN_OPEN_FILE / FN_OPEN_FILE2
  ▼
已打开·未处理
  │ FN_PRE_COMPILE / FN_FORCE_PROCESS
  ├────────失败──────────────┐
  │                          ▼
  │                    已打开·诊断错误
  │                          │ 修正/撤销/重做
  │                          └──────────────┐
  ▼                                         │
已打开·已处理 ◄─────────────────────────────┘
  │ FN_SAVE_FILE / FN_SAVE_AS_FILE
  ▼
已保存·已处理
  │ FN_COMPILE_*
  ├─ 失败 → 已保存·构建错误（旧制品仍有效）
  └─ 成功 → 新制品暂存
              │ 原子提交
              ▼
          已发布/可运行
              │ FN_COMPILE_AND_RUN / *_AND_RUN
              ▼
          运行中
              │ FN_END_RUN / 进程退出
              ▼
          已发布/可运行
```

关键不变量：构建失败不能把“最后一次成功制品”替换成半成品；关闭文件前必须处理未保存修改；运行中禁止破坏性编辑，或把编辑排队到下一次预编译。

## 诊断模型：从结构化行读取到可定位错误

### 程序文本不是唯一诊断来源

`GET_PRG_TEXT_PARAM` 允许插件按行、列读取当前程序项，返回缓冲区大小、类型和“是否标题行”；`VT_*` 常量又覆盖 DLL 命令、用户类型、元素、全局变量、资源、模块、子程序、参数和局部变量。

```text
GET_PRG_TEXT_PARAM(row, col, NULL, 0)
  → 宿主返回所需缓冲区大小 + VT_xxx
GET_PRG_TEXT_PARAM(row, col, buffer, size)
  → 宿主复制单元格文本
  → 返回类型/标题标志
  → 诊断器将 (文档id, 行, 列, 类型) 绑定到符号节点
```

这是一种“结构化编辑表”诊断，而不是只扫描原始字符串。新平台应让诊断位置同时携带：文档版本摘要、节点 id、字段路径、行列范围、错误码、严重级别、可修复动作和相关依赖。

### 诊断分层

```text
编辑诊断
  ├─ 文本/结构化行无法解析
  ├─ 参数数量/类型不匹配
  └─ 当前编辑上下文不允许操作

语义诊断
  ├─ 符号未定义/重复定义
  ├─ 返回类型或引用方向错误
  ├─ 窗体/组件属性和事件不兼容
  └─ 支持库能力/操作系统掩码不满足

构建诊断
  ├─ 支持库制品缺失或 GUID/版本冲突
  ├─ 静态库符号未隔离
  ├─ 外部 linker/资源编译失败
  └─ 目标制品写入/签名/发布失败

运行诊断
  ├─ 进程启动失败
  ├─ 运行时错误通知
  ├─ 断点/单步状态
  └─ 外部资源不可访问
```

每层都应保留上一层结果；构建错误不能覆盖源代码诊断，运行时错误也不能反向修改已提交制品。

## 插件生命周期：附加、调用、卸载与资源边界

### 附加插件拥有的是受限宿主 API

`FN_ADD_TAB`、`FN_GET_ACTIVE_WND_TYPE`、`FN_IS_FUNC_ENABLED`、剪贴板 EPRG 数据读写、`FN_GET_PRG_TEXT`/`FN_GET_PRG_HELP` 等接口表明插件以宿主扩展方式工作，不能假设直接持有 IDE 内部对象。

```text
发现插件 DLL
  → LoadLibrary（宿主行为，公开头文件只描述后续接口）
  → 插件注册通知/菜单/工具页
  → 插件调用 NES_RUN_FUNC
  → 宿主按状态门禁执行
  → 插件通过 GET_PRG_TEXT / EPRG 剪贴板读取结构化数据
  → 插件卸载前撤销页签、回调、临时资源
  → FreeLibrary
```

### 公开 EPK/E-DLL 加载器给出了更完整的失败回滚序列

`epackage/source/epackage.asm`、`el.asm` 和 `dll_pkg.asm` 是归档中的公开汇编包装器，不是官方 `e.exe` 私有源码，但它们直接展示了运行时装载边界。

```text
EPK 包装器启动
  → 取自身目录 + krnln.fnr
  → LoadLibrary
  ├─ 成功 → GetProcAddress("LoadEPKFromCmdLine")
  │          → 调用加载入口
  │          → 成功 ExitProcess(0)
  │          → 失败 FreeLibrary + 错误框 + -1
  └─ 失败 → 读取 HKCU\\Software\\FlySky\\E\\Install\\Path
             → 拼接 krnln.fne
             → LoadLibrary
             → 重复上述入口查找
```

```text
E-DLL 首次进入
  → DLL_PROCESS_ATTACH：只返回成功，不立即执行用户代码
  → 首次 ESub_Caller 调用时才装载核心库（懒加载）
  → 查找 GetNewSock
  → 发送 ITL_NOTIFY_DLL_EXIT，取得退出通知地址
  → 发送 ITL_LOAD_DLL_APP2，取得程序 id/入口信息
  → 缓存程序头地址
  → 跳转到入口偏移

E-DLL 卸载
  → 调用用户代码释放函数
  → 调用核心库 DLL 退出通知（program id）
  → FreeLibrary(krnln)
  → 清理所有地址/句柄
```

`dll_pkg.asm` 的失败分支会清零程序 id、入口、释放地址、通知地址和核心库句柄，然后终止进程。这说明加载失败回滚应清除所有半初始化状态，不能只返回错误码。

### 插件与制品的现代化边界

```text
插件
  ├─ 只拿能力 id/宿主命令，不拿内部指针
  ├─ 回调带插件实例 id 和取消令牌
  ├─ 卸载先撤销注册，再等待调用归零
  └─ 失败只影响插件，不污染 IDE 主状态

运行制品
  ├─ 只拿版本化运行 ABI
  ├─ 入口/退出/资源释放协议完整
  ├─ 制品与编辑元数据分离
  └─ 由进程/沙箱隔离原生库
```

## 无头编译与原子制品提交：从公开编译命令推导的实现契约

归档中的静态编译文档明确流程是“编译器中间数据 → COFF OBJ → 第三方链接器 + 各支持库静态 LIB → EXE/DLL”。公开脚本又显示资源编译、汇编/编译、链接均是独立失败点。

```text
输入快照
  → 锁定工程版本/依赖 GUID/目标配置
  → 预编译程序项
  → 生成中间数据
  → 生成 COFF OBJ
  → 收集支持库 xxx_static.lib / xxx_static.res
  → resym 处理符号前缀
  → 资源编译（可选）
  → 第三方 linker
  → 产出临时 EXE/DLL/ECOM/EPK
  → 结构检查、依赖检查、启动/导出检查
  → 原子重命名/激活指针切换
```

### 无头任务的事务边界

```text
BuildJob(id)
  ├─ 输入：工程摘要、目标配置、工具链摘要、依赖锁
  ├─ 工作目录：job-id 临时目录
  ├─ 日志：阶段、命令、退出码、耗时、产物摘要
  ├─ 取消：停止子进程并清理临时句柄
  └─ 输出：不可变制品 + 诊断清单 + 证据记录
```

```text
阶段失败
  → 不触碰当前激活制品
  → 保留可审计日志和诊断
  → 删除/隔离临时目录
  → 返回可重试分类

阶段成功
  → fsync 临时制品和清单
  → 校验摘要/大小/目标格式
  → 原子 rename 到内容寻址仓库
  → 最后一步更新激活指针
```

`e-packager` 的公开 `ProjectBundle`/原生 section 快照可以作为“编辑缓存复用”参考，但不能证明官方 F5 一定复用 OBJ 或进程快照。新平台必须把缓存命中、失效原因和实际命令写入证据账本，以便回答“快在哪里”。

## 新平台可直接采用的最小契约集合

```text
文档状态契约
  ├─ 文档 id + 版本摘要
  ├─ 活动编辑上下文
  ├─ 未保存/已处理/诊断状态
  └─ 编辑事务与撤销点

编译契约
  ├─ 预编译结果
  ├─ 语义诊断
  ├─ 目标配置 id
  ├─ 工具链/依赖摘要
  └─ 不可变制品输出

插件契约
  ├─ 能力声明和最低宿主版本
  ├─ 有界调用/取消/卸载
  ├─ 结构化读取接口
  └─ 资源释放确认

诊断契约
  ├─ 层级、错误码、位置、节点 id
  ├─ 依赖和版本上下文
  ├─ 可重试/可修复标志
  └─ 与制品及构建证据关联
```

这些契约是从公开 SDK、公开包装器和公开兼容实现交叉归纳的工程建议；不应表述为官方私有实现已被完整恢复。

## SDK 通知总线的四个地址空间：编辑器、桥接层、运行时、库生命周期

`lib2.h` 将通知编号按调用方向和生命周期分成四组。它不是一个无类型的“消息字符串总线”，每个编号都隐含了参数方向、返回值约定和资源所有权。

```text
支持库 DLL
  ├─ m_pfnNotify(nMsg, p1, p2)      ← 宿主通知支持库（NL_*）
  └─ g_fnNotifySys(nMsg, p1, p2)     → 支持库通知宿主（NRS_*）

宿主/IDE
  ├─ NES_*  编辑器专用：主窗口、IDE 菜单功能、图片选择对话框
  ├─ NAS_*  编辑器/运行时共同桥接：图标、版本、路径、HWND/CWnd 映射
  ├─ NRS_*  运行时调用：事件、窗口对象、数组、内存、错误、退出
  └─ NL_*   反向调用库：初始化通知函数、释放、卸载、插件菜单、动态元素
```

### 四类消息的可验证调用流程

```text
装载 .fne/.fnr
  → 宿主读取 LIB_INFO
  → 调用 PFN_NOTIFY_LIB(NL_SYS_NOTIFY_FUNCTION, PFN_NOTIFY_SYS)
  → 支持库保存 g_fnNotifySys
  → 支持库后续所有宿主服务均经 g_fnNotifySys 转发
  → 卸载前调用 PFN_NOTIFY_LIB(NL_FREE_LIB_DATA)
  → 支持库释放库级缓存、窗口类注册和临时句柄
```

```text
IDE 插件支持库（LBS_IDE_PLUGIN）
  → IDE 完成启动
  → NL_IDE_READY 通知插件
  → 用户打开右键菜单
  → NL_RIGHT_POPUP_MENU_SHOW(HMENU, e.exe 资源 ID)
  → 插件可改菜单或拒绝操作
  → 用户请求新变量/子程序/常量资源
  → NL_ADD_NEW_ELEMENT(in 类型 + out 结构)
  → 返回 1 接受、2 终止、0 未处理
```

### 返回码不是统一布尔值

```text
通用通知返回
  NR_OK  = 0
  NR_ERR = -1

特殊生命周期返回
  NL_UNLOAD_FROM_IDE
    ├─ NR_OK         → 可立即卸载
    ├─ NR_DELAY_FREE → 库要求延迟释放（仍需后续 FREE_LIB_DATA）
    └─ NR_ERR        → 指定文件/资源不能卸载

事件通知返回
  0      → 事件被宿主丢弃，未到用户事件处理子程序
  非 0   → 事件已投递
  event.m_blHasReturnValue / m_infRetData
           → 用户处理器是否写回返回值
```

新平台不应把所有插件回调折叠为 `true/false`；应为每个回调定义可观测的结果枚举、是否允许延迟卸载、是否已经交付以及失败后的资源责任。

## NAS/NRS 窗口对象桥：HWND、CWnd、HUNIT 三种身份不能混用

SDK 明确存在三层句柄身份：操作系统 `HWND`、MFC `CWnd*` 和易语言运行时 `HUNIT`。其中 `NAS_CREATE_CWND_OBJECT_FROM_HWND` 创建的是临时 CWnd 包装，不等于创建易语言窗口单元。

```text
已有 HWND
  → NAS_CREATE_CWND_OBJECT_FROM_HWND(HWND)
  → CWnd* 包装对象
  → NAS_ATTACH_CWND_OBJECT(HWND, CWnd*) 重新绑定（必要时）
  → NAS_GET_HWND_OF_CWND_OBJECT(CWnd*) 取回 HWND
  → NAS_DETACH_CWND_OBJECT(CWnd*) 解除绑定
  → NAS_DELETE_CWND_OBJECT(CWnd*) 删除包装对象
```

```text
易语言窗口单元创建
  → ITF_CREATE_UNIT(属性快照, 父 HWND, FormID, UnitID, 设计态标志)
  → 支持库创建 CWnd/VCL 控件
  → 返回 HUNIT
  → 运行时以 (FormID, UnitID) 建立索引
  → 命令通过 NRS_GET_UNIT_PTR 或 NRS_GET_AND_CHECK_UNIT_PTR 取对象
  → 控件销毁时 NRS_UNIT_DESTROIED(FormID, UnitID)
  → 运行时移除索引后允许 DLL 自删除
```

Delphi `elib.pas` 的实现进一步证明销毁顺序：收到 `WM_NCDESTROY` 后先 `NAS_DETACH_CWND_OBJECT`，再 `NAS_DELETE_CWND_OBJECT`，最后释放 VCL 控件；C++ SDK 则要求 `PostNcDestroy` 发送 `NRS_UNIT_DESTROIED` 后 `delete this`。这意味着新平台必须把“宿主索引删除”和“对象内存释放”分成两个阶段，禁止对象释放后仍可按节点 id 查到悬挂句柄。

```text
WM_NCDESTROY
  → 停止新事件进入
  → 从宿主 (form_id, unit_id) 索引摘除
  → DETACH 原生窗口包装
  → DELETE 包装对象/控件
  → 释放插件侧状态
  → 写入 destroyed 终态
```

## 属性 ABI：设计时快照与运行时实时值是两条不同读取路径

### 创建与属性保存

```text
IDE 设计器
  → ITF_GET_ALL_PROPERTY_DATA
  → 插件将全部属性编码为自定义字节流/HGLOBAL
  → 工程文件保存属性快照

运行时加载
  → 读取属性快照
  → ITF_CREATE_UNIT(pAllPropertyData, size, ..., blInDesignMode=FALSE)
  → 控件从快照恢复内部状态
```

### 单属性读写的时态规则

```text
ITF_GET_PROPERTY_DATA(unit, index)
  ├─ 设计时：返回内部保存的设计值
  └─ 运行时：返回控件当前实时值（例如重新 GetWindowText）

ITF_NOTIFY_PROPERTY_CHANGED(unit, index, value)
  → 先校验输入值
  → 更新内部状态和可视外观
  → 返回 need_recreate
  → need_recreate=true 时由 IDE/宿主重新走 CREATE_UNIT
```

`ITF_DLG_INIT_CUSTOMIZE_DATA` 还返回 `pblModified`，用于决定是否建立撤销记录；因此属性系统同时承载状态变更和 IDE 编辑事务，不能只当作静态 JSON 配置。

### 属性内存所有权

```text
读取文本/字节集属性
  → 插件返回只读指针
  → 宿主读取，不直接修改

写入文本/字节集属性
  → 先 NRS_MFREE 释放旧指针
  → 再用 NRS_MALLOC 分配新缓冲区
  → 写入新指针或 NULL

读取/写入复合属性、数组
  → 按字段定义递归释放 SDT_TEXT/SDT_BIN/复合成员
  → NRS_FREE_ARY 释放数组头和元素区
  → 插件不得把自己的 malloc/free 与宿主混用
```

## 事件 ABI：来源索引、参数方向、返回值和释放责任一起传递

```text
原生控件消息
  → 映射为 (FormID, UnitID, EventIndex)
  → 按 EVENT_INFO/EVENT_INFO2 校验参数个数和 DATA_TYPE
  → 组装 EVENT_NOTIFY 或 EVENT_NOTIFY2
  → NRS_EVENT_NOTIFY/NRS_EVENT_NOTIFY2
  → 宿主查找用户事件处理子程序
  → 执行并写回可选返回值
  → 返回“已投递/被丢弃”
```

```text
EVENT_NOTIFY（旧 ABI）
  ├─ 最多 5 个 INT 参数
  ├─ 适合整数/逻辑值
  └─ 返回值为 BOOL/INT

EVENT_NOTIFY2（扩展 ABI）
  ├─ 最多 MAX_EVENT2_ARG_COUNT=12 个 EVENT_ARG_VALUE
  ├─ 参数带 DATA_TYPE 和 EAS_BY_REF
  ├─ 可写回复合返回描述
  └─ 额外返回数据的释放责任由“抛出事件的支持库代码”承担
```

`EAS_BY_REF` 是一个重要边界：引用参数必须使用宿主可访问的内存布局；插件不能把栈地址、私有堆地址或生命周期短于事件调用的临时对象传给用户代码。新平台应把它实现为受控的可变值槽或资源句柄，而不是裸指针。

## NRS 资源调用矩阵：失败策略和所有权必须显式化

```text
NRS_MALLOC(size, fail_mode)
  ├─ fail_mode=0：分配失败时宿主可直接终止当前程序
  └─ fail_mode!=0：分配失败返回 NULL，由插件处理

NRS_MREALLOC(ptr, new_size, fail_mode)
  ├─ 成功返回新地址
  └─ 失败按 fail_mode 终止或返回 NULL

NRS_MFREE(ptr)
  └─ 只能释放宿主分配器产生的地址

NRS_FREE_ARY(data_type, array_ptr)
  └─ 依据系统数据类型递归释放数组成员

NRS_FREE_COMOBJECT(ptr)
  └─ 由宿主释放 COM 对象包装

NRS_GET_BITMAP_DATA(HBITMAP)
  └─ 返回 HGLOBAL BMP 数据，调用方必须按宿主规则释放
```

```text
能力调用结束
  → 统一结果中标记值/句柄/数组类型
  → 宿主按类型选择释放器
  → 释放顺序记录在调用证据
  → 任何未匹配的 owner_token / allocator_id 都拒绝释放
```

这是把旧式 SDK ABI 转换成 Agent 平台契约时的关键：`value`、`resource_handle`、`borrowed_view`、`mutable_ref` 必须分型，不能都塞进一个 JSON 字段。

## 安装器与运行时加载：本地优先、注册表回退、固定入口符号

`epackage/source/epackage.asm` 给出了 EEXE loader 的可验证顺序；它不解析工程，也不搜索任意 DLL，而是只尝试核心运行库的两个固定位置。

```text
EEXE_Loader
  → GetAppPath()
  → 拼接当前程序目录/krnln.fnr
  → LoadLibrary
      ├─ 成功：继续
      └─ 失败：读取 HKCU\\Software\\FlySky\\E\\Install\\Path
                → 规范化末尾反斜杠
                → 拼接安装目录/krnln.fne
                → LoadLibrary
                    ├─ 失败：MessageBox 错误并 ExitProcess(-1)
                    └─ 成功：继续
  → GetProcAddress("GetNewSock")
  → 调用 GetNewSock(ITL_RUN_APP=1000)
  → 返回入口地址
  → 使用固定偏移修正入口并调用
  → ExitProcess(0)
```

这条链说明运行制品启动快的一个原因是：入口只需一次固定库定位、一次符号查找和一次跳转，复杂 IDE 元数据不参与运行时。另一方面，加载依赖安装注册表，离线复制整个目录并不等价于可运行部署。

### setup 制品暴露的安装资产

对归档中 `setup.exe` 的静态字符串可直接确认以下安装资产/兼容边界：`krnln.fnr`、`krnln.fne`、`setup.dll`、`uninstall.ini`、`uninstall.exe`、开始菜单 `.lnk`、`InstallDir/LinkFileName`、`regocx`、`TypeLib/OCX` 相关注册入口，以及 `Software\\Microsoft\\Windows\\CurrentVersion\\Uninstall` 卸载键。字符串证据只能证明存在这些分支和资源名，不能证明每个分支在所有版本都执行。

```text
安装器
  → 选择 InstallDir
  → 复制核心库、支持库、setup.dll 和帮助/代码/表单资源
  → 可选注册 OCX/TypeLib
  → 写入 HKCU\\Software\\FlySky\\E\\Install\\Path
  → 写入卸载信息和快捷方式

卸载器
  → 读取 uninstall.ini
  → 删除已登记文件/快捷方式/注册信息
  → 保留用户工程与未登记外部资源（除非明确勾选）
```

新平台应把安装动作记录为可回滚事务：每个文件、注册项、快捷方式和外部组件都登记 owner、版本、摘要和卸载策略；禁止用“扫描目录后全删”代替清单驱动卸载。

## 版本兼容的实际规则：添加优先、隐藏代替删除、格式号阻断误装

SDK 文档直接给出三条升级约束：

```text
库格式号变化
  → LIB_FORMAT_VER 不匹配
  → 宿主拒绝装载，避免同名库被错误解释

正式版本升级
  → GUID 保持不变
  → 主/次版本按兼容策略递增
  → 构建号顺序递增，用于区分修复构建

接口演进
  → 优先追加命令/属性/事件/元素
  → 已废弃项保留索引和类型
  → 使用 *_IS_HIDED 标记隐藏
  → 不重排旧索引、不删除旧 ABI
```

这与现代平台的不可变契约相符：能力 id、字段号和事件号一旦发布就不可复用；新版本只能追加并声明最低宿主/运行核心版本。对于不兼容变更，发布全新契约 id，而不是让同一 id 在不同版本解释成另一种数据。

## 本轮证据索引与可信度边界

```text

直接实现顺序证据
```

### `.ec` 与 `.fd1` 同头异义

```text
CNWTEPRG + 版本/类型字段
  ├─ .ec：模块接口、命令/类型、资源和实现关联；大小约 2 KiB 至 8 MiB
  └─ .fd1：项目管理器/历史快照，可能嵌入窗体、图片、音频或模块
```

跨样本公共前缀只能证明格式家族；`.ec` 在偏移 12、14 等处存在多种取值组合，不能把它们硬编码成一个“长度字段”。读取器应先验证公共头，再按版本分支解析，未知字段保留原始字节。

### `.epk` 目录和段名候选

两个样本在约 `0x20` 后均出现小端整数目录，`0x50` 附近可复核 `krnln`、32 位十六进制摘要和段名：

```text
epk
  ├─ 保留/版本头（一个样本全零，另一个以 57 4a 开始）
  ├─ 目录候选：0x93、1、3、若干偏移和长度
  ├─ 依赖记录：krnln + 摘要 + 版本/说明
  ├─ 段名候选：const / form / help / code / export
  └─ 段载荷：按目录偏移读取
```

目录字段宽度和校验算法尚未由 SDK 直接确认，因此只能标为候选。安全流程必须检查 `offset + size <= file_size`、整数溢出、段重叠和未知段保留；任何边界失败都拒绝装载，不尝试“修正偏移”。

### `.e8` 键矩阵与装配顺序

```text
[settings] source = ...       # 可重复；.e/.ec/.txt
[AppSettings]
  type = WinEXE | WinConsoleEXE | WinDLL | WinECom | LinuxConsoleELF | LinuxECom
  name / explain / author / ZipCode / address / photo / fax / email
  HomePage / copyright / MajorVersion / MinorVersion / BuildNO1 / BuildNO2
  plugins / EnableExportPublicMethod / icon / OutputFileName
[user_consts]
  中文常量名 = 数值 | [日期] | "文本" | true/false
```

```text
读取 .e8 所在目录
  → 按 source 出现顺序解析相对路径
  → 读取 .e/.ec/.txt
  → 任一 .ec 存在：合并前清除 .e 的原模块引用
  → 重复子程序进入冲突诊断
  → 应用 user_consts 覆盖
  → 按 AppSettings 生成目标制品
```

`user_consts` 是构建时覆盖，不应直接改写源文件；未知键应保留以支持版本前向兼容。

### `.edb/.edt` 配套证据

```text
WEDB 00 00 01 00
  ├─ 后续含表/数据库标识和计数/页目录候选
  └─ 记录区可能编码或压缩
WEDT 00 00 01 00
  ├─ 同样的版本前缀
  ├─ 常为 512 字节整数倍
  └─ 与同名 .edb 共享标识时表现出配套关系
```

样本 `员工信息.edb` 与 `员工信息.edt` 共享相同的 8 字节标识尾部，说明配套关系有证据；同时存在 `WCDB` 变体。因此导入器应先提供只读探针（魔数、版本、页大小候选、摘要），不要未经确认写入未知页结构。

### `.npk` 文本协议

```text
@@ <分类/对象描述>
##1 <原始名称> = <易语言显示名称>
##0 <原始名称>
```

`##1` 是翻译/别名，`##0` 是原名或隐藏记录。它处在 COM/OCX 类型库到 IDE 中文命令/属性/事件的映射层，真实实现仍由 OCX/DLL/注册表提供。

### `.run` 装载门槛

五个样本均为 PE，不是脚本或配置。装载流程应为：

```text
MZ/PE → 位数/机器架构 → 节表边界 → 导出表
      → xxx_LoadLibrary / xxx_FreeLibrary / xxx_GetProcAddress（若存在）
      → 依赖 DLL、摘要/签名 → READY
```

扩展名绝不能直接触发 `LoadLibrary`；导出缺失、架构不符、依赖不可解析或摘要不匹配必须拒绝。

### 复核命令

```bash
7z l -slt ~/Downloads/e.7z
7z e ~/Downloads/e.7z -o/tmp/eformats-review -y <明确的相对路径>
xxd -g1 -l 160 /tmp/eformats-review/<样本>
file /tmp/eformats-review/<样本>
strings /tmp/eformats-review/<样本>
```

推荐先用文件表计数，再按魔数分流；不要对 519 MiB 固体归档执行无边界全量解压。以上证据支持格式家族、段名和装载边界，不足以证明官方私有缓存命中算法或授权内部校验。
