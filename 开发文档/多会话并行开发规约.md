# 系统工程平台 · 多会话并行开发规约

> 目的：多个会话（人 + 多个智能体）在**同一个仓库、同一套集成环境**里同时开发时，不抢同一个文件、不互相卡死、不覆盖彼此成果。
> 方式沿用本平台惯例：上方文本流程图，下方详细条目。
> 事实以实际代码和正式能力索引为准；本文只写"怎么协调"，不写"平台有什么"。

本文只引用**本仓 8766 管理端（MCP）真实注册的 46 个工具**。本仓相关可用的：

- `file_operation` —— 本仓的写盘工具叫 `apply_file_patch`（**不是** `file_operation`，参数表也不同：走"旧文本/新文本 + 预期文件摘要"，不做整文件覆盖，见第五节第 4/5 行）；
- ~~`tool_job_submit` —— 本仓**无后台作业能力**~~ —— **已不成立（2026-09-12 起本仓已有）**：`tool_job_submit` / `tool_job_query` / `tool_job_cancel`（中文名 提交作业/查询作业/取消作业）已在 8766 上线，见第五节第 6 行；

另有一个**易混点**：能力 `文件系统支持库.文本补丁.应用精确替换`（支持库）**确实存在**，且带"预期文件摘要（整文件 SHA256，乐观锁）"参数。但它是**支持库能力**，当前**未暴露为 MCP 工具**（45 个工具里没有动态能力执行入口）——所以它是"能力在、通道缺"，agent 现在没法用它来强制写前校验。详见第五节。

## 一、总览流程图（认领式开工）

```text
【会话开工】
  │
  ├─ 第 0 步　判断工作性质 ─────────────────────────────
  │    ├─ 只读类（探索 / 审计 / 找落点 / 只跑查询）
  │    │     → 不认领任何文件 → 天然无冲突
  │    │     → 干完把发现写进「旁路问题」清单，交给写者批次
  │    │
  │    └─ 写入类（改源码 / 契约 / 产物 / 测试）
  │          → 进入认领
  │
  ├─ 第 1 步　认领（原子，全成功才开工）──────────────────
  │    开工(任务, 修改路径=[...])   ← 协议名 development_start
  │      → 对每个路径做「原子插入」文件租约(路径, 所有者, 心跳)
  │      → 复用现成 占用租约 表（键 = "文件::<相对路径>"，领域 = "文件"）
  │      ├─ 全部插入成功 ─────────────→ 开工，拿到租约id
  │      └─ 任一插入失败（已被占）───→ 拒绝开工
  │            回报：占用者 + 占用开始时间
  │            三条出路（不许硬闯）：
  │              ① 换活：先做别的文件不重叠的工作包
  │              ② 等：对方收口后再来（不建议，会空转）
  │              ③ 记录：写进「旁路问题_待下一批.md」，下一批做
  │
  ├─ 第 2 步　写入（本仓暂无 MCP 写入通道，见第五节）──────
  │    现状：写入由编辑器直接落盘，不走管理端
  │      → 文件级占用只能"开工处挡门口"，挡不住绕过者
  │      → 强制写前校验须先给本仓补写入通道（待建）
  │
  ├─ 第 3 步　心跳与释放 ─────────────────────────────
  │    长任务进行中 → 续租（刷新心跳）
  │    收口 / 提交后 → 释放占用（写明释放证据）
  │    会话崩溃 / 断线 → 300 秒内无心跳 → 自动过期回收，不死锁
  │
  └─ 第 4 步　共享资源避让（与文件无关的另一类冲突）────────
       8766 管理端：单进程共享 → **长工具走后台作业**（`tool_job_submit` 提交即返回，不再堵别的会话）；
       40007 网关：有长任务在跑时，禁止重启
       数据库：     只读查询随便；建表 / 迁移要独占，不能并发
       编译产物：   同一时刻只许一个会话编译
       派生产物：   只重算自己那一包；父级聚合摘要等最后收口者统一重算
```

## 二、为什么"复制一份"走不通，以及第三条路

华哥点出的两条路，各有死穴：

| 做法 | 死穴 |
|------|------|
| 复制一份（工作树 / 克隆）到别处开发 | **没有集成环境**。平台是"网关 40007 + 管理端 8766 + 数据库 + 编译产物"一体的，副本里的源码 import 是全的，但跑起来的服务仍然只认主目录 —— 验证根本没法在副本里做。改完还是要合回主仓，合并那一下照样冲突。 |
| 不复制，多会话直接改主仓 | **抢同一个文件**。A 读了旧内容，B 改了，A 再写回去 → A 把 B 的改动覆盖掉，且常常无声无息。 |

> **注：本仓确实有 `workspace`（隔离 Git worktree）工具**，但它解决的是**单人改动的隔离与最后合并**（分支 `codex/任务-{标识}`），**不解决**上面两个死穴：它仍是同一个 `.git`，且跑起来的服务与数据库仍指向主目录，副本里做不了真实集成验证；合并那一步冲突依旧。

**第三条路：同仓 + 分区认领 + 写前校验。**

理由很直接：文件在 Git 层面本来就能分开提交，两个会话改**不同文件**永远不冲突。真正会出事的只有一种情况 —— **同一文件、同一时刻、两个写者**。所以不需要隔离出一整套环境，只需要保证：

> 同一个文件，同一时刻，只允许一个会话持有写入权；抢不到就立刻让路，而不是写到一半才发现。

这就是本规约的全部核心。下面三套机制分别防三种不同的事故。

## 三、三套机制（详细）

### 机制一：文件租约（防"同时写"）

平台**已经有**一套完全正确的占用机制，目前只挂在"能力级"上（`平台控制面/能力目录/服务.py` 的 `占用租约` 表 + 活跃唯一索引）。把它**下沉到文件级**，**复用同一张表、同一套动作，零建表、零迁移**：

- **不用新建表**：`占用租约` 表本来就有 `能力id`（主键键位）、`领域`、`所有者`、`任务`、`心跳`、`过期时间`、`状态`、`释放证据` 列，唯一索引是 `ON 占用租约(能力id) WHERE 状态='活跃'`。把文件当"租约主体"塞进同一张表即可：

  ```
  key  = "文件::<仓库相对路径>"     ← 写进 能力id 列
  领域 = "文件"                      ← 与真实能力区分
  ```

- **为什么用唯一索引，而不是"先查再写"**：先查再写中间有一个时间窗，两个会话可能同时查到"没人占"，然后双双写入。唯一索引把判断和占用合成一个原子动作，数据库自己保证只有一个能成。
- **复用现成四动作**：`申请占用` / `续租` / `释放占用` / `回收过期占用`（`能力目录/服务.py`）**原样复用**，字段风格一致。
- **粒度到文件，不到包**：包太大（一个支持库几十个文件），按包认领会把并行度压死。按文件认领，两个会话改同一包的不同文件仍然并行无阻。
- **能力级互不干扰**：真实能力租约的 `能力id` 不会以 `文件::` 开头，文件租约查 `状态='活跃' AND 能力id LIKE '文件::%'` 即可隔离，不会互相污染。

### 机制二：写前摘要校验（防"先后写"）—— 本仓通道未建

光有认领还不够。还有一种事故：

> A 会话读了文件（登记了快照摘要），提交、收工、释放了租约；B 会话基于**它自己更早读到的旧内容**来改，此时没人占着这个文件，B 照样能写 —— 就把 A 的改动盖掉了。

**本仓的现实约束**：本仓**没有** `file_operation` 这类"编辑文件"的 MCP 工具 —— 写入由编辑器直接落盘，不经过管理端。所以**机制的"零件"有、通道没有**：

- 零件在：能力 `文件系统支持库.文本补丁.应用精确替换` 已实现"预期文件摘要（整文件 SHA256，乐观锁）"，摘要对不上即拒绝；
- 通道缺：该能力**未暴露为 MCP 工具**，agent 走不了管理端调用它。

因此在通道补齐之前，机制二只能靠**人工约定**兜底（读过内容、写前重读确认），**不能声称"已强制"**。强制化的前置改动见第五节。

### 机制三：心跳与过期回收（防"锁死"）

- 会话跑长任务时定期续租，租约不过期。
- 会话崩溃、断线、被强杀 —— 300 秒内没心跳，别的会话（或定时回收）把租约置为"已过期"，立刻可被重新认领。
- 这一条直接复用现成的 `回收过期占用`，因此**不会出现"锁死了要人工清库"**的局面。

## 七、冲突处置规程（撞上了怎么办）

按冲突的层级分三档处理，**不许硬闯，不许强改别人的文件**：

条目 1：**文件级冲突**（目标文件被活跃租约占着）
   → 不做。记入旁路清单，换下一个不重叠的工作包。这是绝大多数情况。

条目 2：**能力级冲突**（两个会话都声称要新建同一个能力）
   → 走现成的 `claim_capability`，唯一索引保证只有一个能成；抢不到的一方回报"能力已被占用"，改走 `reuse_search` 或换需求。

条目 3：**语义级冲突**（两方改的是**不同文件**，但动的是同一处逻辑）
   → 这类工具挡不住，靠两道人工兜底：
     - 收口时的定向验证（改的路径必须跑对应测试，否则不予收口）；
