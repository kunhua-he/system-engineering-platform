## 2. 语义撞车清单

这些不是“同 id”重复，但会让调用方绕过唯一原子能力。处理原则是“支持库保留原子动作，模块只编排并返回流程结果”；模块不得再注册一个同义原子能力。

边界补充：模块不是直接 import 支持库，而是通过 [中间件网关契约](../../中间件网关契约.md) 的 API 调用。当前源码里 `获取能力调用器()` 是内部客户端形态，只有它最终落到网关 HTTP 请求、被动发现、状态机和租约后，才算满足跨区域契约；进程内注册表不能作为模块的跨区事实源。

| 状态 | 模块公开能力 | 已存在的原子支持库能力 | 处理动作 |
| --- | --- | --- | --- |
| 待迁移 | `模块库/文件管理/包声明.json:48,152` 的读取/写入/删除/复制/移动/文件头 | `支持库/后端/文件系统/包声明.json` 同名能力 | 删除模块原子公开条目；模块只保留“批量文件整理/带回滚的文件流程”等组合能力，通过能力调用器调用文件系统。
| 待迁移 | `模块库/图像处理/包声明.json:144` 等 EXIF、缩放、重编码、哈希、透明合成 | `支持库/适配层/Pillow提供者/包声明.json` | Pillow 是 Provider；图像原子能力的唯一 owner 应是图像支持库契约，模块仅保留“分析图像/批量处理/产物清单”等流程。
| 待迁移 | `模块库/媒体处理/包声明.json:44,92,129` 探测、转码、抽帧 | `支持库/适配层/FFmpeg提供者/包声明.json` | FFmpeg 原子能力唯一化；媒体模块只保留媒体处理流程和状态机。
| 待迁移 | `模块库/媒体转写/包声明.json` 的转写/模型探针 | `支持库/适配层/MLXWhisper提供者/包声明.json` | 统一为 `转写.*` 原子契约；模块只做“媒体→音频→转写→产物”流程，可替换 Provider。
| 待迁移 | `模块库/文档生成/包声明.json` 的生成 PDF/办公文档 | reportlab、python-docx、python-pptx、openpyxl Provider | 生成能力按文档类型归入后端支持库；模块只编排模板、批量生成和交付。
| 待迁移 | `模块库/自修复工具/包声明.json` 的 Git 当前提交等 | `支持库/适配层/Git提供者/包声明.json` | Git 操作全部由 Git 支持库提供；自修复模块保留诊断→补丁→验证→回滚状态机。

数据库 Provider 的 `连接/查询/事务执行/关闭` 也存在同名多实现（psycopg、psycopg2、pg8000）。这不是重复能力 id，而是多 Provider 实现；必须先冻结一个数据库抽象契约，再由运行核心按配置选择 Provider，禁止把驱动名暴露为能力 id。用户要求的命令名应收口为 `数据库.连接`、`数据库.执行SQL`、`数据库.事务`、`数据库.断开`，不保留“查询”这一分叉命令。

## 3. 当前缺口（不能冒充已实现）

- MySQL 没有正式支持库；目前出现的 `pymysql` 只能算适配意向，不能计入可用能力。
- SQLite/PostgreSQL 仍有平台控制面旁路实现，未经过正式支持库、唯一注册表和统一结果契约。
- 本地 LLM Provider 已从工作树删除；后续云端 LLM 重新按统一协议立项，不把未配置 Provider 计入能力目录。
- 支持库声明仍混用 `布尔/数字/任意` 等旧类型；必须先由核心类型词典迁移为 `逻辑型/整数型/双精度数型/字典型/资源引用型` 等正式名称。

## 4. 假绿判定：四层证据，缺一不可

同一能力必须同时通过以下四类验证；任何一类没有执行、被缓存跳过、只验证导入或只验证返回 `成功=True`，状态为“未验证/阻断”，不能算绿。

| 层 | 验证方式 | 必须证明的事实 | 当前证据/问题 |
| --- | --- | --- | --- |
| A 静态契约 | 契约编译、类型/参数/返回、声明=注册=搜索、重复 owner 扫描 | 只有一个 owner，且调用面闭合 | 3 个精确重复已实证；当前阻断 |
| B 反向破坏 | 删除声明、注册、实现、依赖锁、入口后重跑门禁 | 缺任何一项都非零退出；不能靠缓存/skip 通过 | 作为 WP-11 必做；当前尚未形成本轮证据 |
| C 真实确定性返回 | 正常值、非法值、边界、底层失败；核对返回值/错误码/副作用 | 不是只看导入或 `成功=True`，失败必须传播 | 模块仍有吞失败风险，见底座升级方案 §2 |
| D 运行与资源 | 超时、取消、崩溃、重复关闭；线程/进程/临时目录/句柄/证据账本归零 | 运行治理真实闭环 | 任务同步异常被吞、关闭未等待同步线程、无探针健康仍可能成功 |

缓存规则还必须单独满足：缓存条目必须含代码摘要、测试数、结构版本、环境摘要和时间；旧条目缺环境摘要必须失效。现已在 `测试中心/运行测试.py` 收紧为缺失即阻断，并补回归测试。

本轮针对性验证实际结果：`测试_任务进程池有界.py` 6/6、`测试_发布门禁收敛.py` 6/6；`测试_冷启动反向门禁.py` 13 项中仅 11 项通过，基线阶段的“结构”和“完整性摘要”失败，故本轮退出码为 1。该结果进一步证明不能把已有定向测试汇总成全绿；应先解释当前工作树与反向门禁基线的差异，再进入迁移。

## 5. 开工顺序（具体落点）

1. **WP-DUP-01 唯一 owner 对账**：以 `P0-能力重复扫描.json` 为输入，新增“能力 id→唯一支持库→Provider 集合→模块组合能力”清单；3 个精确重复先解除，模块同义原子条目标记迁移，不删除实现文件。
2. **WP-DUP-02 契约收口**：补齐 `能力定义.json` 的参数类型、返回结构、错误码、状态机、资源预算和验证命令；禁止 Provider 自带第二份公开契约。
3. **WP-GREEN-01 门禁修复**：旧缓存缺环境摘要直接失效；负退出码、未执行探针、证据写入失败、未关闭同步线程均非零；修复后新增回归测试再跑常规门禁。
4. **WP-GREEN-02 多证据验证器**：为每个能力生成 A/B/C/D 四项证据，报告必须显示“执行/缓存复用/未验证”状态；任何未验证不得汇总为成功。
5. **WP-MIG-01 原子支持库迁移**：先迁文件系统、图像、媒体、文档，再迁数据库/LLM/ASR；每次迁移只保留一个公开能力 id，模块流程另行验收。

## 6. 开工判定

现在**不能**宣称“底座已审计干净”或“可以直接开发”。可以开始的是上述 WP-DUP-01 和 WP-GREEN-01 两个阻断修复工作包；它们完成并通过四层证据后，才允许迁移和新增支持库。唯一能力规则固定为：一个原子能力一个能力 id、一个公开契约、一个支持库 owner；多个驱动/服务商只能是该 owner 的 Provider，模块不拥有原子能力。
