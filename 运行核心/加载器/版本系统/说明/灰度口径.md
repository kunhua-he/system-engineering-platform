## 一句话口径

**`灰度比例` 参数当前只被「记录」，不被「执行」。**
它写进 `热切换管理器.灰度比例表`（键 = 能力id，值 = 比例），**全仓没有任何读取者**，
路由侧也**不看它**——所以传 `0.1` 与传 `1.0` 的实际效果**完全一样：100% 全量切换**。

**本平台未实现按比例分流。** 这是**如实口径**，不是待修的 bug（见下「为什么不实现」）。

## ① `灰度比例表` 的当前语义 = 记录调用方意图

| 项 | 实况 |
| --- | --- |
| 定义 | `热切换管理器.灰度比例表: dict[str, float]`，位于 `运行核心/加载器/版本系统/热切换.py` |
| 键 / 值 | 键 = **能力id**（不是 `能力id@版本`）；值 = 调用方本次传入的比例（`0.0`～`1.0`） |
| 写入点 | 两处，同一写入口径：`热切换(...)` 第 7 步、`真实热切换(...)` 第 6 步 |
| 读取点 | **零**。全仓 `rg '灰度比例表'` 只命中 `热切换.py` 自身的 1 处声明 + 2 处写入（+ 注释） |
| 生命周期 | **进程内**，随 `热切换管理器` 实例存活；不落盘、不进运行库、不跨重启 |
| 默认值 | 形参默认 `灰度比例: float = 1.0`；调用方不传即等于「全量」 |

另有一处**持久化落点**（同目录 `灰度指标.py` 的 `灰度指标库`）：`运行库` 的 `灰度状态` 域有
`灰度比例` 列，只能经 `灰度指标库.设置灰度比例(能力id, 版本, 比例)` 写入。
它的接线状态同样是**全仓无生产调用方**（`rg '设置灰度比例'` 只命中
`测试中心/运行核心/测试_灰度指标入库.py`），且**`热切换` 与 `真实热切换` 都不会写它**——
两条热切换路径只写进程内的 `灰度比例表`。
`灰度指标库.聚合` 会把该列读进观测视图（`指标.当前灰度比例`），但那是**观察口径，不参与路由**。

> 结论：比例有两个可能的落点，**当前都没有接上路由**。本轮**不合并、不新增**任何落点，
> 只把这件事写清楚（合并口径属「另开需求」）。

## ② `调用路由` 的真实路由判据（唯一路由口子）

```python
def 调用路由(self, 能力id: str, 参数: dict | None = None) -> Any:
    """经当前路由调用能力（新进程优先；无进程回退旧逻辑）。"""
    进程 = self.路由表.get(能力id)
    if 进程 is not None and 进程.状态 == "运行中":
        return 进程.调用(能力id="进程.最小操作", 参数=参数 or {})
    return None
```

判据**只有一条**：**「该能力在 `路由表` 里绑定的提供者进程是否存在、且状态为 `运行中`」**。

- **不看比例**：函数体里没有 `灰度比例表`、没有任何比例/随机/哈希/分桶。
- **不看版本**：`路由表` 是 `能力id → 单个进程`（不是 `能力id → {版本: 进程}`），一次只可能指向一个进程。
- **全量语义**：命中即**所有**调用都走该进程，漏命中即**所有**调用都返回 `None`（当前没有第二腿可回退）。
- `路由表` 的写入点：`真实热切换` 第 8 步 `self.路由表[能力id] = 新进程`；失败时 `_真实回滚` 把它恢复成旧进程。
  传统 `热切换` **根本不写 `路由表`**（它只写 `激活映射`）。

也就是说：**比例参数没有出口**——它进不了 `路由表`，也进不了 `调用路由`。

## ③ 未实现按比例分流：为什么不实现，要真分流该落在哪

**不实现（本轮裁决）**：本平台的调用链是「**单一网关 + 唯一调用腿**」，
`调用路由` 就是这条腿。按比例分流会**新增一条腿**——即新增第二个调用入口/路由分支，
违反平台已定的「**都保留唯一一个口子**」。第 11 条 1 项要「缺能力先证不可替代」：
现阶段没有任何场景证明「同一能力的两个版本必须同时按比例承接流量」不可替代
（本平台是单机私有部署，非灰度发布平台），**不装**。

**要真分流，需另开需求**，且至少要一起解决下面四件事（**本轮一件都不做**）：

| 落点建议 | 为什么绕不过 |
| --- | --- |
| (1) 分流判据必须落在 `调用路由` **这一个口子**里 | 它是唯一路由口子；在别处再插一个分支就是第二条腿 |
| (2) `路由表` 需从「能力id → 单进程」改为「能力id → {版本: 进程}」 | 现在是单进程结构，物理上装不下两个版本；且 `真实热切换` 第 9/10 步在 `状态可迁移` 时会**优雅停止旧进程**——旧进程都没了，没有可分流对象 |
| (3) 需要一个**确定性分桶**判据（按请求id/调用方/用户哈希，而不是 `random`） | 否则同一调用方在两次调用之间会来回跳版本，观察数据不可解释 |
| (4) 比例要有**单一权威来源**与跨重启恢复口径 | 现在进程内 `灰度比例表` 与运行库 `灰度状态` 域两处都能表示比例，且都不参与路由；真分流时两处不一致＝静默偏差 |

## 为什么这样够了（不改造的理由）

灰度发布的**收益**是「新版本出错时只影响一部分流量」。本平台的**风险边界**是单机私有部署、
单一调用腿、热切换本身已具备「影子调用 + 最小调用 + 健康检查 + 观察期 + 自动回滚」
（失败即恢复旧激活映射/旧路由并留证据）。在这个边界内，比例分流带来的是**加一致性、加故障面**，
换来的收益在本平台边界外才有意义。

真正的缺陷是**过去这句话没写下来**：调用方读到「灰度运行（比例 10%）」，
自然会以为已经在按比例分流，于是把「10% 观察」当成风险控制手段——**实际是全量切换**。
**本轮收口的就是这一句**：文案与注释如实说明「比例被记录了，但没在分流」。
