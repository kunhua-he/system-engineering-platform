## 一、这个包是什么

**提供者层**的内部适配器（`AGENTS.md`「系统适配器豁免」名录件，原名 `配置读取`，目录名 2026-09-18 改）。

职责一句话：**把外部提供者配置读进来，按能力 id 取配置段。**

- 数据只来自 `支持库/适配层/提供者配置/提供者配置.json`；
- 对外只有两个符号：`读取提供者配置(配置目录=None)`、`获取能力配置(配置, 能力id)`；
- 文件缺失/目录缺失 → 返回 `{}`（提供者配置是**可选**输入，取不到由调用方走默认/降级，不在此处伪造）。

## 二、它**不做**什么（边界，防止再被当成第二套实现）

| 不做 | 那是谁的事 |
|---|---|
| 全仓统一配置加载（支持库默认→项目默认→环境→提供者→显式覆盖 五层合并） | `项目适配层/配置适配/配置合并.py` |
| 配置结构校验、未知项/类型错误报告、明文密钥检测 | `项目适配层/配置适配/配置校验.py` |
| 配置**来源追踪**（哪个键来自哪一层） | `项目适配层/配置适配/配置读取.py::配置读取结果.来源表` |
| 项目配置目录（`项目适配层/项目配置/*.json`）的读取与合并 | `项目适配层/配置适配/`（门面层） |
| 能力 id 路由与提供者选择 | `支持库/适配层/提供者注册表/`（注册表只**经本包**读配置数据） |

## 三、为什么不与 `项目适配层/配置适配/` 合并（定性依据）

**定性：合法门面层 / 提供者层分层，不是「同一件事两套实现」。**

判据（四条，均可现场复算）：

1. **依赖方向单向且无回环**：`支持库` 层只允许依赖 `公共契约`（`运行核心/依赖防火墙.py::允许依赖表`），
   `项目适配层` 层只允许依赖 `公共契约`/`运行核心`（同表）。**把本包并进 `项目适配层`，等于让
   `项目适配层` 反向依赖 `支持库` = 越层依赖，发布门禁直接判红**；反过来把门面层下沉进本包，
   会污染「适配层只做第三方边界翻译」的口径。合并需要先改分层口径，代价远大于收益。
2. **职责面不同**：本包是「读第三方/外部协议**一份** JSON + 按能力 id 取段」（写路径 = 提供者配置数据）；
   门面层是「读**项目**配置目录 + 五层合并 + 校验 + 来源追踪」（写路径 = 项目适配层注入）。
   双方都读 JSON，但**读的不是同一份数据、交付的不是同一件事**。
3. **包级能力面不交集**：本包 `__all__` = `读取提供者配置`/`获取能力配置`；门面包 `__all__` =
   `配置读取结果`/`读取JSON配置`/`读取配置目录`/`合并配置`/`解析环境配置`/`校验配置`/`配置校验结果`。
   两边**无同名公开符号**（这是 2026-09-18 收口的直接目标）。
4. **两边只有同名文件、没有同名公开入口**：收口前 `配置读取` 这个**目录名**与门面层
   `配置适配/配置读取.py` 撞名，是最容易让人误判「两套实现」的地方 —— 已由改名消除。

同类先例：`开发文档/方案/结构债处置方案_20260916.md` 的 D-6（`平台控制面/*.py` 唯一实现 + 同名包
门面）判定为**合法门面层与提供者层分层**，处置是「不动，只补注释级说明」。
