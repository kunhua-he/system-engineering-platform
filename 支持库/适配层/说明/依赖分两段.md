## 五、判定依据汇总

| 规则 | 口径 |
|---|---|
| 逐项类别 | 锁项 `来源` ∈ {外部应用, 系统工具} ⇒ 环境依赖；否则必须以 AST 现场 import 同名模块证实 ⇒ 第三方库（同一发行包拆成多个 pip 包时，锁内 `发行包` 同值的随附项由同发行包内已 import 证实的那一项互证 ⇒ 同为第三方库）；两者都不成立 ⇒ 判红（无法现场证实，不许猜） |
| 件级类别 | 任一锁项为 第三方库 ⇒ 第三方库；否则有 依赖锁.json ⇒ 环境依赖；无锁则按现场：有第三方 import ⇒ 第三方库，仅有子进程/可执行调用 ⇒ 环境依赖，都没有 ⇒ 无外部依赖 |
| 版本 | 只从各件 依赖锁.json 现场读；根下平铺 .py 内部件从 内部件依赖声明.json 读；读不到写 null 并在 需复核 登记，不编造 |
| 端口 | 先扫本件 listen/bind/serve 监听调用；再扫服务连接字面量（postgresql:// 等）⇒ 本件要连的远端服务在监听，端口取自 服务型环境依赖.json 的声明（不许写死在实现里） |
| 服务型环境依赖 | 现场出现 postgresql:// / postgres:// / mysql:// / redis:// / mongodb:// ⇒ 必须在 服务型环境依赖.json 里有该件条段，且六要素齐（版本/入口/端口/健康探针/启停/降级语义）；声明与现场任一侧单边存在即判红 |
| 内部件依赖 | 支持库/适配层/ 下的内部件（根下平铺 .py + 无包声明目录）不建 依赖锁.json / 包声明.json（AGENTS.md 系统适配器豁免结构要件）⇒ 依赖登记在 内部件依赖声明.json；现场有第三方 import 而声明里没有 ⇒ 判红 |
| 该建声明没建声明 | 内部件现场有外部依赖证据（第三方 import／子进程调用／外部命令查找）却既无 依赖锁.json 也不在 内部件依赖声明.json ⇒ 判红（决策记录 0033：有外部依赖应建锁；本仓内部件上「锁」的正确表达是这条声明） |
| 健康探针 | 由各包 包声明.json 的能力列表中派生（能力 id 含 检查提供者/检查可用/检查可用性/版本探针） |
| 启停语义 | 现场出现 --session/close/守护 调用 ⇒ 有常驻进程；否则一次性子进程，无需启停命令 |
| 降级语义 | 实现源码出现「提供者不可用」⇒ 缺失/失败即 fail-closed；未出现则如实标需复核 |
