## 项目维度（为什么补、语义是什么、老库怎么办）

**为什么补**：本库的表名从一开始就叫 `项目记忆`，但表里没有「项目」这一维 —— 所有项目的记忆
混在一个空间里，写入时无法标明归属、查询时无法按项目过滤。结果是「项目记忆」名不副实：
A 项目的智能体搜到的是 B 项目的记忆。这不是缺一个功能，是缺陷。

**语义**（一句话）：一条记忆最多归属一个项目，项目用文本名标识（如 `系统工程平台`）；
不写项目 = 未归属项目（`项目` 列为空串），语义等于「全局/公共记忆」。

**五个可选参数位，一个默认口径**：

| 能力 | 新增可选参数 | 默认值 | 不传时的行为 |
| --- | --- | --- | --- |
| 写入记忆 | 项目 | 空串 | 与补项目维度前逐字一致 |
| 追加记忆 | 项目 | 空串 | 同上 |
| 搜索记忆 | 项目 | 空串 | 搜索全部项目的记忆 |
| 最近记忆 | 项目 | 空串 | 返回全部项目的最近记忆 |
| 列出记忆 | 项目 | 空串 | 列出全部记忆 |

**向后兼容是硬要求**：五个参数全部可选、全部默认空串，空 = 不加任何 SQL 条件。
老调用方（不传项目）拿到的行集、排序、返回结构完全不变 —— 只有多出一个 `项目` 字段（值空串）。

**标识也要带项目（这是隔离的真正落点）**：`项目记忆` 的主键是 `标识`，`记忆向量` 同样以
`标识` 为主键。如果只加一列而不动标识，两个项目写入同名记忆会得到同一个标识，
`INSERT OR REPLACE` 直接互相覆盖 —— 那不是「各自的记忆空间」，是同一行被两个项目抢。
因此带项目写入时标识形如 `项目名--基础标识`（`基础标识` 仍是标题的规范化结果）：
- 同一项目内同名记忆仍然幂等覆盖（可重复写入，不产生副本）；
- 跨项目同名记忆各占一行，互不覆盖；
- 向量按标识各存各的，语义检索也不会串味。
不传项目时标识逐字等于旧的 `生成标识(标题)`，老库里的老标识一个都不动。

**老库自动迁移（不丢数据、不需人工干预、幂等）**：`项目记忆` 表补一列 `项目`
（`ALTER TABLE ... ADD COLUMN 项目 TEXT NOT NULL DEFAULT ''`）。SQLite 带默认值加列只改元数据、
不重写表，已存在的行自动取默认值空串（= 未归属项目），老记忆零丢失。`ADD COLUMN`
没有 `IF NOT EXISTS`，所以先用 `PRAGMA table_info` 探列，已有就跳过 —— 迁移写在连接工厂里，
每次打开库都会走，重复执行安全。同时建索引 `项目记忆_项目_时间(项目, 更新时间 DESC)`,
让「按项目查最近 N 条」走索引而不是全表扫。

## 仅关键词搜索（为什么要有、怎么算分）

**为什么**：用户要的高频动作是「查某项目的最近 N 条」「在某项目里搜个关键词」——
这是**结构化查询**，答案就在 SQLite 里。走默认的语义搜索要为每次查询付一次
「连接向量模型 → 生成嵌入 → 释放句柄」的调用（查询向量一次，加上没算过向量的记忆逐条补算），
代价与查询复杂度完全不成比例，而且模型不可用时还得退回关键词匹配。
`仅关键词=true` 把这条路掐断：**一次大模型调用都不发**，只做 SQL 过滤 + 字符串匹配。

**口径**：
- 匹配范围：`名称 + 正文 + 标签`，大小写不敏感（统一转小写后子串匹配）；
- 打分：命中词种类数 / 查询词总数（0~1），同分时按命中总次数、再按更新时间倒序（排序确定、可复现）；
- 返回结构不变：仍是 `{数量, 记忆列表}`，每条仍带 `分数` —— 调用方可以无缝切换两种模式，
  不需要分支处理不同的返回形状；
- 命中 0 分的行与默认模式一致，仍会按「返回条数」占位返回，调用方按 `分数 > 0` 自行过滤。

**它不是替代品**：默认模式（向量 + 关键词兜底）负责「意思相近但用词不同」的模糊召回；
`仅关键词` 负责「我就要这个字」的精确命中与零成本。两个模式并存，由调用方按意图挑。
