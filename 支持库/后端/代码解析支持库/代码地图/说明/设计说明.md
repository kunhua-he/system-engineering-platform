## 1. 这个库为什么存在

`codegraph_explore` 此前是**外部 CLI 子进程**（`~/.npm-global/bin/codegraph`，
Node v1.5.0，`codegraph explore <查询> --max-files 20`），由 `MCP工具箱/项目服务.py`
用 `subprocess` 拉起并把 **CLI 的文本输出**当返回值。

按华哥 2026-09-15 裁决（第 10 条 1 项、第 10 条 2 项、第 10 条 3 项、第 10 条 4 项、第 10 条 5 项「缺什么补什么」）：

- 外部 CLI 不是底座能力，**底座要直读它产出的代码地图（SQLite）**；
- 调用方不再依赖 Node 运行时与那层 CLI 的搜索实现；
- 外部 CLI 退场后，检索能力的**唯一权威**是底座原子能力。

## 2. 落点与理由（为什么在 `支持库/后端/代码解析支持库/代码地图/`）

- **职责归属**：代码地图是对「代码」的结构化索引，与同库的 `语法索引` 同级——两者都是
  「把代码变成结构化事实」，一个自己算（ast/tree-sitter 解析源码），一个直读已有索引。
  数据库连接支持库只管「通用 SQLite 读写」，不认识代码地图的表语义（nodes/edges/kind 取值），
  把表语义塞进去会把通用库变成第二个业务库。
- **不新增平级库**：单开「代码地图支持库」是与既有分层并列的第二条腿；代码地图读的是
  **代码索引文件**，属代码解析域，因此作为 `代码解析支持库` 的子包。（第 10 条 3 项：补进对应的那个库）
- **只依赖标准库**：`sqlite3` 是 Python 标准库，不新增第三方依赖；不写 依赖锁 第三方条目。
- **不落 `MCP工具箱`**：MCP 只是适配层（渲染文本、给 Agent 用），它消费本能力，
  不拥有能力。本次只改本库，MCP 侧接线由对应批次负责。

## 3. 管什么、不管什么

管：把代码地图 SQLite 的 `nodes` / `edges` 读成结构化事实。

- `查询节点`：按模式（名称子串/名称精确/限定名子串/路径子串/全文）检索节点，
  可按 节点种类/文件路径/语言 收窄，稳定排序，返回 命中数/已截断。
- `查询关系`：按方向（出边/入边/双向）与关系种类查某节点的关系事实。

不管（刻意留给调用方）：

- **不渲染文本**：CLI 那种「Exploration: X / Blast radius …」的报告是呈现层，属 MCP 适配层。
  底座只给结构化值，调用方自己排版。
- **不读源码**：代码地图只存 文件路径 + 起止行；取源码是文件系统能力的事，本库不拼源码、
  不做「相关文件摘要」。
- **不做相关性排名/爆炸半径评分**：CLI 的 minScore/遍历深度是它自己的启发式；底座不复制第二套评分。
- **不写库**：只读，绝不建表、不加索引、不写元数据、不做 VACUUM。
- **不认识项目目录语义**：目录白名单、角色范围过滤属调用方策略，能力只认参数。

## 5. 只读口径（为什么是 `mode=ro&immutable=1`）

代码地图是**别人的索引**，底座只能读、不能碰：

1. **不新增 `只读模式` 开关**：单一职责下只保留一种打开方式，避免调用方用错参数把
   索引目录写脏。若日后确需在索引目录建 side 文件的模式，应作为**新增参数**另行裁决。
2. **实测依据（2026-09-15）**：`codegraph.db` 是 WAL 库（`PRAGMA journal_mode = wal`）。
   用 `mode=ro` 打开会在 `.codegraph/` 目录里生成 `codegraph.db-shm`（32768 字节）与
   `codegraph.db-wal`（0 字节）——**等于向别人的索引目录写盘**；`immutable=1` 不建锁、
   不建 side 文件、零写入（现场已复原：目录只剩 `.gitignore`、`codegraph.db`、`daemon.log`）。
3. **不缓存连接、不驻留句柄**：每次调用新建只读连接、`finally` 关闭；本库无状态、
   无句柄、无生命周期资源，`.codegraph/` 目录与文件在调用前后逐字节不变。

## 6. 失败如何表达

| 场景 | 错误码 | 口径 |
|---|---|---|
| 缺必填 / 类型不符 / 模式或种类不认识 / 节点名未命中或命中多个 | `参数不合法` | 点名参数名与期望取值，fail-closed，不做兜底降级 |
| 代码地图路径不是文件 | `文件不存在` | 404 语义（网关已登记码） |
| SQLite 打不开、缺 `nodes`/`edges` 表、SQL 执行异常 | `查询失败` | 明确报出真实 SQLite 报错，不返回空列表冒充「没查到」 |

关键区别：**「查不到」不等于「查不了」**——命中为空是成功结果（`节点列表` 为空、`命中数` 0），
库里出问题是失败。旧 CLI 把「没匹配」和「用不了」都混成一句 `No relevant code found`，本库不做这种合并。

## 7. 已知限制（如实披露）

1. `immutable=1` 假定索引文件在读取期间不变。若外部 CLI 正在 sync 且 `-wal` 里有未合并的
   变更，本能力读到的是**主库快照**（可能少最新几条），或在极端撕裂页上明确报 `查询失败`。
   零写入与「读到未合并 WAL」不可兼得，本库选零写入；需要看到未合并 WAL 时，应由调用方
   先让索引进入静止态。
2. 旧 CLI 的探索**对本仓库的中文标识符无效**：`codegraph explore "网关核心"` 实测返回
   `No relevant code found`（`codegraph query "网关核心"` 却能命中 `运行核心/统一网关/网关核心.py:87`），
   即旧工具的关键词评分/分段口径覆盖不到纯中文查询。本库用 SQL `LIKE`/`=` 直接匹配 `nodes.name`，
   中文查询是**真实命中**（现场实测见交付报告），这正是要补底座能力的原因之一。
