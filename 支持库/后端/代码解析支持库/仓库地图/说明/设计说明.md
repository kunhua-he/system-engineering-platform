## 为什么解析一定要复用 语法索引

本包不写任何 `ast` / tree-sitter 调用：

- Python → `代码解析支持库.语法索引.解析Python语法`（ast）
- TS/Vue → `代码解析支持库.语法索引.解析脚本语法`（tree-sitter，不可用时正则降级）
- 批量分派 → `代码解析支持库.语法索引.批量解析语法`（保序，单文件失败隔离）

跨包只走对方**包级公开入口**（依赖防火墙：支持库仅限包级公开入口，`实现/` 一律拒绝）。

## 图模型

节点四类：`file`（文件）、`class`/`function`/`method`（符号）、`import`（导入）。

边三类，带权重（同一 `(起点, 终点, 种类)` 出现一次 `weight +1`）：

| 种类 | 方向 | 含义 |
|---|---|---|
| `contains` | 文件 → 符号 | 文件内定义 |
| `imports` | 文件 → 导入 | 文件引用了外部名字 |
| `calls` | 调用者符号（或文件）→ 被调符号 | 调用/引用关系 |

**不造幻影节点**：解析不到目标的调用直接丢弃。幻影节点会把 PageRank 质量引到不存在的符号上。

## 排名与预算

1. PageRank 在**节点**上算（权重参与），再把节点得分**汇到文件**（同一 `file_path` 求和）
   ——文件节点本身没有入边，直接排文件会把文件分排成接近 0。
2. 锚点作**个性化向量**（命中节点 ×10），无锚点 = 均匀分布。
3. 文件按 `(-得分, 路径)` 稳定排序，展平成渲染单元序列（文件头一单元、每条签名一单元），
   **二分最大可容纳前缀**。

### 为什么二分粒度是符号而不是文件

实测（2026-09-21，文件系统支持库仓）：按文件二分时，`token预算=200` 下排名第一的
`文本补丁/实现/文本补丁.py`（19 条签名）放不下，整张地图空掉，`收录文件数=0`；
改按符号二分后，同样预算能给出文件头 + 若干条签名，地图可用。

## 与 代码地图 的同构边界

`nodes` 列与 `代码地图` 逐字一致；`edges` 列一致且**多一列 `weight`**。
额外列不改变既有 `SELECT` 列表，故 `代码地图.查询节点` / `查询关系` 对本库仍可用。

## 已知边界

- 符号只收集模块级与类体直接子节点（`语法索引` 的口径），函数体内嵌套定义不入图。
- 跨文件调用解析靠**名字末段**匹配（无类型推断），同名符号取首个，可能误连。
- 默认库文件名取仓根目录名，同名仓会互相覆盖；多仓共存请显式传 `库文件`。
- `networkx` 缺失时自动退化为自带幂迭代，排名可用但不保证与 networkx 逐位相同。
