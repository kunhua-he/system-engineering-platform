## 并发容量与吞吐基线（2026-09-16 本机实测）

> **实测容量特性**，用于估算批量任务的并发上限与完成时间；换机器需重新实测。

| 项 | 实测值 | 说明 |
|---|---|---|
| **并发上限（VideoToolbox 会话数）** | **20 路** | 23 路（含 2 个孤儿）→ 380+ 次失败；**32 路 → 399+ 次失败**；均为 `ffmpeg 执行失败：外部命令异常退出（退出码 187）: return code -22 (Invalid argument)`。**关键：32 路时 CPU 仅 23%、`GPU Device Utilization` 仅 54% 仍报错** → 限制来自**硬件编码器的并发会话数量**（约 20 个），**不是算力过载**。CPU/GPU 有空闲 ≠ 能提并发 |
| 20 路吞吐 | **141.4 GB/h**（26.4 分钟采样，按源字节计） | 存档档参数：`hevc_videotoolbox` + 目标码率 = 源×0.35 夹 [500k, 900k] + `-r 15` + `-c:a copy` |
| 单路 CPU 占用 | 约 43%（20 路合计约 853%） | 硬编主要吃媒体引擎，CPU 占用不高 |
| 压缩率 | 63%–90%（源码率越高省得越多） | 源 1–2 Mbps 省 60%+；源 6–8 Mbps 省 85%+ |
| 并发边际收益 | 6→14 路仅快 27% | 说明 14 路时媒体引擎已接近饱和 |

**实践结论**：

1. 批量转码并发定 **20 路**；多任务共享该额度时用 16+4 之类的划分，**总和不要超过 20**——超过的部分会被网关限流拒绝（默认单维度并发 20），或因 **VideoToolbox 会话数超限**触发 `-22` 失败。**不要用 CPU/GPU 占用率判断"还有余量"**：实测 32 路时 CPU 23%、GPU 54% 仍在报错，因为硬编走专用媒体引擎、不走 CPU，空闲的 CPU 核帮不上硬编。（若要用起空闲 CPU，只能另配软编（libx265）并行，但软编仅 1–2x 实时、远慢于硬编 5–6x，且码率控制口径不同，收益有限。）
2. 估算完成时间用 **141.4 GB/h**。
3. **网关重启会在途 ffmpeg 变孤儿**（PPID=1 被 launchd 收养）继续占用媒体引擎，使实际并发超过配置值并触发 `-22`；发现 `ps` 里 ffmpeg 数多于配置时，先查孤儿（`ps ax -o pid,ppid,command | grep ffmpeg | awk '$2==1'`）。按状态机登记归属回收的修法见 `开发文档/未完成事项.md`。
