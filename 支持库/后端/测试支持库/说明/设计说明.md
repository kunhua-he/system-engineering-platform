# 测试支持库 设计说明（设计权威）

> 本文是该库的**设计哲学与边界权威**：它为什么这样切、管什么、不管什么、失败如何表达。
> 调用口径——能力、参数、返回结构、错误码与调用示例——以同目录 `使用说明.md` 为准（由能力契约生成）。
> 两份说明都计入包指纹，任何改动都要升包版本。

- 包id：支持库.后端.测试支持库
- 版本：1.0.0
- 类型：支持库
- 依赖：无（只用 Python 标准库；不 import 任何支持库/提供者/第三方）

## 一、为什么补这三条（第 32–36 条归因）

- **先判定是不是真的缺（第 32 条）**：538 能力全表按「验证计划 / 验证命令白名单 / 验证结果判定 / 零测试 / 未解释跳过」检索 **0 命中**——底座里确实没有这三条原子能力。
- **缺口的真实形态**：这三件事此前**只在平台 MCP 工具箱里存在**（`MCP工具箱/项目服务.py` 暴露的 `verification_plan` / `validate_verification_command` / `judge_verification_result`，实现落在 `MCP工具箱/验证门禁.py`），技能库又照抄了一份私有实现（`技能库/技能/验证编排/scripts/验证编排.py`），开发工具另有一份**静态**跳过检查（`开发工具/测试体系门禁实现/跳过检查.py`）。
  后果：同一份白名单与判定口径散在 3 处，任一处改口径另两处不动就产生漂移；技能脚本注释自己写着「待支持库原子能力就位后改为一处调用」——本次就是把这句兑现。
- **补成原子能力（第 33 条）**：三条各自单一职责、参数一眼能懂，不带业务语义、不带项目特例。
- **补进对应的那个库（第 34 条）**：这三条都属于「测试与验证」职责，且不依赖任何第三方与外部进程，因此新建 `支持库/后端/测试支持库` 承载，而不是塞进 `系统核心支持库`（进程执行）或 `文件系统支持库`（路径与文件）。
- **全套齐活（第 35 条）**：包声明 + 能力契约 + 能力定义 + 能力数据 + 包级入口注册 + 使用说明 + 设计说明 + 验证场景引用 + 正向真实场景 + 完整性摘要 + 权限/配置/依赖契约 + 资源预算 + 复用决策，逐项落盘。
- **真实验收（第 36 条）**：经 `后端核心` 装配后真实调用，回报真实返回值（见第六节验收记录）。

## 二、能力清单

| 能力id | 名称 | 版本 | 返回 | 说明 |
| --- | --- | --- | --- | --- |
| 测试支持库.验证计划 | 验证计划 | 1.0.0 | 结果型 | 只读计算该跑哪些精确 unittest 模块入口与命令；绝不执行 |
| 测试支持库.验证命令白名单 | 验证命令白名单 | 1.0.0 | 结果型 | 纯函数准入判定：三种受控形态，其余一律拒绝并给错误码 |

## 三、边界：管什么、不管什么

**管**：

1. 计划计算——由目标路径算出精确 unittest 模块入口/命令，或 HTML 黑盒 + 唯一发布入口命令。
2. 命令准入——判定命令是否属于本仓允许的验证命令集合。
3. 结果判定——按真实执行输出判定 通过/阻断 并给理由与检出项。

**不管（一律留给已有权威，不造第二条腿）**：

- **不执行命令**：真实执行归 `系统核心支持库.进程管理`（沙箱执行命令）；本包不起子进程、不做 shell 拼接、不写盘。
- **不写验证账本**：证据落账归 MCP `verify_and_record` 与平台控制面证据账本。
- **不做反馈门禁**：开工反馈门禁归 `MCP工具箱/使用反馈.py`。
- **不判断「该不该跑全量」**：级别由调用方显式传入，本包只按级别给命令。
- **不做静态源码审计**：AST 级「跳过无理由」检查仍归 `开发工具/测试体系门禁实现/跳过检查.py`（它扫的是源码，本包判的是**运行输出**，两者互补而非替代，见第五节）。

## 四、第 37 条：「现状做法 ↔ 候选架构」对比与结论

同一把尺：**快 = 实测耗时/步骤数；稳 = 失败面/可回退/边界明确**。

| 维度 | 现状做法（三份私有实现） | 候选架构（收口成本包一条原子能力） | 结论 |
| --- | --- | --- | --- |
| 实现处数 | 白名单 1 份（`MCP工具箱/验证门禁.py:119`）+ 1 份照抄（`技能库/技能/验证编排/scripts/验证编排.py:115`）；判定 2 份（`:178` / `:164`）；静态跳过 1 份（`开发工具/测试体系门禁实现/跳过检查.py:67`、`:106`）；计划 1 份（`MCP工具箱/项目服务.py:328`） | 1 份（本包 3 条能力） | **收口**：口径漂移面 5 处 → 1 处 |
| 调用方接入步骤 | 每个调用方要么复制代码、要么只能经 MCP 工具箱（技能库 stdin/stdout 桥接） | 一次 `调用能力('测试支持库.…', 参数)`，网关/模块/技能/项目同一入口 | **更快**：MCP 桥接 + JSON 进出的中间层可去掉 |
| 失败面 | 任一实现改口径，另几处不动即静默漂移；典型：`_检出未解释跳过` 三处正则各写一遍 | 只有一份正则与判定顺序，改一处全平台生效 | **更稳** |
| 新增判定项成本 | 三处各加一遍（本轮新增「结构化跳过列表」「缓存假绿」就是模型：现状三处都没有） | 一处加，全平台生效 | **更稳** |
| 可回退 | — | 删除本包不影响任何既有调用点（当前无调用方），零回退风险 | **可回退** |
| 边界 | 白名单/判定与「执行」耦合在 MCP 工具箱里，技能脚本要靠 stdin 转手 | 准入/判定/计划与本包外的一切解耦；执行仍是别人的能力 | **边界更清晰** |
| 耗时实测 | `验证编排.py` 需子进程 + stdin/stdout JSON 两次序列化 | 纯函数调用，18 个用例整模块真实跑完 **0.098s**（含 2 次真跑 `python3.14 -m unittest` 子进程） | **更快** |

**结论：采用候选架构，把准入判定与结果判定收口到本包**，MCP 工具箱与技能库改为调用本能力（收口点见第七节，本轮不修改那两处代码——并发会话正在写 `技能库/`）。

**「不做」的结论（不做的同样是结论）**：

- 不新建「执行验证命令」能力——`系统核心支持库.进程管理.沙箱执行命令` 已覆盖，再建就是第二套执行腿（第 26 条）。
- 不给本包加 HTTP/账本/反馈门禁——那会把 3 条纯函数能力变成第四个 MCP 门禁副本（第 26/27 条）。
- 不把「静态跳过检查」合并进来——它扫源码 AST，本包判运行输出；两者输入域不同，强行合并只会造出一个「既读源码又读输出」的杂能力，违反第 27 条「原子能力精而不杂」。正确收口是**两者并存、口径表对齐**（第五节）。

## 五、新能力口径 vs 两处同语义实现的差异

| 判定项 | 本包（测试支持库） | `开发工具/测试体系门禁实现/跳过检查.py` | `技能库/技能/验证编排/scripts/验证编排.py`（与 `MCP工具箱/验证门禁.py` 同源） |
| --- | --- | --- | --- |
| 输入域 | 运行输出（退出码/stdout/stderr/命令/跳过列表）+ 路径扫描 | **源码 AST**（静态） | 运行输出（stdin JSON） |
| 未解释跳过的判据 | ① 输出有跳过标记且无解释；② **结构化 `跳过列表` 里有条目但 `原因` 为空/纯空白** | `skip/skipIf/skipUnless/skipTest/SkipTest` 缺理由实参或理由为空常量；**非常量表达式一律视为已解释**（防误报） | 输出有跳过标记且无解释（正则 `原因\|Skipped:\|reason=\|已解释\|skipped '\|skipped (`） |
| 零测试 | `no tests ran` / `ran 0 tests` / `未发现任何测试用例` / `零测试门禁失败`；精确测试模块无 `Ran N tests`/`N passed` 证据即按零测试阻断 | 不涉及（另有 `零测试检查.py`） | 同前四类；精确模块无证据即零测试 |
| 缓存假绿 | **新增判定**：精确模块命令 + 输出含缓存标记 + 无真实执行证据 → `缓存假绿` 阻断 | 不涉及 | 不涉及（无此判定，只落入零测试） |
| 导入失败当跳过 | **独立错误码** `导入失败当跳过`（跳过标记伴随 ImportError/ModuleNotFoundError） | 静态层只判「有没有理由」，不判理由内容 | 不区分，落 `未解释跳过` 或直接放行（有 `skipped ('` 即认为已解释） |
| 存在性校验 | `校验存在` 参数控制（默认校验，可关） | 不涉及 | **强制**校验模块文件/制品目录存在且不逃逸 |
| 通用拒绝规则 | 逐条同源：shell 元字符、`shell=`、绝对路径、`..`、可执行白名单、unittest 末段 `测试_`、HTML 并发 1–64 | 不涉及 | 同源（本包完全对齐，未放宽） |
| 输出形状 | 统一 `结果型`（成功/值/错误码），判定结论在 `值.判定` / `值.允许` | `list[dict]` 违规清单 | `{成功, 错误码, 消息}` |
| 判定失败语义 | 判定结论一律 `成功=真`，只有参数不合法才 `成功=假` | 只返回违规清单，不退出 | 不通过即 `成功=假` |

**已知的、故意保留的差异（不是缺陷）**：

1. 本包 `验证命令白名单` 的默认形态**不放宽**任何一条拒绝规则；`校验存在=假` 只用于产物外/纯函数判定（例如 538 能力全表的静态准入）。
2. 本包 `验证计划` 的扫描口径比 `MCP工具箱/项目服务.py:328 _验证计划` **更细**：MCP 按固定目录表映射到整个 `测试中心/<域>`；本包优先按目标目录精确扫描，扫不到测试文件时才按首段回退到 `测试中心/<首段>`（回退行为在真实调用中已复现：`支持库/后端/测试支持库` 回退到 `测试中心/支持库`，返回 45 条命令）。
3. 本包不做「精确测试关键词表」（MCP 里 `强制校验`/`传递闭包` 等 5 个关键词），因为它属于 MCP 会话约定而非通用判定；如需要，应由 MCP 侧在调用本能力后自行补充。
